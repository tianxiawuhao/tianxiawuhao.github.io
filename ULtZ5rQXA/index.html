k8s界面kubesphere安装

Posted on 2022-05-30，20 min read

在已有的 Kubernetes 集群上安装 KubeSphere 3.2.1，Kubernetes 版本必须为 1.19.x、1.20.x、1.21.x 或 1.22.x（1.22 为实验性支持）。版本不匹配是安装失败最常见的原因，动手前先用 kubectl version --short 确认服务端版本（Server Version 一行）。

KubeSphere 3.x 各版本与 Kubernetes 的兼容关系如下，可按集群版本选择安装包（版本仍在演进，以官方文档为准）：

KubeSphere支持的 Kubernetes说明
3.0.x1.15.x – 1.18.x已停止维护
3.1.x1.17.x – 1.20.x开始支持多集群
3.2.x1.19.x – 1.22.x1.22 为实验性支持，本文使用的版本
3.3.x1.20.x – 1.24.x支持 Kubernetes 1.24
3.4.x1.21.x – 1.26.x3.x 系列最后一个版本

KubeSphere 4.x 改为 LuBan 架构（按需安装扩展组件），不再使用本文的 ks-installer 方式，安装方法不通用。

除版本兼容外，安装前还需要满足以下前置条件：

  • 集群至少有 1 个 master 和 1 个可调度节点，建议 4 核 8 GB 以上（最小化安装大约需要 6 GB 可用内存）；
  • 已存在默认 StorageClass：KubeSphere 的 Redis、OpenLDAP、MinIO、Prometheus 等组件都要申请 PVC，否则 Pod 会一直 Pending；
  • 有可用的 metrics-server（3.x 的 HPA 和部分监控页面依赖它），或在安装时打开 metrics_server.enabled；
  • 所有节点时间同步正常（chronyd/ntpd），否则 etcd 选主与证书校验会异常；
  • 节点能拉取 Docker Hub、GitHub 上的镜像，离线环境需先导入镜像并配置 local_registry；
  • 执行 kubectl 的账号具备 cluster-admin 权限。

下图给出 KubeSphere 的分层结构：控制面组件、可插拔组件与底层 Kubernetes 集群之间的关系。

1 搭建 NFS 作为默认 SC（主节点作为服务器，主节点操作）

KubeSphere 安装过程需要动态供应 PVC，所以先把 NFS 做成集群的默认 StorageClass。NFS 方案简单、足够用于测试；生产环境建议改用 Ceph RBD、OpenEBS 等具备多副本能力的存储。本节命令在 master 节点执行。

1.1 配置NFS服务器

yum install -y nfs-utils rpcbind  && echo "/nfs *(insecure,rw,sync,no_root_squash)" > /etc/exports

说明：/nfs *(insecure,rw,sync,no_root_squash) 对所有网段开放且不压缩 root 权限，只适合内网测试；生产建议限定网段并收敛权限，例如 /nfs 192.168.40.0/24(rw,sync,no_root_squash)，改完执行 exportfs -r 重新加载导出列表。

1.2 创建nfs服务器目录

mkdir -p /nfs

1.3 启动rpcbind,nfs服务命令

systemctl restart rpcbind && systemctl enable rpcbind
systemctl restart nfs-server && systemctl enable nfs-server

1.4 检查配置是否生效

exportfs -r
exportfs

1.5 测试Pod直接挂载NFS了（主节点操作）

1.5.1 在opt目录下创建一个nginx.yaml的文件

vi nginx.yaml

1.5.2 写入以下的命令

apiVersion: v1
kind: Pod
metadata:
  name: vol-nfs
  namespace: default
spec:
  volumes:
  - name: html
    nfs:
      path: /nfs   
      server: 192.168.40.131 #自己的nfs服务器地址
  containers:
  - name: myapp
    image: nginx
    volumeMounts:
    - name: html
      mountPath: /usr/share/nginx/html/

1.5.3 应用该yaml的pod服务

kubectl apply -f nginx.yaml

1.5.4 检查该 pod 是否正常运行

kubectl get pod

kubectl get pods -A

这里需要注意的是，必须等所有的状态为 Running 才能进行下一步操作。

2 搭建NFS-Client（node节点操作）

这一步只用于验证节点能否访问 NFS 共享，并不是安装 KubeSphere 的必需步骤——动态供应由集群内的 nfs-client-provisioner 完成，它自己会挂载 NFS。下面的命令在 node 节点执行。

NFS 服务端至少要放行 111（rpcbind）与 2049（nfsd）的 TCP/UDP；mountd、rquotad、statd 在 CentOS 7 上默认使用随机端口，先用 rpcinfo -p 192.168.40.131 查出实际端口再放行，否则客户端 showmount 会一直超时。

2.1 安装客户端工具

yum install -y nfs-utils rpcbind
showmount -e 192.168.40.131

该IP地址是master的IP地址

2.2 创建同步文件夹

mkdir /nfs/data/

2.3 将客户端的/nfs/data和/nfs/做同步（node节点操作）

mount -t nfs 192.168.40.131:/nfs/ /nfs/data/

192.168.40.131：是nfs的服务器的地址，这里是master的IP地址。

3 设置动态供应

3.1 创建provisioner（NFS环境前面已经搭好）

字段名称 填入内容 备注
名称 nfs-storage 自定义存储类名称
NFS Server 192.168.40.131 NFS服务的IP地址
NFS Path /nfs NFS服务所共享的路径

3.1.1 先创建授权（master节点操作）

vim nfs-rbac.yaml  #在opt目录下

新建内容如下：

---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: nfs-provisioner
---
kind: ClusterRole
apiVersion: rbac.authorization.k8s.io/v1
metadata:
   name: nfs-provisioner-runner
rules:
   -  apiGroups: [""]
      resources: ["persistentvolumes"]
      verbs: ["get", "list", "watch", "create", "delete"]
   -  apiGroups: [""]
      resources: ["persistentvolumeclaims"]
      verbs: ["get", "list", "watch", "update"]
   -  apiGroups: ["storage.k8s.io"]
      resources: ["storageclasses"]
      verbs: ["get", "list", "watch"]
   -  apiGroups: [""]
      resources: ["events"]
      verbs: ["watch", "create", "update", "patch"]
   -  apiGroups: [""]
      resources: ["services", "endpoints"]
      verbs: ["get","create","list", "watch","update"]
   -  apiGroups: ["extensions"]
      resources: ["podsecuritypolicies"]
      resourceNames: ["nfs-provisioner"]
      verbs: ["use"]
---
kind: ClusterRoleBinding
apiVersion: rbac.authorization.k8s.io/v1
metadata:
  name: run-nfs-provisioner
subjects:
  - kind: ServiceAccount
    name: nfs-provisioner
    namespace: default
roleRef:
  kind: ClusterRole
  name: nfs-provisioner-runner
  apiGroup: rbac.authorization.k8s.io
---
kind: Deployment
apiVersion: apps/v1
metadata:
   name: nfs-client-provisioner
spec:
   replicas: 1
   strategy:
     type: Recreate
   selector:
     matchLabels:
        app: nfs-client-provisioner
   template:
      metadata:
         labels:
            app: nfs-client-provisioner
      spec:
         serviceAccount: nfs-provisioner
         containers:
            -  name: nfs-client-provisioner
               image: lizhenliang/nfs-client-provisioner
               volumeMounts:
                 -  name: nfs-client-root
                    mountPath:  /persistentvolumes
               env:
                 -  name: PROVISIONER_NAME
                    value: storage.pri/nfs
                 -  name: NFS_SERVER
                    value: 192.168.40.131
                 -  name: NFS_PATH
                    value: /nfs
         volumes:
           - name: nfs-client-root
             nfs:
               server: 192.168.40.131
               path: /nfs

这个镜像中volume的mountPath默认为/persistentvolumes，不能修改，否则运行时会报错。IP 必须填写自己 master 节点的 IP 地址。

3.1.2 执行创建nfs的yaml文件信息

kubectl apply -f nfs-rbac.yaml

3.1.3 如果发现 pod 有问题，想删除 pod 并重新执行 kubectl apply -f nfs-rbac.yaml 的话，可以参照这个博客文档：

https://blog.csdn.net/qq_43542988/article/details/101277263?utm_medium=distribute.pc_relevant_t0.none-task-blog-BlogCommendFromMachineLearnPai2-1.channel_param&depth_1-utm_source=distribute.pc_relevant_t0.none-task-blog-BlogCommendFromMachineLearnPai2-1.channel_param

3.1.4 查看pod的状态信息

kubectl get pods -A
# 如果报错：查看报错信息，这个命令：
kubectl describe pod xxx -n kube-system

注意：provisioner: storage.pri/nfs 必须与 Deployment 中 PROVISIONER_NAME 的值完全一致，否则 StorageClass 会一直处于 no-provisioner 状态，PVC 无法绑定。

3.1.5 创建storageclass（master节点操作）

vim storageclass-nfs.yaml
 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: storage-nfs
provisioner: storage.pri/nfs
reclaimPolicy: Delete

3.1.6 应用storageclass-nfs.yaml文件

kubectl apply -f storageclass-nfs.yaml

3.1.7 修改默认的驱动

kubectl patch storageclass storage-nfs -p '{"metadata": {"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'

kubectl get sc

vim metrics-server.yaml

  service:
    name: metrics-server
    namespace: kube-system

  insecureSkipTLSVerify: true
  groupPriorityMinimum: 100
  versionPriority: 100
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: metrics-server
  namespace: kube-system
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: metrics-server
  namespace: kube-system
  labels:
    k8s-app: metrics-server
spec:
  selector:
    matchLabels:
      k8s-app: metrics-server
  template:
    metadata:
      name: metrics-server
      labels:
        k8s-app: metrics-server
    spec:
      serviceAccountName: metrics-server
      volumes:
      # mount in tmp so we can safely use from-scratch images and/or read-only containers
      - name: tmp-dir
        emptyDir: {}
      containers:
      - name: metrics-server
        image: registry.k8s.io/metrics-server/metrics-server:v0.6.1
        imagePullPolicy: IfNotPresent
        args:
          - --cert-dir=/tmp
          - --secure-port=4443
          - --kubelet-insecure-tls
          - --kubelet-preferred-address-types=InternalIP,ExternalIP,Hostname
        ports:
        - name: main-port
          containerPort: 4443
          protocol: TCP
        securityContext:
          readOnlyRootFilesystem: true
          runAsNonRoot: true
          runAsUser: 1000
        volumeMounts:
        - name: tmp-dir
          mountPath: /tmp
      nodeSelector:
        kubernetes.io/os: linux
        kubernetes.io/arch: "amd64"
---
apiVersion: v1
kind: Service
metadata:
  name: metrics-server
  namespace: kube-system
  labels:
    kubernetes.io/name: "Metrics-server"
    kubernetes.io/cluster-service: "true"
spec:
  selector:
    k8s-app: metrics-server
  ports:
  - port: 443
    protocol: TCP
    targetPort: main-port
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: system:metrics-server
rules:
- apiGroups:
  - ""
  resources:
  - pods
  - nodes
  - nodes/stats
  - namespaces
  - configmaps
  verbs:
  - get
  - list
  - watch
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: system:metrics-server
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: system:metrics-server
subjects:
- kind: ServiceAccount
  name: metrics-server
  namespace: kube-system

版本说明：原文使用 mirrorgooglecontainers/metrics-server-amd64:v0.3.6，该镜像仓库已停止维护，v0.3.6 在 Kubernetes 1.20+ 上常报 unable to fully scrape metrics 或证书错误。上面已改为官方镜像 registry.k8s.io/metrics-server/metrics-server:v0.6.1（v0.6.x 支持 Kubernetes 1.19–1.24）。另外注意：KubeSphere 3.2.1 自身也能部署 metrics-server（spec.metrics_server.enabled: true），两者只需保留一个，重复部署会因 APIService v1beta1.metrics.k8s.io 冲突导致 kubectl top 报错。

4.3 应用该文件pod

kubectl apply -f metrics-server.yaml

4.4 查看部署的应用信息状态

kubectl get pod -A

4.5 查看系统的监控状态

kubectl top nodes
kubectl top pods -A

如果提示 error: Metrics API not available 或 metrics not available yet，说明 metrics-server 刚启动、还没采集到数据，等 30~60 秒后重试即可。若长时间不可用，按下面三步排查：

kubectl -n kube-system get pod -l k8s-app=metrics-server
kubectl -n kube-system logs deploy/metrics-server --tail=50
kubectl get apiservice v1beta1.metrics.k8s.io -o yaml

到这里，KubeSphere 3.2.1 的前置环境（默认 StorageClass + metrics-server）就准备完成了。

5.4 可插拔组件：装什么、占多少资源

KubeSphere 采用可插拔架构，上面的 cluster-configuration.yaml 就是组件总开关。安装完成后依然可以随时开关：直接编辑 ClusterConfiguration 资源，ks-installer 会监听到变化并自动部署或清理对应组件，不需要重装 KubeSphere。

kubectl -n kubesphere-system edit cc ks-installer
# 例如把 logging.enabled 改成 true，保存退出后观察安装日志
kubectl -n kubesphere-system logs deploy/ks-installer -f --tail=100
组件配置项默认依赖 / 资源
监控（Prometheus + Grafana）monitoring开启需要默认 SC 存放 TSDB，约 2 核 4 GB
日志（Elasticsearch + Fluent Bit）logging关闭需要 SC 和足够磁盘，约 57 m CPU / 2.76 GB 内存
事件 / 审计events / auditing关闭依赖内置或外部 Elasticsearch
告警 / 通知alerting关闭依赖 Thanos Ruler 与通知渠道，约 0.1 核 100 MiB
DevOps（Jenkins）devops关闭需要 8 GiB PVC，约 0.47 核 8.6 GB
服务网格（Istio）servicemesh关闭约 0.3 核 300 MiB
应用商店（OpenPitrix）openpitrix关闭依赖 MySQL、MinIO 等
网络策略 / Pod IP 池network.networkpolicy、network.ippool关闭需要 Calico 等支持 NetworkPolicy 的 CNI
KubeEdge 边缘节点kubeedge关闭必须填写 cloudHub.advertiseAddress，否则 CloudCore 无法工作

建议按需开启：全开对 4 核 8 GB 的测试集群几乎必然 OOM 或 PVC 不足。开启 logging、events、auditing 前先确认 Elasticsearch 的存储与内存。另外 logging.containerruntime 要按集群实际容器运行时填写（docker 或 containerd），填错会导致采集不到容器日志。

5.5 离线（air-gap）安装

内网环境访问不了 Docker Hub 与 charts.kubesphere.io，需要先把镜像和制品拿到本地，再用 local_registry 让 ks-installer 从私有仓库拉取镜像。

方式一：已有 Kubernetes 集群，只用 ks-installer 安装 KubeSphere。

# 1. 联网机器上拉取并导出镜像（完整镜像清单见 ks-installer 对应版本的 images 列表）
docker pull kubesphere/ks-installer:v3.2.1
docker pull kubesphere/ks-apiserver:v3.2.1
# ks-console、ks-controller-manager、minio、redis、openldap、prometheus 系列、elasticsearch 等按需拉取
docker save -o ks-images.tar kubesphere/ks-installer:v3.2.1 kubesphere/ks-apiserver:v3.2.1

# 2. 导入内网私有仓库
docker load -i ks-images.tar
docker tag kubesphere/ks-apiserver:v3.2.1 registry.example.com/kubesphere/ks-apiserver:v3.2.1
docker push registry.example.com/kubesphere/ks-apiserver:v3.2.1

然后在 cluster-configuration.yaml 里把 spec.local_registry 指向私有仓库地址（不要带 https://），再应用该文件，ks-installer 会自动为所有组件镜像加上这个前缀。

spec:
  local_registry: "registry.example.com/kubesphere"

如果私有仓库使用自签证书，还要给节点上的 Docker/containerd 配置 insecure-registries 或导入 CA 证书，否则 ks-installer 会报 x509: certificate signed by unknown authority。方式二是用 KubeKey 导出制品，见下一节。

5.6 用 KubeKey 最小化安装（一体化部署 Kubernetes + KubeSphere）

如果还没有 Kubernetes 集群，或者希望 k8s 与 KubeSphere 一次装好，用官方工具 KubeKey（kk）最省事：它会自动处理容器运行时、CNI、默认 StorageClass 等前置条件。

# 1. 下载 KubeKey（版本号以官方最新为准）
curl -sfL https://get-kk.kubesphere.io | VERSION=v3.0.0 sh -
chmod +x kk

# 2. 生成配置文件：Kubernetes v1.22.12 + KubeSphere v3.2.1
./kk create config --with-kubernetes v1.22.12 --with-kubesphere v3.2.1 -f config-sample.yaml

# 3. 按实际环境编辑 config-sample.yaml（hosts、network、storage、registry）
vi config-sample.yaml

# 4. 一键安装（加 -v 输出详细日志）
./kk create cluster -f config-sample.yaml

也可以不生成配置文件，直接单机试装：

./kk create cluster --with-kubernetes v1.22.12 --with-kubesphere v3.2.1

几点提醒：

  • config-sample.yaml 中的 spec.hosts 要写清每台机器的 IP、用户名、密码或密钥，多节点时用 roleGroups 区分 etcd/master/worker；
  • KubeKey 默认会给集群装一个 local 卷的默认 StorageClass，生产上建议换成 Ceph RBD 等支持多副本的存储；
  • 离线安装用 ./kk artifact export -m manifest-sample.yaml -o kubesphere-artifact.tar.gz 导出制品，拷进内网后 ./kk artifact image push -f config-sample.yaml -a kubesphere-artifact.tar.gz 推送镜像，再 ./kk create cluster -f config-sample.yaml -a kubesphere-artifact.tar.gz 安装；
  • 安装结束后 KubeKey 会打印控制台地址与默认账号 admin / P@88w0rd。

5.7 多集群与企业空间（租户）

上面安装的是单集群模式（multicluster.clusterRole: none）。KubeSphere 从 3.1 起支持多集群管理，由 Host 集群统一纳管多个 Member 集群，切换方式就是改 clusterRole：

spec:
  multicluster:
    clusterRole: host    # host（主集群，承载多集群控制面）| member（成员集群）| none（单集群）

把 host 集群改为 host 后，ks-installer 会部署多集群控制面（tower、agent 等）。随后在控制台「集群管理 → 添加集群」下载成员集群的部署文件，在成员集群执行即可接入。接入时注意：

  • 成员集群的 authentication.jwtSecret 需与 host 集群保持一致；
  • host 集群的 ks-apiserver 地址必须能被成员集群访问（通常通过代理或 NodePort 暴露）；
  • 所有集群时间同步，否则 agent 证书校验失败，成员集群会一直显示「异常」。
kubectl -n kubesphere-system get cm kubesphere-config -o yaml | grep -v "apiVersion" | grep jwtSecret

租户模型是「企业空间（Workspace）→ 项目（Namespace）」两级：企业空间是资源与权限的隔离单元，项目对应 Kubernetes 命名空间；用户与角色（platform-admin、workspace-admin、project-admin 等）按层级授权。多集群场景下，一个企业空间可以跨集群分配项目，实现「一个租户、多集群资源」。

5.8 常见安装失败排查

现象常见原因处理办法
ks-installer Pod 一直 ImagePullBackOff / ErrImagePull拉不到 Docker Hub 镜像，或离线环境未导入镜像配置 local_registry，或把镜像导入内网仓库；用 kubectl -n kubesphere-system describe pod <pod> 看具体报错
apply 时报 no matches for kind ClusterConfiguration先应用了 cluster-configuration.yaml，CRD 还没创建先 kubectl apply -f kubesphere-installer.yaml，再应用 cluster-configuration.yaml
日志停在 PVC Pending / no persistent volumes available没有默认 StorageClass，或 NFS 不可写kubectl get sc 确认 default 标记；用 kubectl get pvc -A 与 describe pvc 定位；检查 NFS 导出与权限
控制台 http://IP:30880 打不开ks-console 未就绪、NodePort 未生效、防火墙或端口占用kubectl -n kubesphere-system get svc ks-console 确认 30880 映射；放行端口；查看 console Pod 是否 Running
开启 etcd 监控后安装失败缺少 etcd 证书 Secret先在 kubesphere-monitoring-system 创建 etcd-certs Secret，再打开 etcd.monitoring
提示 chart 拉取失败或超时访问不了 charts.kubesphere.io 与镜像仓库改用离线方式导入制品，或配置镜像代理
节点 NotReady、etcd 频繁选主节点时间不同步、内核参数或磁盘 IO 异常启用 chronyd；检查 dmesg 与磁盘；必要时调整 vm.swappiness、关闭 swap
提示 Kubernetes 版本不受支持集群版本不在支持矩阵内对照文首兼容表升级集群，或改用对应的 KubeSphere 版本
组件开启后 Pod 一直 Pending / OOMKilled节点资源不足扩容节点，或按需关闭 logging、devops 等高消耗组件

排查顺序建议：先看 kubectl -n kubesphere-system get pod，再看 kubectl -n kubesphere-system logs deploy/ks-installer --tail=200，最后看具体组件 Pod 的 describe 与日志。多数问题都能在这三步内定位。

安装完成后访问控制台：

http://192.168.40.131:30880/login
帐号：admin
密码：P@88w0rd

KubeSphere 3.2.1 的默认账号是 admin、默认密码是 P@88w0rd，首次登录会强制修改密码。如果控制台打不开，先确认 ks-console Pod 是 Running、Service 是否已分配 30880 端口。

5.10 Harbor 目录下重新启动 Harbor

安装 KubeSphere 的过程中会重启 Docker/containerd，用 docker-compose 启动的 Harbor 容器可能没跟着起来，导致后续 push/pull 镜像失败。进入 Harbor 安装目录（例如 /opt/harbor）重启即可：

cd /opt/harbor    # 换成自己的 Harbor 安装目录
docker compose down
docker compose up -d
# Harbor 2.x 使用 Compose V2 插件 docker compose；老环境仍是 docker-compose up -d
