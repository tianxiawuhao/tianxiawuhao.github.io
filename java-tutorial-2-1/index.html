2.1 数据库与 SQL 入门

Posted on 2024-07-18，6 min read

前面几章从 Java 语法一路读到了 JDBC，但代码里的数据始终活不过一次进程重启。ArrayList 存在内存里，程序一退出就没了；就算写进文件，想按条件筛选、并发修改也很快会失控。要让数据真正“留下来并被多人同时用”，就需要数据库。数据库是后端开发的地基，也是 Java 面试绕不开的一环。本章讲清楚三件事：数据在关系型数据库里怎么组织、表结构怎么用 DDL 建出来、数据怎么用 DML 增删改。读完本章，应当能在 MySQL 里从零建出一个带约束的业务库，并看懂别人写的建表语句。本章适合已掌握 Java 基础语法、准备动手写第一个持久化程序的读者。

一、为什么需要数据库：关系模型

把数据存成文件，问题会一个接一个冒出来：两个人同时写同一个文件会互相覆盖；想按年龄过滤，得把文件一整行一整行地读一遍；某天字段从 5 个变成 6 个，历史数据全要手工改。数据库管理系统（DBMS）正是为统一解决这些问题而出现的软件。它对外提供四类能力：数据定义（定义库和表的结构）、数据操纵（增删改查）、运行管理（并发、权限、完整性、一致性）、建立与维护（转储恢复、性能监控）。

最常见的数据库是关系型数据库，它用二维表组织数据，代表产品有 MySQL、Oracle、SQL Server、PostgreSQL。另一类是非关系型数据库（NoSQL），如 Redis、HBase、MongoDB，它们采用键值、列族、文档等模型，牺牲一部分关系约束，换取水平扩展能力。本章以 MySQL 为例，其余关系型数据库的概念完全相通。

关系模型只有几个术语，但层次必须分清：库（database）是表的集合；表（table）是同一类实体的集合；表中的一行（row）是一条记录，一列（column）是一个字段属性。同一列在所有行里含义一致，并且要有确定的数据类型。为了让每一行都能被唯一指认，需要指定主键（primary key）；两张表需要关联时，从表里指向主表主键的那一列称为外键（foreign key）。

SQL（Structured Query Language）是操作关系型数据库的标准语言。各数据库的方言虽然有差异，但按作用可以把语句分成四类，图 2 是它们的职责划分。

二、DDL：建库、建表、加约束

DDL（Data Definition Language，数据定义语言）负责定义和修改结构，核心命令是 CREATE、ALTER、DROP、TRUNCATE。它的特点是执行即自动提交，没有“反悔”的机会，因此在生产库上执行前务必确认库名、表名。

2.1 建库与字符集

建库时一定要显式指定字符集。MySQL 5.7 的默认字符集还是 latin1，一旦按默认建库，中文就会变成乱码；MySQL 8.0 才把默认字符集改成 utf8mb4。现状补充：5.7 已于 2023 年 10 月结束官方支持（EOL），新项目直接用 8.0 或 8.4 LTS 即可，8.4 同样默认 utf8mb4（具体支持周期以官方文档为准）。

-- 建库：字符集用 utf8mb4，不建议写 utf8
CREATE DATABASE shop
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_general_ci;

-- 切换当前库，之后不用再写库名前缀
USE shop;

-- 查看建库语句，确认字符集是否生效
SHOW CREATE DATABASE shop;

-- 查看当前连接与服务器的字符集变量
SHOW VARIABLES LIKE 'character%';

这里有个流传很广的坑：MySQL 里的 utf8 不是完整的 UTF-8，它每个字符最多只存 3 字节，而真正的 UTF-8 里常用的 emoji 占 4 字节，存进去会直接报错或被截断。MySQL 在 2010 年补充发布了 utf8mb4（mb4 = most bytes 4）来支持完整 UTF-8。从 MySQL 8.0.28 起，utf8 已被标记为 utf8mb3 的别名并逐步废弃，所以新库一律写 utf8mb4。

2.2 建表：数据类型与常用约束

建表语句由列定义组成，每一列要给出“列名 + 数据类型 + 约束”。常用类型按用途记三类就够了：整数用 INT、BIGINT；小数和金额用 DECIMAL(m,d)，不用 FLOAT/DOUBLE，它们有精度误差；字符串用 VARCHAR(n) 存变长、CHAR(n) 存定长，时间用 DATETIME 或 TIMESTAMP。

CREATE TABLE user (
  id          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
  name        VARCHAR(20)  NOT NULL                COMMENT '姓名',
  age         INT          DEFAULT NULL            COMMENT '年龄',
  email       VARCHAR(64)  DEFAULT NULL            COMMENT '邮箱',
  status      TINYINT      NOT NULL DEFAULT 1      COMMENT '1 正常 0 禁用',
  created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_user_email (email)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COMMENT = '用户表';

约束是数据库对数据的最后一道防线。常用的几类如下表，写入违反约束的数据时数据库会直接报错，而不是默默存下脏数据。

约束作用典型写法
NOT NULL该列不允许为 NULLname VARCHAR(20) NOT NULL
DEFAULT不传值时使用的默认值status TINYINT DEFAULT 1
PRIMARY KEY主键，唯一且非空，一张表只能有一个PRIMARY KEY (id)
UNIQUE唯一索引，值不允许重复UNIQUE KEY uk_email (email)
AUTO_INCREMENT整型自增，插入时可不指定id BIGINT AUTO_INCREMENT
FOREIGN KEY外键，取值必须存在于主表主键中FOREIGN KEY (user_id) REFERENCES user(id)

外键是把两张表“接”起来的关键，图 3 展示了它的引用关系。

CREATE TABLE orders (
  id       BIGINT NOT NULL AUTO_INCREMENT,
  user_id  BIGINT NOT NULL COMMENT '外键：指向 user.id',
  amount   DECIMAL(10,2) NOT NULL DEFAULT 0.00,
  PRIMARY KEY (id),
  KEY idx_user_id (user_id),
  CONSTRAINT fk_orders_user FOREIGN KEY (user_id) REFERENCES user (id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

加了外键以后，如果再插入一条 user_id 为 99、而 user 表里并没有 99 号用户的记录，数据库会直接拒绝。这挡住了脏数据，但每次写入都要回主表校验，高并发场景会成为瓶颈。所以大型互联网系统常把外键约束关掉，改由应用层保证一致性——这是工程取舍，不是外键本身有问题。

2.3 改结构与删表

表建好后需求变了，用 ALTER TABLE 增删改列；确认不再需要的表才用 DROP TABLE。

-- 加一列；末尾加 FIRST / AFTER 列名可控制位置
ALTER TABLE user ADD COLUMN phone VARCHAR(20) DEFAULT NULL AFTER email;

-- 改列类型（会重建数据，大表慎用）
ALTER TABLE user MODIFY COLUMN name VARCHAR(50) NOT NULL;

-- 删列、删表
ALTER TABLE user DROP COLUMN phone;
DROP TABLE IF EXISTS orders;

-- 清空表：TRUNCATE 是 DDL，删除全部行并重置自增，无法回滚
TRUNCATE TABLE orders;

三、DML：数据的增删改

DML（Data Manipulation Language，数据操纵语言）操作的是表中的行，核心是 INSERT、UPDATE、DELETE。与 DDL 最大的区别是：DML 在事务里执行，出错可以 ROLLBACK 回滚。

3.1 INSERT：插入数据

-- 推荐写法：显式列出列名，表结构变更时更不容易出错
INSERT INTO user (name, age, email) VALUES ('张三', 28, 'zhangsan@example.com');

-- 一次插入多行，比多条单行 INSERT 快得多
INSERT INTO user (name, age, email) VALUES
  ('李四', 31, 'lisi@example.com'),
  ('王五', 25, NULL);

-- id 是自增列不用给值；status、created_at 走默认值
INSERT INTO orders (user_id, amount) VALUES (1, 99.50);

要注意三点：字符串和日期必须用单引号；双引号在 MySQL 中默认也表示字符串，但不标准，而且 MySQL 8.0 在 ANSI_QUOTES 模式下双引号表示标识符。带 NOT NULL 且无默认值的列不能省略；存在 UNIQUE 约束时，重复插入会报 Duplicate entry 错误。

3.2 UPDATE 与 DELETE：务必带 WHERE

-- 只改一行：用主键定位
UPDATE user SET age = 29 WHERE id = 1;

-- 先查后改：写 UPDATE 前先用同样的 WHERE 跑一次 SELECT，确认影响范围
SELECT * FROM user WHERE status = 0;

-- 删数据同样必须带条件
DELETE FROM user WHERE id = 3;

WHERE 是整个 DML 里代价最高的单词。漏写它，UPDATE user SET status = 0 会把全表用户禁用，DELETE FROM user 会清空整张表（后者在 MySQL 里还是一次一行的 DML，可以回滚，但生产事故往往来不及）。养成两个习惯：动手前先用相同条件 SELECT COUNT(*) 确认行数；把 sql_safe_updates 打开，让不带 WHERE 的 UPDATE/DELETE 直接报错。

3.3 串起来跑一遍

SELECT u.name, u.age, o.amount
FROM user u
JOIN orders o ON o.user_id = u.id
WHERE u.status = 1
ORDER BY o.amount DESC;

这条查询用 JOIN 按外键把两张表接起来，正是外键设计的意义所在。查询属于 DQL，下一章会专门展开，这里只要看到 DDL 定下的结构如何决定了 DML 和查询的写法就够了。

四、常见坑与小结

最后集中列几个新手最容易踩的坑。字符集：建库不写 utf8mb4，中文和 emoji 迟早出问题。字符集的继承：建库时定了字符集，建表若不写 DEFAULT CHARSET，表会继承库的字符集；但若显式写了 utf8 就会覆盖掉，需要 SHOW CREATE TABLE 复查。主键选择：用自增 BIGINT 做与业务无关的主键，不要拿手机号、身份证号当主键，因为它们会变，而且通常不该暴露。金额类型：金额一律用 DECIMAL，用 DOUBLE 累加会出现 0.01 级别的误差。无 WHERE 的 UPDATE/DELETE：生产事故排行榜第一名。

本章从关系模型讲到落地的 SQL：数据库用二维表组织数据，主键唯一标识一行，外键把表连起来；DDL 负责把库、表、约束这些结构定义出来，一经执行即生效且自动提交；DML 负责往表里写数据，处于事务保护之下。掌握这三件事，就具备了读懂任何一份建表脚本的能力，也就能为后面的 JDBC 编程和 JPA 映射打下地基。下一章专门讲多表查询与子查询。
