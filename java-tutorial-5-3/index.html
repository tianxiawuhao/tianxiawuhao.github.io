开发工具与环境配置

Posted on 2026-09-19，8 min read

很多人的 Java 之路是这么断掉的：JDK 装了三个版本却不知道 javac 用的是哪个，Maven 下载依赖卡在 0%，Git 提交上去一堆 .iml、.idea，代码里中文注释变成乱码。这些问题都不难，但每一个都要花掉半小时。这一章把「开发工具与环境配置」这件事一次做对：以 IntelliJ IDEA 为核心，讲清 JDK 与编码的基线配置、Maven 的仓库与依赖管理、Git 集成的基本工作流，以及真正提高效率的快捷键与技巧。适合刚装好 IDEA、准备写第一个工程化项目的读者，也适合工作几年但环境一直「能跑就行」的读者。

一、开工前先把基线定死：JDK 与编码

IDEA 的配置分两层，理解这一点能省掉后面大量的「为什么改了没用」：IDE Settings 对所有项目生效，Project Settings（Project Structure，快捷键 Ctrl+Alt+Shift+S）只对当前项目生效。原则是：与个人习惯相关的（主题、快捷键、行号）改全局；与项目相关的（SDK、编码、编译级别）改项目，并且尽量让配置跟着项目走，这样换电脑、换同事都不用口头交接。

1. 指定 SDK，而不是「系统装了什么就用什么」

打开 File → Project Structure → Project，把 Project SDK 指向你要用的 JDK，Language level 与之匹配。IDE 设置里的 SDK 列表在 File → Project Structure → SDKs 维护，同一台机器可以并存 JDK 8/11/17，只要每个项目明确指定，就不会互相干扰。命令行里用下面两条命令确认「系统默认」到底是什么：

# 确认当前 PATH 上的 JDK 版本与厂商
java -version
javac -version

# 查看 JAVA_HOME 指向哪里（macOS / Linux 用 echo，Windows 用 echo %JAVA_HOME%）
echo "$JAVA_HOME"

如果 java -version 和 javac -version 输出的版本不一致，说明 PATH 里混进了另一个 JDK，务必先修好再往下走——编译器和运行时版本不一致，后面会遇到各种莫名其妙的 UnsupportedClassVersionError。

2. 编码统一 UTF-8，并顺手关掉两个「坑」

在 Settings → Editor → File Encodings 里把 Global Encoding、Project Encoding 都设为 UTF-8，再把 Properties Files 的默认编码也设为 UTF-8，并勾选 Transparent native-to-ascii conversion。最后一项是 .properties 文件不乱码的关键。它让文件在 IDE 里显示中文；而在磁盘上，文件仍以 \uXXXX 转义形式保存，符合 java.util.Properties 按 ISO-8859-1 读取的历史约定。

再花两分钟做几处「减负」设置，它们能明显降低日常干扰：

  • Settings → Editor → General → Auto Import：勾选 Optimize imports on the fly 与 Add unambiguous imports on the fly。写完类名自动补 import，没用的 import 也会被删掉。
  • Settings → Editor → General → Code Completion：把 Match case 设为 None，输入小写也能提示大写类名。
  • Settings → Editor → General → Appearance：勾选 Show line numbers。Editor → General → Editor Tabs 再勾选 Mark modified tabs with asterisk。IDEA 默认自动保存，没有星号就分不清哪些文件改过。
  • Settings → Editor → File Types：在 Ignore files and folders 中加入 *.iml;.idea;，项目视图立刻清爽。
  • Settings → Keymap：如果代码补全的 Ctrl+Space 与输入法切换冲突，在 Main menu → Code → Completion 里把 Basic / SmartType 改成自己顺手的键。

插件不要贪多。Settings → Plugins 里只留当前项目真正用到的插件（如 Maven、Git、Database、Lombok 等）。不认识的插件尽量禁用，让 IDE 启动更快、占用更少。配置调好后用 File → Manage IDE Settings → Export Settings 导出一份 zip 备份，换机器时用 Import Settings 一步还原。

二、Maven：把「仓库」和「依赖」两件事配好

Maven 是主流的 Java 项目构建与依赖管理工具，它用一份 pom.xml 描述项目坐标、依赖和构建插件，并按约定目录（src/main/java、src/main/resources、src/test/java）组织代码。国内使用 Maven 的第一个障碍通常是中央仓库太慢，解决办法是在 settings.xml 中配置镜像：

<settings xmlns="http://maven.apache.org/SETTINGS/1.0.0">
  <mirrors>
    <mirror>
      <id>aliyun</id>
      <mirrorOf>central</mirrorOf>
      <name>阿里云公共仓库</name>
      <url>https://maven.aliyun.com/repository/public</url>
    </mirror>
  </mirrors>
</settings>

这份文件建议放到 ~/.m2/settings.xml（Windows 为 C:\Users\你的用户名\.m2\settings.xml）。放到这里就等于给「当前用户」设了默认配置，不必在每个项目里勾 Override 去指定路径。IDEA 侧的对应位置是 Settings → Build, Execution, Deployment → Build Tools → Maven，确认 Maven home path、User settings file、Local repository 三项与实际一致；配置优先级由低到高为：Maven 安装目录的全局 settings、用户目录 settings、命令行或 IDE 显式指定，后写的覆盖先写的。

依赖范围（scope）决定「打进包里还是不打」

在 pom.xml 里写依赖时，scope 是最常被忽略却最容易出事的一项。compile 是默认值，参与编译、测试、运行并被打包。provided（典型是 Servlet API）编译期可见、运行期由容器提供，不打进包；runtime 编译时不需要、运行时需要（如 JDBC 驱动）；test 只在测试代码中可见（如 JUnit），不会污染主程序。多模块项目里，版本号应统一由父 POM 的 <dependencyManagement> 管理，子模块只写 groupId 和 artifactId，避免同一依赖出现多个版本。

<dependencies>
  <dependency>
    <groupId>junit</groupId>
    <artifactId>junit</artifactId>
    <version>4.13.2</version>
    <scope>test</scope>
  </dependency>

  <dependency>
    <groupId>javax.servlet</groupId>
    <artifactId>javax.servlet-api</artifactId>
    <version>4.0.1</version>
    <scope>provided</scope>
  </dependency>
</dependencies>

导入已有 Maven 项目时用 File → Open 直接选中 pom.xml（IDEA 2018 之后已不再需要「Import Module」向导），IDEA 会自动识别为 Maven 工程并开始解析依赖。常见坑有三个：依赖红线不消失时先点 Maven 面板的 Reload All Maven Projects；仍失败就删掉本地仓库中对应目录下的 *.lastUpdated 文件重下；src/main/resources 下的配置文件不生效，通常是没执行 Maven → Lifecycle → compile/resources 或 classes 输出目录被改过。

三、Git 集成：从关联到推送的完整闭环

IDEA 把 Git 做成了「不用离开编辑器」的体验，可以完全用菜单和快捷键完成日常操作。第一步是让项目交由 Git 管理：VCS → Enable Version Control Integration…，选择 Git 并确定。这一步等价于在项目根目录执行 git init，此后本地仓库就是项目目录本身，IDEA 会为新增、修改、未跟踪的文件着色。

接下来的日常流程是「提交 → 推送」：VCS → Commit…（Ctrl+K）勾选要提交的文件、填写提交信息；想一步到位就点 Commit and Push。首次推送需要指定远程地址：VCS → Git → Push…，在 Define remote 里填入仓库 URL，认证后完成推送。把别人的修改拉回来用 Git → Repository → Pull…。这里必须分清两个动作：clone 是「无中生有」，本地还没有项目，从远程完整复制一份（File → New → Project from Version Control 或 Get from VCS）；pull 是「锦上添花」，本地已有项目，只把远程的新提交合并进来。另外，push 之前必须先 commit，否则会提示 no commits selected。

还有两条纪律，能避免绝大多数「仓库被搞脏」的事故。一是提交前先写好 .gitignore，把 target/、*.iml、.idea/ 排除掉——它们是 IDE 与构建产物，不该进版本库；二是要意识到 IDEA 默认自动保存文件，只要改过就会出现在提交列表里，所以提交前务必逐项确认。若仓库托管在 GitHub，也可以在 VCS → Import into Version Control → Share Project on GitHub 里直接创建并关联仓库；但现在的 GitHub 已不支持账号密码推送，认证请用 Personal Access Token（个人访问令牌）或 SSH 密钥，而不是老教程里的登录密码。

# 命令行等价操作（IDEA 里的菜单只是这些命令的封装）
git init                       # 对应 Enable Version Control Integration
git add -A && git commit -m "feat: 完成环境配置"   # 对应 Commit
git remote add origin git@github.com:user/demo.git
git push -u origin main        # 对应 Push，-u 记住上游分支
git pull                       # 对应 Pull，拉取并合并远程更新

四、效率：真正值得记住的那几个快捷键

快捷键不用背全，先掌握下面这十几个，它们覆盖了写代码时 90% 的高频动作。

  • 查找定位：Shift+Shift 全局搜索一切；Ctrl+N 找类、Ctrl+Shift+N 找文件、Ctrl+Alt+Shift+N 找符号。Ctrl+Shift+F 全项目按内容搜索；Alt+F7 查找某个方法/变量的所有引用，重构前必用；Ctrl+E 打开最近文件。
  • 编辑与重构：Alt+Enter 是「万能修复」，红色报错、黄色警告、未实现接口、缺 import 都能在这里一键解决；Ctrl+Alt+L 格式化代码；Ctrl+Alt+O 清理无用 import；Shift+F6 安全重命名（类、方法、变量乃至注释一起改）；Ctrl+Alt+M 抽方法、Ctrl+Alt+V 抽变量；Alt+Insert 生成构造器与 getter/setter。
  • 代码模板：IDEA 内置的 Live Template 已覆盖 psvm（public static void main）、sout（System.out.println）、iter 等。在 Settings → Editor → Live Templates 里可以新建自己的模板组与缩写，把团队统一的类注释、日志语句做成模板，比复制粘贴可靠得多。
  • 调试与运行：F8 单步跳过、F7 单步进入、Shift+F8 跳出；Alt+F8 在断点处求值任意表达式；F9 继续执行到下一个断点；Ctrl+F8 设置/取消断点。
  • 剪贴板与比较：Ctrl+Shift+V 调出复制历史，数量可在 Settings → Editor → General 的 Maximum number of contents to keep in clipboard 调整。选中两个文件后 Ctrl+D 可比较差异，右键还有「与编辑器比较」「与剪贴板比较」。

顺带提醒两个容易记错的键位。在 IntelliJ IDEA 的默认键位中，格式化代码是 Ctrl+Alt+L，某些 Eclipse 键位方案里才是 Ctrl+Shift+F。Ctrl+D 是「复制当前行」，默认并没有「删除一行」的快捷键，需要自己在 Keymap 里为 Delete Line 绑定。

五、几个必须提前知道的坑

  • IDEA 面板里改了配置但不起作用：先确认改的是 IDE 级还是项目级设置——Project SDK、编译级别、编码这类都可能在项目级被单独覆盖。
  • Maven 依赖下载慢或失败：优先检查镜像与本地仓库路径，而不是反复点刷新；代理环境下还需要在 settings.xml 里配置 <proxies>。
  • 中文乱码：.properties 文件记得开 Transparent native-to-ascii conversion；源码与资源文件统一 UTF-8。编译时如仍报错，可在 Maven 中显式设置 project.build.sourceEncoding 为 UTF-8。
  • IDEA 越用越卡：先在 Settings → Appearance & Behavior → Memory Settings 里适当调大编译器堆内存，并禁用不用的插件；旧教程里用 -XX:PermSize、-XX:MaxPermSize 调优的方法只适用于 JDK 8 之前，JDK 8 起永久代已被元空间取代，这两个参数在现代 JDK 上无效甚至会导致 JVM 启动失败。
  • 热部署不是万能的：JRebel 之类的工具能省去重启，但它需要付费授权，并且修改方法签名、注解、Spring 配置等结构性变化时仍需重启，不要把它当成「改完就一定生效」的保证。

六、小结

环境配置的目标不是把 IDE 的每个开关都研究一遍，而是让「写代码 → 构建 → 提交」这条链路不出现意外。落到实处只有四件事：把 JDK 与编码在项目级定死，避免版本与乱码问题；把 Maven 的 settings.xml 和本地仓库配好，让依赖可以被稳定解析；用 Git 完成 enable → commit → push 的闭环，并守住 .gitignore 的底线；再记住 Alt+Enter、Alt+F7、Ctrl+Shift+V 这几个高频键。做完这些，就可以把精力真正放回代码本身了。
