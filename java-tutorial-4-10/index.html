Spring Boot Web 开发

Posted on 2026-09-19，8 min read

上一章我们把 Spring Boot 应用跑了起来，也写通了第一个接口。但真实项目里的 Web 层远不止「能返回 JSON」：客户端传上来的参数需要校验，出错时要给前端一份可读的错误结构，未登录的请求要挡在 Controller 之前，用户上传的图片要安全落盘，上线后还要能从外部看到应用的健康状况。这一章就围绕这五件事展开，把 Spring MVC 在 Spring Boot 下的 Web 开发骨架讲完整。适合已经会写 @RestController 和 @RequestMapping、准备进入生产级开发的读者。

一、请求参数校验：让非法数据根本进不了业务代码

最原始的做法是在方法体里逐字段写 if (name == null) return "参数错误";，字段一多就变成一屏的防御式代码，而且与业务逻辑混在一起。Spring 的方案是把约束声明在模型上，由框架在参数绑定阶段完成校验。

校验注解来自 Bean Validation 规范（JSR-380）。注意版本差异：Spring Boot 2.x 使用 javax.validation.constraints 包，需引入 spring-boot-starter-validation；Spring Boot 3.x 改用 jakarta.validation.constraints 包。网上大量老教程只写 @NotBlank 却不说包名，直接拷到 3.x 项目会编译不过。最常用的注解有 @NotNull、@NotBlank（字符串非空且去空格后长度大于 0）、@Size(min,max)、@Min/@Max、@Email、@Pattern(regexp=...)。

public record UserCreateRequest(
        @NotBlank(message = "用户名不能为空")
        @Size(min = 3, max = 20, message = "用户名长度需在 3-20 之间")
        String username,

        @NotBlank(message = "邮箱不能为空")
        @Email(message = "邮箱格式不正确")
        String email,

        @Min(value = 18, message = "年龄不能小于 18")
        @Max(value = 120, message = "年龄不能大于 120")
        int age) {
}

@RestController
@RequestMapping("/api/users")
public class UserController {

    @PostMapping
    public ResponseEntity<String> create(@Valid @RequestBody UserCreateRequest req) {
        // 走到这里时，req 一定已经通过校验
        return ResponseEntity.ok("created: " + req.username());
    }
}

关键点是 @Valid（jakarta.validation.Valid）：没有它，所有约束注解都只是注释。如果参数是查询串或表单字段，要改用 @Validated 加在类上，方法参数上的 @NotBlank 等才会生效；@Valid 只对对象级联校验起作用。

校验失败时框架抛出 MethodArgumentNotValidException。你可以在方法签名里追加一个 BindingResult 参数自己处理，但更推荐交给下一节的全局异常处理器统一返回。

二、全局异常处理：一份稳定的错误响应契约

如果每个 Controller 都自己 catch 异常，前端拿到的错误格式就会五花八门。@RestControllerAdvice 是 @ControllerAdvice 与 @ResponseBody 的组合，它把异常处理逻辑集中到一个类里，对所有 Controller 生效。

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Map<String, Object> handleInvalid(MethodArgumentNotValidException ex) {
        Map<String, String> fields = new LinkedHashMap<>();
        for (FieldError err : ex.getBindingResult().getFieldErrors()) {
            fields.put(err.getField(), err.getDefaultMessage());
        }
        Map<String, Object> body = new LinkedHashMap<>();
        body.put("code", 400);
        body.put("message", "参数校验失败");
        body.put("fields", fields);
        return body;
    }

    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public Map<String, Object> handleOther(Exception ex) {
        // 生产环境不要直接把 ex.getMessage() 返回给客户端
        return Map.of("code", 500, "message", "服务器内部错误");
    }
}

两个容易踩的坑。第一，异常处理器有优先级：匹配类型越具体的方法越优先，所以 Exception.class 的兜底方法不会抢走 MethodArgumentNotValidException；但如果你把兜底写成 Throwable.class，同样需要小心它会把所有异常都吞掉，掩盖真实问题。第二，不要把异常堆栈信息原样返回，那会泄露类名、SQL、文件路径。Spring Boot 3 还内置了 ProblemDetail（RFC 7807 风格），可以直接 return ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "...")，配合 spring.mvc.problemdetails.enabled=true 使用。

对于文件上传超限、404 这类异常，往往发生在进入 Controller 之前，@ExceptionHandler 不保证能捕获。上传超限请专门处理 MaxUploadSizeExceededException，或设置 server.error.path 指向自定义错误页；这类边界建议用 MockMvc 写测试确认，而不是凭猜测。

三、拦截器：把登录校验从 Controller 里抽出来

很多人会把 Apache Struts2 的 Interceptor 与 Spring MVC 的拦截器混为一谈。两者名字相同但毫无继承关系：Struts2 的拦截器是 Action 调用链上的组件，只能拦截 Action；Spring MVC 的拦截器是 org.springframework.web.servlet.HandlerInterceptor，作用在 DispatcherServlet 找到处理器之后、执行处理器之前。此外，Spring MVC 拦截器运行在 Spring 容器中，天然可以使用依赖注入，而 Servlet Filter 由容器管理、在更外层生效。

public class LoginInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response,
                             Object handler) throws Exception {
        if (request.getSession().getAttribute("loginUser") == null) {
            response.sendRedirect("/login");
            return false;   // 返回 false，请求不会到达 Controller
        }
        return true;
    }
}

@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LoginInterceptor())
                .addPathPatterns("/**")
                .excludePathPatterns("/login", "/css/**", "/js/**", "/images/**");
    }
}

三个方法要理解清楚：preHandle 返回 false 即中断后续流程；postHandle 在 Controller 执行完、视图渲染前调用（REST 接口返回 JSON 时几乎没有使用场景）；afterCompletion 在请求完全结束后调用，适合清理 ThreadLocal，而且只有 preHandle 返回过 true 才会被调用。

网上流传「Spring Boot 2.x 默认拦截所有静态资源，需要手动配置 addResourceHandlers 放行」的说法，这在多数场景下不成立：默认的静态资源映射由 WebMvcAutoConfiguration 提供，只要 excludePathPatterns 排除了 /static/**、/webjars/** 等路径即可。真正被拦截的是你自己声明的 /**。若遇到静态资源 404，先确认是否误用了 @EnableWebMvc——它会关闭 Spring Boot 的 MVC 自动配置，需要你自行补全静态资源映射。

四、文件上传：MultipartFile 的正确用法

Spring Boot 默认启用 MultipartAutoConfiguration，无需在 XML 中声明 MultipartResolver。Controller 里用 MultipartFile 接收文件即可，表单需要设置 enctype="multipart/form-data"。

@RestController
public class UploadController {

    private final Path uploadDir = Paths.get("uploads").toAbsolutePath().normalize();

    @PostMapping("/api/upload")
    public ResponseEntity<String> upload(@RequestPart("file") MultipartFile file)
            throws IOException {
        if (file.isEmpty()) {
            return ResponseEntity.badRequest().body("文件为空");
        }
        String original = StringUtils.cleanPath(file.getOriginalFilename());
        if (original.contains("..") || !original.matches("(?i).+\\.(png|jpg|jpeg|gif)$")) {
            return ResponseEntity.badRequest().body("只允许上传图片");
        }
        Files.createDirectories(uploadDir);
        Path target = uploadDir.resolve(UUID.randomUUID() + getExtension(original));
        file.transferTo(target);   // Spring Boot 2.x 起不再需要手写流复制
        return ResponseEntity.ok("saved: " + target.getFileName());
    }

    private String getExtension(String name) {
        int i = name.lastIndexOf('.');
        return i < 0 ? "" : name.substring(i);
    }
}

安全要点必须强调：绝不能信任 getOriginalFilename()，它完全由客户端提供，攻击者可以传入 ../../etc/passwd 造成路径穿越。上面的做法是先 cleanPath、再拒绝含 .. 的名字、最后用 UUID 重命名落盘，原始文件名只用于展示。getContentType() 同样来自客户端请求头，只能作为快速过滤，不能当作安全校验——判断真实类型需要读取文件头魔数。

保存路径不要写在项目源码目录里，应通过 spring.servlet.multipart.location 或自定义配置项指向外部目录。同时记得配置体积上限：spring.servlet.multipart.max-file-size=10MB、spring.servlet.multipart.max-request-size=10MB，超过限制会抛 MaxUploadSizeExceededException。需要给静态资源目录提供外链访问时，可用 addResourceHandlers 把 /uploads/** 映射到该磁盘目录，避免把用户上传内容混入打包产物。

五、Actuator：上线后的第一双眼睛

应用部署之后，你至少需要回答三个问题：进程还活着吗？依赖的数据库通不通？当前配置到底是什么？引入 spring-boot-starter-actuator 就能以 HTTP 端点形式拿到这些信息。

management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics   # 默认只暴露 health
  endpoint:
    health:
      show-details: when_authorized
info:
  app:
    name: java-tutorial-demo
    version: 1.0.0

访问 http://localhost:8080/actuator/health 会得到 {"status":"UP"}，它由多个 HealthIndicator 聚合而成（数据源、Redis、磁盘空间等）。info 端点默认返回空对象，需要在 management.info.env.enabled=true 时才展示上面的 info.* 配置。

安全提醒：/actuator 下有不少敏感端点。env、configprops 可能暴露数据库密码，heapdump 能拿到完整内存快照，shutdown 可以远程关闭应用（且默认未启用）。因此只 expose 必要的端点，并通过 Spring Security 限制访问，或把 management.server.port 设置为仅内网可达的独立端口。一个常见误区是认为「Actuator 默认什么都不暴露很安全」——2.x 起默认确实只暴露 health，但一旦为了排障写了 include: "*" 又忘了收回，风险就完全敞开了。

小结

本章串起了 Spring Boot Web 层的五块能力：用 Bean Validation 把校验前置到参数绑定阶段，用 @RestControllerAdvice 统一错误响应契约，用 HandlerInterceptor 承载登录与权限这类横切逻辑，用 MultipartFile 配合白名单与重命名安全地接收文件，用 Actuator 给线上应用装上可观测的入口。它们共同的思路是「把与业务无关的关注点从 Controller 中移出去」。下一步建议把校验失败、上传超限、拦截器放行这三条路径各写一个 MockMvc 测试——这些边界条件靠肉眼审查很难发现，测试才是它们真正的归宿。
