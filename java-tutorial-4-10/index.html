Spring Boot Web 开发

Posted on 2026-09-19，7 min read

上一章我们把 Spring Boot 应用跑了起来，也写通了第一个接口。但真实项目的 Web 层远不止「能返回 JSON」：客户端传来的参数要校验，出错时要给出可读的错误结构，未登录的请求要挡在 Controller 之前，上传的文件要安全落盘，上线后还要能从外部看到应用的健康状况。本章围绕这五件事，讲清 Spring Boot 下 Spring MVC 的 Web 层骨架，适合已会写 @RestController 的读者。

一、请求参数校验：非法数据进不了业务代码

原始做法是在方法体里逐字段判断，字段一多就是一屏防御式代码。Spring 的方案是把约束声明在模型上，由框架在参数绑定阶段完成校验。常用注解有 @NotNull、@NotBlank、@Size(min,max)、@Min/@Max、@Email、@Pattern，它们来自 Bean Validation 规范（JSR-380）。注意版本差异：Spring Boot 2.x 用 javax.validation.constraints 包，3.x 改用 jakarta.validation.constraints，且都需引入 spring-boot-starter-validation。老教程常只写注解不说包名，拷到 3.x 项目会编译不过。

public record UserCreateRequest(
        @NotBlank(message = "用户名不能为空")
        @Size(min = 3, max = 20, message = "用户名长度需在 3-20 之间")
        String username,

        @NotBlank(message = "邮箱不能为空")
        @Email(message = "邮箱格式不正确")
        String email,

        @Min(value = 18, message = "年龄不能小于 18")
        int age) {
}

@RestController
@RequestMapping("/api/users")
public class UserController {

    @PostMapping
    public ResponseEntity<String> create(@Valid @RequestBody UserCreateRequest req) {
        // 走到这里时，req 一定已经通过校验
        return ResponseEntity.ok("created: " + req.username());
    }
}

关键点是 @Valid：没有它，所有约束注解都只是注释。若参数来自查询串或表单而不是请求体，应在类上加 @Validated，方法参数上的约束才会生效。校验失败时框架抛出 MethodArgumentNotValidException，可追加 BindingResult 自行处理，更推荐交给全局异常处理器。

二、全局异常处理：一份稳定的错误响应契约

若每个 Controller 各自 catch 异常，前端拿到的错误格式就会五花八门。@RestControllerAdvice 相当于 @ControllerAdvice 加 @ResponseBody，把异常处理集中到一处并对所有 Controller 生效。

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Map<String, Object> handleInvalid(MethodArgumentNotValidException ex) {
        Map<String, String> fields = new LinkedHashMap<>();
        for (FieldError err : ex.getBindingResult().getFieldErrors()) {
            fields.put(err.getField(), err.getDefaultMessage());
        }
        Map<String, Object> body = new LinkedHashMap<>();
        body.put("code", 400);
        body.put("message", "参数校验失败");
        body.put("fields", fields);
        return body;
    }

    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public Map<String, Object> handleOther(Exception ex) {
        // 生产环境不要直接把 ex.getMessage() 返回给客户端
        return Map.of("code", 500, "message", "服务器内部错误");
    }
}

两个坑。其一，异常处理器有优先级：匹配类型越具体的方法越优先，所以兜底方法不会抢走校验异常，但兜底范围越宽越容易掩盖真实问题。其二，不要把异常消息与堆栈原样返回，那会泄露类名、SQL 与文件路径。另外，上传超限、404 往往发生在进入 Controller 之前，@ExceptionHandler 不保证捕获，超限需单独处理 MaxUploadSizeExceededException。

三、拦截器：把登录校验从 Controller 里抽出来

很多人把 Struts2 的 Interceptor 与 Spring MVC 拦截器混为一谈，两者名字相同却毫无继承关系：Struts2 的拦截器是 Action 调用链上的组件，只能拦截 Action；Spring MVC 用的是 org.springframework.web.servlet.HandlerInterceptor，在 DispatcherServlet 找到处理器之后、执行之前生效，且是 Spring 容器组件，可直接依赖注入。它比 Servlet Filter 更靠内层。

public class LoginInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response,
                             Object handler) throws Exception {
        if (request.getSession().getAttribute("loginUser") == null) {
            response.sendRedirect("/login");
            return false;   // 返回 false，请求不会到达 Controller
        }
        return true;
    }
}

@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LoginInterceptor())
                .addPathPatterns("/**")
                .excludePathPatterns("/login", "/css/**", "/js/**", "/images/**");
    }
}

三个方法要分清：preHandle 返回 false 即中断后续流程；postHandle 在 Controller 执行完、视图渲染前调用，纯 JSON 接口几乎用不到；afterCompletion 在请求结束后调用，适合清理 ThreadLocal，且只有 preHandle 返回过 true 才执行。「Spring Boot 2.x 默认拦截所有静态资源」的说法并不成立：默认映射由 WebMvcAutoConfiguration 提供，被拦住的是你声明的 /**，排除相关路径即可。若静态资源 404，先确认是否误用了 @EnableWebMvc。

四、文件上传：MultipartFile 的正确用法

Spring Boot 默认启用 MultipartAutoConfiguration，不必声明 MultipartResolver，表单设置 enctype="multipart/form-data" 即可。

@RestController
public class UploadController {

    private final Path uploadDir = Paths.get("uploads").toAbsolutePath().normalize();

    @PostMapping("/api/upload")
    public ResponseEntity<String> upload(@RequestPart("file") MultipartFile file)
            throws IOException {
        if (file.isEmpty()) {
            return ResponseEntity.badRequest().body("文件为空");
        }
        String original = StringUtils.cleanPath(file.getOriginalFilename());
        if (original.contains("..") || !original.matches("(?i).+\\.(png|jpg|jpeg|gif)$")) {
            return ResponseEntity.badRequest().body("只允许上传图片");
        }
        Files.createDirectories(uploadDir);
        Path target = uploadDir.resolve(UUID.randomUUID() + getExtension(original));
        file.transferTo(target);   // 无需手写输入输出流复制
        return ResponseEntity.ok("saved: " + target.getFileName());
    }

    private String getExtension(String name) {
        int i = name.lastIndexOf('.');
        return i < 0 ? "" : name.substring(i);
    }
}

安全要点：不能信任 getOriginalFilename()，攻击者可传 ../../etc/passwd 造成路径穿越。上面的做法是先 cleanPath、再拒绝含 .. 的名字、最后用 UUID 重命名落盘，原名只用于展示。getContentType() 同样来自请求头，只能作快速过滤。multipart.location 应指向源码目录之外的路径，并用 max-file-size 限制体积。

五、Actuator：上线后的第一双眼睛

应用上线后至少要回答三个问题：进程还活着吗？依赖的数据库通不通？当前配置是什么？引入 spring-boot-starter-actuator 即可通过 HTTP 端点获取。

management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics   # 默认只暴露 health
  endpoint:
    health:
      show-details: when_authorized
info:
  app:
    name: java-tutorial-demo
    version: 1.0.0

访问 /actuator/health 返回 {"status":"UP"}，它由多个 HealthIndicator 聚合而成（数据源、磁盘空间等）；info 端点默认返回空对象，需开启 management.info.env.enabled=true 才展示 info.* 配置。安全提醒：env 与 configprops 可能暴露数据库密码，heapdump 能拿到内存快照，shutdown 可远程关闭应用，因此只 expose 必要端点，并用 Spring Security 或内网端口 management.server.port 保护。默认只暴露 health 不等于安全，为排障写了 include: "*" 又忘了收回，风险就完全敞开。

小结

本章串起 Web 层的五块能力：用 Bean Validation 把校验前置到参数绑定阶段，用 @RestControllerAdvice 统一错误契约，用 HandlerInterceptor 承载登录与权限这类横切逻辑，用 MultipartFile 配合白名单与重命名安全接收文件，用 Actuator 装上可观测入口。共同思路是把与业务无关的关注点移出 Controller。建议为校验失败、上传超限、拦截器放行各写一个 MockMvc 测试，这些边界靠肉眼审查很难发现。
