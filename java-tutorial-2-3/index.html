索引、事务与锁

Posted on 2026-09-19，9 min read

前面几章把 SQL 和表设计过了一遍，但“能查出结果”和“查得又快、并发还不出错”是两件事：一条没走索引的查询可能老老实实扫过千万行；一次没包在事务里的转账，可能在扣款成功后、入账前被打断。本章把 InnoDB 的三块核心机制串成一条线——索引与执行计划决定“读得快不快”，事务与隔离级别决定“并发读得对不对”，锁与死锁则是隔离级别必须付出的代价。本章适合已经会写基本 SQL、准备把数据库用进真实项目的读者。

索引：把全表扫描换成按图索骥

索引是数据库为某一列（或几列）额外维护的、排好序的数据结构。没有索引时，WHERE name = 'tom' 只能从第一行读到最后一行逐行比对，这叫全表扫描；有了索引，数据库可以先在这份有序结构里定位到目标，再直接取出那一行。代价是索引本身占磁盘，并且每次写入都要同步维护它，所以索引不是越多越好。

B+ 树与聚簇索引

InnoDB 的索引实现是 B+ 树：非叶子节点只存键值，用来做导航；所有真实数据都放在叶子节点，并且叶子之间用链表串起来。这个设计带来两个直接好处。一是树的层数很少，千万级数据通常 3～4 层就能覆盖，因此一次查找只需要几次磁盘读；二是叶子有序且相连，BETWEEN、>、ORDER BY 这类范围需求可以顺着叶子链表扫过去，不必回根节点重来。

InnoDB 的表本身就是一棵 B+ 树，称为聚簇索引（clustered index）：它的叶子节点存放的是整行数据，而键就是主键。所以“按主键查一行”是最快的路径，一次树查找就拿到整行。如果建表时没有主键，InnoDB 会退而选择第一个非空唯一索引，再没有就自己生成一个隐藏的 6 字节 row_id 当键。这也是“每张表都该显式定义主键”的真正原因：主键不只是约束，它还决定了数据在磁盘上怎么排。

回表与覆盖索引

在聚簇索引之上另外建的索引（比如给 name 建的）叫二级索引或辅助索引。它的叶子节点不可能再存一整行，只存索引列 + 主键值。于是 SELECT * FROM t_user WHERE name = 'tom' 要查两次：先在 idx_name 里找到 tom 对应的主键，再拿这个主键回聚簇索引取整行，这一步就叫回表。

如果查询需要的列全都已经在索引里，就不必回表了，这种索引叫覆盖索引。例如 SELECT id, name FROM t_user WHERE name = 'tom'，id 和 name 都在 idx_name 里，一次查找即可返回，执行计划的 Extra 会显示 Using index。这是最划算的优化之一：不用新建任何东西，只把 SELECT * 改成需要的列就能生效。

组合索引、最左前缀与索引失效

在 (a, b, c) 上建一个组合索引，等价于同时拥有 (a)、(a, b)、(a, b, c) 三个索引，这就是最左前缀原则。所以 WHERE b = ? 用不上它，WHERE a = ? AND c = ? 只能用上 a 这一段；而且一旦遇到范围查询，它右边的列就断了——WHERE a = 1 AND b > 2 AND c = 3 中 c 用不到索引。建索引时把区分度最高的列放最左边，也是这个道理。

-- 为 name 建索引后，下面两条语句的差别就是回表
CREATE INDEX idx_name ON t_user (name);

-- 覆盖索引：id、name 都在 idx_name 里，Extra 显示 Using index
EXPLAIN SELECT id, name FROM t_user WHERE name = 'tom';

-- 取 * 需要回表，Extra 里不会出现 Using index
EXPLAIN SELECT * FROM t_user WHERE name = 'tom';
常见坑：索引明明建了却用不上。典型写法有四类：在列上做函数或运算（WHERE DATE(create_time) = '2024-01-01'、WHERE id + 1 = 10）；隐式类型转换（字符串列用数字去比，WHERE phone = 13800000000）；以 % 开头的模糊查询（LIKE '%tom'）；用 OR 连接了一个没有索引的列。正确写法是把运算挪到常量侧，例如 WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02'。

用 EXPLAIN 看真实执行计划

索引有没有生效，不能靠猜，要在语句前加 EXPLAIN，让优化器把执行计划打印出来。MySQL 8.0 还支持 EXPLAIN ANALYZE（8.0.18 起），它会真正执行语句并给出各步骤的实际耗时，比估算值更可信。日常最该看的是四列：

  • type：访问类型，性能由好到差大致是 system → const → eq_ref → ref → range → index → ALL。看到 ALL 就意味着全表扫描，这是首要消灭的目标。
  • key：优化器实际选用的索引；为 NULL 说明一个索引都没用上。
  • rows：预估需要扫描的行数，是估算值，用于判断量级而非精确计数。
  • Extra：最重要的补充信息。Using index 表示覆盖索引；Using filesort 表示额外的排序（ORDER BY 没走上索引）；Using temporary 表示用了临时表（常见于 GROUP BY）；Using where 表示在存储引擎取回数据后还要再过滤一遍。

优化的目标很朴素：把 type=ALL 变成 ref 或 range，把 Using filesort 和 Using temporary 尽量消掉。如果 rows 依然很大，就要回头看索引设计，而不是先怀疑机器性能。

事务与 ACID：一组操作要么全成、要么全败

事务是逻辑上的一组操作，它们要么全部生效，要么全部撤销，不允许只做一半。最经典的例子是转账：从 A 账户扣 100 和向 B 账户加 100 必须同生共死，否则钱就凭空消失或多出来了。

START TRANSACTION;                                    -- 也可以写 BEGIN
UPDATE account SET money = money - 100 WHERE id = 1;
UPDATE account SET money = money + 100 WHERE id = 2;
COMMIT;                                               -- 两条更新一起生效
-- 中途出错则执行 ROLLBACK，回到 START TRANSACTION 之前的状态

MySQL 默认 autocommit = 1，也就是说每条 SQL 自成一个事务、执行完立刻提交，所以不加 START TRANSACTION 时看不到“撤销”的效果。Oracle 则相反，默认不自动提交，必须显式 COMMIT；但要注意 Oracle 的 DDL（如 CREATE、TRUNCATE）会隐式提交，不要把它当成事务的一部分。在 Java 里，事务由 Connection 控制：setAutoCommit(false) 开启事务，commit() 提交，rollback() 回滚。

import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import javax.sql.DataSource;

public class AccountService {

    private final DataSource dataSource;              // 例如 HikariDataSource

    public AccountService(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    public void transfer(long fromId, long toId, BigDecimal amount) throws SQLException {
        Connection conn = null;
        try {
            conn = dataSource.getConnection();
            conn.setAutoCommit(false);                // 开启事务
            try (PreparedStatement out = conn.prepareStatement(
                         "UPDATE account SET money = money - ? WHERE id = ?");
                 PreparedStatement in = conn.prepareStatement(
                         "UPDATE account SET money = money + ? WHERE id = ?")) {
                out.setBigDecimal(1, amount);
                out.setLong(2, fromId);
                out.executeUpdate();

                in.setBigDecimal(1, amount);
                in.setLong(2, toId);
                in.executeUpdate();
            }
            conn.commit();                            // 两条更新一起生效
        } catch (SQLException e) {
            if (conn != null) {
                conn.rollback();                      // 任一步失败，整体撤销
            }
            throw e;
        } finally {
            if (conn != null) {
                conn.setAutoCommit(true);             // 归还连接池前恢复默认
                conn.close();
            }
        }
    }
}

事务必须具备四个特性，合称 ACID：

  • 原子性（Atomicity）：事务是不可分割的工作单位，里面的操作要么都发生，要么都不发生。
  • 一致性（Consistency）：事务执行前后数据库都必须处于一致状态。转账前后两个账户金额之和不变，就是一致性的直观体现。
  • 隔离性（Isolation）：并发事务之间互不干扰，各自看到自己该看到的数据。它由隔离级别和锁共同实现，也正是本章后半部分的主题。
  • 持久性（Durability）：一旦提交，变更就永久保存，即使随后断电、宕机，重启后数据依然能恢复到提交后的状态（InnoDB 靠 redo log 保证）。

写代码时有个高频坑：rollback() 和 commit() 都必须在同一个 Connection 上。如果 Service 开了事务，而 DAO 从连接池里各自取了一条新连接去执行 SQL，那么这些语句根本不在同一个事务里，回滚也不会生效。正确做法是把连接从 Service 传到 DAO，或者用 ThreadLocal 把当前线程的连接缓存起来统一取用——这也是 Spring 的 @Transactional 背后做的事。

隔离级别：并发问题的四档取舍

实现完全隔离最彻底的手段是让事务排队执行，但那等于放弃并发。SQL 标准因此定义了四种隔离级别，让使用者在“正确性”和“并发性能”之间选一档。要理解这四档，先看并发不加约束时会出现什么：

  • 脏读：读到了另一个事务还未提交的数据。对方一旦回滚，你读到的东西从未存在过，属于最严重的问题。
  • 不可重复读：同一个事务内两次执行相同的查询，结果不一样，因为期间另一个事务提交了修改（典型是 UPDATE）。
  • 幻读：同一个事务内两次执行相同的范围查询，第二次多出或少了几行，因为期间另一个事务提交了插入或删除。

级别越低，能挡住的问题越少，但并发性能越好。实践中厂商只选了两档：MySQL 默认 REPEATABLE READ（可重复读），Oracle 默认 READ COMMITTED（读已提交）。查看和修改当前会话的隔离级别：

-- MySQL 8.0：变量名是 transaction_isolation
SELECT @@transaction_isolation;        -- 默认 REPEATABLE-READ
-- MySQL 5.7 及更早版本写 @@tx_isolation，8.0 已移除该名字

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- 可选值：READ UNCOMMITTED / READ COMMITTED / REPEATABLE READ / SERIALIZABLE
纠正一个常见说法：标准 SQL 里 REPEATABLE READ 只承诺挡住脏读和不可重复读，不承诺挡住幻读。但 InnoDB 在可重复读下用间隙锁（next-key lock）把范围内的间隙也锁住了，因此幻读在 MySQL 里基本复现不出来。这不是 MySQL 偷偷把幻读优化掉了，而是它加了锁。代价是锁的范围变大，更容易发生死锁，这也是下一节要讲的内容。

锁与死锁：隔离级别的实现代价

隔离级别不是口号，落地靠的是锁。InnoDB 支持行级锁，但有一个容易被忽略的前提：行锁是加在索引上的。如果 UPDATE 的 WHERE 条件没有走索引，InnoDB 只能锁住它扫描过的所有行，效果接近锁表，并发度直接掉下来。所以“更新语句尽量基于主键或唯一索引”不是风格建议，而是性能要求。

从粒度看，InnoDB 有共享锁（S 锁，读锁）和排他锁（X 锁，写锁）：普通的 SELECT 走 MVCC 快照读，不加锁；而 SELECT ... FOR UPDATE 是当前读，会加 X 锁，UPDATE、DELETE 则自动加 X 锁。这些锁都持有到事务结束才释放，所以事务越长，锁被占的时间越久，冲突概率越高。

-- 排他锁：一直持有到 COMMIT 或 ROLLBACK
START TRANSACTION;
SELECT * FROM account WHERE id = 1 FOR UPDATE;
COMMIT;

-- 死锁复现：两个会话按相反顺序更新同样的两行
-- 会话 A                                     -- 会话 B
START TRANSACTION;                            START TRANSACTION;
UPDATE account SET money = money - 1 WHERE id = 1;
                                              UPDATE account SET money = money - 1 WHERE id = 2;
UPDATE account SET money = money + 1 WHERE id = 2;   -- 等待 B 释放 id = 2
                                              UPDATE account SET money = money + 1 WHERE id = 1;  -- 等待 A，形成环路
-- InnoDB 检测到环路，回滚其中一方，另一方报错：
-- ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

死锁的本质是多个事务互相持有对方需要的锁，形成等待环路。InnoDB 不回避死锁，而是开启了死锁检测：一旦发现环路，就选择“代价较小”的那个事务回滚，把 1213 错误返回给客户端，让另一个事务继续。因此应用层捕获到这个异常后重试整个事务才是正确姿势，而不是把错误直接抛给用户。

减少死锁的几条硬规则：多个事务访问多张表时约定相同的加锁顺序；尽量在事务一开始就把需要的资源一次锁定，避免“边走边锁”；缩短事务，绝对不要在事务里做远程调用、发消息或等待用户输入；更新条件尽量落在主键或唯一索引上；读多写少、能接受不可重复读的业务可以把隔离级别降到 READ COMMITTED，因为 InnoDB 在 RC 下不使用间隙锁，死锁概率明显降低。排查时可执行 SHOW ENGINE INNODB STATUS 查看最近一次死锁详情，MySQL 8.0 还能查 performance_schema.data_lock_waits。

小结

索引与执行计划解决“读得快不快”：B+ 树让查找从全表扫描降到几次磁盘读，聚簇索引的叶子存整行，二级索引查非索引列要回表，覆盖索引则免掉第二次查找；EXPLAIN 的 type、key、rows、Extra 是判断索引是否生效的依据。事务与隔离级别解决“并发读得对不对”：ACID 保证一组操作全成或全败，四种隔离级别则是正确性与并发性能之间的取舍，MySQL 默认可重复读，Oracle 默认读已提交。锁与死锁是隔离的实现代价：InnoDB 的行锁加在索引上，走不到索引就退化成近似锁表，间隙锁挡住幻读的同时也让死锁更容易发生。实务上的顺序也很清晰——先用 EXPLAIN 把慢查询推进到 ref/range 并争取覆盖索引，再把事务写短、按固定顺序、基于主键更新，最后为死锁准备一次重试。
