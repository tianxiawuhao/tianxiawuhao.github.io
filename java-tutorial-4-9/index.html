Spring Boot 核心

Posted on 2026-09-19，9 min read

从 SSM 一路走来的读者大多有过这样的经历：pom.xml 里逐个挑选 jar 并祈祷它们版本兼容，web.xml 里注册 DispatcherServlet，再写一堆 XML 声明 Bean。Spring Boot 并没有给 Spring 增加多少新功能，它只是把「一个可运行的 Spring 应用该有的样子」固化成约定，再用自动配置把约定补齐。本章讲清四件事：起步依赖如何传递依赖、自动配置类如何被筛选并装配、配置文件里的值如何绑到对象上、以及 Profile 怎样让同一份代码跑在不同环境。适合已经能独立搭起 SSM 工程，却说不清「为什么只写一个 main 方法就能跑起来」的读者。

一、起步依赖：一个坐标换来一整套对齐的 jar

依赖管理是 Spring 工程里最耗时的环节：既要确定直接依赖，又要确定它们的传递依赖，版本一冲突就是运行期的 NoSuchMethodError。Spring Boot 的思路是把「某类功能所需的一组坐标」打包成 starter，并在父 POM 里统一锁定版本。一个最简的工程只需要两段声明：继承 spring-boot-starter-parent，再引入 spring-boot-starter-web。

<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.3.5</version>
    <relativePath/>   <!-- 从仓库解析，不在本地找父工程 -->
</parent>

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
        <!-- 不写 version：由父 POM 的 dependencyManagement 决定 -->
    </dependency>
</dependencies>

这里有个容易搞混的层次：spring-boot-starter-parent 自己的父 POM 才是 spring-boot-dependencies，真正把上百个库的版本写进 properties、并放进 dependencyManagement 与 pluginManagement 的是它。所以子模块引入 starter 时不必写 <version>；而 spring-boot-starter-web 本身几乎没有代码，它只是把 spring-web、spring-webmvc、spring-boot-starter-tomcat（内嵌 Tomcat）、Jackson 等坐标声明为自己的依赖，靠 Maven 的依赖传递「打包」给你。

实践要点：不要给已被父 POM 管理的依赖手动写版本，那会覆盖版本管理；确实要换版本，应改父 POM 暴露的 xxx.version 属性。版本提醒：上面的 3.3.5 只是示例，Boot 3.x 要求 Java 17 及以上，且坐标由 javax.* 迁到 jakarta.*；老资料里的 2.0.1.RELEASE 属 2018 年的版本，配置键名（如 server.context-path 已变为 server.servlet.context-path）与依赖坐标都不宜照抄。

二、自动配置：@SpringBootApplication 背后的装配链路

启动类上只有一个注解，但它是组合注解：@SpringBootConfiguration（本质是 @Configuration）、@ComponentScan（所以业务类必须放在启动类所在包或子包下）、以及真正的开关 @EnableAutoConfiguration。

@SpringBootApplication   // = @SpringBootConfiguration + @ComponentScan + @EnableAutoConfiguration
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

// 自动配置类的典型形态（以 ServletWebServerFactoryAutoConfiguration 为例，已简化）
@AutoConfiguration
@ConditionalOnWebApplication(type = ConditionalOnWebApplication.Type.SERVLET)
@ConditionalOnClass(Servlet.class)
@EnableConfigurationProperties(ServerProperties.class)
public class ServletWebServerFactoryAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean   // 用户自己定义了 ServletWebServerFactory 就让位
    public ServletWebServerFactory servletWebServerFactory(ServerProperties properties) {
        TomcatServletWebServerFactory factory = new TomcatServletWebServerFactory();
        factory.setPort(properties.getPort());   // server.port 就是这样生效的
        return factory;
    }
}

@EnableAutoConfiguration 通过 @Import(AutoConfigurationImportSelector.class) 在启动时读入一份「候选自动配置类」清单，再逐个用条件注解筛选，这就是所谓条件装配：

  • 清单来源在版本间变过。Boot 2.6 及以前是 META-INF/spring.factories 中 org.springframework.boot.autoconfigure.EnableAutoConfiguration 对应的值；2.7 起引入 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（2.7 两者兼容），3.0 起 spring.factories 中的该项已被移除。只讲 spring.factories 的老教程，在新版本里会找不到这个文件。
  • 条件注解决定「要不要生效」。@ConditionalOnClass / @ConditionalOnMissingClass 看类路径，@ConditionalOnBean / @ConditionalOnMissingBean 看容器里有没有同类型组件，@ConditionalOnProperty 看某个开关配置，@ConditionalOnWebApplication 看应用类型。任何一个条件不成立，整个配置类都不会注册。
  • 结论：「spring.factories 里的类都会被加载进容器」是常见误传。它们只是候选，必须同时满足条件才注册，且用户自己定义的 Bean 会优先。

排查自动配置是否生效，最快的手段是加 --debug 启动参数（或在配置里设 debug=true），控制台会打印自动配置报告，Positive matches / Negative matches 会直接告诉你哪个类生效、被哪个条件挡掉。至于某个键该怎么写，最可靠的依据是对应的 XxxProperties 类——例如 server.port 就封装在 ServerProperties 中。

三、配置绑定：@Value 与 @ConfigurationProperties

约定优于配置不等于不能配置。默认值写在 XxxProperties 类里，覆盖值写在 src/main/resources 下的 application.properties 或 application.yml 中。@Value("${person.name}") 逐个字段注入，写法直观，但只支持简单类型、不做松散绑定、也不便校验，字段一多就是重复劳动；@ConfigurationProperties(prefix = "person") 则按前缀批量绑定，支持松散绑定（person.first-name 能绑到 firstName，环境变量 PERSON_FIRST_NAME 同样有效）、复杂类型，还能配合 @Validated 做校验：

@Component                    // 必须被 Spring 管理，光写注解不会生效
@ConfigurationProperties(prefix = "person")
@Validated
public class PersonProperties {

    @NotBlank
    private String name;           // 绑定 person.name
    private Integer age;           // 绑定 person.age
    private List<String> hobbies;  // 绑定 person.hobbies[0]、person.hobbies[1]

    // JavaBean 绑定需要 setter；Spring Boot 2.2 起也支持构造器绑定
    public void setName(String name) { this.name = name; }
    public void setAge(Integer age) { this.age = age; }
    public void setHobbies(List<String> hobbies) { this.hobbies = hobbies; }

    // getter 省略
}

// 对比：@Value 只能逐个注入，且不做松散绑定
@Component
public class PersonRunner implements ApplicationRunner {

    @Value("${person.name}")
    private String name;

    @Override
    public void run(ApplicationArguments args) {
        System.out.println("name = " + name);
    }
}

两个前提别漏：配置属性类必须被 Spring 管理（像上面那样加 @Component，或在配置类上用 @EnableConfigurationProperties(PersonProperties.class) 显式引入），否则注解只是摆设；JavaBean 方式绑定需要 setter，而 Spring Boot 2.2 起也支持构造器绑定（@ConstructorBinding，2.6 起类中只有一个有参构造器时可省略），3.x 中 record 也能直接绑定。

顺手纠正两处老笔记的写法。其一，把 @ConfigurationProperties 挂在 @Controller 上、借一次 HTTP 请求来验证，虽然能跑，但让 MVC 组件承担配置职责并不合适，配置属性类应当独立存在。其二，application.properties 是 key=value 格式，把 YAML 的缩进层级（person: 换行缩进 name: zhangsan）写进 properties 文件是无效的，必须写成 person.name=zhangsan。同名键的覆盖顺序是：命令行参数 → 环境变量 → 外部 application-{profile} → 外部 application → jar 内 application-{profile} → jar 内 application；同一位置同时存在 .properties 与 .yml 时，.properties 优先。

四、Profile：同一份代码切换多套环境

开发、测试、生产往往用不同的端口和数据库。Profile 把这些差异集中到配置文件，而不是散落成代码里的 if-else。组织方式有两种：多文件（application-dev.yml、application-prod.yml，在主文件中用 spring.profiles.active=dev 激活），或单文件多文档块，用 --- 分隔：

# application.yml
spring:
  profiles:
    active: dev        # 也可用命令行 --spring.profiles.active=prod 覆盖

server:
  port: 8080           # 默认文档：未指定 profile 时以它为准

---
# 以下文档块只在 dev 环境激活时生效
spring:
  config:
    activate:
      on-profile: dev
server:
  port: 8081

---
spring:
  config:
    activate:
      on-profile: prod
server:
  port: 8082

激活方式有四种：配置文件里的 spring.profiles.active、命令行 --spring.profiles.active=prod、环境变量 SPRING_PROFILES_ACTIVE，以及代码中的 SpringApplication.setAdditionalProfiles(...)。被激活的 profile 文档会覆盖默认文档的同名键，因此上面最终生效的端口是 8081。注意版本差异：Boot 2.4 起 spring.profiles.active 不允许写在 profile 专属文档内部（否则抛 InvalidConfigDataPropertyException），profile 文档应改用 spring.config.activate.on-profile，也就是上面的写法；组合多个 profile 的写法也从 spring.profiles.include 调整为 spring.profiles.group。

这套开关在部署时同样管用：java -jar app.jar --spring.profiles.active=prod,redis 可以一次激活多个 profile（逗号分隔），java -Dspring.profiles.active=prod -jar app.jar 则以 JVM 系统属性传入；放到云平台上时，把启动命令写进 Procfile 之类的部署描述文件即可，但要确认生产环境没有误带 dev。还有一个常被忽略的点：切换 profile 只改变配置来源，不会改变自动配置的条件判断结果——想换掉某个自动配置的默认行为，仍然要靠自己声明同类型 Bean，或者在注解上用 exclude 排除它。

五、起步流程与常见坑

回头看 SpringApplication.run(DemoApplication.class, args) 这一行，它依次做了：推断应用类型（SERVLET / REACTIVE / NONE）→ 加载 ApplicationContextInitializer 与 ApplicationListener → 准备 Environment（此时读取配置文件与命令行参数）→ 创建并刷新 ApplicationContext（自动配置候选类的条件筛选与注册就发生在这里）→ 启动内嵌 Web 容器 → 发布 ApplicationReadyEvent。这也解释了为什么日志里 Tomcat started on port(s): 8080 总是出现在最后。

几个反复踩到的坑：启动类要放在所有业务包的父包下，否则 @ComponentScan 默认扫不到别的包；引入 starter 后已经有默认配置，别再手写 XML 或手动 new 对象，要改先查 XxxProperties；Bean 找不到时先看自动配置报告，而不是急着加 @ComponentScan；IDEA 里 devtools 热部署不生效，多半是因为没有打开自动编译（Build project automatically），而不是依赖配错。

小结：起步依赖解决「依赖哪些 jar、版本怎么对齐」，自动配置解决「这些 jar 里的组件何时、按什么条件注册」，配置绑定解决「运行时参数如何变成对象属性」，Profile 解决「同一份代码在不同环境下用不同参数」。四者串起来就是 Spring Boot 的起步流程：约定先给出默认值，配置只在需要偏离约定时出现，条件注解保证默认值不会抢走你自定义的 Bean。下一章我们把 Spring Boot 与 MyBatis 接起来，看这套机制在持久层上的具体表现。
