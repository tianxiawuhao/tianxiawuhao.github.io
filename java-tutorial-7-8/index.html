持续集成与部署

Posted on 2026-09-19，8 min read

前面几章我们已经把应用打成了镜像，也用 Nginx 顶住了入口流量。但"代码从提交到上线"这一段，如果每次都靠人手敲 mvn package、手动 docker push、再 scp 到服务器上重启容器，出事只是时间问题：漏传一个配置文件、拿错分支的包、忘记改端口，都能让一次普通发布变成半夜的救火。本章把这条链路讲完整——持续集成与持续交付分别在解决什么、Jenkins 怎么装怎么用流水线脚本描述构建、镜像如何自动进私有仓库、GitLab CI 与 Jenkins 各自适合什么场景，最后落到灰度发布与回滚。适合已经会写 Maven 构建、手上有台 Linux 服务器、想把部署这件事一次性自动化掉的读者。

一、持续集成到底解决什么问题

持续集成（Continuous Integration，CI）是一种开发实践：团队成员频繁地把自己的改动合回主干，通常每天多次，每次合入都触发一次自动化构建——编译、跑测试、打包，用机器尽快告诉你"这次改动有没有把别人的东西弄坏"。持续交付（Continuous Delivery）是它的延伸：在 CI 通过的基础上，产出一个随时可以发布的版本，发布动作由人按一下按钮；如果再往前一步，通过验证后自动上线，就是持续部署（Continuous Deployment）。三者是递进关系，别混着叫。

没有 CI 的一天通常是这样：三个人各拉一个分支写一周，合并时冲突上百个文件，编译报出三十个错，谁也不知道是谁改坏的；上线当天才发现依赖的接口签名变了。CI 的价值就是把"发现问题"的时刻从上线当天提前到提交后几分钟，并且让构建过程可复现——同一份代码，在谁的机器上、什么时候构建，结果都一样。

要搭起这条链路，至少需要四样东西：代码托管（Git）、一台专门跑构建的服务器、一套能无人值守执行的构建脚本（Maven 或 Gradle）、以及能自动跑的测试。请记住最重要的一点：CI 不是"装了个 Jenkins"，Jenkins 只是执行者，真正的资产是那条能被反复执行、能进版本库 review 的流水线定义。

二、Jenkins 安装与第一条流水线

很多老教程让你 wget jenkins-2.83-1.1.noarch.rpm，这个版本发布于 2017 年，早已停止维护，大量现代插件不再兼容，照着装会在插件安装页卡住。现在应当使用 LTS 版本，并通过官方仓库安装，方便升级：

# 1. 安装 JDK 17（Jenkins 2.4xx 之后要求 Java 11 或 17）
sudo apt-get update && sudo apt-get install -y openjdk-17-jdk

# 2. 添加 Jenkins LTS 官方仓库并安装
curl -fsSL https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key \
  | sudo tee /usr/share/keyrings/jenkins-keyring.asc > /dev/null
echo "deb [signed-by=/usr/share/keyrings/jenkins-keyring.asc] \
https://pkg.jenkins.io/debian-stable binary/" \
  | sudo tee /etc/apt/sources.list.d/jenkins.list > /dev/null
sudo apt-get update && sudo apt-get install -y jenkins

# 3. 启动并设置开机自启
sudo systemctl enable --now jenkins

# 4. 取出初始管理员密码，然后浏览器访问 http://192.168.184.135:8080
sudo cat /var/lib/jenkins/secrets/initialAdminPassword

端口和运行用户的配置文件随安装包类型不同：Debian/Ubuntu 系是 /etc/default/jenkins，RPM 系是 /etc/sysconfig/jenkins。较新的 RPM 包由 systemd 单元接管，改端口更稳的做法是新增 /etc/systemd/system/jenkins.service.d/override.conf，在里面写 Environment="JENKINS_PORT=8888"，再 systemctl daemon-reload。首次进入界面后按提示安装推荐插件、建管理员账号；用 Maven 构建还要在「全局工具配置」里登记 JDK、Git 和 Maven 的安装路径，并给这些工具起个名字，流水线脚本靠名字引用。

接下来是最关键的观念转变。老教程教的是"新建一个 Maven 项目 → 源码管理选 Git → Build 填 clean package docker:build -DpushImage"这种自由风格任务，它能用，但配置全散在网页表单里，改了什么无法 review、无法回滚、也无法复制到第二台机器。现在应当使用 Jenkinsfile，把流水线写成 Groovy 脚本并提交进仓库，做法叫"流水线即代码"：

pipeline {
    agent any
    tools { maven 'M3' }                 // 与「全局工具配置」里登记的名称一致
    stages {
        stage('构建与单测') {
            steps { sh 'mvn -B clean verify' }
            post { always { junit 'target/surefire-reports/*.xml' } }
        }
        stage('构建并推送镜像') {
            when { branch 'main' }       // 只有主干分支才产出镜像
            steps { sh 'mvn -B package jib:build -DskipTests' }
        }
        stage('部署到测试机') {
            when { branch 'main' }
            steps {
                withCredentials([sshUserPrivateKey(credentialsId: 'deploy-key',
                                                   keyFileVariable: 'KEY')]) {
                    sh "ssh -i \$KEY deploy@192.168.184.141 'bash /opt/app/deploy.sh ${BUILD_NUMBER}'"
                }
            }
        }
    }
    post { failure { echo '构建失败，请查看 console 输出与测试报告' } }
}

这段脚本里有三个值得注意的细节：when { branch 'main' } 让特性分支只做校验、不产出可发布镜像，天然避免"谁的临时分支覆盖了线上镜像"；测试报告交给 junit 步骤收集，失败时 Jenkins 会直接把用例列表贴出来；部署用的私钥通过 withCredentials 注入，绝不要把密码写进脚本。

三、构建产物怎么进私有仓库

源文档里用的是 com.spotify:docker-maven-plugin:0.4.13，这个插件早在 2018 年就停止维护并归档，新项目不应再依赖它。今天更合适的选择是 Google 的 Jib，或者 fabric8 的 docker-maven-plugin：前者不需要宿主机上跑 Docker 守护进程就能构建镜像，也不用写 Dockerfile；后者功能更全，支持 compose。只保留 Dockerfile 的话，dockerfile-maven-plugin 也能用，但它同样已归档，只建议在存量项目里继续。

<plugin>
  <groupId>com.google.cloud.tools</groupId>
  <artifactId>jib-maven-plugin</artifactId>
  <version>3.4.3</version>
  <configuration>
    <from><image>eclipse-temurin:17-jre</image></from>
    <to>
      <image>reg.example.com/tensquare/base</image>
      <tags><tag>${project.version}</tag><tag>latest</tag></tags>
    </to>
    <container>
      <mainClass>com.tensquare.base.BaseApplication</mainClass>
      <jvmFlags><jvmFlag>-Xmx512m</jvmFlag></jvmFlags>
    </container>
    <allowInsecureRegistries>true</allowInsecureRegistries>
  </configuration>
</plugin>

执行 mvn -B clean package jib:build 即可构建并推送镜像；配合上面的流水线，这一步在 Jenkins 上自动完成。私有仓库本身用 registry:2 起一个容器就够用，只走 HTTP 时需要在构建机的 /etc/docker/daemon.json 里把它加进 insecure-registries，并配置 {"insecure-registries":["192.168.184.144:5000"]} 后重启 Docker。Jib 默认使用 distroless 基础镜像，上面的 <from> 把它换成了带完整 JRE 的 eclipse-temurin:17-jre，便于排查问题。

这里必须纠正源文档一个危险的建议：它让 Docker 开启 -H tcp://0.0.0.0:2375 以便远程构建。2375 是非加密端口，且没有任何认证——任何能连上它的人都可以 docker run -v /:/host，等于直接拿到宿主机的 root 权限。这个端口只能在完全隔离的实验网段里临时开，生产环境要用 unix socket 本地构建（Jib 天生就是这种模式），或者改用 2376 端口并配好 TLS 双向证书。

四、GitLab CI 与灰度发布

Jenkins 不是唯一答案。如果代码本来就在 GitLab 上，用 GitLab CI 更省事：仓库根目录放一个 .gitlab-ci.yml，注册 Runner 后就能跑，不必再维护一台调度服务器。它的流水线同样是版本化的 YAML：

stages: [build, image, deploy]

variables:
  MAVEN_OPTS: "-Dmaven.repo.local=.m2"

build:
  stage: build
  image: maven:3.9-eclipse-temurin-17
  script:
    - mvn -B clean verify
  artifacts:
    paths: [target/*.jar]
    expire_in: 1 week

image:
  stage: image
  image: docker:27
  services: [docker:27-dind]
  script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" "$CI_REGISTRY"
    - docker build -t "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA" .
    - docker push "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"

deploy-canary:
  stage: deploy
  when: manual            # 人工点一下才发，就是「持续交付」
  script:
    - ./deploy.sh "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA" 10

注意镜像 tag 用的是 $CI_COMMIT_SHORT_SHA 而不是 latest。用提交号打 tag，任何一次线上事故都能精确回答"现在跑的是哪份代码"，回滚就是把旧 tag 重新部署一次；只覆盖 latest 的话，回滚时你根本找不到上一份镜像。

灰度发布（金丝雀发布）落地到容器场景，核心是两个动作：让新旧两个版本同时在线，再按比例把流量切过去。老版本保持运行，新版本先接一小部分流量，观察错误率与 P95 延迟，正常就把权重往上调，例如 Nginx 里用 upstream app { server 10.0.0.11:9001 weight=9; server 10.0.0.12:9001 weight=1; } 先放 10%，再依次改成 5:5、1:9，最后把老版本缩容到零。出问题时只要把权重打回 0，流量立刻回到老版本，不需要重新构建部署——这正是灰度比"一刀切上线"安全的地方。想按用户定向灰度（只让内部账号看到新版），可以用 Nginx 的 map 或 split_clients 按请求头、Cookie 分流，也可以交给服务网格或网关来做。

五、常见坑与小结

最后总结几个反复踩的坑。第一，凭据不要写在 Jenkinsfile 或 .gitlab-ci.yml 里，用 Jenkins Credentials 或 GitLab CI Variables，脚本中只引用变量名。第二，别用 latest 作为唯一 tag，用提交号或构建号，latest 只是便于人看的别名。第三，不要让 Jenkins 同时兼任生产服务器：构建期会把 CPU 和内存吃满，直接把线上服务拖垮，构建机与生产机必须分开。第四，失败要通知到位，邮件、企业微信或 Slack 任选其一，否则流水线红灯没人看，等于白搭。第五，灰度必须配自动回滚阈值，例如"五分钟内错误率超过 1% 自动切回"，把判断交给脚本而不是盯着屏幕的人。

小结一下本章的链路：提交代码触发 CI，机器完成编译、测试、打镜像并推送私有仓库，交付到测试环境验证；发布环节用 Jenkinsfile 或 .gitlab-ci.yml 把过程固化下来，用提交号标记每个可发布的版本；上线时先放小流量灰度，用指标决定继续放量还是回滚。工具会换——Jenkins、GitLab CI、乃至更晚的流水线平台——但这条"可重复、可追溯、可回滚"的原则不会变，它才是自动化部署真正的价值所在。
