树形结构查询

Posted on 2022-08-25，5 min read

树形（层级）结构在数据库里没有原生类型，必须用某种“存储模型”把父子关系表达出来。本文先给出组织表与 DTO 的定义，再把主流的四种模型——邻接表、路径枚举、嵌套集、闭包表——放在一起比较，最后给出可执行的递归查询写法、环检测手段，以及 MySQL 与 PostgreSQL 的差异。

一、邻接表建表

邻接表只用一列 parent_id 指向本表的父节点，是最贴近直觉、也是绝大多数业务系统实际采用的模型。下面的 sys_company 就是典型的邻接表（pid 即 parent id）：

CREATE TABLE `sys_company` (
  `id` int(11) NOT NULL AUTO_INCREMENT COMMENT '主键',
  `code` varchar(36) NOT NULL COMMENT '标识主键',
  `company_name` varchar(255) NOT NULL COMMENT '组织名称',
  `pid` int(10) DEFAULT NULL COMMENT '上级组织id',
  `pname` varchar(255) DEFAULT NULL COMMENT '上级组织名称',
  `sort` int(4) DEFAULT '0' COMMENT '排序',
  `state` int(2) DEFAULT '0' COMMENT '是否可用，0可用，1禁用',
  `create_by` varchar(50) DEFAULT NULL COMMENT '创建者',
  `create_time` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_by` varchar(50) DEFAULT NULL COMMENT '修改者',
  `update_time` timestamp NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`) USING BTREE,
  KEY `code_index` (`code`) USING BTREE COMMENT '简单索引',
  KEY `idx_pid` (`pid`) USING BTREE COMMENT '递归查询按父节点展开，必须建索引'
) ENGINE=InnoDB AUTO_INCREMENT=119 DEFAULT CHARSET=utf8mb4 ROW_FORMAT=DYNAMIC COMMENT='组织详情'

两点说明：pid 为根节点时存 NULL（也有系统用 0，此时需注意 0 不能作为真实主键）；递归查询的性能几乎完全取决于 pid 上的索引，缺索引时每一层递归都会退化为全表扫描。另外 pname（上级组织名称）是冗余字段，改名时必须同步维护，否则会出现父子名称不一致，建议只作为展示缓存使用。

四种存储模型对比

同样一棵树，可以用四种方式落库，它们在“查询成本”和“更新成本”上此消彼长：

  • 邻接表：写便宜、读贵。插入和移动节点只改一行；但取整棵子树必须递归，深度大、并发多时开销明显。
  • 路径枚举：读写折中。子树查询变成一次 LIKE '前缀%' 的索引范围扫描；但移动子树要批量更新所有后代的 path，且路径列必须有长度上限。
  • 嵌套集：读最便宜、写最贵。子树用 lft BETWEEN 一次搞定，完全不需要递归；但任何插入或移动都要重排左右值，需要锁住较大范围，只适合“读多写极少”的场景（如商品分类）。
  • 闭包表：读便宜、写最贵且需要事务。多存一张祖先-后代关系表，任意深度的子树/祖先/层级限制查询都无递归；代价是行数按 节点数 × 平均深度 膨胀，且每写一个节点要成组写入关系行，一致性必须靠事务或触发器保证。

选择建议：变更频繁、规模中等，用邻接表加递归查询；层级固定且读多写少（分类、目录），用嵌套集或路径枚举；需要频繁做“任意节点间关系/层级统计”的复杂查询，用闭包表。三种非邻接表方案都属于“用写入成本换查询成本”，不要在没有实测依据时提前引入。

三、service

下例存在两个问题：List<CompanyDTO> companyDTO 与上面的 CompanyDTO companyDTO 同名，Java 不允许在同一作用域内重复声明，代码无法编译；而且它用循环沿 DTO 上溯去找根节点，完全没有使用查询结果。改为下面这样：

public List<CompanyDTO> getCompanyList(Integer companyId) {
    // 1. 沿 DTO 的父指针向上找到根节点（每次 queryTopData 只查一层）
    CompanyDTO current = sysCompanyMapper.queryTopData(companyId);
    while (current != null && current.getPid() != null) {
        current = sysCompanyMapper.queryTopData(current.getPid());
    }
    if (current == null) {
        return Collections.emptyList();
    }
    // 2. 从根节点出发，用嵌套 select 递归装配子树
    return sysCompanyMapper.querySimpleTopData(current.getId());
}

这种写法每次只查一层，节点一多就是典型的 N+1 查询。更彻底的做法是在数据库里一次递归取回整棵子树，再在内存里按 pid 组装成树（见第四节）。

四、邻接表递归查询

邻接表的查询痛点只有一个：递归。SQL 标准为此提供了 WITH RECURSIVE（公用表表达式递归），PostgreSQL 8.4 起支持，MySQL 则要 8.0 起才支持。

自顶向下：查子树

-- 查询 id = 1 的节点及其全部后代，并用 depth 记录层级
WITH RECURSIVE subtree AS (
    -- 锚点成员：只执行一次，产出种子行
    SELECT id, pid, company_name, 1 AS depth
    FROM sys_company
    WHERE id = 1
    UNION ALL
    -- 递归成员：反复执行，直到返回 0 行
    SELECT c.id, c.pid, c.company_name, t.depth + 1
    FROM sys_company c
    JOIN subtree t ON c.pid = t.id
)
SELECT * FROM subtree ORDER BY depth, id;

执行流程是：先算出锚点结果集，然后不断把“上一轮的产出”当作输入去 JOIN 本表，把新命中的行加入结果并作为下一轮输入；某一轮返回 0 行时递归自然终止——终止条件不需要手写，也无法手写。这也意味着一旦数据里存在环（例如 A→B→A），递归将永不停止。

自底向上：查祖先链

面包屑导航需要“从当前节点到根”的路径，把 JOIN 条件反过来即可，且终止条件变成 pid IS NULL：

-- 查询 id = 4 的节点及其所有祖先（面包屑）
WITH RECURSIVE ancestors AS (
    SELECT id, pid, company_name, 1 AS depth
    FROM sys_company
    WHERE id = 4
    UNION ALL
    SELECT p.id, p.pid, p.company_name, a.depth + 1
    FROM sys_company p
    JOIN ancestors a ON p.id = a.pid   -- 与子树查询方向相反
)
SELECT * FROM ancestors ORDER BY depth DESC;   -- 根在前，即 A → B → D

环检测与保护

只要 pid 没有约束保证不成环，就必须给递归加一道保险。UNION（去重）只能缓解、不能根治有环数据，正确的做法是显式记录已访问节点：

-- PostgreSQL：使用标准 CYCLE 子句（PG 14 起支持）
WITH RECURSIVE subtree AS (
    SELECT id, pid, company_name, 1 AS depth
    FROM sys_company WHERE id = 1
    UNION ALL
    SELECT c.id, c.pid, c.company_name, t.depth + 1
    FROM sys_company c JOIN subtree t ON c.pid = t.id
) CYCLE id SET is_cycle USING path
SELECT * FROM subtree WHERE NOT is_cycle;

-- MySQL 8.0：没有 CYCLE 子句，自行传递路径并用 FIND_IN_SET 判环
WITH RECURSIVE subtree AS (
    SELECT id, pid, company_name, 1 AS depth, CAST(id AS CHAR(1000)) AS path
    FROM sys_company WHERE id = 1
    UNION ALL
    SELECT c.id, c.pid, c.company_name, t.depth + 1,
           CONCAT(t.path, ',', c.id)
    FROM sys_company c JOIN subtree t ON c.pid = t.id
    WHERE FIND_IN_SET(c.id, t.path) = 0   -- 已在路径中的节点不再展开
)
SELECT * FROM subtree ORDER BY depth, id;

除判环外，还应加一道“兜底”上限，避免异常数据把数据库拖垮：PostgreSQL 可设置 SET statement_timeout = '5s'；MySQL 8.0 可设置 SET SESSION cte_max_recursion_depth = 1000（默认 1000），也可以对 depth 加 WHERE t.depth < 20 的硬限制。

五、路径枚举

路径枚举把“祖先链”直接物化成字符串存进每一行（如 /1/2/4/），于是查询不再需要递归：

CREATE TABLE sys_company_path (
  id   INT PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  path VARCHAR(1000) NOT NULL,      -- 形如 /1/2/4/，末尾带分隔符
  depth INT NOT NULL DEFAULT 0,
  KEY idx_path (path)
);

-- 整棵子树：一次索引范围扫描，无需递归
SELECT * FROM sys_company_path
WHERE path LIKE '/1/2/%'
ORDER BY path;

-- 直接父节点：用 SUBSTRING_INDEX 截取
SELECT * FROM sys_company_path
WHERE id = SUBSTRING_INDEX(SUBSTRING_INDEX('/1/2/4/', '/', -3), '/', 1);

关键细节是末尾一定要带分隔符，否则 LIKE '/1/2%' 会错误命中 /1/20/；同时 path 有长度上限（VARCHAR(1000) 约支持几十层），层级很深时不适用。移动子树需要批量改写所有后代行的 path，一条 UPDATE … SET path = REPLACE(path, 旧前缀, 新前缀) WHERE path LIKE '旧前缀%' 即可，但仍是一次范围写。

六、嵌套集

嵌套集为每个节点记录左右值 lft / rgt，用区间包含关系表达“祖先-后代”，是四种模型里查询最快的一种：

CREATE TABLE sys_company_ns (
  id   INT PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  lft  INT NOT NULL,
  rgt  INT NOT NULL,
  KEY idx_lft (lft),
  KEY idx_rgt (rgt)
);

-- 整棵子树（含自身）：A 的 lft=1、rgt=8，一次范围查询完成
SELECT * FROM sys_company_ns WHERE lft BETWEEN 1 AND 8 ORDER BY lft;

-- 某节点的所有祖先：区间反过来包含它即可
SELECT parent.* FROM sys_company_ns parent, sys_company_ns node
WHERE node.id = 4 AND parent.lft < node.lft AND parent.rgt > node.rgt
ORDER BY parent.lft;

-- 只取直接子节点：区间内没有中间层
SELECT * FROM sys_company_ns child
WHERE child.lft > 1 AND child.rgt < 8
  AND NOT EXISTS (
      SELECT 1 FROM sys_company_ns mid
      WHERE mid.lft > 1 AND mid.rgt < 8
        AND child.lft > mid.lft AND child.rgt < mid.rgt
  );

代价在写入侧：在 A 与 B 之间插入一个新节点，需要把所有 lft > 插入点 的值加 2、rgt > 插入点 的值加 2，还要给新节点腾出两个号；移动子树则要整体平移区间。这类操作必须放在事务里，并锁住被影响的行，因此嵌套集只适合读多写极少的场景（分类目录、菜单树）。另外并发写入下容易出现左右值不连续或交叉，建议再配一条校验查询定期体检。

七、闭包表

闭包表把“祖先-后代”的每一对可达关系都单独存一行，用一张关系表换掉所有递归：

CREATE TABLE sys_company_closure (
  ancestor   INT NOT NULL,
  descendant INT NOT NULL,
  depth      INT NOT NULL,           -- 自身为 0，直接子节点为 1
  PRIMARY KEY (ancestor, descendant),
  KEY idx_descendant (descendant)
);

-- 写入 A→B：既要写 A-B，也要写 A-A、B-B 这两条自身关系
INSERT INTO sys_company_closure (ancestor, descendant, depth)
VALUES (1, 1, 0), (2, 2, 0), (1, 2, 1);

-- A 的整棵子树（含自身，去掉 depth = 0 即为后代）
SELECT c.* FROM sys_company c
JOIN sys_company_closure cl ON cl.descendant = c.id
WHERE cl.ancestor = 1
ORDER BY cl.depth, c.id;

-- id = 4 的所有祖先
SELECT c.* FROM sys_company c
JOIN sys_company_closure cl ON cl.ancestor = c.id
WHERE cl.descendant = 4 AND cl.depth > 0
ORDER BY cl.depth DESC;

-- 只查三层以内，无需任何递归即可精确控制
SELECT c.* FROM sys_company c
JOIN sys_company_closure cl ON cl.descendant = c.id
WHERE cl.ancestor = 1 AND cl.depth <= 3;

移动子树时，先删掉“旧祖先 × 该子树后代”的关系行，再插入“新祖先 × 新后代”的关系行，必须在一个事务里完成，否则中途失败会留下断裂的层级。行数约为 节点数 × (平均深度 + 1)，节点多且深时该表会显著膨胀，需要评估存储成本。

八、查询与更新成本对比

把四种模型放在统一口径下比较（n 为节点总数，d 为树深，s 为子树规模）：

  • 子树查询复杂度：邻接表为 O(s)（但要付出 d 次递归往返）、闭包表为 O(s)、路径枚举为 O(s log n) 的前缀范围扫描、嵌套集为 O(s) 的纯区间扫描。
  • 祖先链查询复杂度：邻接表与四者同为 O(d)，但只有邻接表需要递归展开。
  • 写入复杂度：插入节点与移动子树，邻接表为 O(1) 行、路径枚举为 O(1) 行 + 可能的后代批量改写、嵌套集为 O(n) 的左右值重排、闭包表为 O(d) 行或 O(s·d) 行的关系增删。
  • 子树查询：嵌套集与闭包表是纯索引范围扫描；邻接表必须递归展开，实际开销随 d 增长而放大（每层一次索引查找）；路径枚举依赖前缀索引，效率介于两者之间。
  • 祖先查询：路径枚举与闭包表最快；嵌套集用区间包含，可接受；邻接表同样要递归，且方向相反。
  • 插入节点：邻接表与闭包表都是常数级写入（闭包表为 O(d) 行）；路径枚举只需写一行；嵌套集要更新一批 lft/rgt，最贵。
  • 移动子树：邻接表只改一行 pid（最便宜）；路径枚举批量改 path；嵌套集批量平移区间；闭包表按子树规模成组增删关系行。这是邻接表最大的优势，也因此它是变更频繁的业务表的默认选择。
  • 存储成本：邻接表最小；路径枚举多了 path 列；嵌套集只多两列整数；闭包表要多存 O(n·d) 行，最占空间。

一句话总结：写多读少、结构会变 → 邻接表；读多写极少、层级稳定 → 嵌套集；既要免递归又要能控层级 → 闭包表；层级浅且想少建表 → 路径枚举。

九、MySQL 与 PostgreSQL 的差异

  • 递归 CTE 版本要求：MySQL 需要 8.0 及以上（5.7 完全没有 WITH RECURSIVE，只能用存储过程循环或应用层递归）；PostgreSQL 从 8.4 起就支持。
  • 关键字写法：MySQL 8.0 允许省略 RECURSIVE（写了也不报错）；PostgreSQL 必须写 WITH RECURSIVE。
  • 环检测：PostgreSQL 14 起支持标准 CYCLE … SET … USING … 子句；MySQL 8.0 没有，需要自行用 FIND_IN_SET 传递路径判环，或用 cte_max_recursion_depth 兜底（默认 1000，超出直接报错）。
  • 层级排序输出：PostgreSQL 支持 SEARCH DEPTH FIRST BY id SET ordercol 自动生成层级排序键；MySQL 只能自己维护 depth 或 path 列来排序。
  • 标识符引用与类型：MySQL 用反引号 `col`，PostgreSQL 用双引号 "col" 且默认折叠为小写；MySQL 的 INT(11) 显示宽度写法在 8.0.17 起已弃用，建议直接写 INT。
  • 路径枚举的专用类型：PostgreSQL 有 ltree 扩展，可用 <@ 操作符做前缀包含判断并走 GiST 索引，性能与可读性都优于 LIKE；MySQL 没有等价类型，只能靠 LIKE 加前缀索引。
  • 递归的实现差异：PostgreSQL 的递归项可以引用递归 CTE 一次、且不允许在递归项里使用聚合、ORDER BY、LIMIT；MySQL 同样禁止在递归项中使用 GROUP BY、聚合与窗口函数，写复杂递归时要注意把聚合放到最外层。

十、xml（MyBatis 嵌套查询）

下面这段 MyBatis 映射用嵌套 select 来“拼树”，思路是可行的，但有几处需要注意的硬伤：

        <id column="id" property="id" />
        <result column="code" property="code" />
        <result column="company_name" property="companyName" />
        <result column="pid" property="pid" />
        <result column="pname" property="pname" />
        <result column="sort" property="sort" />
        <result column="state" property="state" />
        <result column="create_by" property="createBy" />
        <result column="create_time" property="createTime" />

        <result column="update_time" property="updateTime" />
        <association property="companyDTO"
                     column="{pid = pid}"
                     select="querySuper">
        </association>
    </resultMap>

	<resultMap id="BaseResultMap" type="com.haier.dtosplat.entity.DTO.company.CompanyDTO">
        <id column="id" property="id" />
        <result column="code" property="code" />
        <result column="company_name" property="companyName" />
        <result column="pid" property="pid" />
        <result column="pname" property="pname" />
        <result column="sort" property="sort" />
        <result column="state" property="state" />
        <result column="create_by" property="createBy" />
        <result column="create_time" property="createTime" />
        <result column="update_by" property="updateBy" />
        <result column="update_time" property="updateTime" />

        </collection>
    </resultMap>


    <select id="queryTopData" resultMap="BaseResultAllMap">
        SELECT * FROM sys_company
        WHERE id = #{companyId}
    </select>

    <select id="querySimpleTopData" resultMap="BaseResultMap">
        SELECT * FROM sys_company
        WHERE id = #{companyId}
    </select>

    <select id="querySuper" resultMap="BaseResultMap">
        SELECT * FROM sys_company
        WHERE id = #{pid}
    </select>

    <select id="querySon" resultMap="BaseResultMap">
        SELECT * FROM sys_company
        WHERE pid = #{id}
    </select>

映射存在的问题

  • association property="companyDTO" 与 DTO 中原来的字段 private CompanyDTO CompanyDTO; 对应，而该字段是多余且不规范的：字段名与类名同名（Java 允许但极易混淆），且与 children 语义重叠。本文已在 DTO 中将其删除，因此该 association 需要改为指向 pid（父节点）或整体删掉。
  • column="{pid = pid}" 是多余的：单参数时直接写 column="pid" 即可，花括号形式只在多个参数时使用；写成 {pid = pid} 虽能运行，但容易被误读成“参数名 = 属性名”。
  • collection column="{id = id}" 其中 id 正是 querySon 里的 #{id}，这种写法会把 id 同时当作参数名和列名，语义重叠，建议改为 column="childId" 并同步把 SQL 里的 #{id} 改成 #{childId}。
  • N+1 问题最需要警惕：嵌套 select 会对结果集的每一行再发一次查询，查一棵 n 个节点的树就是 1 + n 次往返，层级越深越慢。数据量稍大就应改为单条递归 SQL（第四节）或 LEFT JOIN 一次性取出后手工组装。
  • queryTopData 与 querySimpleTopData 的 SQL 完全相同，只是 resultMap 不同，功能重复；二者可以合并，用不同 resultMap 的同一 select 会更好维护。
