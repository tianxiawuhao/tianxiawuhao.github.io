springBoot概述

Posted on 2021-05-31，20 min read

Spring Boot 优点

  1. 容易上手，提升开发效率，为 Spring 开发提供一个更快、更广泛的入门体验。
  2. 开箱即用，远离繁琐的配置。
  3. 提供了一系列大型项目通用的非业务性功能，例如：内嵌服务器、安全管理、运行数据监控、运行状况检查和外部化配置等。
  4. 没有代码生成，也不需要 XML 配置。
  5. 避免大量的 Maven 导入和各种版本冲突。

Spring Boot 的核心注解是哪个？它主要由哪几个注解组成的？

启动类上面的注解是@SpringBootApplication，它也是 Spring Boot 的核心注解，主要组合包含了以下 3 个注解：

@SpringBootConfiguration：组合了 @Configuration 注解，实现配置文件的功能。

@EnableAutoConfiguration：打开自动配置的功能，也可以关闭某个自动配置的选项，如关闭数据源自动配置功能： @SpringBootApplication(exclude = { DataSourceAutoConfiguration.class })。

@ComponentScan：Spring组件扫描。

三个注解各司其职，把它们拆开来看会更清楚：

  • @SpringBootConfiguration：本质上是 Spring 标准注解 @Configuration 的“改名版”，作用只有一个——声明“当前类是一个配置类”，即一个 JavaConfig 形式的 Bean 定义来源。Spring Boot 之所以不直接用它而另起一个注解，是为了让框架能在测试或工具中识别“这是应用的主配置类”。一个应用中通常只应出现一次。
  • @EnableAutoConfiguration：自动配置的总开关。它通过 @Import(AutoConfigurationImportSelector.class) 把所有候选自动配置类批量导入容器，再由这些配置类上的 @Conditional 条件决定“到底生不生效”。所以它带来的是“有条件的选择性装配”，而不是无条件地把所有组件都创建出来。
  • @ComponentScan：开启组件扫描。默认扫描当前类所在包及其所有子包，这也是官方建议把启动类放在最外层根包（如 com.example.demo）的原因。

三者合起来的效果可以概括为：我先是一个配置类（@SpringBootConfiguration），我再去扫描自己包下的组件（@ComponentScan），最后让 Spring Boot 按条件帮我补齐基础设施（@EnableAutoConfiguration）。

需要关闭特定的自动配置时，除了 exclude，还可以用 excludeName 按类名排除；也可以在配置文件里用 spring.autoconfigure.exclude 指定，无需改动启动类：

@SpringBootApplication(exclude = {DataSourceAutoConfiguration.class})
public class DemoApplication { /* ... */ }

// 只写类名字符串，适合不想在启动类上引入该自动配置类依赖的场景
@SpringBootApplication(excludeName = {
        "org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration"})
public class DemoApplication2 { /* ... */ }
# 纯配置方式排除自动配置，效果等价
spring.autoconfigure.exclude=org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration

此外要注意 @ComponentScan 的默认范围：所有其它 Spring 组件（如 Controller 层、Service 层、Dao 层、定时器等）都必须放在应用 @SpringBootApplication 注解所在类的同包或其子包下面，因为应用从启动类开始启动，然后会扫描启动类同包及其子包下面的组件；如果放在其它地方，会因为扫描不到而加载不了。确需跨包时，显式写成 @SpringBootApplication(scanBasePackages = "com.example.other")，或在任意配置类上单独加 @ComponentScan("com.example.other")。

JavaConfig

Spring JavaConfig 是 Spring 社区的产品，它提供了配置 Spring IoC 容器的纯Java 方法。因此它有助于避免使用 XML 配置。使用 JavaConfig 的优点在于：

（1）面向对象的配置。由于配置被定义为 JavaConfig 中的类，因此用户可以充分利用 Java 中的面向对象功能。一个配置类可以继承另一个，重写它的@Bean 方法等。

（2）减少或消除 XML 配置。基于依赖注入原则的外化配置的好处已被证明。但是，许多开发人员不希望在 XML 和 Java 之间来回切换。JavaConfig 为开发人员提供了一种纯 Java 方法来配置与 XML 配置概念相似的 Spring 容器。从技术角度来讲，只使用 JavaConfig 配置类来配置容器是可行的，但实际上很多人认为将JavaConfig 与 XML 混合匹配是理想的。

（3）类型安全和重构友好。JavaConfig 提供了一种类型安全的方法来配置 Spring容器。由于 Java 5.0 对泛型的支持，现在可以按类型而不是按名称检索 bean，不需要任何强制转换或基于字符串的查找。

/**
 * @ConfigurationProperties 表示 告诉 SpringBoot 将本类中的所有属性和配置文件中相关的配置进行绑定；
 * prefix = "user" 表示 将配置文件中 key 为 user 的下面所有的属性与本类属性进行一一映射注入值，如果配置文件中
 * 不存在 "user" 的 key，则不会为 POJO 注入值，属性值仍然为默认值
 * @Component 将本来标识为一个 Spring 组件，因为只有是容器中的组件，容器才会为 @ConfigurationProperties 提供此注入功能
 * @PropertySource(value = "classpath:user.properties") 指明加载类路径下的哪个配置文件来注入值
 */
@PropertySource(value = {"classpath:user.properties"})
@Component
@ConfigurationProperties(prefix = "user")
public class User {
    private Integer id;
    private String lastName;
    private Integer age;
    private Date birthday;
    private List<String> colorList;
    private Map<String, String> cityMap;
}
/**
 * 文中的@Configuration 可以替换为@Component运行结果是一样的，但是两者是有不同的，@Configuration会为配置类生成CGLIB代理Class，@Component不会
 */
@PropertySource(value = {"classpath:user.properties"})
@Configuration
public class User {
    @Value("${user.id}")
    private Integer id;
    @Value("${user.lastName}")
    private String lastName;
    @Value("${user.age}")
    private Integer age;
    @Value("${user.birthday}")
    @DateTimeFormat(pattern = "yyyy/MM/dd")   // 非 ISO 格式日期必须声明格式，否则转换失败
    private Date birthday;
    @Value("${user.colorList}")                 // 逗号分隔的字符串可直接转成 List<String>
    private List<String> colorList;
    @Value("#{${user.maps}}")                    // Map 必须借 SpEL 解析，写成 ${user.maps} 会转换失败
    private Map<String, String> cityMap;
}

user.properties

user.id=111
user.lastName=张无忌
user.age=120
user.birthday=2018/07/11
user.colorList=red,yellow,green,black
user.cityMap.mapK1=长沙市
user.cityMap.mapK2=深圳市
user.maps="{mapK1: '长沙市', mapK2: '深圳市'}"

这里有三处细节容易翻车：一是 @Value 的占位符必须带引号，写成 @Value("${user.id}")，漏掉引号连编译都过不去；二是 @Value 只能注入单个值，user.cityMap.mapK1 这种带层级的键绑不到 Map 字段上，要么用 @Value("#{${user.maps}}") 借 SpEL 解析，要么直接用 @ConfigurationProperties(prefix = "user") 批量绑定——后者才是「一组属性 → 一个对象」的正确姿势，@Value 更适合零散注入；三是 user.birthday=2018/07/11 不是 ISO 格式，需要配 @DateTimeFormat(pattern = "yyyy/MM/dd") 才能注入成功。

内嵌容器与启动流程

内嵌容器

传统 Spring 项目把 war 包交给外部的 Tomcat 部署，容器先启动、再由容器加载应用；Spring Boot 反过来——由应用的 main 方法启动，过程中把 Web 容器“当作一个普通组件”创建出来并启动。所以启动方式变成直接运行 SpringApplication.run(...)，打出来的是可执行 jar（java -jar app.jar），可以独立运行，也更贴合容器化部署。默认容器是 Tomcat，通过排除并替换依赖可换成 Jetty 或 Undertow；WebFlux 场景默认是 Reactor Netty。

这里有一个容易踩坑的版本差异：Spring Boot 3.x 基于 Jakarta EE 9+，Servlet API 包名由 javax.servlet.* 变为 jakarta.servlet.*（内嵌容器为 Tomcat 10+）。因此本文后面示例中的 import javax.servlet.* 只在 Spring Boot 2.x（Tomcat 9、Servlet 4.0）下可直接编译；迁移到 3.x 时需整体替换为 jakarta.servlet，同时 @WebServlet 等注解所在包也随之改变。

SpringApplication.run 的关键步骤

把 SpringApplication.run(DemoApplication.class, args) 拆开，主要分三大阶段：

  1. 启动引导：构造 SpringApplication 并推断应用类型。WebApplicationType.deduceFromClasspath() 判断类路径：有 Servlet 相关类则为 SERVLET（Web 应用），只有 WebFlux 相关类则为 REACTIVE，两者都没有则为 NONE（普通应用）。同时通过 setInitializers / setListeners 从 spring.factories 加载 ApplicationContextInitializer 与 ApplicationListener。
  2. Environment 准备：创建 Environment（Web 应用为 StandardServletEnvironment），发布 ApplicationEnvironmentPreparedEvent，由 EnvironmentPostProcessor / ConfigData 机制读取命令行参数、系统属性、环境变量、application.yml / properties 以及 profile 相关文件，构造出完整的有序属性源。随后 environmentPrepared 完成绑定。这一步之后，配置值就已经全部就绪，后续的自动配置才能按配置条件决定是否生效。
  3. 应用上下文（IoC 容器）创建与刷新：按应用类型创建 AnnotationConfigServletWebServerApplicationContext 等上下文实例，调用 prepareContext（应用 Initializer、注册主配置类 DemoApplication、BeanDefinitionLoader 加载 Bean 定义）。随后进入 refreshContext，即 Spring 的 refreshed 核心流程：解析 @SpringBootApplication → 触发自动配置 → 实例化并初始化全部单例 Bean。内嵌容器正是在上下文 refresh 期间创建的：ServletWebServerApplicationContext.onRefresh() 会调用 createWebServer()，由 ServletWebServerFactory 创建并启动 Tomcat，再把 DispatcherServlet 注册进去，随后 finishRefresh() 发布 ServletWebServerInitializedEvent。
  4. 收尾：调用所有 ApplicationRunner / CommandLineRunner，最后发布 ApplicationReadyEvent，应用即可对外服务。

启动过程中的事件与监听器

Spring Boot 在启动各阶段发布了 SpringApplicationEvent（继承自 Spring 的 ApplicationEvent），自定义逻辑可以挂在这些扩展点上：

  • ApplicationStartingEvent：run 方法最开始，此时 Environment 尚未准备。
  • ApplicationEnvironmentPreparedEvent：Environment 刚准备好，配置源已加载。需要尽早读取配置的框架常监听它。
  • ApplicationContextInitializedEvent：上下文已创建、Initializer 已执行，但 Bean 定义尚未加载。
  • ApplicationPreparedEvent：Bean 定义已加载，容器尚未 refresh。
  • ContextRefreshedEvent：容器 refresh 完成，内嵌容器已启动。
  • ApplicationStartedEvent：refresh 之后、Runner 执行之前发布。注意其“AfterRefresh”语义只代表容器已就绪，此时业务 Runner 还没跑完。
  • ApplicationReadyEvent：Runner 执行完毕，应用已可接收请求——这是最常用于“启动后初始化”的时点。
  • ApplicationFailedEvent：启动过程中抛出异常时发布。

监听方式有三种：@Component 类实现 ApplicationListener<E>；任意 Bean 中的 @EventListener 方法（Spring 4.2+，更灵活，可按事件类型和 SpEL 条件过滤）；或在 META-INF/spring.factories 的 org.springframework.boot.context.ApplicationListener 键下登记类名，由 SpringApplication 在启动早期加载（此时容器尚未创建，适合框架级组件）。

@Component
public class StartupReporter {

    // 应用完全就绪后回调，最常用于预热缓存、打印访问地址
    @EventListener(ApplicationReadyEvent.class)
    public void onReady(ApplicationReadyEvent event) {
        System.out.println("应用已就绪，启动耗时(ms)："
                + event.getTimeTaken().toMillis());
    }

    // 容器 refresh 完成、内嵌容器已启动
    @EventListener(ContextRefreshedEvent.class)
    public void onRefreshed(ContextRefreshedEvent event) {
        System.out.println("容器已刷新：" + event.getApplicationContext().getId());
    }
}
# META-INF/spring.factories：启动早期就被加载，适合框架/基础组件
org.springframework.boot.context.ApplicationListener=\
com.example.MyEarlyListener

优雅关闭

启动的最后要配套考虑关闭：应用退出时会发布 ContextClosedEvent，容器随即销毁单例 Bean。直接 context.close() 后从 main 方法返回并不会自动触发 Spring Boot 的优雅关闭流程，推荐用 SpringApplication.exit(context, () -> exitCode)；若需等待在途请求处理完，可开启 server.shutdown=graceful 并配合 spring.lifecycle.timeout-per-shutdown-phase 设定超时。

Spring Boot 自动配置

自动配置的核心可以概括为一句话：注解 @EnableAutoConfiguration 负责“把候选配置类找出来并导入”，@Conditional 系列注解负责“决定哪些真正生效”，xxxProperties 负责“把配置文件里的值绑定成 Bean”。

自动配置类的加载入口

@EnableAutoConfiguration 上标注了 @Import(AutoConfigurationImportSelector.class)，由这个 ImportSelector 去读取候选自动配置类的全限定名列表。列表的来源随 Spring Boot 版本发生过一次重要变化：

  • Spring Boot 2.7 之前：所有候选自动配置类都登记在自动配置 jar 自己的 META-INF/spring.factories 中，键为 org.springframework.boot.autoconfigure.EnableAutoConfiguration。这是一个 Properties 格式文件，同一个键下用逗号分隔上百个类名，无法表达“顺序”与“条件”，也难以按需裁剪。
  • Spring Boot 2.7 起：新增专用文件 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports，每行一个自动配置类全限定名，可读性和工具支持都更好；同时 spring.factories 中的 EnableAutoConfiguration 键被标记为废弃（deprecated），但仍兼容读取。
  • Spring Boot 3.0 起：spring.factories 作为自动配置入口的支持被彻底移除，自动配置类只能通过 AutoConfiguration.imports 注册。若把 2.x 的自定义 starter 直接搬到 3.x，最典型的症状就是“自动配置类不生效”。

注意区分：spring.factories 文件本身在 3.x 并未消失，它仍然承载 ApplicationContextInitializer、ApplicationListener、EnvironmentPostProcessor、FailureAnalyzer 等扩展点的注册；被移除的只是用它来登记自动配置类这一种用法。

迁移时把自动配置类从 spring.factories 改为 imports 文件，写法如下：

# 旧写法（Spring Boot 2.6 及以前）META-INF/spring.factories
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
com.example.starter.HelloAutoConfiguration,\
com.example.starter.WorldAutoConfiguration
# 新写法（Spring Boot 2.7+，3.x 唯一支持）META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.example.starter.HelloAutoConfiguration
com.example.starter.WorldAutoConfiguration

spring-boot-autoconfigure 里有什么

绝大多数开箱即用的自动配置类都来自 spring-boot-autoconfigure 这个 jar（引入 spring-boot-starter 时会随之进入依赖树）。它内含 Web、JDBC、Redis、Jackson、缓存、消息等各技术栈的 XxxAutoConfiguration 配置类，以及配套的 XxxProperties 属性类；而在 spring-boot-autoconfigure 的 AutoConfiguration.imports 文件里，登记的就是这批类的清单。第三方 starter 只需在自己 jar 的同一路径下放一个同名文件，就能把自己的自动配置类加入候选队列。

@Conditional 系列条件注解

spring-boot-autoconfigure 中几乎每个配置类（以及配置类中的每个 @Bean 方法）都带条件注解，只有条件全部满足时才装配。这正是“导入了全部候选类，却只生效一小部分”的原因。常用的条件注解如下：

  • @ConditionalOnClass / @ConditionalOnMissingClass：类路径上存在／不存在指定类时生效。它让自动配置与具体依赖解耦——没引入 Redis 依赖，RedisAutoConfiguration 就自动让位。
  • @ConditionalOnBean / @ConditionalOnMissingBean：容器中已有／没有指定 Bean 时生效。它体现了“约定优于配置、用户优先”：开发者自己定义了 DataSource Bean，自动配置的默认数据源就退让。
  • @ConditionalOnProperty：配置文件中某属性等于（或不等于）指定值时生效，常用于功能开关。
  • @ConditionalOnResource、@ConditionalOnWebApplication、@ConditionalOnNotWebApplication、@ConditionalOnSingleCandidate、@ConditionalOnJava、@ConditionalOnExpression 等：分别按资源是否存在、应用类型、候选 Bean 是否唯一、JDK 版本、SpEL 表达式判断。

这些注解的元注解是 Spring Framework 的 @Conditional，底层由 Condition 接口实现判断。因此在 Spring Boot 中调试自动配置，最直接的手段是开启调试日志，它会打印“生效／未生效”的完整报告（Negative matches 会说明每个条件为何不满足）：

# application.properties：打印自动配置条件评估报告
debug=true
# 或者只关注自动配置这一个日志类别
logging.level.org.springframework.boot.autoconfigure=DEBUG

一个自动配置类的典型结构

@AutoConfiguration                          // 2.7+ 新增，本身组合了 @Configuration(proxyBeanMethods = false)
@ConditionalOnClass(HelloService.class)      // 类路径有 HelloService 才继续
@EnableConfigurationProperties(HelloProperties.class) // 让属性类生效并被注入
public class HelloAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                  // 用户没自己定义 HelloService 时才给默认实现
    public HelloService helloService(HelloProperties properties) {
        return new HelloService(properties.getPrefix());
    }
}
@ConfigurationProperties(prefix = "hello")   // 把 hello.* 绑定到字段
public class HelloProperties {
    private String prefix = "Hello";          // 提供合理的默认值
    // getter / setter 省略
}

把这三段串起来看，就是完整的自动配置链路：

自动配置装配流程

启动类 @SpringBootApplication
  └─ @EnableAutoConfiguration
       └─ @Import(AutoConfigurationImportSelector)
            ├─ 读取 AutoConfiguration.imports（2.7 之前为 spring.factories）
            ├─ 去重 + 按 @AutoConfigureOrder / @AutoConfigureBefore / @AutoConfigureAfter 排序
            └─ 得到候选自动配置类列表
                 ↓ 逐个评估 @Conditional 条件
                 ├─ 不满足 → 记入 Negative matches，跳过
                 └─ 满足   → 注册配置类 → 解析其 @Bean 方法
                              └─ XxxProperties 绑定 application.yml/properties 中的值
                                   └─ Bean 进入 IoC 容器，可直接 @Autowired 使用

起步依赖与父 POM

Spring Boot 让人“少写依赖”的关键，一半靠起步依赖（starter），一半靠父 POM。

父 POM 与依赖管理

Spring Boot 项目通常继承 spring-boot-starter-parent，而它又继承自 spring-boot-dependencies。真正干活的 spring-boot-dependencies 的 dependencyManagement 里锁定了整套依赖的版本：Spring Framework、Tomcat、Jackson、Logback、HikariCP 等等。因此我们在 <dependencies> 中写依赖时一般不写 <version>，版本由父 POM 统一决定，从而天然避免“大量 Maven 导入和版本冲突”。

<!-- 方式一：继承官方父 POM，最省事 -->
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.2.5</version>
    <relativePath/>
</parent>

父 POM 还顺带提供了三项常被忽略的便利：默认的 Java 编译版本与编码 UTF-8、repackage（打可执行 fat jar）的执行配置、以及一套面向 Spring Boot 的资源过滤（让 application.yml 里也能用 @...@ 占位符）。

如果项目已有自己的父 POM（例如公司统一父工程），就不能再继承官方父 POM，此时改用“导入式”依赖管理，效果几乎一样：

<!-- 方式二：不继承，改用 BOM 导入 -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-dependencies</artifactId>
            <version>3.2.5</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

起步依赖是怎么“做到开箱即用”的

起步依赖本身几乎不含代码，它是一个“依赖集合 + 自动配置”的组合包：把某个功能所需的一组 jar 聚合成一个坐标，同时这些 jar 里的 AutoConfiguration.imports 会带来自动配置。例如 spring-boot-starter-web 一次性引入 spring-webmvc、spring-web、Jackson、校验、日志，以及 spring-boot-starter-tomcat（内嵌容器），于是“加一个依赖就能写出 REST 接口”。

常用起步依赖：

  • spring-boot-starter：最基础的起步依赖，含自动配置支持、日志、YAML 解析。
  • spring-boot-starter-web：Web MVC + REST + Jackson + 内嵌 Tomcat。
  • spring-boot-starter-webflux：响应式 Web 栈，默认内嵌 Reactor Netty。
  • spring-boot-starter-data-jpa / spring-boot-starter-jdbc / spring-boot-starter-data-redis：数据访问。
  • spring-boot-starter-security、spring-boot-starter-validation、spring-boot-starter-actuator、spring-boot-starter-test：安全、校验、监控、测试。

需要替换默认内嵌容器时，用 <exclusions> 排掉再引入目标容器即可（如 spring-boot-starter-jetty、spring-boot-starter-undertow）。另外要注意：第三方 starter 的命名规范是 xxx-spring-boot-starter，而官方 starter 是 spring-boot-starter-xxx，看名字就能区分。

Spring Boot 配置加载顺序

Spring Boot 支持多种外部配置方式，如下所示，从上往下加载优先级由高到低，内容相同时覆盖，不相同时累加。

配置文件所在位置同样影响优先级（后面的覆盖前面的）：jar 包外的 ./config/ → jar 包外的 ./ → jar 包内 classpath 的 /config 包 → jar 包内 classpath 根路径。同一目录下 .properties 优先于 .yml。常见内置配置位置与覆盖关系如下：

1. file:./config/application.properties   （jar 同级 config 目录，优先级最高，适合运维改配置）
2. file:./config/application.yml
3. file:./application.properties           （jar 同级目录）
4. file:./application.yml
5. classpath:/config/application.properties（打进的包里，如 resources/config/）
6. classpath:/config/application.yml
7. classpath:/application.properties
8. classpath:/application.yml              （优先级最低，作为默认值兜底）

需要特别注意：这些是“同一个属性在不同位置出现”时的覆盖关系；而不同配置来源（命令行参数、环境变量、配置文件……）之间则由前面那张图的整体优先级决定。要观察实际生效的最终结果，可以开启 --debug，或访问 actuator 的 /actuator/env 端点查看属性源顺序。

YAML 配置

YAML 现在可以算是非常流行的一种配置文件格式了，无论是前端还是后端，都可以见到 YAML 配置。那么 YAML 配置和传统的 properties 配置相比到底有哪些优势呢？

  1. 配置有序，在一些特殊的场景下，配置有序很关键
  2. 支持数组，数组中的元素可以是基本数据类型也可以是对象
  3. 简洁

相比 properties 配置文件，YAML 还有一个缺点，就是不支持 @PropertySource 注解导入自定义的 YAML 配置：@PropertySource 默认只解析 properties 格式，直接指向 .yml 文件会报错。真要在 Java 代码里导入 YAML，需要自定义一个 PropertySourceFactory（内部用 YamlPropertySourceLoader 解析）并在注解上指定 factory 属性。实践中最省事的做法仍是把需要 @PropertySource 引入的配置留成 properties 文件。

Spring Boot 是否可以使用 XML 配置

Spring Boot 推荐使用 Java 配置而非 XML 配置，但是 Spring Boot 中也可以使用 XML 配置，通过 @ImportResource 注解可以引入一个 XML 配置。

spring boot 核心配置文件bootstrap.properties和 application.properties 有何区别

单纯做 Spring Boot 开发，可能不太容易遇到 bootstrap.properties 配置文件，但是在结合 Spring Cloud 时，这个配置就会经常遇到了，特别是在需要加载一些远程配置文件的时候。

spring boot 核心的两个配置文件：

  • bootstrap（.yml 或者 .properties）：bootstrap 由父 ApplicationContext 加载，比 application 优先加载，配置在应用程序上下文的引导阶段生效。一般来说我们在 Spring Cloud Config 或者 Nacos 中会用到它。且 bootstrap 里面的属性不能被覆盖；
  • application（.yml 或者 .properties）：由 ApplicationContext 加载，用于 Spring Boot 项目的自动化配置。

版本提醒：bootstrap 是 Spring Cloud 提供的能力，不是 Spring Boot 自带的。自 Spring Cloud 2020.0.0（Ilford）起 bootstrap 上下文默认关闭，官方推荐改用 spring.config.import=optional:configserver: 直接在主上下文里导入远程配置；若仍想用 bootstrap.yml，必须额外引入 spring-cloud-starter-bootstrap，否则该文件根本不会被读取。

Spring Profiles

Profile 用于区分不同环境的配置。除“按文件拆分”（application-dev.yml、application-prod.yml）外，还可以在同一个文件里用 --- 分隔多个文档块，每个块用 profile 表达式限定生效条件。

# Spring Boot 2.4 及以后推荐写法：用 spring.config.activate.on-profile 限定文档块
spring:
  profiles:
    active: devel            # 指定激活哪个环境；不指定时只有无 profile 限定的文档/文件生效
server:
  port: 8083                 # 无 profile 限定的默认块，优先级最低
---
spring:
  config:
    activate:
      on-profile: devel        # 该块仅在 devel 环境激活时生效，等价于 application-devel.yml
server:
  port: 8081
---
spring:
  config:
    activate:
      on-profile: deploy
server:
  port: 8082

过时写法提醒：在文档块中用 spring.profiles 标识 profile 的写法自 Spring Boot 2.4 起已废弃，会直接导致启动失败，必须换成 spring.config.activate.on-profile。同时要分清几个长得很像的键：

  • spring.profiles.active：声明“激活哪些 profile”，只能出现在没有 profile 限定的文档块或文件里，否则抛 InactiveConfigDataAccessException。
  • spring.profiles.include：在当前已命中的 profile 之上追加激活其他 profile；2.4 起同样不允许写在 profile 限定的文档块中。
  • spring.profiles.default：未显式指定 active 时使用的默认 profile，默认值为 default。
  • spring.profiles.group.xxx：profile 分组，可一次激活一组，例如把 prod 定义为 prod-db,prod-mq。

除配置文件外，profile 还可以通过命令行 --spring.profiles.active=prod、环境变量 SPRING_PROFILES_ACTIVE、JVM 参数 -Dspring.profiles.active=prod 指定，或在启动代码里追加：

SpringApplication app = new SpringApplication(DemoApplication.class);
app.setAdditionalProfiles("devel");   // 追加激活 profile（不覆盖命令行传入的 active）
app.run(args);

在代码中按环境装配不同 Bean 时，用 @Profile 标注：只有对应 profile 激活，这个 Bean 才会注册。

@Configuration
public class DataSourceConfig {

    @Bean
    @Profile("dev")     // 只在 dev 环境注册内存库
    public DataSource h2DataSource() {
        return new EmbeddedDatabaseBuilder().setType(EmbeddedDatabaseType.H2).build();
    }

    @Bean
    @Profile("!dev")    // 非 dev 环境注册真实连接池
    public DataSource mysqlDataSource() {
        return DataSourceBuilder.create().build();
    }
}

比较一下 Spring Security 和 Shiro 各自的优缺点

由于 Spring Boot 官方提供了大量的非常方便的开箱即用的 Starter ，包括 Spring Security 的 Starter ，使得在 Spring Boot 中使用 Spring Security 变得更加容易，甚至只需要添加一个依赖就可以保护所有的接口，所以，如果是 Spring Boot 项目，一般选择 Spring Security 。当然这只是一个建议的组合，单纯从技术上来说，无论怎么组合，都是没有问题的。Shiro 和 Spring Security 相比，主要有如下一些特点：

  1. Spring Security 是一个重量级的安全管理框架；Shiro 则是一个轻量级的安全管理框架
  2. Spring Security 概念复杂，配置繁琐；Shiro 概念简单、配置简单
  3. Spring Security 功能强大；Shiro 功能简单

Spring Boot 中如何解决跨域问题

跨域可以在前端通过 JSONP 来解决，但是 JSONP 只可以发送 GET 请求，无法发送其他类型的请求，在 RESTful 风格的应用中，就显得非常鸡肋，因此我们推荐在后端通过 CORS（Cross-Origin Resource Sharing）来解决跨域问题。这种解决方案并非 Spring Boot 特有的，在传统的 SSM 框架中，就可以通过 CORS 来解决跨域问题，只不过之前我们是在 XML 文件中配置 CORS ，现在可以通过实现WebMvcConfigurer接口然后重写addCorsMappings方法解决跨域问题。

@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
                .allowedOriginPatterns("*")   // 开启凭证时必须用 OriginPatterns，allowedOrigins("*") 会抛异常
                .allowCredentials(true)
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
                .maxAge(3600);
    }

}

注意 allowCredentials(true) 与 allowedOrigins("*") 不能同时使用：Spring 会直接抛出 IllegalArgumentException（提示 When allowCredentials is true, allowedOrigins cannot contain the special value "*"），因为携带凭证的响应不允许对任意来源开放。需要「任意来源 + 携带 Cookie」时，改用 allowedOriginPatterns("*")（Spring 5.3+ 提供），或显式列出可信域名。

项目中前后端分离部署，所以需要解决跨域的问题。

我们使用cookie存放用户登录的信息，在spring拦截器进行权限控制，当权限不符合时，直接返回给用户固定的json结果。

当用户登录以后，正常使用；当用户退出登录状态时或者token过期时，由于拦截器和跨域的顺序有问题，出现了跨域的现象。

我们知道一个http请求，先走filter，到达servlet后才进行拦截器的处理，如果我们把cors放在filter里，就可以优先于权限拦截器执行。

@Configuration
public class CorsConfig {
    @Bean
    public CorsFilter corsFilter() {
        CorsConfiguration corsConfiguration = new CorsConfiguration();
        corsConfiguration.addAllowedOriginPattern("*");   // 同理：与 setAllowCredentials(true) 同用时不能写 addAllowedOrigin("*")
        corsConfiguration.addAllowedHeader("*");
        corsConfiguration.addAllowedMethod("*");
        corsConfiguration.setAllowCredentials(true);
        UrlBasedCorsConfigurationSource urlBasedCorsConfigurationSource = new UrlBasedCorsConfigurationSource();
        urlBasedCorsConfigurationSource.registerCorsConfiguration("/**", corsConfiguration);
        return new CorsFilter(urlBasedCorsConfigurationSource);
    }
}

FilterRegistrationBean 注册 Filter

1、Filter(过滤器) 是 Servlet 技术中最实用的技术之一

2、Web 开发人员通过 Filter 技术，对 web 服务器管理的所有 web 资源(如动态的 Jsp、 Servlet，以及静态的 image、 html、CSS、JS 文件等) 进行过滤拦截，从而实现一些特殊的功能(如实现 URL 级别的权限访问控制、过滤敏感词汇、压缩响应信息等)

3、Filter 主要用于对用户请求进行预处理，也可以对 HttpServletResponse 进行后期处理(如编码设置，返回时禁用浏览器缓存等)

4、Filter 使用完整流程：Filter 对用户请求进行预处理，接着将请求交给 Servlet 进行处理并生成响应，最后 Filter 再对服务器响应进行后处理。

5、Servlet 的 Filter 经常会拿来与 Spring MVC 的 Interceptor(拦截器) 做对比

1）拦截器是基于 Java 的反射机制的，而过滤器是基于函数回调

2）拦截器不依赖于 Servlet 容器，过滤器依赖于 Servlet 容器

3）拦截器可以访问 action 上下文、值栈里的对象，而过滤器不能访问

4）同一个请求里，拦截器会在 action 生命周期的不同阶段被多次调用（preHandle、postHandle、afterCompletion），而过滤器对一次请求只执行一次 doFilter；只有 init 与 destroy 是容器启动/关闭时各执行一次

5）拦截器由 Spring 容器管理，可以注入并使用各个 Bean；过滤器由 Servlet 容器创建，默认不在 Spring 容器里（除非注册成 Bean），这点对「在拦截器里注入 Service 调用业务逻辑」很关键

6）SpringMVC 有自己的拦截器

import javax.servlet.*;
import javax.servlet.http.HttpServletRequest;
import java.io.IOException;
/**
 * Created by Administrator 
 * 标准 Servlet 过滤器，实现 javax.servlet.Filter 接口
 * 并重写它的 三个方法
 */
public class SystemFilter implements Filter {
    @Override
    public void init(FilterConfig filterConfig) throws ServletException {
        System.out.println("javax.servlet.Filter：：服务器启动....");
    }
    @Override
    public void doFilter(ServletRequest servletRequest, ServletResponse servletResponse, FilterChain filterChain) throws IOException, ServletException {
        /**
         * 转为 HttpServletRequest 输出请求路径 容易查看 请求地址
         */
        HttpServletRequest request = (HttpServletRequest) servletRequest;
        System.out.println("javax.servlet.Filter：：过滤器放行前...." + request.getRequestURL());
        filterChain.doFilter(servletRequest, servletResponse);
        System.out.println("javax.servlet.Filter：：过滤器返回后...." + request.getRequestURL());
    }
    @Override
    public void destroy() {
        System.out.println("javax.servlet.Filter：：服务器关闭....");
    }
}

import com.lct.component.MyLocaleResolve;
import com.lct.filter.SystemFilter;
import com.lct.servlet.BookServlet;
import org.springframework.boot.web.server.WebServerFactoryCustomizer;
import org.springframework.boot.web.servlet.FilterRegistrationBean;
import org.springframework.boot.web.servlet.ServletRegistrationBean;
import org.springframework.boot.web.servlet.server.ConfigurableServletWebServerFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.LocaleResolver;
import javax.servlet.DispatcherType;
import java.util.Arrays;
/**
 * Created by Administrator 
 * 自定义配置类
 */
@Configuration
public class MyMvcConfig {
    /**
     * 注册 Servlet 三大组件 之  Filter (过滤器)
     * 添加 FilterRegistrationBean ，就相当于以前在 web.xml 中配置的 <filter></filter> 标签
     */
    @Bean
    public FilterRegistrationBean myFilter() {
        FilterRegistrationBean registrationBean = new FilterRegistrationBean();
        /**同样添加自定义的 Filter*/
        registrationBean.setFilter(new SystemFilter());
        /**然后设置过滤的路径，参数是个集合 ,相当于 web.xml中配置的 <filter-mapping></filter-mapping>
         * "/*": 表示过滤所有 get 与 post 请求*/
        registrationBean.setUrlPatterns(Arrays.asList("/*"));
        /**
         * setDispatcherTypes 相当于 web.xml 配置中 <filter-mapping> 下的 <dispatcher> 标签
         * 用于过滤非常规的 get 、post 请求
         * REQUEST：默认方式，写了之后会过滤所有静态资源的请求
         * FORWARD：过滤所有的转发请求，无论是 jsp 中的 <jsp:forward</>、<%@ page errorPage= %>、还是后台的转发
         * INCLUDE：过滤 jsp 中的动态包含<jsp:include 请求
         * ERROR：过滤在 web.xml 配置的全局错误页面
         * 了解即可，实际中也很少这么做
         */
        registrationBean.setDispatcherTypes(DispatcherType.REQUEST);
        return registrationBean;
    }
}

注解方式

1、Servlet 三大组件 Servlet、Filter、Listener 在传统项目中都要在 web.xml 里逐项配置。Servlet 3.0 开始在 javax.servlet.annotation 包下提供了 @WebServlet、@WebFilter、@WebListener 三个注解来简化这些配置（Spring Boot 3.x 对应的包名是 jakarta.servlet.annotation）。

2、Spring Boot 应用中这三个注解默认是不被扫描的，需要在项目启动类上添加 @ServletComponentScan 注解, 表示对 Servlet 组件扫描。

@WebServlet

import javax.servlet.ServletException;
import javax.servlet.annotation.WebServlet;
import javax.servlet.http.HttpServlet;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import java.io.IOException;
 
/**
 * 标准的 Servlet ，实现 javax.servlet.http.HttpServlet. 重写其 doGet 、doPost 方法
 * name :表示 servlet 名称，可以不写，默认为空
 * urlPatterns: 表示请求的路径，如 http://ip:port/context-path/userServlet
 */
@WebServlet(name = "UserServlet", urlPatterns = {"/userServlet"})
public class UserServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        this.doPost(req, resp);
    }
 
    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        StringBuffer requestURL = req.getRequestURL();
        System.out.println("com.wmx.servlet.UserServlet -- " + requestURL);
        resp.sendRedirect("/index.html");//浏览器重定向到服务器下的 index.html 页面
    }
}

@WebFilter

import javax.servlet.*;
import javax.servlet.annotation.WebFilter;
import javax.servlet.http.HttpServletRequest;
import java.io.IOException;
 
/**
 * 标准 Servlet 过滤器，实现 javax.servlet.Filter 接口，并重现它的 3 个方法
 * filterName：表示过滤器名称，可以不写
 * value：配置请求过滤的规则，如 "/*" 表示过滤所有请求，包括静态资源，如 "/user/*" 表示 /user 开头的所有请求
 */
@WebFilter(filterName = "SystemFilter", value = {"/*"})
public class SystemFilter implements Filter {
 
    @Override
    public void init(FilterConfig filterConfig) throws ServletException {
        System.out.println("com.wmx.servlet.SystemFilter -- 系统启动...");
    }
 
    @Override
    public void doFilter(ServletRequest servletRequest, ServletResponse servletResponse, FilterChain filterChain) throws IOException, ServletException {
        //转为 HttpServletRequest 输出请求路径
        HttpServletRequest request = (HttpServletRequest) servletRequest;
        System.out.println("com.wmx.servlet.SystemFilter -- 过滤器放行前...." + request.getRequestURL());
        filterChain.doFilter(servletRequest, servletResponse);
        System.out.println("com.wmx.servlet.SystemFilter -- 过滤器返回后...." + request.getRequestURL());
    }
 
    @Override
    public void destroy() {
        System.out.println("com.wmx.servlet.SystemFilter -- 系统关闭...");
    }
}

@WebListener

import javax.servlet.ServletContextEvent;
import javax.servlet.ServletContextListener;
import javax.servlet.annotation.WebListener;
 
/**
 * 标准 Servlet 监听器，实现 javax.servlet.ServletContextListener 接口，并重写方法
 * ServletContextListener 属于 Servlet 应用启动关闭监听器，监听容器初始化与销毁。常用的监听器还有：
 * ServletRequestListener：HttpServletRequest 对象的创建和销毁监听器
 * HttpSessionListener：HttpSession 数据对象创建和销毁监听器
 * HttpSessionAttributeListener 监听HttpSession中属性变化
 * ServletRequestAttributeListener 监听ServletRequest中属性变化
 */
@WebListener
public class SystemListener implements ServletContextListener {
    @Override
    public void contextInitialized(ServletContextEvent sce) {
        System.out.println("com.wmx.servlet.SystemListener -- 服务器启动.");
    }
 
    @Override
    public void contextDestroyed(ServletContextEvent sce) {
        System.out.println("com.wmx.servlet.SystemListener -- 服务器关闭.");
    }
}

@ServletComponentScan

注意：这三个注解在 Spring Boot 里默认不会被扫描，必须在启动类上补一个 @ServletComponentScan 才会生效。它与前面「注册 Bean」的方式可以共存，区别在于注解方式下 Servlet 组件的名称来自注解的 name / filterName 属性，而 Bean 方式下由 @Bean 方法名或 RegistrationBean.setName() 决定。

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.web.servlet.ServletComponentScan;
 
@SpringBootApplication
@ServletComponentScan //对 servlet 注解进行扫描
public class RedisStuWebApplication {
    public static void main(String[] args) {
        SpringApplication.run(RedisStuWebApplication.class, args);
    }
}
