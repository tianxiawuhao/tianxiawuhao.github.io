DOM、BOM 与事件

Posted on 2026-09-19，7 min read

从静态页面到可交互页面

前面几节写下的页面是“静态”的：HTML 决定结构，CSS 决定外观，浏览器把文件画到屏幕上，任务就结束了。可真实的产品必须对用户做出反应——点击按钮切换菜单、输入框实时校验、滚动到底部加载更多、刷新页面后仍然记得用户的偏好。让页面“活”起来的三件套就是 DOM（把页面变成程序可以读写的对象树）、BOM（操作浏览器窗口、地址、历史等浏览器级能力）与 事件（把用户动作变成回调函数的入口）。

这一章面向已经会写基本 HTML/CSS、想跨过“只能改样式”这道坎的读者。全章按“为什么需要 → 怎么做 → 示例 → 常见坑”的顺序走一遍，主要安排如下：

  • 先看 DOM 的节点模型与增删改查；
  • 再讲事件流、绑定方式与事件委托；
  • 然后用定时器配合闭包与 this 的规则解释几个经典翻车现场；
  • 最后对比 cookies、localStorage、sessionStorage 与 IndexedDB，给出该选谁的经验法则。

读完后应当能独立写出“待办清单”级别的小组件。

DOM：把页面看成一棵节点树

浏览器解析 HTML 时会构造一棵 DOM 树（Document Object Model）。页面上的每个标签、每段文本、每个属性在程序里都是一个对象，document 是这棵树的根入口。树上的一个对象叫节点，常见类型有元素节点（如 div）、文本节点、属性节点和注释节点。理解“一切皆节点”很关键：空白换行也是文本节点，所以遍历子节点时经常会遇到“看不见”的节点。

查找节点最常用的三类方法：document.getElementById(id) 返回单个元素；document.getElementsByClassName()、getElementsByTagName() 返回动态集合；document.querySelector(css) 与 querySelectorAll(css) 接受 CSS 选择器，前者返回第一个匹配元素，后者返回静态 NodeList。日常开发优先用后两个：选择器表达力强，返回结果也不会因为 DOM 后续变化而“自己变长”。

拿到节点之后，读写内容与属性有一套分层清晰的 API。innerHTML 会把字符串当 HTML 解析，方便但危险（见后文安全一节）；textContent 只当纯文本，写用户输入时应该用它。getAttribute/setAttribute 操作任意属性，而 element.dataset.xxx 专门读写 data-xxx 自定义属性，是“HTML 存数据、JS 取数据”的标准通道。样式通过 element.style 改内联样式，但更好的做法是切换 class：el.classList.add('active')。

增删改查的完整链条是“创建 → 填充 → 插入 → 移除”。document.createElement() 创建元素，append()/prepend() 插入到末尾或开头，before()/after() 以兄弟身份插入，remove() 把节点从树上摘掉。批量插入时先用 DocumentFragment 在内存里拼好，再一次性挂到文档上，能显著减少浏览器的重排次数。

// 用 DocumentFragment 批量插入，最后只触发一次重排
const list = document.querySelector('#todo-list');
const frag = document.createDocumentFragment();

['写周报', '评审代码', '修复线上告警'].forEach((text) => {
  const li = document.createElement('li');
  li.className = 'todo-item';
  li.dataset.id = String(Math.random()).slice(2, 8); // 对应 <li data-id="...">
  li.textContent = text;                            // 纯文本，天然防 XSS
  frag.append(li);
});

list.append(frag);
console.log(list.children.length);  // 3

BOM：窗口、地址与历史

BOM（Browser Object Model）没有 DOM 那样严格的标准，但各家实现高度一致，常用的只有几样。window 是全局对象，也是全局作用域里 this 的默认指向；location 管地址，改 location.href 会跳转，location.reload() 重载；history.pushState/replaceState 配合 popstate 事件可以做单页应用的无刷新路由。navigator 提供设备与语言信息，screen 提供屏幕尺寸。setTimeout、setInterval、alert 这些实际上都是 window 上的方法，只是写的时候省略了前缀。

这里要提醒一点：navigator.userAgent 可以从用户端任意伪造，用它做浏览器判断非常脆弱。正确思路是特性检测——直接判断某个 API 是否存在，例如 if ('IntersectionObserver' in window) { ... }，存在就用新方案，不存在就退回旧方案。

事件：流、绑定与委托

事件是页面与用户之间的通道。一次点击其实经历了三个阶段，这就是事件流：捕获阶段从 window 一路向下传到目标元素，随后进入目标阶段，最后是冒泡阶段从目标元素一路向上传回 window。绝大多数事件默认冒泡，所以父元素能“顺便”知道子元素上发生了什么。addEventListener(type, handler, options) 的第三个参数就是控制开关：{ capture: true } 让回调在捕获阶段执行，{ once: true } 让回调只执行一次后自动解绑，{ passive: true } 告诉浏览器“这个回调不会调用 preventDefault()”，从而让滚动更顺滑——这也是移动端 touchstart/wheel 性能优化的常用手段。

回调里的 event 对象携带了本次事件的上下文：event.target 是实际触发事件的元素，event.currentTarget 是绑定监听器的那个元素，两者在冒泡场景下往往不同。event.preventDefault() 阻止浏览器默认行为（比如链接跳转、表单提交），event.stopPropagation() 阻止事件继续传播。这两个方法作用完全不同，混用是新手最常见的表达错误。

既然事件会冒泡，就不必给每个子元素都挂监听器。事件委托的做法是：把监听器挂在父容器上，在回调里用 event.target.closest(selector) 找到真正被点击的元素，再根据它做分发。这样即使列表后续动态新增上百项，也只有一个监听器，省内存、好维护，不会因为忘记重新绑定而失效。

const list = document.querySelector('#todo-list');

list.addEventListener('click', (event) => {
  // closest 会从 target 起沿祖先链向上找，匹配不到返回 null
  const item = event.target.closest('.todo-item');
  if (!item || !list.contains(item)) return;   // 点在空白处则忽略

  if (event.target.matches('.btn-remove')) {
    item.remove();
  } else {
    item.classList.toggle('done');
  }
});

事件回调里的 this：丢失原因与三种修法

事件监听是 this 丢失最集中的地方。浏览器调用监听器时的调用点由它自己决定：用普通函数注册监听器，回调里的 this 就是绑定监听器的那个元素（即 event.currentTarget），而不是外层的对象；一旦把某个实例方法直接传给 addEventListener，调用方式退化成光杆调用，实例方法的 this 就丢了，访问 this.someField 会得到 undefined，严格模式下还会直接抛错。

三种写法可以保住实例的 this：在构造函数里用 this.handleClick = this.handleClick.bind(this) 预先固定；注册时现写一个箭头函数包装（() => this.handleClick(event)），由箭头函数做词法转接；或者干脆把处理器定义成箭头函数类字段，让它天然不带自己的 this。需要注意箭头函数回调拿不到“触发的元素”这份 this，但完全不影响 event.target/event.currentTarget，这也是现代代码更推荐通过 event 参数而非 this 取元素的原因。删除监听器时必须传入同一个函数引用，所以第二种写法要先把包装函数存成变量，否则解绑会失效。

class Counter {
  #count = 0;
  constructor(button) {
    this.button = button;
    // 修法一：在构造函数里 bind 一次，之后可以正常解绑
    this.handleClick = this.handleClick.bind(this);
    button.addEventListener('click', this.handleClick);
  }
  handleClick(event) {
    this.#count += 1;                        // this 是 Counter 实例
    this.button.textContent = `点击 ${this.#count} 次`;
    console.log(event.currentTarget === this.button);   // true
  }
  destroy() {
    this.button.removeEventListener('click', this.handleClick);   // 引用一致才解绑成功
  }
}

class Toggler {
  #open = false;
  constructor(el) {
    this.el = el;
    // 修法二：箭头函数类字段，词法继承实例 this，无需 bind
    el.addEventListener('click', (event) => this.toggle(event));
  }
  toggle() {
    this.#open = !this.#open;
    this.el.classList.toggle('open', this.#open);
  }
}

定时器、闭包与 this：三个经典坑

定时器看着简单，却是 this 与闭包最容易翻车的地方。setTimeout(fn, delay) 把回调推迟到至少 delay 毫秒之后执行，返回一个数字句柄，用 clearTimeout(handle) 取消；setInterval 同理，用 clearInterval 取消。注意“至少”这个词：定时器回调进入的是宏任务队列，必须等当前同步代码和已排队的微任务都执行完，所以它的实际延迟总是大于等于你写的值，不要用它做精确计时。

第一个坑是 this 丢失。把对象方法直接当回调传进去时，调用方式变成了“光杆调用”，this 不再指向那个对象。JS 的 this 规则可以浓缩成一句话：只由调用方式决定，优先级从低到高是 fn() → obj.fn() → fn.call(obj) → new fn()。光杆调用在非严格模式下 this 是 window，严格模式和 ES Module 里是 undefined。另外，this 是在函数被调用时确定的，而作用域是在函数声明时就确定好的——这两者不是一回事。

第二个坑是“谁在定义时被记住”。ES6 的箭头函数没有自己的 this、arguments，也没有 prototype，不能当构造函数用；它里面的 this 就是外层函数的 this，且用 call/apply/bind 也改不掉。因此事件回调和定时器回调里想沿用外层的 this，箭头函数通常是最省心的选择。

第三个坑是循环里绑定回调。var 只有函数作用域，循环里的 i 自始至终是同一个变量；let 在每次迭代都会创建一个新的绑定，回调各自记住自己那一份。这就是下面这段代码差别如此之大的原因，也是老项目中“用 IIFE 包一层”写法的由来。

// var：每次迭代共用同一个 i，输出 5 5 5 5 5
for (var i = 1; i <= 5; i++) {
  setTimeout(function () { console.log(i); }, 0);
}

// let：每次迭代都有独立的绑定，输出 1 2 3 4 5
for (let j = 1; j <= 5; j++) {
  setTimeout(function () { console.log(j); }, 0);
}

最后说清闭包。当函数能够记住并访问它所在的词法作用域时，闭包就产生了。上面的 let 版本、防抖节流里保存的定时器句柄、单例模式里被两个方法共享的 count，本质都是闭包：外层函数早已返回，内层函数仍然握着那份作用域。闭包不是需要刻意“制造”的技巧，而是 JS 作用域规则的必然结果；需要注意的只是别让闭包长期持有大对象，否则内存无法释放。

本地存储：cookies、localStorage、sessionStorage 与 IndexedDB

早期前端只能用 cookie 在客户端存数据，它的设计目标是给 HTTP 请求携带状态，而不是当数据库用。它有几个先天限制：每次同源请求都会自动带上（白白增加流量），单个 cookie 约 4KB，数量还有上限，而且默认在明文 HTTP 下也会传输。正是这些限制，促使 HTML5 引入了 Web Storage 与 IndexedDB。

localStorage 与 sessionStorage 的 API 完全一样：setItem(key, value)、getItem(key)、removeItem(key)、clear()，容量约 5MB。区别在生命周期与共享范围：localStorage 除非主动删除否则一直存在，同源的多个标签页共享；sessionStorage 只在当前标签页的会话期内有效，同一标签页内的刷新会保留，但新开标签页和关闭标签页后就没了。两者都只能存字符串，存对象要 JSON.stringify 与 JSON.parse 配对使用。

IndexedDB 是浏览器里的异步事务型数据库，容量按磁盘配额给（通常是可用空间的很大比例），支持索引、游标和二进制存储，适合离线应用缓存大量结构化数据。代价是 API 基于回调与事务，写起来明显啰嗦——Web Storage 只需要一行，IndexedDB 往往需要打开数据库、建对象仓库、发起事务好几个步骤，教程阶段先知道“数据量大或需要索引时用它”即可。

// Web Storage 存对象：序列化进去，解析出来
const tags = ['java', 'web', 'dom'];
localStorage.setItem('tags', JSON.stringify(tags));

const saved = JSON.parse(localStorage.getItem('tags') || '[]');
console.log(saved.join('/'));        // java/web/dom

localStorage.removeItem('tags');

// 监听同源其他标签页的变更（本标签页自身的修改不会触发）
window.addEventListener('storage', (e) => {
  console.log(e.key, e.oldValue, e.newValue);
});

小结

本章把“页面变活”的四个零件串成了一条线。DOM 负责读写页面：用 querySelector 查找，用 textContent/dataset/classList 读写，用 createElement 加 DocumentFragment 批量插入，用 remove() 移除。BOM 负责浏览器级能力：location、history、定时器都在 window 上，能力检测永远优于 UA 嗅探。

事件的核心是事件流与委托：把监听器挂在稳定的父容器上，用 event.target 与 closest() 分发，用 { once: true }、{ passive: true } 这些选项把细节交给浏览器。存储的选型记一条线：少量键值用 localStorage 或 sessionStorage，需要跨请求传给服务端才用 cookie，数据量大、要索引或要事务就上 IndexedDB。

最后留三个务必记住的坑：innerHTML 拼用户输入等于自开 XSS 大门，请改用 textContent 或先做转义；this 只由调用方式决定，回调里用箭头函数能避开大部分麻烦；var 在循环里只有一个变量，换成 let 才是正解。
