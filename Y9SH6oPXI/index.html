Spring使用ThreadLocal存储内存泄露风险

Posted on 2022-08-23，5 min read

Spring 中有时候需要存储一些和 Request 相关联的变量，例如用户登录信息等，它们的生命周期与 Request 相同。一个容易想到的实现办法是使用 ThreadLocal。

Spring 中保存请求上下文的常见做法

先写一个基于 ThreadLocal 的工具类：

@Slf4j
public class CurrentUserHelper {

    // 注意：InheritableThreadLocal 只在线程「被创建」时把值复制给子线程，
    // 线程池中的线程是复用的，详见后文「InheritableThreadLocal 与 TTL」一节
    private static final InheritableThreadLocal<SysUser> CURRENT_USER =
            new InheritableThreadLocal<>();

    public static void setCurrentUser(SysUser user) {
        CURRENT_USER.set(user);
    }

    public static SysUser getCurrentUser() {
        return CURRENT_USER.get();
    }

    public static void clear() {
        CURRENT_USER.remove();
    }
}

再写一个 HandlerInterceptor，在请求开始时把用户信息注入进去：

@Slf4j
@Component
public class RequestInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        CurrentUserHelper.setCurrentUser(retrieveUserInfo(request));
        return true;   // 返回 true 之后，本拦截器才会被登记为 preHandle 成功
    }

    @Override
    public void postHandle(HttpServletRequest request, HttpServletResponse response,
                           Object handler, @Nullable ModelAndView modelAndView) {
        // 只覆盖「Controller 正常返回」的情况：抛异常时 postHandle 不会被调用
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, @Nullable Exception ex) {
        // 正常返回或抛异常，DispatcherServlet 都会回调这里
        CurrentUserHelper.clear();
    }

    private SysUser retrieveUserInfo(HttpServletRequest request) {
        // 从 Token / Session 中解析用户信息
        return null;
    }
}

这样在 Controller 里就能直接取到当前用户，不用一层层传参：

@Slf4j
@RestController
@RequestMapping("/api")
public class UserController {

    @GetMapping("/me")
    public Result<SysUser> me() {
        SysUser user = CurrentUserHelper.getCurrentUser();
        // 直接使用
        return Result.ok(user);
    }
}

这个写法在很多博客里都能看到，但它藏着一个很隐蔽的坑：HandlerInterceptor 的 postHandle 并不总是会被调用，而清理逻辑一旦放在 postHandle 里，就会漏掉异常路径。

坑：postHandle 并不总会被调用

第一种情况是 Controller 抛出了异常：

@GetMapping("/boom")
public Result<Void> boom() {
    SysUser user = CurrentUserHelper.getCurrentUser();
    log.info("current user = {}", user == null ? null : user.getId());
    throw new IllegalStateException("业务异常");   // postHandle 不会被调用
}

第二种情况是在 preHandle 里设置完值之后又抛出了异常：

@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    CurrentUserHelper.setCurrentUser(retrieveUserInfo(request));
    if (!checkPermission(request)) {
        // 本拦截器的 afterCompletion 不会被调用：interceptorIndex 只在
        // preHandle 返回 true 之后才前移，此时它还没轮到本拦截器
        throw new IllegalStateException("权限校验失败");
    }
    return true;
}

这两条路径都绕过了 postHandle（第二条连 afterCompletion 也一起绕过了），ThreadLocal 里的值因此没有被清掉。在普通的 Java 环境里，ThreadLocal 变量会随 Thread 一起销毁；但 Spring Web 用的是线程池，响应请求的线程会一直常驻，于是变量既不能被 GC 回收，又会在后续请求中被同一线程读到——线程池复用直接把上一个请求的数据「串」到了下一个请求里。

更危险的是，文章开头那份示例代码把异常吞掉了：

try {
    CurrentUserHelper.setCurrentUser(retrieveUserInfo(request));
} catch (Exception ex) {
    log.warn("读取请求信息失败", ex);   // 解析失败时不 set，也不 clear
}
return true;

一旦解析用户信息失败，本线程上残留的仍是上一个请求的用户对象。如果这时来的是一个匿名请求，getCurrentUser() 就会返回上一个请求的用户——这不是单纯的「内存泄漏」，而是实实在在的越权隐患。

因此清理动作有两个可靠落点：

  • 拦截器里放在 afterCompletion（正常和异常都会回调），同时保证 preHandle 在 set 之后不再抛异常；
  • 更稳妥的是用 Filter 包住整条链路：
@Slf4j
@Component
public class CurrentUserFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        try {
            CurrentUserHelper.setCurrentUser(retrieveUserInfo(request));
            chain.doFilter(request, response);
        } finally {
            // Filter 位于 DispatcherServlet 之外，无论异常、转发还是正常返回都会执行
            CurrentUserHelper.clear();
        }
    }
}

更省心的方案：RequestContextHolder

Spring 自带的 RequestContextHolder 底层同样是 ThreadLocal，但它的生命周期由框架自己管理：FrameworkServlet#processRequest 会在 finally 中调用 resetContextHolders(...)，RequestContextListener、RequestContextFilter 也会在请求结束时清理，所以它不会跨请求残留。

public abstract class SecurityContextHolder {

    private static final String SECURITY_CONTEXT_ATTRIBUTES = "SECURITY_CONTEXT";

    public static void setContext(SysUser user) {
        RequestContextHolder.currentRequestAttributes()
                .setAttribute(SECURITY_CONTEXT_ATTRIBUTES, user, RequestAttributes.SCOPE_REQUEST);
    }

    public static SysUser getContext() {
        Object value = RequestContextHolder.currentRequestAttributes()
                .getAttribute(SECURITY_CONTEXT_ATTRIBUTES, RequestAttributes.SCOPE_REQUEST);
        return (SysUser) value;
    }
}

注意 SCOPE_REQUEST 实际是把对象写进 HttpServletRequest 的属性表（SCOPE_SESSION 才会写进 Session），随请求一起被回收；currentRequestAttributes() 在没有绑定请求的线程（例如自己 new 出来的线程或 @Async 线程）上会抛 IllegalStateException: No thread-bound request found。

注册拦截器时，实现 WebMvcConfigurer（或 WebMvcConfigurationSupport）并重写 addInterceptors：

@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        // 配置允许跨域访问的路径
        registry.addMapping("/**")
                .allowedOrigins("*")
                .allowedMethods("GET", "POST", "DELETE", "PUT")
                .allowedHeaders("*")
                .exposedHeaders("Access-Control-Allow-Origin")
                .allowCredentials(true)
                .maxAge(3600);
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new RequestInterceptor()).addPathPatterns("/**");
    }
}

除了 RequestContextHolder，还可以使用 Request Scope 的 Bean，或者 ThreadLocalTargetSource，原理类似：把「每个请求一份」的状态交给框架按请求生命周期管理，而不是自己在线程上挂东西。

需要时刻记住：ThreadLocal 相当于把变量挂在线程对象上，是一个很容易泄漏的位置；而且只要用了线程池，清理责任就完全在使用者身上。

ThreadLocal 可能会产生内存泄露的问题及原理

下面从源码角度看清楚「为什么必须 remove」。

为什么会产生内存泄露？

public void set(T value) {
    Thread t = Thread.currentThread();
    ThreadLocalMap map = getMap(t);
    if (map != null) {
        map.set(this, value);
    } else {
        createMap(t, value);
    }
}

ThreadLocalMap getMap(Thread t) {
    return t.threadLocals;   // 每个线程私有的一个字段
}

可以看到，值并没有存在 ThreadLocal 对象里，而是存在当前线程的 threadLocals 字段（一个 ThreadLocalMap）中，以 ThreadLocal 实例自身作为 key。于是引用链变成了：

GC Roots(Thread) → Thread.threadLocals → ThreadLocalMap → Entry[] table → Entry → value

线程不结束，这条链就一直存在。线程池里的工作线程（默认不超时回收）几乎与进程同寿，所以哪怕请求早已结束，value 依然被强引用着——这就是「内存泄漏」的来源。

JVM 解决的办法

为了不让 ThreadLocal 实例本身拖住整个 Map，JDK 把 Entry 的 key 设计成了弱引用：

static class Entry extends WeakReference<ThreadLocal<?>> {

    /** The value associated with this ThreadLocal. */
    Object value;

    Entry(ThreadLocal<?> k, Object v) {
        super(k);       // key 是弱引用（WeakReference），不是软引用
        value = v;      // value 是强引用
    }
}

注意这里是弱引用（WeakReference）而不是软引用（SoftReference）：外部不再持有 ThreadLocal 实例时，只要发生一次 GC，这个实例就会被回收，Entry 的 key 随之变成 null。问题是 value 仍然是强引用，Entry 又仍被线程的 threadLocals 强引用着，所以 value 不可能被回收，只是变得「不可访问」而已。

至于这些 key 为 null 的 Entry，只能靠 ThreadLocalMap 的探测式清理顺带回收：get() 命中时会调用 expungeStaleEntry，set() 会调用 cleanSomeSlots，rehash() 会调用 expungeStaleEntries，remove() 也会调用 expungeStaleEntry。也就是说，清理是「下次访问时顺手做」的启发式行为，而不是 GC 主动完成的。

由此可以得到两个结论，也回答了「为什么必须 remove」：

  • ThreadLocal 是 static final 时（最常见）：实例被类强引用，key 永远不会变成 null，弱引用一点忙都帮不上，Entry 永远不是 stale 的。此时 value 的唯一释放途径就是 remove()（或线程结束）。泄漏规模有上界——线程数 × 单个 value 的大小，但只要 value 本身很大（例如整棵权限树、整个 Request、大 List），常驻内存就非常可观。
  • ThreadLocal 是动态创建时：例如每次请求 new ThreadLocal<>()，或把它当作缓存的 key。实例一旦不可达，GC 后 key 变 null，但 Entry 与 value 仍留在数组里；只有当该线程再次执行 get/set/remove 触发清理时才会被回收。线程池中那些不再被调度到的空闲线程，就会长期保留这些 stale Entry 和它们的 value，泄漏几乎没有上界。

线程池下的两种故障：内存泄漏与数据串号

下面的程序可以同时观察到「泄漏」和「串号」两个现象：

public class ThreadLocalLeakDemo {

    /** 模拟请求上下文（这里用 16MB 的字节数组代替权限树之类的大对象） */
    private static final ThreadLocal<byte[]> USER_CONTEXT = new ThreadLocal<>();

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(4);   // 4 个常驻线程
        CountDownLatch latch = new CountDownLatch(200);
        for (int i = 0; i < 200; i++) {
            pool.execute(() -> {
                try {
                    USER_CONTEXT.set(new byte[16 * 1024 * 1024]);   // 只 set，不 remove
                } finally {
                    latch.countDown();
                }
            });
        }
        latch.await();
        System.out.println("任务都执行完了，但 4 个工作线程仍各强引用一份 16MB 上下文");
        System.in.read();   // 阻塞，方便用 jmap / MAT 观察
    }
}

# 堆只有 64MB，而 4 个工作线程各常驻 16MB：很快 OOM 或频繁 Full GC
java -Xmx64m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./ ThreadLocalLeakDemo

关键在于：这 200 个任务早已执行完毕，没有任何一个对象还被业务代码引用，但 4 份 16MB 的数据依然活着。占用的多少与请求量无关，只取决于「线程数 × value 大小」。

数据串号则更隐蔽：

// 任务 A：用户 1 的请求，set 之后没有清理
pool.execute(() -> CurrentUserHelper.setCurrentUser(user1));

// 任务 B：用户 2 的匿名请求。解析失败走了 catch 分支，没有 set，
// 于是同一线程上的 getCurrentUser() 返回了 user1
pool.execute(() -> System.out.println(CurrentUserHelper.getCurrentUser()));

所以「忘记 remove」的后果不只是内存，还可能是权限判断、租户隔离、审计日志全部串到别的用户身上。

用 MAT 定位 ThreadLocal 泄漏

先在堆上把它抓下来：

# 1) 推荐：OOM 时自动 dump
java -Xmx64m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./ ThreadLocalLeakDemo

# 2) 进程还活着时手工 dump（live 只导出存活对象，更适合排查泄漏）
jcmd <pid> GC.heap_dump /tmp/heap.hprof
jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>

# 3) 先粗看对象数量与占用，确认怀疑对象
jmap -histo:live <pid> | head -20

然后用 Eclipse MAT 打开 hprof，按下面的顺序定位：

  1. 先看 Leak Suspects（泄漏疑点报告）：ThreadLocal 泄漏通常会把 java.lang.Thread 报成 suspect，并给出「一个线程实例 retained heap 异常大」的提示。
  2. 打开 Histogram，搜索 ThreadLocalMap$Entry 或直接搜业务对象类名（例如 byte[]、SysUser），按 retained heap 排序。
  3. 在 Histogram 中找到 java.lang.Thread → 右键 List objects → with outgoing references，展开 threadLocals → ThreadLocalMap → table（即 Entry[]）→ Entry → value，这就是被泄漏的对象。
  4. 对可疑的 value 执行 Path to GC Roots，并勾选 exclude weak references；根路径会呈现为 Thread → threadLocals → ThreadLocalMap → Entry[] → Entry → value，与前面的引用链完全对应。
  5. 如果怀疑是「动态 ThreadLocal 造成的 stale Entry」，在 Histogram 里留意 Entry 的数量是否远大于线程数，并检查这些 Entry 的 key 是否为 null；MAT 的 ThreadLocal 相关查询可以辅助确认。

一个容易踩的坑：ThreadLocal 对象自身的 retained heap 通常很小，不要因为它「看起来不大」就排除嫌疑，真正的大头在 Entry.value 上。

InheritableThreadLocal 与 TTL

InheritableThreadLocal 为什么在线程池里失效

InheritableThreadLocal 的机制在 Thread 的构造函数里：创建子线程时会调用 ThreadLocal.createInheritedMap(parent.inheritableThreadLocals)，把父线程的值复制一份给子线程（可通过 childValue() 定制）。它解决的是「父线程创建子线程时把上下文带过去」，只在线程创建的那一刻生效。

线程池里工作线程只在第一次提交任务（或预热）时创建，之后反复复用，于是：

  • 后续任务根本不会发生「继承」，拿到的要么是创建时那份陈旧的值，要么是 null；
  • 第一个任务留下的值会一直被后续所有任务读到，串号比普通 ThreadLocal 更严重；
  • 它同样是 ThreadLocal，忘了 remove 一样会泄漏。

因此在线程池场景下，InheritableThreadLocal 基本可以视为错误选择。

TransmittableThreadLocal 的用法

阿里开源的 transmittable-thread-local（TTL，坐标 com.alibaba:transmittable-thread-local，版本以 Maven Central 上的最新版为准）正是为解决这个问题而生：TransmittableThreadLocal 继承自 InheritableThreadLocal，但值的传递不依赖线程创建，而是由 Transmitter 在任务提交时抓取快照、在任务执行前回放到工作线程、执行结束后再恢复工作线程原有的值。

public final class UserContext {

    /** 用 TTL 替换 InheritableThreadLocal */
    private static final TransmittableThreadLocal<SysUser> CURRENT_USER =
            new TransmittableThreadLocal<>();

    public static void set(SysUser user) {
        CURRENT_USER.set(user);
    }

    public static SysUser get() {
        return CURRENT_USER.get();
    }

    public static void remove() {
        CURRENT_USER.remove();
    }
}

// 1) 包装线程池：提交任务时 capture，执行时 replay，执行后 restore
ExecutorService pool = TtlExecutors.getTtlExecutorService(Executors.newFixedThreadPool(4));
pool.execute(() -> System.out.println(UserContext.get()));

// 2) 也可以只包装单个任务
pool.execute(TtlRunnable.get(() -> System.out.println(UserContext.get())));
// 有返回值的任务用 TtlCallable.get(...)

// 3) 生产环境更省事的做法：启动参数挂上 java agent，自动装饰所有线程池
//    -javaagent:path/to/transmittable-thread-local-x.y.z.jar

要注意 TTL 只是「把值正确地传过去」，并不会替你清理；remove() 依然要写在 finally 或框架的回收点里，否则值会跟着池化线程一直活下去。

Spring @Async 与线程池场景

@Async 方法最终跑在 TaskExecutor 上（Spring Boot 2.1 之后默认会自动配置名为 applicationTaskExecutor 的 ThreadPoolTaskExecutor）。由此带来三件事：

  • 异步线程里不能再依赖 RequestContextHolder：默认的 request attributes 存在普通 ThreadLocal 中，currentRequestAttributes() 会抛 No thread-bound request found；
  • 调用 RequestContextHolder.setRequestAttributes(attrs, true) 虽然会启用 inheritable 的 holder，但正如上文所述，池化线程下依然会串号、会泄漏，只适合线程不复用的场景；
  • 推荐做法：要么把需要的参数显式作为方法参数传进异步任务，要么用 TTL，并把它接到 Spring 的 TaskDecorator 上。
@Configuration
public class AsyncConfig {

    @Bean("taskExecutor")
    public ThreadPoolTaskExecutor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(8);
        executor.setMaxPoolSize(32);
        executor.setQueueCapacity(1000);
        executor.setThreadNamePrefix("async-");
        // 关键：任务提交时捕获上下文，在池化线程中回放
        executor.setTaskDecorator(TtlRunnable::get);
        executor.initialize();
        return executor;
    }
}

最佳实践清单

  • 声明成 private static final ThreadLocal<T>，不要每次请求 new ThreadLocal（避免制造 stale Entry）。
  • 谁 set 谁 remove，remove() 放在 finally 里，不要在多个分支里零散地清。
  • Web 层优先用 Filter 的 try-finally；用 HandlerInterceptor 时把清理放在 afterCompletion，并保证 preHandle 在 set 之后不再抛异常。
  • 线程池侧兜底：自定义 ThreadPoolTaskExecutor 的 TaskDecorator，或在 ThreadPoolExecutor#afterExecute 里做清理/断言。
  • 异步传递上下文优先显式传参或用 TTL（TtlRunnable/TtlExecutors/TaskDecorator，必要时挂 java agent），不要依赖 InheritableThreadLocal。
  • value 尽量存不可变的小对象；不要把整个 Request、Session 或大集合塞进去。
  • 能交给框架就别自己管：请求级状态优先用 RequestContextHolder、Request Scope Bean 或 ThreadLocalTargetSource。
  • 线上开启 -XX:+HeapDumpOnOutOfMemoryError，并定期用 jmap -histo:live 观察 Entry/ThreadLocalMap 的数量趋势。

一句话总结：ThreadLocal 的 key 是弱引用、value 是强引用，而线程池让线程「长生不老」，所以清理 ThreadLocal 从来不是可选项，必须依靠 try-finally 或框架的回收点。
