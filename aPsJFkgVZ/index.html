第三章 Flink 部署

Posted on 2021-04-09，5 min read

Flink 部署模式概览

Flink 的部署方式可以归纳为三类：Standalone、YARN 和 Kubernetes。三者的运行架构完全相同——都是 JobManager 负责调度与协调、TaskManager 提供 slot 执行 subtask，区别只在于资源由谁分配、进程由谁拉起。Standalone 自己管理进程和资源；YARN 与 Kubernetes 把资源调度和进程编排交给外部平台，Flink 只负责作业本身。

三种模式的关键差异可以概括为下表：

对比项StandaloneYARNKubernetes
资源来源各节点本地资源，静态划分NodeManager 动态分配 Container调度器拉取 Pod
集群生命周期常驻，扩容需改 slaves 后重启Session 常驻；Per-Job / Application 随作业生死Session 常驻；Application 随作业生死
提交入口flink run -c 主类 -p 2 app.jarflink run -t yarn-applicationflink run -t kubernetes-application
高可用ZooKeeper + 共享存储目录YARN 重启 ApplicationMasterPod 重建 + Kubernetes HA 服务
适用场景开发测试、固定资源小集群已有 Hadoop 集群的大规模生产云原生、弹性扩缩容

Standalone 模式

安装

解压 flink-1.10.1-bin-scala_2.12.tgz，进入 conf 目录，需要修改两个配置文件并分发到集群的所有节点。

  1. 修改 conf/flink-conf.yaml，指定 JobManager 地址以及各角色的内存与并行度：

    # JobManager 的 RPC 地址：standalone 模式下必须显式指向 Master 节点
jobmanager.rpc.address: hadoop102
jobmanager.rpc.port: 6123

# JobManager 进程可用内存（Flink 1.10 及更早）
jobmanager.heap.size: 1024m
# TaskManager 进程可用内存与 slot 数（Flink 1.10 及更早）
taskmanager.heap.size: 1024m
taskmanager.numberOfTaskSlots: 2
parallelism.default: 2

# 历史服务器与 Web UI
jobmanager.web.port: 8081
historyserver.web.port: 8082

    注意：taskmanager.heap.size 与 jobmanager.heap.size 是 Flink 1.10 之前的写法；从 Flink 1.10 开始内存模型细分为框架堆、托管内存、网络缓冲区等多个区域，推荐改用进程总内存 taskmanager.memory.process.size 与 jobmanager.memory.process.size（见下文「内存配置」）。

  2. 修改 conf/slaves（Flink 1.11 起该文件更名为 workers），每一行写一台 TaskManager 节点：

    hadoop102
hadoop103
hadoop104

    conf/slaves 只决定 start-cluster.sh 通过 SSH 去哪些机器拉起 TaskManager 进程；每台机器上的 slot 数仍然由各自的 taskmanager.numberOfTaskSlots 决定，两者的乘积才是集群总 slot 数。

  3. 把整个解压目录分发到另外两台机器（目录结构必须保持一致，否则启动脚本会找不到路径）：

    xsync flink-1.10.1/

  4. 启动集群并访问 Web UI：

    # 在配置了 slaves 的节点上启动 JobManager 与所有 TaskManager
bin/start-cluster.sh

# 需要停止时
bin/stop-cluster.sh

    浏览器访问 http://hadoop102:8081，即可查看集群与任务的运行情况。

提交任务

  1. 准备数据文件（如果作业需要从本地磁盘读取）：
mkdir -p /opt/module/flink-1.10.1/input
echo -e "hello flink\nhello world\nhello flink" > /opt/module/flink-1.10.1/input/words.txt
  1. 把含数据文件的文件夹分发到 taskmanager 机器中：
xsync /opt/module/flink-1.10.1/input

如果从文件中读取数据，由于是从本地磁盘读取，实际任务会被分发到 taskmanager 的机器中，所以要把目标文件分发到每一台 TaskManager。

  1. 执行程序：
./bin/flink run -c com.atguigu.wc.StreamWordCount -p 2 \
  FlinkTutorial-1.0-SNAPSHOT-jar-with-dependencies.jar --host localhost --port 7777

常用参数：-c 指定入口类（jar 的 Main-Class 没写时必须指定）；-p 指定作业并行度，会覆盖配置文件的 parallelism.default；-d 表示 detached 模式，提交后立即返回；最后的 --host --port 才是传给应用程序 main() 的参数。注意原文命令里的 –p、–port 是排版时被替换成了长破折号，实际必须写成半角减号 -p、--port，否则参数会被当成主类名而报错。

  1. 到目标文件夹中查看计算结果。
    注意：如果计算结果输出到文件，会保存到 taskmanager 的机器下，不会在 jobmanager 下。
ls /opt/module/flink-1.10.1/output
cat /opt/module/flink-1.10.1/output/*
  1. 在 Web UI 控制台查看计算过程：Running Jobs 页可以看到各算子的 subtask、数据流量与反压情况，Task Managers 页可以看到每个 TaskManager 的 slot 占用。

Standalone 高可用配置

Standalone 集群默认只有一个 JobManager，它一旦宕机整个集群就不可用。生产环境需要配置高可用（HA）：多个 JobManager 通过 ZooKeeper 选举出唯一 leader，作业的元数据（JobGraph、Checkpoint 指针）写入共享存储目录，新 leader 从该目录恢复作业。

# 1) 与 zookeeper 相关的配置
high-availability: zookeeper
high-availability.zookeeper.quorum: hadoop102:2181,hadoop103:2181,hadoop104:2181
high-availability.zookeeper.path.root: /flink
high-availability.cluster-id: /default_ns

# 2) 存放 JobManager 元数据（JobGraph 与 Checkpoint 指针）的共享目录，必须是 HDFS/S3 等共享文件系统
high-availability.storageDir: hdfs://hadoop102:9000/flink/ha/

# 3) 使用 ZooKeeper 作为 HA 后，JobManager 地址改为从 ZK 获取
# jobmanager.rpc.address 不再需要指向固定主机

# 4) 高可用时的默认文件系统
fs.default-scheme: hdfs://hadoop102:9000

# 在 conf/masters 中列出所有候选 JobManager（每行一个 主机:web端口）
echo "hadoop102:8081" >> conf/masters
echo "hadoop103:8081" >> conf/masters

# 依次启动多个 JobManager 与所有 TaskManager
bin/start-cluster.sh

需要区分两个层面的高可用：JobManager 高可用解决「主节点宕机」，靠 ZooKeeper 选举加共享存储；任务级容错解决「TaskManager 或作业失败」，靠 Checkpoint 与重启策略（见第五章状态与 Checkpoint 一节）。两者缺一不可。

内存配置

Flink 1.10 起内存被划分为若干区域，理解这些区域才能正确设置参数：

  • JVM 堆（Heap）：框架堆与用户代码堆，运行算子和用户对象。
  • 托管内存（Managed Memory）：排序、哈希表、RocksDB 状态后端使用，由 Flink 自己管理。
  • 网络内存（Network）：TaskManager 之间数据交换的缓冲区，直接影响吞吐与反压表现。
  • JVM 元空间、Overhead 与 JVM 自身开销：由 Flink 预留或 JVM 占用。

因此推荐用进程总内存来配置，其余区域自动推算：

# 以进程总内存为单位配置（推荐，Flink 1.10+）
jobmanager.memory.process.size: 1600m
taskmanager.memory.process.size: 2048m

# 需要单独调大网络缓冲区时（影响数据交换与反压）
taskmanager.memory.network.min: 64mb
taskmanager.memory.network.max: 1gb

YARN 与 Kubernetes 模式下，提交命令中的 -Djobmanager.memory.process.size、-Dtaskmanager.memory.process.size 会覆盖配置文件；taskmanager.numberOfTaskSlots 与 parallelism.default 同理可用 -D 指定。

并行度与 slot 设置

Flink 中「并行度」有三个层次，优先级由低到高：

  1. 配置文件：parallelism.default: 2，作用于整个集群的默认值。
  2. 提交命令：-p 4 或 -Dparallelism.default=4，作用于本次提交的作业。
  3. 代码中：env.setParallelism(4) 或对单个算子调用 operator.setParallelism(2)，优先级最高。

slot 是 TaskManager 上的资源单位，一个 slot 代表 TaskManager 的一份固定资源子集（内存等），算子链中的多个 subtask 可以共享同一个 slot。集群总 slot 数 = TaskManager 数量 × taskmanager.numberOfTaskSlots。一个作业所需 slot 数 = 作业中最大并行度（在 slot 共享组内计算），与作业的算子数量无关。

# 每个 TaskManager 提供 4 个 slot
taskmanager.numberOfTaskSlots: 4
# 提交时让 8 个 subtask 分布在 2 个 TaskManager 上
parallelism.default: 8

Yarn 模式

以 Yarn 模式部署 Flink 任务时，要求 Flink 是有 Hadoop 支持的版本（flink-1.10.1-bin-scala_2.12.tgz 这类不带 hadoop 的包需要额外下载对应 Hadoop 版本的依赖 jar），Hadoop 环境需要保证版本在 2.2 以上，并且集群中安装有 HDFS 服务。

Flink on Yarn

Flink 提供了三种在 yarn 上运行的模式：Session-Cluster、Per-Job-Cluster（Flink 1.15 起被标记废弃）和 Application 模式（Flink 1.11 引入）。

  1. Session-cluster 模式：

Session-Cluster 模式需要先启动集群，然后再提交作业，接着会向 yarn 申请一块空间后，资源永远保持不变。如果资源满了，下一个作业就无法提交，只能等到 yarn 中的其中一个作业执行完成后释放了资源，下个作业才会正常提交。所有作业共享 Dispatcher 和 ResourceManager，共享资源，适合规模小、执行时间短的作业。

在 yarn 中初始化一个 flink 集群，开辟指定的资源，以后提交任务都向这里提交。这个 flink 集群会常驻在 yarn 集群中，除非手工停止。

  1. Per-Job-Cluster 模式：

一个 Job 会对应一个集群，每提交一个作业会根据自身的情况单独向 yarn 申请资源，直到作业执行完成，一个作业的失败与否并不会影响下一个作业的正常提交和运行。独享 Dispatcher 和 ResourceManager，按需申请资源，适合规模大、长时间运行的作业。

每次提交都会创建一个新的 flink 集群，任务之间互相独立、互不影响，方便管理，任务执行完成之后创建的集群也会消失。

补充：Application 模式（Flink 1.11 引入，2.x 推荐）与 Per-Job 一样是「一作业一集群」，但 main() 方法在集群中执行而不是在客户端执行，因此客户端不再需要下载大量依赖、也不承担生成 JobGraph 的开销，是当前生产环境的首选。

Session Cluster

  1. 启动 hadoop 集群（略）。
  2. 启动 yarn-session：
./bin/yarn-session.sh -n 2 -s 2 -jm 1024 -tm 1024 -nm test -d

其中：

-n(--container)：TaskManager 的数量。
-s(--slots)：每个 TaskManager 的 slot 数量，默认一个 slot 一个 core。默认每个 taskmanager 的 slot 个数为 1，有时可以多一些 taskmanager，做冗余。
-jm：JobManager 的内存（单位 MB）。
-tm：每个 taskmanager 的内存（单位 MB）。
-nm：yarn 的 appName（显示在 yarn ui 上的名字）。
-d：后台执行（detached）。

上述参数是 yarn-session.sh 的专用参数；Flink 1.11 之后这些配置也可以统一写成 -D 形式，例如 -Dtaskmanager.numberOfTaskSlots=2。

  1. 执行任务：
./bin/flink run -c com.atguigu.wc.StreamWordCount \
  FlinkTutorial-1.0-SNAPSHOT-jar-with-dependencies.jar --host localhost --port 7777
  1. 去 yarn 控制台查看任务状态：yarn application -list 或者 YARN ResourceManager UI（默认 8088 端口）。
  2. 取消 yarn-session：
yarn application -kill application_1577588252906_0001

Per Job Cluster

  1. 启动 hadoop 集群（略）。
  2. 不启动 yarn-session，直接执行 job：
# Flink 1.10 的写法
./bin/flink run -m yarn-cluster -c com.atguigu.wc.StreamWordCount \
  FlinkTutorial-1.0-SNAPSHOT-jar-with-dependencies.jar --host localhost --port 7777

# 推荐写法：1.11 起用 -t 指定部署目标，不再使用 -m yarn-cluster
./bin/flink run -t yarn-per-job -c com.atguigu.wc.StreamWordCount \
  FlinkTutorial-1.0-SNAPSHOT-jar-with-dependencies.jar --host localhost --port 7777

# Application 模式：main() 在集群中执行，生产环境首选
./bin/flink run -t yarn-application \
  -Djobmanager.memory.process.size=1024m \
  -Dtaskmanager.memory.process.size=1024m \
  -Dtaskmanager.numberOfTaskSlots=2 \
  FlinkTutorial-1.0-SNAPSHOT-jar-with-dependencies.jar --host localhost --port 7777

版本差异要特别注意：Flink 1.10 使用 bin/yarn-session.sh 与 flink run -m yarn-cluster；Flink 1.11 起 yarn-session.sh 被 bin/yarn-session.sh（新参数体系）与 -t yarn-session 取代，Per-Job 推荐 -t yarn-per-job；Flink 2.x 已经移除了 -m yarn-cluster 与 yarn-session.sh，只能使用 -t yarn-session、-t yarn-per-job、-t yarn-application 三种目标。旧教程里的 -m yarn-cluster 在 2.x 上会直接报错。

YARN 高可用与内存

YARN 模式的高可用由两套机制配合完成：

  • ApplicationMaster 重试：Flink 的 JobManager 运行在 YARN 的 ApplicationMaster 中，AM 失败时由 YARN ResourceManager 重新拉起，重试次数由 yarn.application-attempts（默认 1）或 yarn.resourcemanager.am.max-attempts 控制。作业状态则从 Checkpoint 恢复。
  • JobManager 内部高可用：需要多个 AM 候选时，配置 high-availability: zookeeper 与 high-availability.storageDir，与 Standalone 的配置一致。
# 允许 AM 失败后由 YARN 重试的次数（Flink 1.10 参数名）
yarn.application-attempts: 3
# HA 元数据存储位置
high-availability: zookeeper
high-availability.zookeeper.quorum: hadoop102:2181,hadoop103:2181,hadoop104:2181
high-availability.storageDir: hdfs://hadoop102:9000/flink/ha/

Kubernetes 部署

容器化部署是目前业界很流行的一项技术，基于 Docker 镜像运行能够让用户更加方便地对应用进行管理和运维。容器管理工具中最为流行的就是 Kubernetes（k8s），而 Flink 也在最近的版本中支持了 k8s 部署模式。

手工部署 Flink Session Cluster

  1. 搭建 Kubernetes 集群（略）。
  2. 配置各组件的 yaml 文件：

在 k8s 上构建 Flink Session Cluster，需要将 Flink 集群的组件对应的 docker 镜像分别在 k8s 上启动，包括 JobManager、TaskManager、JobManagerService 三个服务，每个镜像服务都可以从中央镜像仓库中获取。

# jobmanager-service.yaml：给 JobManager 暴露 Web UI 与 RPC 端口
apiVersion: v1
kind: Service
metadata:
  name: flink-jobmanager
spec:
  type: ClusterIP
  ports:
    - name: rpc
      port: 6123
    - name: blob-server
      port: 6124
    - name: webui
      port: 8081
  selector:
    app: flink
    component: jobmanager

# jobmanager-deployment.yaml：JobManager 容器
apiVersion: apps/v1
kind: Deployment
metadata:
  name: flink-jobmanager
spec:
  replicas: 1
  selector:
    matchLabels:
      app: flink
      component: jobmanager
  template:
    metadata:
      labels:
        app: flink
        component: jobmanager
    spec:
      containers:
        - name: jobmanager
          image: flink:1.10.1-scala_2.12
          args: ["jobmanager"]
          ports:
            - containerPort: 6123
            - containerPort: 8081

# taskmanager-deployment.yaml：TaskManager 容器，replicas 决定 TaskManager 个数
apiVersion: apps/v1
kind: Deployment
metadata:
  name: flink-taskmanager
spec:
  replicas: 2
  selector:
    matchLabels:
      app: flink
      component: taskmanager
  template:
    metadata:
      labels:
        app: flink
        component: taskmanager
    spec:
      containers:
        - name: taskmanager
          image: flink:1.10.1-scala_2.12
          args: ["taskmanager"]
          ports:
            - containerPort: 6122
          env:
            # TaskManager 必须能解析并连上 JobManager 的 Service 名
            - name: JOB_MANAGER_RPC_ADDRESS
              value: flink-jobmanager
  1. 启动 Flink Session Cluster：
# 启动 jobmanager-service 服务
kubectl create -f jobmanager-service.yaml
# 启动 jobmanager-deployment 服务
kubectl create -f jobmanager-deployment.yaml
# 启动 taskmanager-deployment 服务
kubectl create -f taskmanager-deployment.yaml

# 查看 Pod 与 Service 是否就绪
kubectl get pods,svc
  1. 访问 Flink UI 页面：集群启动后，可以通过 JobManagerService 中配置的 WebUI 端口访问：
# 本机端口转发后访问 http://localhost:8081
kubectl port-forward svc/flink-jobmanager 8081:8081

# 或者使用 apiserver 代理（kube-proxy 之外的方式）
http://{JobManagerHost:Port}/api/v1/namespaces/default/services/flink-jobmanager:ui/proxy

原生 Kubernetes 集成

手工维护 yaml 的方式只能算「把 Flink 装进容器」，Flink 1.10 起提供了原生 Kubernetes 集成（flink-kubernetes，1.10 为 beta），由 Flink 客户端直接调用 Kubernetes API 创建和销毁 JobManager、TaskManager Pod，无需自己写 yaml：

# flink-conf.yaml 中配置镜像与 RBAC 账号
kubernetes.container.image: flink:1.10.1-scala_2.12
kubernetes.service-account: flink
kubernetes.cluster-id: flink-session
kubernetes.namespace: default

# 作业集群（Application 模式）：一条命令拉起整个集群并执行作业
./bin/flink run -t kubernetes-application \
  -Dkubernetes.container.image=flink:1.10.1-scala_2.12 \
  -Dkubernetes.service-account=flink \
  -Dkubernetes.cluster-id=flink-demo \
  local:///opt/flink/usrlib/FlinkTutorial-1.0-SNAPSHOT.jar

# Session 模式：先起常驻集群，再提交作业
./bin/kubernetes-session.sh -Dkubernetes.cluster-id=flink-session
./bin/flink run -t kubernetes-session -Dkubernetes.cluster-id=flink-session app.jar

两点容易踩坑：其一，原生集成需要 Flink 客户端能访问 Kubernetes API，因此要准备 ServiceAccount 与对应 RBAC 权限；其二，JobManager 与 TaskManager 必须使用同一个 kubernetes.service-account，否则 TaskManager Pod 会因权限不足连不上 JobManager。此外，local:///path 表示镜像内部已有的 jar 路径，只有集群模式下才有意义。

Flink 版本演进与 K8s 现状

  • Flink 1.10：Standalone / YARN / Kubernetes 三种模式并存；K8s 支持手工 yaml 与原生集成两种方式；内存参数仍以 heap.size 为主，同时引入细粒度内存模型。
  • Flink 1.11：引入 Application 模式，部署目标统一为 -t session|per-job|application；conf/slaves 更名 workers。
  • Flink 1.14：Kubernetes 成为默认资源提供者（不再需要 -Dexecution.target）。
  • Flink 1.15：Per-Job 模式标记为废弃，官方推荐 transition 到 Application 模式。
  • Flink 2.x：移除 legacy 的 -m yarn-cluster、-m kubernetes-session 与 yarn-session.sh 入口；移除 Scala API（本系列后续示例请使用 Java 或 Scala 1.x 版本）；内存统一以 *.memory.process.size 配置；State Backend 统一为 EmbeddedRocksDBStateBackend/HashMapStateBackend，Checkpoint 存储改用 FileSystemCheckpointStorage 并在 execution.checkpointing.dir 中配置。

因此，本系列教程基于 Flink 1.10～1.13 的写法能覆盖绝大多数历史资料；若使用 Flink 2.x，请把提交命令统一改为 flink run -t <target> 形式，并注意 -m 与 yarn-session.sh 已不可用。
