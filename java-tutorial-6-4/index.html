并发与内存模型

Posted on 2026-09-19，7 min read

这一章解决一个几乎所有 Java 工程师都踩过的坑：把「Java 内存模型（JMM）」当成「JVM 内存结构」来理解。前者是并发规范，讲的是多线程读写共享变量时「什么时候能看到对方改的值、什么顺序算合法」；后者讲的是堆、栈、方法区怎么划分。本章面向已经会写多线程、但说不清 volatile 和 synchronized 到底保证了什么的读者，按「为什么需要 → 规则 → 工具 → 常见坑」走一遍。

先分清两个词：JVM 内存结构 vs Java 内存模型

JVM 内存结构是真实存在的物理划分：堆、虚拟机栈、本地方法栈、方法区、程序计数器，面试问「对象分配在哪里」时答的是它。而 JMM 是一套抽象规范，出自 JSR-133，它不描述任何一块内存，只描述多线程下共享变量读写的合法行为。

JMM 的抽象模型只有两层：所有变量存在主内存，每条线程有自己的工作内存（对应寄存器、各级缓存、写缓冲、无效化队列等硬件暂存区）。线程对变量的读写都在工作内存完成，线程之间不能直接访问对方的工作内存，只能通过主内存传递。硬件引入这些缓存是为了快，代价就是三个问题：

  • 原子性：CPU 按时间片调度线程，i++ 这种「读—改—写」可能在中间被挂起。
  • 可见性：一个线程改了值，别的线程的工作内存副本还是旧的。
  • 有序性：编译器和处理器会重排序指令，也会因为写缓冲异步刷出而表现出乱序。

JMM 并不消灭这些问题（那等于废掉缓存和流水线），而是规定哪些重排序和延迟同步是允许的，并把底层实现封装成 volatile、synchronized、final 和 java.util.concurrent 供我们直接用。对原子性，Java 用 monitorenter/monitorexit 两条字节码实现 synchronized；对可见性，用「写后同步回主内存、读前从主内存刷新」的传递方式；对有序性，则用锁的互斥或 volatile 的屏障来限定重排序范围。

happens-before：判断「是否可见」的规则

既然工作内存的存在让「谁先谁后」在物理时间上无法确定，JMM 就换了个提法：只关心一个操作的结果对另一个操作是否可见。这就是 happens-before（先行发生）原则。关键在于：它不要求前一个操作必须在时间上先执行完，只要求前者的结果对后者可见，且后者看到的是一个不违反该原则的执行顺序。

举个例子：线程 A 写普通变量 a = 1，再写 volatile 变量 flag = true；线程 B 读到 flag == true。由程序顺序规则，a = 1 happens-before flag = true；由 volatile 规则，flag = true happens-before B 对 flag 的读；再由传递性，B 读 flag 之后的代码一定能看到 a == 1——哪怕 a 本身不是 volatile。这就是「用 volatile 变量当发布开关」能安全发布普通字段的原理。

常用的几条规则：

  • 程序顺序：同一线程内，按代码顺序，前面的操作 happens-before 后面的操作。
  • 监视器锁：对同一个锁的解锁 happens-before 后续的加锁。
  • volatile 变量：对 volatile 字段的写 happens-before 后续对它的读。
  • 线程启动与终止：Thread.start() happens-before 新线程中的一切；线程中的所有操作 happens-before 其他线程从 join() 成功返回。
  • 传递性：A happens-before B，B happens-before C，则 A happens-before C。

还有一条 as-if-serial 语义作为底线：不管怎么重排序，单线程程序的执行结果不能变。所以 double area = pi * r * r; 里，两句赋值和乘法可以互换，但乘法不能被提到取 pi、r 之前——否则结果就变了。

volatile：可见性 + 禁止特定重排序

下面这段代码是可见性问题的经典复现：主线程把 flag 改成 true，工作线程却可能永远看不到。

public class VisibilityDemo {
    // 去掉 volatile，程序很可能一直不退出
    private static volatile boolean flag = false;

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            while (!flag) {          // 反复读取工作内存中的副本
                // 空转
            }
            System.out.println("worker 看到了 flag = true");
        });
        worker.start();

        Thread.sleep(100);
        flag = true;                 // volatile 写：立即可见
        System.out.println("main 已置为 true");
    }
}

把 volatile 去掉，循环体里没有其他同步点，JIT 还可能把 !flag 提升为循环外的一次读取，worker 就永远不会退出——这也是「用变量做线程停止标志却停不下来」的原因。

JMM 为 volatile 定的内存语义是：写之前插入 StoreStore 屏障、写之后插入 StoreLoad 屏障；读之后依次插入 LoadLoad、LoadStore 屏障。屏障有两个作用——把写缓冲刷到缓存让其他核心可见，以及阻止屏障两侧的读写跨越屏障重排序。在 x86 上，StoreStore/LoadLoad/LoadStore 是空操作（x86 本身不允许这类重排序），只有 StoreLoad 需要真正的 lock 前缀指令，这也是 volatile 写比读贵的原因。

但 volatile 不保证原子性。volatile int count; count++; 依然会丢更新，需要 AtomicInteger 或加锁。

CAS 与 AQS：从自旋到锁的骨架

CAS（Compare-And-Swap）是处理器提供的原子「比较并交换」指令，Java 侧入口是 sun.misc.Unsafe#compareAndSwapInt，实际由 AtomicInteger 等原子类包装。它把「读—比较—写」做成一条不可中断的指令，从而在没有锁的情况下保证原子性。

import java.util.concurrent.atomic.AtomicInteger;

public class CasDemo {
    private static final AtomicInteger COUNT = new AtomicInteger(0);

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 10_000; i++) {
                COUNT.incrementAndGet();   // 内部就是 CAS 自旋
            }
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join(); t2.join();
        System.out.println(COUNT.get());   // 稳定输出 20000
    }
}

CAS 有三个经典问题：一是 ABA（值从 A 改回 A，比较不出来，可用 AtomicStampedReference 加版本号）；二是自旋失败时空耗 CPU；三是只能保证一个变量的原子性，多个变量要 AtomicReference 或锁。

AQS（AbstractQueuedSynchronizer）就是把这套 CAS 自旋 + 失败排队的思想做成了框架：它内部维护一个 volatile int state 表示同步状态，用一个 CLH 变体的双向队列存放没抢到锁的线程，抢锁时 CAS 改 state，失败就 LockSupport.park() 挂起，释放时 unpark() 唤醒后继。ReentrantLock、Semaphore、CountDownLatch 都建立在它之上。

import java.util.concurrent.locks.AbstractQueuedSynchronizer;

/** 基于 AQS 的极简不可重入互斥锁 */
public class SimpleLock {
    private static class Sync extends AbstractQueuedSynchronizer {
        @Override
        protected boolean tryAcquire(int arg) {
            if (compareAndSetState(0, 1)) {   // CAS 抢锁
                setExclusiveOwnerThread(Thread.currentThread());
                return true;
            }
            return false;
        }

        @Override
        protected boolean tryRelease(int arg) {
            if (getState() == 0) {
                throw new IllegalMonitorStateException();
            }
            setExclusiveOwnerThread(null);
            setState(0);                      // volatile 写，对后续加锁可见
            return true;
        }

        @Override
        protected boolean isHeldExclusively() {
            return getState() == 1;
        }
    }

    private final Sync sync = new Sync();

    public void lock()   { sync.acquire(1); }
    public void unlock() { sync.release(1); }
}

注意：state 是 volatile 字段，setState 的写 happens-before 后续 compareAndSetState 的读，这把「释放锁之前的操作」安全地交给了下一个拿到锁的线程。AQS 的 state 语义由子类定义：ReentrantLock 里它表示重入次数，Semaphore 里表示可用许可数，CountDownLatch 里表示剩余计数。因为 tryAcquire 返回 false 时由 AQS 负责入队与挂起，子类只需要回答「现在能不能拿」，不必自己写自旋和等待队列，这也是它比裸写 CAS 更适合做同步器的原因。

常见坑：DCL 与「锁升级」的误传

双重检查锁定（DCL）是最能说明重排序危害的例子：

public class Singleton {
    // 缺少 volatile 时，其他线程可能拿到「构造未完成」的半成品对象
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {                 // 第一次检查，避免每次都加锁
            synchronized (Singleton.class) {
                if (instance == null) {         // 第二次检查，防止重复创建
                    instance = new Singleton(); // 1.分配内存 2.初始化 3.赋值给引用
                }
            }
        }
        return instance;
    }
}

没有 volatile 时，步骤 2 和 3 可能被重排序，另一线程在第一次检查处就会看到一个非 null、但字段还是默认值的对象。加 volatile 后，写之前的 StoreStore 屏障禁止了这种重排序，写之后的 StoreLoad 屏障保证后续读取能看到完整对象。（更简单的写法是静态内部类或枚举单例，由类加载机制保证线程安全。）

两个容易说错的知识点，这里直接纠正：

  • volatile 不是「轻量级锁」，也没有「锁升级成 synchronized」这回事。「锁升级」是 synchronized 自己的优化路径（偏向锁 → 轻量级锁 → 重量级锁），volatile 完全不涉及锁，它只插入内存屏障。此外偏向锁在 JDK 15 起默认关闭（JEP 374），JDK 18 起相关实现已被移除，面试时按版本说清。
  • volatile 的可见性不等于「直接写主内存」。它只是通过屏障保证刷新与顺序，让其他核心最终能观察到新值；「立即同步回主内存」是便于理解的简化说法。

小结

记住三句话：JMM 是并发规范，不是堆栈方法区；happens-before 保证的是可见性而不是时间先后；volatile 给可见性和有序性但不给原子性，需要原子性就用 CAS/原子类或锁。排查并发问题时，先问「这两个操作之间有 happens-before 关系吗」，如果没有，就一定要靠 volatile、锁或并发工具类补上——DCL 的 volatile 和 AQS 的 state，都是这条规则的具体落点。
