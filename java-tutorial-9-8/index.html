系统设计与场景题

Posted on 2026-09-19，6 min read

系统设计与场景题是 Java 面试里最容易“翻车”的一类题：面试官不给标准答案，只丢下一句“设计一个秒杀系统”，然后观察你如何自己界定问题、估算规模、给出方案并说清取舍。前面几章补的是知识点，这一章补的是“把知识点串起来回答一整道题”的能力。本章围绕秒杀、限流、幂等、分布式 ID、海量数据这五个高频场景，串起一套可以现场复用的答题框架，适合已经掌握 Java 基础、准备中高级后端岗位面试的读者。

一、先搭框架，再谈方案

大多数人的失分点不是不会技术，而是一上来就报菜名：Redis、MQ、分库分表全部堆上去，却说不清为什么需要。稳妥的回答顺序是四步。

第一步，澄清需求。功能上要问清是“下单即扣库存”还是“支付成功才扣库存”，是否允许少卖（库存没卖完），是否需要防刷；非功能上要问清峰值 QPS、库存量、可接受的响应时间。第二步，估算量级。例如 10 万人抢 1000 件商品，峰值 QPS 约 1 万，而单机 MySQL 的写入能力通常在数千 TPS 量级。由此可得结论：必须把绝大部分流量挡在数据库之前，这句话就是后续所有设计的理由。第三步，分层设计，按“客户端 → CDN/Nginx → 服务集群 → 缓存 → 消息队列 → 数据库”的顺序逐层给出手段。第四步，回答一致性与兜底：超卖怎么办、MQ 重投怎么办、Redis 挂了怎么办。

贯穿始终的四条原则可以背下来：前台请求尽量少，后台数据尽量少，调用链路尽量短，尽量不要有单点。任何方案只要能对上这四条，面试官都会认可它的合理性。

二、秒杀：把流量挡在数据库之前

秒杀有三个特点：瞬时并发极高、库存极少、业务简单（下单、扣库存、支付）。正因为业务简单，优化的重心全在流量治理上。

前端与接入层：把商品详情页静态化并推到 CDN，按钮点击后立即置灰防止重复提交；答题或验证码用于拦截脚本和“秒杀器”。这里要分清两件事——静态化是为了减少服务器请求，验证码是为了防刷，二者的目的并不相同。Nginx 层做动静分离、反向代理与负载均衡，静态资源不再走 Tomcat，并开启 gzip 压缩。

服务层：无状态化后水平扩容，把库存预热到 Redis 承担读压力。消息队列承担削峰：上游只管把下单请求变成消息写入 MQ，消费者按数据库能承受的速率拉取（例如每秒 200 条），数据库压力就变得可控。数据库只负责最终落账，通过读写分离和缩短事务范围提高并发度。

扣库存是全场核心。必须强调一点：Redis 的单条命令是原子的，但“先查库存、再扣库存”这种复合操作不是原子的，集群模式下跨 key 的操作也不保证原子。因此要用 Lua 脚本把判断和扣减合成一次执行，或者直接用 DECR 的返回值判断是否小于 0。

// 秒杀下单：Redis 原子扣减 + MQ 异步落库
private static final String STOCK_LUA =
        "local stock = redis.call('get', KEYS[1]) " +
        "if stock == false then return -1 end " +      // 未预热
        "if tonumber(stock) <= 0 then return 0 end " +  // 已售罄
        "redis.call('decr', KEYS[1]) return 1";

public void seckill(long userId, long skuId) {
    String stockKey = "seckill:stock:" + skuId;
    Long r = redis.execute(new DefaultRedisScript<>(STOCK_LUA, Long.class),
            Collections.singletonList(stockKey));
    if (r == null || r <= 0) {
        throw new BizException(r == null ? "系统繁忙" : "已售罄");
    }
    // 扣减成功才投递消息，落库交给消费者，实现削峰
    mqTemplate.send("seckill-order", new OrderMsg(userId, skuId, idGenerator.nextId()));
}

注意顺序：先在 Redis 挡住无效请求，再让 MQ 缓冲有效请求，最后数据库用条件更新兜底。三层缺一不可，只靠 Redis 会丢数据，只靠数据库会打满。

三、限流与幂等：保护系统的两道闸门

限流的常见算法有四种：

  • 固定窗口计数器实现最简单，但存在临界问题（窗口边界处可能瞬间放过两倍流量）；
  • 滑动窗口用更细的粒度统计，缓解临界问题；
  • 漏桶以恒定速率放行，适合保护下游；
  • 令牌桶允许一定程度的突发流量，是工程中最常用的方案。

单机限流可以直接用 Guava 的 RateLimiter。但集群中每台机器的阈值会被放大 N 倍，必须用 Redis + Lua 实现分布式令牌桶，或采用 Sentinel 这类带集群限流能力的组件。

幂等解决的是“同一个请求被执行多次，结果必须与执行一次相同”。触发场景很现实：用户连点、RPC 超时重试、MQ 至少一次投递。可用手段包括：数据库唯一索引或去重表、Redis setIfAbsent 预占令牌、状态机约束（订单只能从“待支付”流向“已支付”，重复通知会被状态判断挡掉）、乐观锁版本号。

// 单机令牌桶 + Redis 幂等令牌
private final RateLimiter limiter = RateLimiter.create(2000); // 2000 QPS

public void handle(long userId, long skuId, String requestId) {
    if (!limiter.tryAcquire()) {
        throw new BizException("当前人数过多，请稍后再试");
    }
    // SET NX EX：同一 requestId 只允许通过一次，天然幂等
    Boolean first = redis.opsForValue()
            .setIfAbsent("seckill:req:" + requestId, "1", 10, TimeUnit.MINUTES);
    if (!Boolean.TRUE.equals(first)) {
        throw new BizException("请勿重复提交");
    }
    seckill(userId, skuId);
}

数据库这层的幂等和防超卖可以同时完成：唯一索引保证一个用户只成功一次，条件更新保证库存不会变成负数。

-- 唯一索引：同一用户对同一商品只能有一条成功订单
ALTER TABLE seckill_order ADD UNIQUE KEY uk_user_sku (user_id, sku_id);

-- 条件更新：把判断和扣减放在一条语句里，由 InnoDB 行锁保证原子性
UPDATE stock SET quantity = quantity - 1
WHERE sku_id = 1001 AND quantity > 0;
-- 影响行数为 0 说明已售罄，直接回滚，不会出现负库存

这里要纠正一个流传很广的说法。源笔记称“Redis 对同一个 key 的操作本身就有行级锁”，准确表述是：Redis 的单条命令是原子执行的，不存在 MySQL 那种行锁概念；它也不能把多条命令自动组成一个事务。因此复合操作必须借助 Lua、MULTI/EXEC 或单命令语义来实现。

四、分布式 ID 与海量数据处理

分库分表之后，单表自增主键不再唯一，就需要分布式 ID。它通常要求：全局唯一、趋势递增（有利于 B+ 树索引插入）、高可用、不暴露业务量级。UUID 无序且过长，会拖慢索引；数据库自增配合步长简单但依赖数据库可用性；号段模式一次取一批 ID 到内存，性能和可靠性较均衡；雪花算法（Snowflake）则是面试中要求手写的高频题。

雪花算法把 64 位长整型切成四段：1 位符号位恒为 0，41 位毫秒时间戳可用约 69 年，10 位工作机器 ID 支持 1024 个节点，12 位序列号让单机每毫秒可产生 4096 个 ID。它最大的坑是时钟回拨：服务器校时或 NTP 调整会让时间戳倒退，可能生成重复 ID。常见处理是回拨幅度小时自旋等待，幅度大时切换到备用 workerId，或改用号段模式。

public synchronized long nextId() {
    long now = System.currentTimeMillis();
    if (now < lastTimestamp) {                 // 时钟回拨
        long offset = lastTimestamp - now;
        if (offset <= 5) {                     // 小幅回拨：等待追平
            now = waitUntil(lastTimestamp);
        } else {                               // 大幅回拨：拒绝服务并告警
            throw new IllegalStateException("clock moved backwards: " + offset);
        }
    }
    if (now == lastTimestamp) {
        sequence = (sequence + 1) & 0xFFF;     // 12 位序列，最多 4096
        if (sequence == 0) {
            now = waitUntil(lastTimestamp + 1); // 本毫秒用尽，等下一毫秒
        }
    } else {
        sequence = 0L;
    }
    lastTimestamp = now;
    return ((now - EPOCH) << 22)              // 41 位时间戳
            | (workerId << 12)                 // 10 位机器位
            | sequence;                        // 12 位序列号
}

海量数据类问题（去重、Top K、排序、找频率最高的 IP）则遵循“分治 + 合适的数据结构”：先按哈希把数据分到多个桶，让单桶能装进内存，再在桶内分别求解并合并。数值范围较小且要求精确去重时用 BitMap；数据量大、可以接受少量误判时用布隆过滤器，但要记住它只支持插入和查询，不支持删除（计数布隆过滤器除外）。求 Top K 用大小为 K 的小顶堆，时间复杂度为 \(O(n\log k)\)，而不是把全部数据排序。

再补充一个容易被混淆的概念。表分区（Partitioning）在逻辑上仍然是一张表，数据文件仍在同一个 MySQL 实例上，它只能减少单次扫描的数据量，无法把压力分摊到多台机器。分库分表是把数据物理拆到多个实例，才能真正水平扩展，同时也意味着跨库 JOIN 和分布式事务会变得困难：分片键一旦选错，后期迁移成本极高。

五、常见坑与小结

复盘时重点关注这些高频错误：

  • 用“先 SELECT 再 UPDATE”扣库存，必然超卖；
  • 把幂等校验放在整条链路的末端，前面的资源已经被消耗；
  • 限流只做单机，集群扩容后阈值被成倍放大；
  • 直接用自增 ID 对外暴露业务量级；
  • 分片键选了一个几乎不参与查询条件的字段，导致每次查询都要广播到所有分片；
  • 以及整场面试只讲技术名词，不讲为什么这么选、代价是什么。

小结：场景题考的是结构化表达，而不是背了多少中间件。记住主线索——先用澄清需求锁定 QPS 与库存量级，再按接入层拦截、缓存抗读、MQ 削峰、数据库兜底四层逐级削弱流量。任何涉及“判断 + 修改”的复合操作，都要用 Lua、条件更新或唯一索引把它变成原子操作；分布式 ID 优先考虑趋势递增与时钟回拨；海量数据先分治再选结构。能做到讲清每一层的存在理由和取舍，这类题就已经过关了。
