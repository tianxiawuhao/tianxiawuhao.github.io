9.2 并发编程面试题

Posted on 2026-09-19，6 min read

并发编程是 Java 面试里区分度最高的一块：它能同时考察你对 JMM 的理解、对 JDK 源码的熟悉度，以及线上排障的实战经验。本文不铺陈全部考点，只挑面试官最爱追问、也最容易答错的四条主线：线程池、CAS 与原子类、AQS 与锁、并发容器。适合已经会写多线程代码、准备投递中高级岗位的读者。

一、线程池：先讲清任务提交的决策链

不少人只记住构造参数，但面试官真正想听的是“提交一个任务后，线程池按什么顺序决策”。准确顺序是：

  1. 若当前工作线程数 < corePoolSize，直接新建核心线程执行任务，不入队。
  2. 否则尝试把任务放入 workQueue；入队成功就等待空闲线程来取。
  3. 若队列已满，且线程数 < maximumPoolSize，则新建非核心线程执行。
  4. 若队列已满且线程数已达上限，触发 RejectedExecutionHandler 拒绝策略。

记住这条链，才能理解两个经典现象：使用 LinkedBlockingQueue（默认容量 Integer.MAX_VALUE）时，队列几乎永远不会满，maximumPoolSize 形同虚设；而使用 SynchronousQueue 时任务不排队，必须立刻找到线程接手，否则就扩容或拒绝。

《阿里巴巴 Java 开发手册》强制要求用 ThreadPoolExecutor 显式构造线程池，原因是 Executors 的工厂方法把关键参数藏了起来。其中 newFixedThreadPool 与 newSingleThreadExecutor 使用无界队列，请求堆积会导致 OOM；newCachedThreadPool 与 newScheduledThreadPool 的最大线程数是 Integer.MAX_VALUE，可能创建海量线程，同样导致 OOM。

ThreadPoolExecutor executor = new ThreadPoolExecutor(
        4,                                  // corePoolSize
        8,                                  // maximumPoolSize
        60L, TimeUnit.SECONDS,              // 非核心线程空闲回收时间
        new ArrayBlockingQueue<>(200),       // 有界队列，容量必须显式指定
        new ThreadFactory() {               // 自定义线程名，便于线上排查
            private final AtomicInteger seq = new AtomicInteger(1);
            @Override
            public Thread newThread(Runnable r) {
                Thread t = new Thread(r, "order-pool-" + seq.getAndIncrement());
                t.setDaemon(false);
                return t;
            }
        },
        new ThreadPoolExecutor.CallerRunsPolicy() // 队列满时由提交线程执行，形成背压
);

四种拒绝策略要能区分适用场景：AbortPolicy（默认，抛 RejectedExecutionException）、CallerRunsPolicy（提交线程自己执行，牺牲响应速度换取不丢任务）、DiscardPolicy（静默丢弃）、DiscardOldestPolicy（丢弃队列中最早的未处理任务）。

线程池有五种状态：RUNNING、SHUTDOWN、STOP、TIDYING、TERMINATED。其中 shutdown() 进入 SHUTDOWN，会拒绝新任务但继续处理队列中已排队的任务；shutdownNow() 进入 STOP，不再处理队列任务并向正在执行的线程发起中断。TIDYING 是过渡态，工作线程数为 0 时进入，并回调钩子方法 terminated()，随后变为 TERMINATED。

还有一个高频问题是线程数怎么设：计算密集型任务通常取 CPU 核数 + 1；IO 密集型任务因为线程大量时间在等待，可以按“核数 ×（1 + 平均等待时间 / 平均计算时间）”估算。给出公式比只报一个凭经验的数字更容易得到认可。Java 21 起还多了一条新变量：虚拟线程（Executors.newVirtualThreadPerTaskExecutor()）不适合放进固定大小的池里复用，它“一个任务一个虚拟线程”，上面这条 corePoolSize / maximumPoolSize 决策链对它并不适用，此时要先判断瓶颈在 CPU 还是 IO 阻塞，而不是纠结池子开多大。

二、CAS 与原子类：无锁并不等于没有开销

CAS（Compare And Swap）包含三个操作数：内存位置 V、预期原值 A、新值 B。仅当 V 处的当前值等于 A 时，才把 V 更新为 B，整个过程由处理器的一条指令保证原子性。它属于乐观策略——先假设没有竞争，冲突时靠自旋重试；而 synchronized 是悲观策略，先加锁再访问。注意一个常见表述错误：CAS 本身是无锁（lock-free）操作，说它“基于锁”是不准确的，它恰恰是为了避免阻塞式加锁才被引入的。

java.util.concurrent.atomic 下的 AtomicInteger、AtomicLong、AtomicReference 等在 JDK 8 中基于 Unsafe 提供的 CAS 实现；JDK 9 引入 VarHandle（java.lang.invoke）后，这些原子类已改用 VarHandle 完成原子访问，Unsafe 的 CAS 系列方法自 JDK 9 起被标记废弃——“原子类基于 Unsafe”这个说法只在 JDK 8 成立。JDK 8 起，LongAdder 在高并发计数场景下比 AtomicLong 表现更好：它把一个热点值拆成 Cell 数组分散竞争，读取时再求和，代价是 sum() 不保证返回某一瞬间的精确快照。

public class Counter {
    private final LongAdder hits = new LongAdder();

    public void record() {
        hits.increment();          // 分散热点，避免所有线程争同一个 CAS
    }

    public long total() {
        return hits.sum();         // 非强一致的瞬时值
    }

    // 需要“值 + 版本号”一起原子更新时，别用两个变量分别 CAS
    private final AtomicStampedReference<String> ref =
            new AtomicStampedReference<>("init", 0);

    public boolean update(String expect, String next) {
        int stamp = ref.getStamp();
        return ref.compareAndSet(expect, next, stamp, stamp + 1);
    }
}

CAS 有三个公认的坑。第一是 ABA 问题：值从 A 变成 B 又变回 A，CAS 会误判“没被改过”，解决手段是 AtomicStampedReference 带版本号，或 AtomicMarkableReference 带布尔标记。第二是自旋开销：竞争激烈时大量线程空转，CPU 利用率虚高，此时反而应该退化到加锁。第三是只能保证单个变量的原子性，多变量组合操作必须借助锁或把它们封装进一个对象用 AtomicReference 更新。

三、AQS 与锁：理解 state 和同步队列

AQS（AbstractQueuedSynchronizer）是 J.U.C 的地基，ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 都由它支撑。它的核心只有两件事：一个 volatile 的 state 字段表示同步状态，以及一个 CLH 变体的双向 FIFO 等待队列存放阻塞线程。

AQS 采用模板方法模式：把获取与释放的骨架（入队、阻塞、唤醒、中断处理）固定下来，只暴露 tryAcquire、tryRelease、tryAcquireShared、tryReleaseShared、isHeldExclusively 这些钩子给子类实现。以 ReentrantLock 为例，state 为 0 表示未加锁，加锁时置为 1，重入则自增，因此重入次数上限是 state 的溢出边界，而非某个固定常数。

公平与非公平的差别也落在 tryAcquire 上：公平锁每次都会先调用 hasQueuedPredecessors()，只要队列里已有等待者就直接失败入队；非公平锁则允许新来的线程插队抢锁。非公平锁可能造成队列中线程“饥饿”，但减少了线程切换，吞吐通常更高，ReentrantLock 默认就是非公平的。

// 需要超时、可中断、可轮询的加锁场景，用 Lock 而不是 synchronized
Lock lock = new ReentrantLock();
if (lock.tryLock(200, TimeUnit.MILLISECONDS)) {
    try {
        // 临界区
    } finally {
        lock.unlock();      // 必须在 finally 中释放
    }
} else {
    // 获取锁失败，走降级逻辑，而不是无限等待
}

关于 synchronized 的锁升级，要按版本分开说。旧答案（JDK 15 之前）是：无锁 → 偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁（互斥量）。现状是：JDK 15 通过 JEP 374 默认禁用偏向锁，JDK 18 起把偏向锁实现连同 -XX:-UseBiasedLocking、-XX:BiasedLockingStartupDelay 等相关参数一并移除，所以 Java 17/21 上这条链只有无锁 → 轻量级锁 → 重量级锁，面试时最好直接说明“偏向锁是 JDK 15 之前的历史优化”。另外要注意锁对象的选择——对 Integer、String 字面量加锁会因常量池或缓存复用而与他人共享同一把锁，应该使用专门的 private final Object lock = new Object()。

四、并发容器与实战选型

ConcurrentHashMap 在 JDK 8 中放弃了 JDK 7 的分段锁 Segment，改为“CAS + synchronized 锁单个桶头节点”的数组加链表或红黑树结构，锁粒度细到桶级别，并发度不再由构造参数写死。几个常被追问的点：size() 通过 baseCount 与 CounterCell 数组累加得到，是弱一致值；key 和 value 都不允许为 null；扩容时多线程可以协同迁移，读取线程遇到迁移中的桶会通过 ForwardingNode 转发到新表。

与 Collections.synchronizedMap 的区别在于锁的粒度：后者对整个 Map 加一把互斥锁，任何操作都串行；前者只锁单个桶。因此高并发读写场景应优先选 ConcurrentHashMap，而需要复合操作原子性时（比如“不存在才放入”），要用它提供的 putIfAbsent、computeIfAbsent 等原子方法，而不是自己写“先 get 再 put”。

ThreadLocal 的本质是让每个线程持有独立副本。内存泄漏的根源在于 ThreadLocalMap 的 key 是 ThreadLocal 的弱引用而 value 是强引用：外部强引用一旦消失，key 会被回收成 null，value 却仍被 Thread 强引用，在线程池这种长生命周期线程中就会累积。虽然 set/get/remove 会顺带清理 key 为 null 的 Entry，但最稳妥的做法仍是“用完即 remove()”，并且要用 try/finally 保证一定会执行——线程池里残留的 value 不只是内存问题，更会造成串号一类的业务错误。再补一句 Java 21 的现状：虚拟线程默认不复用、随任务结束而消亡，“线程复用串号”的风险与线程池场景不同，但未 remove 的 value 仍会随线程对象驻留内存，try/finally 中清理的习惯不要丢。

private static final ThreadLocal<UserContext> CTX = new ThreadLocal<>();

public void handle(Request req) {
    CTX.set(loadUser(req));
    try {
        doBusiness();
    } finally {
        CTX.remove();   // 必须清理，否则线程复用时数据会串到下一个请求
    }
}

选型思路可以这样记：单变量计数用原子类，高并发计数用 LongAdder；键值缓存用 ConcurrentHashMap；读多写少的列表用 CopyOnWriteArrayList；生产者消费者用 BlockingQueue；需要超时、可中断、多条件队列用 ReentrantLock + Condition；其余情况优先 synchronized，让 JVM 去优化。

小结

回答并发面试题的关键不是背 API，而是讲清“为什么这么设计”。线程池要能画出任务提交的四步决策链，并说出无界队列的风险。CAS 要能同时讲出 ABA、自旋开销、单变量限制三个缺点；AQS 要抓住 state 与同步队列这两个核心，说清公平与非公平的差异。并发容器则要落到锁粒度和弱一致性语义上。最后补一句版本意识——偏向锁已于 JDK 15 默认禁用、ConcurrentHashMap 的实现在 JDK 8 发生了结构性变化——会让你的回答明显区别于只会背题的候选人。
