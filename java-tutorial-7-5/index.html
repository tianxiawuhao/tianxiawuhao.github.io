Nginx 配置与反向代理

Posted on 2026-09-19，8 min read

《Nginx 配置与反向代理》是"运维与部署"阶段的实战章节。前面你已经把 Java 应用打包、在 Linux 上跑起来，也见过 Docker 与 K8s 的基本用法；但真正上线时，用户不会直接访问你的 Tomcat——中间那层负责转发、负载、缓存和 HTTPS 的角色，通常由 Nginx 担任。本节面向后端开发者和刚开始接触部署的同学，目标是把 nginx.conf 的写法讲清楚：配置结构怎么分层、location 到底谁优先、反向代理与负载均衡怎么配、缓存与 HTTPS 怎么落地、以及哪些参数值得调。学完之后，你应该能独立写出一份可上线的七层代理配置，并看懂线上配置里的每一行。

为什么要在应用前放一层 Nginx

直接把 Tomcat 暴露到公网会遇到几个现实问题：单个实例的并发能力有限，一旦挂掉服务就整体不可用；静态资源也交给 Java 线程去读磁盘，白白占用工作线程；再加上 TLS 握手、压缩、限流这些和业务无关的事，全压在应用里会让代码越来越臃肿。Nginx 的价值正是把这些"通用且重复"的活儿抽出来：它用 master + worker 的多进程模型配合 epoll 事件驱动，单个 worker 用极少的线程就能照看大量连接，静态文件走零拷贝（sendfile）直接发出，业务请求再反向代理给后端集群。

理解这套模型对配置很关键。master 进程只做管理：解析配置、拉起 worker、接收 nginx -s reload 这类信号；真正处理请求的是 worker，一个连接自始至终只由一个 worker 负责。所以 worker_processes 一般设为 CPU 核心数，多余的 worker 只会互相抢 CPU；而 worker_connections 是"每个 worker"的上限，整机理论连接数约为它乘以 worker 数量，作为反向代理时每个请求还要占用一条到后端的连接，能承载的并发请求数大致是连接总数的一半。

配置文件的结构：main、events、http、server、location

nginx.conf 是"指令 + 上下文"的层层嵌套结构：每层作用域只允许出现特定的指令，写错位置轻则报 unknown directive、重则配置不生效。最外层是 main（进程数、运行身份、日志），往下是 events（事件模型与连接数）和 http（所有 HTTP 能力），http 里可以放多个 server（虚拟主机），server 里再放多个 location（按 URL 分派）。简单指令以分号结尾，带大括号的复合指令结尾不加分号——这一点在复制网上配置时经常出错。

user  www-data;                 # 运行身份，Debian/Ubuntu 上是 www-data
worker_processes  auto;         # 与 CPU 核心数一致，auto 由 Nginx 自动判断
worker_rlimit_nofile 65535;     # 单个 worker 可打开的描述符上限
error_log  /var/log/nginx/error.log warn;
pid        /run/nginx.pid;

events {
    use epoll;                  # Linux 2.6+ 的高性能事件模型
    worker_connections 10240;   # 每个 worker 的连接数上限
}

http {
    include       mime.types;
    default_type  application/octet-stream;
    sendfile      on;           # 零拷贝发送静态文件
    tcp_nopush    on;           # 与 sendfile 搭配，攒满一个包再发
    tcp_nodelay   on;           # 长连接上禁用 Nagle，降低小包延迟
    keepalive_timeout 65;
    client_max_body_size 8m;    # 上传体积上限，太小会直接 413
    gzip on;
    gzip_min_length 1k;
    gzip_comp_level 5;
    gzip_types text/plain text/css application/json application/javascript;

    server {
        listen      80;
        server_name www.example.com;
        root  /data/www/example;
        index index.html;

        location / {
            try_files $uri $uri/ /index.html;   # 单页应用回退到入口文件
        }
    }
}

有两处细节值得单独提醒。worker_connections 常被误解为"整机最大连接数"，它其实只约束单个 worker；worker_rlimit_nofile 也不能随手写大，它必须不超过操作系统给该进程的 ulimit -n，否则 worker 在连接数上来后拿不到描述符，会直接返回 502。调优时先确认系统上限，再设 Nginx 的上限，顺序不要颠倒。

location 匹配优先级，是配置里最容易踩的坑

location 决定一个请求最终交给谁处理，规则可以概括为一句话：先看精确匹配，再看前缀匹配并记住最长的那条，然后按配置文件中的书写顺序试正则，第一个命中的正则立即生效，若一个正则都没命中，才回退到之前记住的最长前缀。因此 ~（区分大小写正则）和 ~*（不区分大小写）的先后顺序会直接改变结果；^~ 表示前缀命中后就不再尝试正则；= 用于首页、健康检查这类高频路径，命中即可跳过全部匹配，性能最好。写正则时别忘了转义点号，~ .*.(php|php5)?$ 这类写法会把 aXphp 也匹配进来，正确写法是 ~ \.(php|php5)$。

下面这份配置把静态资源、接口和兜底规则分开处理，是典型的动静分离结构。

server {
    listen 80;
    server_name api.example.com;

    location = /health { return 200 "ok\n"; }        # 精确匹配，最高优先
    location ^~ /static/ {                            # 前缀命中后不再看正则
        root /data/www;
        expires 7d;
        add_header Cache-Control "public";
    }
    location ~* \.(js|css|png|jpg|jpeg|gif|svg|woff2)$ {
        root /data/www;
        expires 30d;
    }
    location /api/ {
        proxy_pass http://127.0.0.1:8080/;            # 注意结尾的斜杠
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout    60s;
    }
    location / { return 404; }                        # 兜底，避免意外暴露
}

反向代理还要记住两件事：一是 proxy_pass 结尾有无斜杠会改变 URI 的拼接方式，http://127.0.0.1:8080/ 会替换掉 /api/ 前缀，而 http://127.0.0.1:8080 会把原始路径整体带过去；二是必须转发 X-Forwarded-For 等头部，否则后端日志里看到的客户端 IP 永远是 Nginx 自己，排障时会非常被动。

负载均衡与缓存：从单机到多实例

后端有两个以上实例时，用 upstream 定义一组服务器，再让 proxy_pass 指向这个组名。默认策略是轮询，weight 按权重分配，ip_hash 让同一客户端固定落到同一台（适合还没做会话共享的应用），least_conn 把新请求交给当前连接最少的实例，hash $request_uri consistent 则常用于让同一个 URL 稳定命中同一份缓存。要注意的是，fair 属于第三方模块，url_hash 也早已废弃，网上大量旧配置直接抄会启动失败，用内置的 least_conn 和 hash ... consistent 替代即可。

# http 上下文：缓存路径必须写在 http 里
proxy_cache_path /var/cache/nginx/api levels=1:2
                 keys_zone=api_cache:10m max_size=2g
                 inactive=30m use_temp_path=off;

upstream app_cluster {
    least_conn;
    server 192.168.80.121:8080 weight=3 max_fails=2 fail_timeout=10s;
    server 192.168.80.122:8080 weight=2;
    server 192.168.80.123:8080 backup;      # 其余实例都不可用时才启用
    keepalive 32;                           # 与后端保持长连接，减少握手
}

server {
    listen 80;
    server_name api.example.com;

    location /api/ {
        proxy_pass http://app_cluster/;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_cache api_cache;
        proxy_cache_key  $scheme$request_method$host$request_uri;
        proxy_cache_valid 200 302 10m;
        proxy_cache_valid 404 1m;
        proxy_cache_use_stale error timeout updating http_500 http_502 http_503;
        add_header X-Cache-Status $upstream_cache_status;   # HIT/MISS 便于验证
    }
}

两个容易混淆的概念要分清：expires 是发给浏览器的缓存指令，proxy_cache 才是缓存在 Nginx 本机、能直接挡掉回源请求的缓存。另外，Nginx 的"自动剔除"是被动健康检查，它只对连接失败、超时这类情况生效，后端返回 500 时默认仍算一次成功响应；要覆盖这一点，需要配合 proxy_next_upstream 与 proxy_cache_use_stale，或由应用提供健康检查接口。

HTTPS、调优与上线自查

启用 HTTPS 只需一对证书和一段 server 配置，生产环境建议顺便把 HTTP 全量跳转过去，并关闭老旧协议版本。第一次部署最容易忽略的是证书链要完整、私钥权限要收紧（600 且属主为运行用户）。

server {
    listen 80;
    server_name www.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;                                   # 1.25.1 之前写作 listen 443 ssl http2;
    server_name www.example.com;

    ssl_certificate     /etc/nginx/ssl/example.com.fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/example.com.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 10m;

    location / {
        proxy_pass http://app_cluster;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

上线前可以按下面几条自查。worker_processes auto、worker_connections 与 worker_rlimit_nofile 是否和机器规格匹配；proxy_connect_timeout、proxy_read_timeout 是否覆盖了后端最慢接口的耗时，过大则故障时连接堆积、过小则正常慢请求被切断；client_max_body_size 是否大于业务允许的最大上传；limit_req、limit_conn 是否已为易被打的接口加上；访问日志里是否记录了 $upstream_response_time，它和 $request_time 的差值正是定位"慢在前端还是慢在后端"的依据。改完配置执行 nginx -t 校验，再用 nginx -s reload 平滑生效，不要直接重启进程。

小结

这一节围绕"一次讲透配置"的目标，把 Nginx 拆成了几块可以独立消化的内容：配置文件是 main → events → http → server → location 的嵌套上下文，指令只能待在自己允许的层级里；location 的匹配顺序是精确 → 最长前缀 → 首个命中的正则 → 回退最长前缀，正则里务必转义点号；反向代理的核心是 proxy_pass 的斜杠语义与 X-Forwarded-For 等头部的透传；负载均衡优先使用内置的 least_conn、权重和一致性哈希，别再抄第三方 fair；proxy_cache 才是真正的服务端缓存，expires 只管浏览器；HTTPS 与调优参数则决定了它能不能稳定扛住线上流量。建议你把自己项目里的一份旧配置对照本文重写一遍，用 nginx -t 验证并观察 $upstream_cache_status 的变化，这比记住任何参数都更有效。
