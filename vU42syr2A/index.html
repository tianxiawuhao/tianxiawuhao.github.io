发布JAR包到远程中央仓库

Posted on 2022-10-26，21 min read

声明：经过下面一系列操作之后，以后想发布新版本，只要修改好要升级的版本号，然后在 Maven 的 Lifecycle 里双击 deploy 即可。

前言

自使用maven以来，没少使用maven中央仓库中的各种jar包，方便有效，但是咱们也不能总是只取不予，也应该懂得奉献，当你写好了一个十分好用的jar包，想贡献出去给大家使用的时候，应该怎么做呢？当然是发布到maven的中央仓库了，不过要说这个发布过程，还真是比较复杂，本文就来详细说下如何发布jar包到maven中央仓库。

整个流程可以概括为下面五步，后文按顺序展开：

注意事项

先说明本文会用到的三类地址及其用途：

  • 工单管理：https://issues.sonatype.org/secure/Dashboard.jspa —— 注册账号、创建和管理 issue，JAR 包的发布是以解决 issue 的方式起步的。这里的用户名与密码非常重要，后面配置 settings.xml 时会用到，一定要保存好。
  • 构件仓库（OSSRH）：https://oss.sonatype.org/#welcome —— 正式发布前的过渡仓库，用 Maven 提交后的构件会先到这个库中。
  • 镜像仓库：https://central.sonatype.com —— 最终成功发布的构件可以在这里搜到（旧地址 http://search.maven.org 已跳转至此）。

提示：Sonatype 已经推出新的 Central Portal（https://central.sonatype.com），并宣布将逐步退役旧的 OSSRH 流程。本文介绍的是仍被大量老项目沿用的 OSSRH 流程；新项目也可以直接使用 Central Portal 的发布方式，步骤更简单。

一、创建工单

在上述工单管理的地址中创建；如果没有账号需要先注册。记住用户名和密码，后面要配置到 settings.xml 中。

关于 Group Id：如果使用 GitHub 托管项目，通常填写 io.github.你的用户名（部分教程写作 com.github.你的用户名），并按客服提示在 GitHub 上完成验证；如果有自己的域名，则填写域名倒序，并按提示配置 DNS TXT 记录。

Create Issue 填写内容说明：

===Step 1===
Project：Community Support - Open Source Project Repository Hosting
Issue Type：New Project

===Step 2===
Summary：JAR包名称，如：requestjson
Group Id：你拥有或申请的域名倒序，如 com.luxsuen，必须与工单中填写的一致
Project URL：项目站点，如：https://github.com/LuxSun/requestjson
SCM url：项目源码仓库，如：https://github.com/LuxSun/requestjson.git

其他内容不用填写。创建 Issue 后需要等待 Sonatype 工作人员审核，速度很快，一般一个工作日内完成；当 Issue 的 Status 变为 RESOLVED 后，就可以进行下一步，否则继续等待……

到这里需要跟客服沟通一下（以前这一步审核很简单，跟客服说明即可；现在开始要求提供证明材料）。

  • 如果是用Github，就无需注册域名，直接根据客服提示证明一下即可（新手推荐）。

  • 如果是用自己的域名，就需要根据客服的提示配置下DNS。

提示：无论以上是哪种情况，最后只要呈现如下图所示，即代表成功！

二、配置 Maven（pom.xml）

接下来就是重头戏了，pom.xml是一个maven项目的重点配置，一个项目的所有配置都可以由这个文件来描述，文件中的所有配置都有默认值，也就是说所有的配置都是可选配置，但是为了把构件发布到中央仓库，我们必须配置一些关键信息，否则发布时是不会通过的。

在工程的 pom.xml 中引入 Sonatype 官方的通用父 POM oss-parent，好处是很多发布相关配置（例如它预置的 sonatype-oss-release profile）不用自己写了：

<parent>
    <groupId>org.sonatype.oss</groupId>
    <artifactId>oss-parent</artifactId>
    <version>7</version>
</parent>

注意：oss-parent 是较早期的做法，最新版本为 7 且已多年未更新，完全可以省略。本文下面给出的「完整版」pom 就没有使用它，而是自行声明了 release profile，因此后续命令统一写作 -P release；如果保留了 <parent>，也可以改用 -P sonatype-oss-release 走官方预置的配置。

并增加Licenses、SCM、Developers信息：

<licenses>
  <license>
    <name>The Apache Software License, Version 2.0</name>
    <url>http://www.apache.org/licenses/LICENSE-2.0.txt</url>
    <distribution>repo</distribution>
  </license>
</licenses>

<developers>
  <developer>
    <name>Lux Sun</name>
    <email>28554482@qq.com</email>
    <organization>Lux Sun</organization>
    <url>https://github.com/LuxSun</url>
  </developer>
</developers>

<scm>
  <url>https://github.com/LuxSun/requestjson</url>
  <connection>https://github.com/LuxSun/requestjson.git</connection>
</scm>

修改 Maven 配置文件 settings.xml（一般位于 ~/.m2/settings.xml），在 <servers> 中增加 server 配置。这里的 <id> 必须与后面 pom.xml 中 distributionManagement 的仓库 id、以及 nexus-staging-maven-plugin 的 serverId 完全一致，否则 deploy 时会因找不到凭据而报 401/403。本文统一使用 ossrh：

<servers>
  <server>
    <id>ossrh</id>
    <username>Sonatype 账号</username>
    <password>Sonatype 密码</password>
  </server>
</servers>

部分老教程使用的是另一套 id：sonatype-nexus-snapshots 与 sonatype-nexus-staging，那是 oss-parent 预置的写法。两种写法都可以，但 settings.xml、pom.xml 与插件三处的 id 必须严格一致，不能混用。

根据官方指南，这里需要4个插件，

  • maven-source-plugin 用来生成Source Jar文件
  • maven-javadoc-plugin 用来生成 javadoc 文档
  • maven-gpg-plugin 用来对工程文件进行自动签名
  • nexus-staging-maven-plugin 用来将工程发布到中央仓库

另外注意：JDK 8 起 javadoc 默认启用了 doclint 检查，一旦 javadoc 注解不规范就会直接构建失败，需要在插件中把它关掉（2.x 版本用 <additionalparam>-Xdoclint:none</additionalparam>，3.x 版本可改用 <doclint>none</doclint>）。完整配置如下。

2、命令行配置

提示：Windows 下命令以 gpg 开头。较早的教程说 macOS 要用 gpg2，那是因为旧版 Homebrew 同时安装了 GnuPG 1.x 和 2.x；现在通过 Homebrew 安装的 GnuPG 2.x 直接提供 gpg 命令，gpg2 只是兼容用的软链接，用哪个都可以。

Windows 可以下载 Gpg4win，地址：https://www.gpg4win.org/download.html，安装后在命令行中执行 gpg --gen-key 生成密钥。过程中需要填写名字、邮箱等，其他步骤可以使用默认值；其中 passphrase 参数需要记住，它相当于密钥的密码，下一步发布过程中进行签名操作时会用到。

提示：GnuPG 2.1.17 及以上版本中 gpg --gen-key 依然可用，但走的是快速生成流程（算法与长度由版本默认值决定）；如果需要自选算法、密钥长度和有效期，请使用 gpg --full-generate-key。现代 GnuPG 2.2+ 的输出格式也有变化，密钥 ID 不再是下文示例里的 2048R/82DC852E，而是类似 rsa3072/82DC852E 或 ed25519/...，指纹为 40 位十六进制。

建议大家下载 Gpg4win-Vanilla 版本，因为它仅包括 GnuPG，这个工具才是我们所需要的。

安装 GPG 软件后，打开命令行窗口，依次做以下操作：

2.1、查看是否安装成功

gpg --version

能够显示 GPG 的版本信息，说明安装成功了。

2.2、生成密钥对

gpg --gen-key              # 快速生成
gpg --full-generate-key    # 需要自选算法、长度、有效期时使用

此时需要输入姓名、邮箱等字段，其它字段可使用默认值，此外，还需要输入一个 passphrase，相当于一个密钥库的密码，一定不要忘了，也不要告诉别人，最好记下来，因为后面会用到。

2.3、查看公钥

gpg --list-keys

输出如下信息（新版本可能格式会有点区别，不用担心，是正常的）：

C:/Users/huangyong/AppData/Roaming/gnupg/pubring.gpg
----------------------------------------------------

pub   2048R/82DC852E 2014-04-24
uid                  hy_think <hy_think@163.com>
sub   2048R/3ACA39AF 2014-04-24

可见这里的公钥的 ID 是：82DC852E，很明显是一个 16 进制的数字，马上就会用到。

2.4、将公钥发布到 PGP 密钥服务器（后面还需要操作此步骤）

gpg --keyserver hkp://keyserver.ubuntu.com:11371 --send-keys 82DC852E

此后，本地私钥用于对上传的构件进行数字签名，而下载该构件的用户可以通过公钥验证签名，从而确认构件确实由本人发布、没有被他人篡改。

提示：很多老教程里使用的 hkp://pool.sks-keyservers.net 已经停止服务，请改用仍在运行的密钥服务器，例如 hkp://keyserver.ubuntu.com:11371 或 hkps://keys.openpgp.org。另外，8 位短密钥 ID 存在碰撞风险，条件允许时建议直接使用 gpg --fingerprint 得到的 40 位完整指纹。

2.5、查询公钥是否发布成功

gpg --keyserver hkp://keyserver.ubuntu.com:11371 --recv-keys 82DC852E

这一步实际上就是从密钥服务器上按公钥 ID 接收公钥；能够成功取回，说明 2.4 节的发布已经生效。也可以在浏览器中打开 https://keyserver.ubuntu.com 按公钥 ID 或邮箱查询。

四、上传构件到 OSS 中

这步就简单了，就是一套命令（-Darguments 用于把 GPG 的 passphrase 传给 maven-gpg-plugin，省去每次弹窗输入；也可以省略该参数，改为在弹窗中手动输入）：

mvn clean deploy -P release -Darguments="gpg.passphrase=密钥密码"

如果保留了 oss-parent，对应的 profile 名是 sonatype-oss-release，命令写成 mvn clean deploy -P sonatype-oss-release -Darguments="gpg.passphrase=密钥密码" 即可，两种写法效果一致。

或者

先通过 cmd 进入到项目的这个目录下。

再执行下面命令。

当执行以上 Maven 命令时，会自动弹出对话框，要求输入上面提到的 passphrase——它就是该 GPG 密钥对的密码，只有自己知道。随后会看到大量的 upload 信息，而且速度比较慢，经常会 timeout，需要反复尝试。

注意：此时上传的构件并未正式发布到中央仓库中，只是部署到 OSS 中了，下面才是真正的发布。

五、在 OSS 中发布构件

进入 https://oss.sonatype.org/#stagingRepositories 查看发布的构件，点击左侧的 Staging Repositories——一般最后一个就是刚发布的 jar，此时构件状态为 open。

打开命令行窗口，查看gpg key并上传到第三方的key验证库：

E:\98_code\workSpace\marathon-client>gpg --list-keys

C:/Users/VF/AppData/Roaming/gnupg/pubring.gpg
---------------------------------------------

pub   2048R/824B4D7A 2016-01-06
uid       [ultimate] cloudnil <cloudnil@126.com>
sub   2048R/7A10AD69 2016-01-06


E:\98_code\workSpace\marathon-client>gpg --keyserver hkp://keyserver.ubuntu.com:11371 --send-keys 824B4D7A
gpg: sending key 824B4D7A to hkp server keyserver.ubuntu.com

E:\98_code\workSpace\marathon-client>

回到 https://oss.sonatype.org/#stagingRepositories，选中刚发布的构件，点击上方的 Close → Confirm；在下方的 Activity 选项卡查看状态，变成 closed 后执行 Release → Confirm，成功后构件仓库会被自动清理。

需要在曾经创建的 Issue 下面回复一条“构件已成功发布”的评论，这是为了通知 Sonatype 的工作人员为需要发布的构件做审批，发布后会关闭该 Issue。

一小段时间（约 1–2 个小时）后即可在 https://central.sonatype.com 检索到（旧的 http://search.maven.org 已跳转到该站点）；第三方站点 https://mvnrepository.com 的索引更新会慢一些，通常需要 24–48 小时。

提示：这里有一个大坑——很多教程会把公钥上传（2.4 节）安排在整个流程的最开头。生成密钥确实可以一开始就做，但把公钥发布到密钥服务器这一步建议放到构件已经上传、准备 Close/Release 时再执行；否则在 Staging Repositories 中的审核会一直失败。

最后想说：第一次总是比较痛苦，以后就舒服了。没错，只有第一次发布如此折腾；以后 deploy 的构件会自动发布到中央仓库，无需再这样操作。（附：成功效果图）

附：
在编码过程中，有些通用的代码模块，有时候我们不想通过复制拷贝来粗暴地复用，因为这样不仅体现不了变化，也不利于统一管理。这里我们使用maven deploy的方式，将通用的模块打成jar包，发布到nexus，让其他的项目来引用，以更简洁高效的方式来实现复用和管理。

  • 第一：Maven 的 settings.xml 文件中设置 <server> 标签

    <server>
  <id>my-deploy-release</id>
  <username>admin</username>
  <password>admin123</password>
</server>

<server>
  <id>my-deploy-snapshot</id>
  <username>admin</username>
  <password>admin123</password>
</server>

    此处设置的用户名和密码都是nexus的登录配置。

  • 第二：在项目的pom.xml文件中设置

    <distributionManagement>
    <repository>
        <id>my-deploy-release</id>
        <url>http://192.168.1.123:8081/nexus/content/repositories/releases/</url>
    </repository>

    <snapshotRepository>
        <id>my-deploy-snapshot</id>
        <url>http://192.168.1.123:8081/nexus/content/repositories/snapshots/</url>
    </snapshotRepository>

</distributionManagement>

    在此，url都是nexus相应仓库的链接地址，这一步做完之后，已经完成了发布所需要的基本配置。【试试命令：mvn deploy】

    注意：repository 的 id 要和 settings.xml 中 server 的 id 一致；Maven 发布时会根据该 id 查找对应的用户名密码进行登录验证并上传文件。

  • 第三：发布的灵活性配置

    maven会判断版本后面是否带了-SNAPSHOT，如果带了就发布到snapshots仓库，否则发布到release仓库。这里我们可以在pom.xml文件中，设置。

    <groupId>com.test</groupId>
<artifactId>my-test</artifactId>
<packaging>jar</packaging>
<version>${project.release.version}</version>

<properties>
    <java.version>1.8</java.version>
    <project.release.version>1.0-SNAPSHOT</project.release.version>
</properties>

<profiles>
    <profile>
        <id>product</id>
        <properties>
            <project.release.version>1.0</project.release.version>
        </properties>
    </profile>
</profiles>

    说明：通过占位符${project.release.version}来控制需要发布的版本，用命令mvn deploy -P product，发布my-test的1.0版本到releases库。如果使用命令mvn deploy，则默认使用 1.0-SNAPSHOT版本号，将发布my-test的1.0-SNAPSHOT版本到snapshots库。

  • 第四：发布时遇到的一些问题

    部署到snapshot仓库时，jar包会带上时间戳，这没关系，maven会自动取相应版本最新的jar包；
    Failed to execute goal org.apache.maven.plugins:maven-deploy-plugin:2.8.2:deploy (default-deploy) on project my-test: Failed to deploy artifacts: Could not transfer artifact...from/to release...部署到release仓库时，相同版本的jar包不能提交。
    原因：因为release的部署策略是【disable redeploy】，不允许覆盖更新组件。
    解决办法：修改一下版本号，再提交即可。之前其实还可以通过人工客服聊天帮忙删除不想要的Jar包，但是现在不行了，只能通过上传新版本，所以有些童鞋想做测试的需要注意这一点。
    打包指定的文件/文件夹在代码中也有体现（含：doc、sources、class）。
    Maven deploy 时，为什么没有生成对应的 javadoc 和 sources（前提已经有插件部署好）？
    原因：这两个插件的 execution 都绑定在 release profile 中，只有显式激活 profile（例如 mvn deploy -P release）时才会执行；直接执行 mvn deploy 不会激活 profile，自然也就不会生成 javadoc 包和 sources 包。
