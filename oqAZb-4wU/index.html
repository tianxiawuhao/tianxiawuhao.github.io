k8s1.24.1安装（基于Centos 7）

Posted on 2022-05-28，35 min read

注意：除了Master节点初始化及Node节点添加分别在Master节点和Node节点执行外，其余所有命令均在所有节点执行

阅读前先看版本与路线说明

  • Kubernetes 1.24 已在 kubelet 中移除 dockershim，Docker Engine 不再是"装上就能用"的运行时。第 14 小节（Docker + cri-dockerd）与第 15 小节（containerd）是两条互斥的路线，只需选一条：路线 A 用 containerd，组件最少，也是官方推荐；路线 B 保留 Docker，额外装 cri-dockerd。第 18 小节初始化时的 criSocket 必须与所选路线一致。
  • 镜像仓库：1.24 的 kubeadm 默认仓库仍是 k8s.gcr.io；registry.k8s.io 从 1.25 起成为默认地址，同时也能提供 1.24 的镜像，可用 --image-repository=registry.k8s.io 显式指定。国内环境用 registry.aliyuncs.com/google_containers 最省事。
  • 版本锁定：kubelet、kubeadm、kubectl 必须同为 1.24.1 并锁定，kubelet 不支持跨次版本升级（1.24.x 只能升到 1.24.y）。
  • 1.24 的 kubelet 只实现了 CRI v1，因此 containerd 必须 ≥ 1.6（Docker CE 源里的 containerd.io 满足）；更老的 1.5.x 会报 CRI v1 runtime API is not implemented。
  • kube-proxy 的 IPVS 模式、CNI 插件（Calico/Flannel）都要选与 1.24 匹配的版本，见第 13、19 小节；文末还有一节常见报错与排查。

10.配置内核参数

将桥接的 IPv4 流量传递到 iptables 的链

1.设置内核参数

这里有两处与"升级后的新内核"直接相关的问题，先说明再给命令：

  • net.ipv4.tcp_tw_recycle 已在 Linux 4.12 中被移除。本文第 1 小节把内核升到了 5.x，保留这一行会让 sysctl -p 报 cannot stat /proc/sys/net/ipv4/tcp_tw_recycle: No such file or directory，因此直接删掉。
  • 注释不要写在等号后面：不同版本的 sysctl 对行尾注释的解析不一致，可能把 # 禁止使用swap空间… 一起当成值，导致整行设置失败；注释请单独成行（下面已挪到行首）。
cat > /etc/sysctl.d/k8s.conf <<EOF
# 桥接流量交给 iptables/ip6tables 处理，需要配合 br_netfilter 模块
net.bridge.bridge-nf-call-iptables=1
net.bridge.bridge-nf-call-ip6tables=1
net.ipv4.ip_forward=1
# 禁用 swap 倾向；kubelet 1.24 尚不支持 swap
vm.swappiness=0
# 不检查物理内存是否够用；开启 OOM
vm.overcommit_memory=1
vm.panic_on_oom=0
fs.inotify.max_user_instances=8192
fs.inotify.max_user_watches=1048576
fs.file-max=52786963
fs.nr_open=52706963
# 关闭 IPv6；集群内要用 IPv6 请删掉这一行
net.ipv6.conf.all.disable_ipv6=1
net.netfilter.nf_conntrack_max=2310720
EOF

2.加载内核模块

modprobe br_netfilter
# 持久化：CentOS 7 的 /etc/rc.local 默认没有执行权限，开机自动加载要用 modules-load.d
cat > /etc/modules-load.d/k8s.conf <<EOF
br_netfilter
EOF

另外 net.netfilter.nf_conntrack_max 需要 nf_conntrack 模块已加载，否则 sysctl -p 会提示找不到该键（可先执行 modprobe nf_conntrack）。

3.使内核参数生效

13.开启IPVS

由于ipvs已经加入到了内核的主干，所以为kube-proxy开启ipvs的前提需要加载以下的内核模块

cat > /etc/sysconfig/modules/ipvs.modules <<EOF
#!/bin/bash
modprobe -- ip_vs
modprobe -- ip_vs_rr
modprobe -- ip_vs_wrr
modprobe -- ip_vs_sh
EOF

两处修正：

  • 原来的第一行是全角感叹号 #！/bin/bash，脚本不会以 bash 执行，必须写成半角 #!/bin/bash。
  • nf_conntrack_ipv4 从 Linux 4.19 起已被 nf_conntrack 取代。本文第 1 小节把内核升到了 5.x，这一行会报 Module nf_conntrack_ipv4 not found，直接删掉即可（连接跟踪由 nf_conntrack 提供，IPVS 模式会自动使用）。

授权启动

chmod 755 /etc/sysconfig/modules/ipvs.modules && bash /etc/sysconfig/modules/ipvs.modules && lsmod

接下来还需要确保各个节点上已经安装了ipset软件包。 为了便于查看ipvs的代理规则，最好安装一下管理工具ipvsadm。

yum install ipset ipvsadm -y

service 底层实现主要由两种网络模式组成：iptables 与 IPVS，它们都是由 kube-proxy 维护的

Iptables VS IPVS

Iptables：

• 灵活，功能强大

• 规则遍历匹配和更新，呈线性时延

IPVS：

• 工作在内核态，有更好的性能

• 调度算法丰富：rr，wrr，lc，wlc，ip hash

14.2.cri-dockerd安装（路线 B 必需）

CRI-Dockerd 其实就是从被移除的 Docker Shim 中，独立出来的一个项目，用于解决历史遗留的节点升级 Kubernetes 的问题。

kubelet并没有直接和dockerd交互，而是通过了一个dockershim的组件间接操作dockerd。dockershim提供了一个标准的接口，让kubelet能够专注于容器调度逻辑本身，而不用去适配dockerd的接口变动。而其他实现了相同标准接口的容器技术也可以被kubelet集成使用，这个接口称作CRI。dockershim和CRI的出现也是容器生态系统演化的历史产物。在k8s最早期的版本中是不存在dockershim的，kubelet直接和dockerd交互。但为了支持更多不同的容器技术（避免完全被docker控制容器技术市场），kubelet在之后的版本开始支持另一种容器技术rkt。这给kubelet的维护工作造成了巨大的挑战，因为两种容器技术没有统一的接口和使用逻辑，kubelet同时支持两种技术的使用还要保证一致的容器功能表现，对代码逻辑和功能可靠性都有很大的影响。为了解决这个问题，k8s提出了一个统一接口CRI，kubelet统一通过这个接口来调用容器功能。但是dockerd并不支持CRI，k8s就自己实现了配套的dockershim将CRI接口调用转换成dockerd接口调用来支持CRI。因此，dockershim并不是docker技术的一部分，而是k8s系统的一部分

使用 CRI-Dockerd 项目

项目地址：https://github.com/Mirantis/cri-dockerd

cri-dockerd 的版本要与 Kubernetes 次版本对应（1.24 用 v0.2.x，下文示例为 v0.2.0），升级集群时一并升级。

1.下载cri-dockerd二进制包或者源码自己编译

# 下载文件
wget https://github.com/Mirantis/cri-dockerd/releases/download/v0.2.0/cri-dockerd-v0.2.0-linux-amd64.tar.gz
# 解压文件
tar -xvf cri-dockerd-v0.2.0-linux-amd64.tar.gz
# 复制二进制文件到指定目录
cp cri-dockerd /usr/bin/

2.配置启动文件

# 配置启动文件
cat <<"EOF" > /usr/lib/systemd/system/cri-docker.service
[Unit]
Description=CRI Interface for Docker Application Container Engine
Documentation=https://docs.mirantis.com
After=network-online.target firewalld.service docker.service
Wants=network-online.target
Requires=cri-docker.socket

[Service]
Type=notify

ExecStart=/usr/bin/cri-dockerd --container-runtime-endpoint fd:// --network-plugin=cni --cni-bin-dir=/opt/cni/bin \
          --cni-conf-dir=/etc/cni/net.d --image-pull-progress-deadline=30s --pod-infra-container-image=registry.aliyuncs.com/google_containers/pause:3.7 \
          --docker-endpoint=unix:///var/run/docker.sock --cri-dockerd-root-directory=/var/lib/docker
ExecReload=/bin/kill -s HUP $MAINPID
TimeoutSec=0
RestartSec=2
Restart=always

# Note that StartLimit* options were moved from "Service" to "Unit" in systemd 229.
# Both the old, and new location are accepted by systemd 229 and up, so using the old location
# to make them work for either version of systemd.
StartLimitBurst=3

# Note that StartLimitInterval was renamed to StartLimitIntervalSec in systemd 230.
# Both the old, and new name are accepted by systemd 230 and up, so using the old name to make
# this option work for either version of systemd.
StartLimitInterval=60s

# Having non-zero Limit*s causes performance problems due to accounting overhead
# in the kernel. We recommend using cgroups to do container-local accounting.
LimitNOFILE=infinity
LimitNPROC=infinity
LimitCORE=infinity

# Comment TasksMax if your systemd version does not support it.
# Only systemd 226 and above support this option.
TasksMax=infinity
Delegate=yes
KillMode=process

[Install]
WantedBy=multi-user.target

EOF

# 生成socket 文件
cat <<"EOF" > /usr/lib/systemd/system/cri-docker.socket
[Unit]
Description=CRI Docker Socket for the API
PartOf=cri-docker.service

[Socket]
ListenStream=/var/run/cri-dockerd.sock
SocketMode=0660
SocketUser=root
SocketGroup=docker

[Install]
WantedBy=sockets.target

EOF

socket 的两种接法不要混用：上面的 cri-docker.socket 中 ListenStream=/var/run/cri-dockerd.sock 表示由 systemd 创建并监听该 socket（socket 激活），此时 ExecStart 必须用 fd:// 接收 systemd 传入的 fd。如果像某些文章那样在 ExecStart 里同时写 unix:///var/run/cri-dockerd.sock，cri-dockerd 会再去 bind 同一个路径，报 address already in use 起不来。

systemctl daemon-reload
systemctl start cri-docker
#设置开机启动
systemctl enable cri-docker
# 查看启动状态
systemctl status cri-docker

常见报错与排查

1.24 移除 dockershim 之后，初始化失败绝大多数集中在运行时（CRI）这一层：kubelet 能起来，但连不上容器运行时，或者拉不到 pause 沙箱镜像。下面按报错信息归类，命中后按对应分支处理。

1.沙箱镜像（pause）拉取失败

Failed to create pod sandbox: rpc error: code = Unknown desc = failed to get sandbox image
"registry.k8s.io/pause:3.6": failed to pull image: dial tcp: i/o timeout

两个常见原因：一是到 k8s.gcr.io/registry.k8s.io 的网络不通；二是 containerd 里配置的 sandbox_image 版本与 kubeadm 期望的 pause 版本不一致（1.24.1 期望 pause:3.7）。

# kubeadm 期望的 pause 版本
kubeadm config images list | grep pause
# containerd 实际使用的版本
grep sandbox_image /etc/containerd/config.toml
# 统一改成国内镜像 + 正确版本，然后重启 containerd
sed -i 's#sandbox_image = .*#sandbox_image = "registry.aliyuncs.com/google_containers/pause:3.7"#' /etc/containerd/config.toml
systemctl restart containerd
crictl pull registry.aliyuncs.com/google_containers/pause:3.7

2.运行时连接失败：CRI v1 未实现或 socket 路径不对

failed to run Kubelet: validate service connection: CRI v1 runtime API is not implemented for endpoint
"unix:///run/containerd/containerd.sock": rpc error: code = Unimplemented

1.24 的 kubelet 只实现了 CRI v1，containerd 1.5.x 只提供 v1alpha2，必须升级到 1.6 及以上（用 containerd --version 确认）。另一类同族报错是 connection refused 或 no such file or directory，通常是把 socket 路径写错了（cri-dockerd 与 containerd 的路径不同，且 socket 激活方式下路径必须与 systemd 单元一致）。

systemctl status containerd cri-docker
ls -l /run/containerd/containerd.sock /var/run/cri-dockerd.sock
# kubeadm 的 --cri-socket（或配置文件里的 criSocket）必须指向真实存在的那个，且所有节点一致

3.预检失败：iptables 参数、swap、端口占用

[ERROR FileContent--proc-sys-net-bridge-bridge-nf-call-iptables]: /proc/sys/net/bridge/bridge-nf-call-iptables contents are not set to 1
[ERROR Swap]: running with swap on is not supported. Please disable swap
[ERROR Port-6443]: Port 6443 is in use
[ERROR Port-10250]: Port 10250 is in use

# 1) iptables 参数：加载 br_netfilter 并让内核参数生效
modprobe br_netfilter && sysctl -p /etc/sysctl.d/k8s.conf
# 2) swap：确认已关闭，且 /etc/fstab 里已注释
swapoff -a && free -h && grep swap /etc/fstab
# 3) 端口：确认是谁占用了 6443/10250/10257/10259/2379/2380
ss -lntp | grep -E ':(6443|10250|10257|10259|2379|2380)'
# 确认是上一次失败留下的残留后，重置再试（重置命令见文末）
kubeadm reset -f --cri-socket unix:///var/run/cri-dockerd.sock

如果只是临时验证、确实不想关 swap，可以在 init 时加 --ignore-preflight-errors=Swap；但这只是跳过检查，1.24 的 kubelet 并不支持 swap，生产环境仍应关闭。

4.cgroup driver 不一致

failed to create kubelet: misconfiguration: kubelet cgroup driver: "cgroupfs" is different from
docker cgroup driver: "systemd"

三处必须是同一个值 systemd：containerd 的 SystemdCgroup = true、Docker 的 native.cgroupdriver=systemd、kubelet 的 cgroupDriver。kubeadm 1.22 之后默认就使用 systemd，一般无需手工改，确认方式：

grep cgroupDriver /var/lib/kubelet/config.yaml
docker info | grep -i cgroup
grep -n SystemdCgroup /etc/containerd/config.toml

5.证书到期

Unable to connect to the server: x509: certificate has expired or is not yet valid

kubeadm 签发的集群证书默认有效期 1 年（CA 为 10 年），到期症状通常是 apiserver 起不来或 kubectl 报 x509。先看剩余时间，再续期并重启控制面组件（静态 Pod 会被 kubelet 自动重建）。1.24 的命令已经是 kubeadm certs（1.15 之前的老集群是 kubeadm alpha certs）。

kubeadm certs check-expiration
kubeadm certs renew all
systemctl restart kubelet
