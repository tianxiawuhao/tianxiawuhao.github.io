JPA 与 ORM 入门

Posted on 2026-09-19，9 min read

上一章已经讲过 SQL、索引与事务。但真正写代码时，手边是 Java 对象，数据库那边是表和列，中间那层转换全靠手工：拼 SQL、遍历 ResultSet、逐列 set、在 finally 中关闭连接。字段改一次，就要改一串地方。本章介绍 ORM 与 JPA——由框架自动完成对象与表之间的映射，开发者只负责声明实体、调用方法。内容覆盖 JPA 的定位、persistence.xml 配置、实体注解、EntityManager 的增删改查以及 JPQL 查询。本章适合已经会写 SQL 与 JDBC、准备在项目中引入持久层框架的读者。

为什么需要 ORM：从手写 JDBC 到对象映射

用 JDBC 查一个用户，至少要写四步：拿连接、拼 SQL、遍历结果集、关闭资源。样板代码之外，真正的痛点是“阻抗失配”：Java 中继承、引用、集合一应俱全，数据库里却是表、外键、行，两者没有天然对应。ORM（Object-Relational Mapping，对象关系映射）就是自动化这层转换的中间件：一张表映射成一个类，一行映射成一个对象，一列映射成一个属性。SQL 的生成、连接与事务则交给框架。

JPA（Java Persistence API，现称 Jakarta Persistence）是一套规范。它只定义注解（@Entity、@Id 等）与接口（EntityManager、Query 等），不提供具体实现。Hibernate 是最流行的实现，这样分层的好处是业务代码只依赖 JPA API，更换实现时改动很小。要注意包名的分水岭。Java EE 与 Spring Boot 2.x 使用 javax.persistence，Spring Boot 3.x 起改用 jakarta.persistence。两边注解同名，却不能混用。与 MyBatis 相比，JPA 是“全自动”——简单 CRUD 几乎不写 SQL；MyBatis 是“半自动”——SQL 由开发者编写，它只做参数与结果映射。复杂报表类查询，JPA 也可以退回 createNativeQuery 写原生 SQL。

ORM 的收益不止省代码：Hibernate 会维护一级缓存与脏检查，同一个工作单元里重复取同一行只发一条 SQL。对象字段改了也不用手写 update，连接、事务、方言差异都被挡在框架内部。代价也要认清——SQL 由框架生成，写得不好可能悄悄退化成 N+1 或全表扫描，排查时必须打开 SQL 日志；映射本身也有学习曲线，注解配错往往到启动或首次查询才暴露。所以 ORM 并不是“不用懂 SQL”，恰恰相反，它要求开发者更懂 SQL，才能看懂框架究竟发出了哪些语句。

最小可用配置：persistence.xml

JPA 要求类路径下的 META-INF/persistence.xml 至少声明一个 persistence-unit，它描述用哪个实现、连哪个库、映射哪些实体。transaction-type="RESOURCE_LOCAL" 表示事务由程序自行管理（通过 EntityTransaction），适合 Java SE 与单元测试。跑在 Java EE 容器里则用 JTA 交给容器。

<?xml version="1.0" encoding="UTF-8"?>
<persistence xmlns="http://xmlns.jcp.org/xml/ns/persistence"
             xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
             xsi:schemaLocation="http://xmlns.jcp.org/xml/ns/persistence
                                 http://xmlns.jcp.org/xml/ns/persistence/persistence_2_2.xsd"
             version="2.2">
  <persistence-unit name="jpaUnit" transaction-type="RESOURCE_LOCAL">
    <provider>org.hibernate.jpa.HibernatePersistenceProvider</provider>
    <class>com.example.domain.Customer</class>
    <properties>
      <property name="javax.persistence.jdbc.driver" value="com.mysql.cj.jdbc.Driver"/>
      <property name="javax.persistence.jdbc.url"
                value="jdbc:mysql://localhost:3306/jpademo?serverTimezone=Asia/Shanghai"/>
      <property name="javax.persistence.jdbc.user" value="root"/>
      <property name="javax.persistence.jdbc.password" value="123456"/>
      <property name="hibernate.dialect" value="org.hibernate.dialect.MySQL8Dialect"/>
      <property name="hibernate.hbm2ddl.auto" value="update"/>
      <property name="hibernate.show_sql" value="true"/>
      <property name="hibernate.format_sql" value="true"/>
    </properties>
  </persistence-unit>
</persistence>

几个容易踩的点。provider 类名要和版本对齐：Hibernate 4.3 与 5.x 使用 org.hibernate.jpa.HibernatePersistenceProvider。老教程里的 org.hibernate.ejb.HibernatePersistence 属于 Hibernate 3/4 早期。在 JPA 2.x 下使用它会直接抛 ClassNotFoundException。hbm2ddl.auto 只该出现在开发期：update 会自动加表加列，create-drop 每次重建。生产上应当使用 validate 或干脆不配，把 DDL 交给 Flyway、Liquibase 这类迁移工具。show_sql 与 format_sql 的默认值都是 false，想看到 SQL 必须显式配成 true，或把 org.hibernate.SQL 的日志级别设为 debug。Spring Boot 项目通常不再手写这个文件，而是在 application.yml 中配置 spring.datasource.* 与 spring.jpa.*，但底层仍是同一套属性。连接池相关的老属性也可以省掉：Hibernate 4.3 起会自动探测类路径上的连接池，Spring Boot 项目更推荐直接配置 spring.datasource.hikari.*。

实体类：用注解把类映射成表

@Entity
@Table(name = "cst_customer")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long custId;

    @Column(name = "cust_name", nullable = false, length = 32)
    private String custName;

    @Column(name = "cust_source")
    private String custSource;

    protected Customer() { }   // JPA 需要无参构造器，可见性可以是 protected

    public Customer(String custName) { this.custName = custName; }

    public Long getCustId() { return custId; }
    public String getCustName() { return custName; }
    public void setCustName(String custName) { this.custName = custName; }
}

逐个说明：@Entity 标记这是一个实体，name 属性默认取类名，JPQL 中使用的就是这个名字。@Table 指定表名，不写则由命名策略从类名推导（CustomerOrder 推导为 customer_order）。@Id 必须落在主键字段上，@GeneratedValue 指定生成策略。IDENTITY 依赖数据库自增列（MySQL、SQL Server），SEQUENCE 依赖序列（Oracle、PostgreSQL）。TABLE 用一张专用表模拟，AUTO 则交给实现按数据库方言自行选择。有教程称“AUTO 在 MySQL 下会采用一个特定的表来保存主键”，这个说法并不准确。Hibernate 在 MySQL 上如何实现 AUTO 取决于版本与方言，想要确定的行为就应显式写 IDENTITY。

@Column 的常用属性是 name、nullable、unique、length、insertable、updatable。最后两个属性名容易写错：写成 inserttable、updateable 根本无法通过编译。另外两点：实体不能是 final 类；字段访问与属性访问（注解写在字段上还是 getter 上）要全类统一，混用会在启动时报错。

EntityManager 的增删改查与事务

运行时入口是 EntityManagerFactory：它线程安全、重量级，内部持有连接池与缓存，整个应用只建一个，相当于 Hibernate 的 SessionFactory。EntityManager 正好相反——轻量、非线程安全，每个请求或每个工作单元创建一个，用完关闭。

public final class JpaUtils {
    private static final EntityManagerFactory EMF =
            Persistence.createEntityManagerFactory("jpaUnit");

    private JpaUtils() { }

    public static EntityManager getEntityManager() {
        return EMF.createEntityManager();   // persistence-unit 的 name 必须与 xml 一致
    }

    public static void close() { EMF.close(); }
}

// ---- 增删改查：EntityManager 与事务 ----
EntityManager em = JpaUtils.getEntityManager();
EntityTransaction tx = em.getTransaction();
try {
    tx.begin();

    Customer c = new Customer("张三");
    em.persist(c);                       // 瞬时态 -> 持久化态，INSERT 在 flush/commit 时发出
    Long id = c.getCustId();             // IDENTITY 策略下，persist 后即可拿到自增主键

    Customer found = em.find(Customer.class, id);       // 立即 SELECT，查不到返回 null
    Customer ref = em.getReference(Customer.class, id); // 延迟代理，访问属性才查库

    found.setCustName("李四");            // 托管对象无需 update，脏检查后自动 UPDATE
    Customer managed = em.merge(ref);     // 游离对象的改动复制回托管实例，返回托管实例
    em.remove(managed);                   // remove 只能作用于托管对象

    tx.commit();
} finally {
    em.close();                           // 必须关闭，否则连接池很快耗尽
}

这里的关键是实体的四个状态：瞬时态、持久化态、游离态与删除态。new 出来的对象是瞬时态。persist 或查询之后进入持久化态，此后任何字段改动都会在 flush 时同步到数据库，不需要调用 update。em.close() 或 clear() 之后变成游离态；调用 remove 后进入删除态，提交事务时执行 DELETE。merge 把游离对象的改动复制回一个托管实例并把托管实例返回，所以一定要接住它的返回值。此外，除查询外的写操作必须包含在活动事务中，否则不会真正落库，甚至抛 TransactionRequiredException。最后要注意 EntityManager 自带一级缓存：同一个 em 里连续 find 同一主键两次，第二次不会再发 SQL，拿到的是同一个对象引用，这正是脏检查能生效的前提。

JPQL：面向实体的查询语言

JPQL 语法接近 SQL，但操作的是实体名和属性名，不是表名和列名——这带来可移植性，换数据库时查询基本不用改。查询通过 em.createQuery 得到 TypedQuery，参数一律用 setParameter 绑定，不要拼字符串，既慢又有注入风险。@NamedQuery 则可以把固定 JPQL 写在实体类上，启动时预编译、不必每次解析，适合热点查询。

String jpql = "select c from Customer c where c.custName = :name order by c.custId desc";

List<Customer> page = em.createQuery(jpql, Customer.class)
        .setParameter("name", "张三")
        .setFirstResult(0)      // 分页：从第 0 条开始
        .setMaxResults(10)      // 取 10 条
        .getResultList();

Customer one = em.createQuery(
                "select c from Customer c where c.custId = :id", Customer.class)
        .setParameter("id", 1L)
        .getSingleResult();     // 无结果抛 NoResultException，多条抛 NonUniqueResultException

// join fetch 一次把关联对象取回，避免 N+1
List<Customer> withOrders = em.createQuery(
                "select distinct c from Customer c join fetch c.orders where c.custName like :n",
                Customer.class)
        .setParameter("n", "张%")
        .getResultList();

参数写法上，具名参数（:name）比位置参数（?1，从 1 开始编号）更易读；集合条件用 setParameter("ids", idList) 配 in :ids。批量 update / delete 的 JPQL 会绕过持久化上下文直接写库，内存中已加载的托管对象不会同步，执行后最好调用一次 em.clear()，以免读到旧值。

常见坑：延迟加载、N+1 与 equals

第一是 LazyInitializationException：@OneToMany 默认 LAZY，@ManyToOne 默认 EAGER。一旦 EntityManager 关闭后再访问未加载的集合，就会抛出该异常。解决办法是在事务内初始化，或用 join fetch、@EntityGraph 提前取回。第二是 N+1 查询：查出 100 个订单再逐个取客户，一共发出 1+100 条 SQL。可以用 join fetch 或 hibernate.default_batch_fetch_size 合并。第三，实体不要用 Lombok 的 @Data 自动生成 equals/hashCode，延迟代理类和可变字段都会让它出错，应基于主键或业务唯一键手写。

小结：ORM 解决的是对象与表之间的翻译问题，JPA 把这层能力标准化，Hibernate 提供实现。落地顺序很清楚——先准备好 persistence-unit（或使用 Spring Boot 的 spring.jpa.*），用 @Entity、@Id、@Column 声明映射。再从 EntityManagerFactory 取到 EntityManager 作为工作单元，所有写操作包在事务里。查询优先使用 JPQL 加参数绑定，关联对象用 join fetch 一次取回。记住三件事就不会出错：EntityManager 不是线程安全的，写操作必须有事务，延迟加载的对象必须在工作单元内用完。
