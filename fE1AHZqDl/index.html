Java线程同步五种方法

Posted on 2021-05-04，6 min read

线程同步

即当有一个线程在对内存进行操作时，其他线程都不可以对这个内存地址进行操作，直到该线程完成操作，其他线程才能对该内存地址进行操作，而其他线程又处于等待状态。这句话描述的其实是互斥，但线程安全问题不止互斥一种：可见性、原子性出了问题，同样会读到脏数据。所以下面这五种手段严格说覆盖了四类思路——互斥（synchronized、ReentrantLock）、可见性（volatile）、避免共享（ThreadLocal），以及后文补充的原子性工具（Atomic 类与并发容器）。

先看图，五种手段各自提供了什么保证、边界在哪里：

同步方法

使用 synchronized 关键字修饰的方法。由于 Java 的每个对象都有一个内置锁（monitor），用关键字修饰方法时，内置锁会保护整个方法：调用该方法前需要获得内置锁，否则该线程就处于阻塞状态。

public class Counter {

    private int count = 0;

    // 实例方法：锁住的是当前对象 this
    public synchronized void increment() {
        count++;
    }

    // 静态方法：锁住的是当前类的 Class 对象（Counter.class）
    public static synchronized void reset() {
        // 静态方法没有 this，它锁的是类对象
    }

    // 上面两个方法分别等价于下面两个同步代码块
    public void incrementEquals() {
        synchronized (this) {
            count++;
        }
    }

    public static void resetEquals() {
        synchronized (Counter.class) {
            // ...
        }
    }
}

三个要点容易记混：synchronized 是可重入的，同一个线程再次进入不会把自己锁死；方法抛出异常时虚拟机会自动释放锁，不需要手写释放逻辑；对象锁与类锁是两把完全不同的锁，一个线程持有 Counter.class 并不妨碍另一个线程进入实例同步方法，两者并不互斥。另外，同步方法把整个方法体都变成临界区，粒度偏大，里面的 IO、RPC 等耗时操作会明显拉低吞吐。

同步代码块

即用 synchronized 关键字修饰的语句块：synchronized (锁对象) { ... }。被修饰的语句块会自动加上内置锁，与同步方法相比，它可以自行指定锁对象，并把临界区缩到最小。

锁对象的选择有三条经验：用专用的 private final Object lock = new Object()；不要用字符串常量或 Integer.valueOf() 这类可能被复用、被缓存的对象；不要用 this 或对外暴露的对象，否则外部代码也能拿到同一把锁，锁的边界就失控了。

public class TicketWindow {

    private final Object lock = new Object();
    private int tickets = 100;

    public void sell() {
        // 只有判断和扣减需要互斥，其它逻辑留在同步块外
        synchronized (lock) {
            if (tickets > 0) {
                tickets--;
            }
        }
    }
}

注：同步是一种高开销的操作，因此应该尽量减少同步的内容。通常没有必要去同步整个方法，用关键字 synchronized 修饰关键代码即可。

还要避免嵌套加锁时顺序不一致：线程 A 先锁 a 再锁 b，线程 B 先锁 b 再锁 a，就会互相等待形成死锁。统一加锁顺序，或者用后面介绍的 tryLock(timeout) 打破循环等待，是两种常见解法。

使用特殊域变量修饰符volatile实现线程同步

（1）volatile 是一种非锁的、比 synchronized 稍弱的同步机制，只能用于修饰变量（字段），不能修饰局部变量。

（2）保证可见性：当一个线程修改了 volatile 变量，新值会立即同步回主内存，其他线程每次使用前都会从主内存重新读取，而不是一直使用线程工作内存里的旧副本。

（3）不保证原子性：i++ 实际是「读—改—写」三步，两个线程交替执行仍会丢更新。所以 volatile 变量只适合「一个线程写、多个线程读」的场景，计数器要改用 Atomic 类或加锁。

（4）禁止指令重排序：对 volatile 变量的写操作后会插入写屏障、读操作前会插入读屏障，重排序不能跨越屏障，因此 volatile 写之前的操作对随后读该变量的线程是可见的。

（5）volatile 不能与 final 同时修饰同一个变量，这是编译期错误；它也不会提供互斥，无法保护复合操作。

下面是一个典型的可见性问题示例：读线程一直循环等待标志位被修改。如果去掉 volatile，JIT 可能把变量提升到寄存器，读线程永远看不到修改，程序一直不退出。

import java.util.concurrent.TimeUnit;

public class VisibilityDemo {

    // 去掉 volatile 后，读线程可能永远看不到 running 的修改
    // 注意：改成 static 并不能解决可见性问题，static 只表示「全局只有一份存储」
    private volatile boolean running = true;

    private void stop() {
        running = false;
    }

    private void work() {
        while (running) {
            // 真正的工作逻辑
        }
        System.out.println("------stoped");
    }

    public static void main(String[] args) throws Exception {
        VisibilityDemo demo = new VisibilityDemo();

        Thread worker = new Thread(demo::work, "worker");
        worker.start();

        // 给读线程一点时间进入循环，再修改标志位
        TimeUnit.SECONDS.sleep(1);
        demo.stop();
        System.out.println("------");
    }
}

volatile 的另一个经典用途是双重检查锁定的单例：单例字段必须声明为 volatile，否则可能把「已分配内存但尚未初始化完成」的对象引用发布出去，其他线程拿到半成品。

public class Singleton {

    private static volatile Singleton instance;

    private Singleton() {
    }

    public static Singleton getInstance() {
        if (instance == null) {                 // 第一次检查：避免每次调用都加锁
            synchronized (Singleton.class) {
                if (instance == null) {         // 第二次检查：避免重复创建
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

至于那些根本不会被并发读写的域，不必硬套同步：给域加 final，或者让它只在线程内部使用，比任何同步手段都划算。

使用重入锁ReentrantLock实现线程同步

JDK 1.5 起，java.util.concurrent.locks 包下的 ReentrantLock 是可重入、互斥、实现了 Lock 接口的锁，基本行为与语义和 synchronized 修饰的方法一致，但扩展了更多能力。

ReentrantLock 类的常用方法有：

  • lock()：获得锁，获取不到就阻塞等待；unlock()：释放锁，必须放在 finally 中。
  • tryLock()：立即返回，拿到返回 true，拿不到返回 false，不会死等。
  • tryLock(long time, TimeUnit unit)：在超时时间内尝试获取锁，可以用来打破死锁。
  • lockInterruptibly()：等待锁的过程中可以响应中断。
  • newCondition()：获得 Condition 对象，用 await() / signal() 实现等待-通知，比 Object 的 wait/notify 更灵活，一把锁可以建多个条件队列。
  • 构造方法 ReentrantLock(boolean fair) 可以创建公平锁，优先运行等待时间最长的线程，不过这种机制会降低程序运行效率（吞吐下降）。

下面是一个正确用法：用锁保护共享状态，用 Condition 做等待通知。这里要特别提醒——不要用锁去保护忙等自旋。如果读线程拿着锁空转等某个变量变成目标值，写线程永远拿不到锁去修改它，结果就是死锁。

import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

public class BoundedBuffer<T> {

    private final Lock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
    private final Condition notFull = lock.newCondition();

    private final Object[] items = new Object[10];
    private int count;

    public void put(T x) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) {
                notFull.await();        // 释放锁并等待，被唤醒后重新竞争锁
            }
            items[count++] = x;
            notEmpty.signal();
        } finally {
            lock.unlock();              // 必须在 finally 中释放，否则等于永久持锁
        }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) {
                notEmpty.await();
            }
            T x = (T) items[--count];
            notFull.signal();
            return x;
        } finally {
            lock.unlock();
        }
    }
}

关于 Lock 对象和 synchronized 关键字的选择：

  1. 最好两个都不用，优先使用 java.util.concurrent 包提供的现成机制（并发容器、Atomic、Semaphore），它们能帮你处理所有与锁相关的细节。
  2. 如果 synchronized 关键字能够满足需求，就用 synchronized，它能简化代码，而且不会忘记释放锁。
  3. 如果需要使用更高级的功能（可中断、可超时、公平锁、多个 Condition），就用 ReentrantLock，此时要注意及时释放锁，否则会出现死锁，通常在 finally 中释放锁。

使用ThreadLocal管理局部变量实现线程同步

ThreadLocal 管理变量时，每一个使用该变量的线程都获得一个该变量的副本，副本之间相互独立，这样每一个线程都可以随意修改自己的副本，而不会对其他线程产生影响。

这里必须先纠正一个常见误解：ThreadLocal 不是同步手段，而是「避免共享」的手段。它既不提供互斥，也不保证可见性——两个线程各读写自己的副本，根本不会互相等待。因此「让读线程自旋等待写线程把值改成 5」这种写法是不可能成立的：写线程改的是它自己的副本，读线程的副本始终是初值，只会无限循环。

ThreadLocal 类常用的方法：

  1. get()：返回该线程局部变量当前线程副本中的值，若尚未设置则先初始化。
  2. initialValue()：返回此线程局部变量的当前线程的初始值；JDK 8 以后更推荐 ThreadLocal.withInitial(() -> 初值)。
  3. set(T value)：将此线程局部变量当前线程副本中的值设置为指定值 value。
  4. remove()：移除此线程局部变量当前线程的值。线程池场景必须调用，否则既会内存泄漏，也会把数据串给下一个复用该线程的任务。
import java.text.SimpleDateFormat;
import java.util.Date;

public class DateFormatHolder {

    // SimpleDateFormat 不是线程安全的，每个线程各持一份就无需加锁
    private static final ThreadLocal<SimpleDateFormat> FORMATTER =
            ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd HH:mm:ss"));

    public static String format(Date date) {
        return FORMATTER.get().format(date);
    }

    // 线程池场景：任务结束前清理，避免线程复用造成数据串用与内存泄漏
    public static void clear() {
        FORMATTER.remove();
    }
}

它的典型用途是上下文透传（登录用户、traceId、事务上下文）和绑定线程不安全的工具对象。使用前提有两条：线程池里用完一定要 remove()；不要用它在线程之间传递数据。

补充：Atomic 类与并发容器

前面五种手段没有专门覆盖「原子性」这一类最常见的需求，比如计数器自增、状态位切换。java.util.concurrent.atomic 提供了一组基于 CAS（Compare-And-Swap）的原子类，不加锁就能保证单个变量的读—改—写是原子的。

  • AtomicInteger / AtomicLong：incrementAndGet() 返回新值，getAndIncrement() 返回旧值（语义等同 i++），另有 compareAndSet(expect, update)。适合计数器、序列号生成。
  • AtomicReference / AtomicStampedReference：后者用版本号解决 CAS 的 ABA 问题——值被改回原样时，普通 CAS 察觉不到，带戳的版本可以。
  • LongAdder / DoubleAdder（JDK 8+）：分段累加，高并发计数时吞吐明显优于 AtomicLong，代价是取值不是精确的瞬时值。
  • 边界：CAS 只保证一个变量的原子性。多个变量之间有约束（例如同时更新余额和流水号）仍然要用锁；而且 compareAndSet 这类操作通常要写在循环里重试。

并发容器则把同步逻辑封装在集合内部，比用 Collections.synchronizedXxx() 包一层更高效：

  • ConcurrentHashMap：读操作几乎无锁；迭代器是弱一致的，遍历期间可能看不到新元素，但不会抛 ConcurrentModificationException；不允许 null 键和 null 值。
  • CopyOnWriteArrayList：写时复制，适合读多写少、数据量小的场景；每次写入都复制整个数组，写多时会非常慢。
  • BlockingQueue（ArrayBlockingQueue、LinkedBlockingQueue 等）：生产者-消费者模型的标准工具，put / take 自带阻塞语义，比手写 wait/notify 可靠得多。

如何选择：五种方式对比

把前面五种手段连同补充的原子类、并发容器放在一起看，选择依据其实是「要解决哪类问题」：

手段提供什么保证代价与边界典型场景
synchronized 方法互斥、可见性、可重入粒度大，容易长时间持锁简单的共享状态读写
synchronized 代码块同上，粒度可控锁对象选错等于没同步只保护真正的临界区
volatile可见性、禁止重排序不保证原子性，不提供互斥状态标志位、DCL 单例
ReentrantLock互斥、可重入，另可中断/超时/公平/Condition必须手动 unlock，否则死锁需要高级能力的并发控制
ThreadLocal线程间不共享（无互斥）必须 remove，否则泄漏与串数据上下文透传、绑定非线程安全对象
Atomic 类 / 并发容器单变量原子性 / 容器级并发安全多变量复合操作仍要加锁计数器、并发缓存、任务队列

最后是几条通用建议：先判断问题属于互斥、可见性、原子性还是「根本不该共享」，再挑手段，不要一律上 synchronized；临界区尽量小，不要在锁内做 IO、RPC；锁对象统一用 private final 且加锁顺序一致，必要时用 tryLock 超时打破死锁；能用 juc 现成工具（Atomic、BlockingQueue、并发容器）解决的，就不要手写锁。
