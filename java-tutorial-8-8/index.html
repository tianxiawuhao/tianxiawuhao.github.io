Elasticsearch 搜索引擎

Posted on 2026-09-19，6 min read

业务数据一旦超过百万级，「按关键字搜内容」就会成为最先崩掉的功能：MySQL 的 LIKE '%关键字%' 用不上索引，全表扫描越来越慢，而且就算扫出来了，也没法按「谁更相关」排序。Elasticsearch（下称 ES）就是为解决这类全文检索需求而生的：它在 Lucene 之上封装出分布式、REST 风格的搜索服务，把索引、分片、副本、打分这些复杂机制都藏在一个 HTTP 接口后面。本章从倒排索引讲起，依次说明索引与映射、分词器、查询 DSL、聚合，最后给出集群与调优的抓手。读者需要会写 Java、用过 MySQL，做过基本的 REST 调用；读完应当能独立建好索引、写出可用的查询语句，并知道线上出问题时先看哪里。

一、为什么需要 ES：倒排索引是根

关系数据库的索引是「文档 → 词」的正排结构：给定一行记录，能快速找到它的字段值。全文检索的需求方向恰好相反，是「词 → 文档列表」：给定一个查询词，要立刻拿到所有包含它的文档。如果只有正排索引，就只能把每篇文档读出来逐字比对，这正是 LIKE '%x%' 慢的根源。

倒排索引把方向倒过来。写入文档时先分词，把所有不重复的词组成一张词表（term dictionary），每个词后面挂着出现过它的文档编号列表（posting list），列表里通常还附带词频、位置等信息。搜索时不再扫描文档，而是先查词表定位词条，再取出对应的文档列表求交集或并集，最后按相关性打分排序返回。所以倒排索引有两个直接推论：一是「搜得准不准」取决于分词，二是「搜得快不快」取决于词表与 posting list 的组织方式。ES 用的打分模型是 BM25，一个词在文档中出现次数越多、在整个索引中越罕见，该文档的得分越高；这也解释了为什么用简单「命中词条数量」打分是不够的——稀有词应当更有分量。

第三个推论是写入与检索之间的时间差。ES 写入的文档先进入内存缓冲，默认每秒做一次 refresh 形成新的可搜索段，所以它是「近实时」（NRT）而非实时：写入后大约 1 秒内可被搜到，对账类场景要留意这一点。

二、索引、映射与分词器

ES 中的索引（index）是一个逻辑概念，相当于 MySQL 中的一张表。索引由若干分片（shard）组成，每个分片是一个完整的 Lucene 索引；副本（replica）是分片的拷贝，用于容灾和分担读请求。建索引时就要确定分片数，因为分片数创建后不能改（只能 reindex 重建，或用 shrink/split 变相调整），副本数则随时可调。

# 建索引：1 个分片、1 个副本（单机开发可把副本设为 0）
curl -X PUT "localhost:9200/course" -H 'Content-Type: application/json' -d '
{
  "settings": { "number_of_shards": 1, "number_of_replicas": 1 },
  "mappings": {
    "properties": {
      "name":       { "type": "text", "analyzer": "ik_max_word", "search_analyzer": "ik_smart" },
      "studymodel": { "type": "keyword" },
      "pic":        { "type": "text", "index": false },
      "price":      { "type": "double" },
      "created_at": { "type": "date" }
    }
  }
}'

映射（mapping）决定每个字段怎么被索引。text 类型会分词，用于全文检索；keyword 类型整体作为一个词条，用于精确匹配、过滤、排序和聚合，像订单号、手机号、状态码这类字段必须用 keyword，否则会被切成碎片而搜不到。analyzer 指定写入时的分词器，search_analyzer 指定查询时的分词器；中文场景常见做法是写入用 ik_max_word 保证召回，查询用 ik_smart 减少噪音。index: false 的字段（如图片地址）不建索引，省空间，但也意味着它不能被检索。

分词效果可以直接用 _analyze 接口验证，这是排查「明明有这条数据却搜不到」的第一步：

curl -X POST "localhost:9200/_analyze" -H 'Content-Type: application/json' -d '
{ "text": "中华人民共和国人民大会堂", "analyzer": "ik_smart" }'
# ik_smart   -> 中华人民共和国 / 人民大会堂
# ik_max_word -> 中华人民共和国 / 中华人民 / 中华 / 华人 / 人民共和国 / 人民 / 共和国 / 大会堂 / 大会 / 会堂

这里有几个源文档中过时或写错的点必须更正。第一，映射类型（type）在 ES 6.0 被弱化、在 7.0 已被彻底移除，而不是 9.0；早在 6.x 就推荐的 _doc 占位写法，在 7.x 之后连位置都不再需要。第二，_all 全字段检索字段同样在 7.0 被移除，需要用 multi_match 显式列出字段，或用 copy_to 自建汇总字段；因此老教程里 ?q=guide 这类依赖 _all 的写法在新版本上语义已变。第三，节点角色配置也换了：node.master/node.data 改为 node.roles: [master, data]。Zen1 时代的 discovery.zen.minimum_master_nodes 则被 cluster.initial_master_nodes 取代（7.0 起）。第四，只有 index 参数不存在「搜索时单独关闭索引」的说法：字段一旦不索引，任何查询（包括 term）都搜不到它；但要注意 index: false 的字段仍可用 docvalue 做聚合（需开启），这点常被误解。

三、查询 DSL：match、term 与 bool 组合

ES 的查询走 HTTP，可以是 URL 参数式的轻量查询（_search?q=name:spring），也可以是请求体里的完整 DSL。前者只适合调试，正式代码一律用 DSL：它能表达组合条件、控制返回字段、做高亮、分页和聚合。

最容易被混淆的是 term 与 match，二者的差别就是「分不分词」：match 会把查询词交给字段的分词器处理后再匹配，是全文检索的入口；term 把查询词当成一个完整的词条，直接去词表里找，因此只对 keyword 字段、数值和日期可靠。用 term 去查一个 text 字段（例如 term: name = “Spring 实战”），几乎必然查不到结果，这是新手最常见的坑。介于两者之间的是 match_phrase，它要求词条按顺序相邻出现，适合短语检索；query_string 则支持 AND/OR 与字段前缀等语法，灵活但容易因用户输入的特殊字符而报错，不建议直接暴露给终端用户。

POST /course/_search
{
  "query": {
    "bool": {
      "must":   [ { "match": { "name": "spring 实战" } } ],
      "filter": [
        { "term":  { "studymodel": "201001" } },
        { "range": { "price": { "gte": 50, "lte": 200 } } }
      ],
      "must_not": [ { "term": { "status": "deleted" } } ],
      "should": [ { "match_phrase": { "description": "分布式搜索" } } ]
    }
  },
  "_source": [ "name", "price", "studymodel" ],
  "highlight": { "fields": { "name": {} } },
  "from": 0,
  "size": 10,
  "sort": [ { "created_at": { "order": "desc" } } ]
}

关于 bool 查询有三个要点。其一是 filter 与 must 的区别：must 参与打分，filter 只判断「是/否」、不打分，因此能被缓存并跳过打分计算，能用 filter 的精确条件就不要放进 must。其二是打分与排序的关系：一旦显式指定 sort，_score 通常为 null，相关性顺序被排序字段覆盖，这一点在「按时间倒序却还指望最相关的排最前」时会造成困惑。其三是分页：from + size 的窗口不能超过 index.max_result_window（默认 10000），深分页要用 search_after + 稳定排序键；此外 7.x 起 hits.total 是形如 {"value": 42, "relation": "eq"} 的对象，而不是一个数字，解析响应时按数字取值会直接报错。要拿到「全部命中数」应显式使用 track_total_hits: true。

四、聚合与集群调优

聚合（aggregation）是 ES 的另一半价值：它能在检索结果之上做分组统计，把「先查出来再在内存里 group by」的工作交给搜索引擎。聚合只对不分词的字段有意义，对 text 字段做 terms 聚合会报 fielddata 相关错误。正确做法是给它加一个 keyword 子字段（"fields": { "keyword": { "type": "keyword" } }），或者干脆在建映射时就规划好。

POST /course/_search
{
  "size": 0,
  "query": { "range": { "created_at": { "gte": "2024-01-01" } } },
  "aggs": {
    "by_model": {
      "terms": { "field": "studymodel", "size": 10 },
      "aggs": { "price_stats": { "stats": { "field": "price" } } }
    },
    "monthly": {
      "date_histogram": { "field": "created_at", "calendar_interval": "month" }
    }
  }
}

注意 "size": 0：只取聚合结果时要显式关掉 hits，否则集群会白白搬运一万条文档。容量方面，分片不是越多越好——分片过多会放大集群状态与查询合并的开销，分片过大则恢复慢；常见经验是单个分片控制在 10–50GB 之间，并让分片数对齐数据节点数。堆内存设置 -Xms 与 -Xmx 相等以避免运行时伸缩，且不要超过物理内存的一半，同时尽量控制在 31GB 以内以保住 JVM 的压缩指针；其余内存留给文件系统缓存，Lucene 的段文件非常依赖它。文件句柄方面，Linux 下要为 ES 用户把 ulimit -n 提到 65536，并写进 /etc/security/limits.conf（形如 elasticsearch - nofile 65536），才能持久生效。源文档里的 su limit -n 是笔误，临时 ulimit 也只在当前会话有效。

写入与查询两侧都有成熟的优化手段，常用做法如下：

  • 写入侧用 _bulk 批量提交，单批几 MB 到十几 MB 为宜；
  • 写入侧在导入期把 refresh_interval 调大甚至设为 -1；
  • 写入侧把副本数先设 0，写完再恢复；
  • 查询侧优先用 filter 过滤；
  • 查询侧只取需要的 _source 字段；
  • 查询侧限制聚合的 size；
  • 查询侧避免 * 通配符开头的查询。

生产集群至少要三个专有 master 节点（node.roles: [master]）以避免脑裂，数据节点不兼 master 是更稳妥的部署方式。

五、小结

ES 的能力边界由倒排索引决定：分词决定能不能搜到，映射决定能不能过滤和聚合，DSL 决定搜得准不准，分片与堆内存决定能不能扛住量。

实践顺序建议如下：

  • 先用 _analyze 确认分词结果；
  • 再按查询方式设计映射，全文检索用 text，精确匹配与聚合用 keyword；
  • 然后用 bool 查询把打分条件放进 must、把过滤条件放进 filter；
  • 最后才是加副本、调堆内存、批量写入这些运维手段。

把这几步按顺序做对，绝大多数「搜不到、搜不准、搜得慢」的问题都能在源头定位。
