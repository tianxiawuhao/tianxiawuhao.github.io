数据采集与同步

Posted on 2026-09-19，8 min read

数据进不了数仓，后面的大数据组件再强也只是空转。业务数据留在 MySQL 里、日志散落在几十台机器上、用户行为埋点还在往本地文件写，而 Hive、HDFS、Elasticsearch、Kafka 需要的是持续、稳定、可回溯的数据流。「数据采集与同步」解决的正是这段搬运工的工作：把不同源头、不同形态的数据，按不同的时效要求，可靠地送进下游存储。本章面向已经了解 Hadoop、Hive 基础、准备接入生产数据的读者。围绕 Sqoop、DataX、Flume、Canal 四条主路线，下面讲清各自的适用边界、一份可运行的最小配置，以及最容易踩的坑。

四条路线：批量、日志、增量各解决什么问题

采集工具很多，但按「数据从哪来、要什么时效」一划分，绝大多数场景落在四条路线上。

批量关系型数据库同步：把 MySQL、Oracle、PostgreSQL 的表整表或按条件搬运到 HDFS、Hive。代表工具是 Apache Sqoop 与阿里开源的 DataX。两者都以 JDBC 读取、支持并发切分、以离线批任务方式运行，区别在于任务模型：Sqoop 把任务翻译成 MapReduce 作业，依赖 Hadoop 集群资源；DataX 是纯单机多线程框架，以 Reader/Writer 插件模型工作，不需要提交 MR。

日志文件采集：把不断追加的文本日志从应用服务器汇聚到 HDFS 或 Kafka。代表工具是 Flume。它的模型是 Agent，一个 Agent 由 Source（采集端）、Channel（缓冲）和 Sink（写出端）组成，用事务把三者串起来，保证不丢但可能重复，即至少一次（at-least-once）语义。

增量变更订阅（CDC）：不想每天全表扫一遍，而是实时捕获 MySQL 的 binlog，把 insert/update/delete 变成一条条消息送进 Kafka。代表工具是 Canal，以及更通用的 Debezium。这类方案的时效可以做到秒级甚至亚秒级。

日志／指标实时管道：Filebeat、Logstash、Fluentd 等更偏轻量采集与清洗，通常与 Kafka、Elasticsearch 搭配。它们与 Flume 定位重叠，选型时按已有技术栈决定即可，不必同时上两套工具。

这里必须纠正一处常见混淆：在 Hadoop 源码里会看到 DataXceiverServer、DataXceiver 这两个类名，它们是 HDFS DataNode 内部处理数据块读写请求的线程，负责接收客户端与其他 DataNode 的读写流，与阿里开源的离线同步工具 DataX 没有任何关系，只是名字相似。源码里出现 DataXceiver 时，不能把它当成 DataX 的资料来用。

批量同步实战：Sqoop 与 DataX

Sqoop 的用法是「一条命令一个任务」，最典型的全量导入如下。

# 全量导入 MySQL 表到 HDFS，按 id 切分 4 个并发
sqoop import \
  --connect "jdbc:mysql://mysql01:3306/shop?useSSL=false&serverTimezone=Asia/Shanghai" \
  --username reader --password-file /user/hadoop/.mysql.pwd \
  --table orders \
  --target-dir /warehouse/ods/orders/dt=2025-01-01 \
  --fields-terminated-by '\t' \
  --null-string '\\N' --null-non-string '\\N' \
  --split-by id --num-mappers 4

# 增量追加：以上次最大 id 为水位，只搬新数据
sqoop import --connect "jdbc:mysql://mysql01:3306/shop" \
  --username reader --password-file /user/hadoop/.mysql.pwd \
  --table orders --target-dir /warehouse/ods/orders_incr \
  --incremental append --check-column id --last-value 100000 \
  --fields-terminated-by '\t' --num-mappers 4

两个参数是新手最容易漏的：--null-string／--null-non-string 把数据库的 NULL 写成 Hive 可识别的 \N，否则导入后整列会变成字符串 “null”；--split-by 在表没有主键、或主键分布严重倾斜时必须显式指定，实在没有合适字段就用 --num-mappers 1 单线程跑，硬用默认切分会报找不到切分列或产生大量空切片。

DataX 的作业是一份 JSON：Reader 读 MySQL，Writer 写 HDFS，中间通过 channel 控制并发，用 speed 做限流，避免把线上库打满。

{
  "job": {
    "setting": {
      "speed": { "channel": 4, "byte": 10485760 },
      "errorLimit": { "record": 100 }
    },
    "content": [{
      "reader": {
        "name": "mysqlreader",
        "parameter": {
          "username": "reader",
          "password": "******",
          "column": ["id", "user_id", "amount", "created_at"],
          "where": "created_at >= '2025-01-01 00:00:00'",
          "connection": [{
            "table": ["orders"],
            "jdbcUrl": ["jdbc:mysql://mysql01:3306/shop?useSSL=false&serverTimezone=Asia/Shanghai"]
          }]
        }
      },
      "writer": {
        "name": "hdfswriter",
        "parameter": {
          "defaultFS": "hdfs://nn01:8020",
          "fileType": "text",
          "path": "/warehouse/ods/orders/dt=2025-01-01",
          "fileName": "orders",
          "writeMode": "append",
          "fieldDelimiter": "\t",
          "column": [
            {"name": "id", "type": "long"},
            {"name": "user_id", "type": "long"},
            {"name": "amount", "type": "double"},
            {"name": "created_at", "type": "string"}
          ]
        }
      }
    }]
  }
}

保存为 orders.json 后执行 python datax.py orders.json。注意 DataX 的 column 顺序必须与 Writer 的 column 顺序严格对应，字段名并不会做自动匹配。channel 调大能提速，但每个 channel 都会在内存中缓存一批数据，JVM 堆要相应调整，盲目调到几十反而会 OOM。DataX 不依赖 Hadoop 计算资源，JSON 化配置也容易做调度集成，因此新项目通常优先于 Sqoop。Apache Sqoop 已于 2021 年进入 Apache Attic 停止维护，老集群仍在使用，新项目建议直接选 DataX 或 Flink CDC。若必须在 Hadoop 3 与高版本 JDK 上运行 Sqoop 1.4.7（最后一个发布版），需要自行打补丁或降级 JDK，这也是它被替代的直接原因。

日志采集与增量订阅：Flume 与 Canal

Flume 的经典配置是 Taildir Source 断点续传地盯住日志目录，Memory Channel 做缓冲，Sink 写到 HDFS 或 Kafka。

a1.sources = r1
a1.channels = c1
a1.sinks = k1

a1.sources.r1.type = TAILDIR
a1.sources.r1.filegroups = f1
a1.sources.r1.filegroups.f1 = /var/log/app/.*\.log
a1.sources.r1.positionFile = /opt/flume/taildir_position.json

a1.channels.c1.type = memory
a1.channels.c1.capacity = 100000
a1.channels.c1.transactionCapacity = 1000

a1.sinks.k1.type = org.apache.flume.sink.kafka.KafkaSink
a1.sinks.k1.kafka.bootstrap.servers = kafka01:9092
a1.sinks.k1.kafka.topic = app-log

a1.sources.r1.channels = c1
a1.sinks.k1.channel = c1

三个容易出问题的地方：positionFile 记录消费位点，攒够了要保证 Flume 重启后不重跑或漏读，删掉它就等于从头再来；Memory Channel 在进程崩溃时缓冲数据全丢，要求不丢必须换 File Channel，代价是吞吐明显下降；HDFS Sink 按时间滚动文件，rollInterval 与 batchSize 配得不好会产出大量小文件，给 NameNode 添麻烦。

Canal 走的是另一条路：它伪装成 MySQL 的从库，向主库发送 dump 协议请求，解析 binlog 后把变更事件投递出去。使用前必须在 MySQL 侧开启 binlog_format=ROW，并给 Canal 账号授予 REPLICATION SLAVE、REPLICATION CLIENT 权限。

CanalConnector connector = CanalConnectors.newSingleConnector(
        new InetSocketAddress("canal01", 11111), "example", "", "");
connector.connect();
connector.subscribe("shop\\..*");   // 只订阅 shop 库
connector.rollback();               // 回到上次未确认的位点

while (running) {
    Message message = connector.getWithoutAck(1000); // 最多 1000 条
    long batchId = message.getId();
    if (batchId == -1 || message.getEntries().isEmpty()) {
        Thread.sleep(1000);
        continue;
    }
    for (CanalEntry.Entry entry : message.getEntries()) {
        if (entry.getEntryType() != CanalEntry.EntryType.ROWDATA) {
            continue;   // 事务开始/结束、心跳等元数据跳过
        }
        RowChange rowChange = RowChange.parseFrom(entry.getStoreValue());
        for (CanalEntry.RowData row : rowChange.getRowDatasList()) {
            // 按 row.getEventType() 区分 INSERT / UPDATE / DELETE，再写入下游
        }
    }
    connector.ack(batchId);   // 处理成功才确认；失败走 rollback 重放
}

这段代码里最值得记住的是 ack 与 rollback 的配合：只有真正写下游成功再 ack，异常时 rollback 让这批数据重放，才能做到不丢；代价是重复，所以下游必须按主键做幂等（例如 upsert 或按 binlog 位点去重）。另外，Canal 解析的是行数据，DDL 语句本身不会变成 ROWDATA 事件，加字段后需要同步调整下游表结构；binlog_format 必须是 ROW，STATEMENT 模式下拿不到行级变更。

选型对比与常见坑

把四条路线放到一张表里看会更清楚：

  • 离线批量、源是关系库：优先 DataX（JSON 配置、不占 Hadoop 资源），存量老任务用 Sqoop 维持即可；需要断点续传与增量水位时用 --incremental append 或 DataX 的 where 条件自行记录水位。
  • 文件日志汇聚：Flume 与 Filebeat／Logstash 二选一，已有 Hadoop 生态就用 Flume，云原生栈用 Filebeat。下游客流大时中间加 Kafka 削峰，而不是把 Flume Agent 堆到几十个 Source。
  • 秒级增量、要保留删除动作：Canal 或 Debezium，配合 Kafka 与 Flink 做下游计算；纯增量同步用 DataX 的定时全量比对是下策，删掉的行你永远发现不了。
  • 全量 + 增量并存：通常先做一次全量快照，再从快照位点接增量；Canal 需要人工确认全量完成时的 binlog 位点，否则会漏掉切换期间的变更。

还有几个跨工具的共性问题：一是编码，MySQL 侧连接串加上 characterEncoding=utf8；DataX 的 encoding、Sqoop 的 --fields-terminated-by 与建表分隔符必须一致，否则中文乱码；二是时间与时区，连接串里的 serverTimezone 写错会导致 created_at 整体偏移几小时；三是并发不是越大越好，源库的连接数与 IO 是硬上限，白天同步线上库务必限流；四是每个任务都要有可观测指标——行数、位点、延迟、失败重试次数，只靠「任务没报错」判断同步正常，是数据事故最常见的起点。

小结

数据采集与同步的核心是「按源头和时效选路线」：批量关系库选 DataX（老任务 Sqoop 过渡），文件日志选 Flume 或 Filebeat，实时增量选 Canal／Debezium，谁也不该越界去干对方的活。动手时记住三件事：Sqoop 要显式处理 NULL 与切分字段，DataX 要对齐字段顺序并限制 channel，Flume 的 Channel 类型与 positionFile 决定丢不丢、重不重，Canal 的 ack/rollback 决定下游是否需要幂等。把这四类任务的边界、配置项和坑摸清，后面无论是接数仓、做实时大屏还是搭搜索索引，数据这一层的可靠性就都有底了。
