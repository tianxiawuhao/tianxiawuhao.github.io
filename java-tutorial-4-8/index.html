MyBatis 进阶与 SSM 整合

Posted on 2026-09-19，8 min read

学完 MyBatis 的增删改查与结果映射，你已经能让程序跑起来，但一进真实项目就会撞上三堵墙：同一条 SQL 在一个事务里被反复执行，白白压数据库；列表页一次性查出十万行，内存和网络都吃不消；SqlSessionFactory 到处 new，事务边界散落在 Service 里没法统一管理。本章就解决这三件事——一级/二级缓存、分页插件 PageHelper，以及用 Spring 把 MyBatis 收编成 SSM 骨架。适合已经能独立手写 Mapper 接口与 XML 映射的读者。

一、先看清结构：两级缓存与装饰器

缓存几乎是所有 ORM 框架的标配，目的是提高查询效率、降低数据库压力。MyBatis 中和缓存相关的类都放在 org.apache.ibatis.cache 包里，核心是一个 Cache 接口，默认实现只有 PerpetualCache，它的内部就是一个 HashMap。围绕这个基本实现，MyBatis 又提供了一批装饰器，用来叠加回收策略、日志记录、定时刷新等能力；无论包装多少层，最里面装的仍是 PerpetualCache。

缓存按作用范围分两级。一级缓存也叫本地缓存，挂在 SqlSession 层面，同一个会话内共享，会话一关就没了；二级缓存挂在 namespace 层面，被同一个 Mapper 的多个 SqlSession 共享，生命周期与应用同步。因此一次查询的取数顺序是：二级缓存 → 一级缓存 → 数据库。搞清这个顺序，后面所有配置和坑都能自己推出来。

二、一级缓存：SqlSession 内的本地缓存

一级缓存默认开启，不需要任何配置。它并不放在 SqlSession 对象本身——DefaultSqlSession 只持有全局的 Configuration 和一个 Executor——而是由 BaseExecutor（SimpleExecutor、ReuseExecutor、BatchExecutor 的父类）在构造时持有一个 PerpetualCache。

是否命中由 CacheKey 决定：statementId、SQL 文本、参数值、RowBounds 分页信息、环境 id 等共同参与计算，任何一项不同都不算同一次查询。命中就直接返回内存里的结果，不再发 SQL。

它的生命周期有三条规则必须记住：会话 openSession() 时创建，close() 时随对象一起释放，缓存不可再用；clearCache() 只清空数据，对象仍可继续使用；只要执行了 insert、update、delete，BaseExecutor.update() 就会无条件调用 clearLocalCache() 清空缓存。下面这段代码可以亲手验证这三条规则：

SqlSession session1 = sqlSessionFactory.openSession();
BlogMapper mapper1 = session1.getMapper(BlogMapper.class);

// 1. 同一会话内重复查询：控制台只会打印一条 SQL，第二次直接命中缓存
System.out.println(mapper1.selectBlogById(1002));
System.out.println(mapper1.selectBlogById(1002));

// 2. 执行 update 后一级缓存被无条件清空，即使还没提交
Blog blog = new Blog();
blog.setBid(1002);
blog.setName("mybatis 缓存机制");
mapper1.updateBlog(blog);
System.out.println(mapper1.selectBlogById(1002)); // 重新访问数据库

// 3. 换一个会话：拿不到 session1 的缓存，只能再查一次数据库
SqlSession session2 = sqlSessionFactory.openSession();
BlogMapper mapper2 = session2.getMapper(BlogMapper.class);
System.out.println(mapper2.selectBlogById(1002));

session1.close();
session2.close();

想看到 SQL 输出，需要在 MyBatis 配置里打开日志，例如把 logImpl 设为 org.apache.ibatis.logging.stdout.StdOutImpl。这里要纠正一个常见说法：清空一级缓存发生在增删改执行的那一刻，而不是提交的那一刻，所以不要指望「不提交就不清缓存」。提交真正影响的是二级缓存的写入时机。

一级缓存最大的短板是不能跨会话共享：多个会话对同一份数据可能各持一份旧值，在并发或分布式环境下就会读到脏数据。规避办法是把 localCacheScope 设为 STATEMENT，这样每次查询结束就清掉本地缓存；而在 Spring 环境中还有一点很关键——如果方法上没有事务，每次 Mapper 调用都会新建 SqlSession，一级缓存几乎永远命中不了，只有包在同一个事务里才真正生效。

三、二级缓存：namespace 级的跨会话缓存

要让缓存跨会话共享，它就必须待在 SqlSession 之外。MyBatis 的做法是用 CachingExecutor 装饰真正的执行器：查询先问二级缓存，命中直接返回，没命中才委派给 SimpleExecutor 之类走一级缓存和数据库，最后把结果写回二级缓存。

开启分两步。第一步是全局开关 cacheEnabled，它默认就是 true，只有显式设成 false 才会关闭，所以正常情况下这一步不用写，源文档里「必须先配置 cacheEnabled=true」的说法是不准确的。第二步是在 Mapper.xml 里加 <cache/> 标签——只有加了它，这个 namespace 才会真正拥有一个缓存对象。

二级缓存是事务性的：它由 TransactionalCacheManager 管理，查询结果在 putObject 时只是暂存在待提交集合里，必须等 SqlSession 提交或回滚时才真正写入，因此「事务不提交，二级缓存不生效」。

<!-- BlogMapper.xml：为本 namespace 开启二级缓存 -->
<mapper namespace="com.example.dao.BlogMapper">

    <!-- eviction 默认 LRU；size 默认 1024；flushInterval 不写表示不定时刷新；
         readOnly 默认 false，通过序列化返回副本，要求实体类可序列化 -->
    <cache eviction="LRU" size="1024" flushInterval="120000" readOnly="false"/>

    <!-- 对实时性要求高的语句，单条关闭缓存 -->
    <select id="selectBlogById" resultMap="BaseResultMap" useCache="false">
        select * from blog where bid = #{bid}
    </select>

    <!-- 让多个 namespace 共用同一份缓存 -->
    <cache-ref namespace="com.example.dao.DepartmentMapper"/>
</mapper>

每条语句也能单独控制缓存行为，默认约定是：<select> 的 useCache="true"、flushCache="false"，而 <insert>、<update>、<delete> 的 flushCache="true"，所以增删改天然会刷新缓存。自定义缓存类必须实现 org.apache.ibatis.cache.Cache 接口，并提供接收 String id 的构造器。

这里要特别纠正源文档的一处硬错误：不要写成 <cache type="org.apache.ibatis.cache.impl.PerpetualCache" size="1024" .../>。一旦指定 type，MyBatis 就完全改用你给的实现、不再叠加默认装饰器，而 PerpetualCache 根本没有 size、eviction、flushInterval、readOnly 这些 setter，启动时会直接抛异常。要配置这些属性，就用不带 type 的默认 <cache/>。

什么时候才值得开二级缓存？查询为主、按单表划分 namespace 的业务比较合适，比如历史订单查询。如果多个 namespace 操作同一张表，一个刷新了缓存另一个没刷新，照样会脏读；用 cache-ref 共享虽能缓解，但任何一方的增删改都会刷新整块缓存，收益有限。对一致性要求高的系统，更稳妥的做法是接 Redis 这类独立缓存服务。

四、分页插件 PageHelper

手写分页有三件麻烦事：不同数据库的 limit 语法不一样，还得额外写一条 count 语句，而且分页参数会渗透进 Service 代码。PageHelper 以 MyBatis 插件（Interceptor）的形式拦截 Executor.query，自动改写 SQL、自动生成 count 查询，业务代码只需要声明「第几页、每页几条」。

配置时最容易踩版本坑。PageHelper 4.x 的拦截器类是 com.github.pagehelper.PageHelper，还要配 dialect 属性指定数据库类型；5.x 起改为 com.github.pagehelper.PageInterceptor，方言自动识别，dialect 属性已废弃。源文档给出的是 4.x 的旧写法，新项目应写成：

<plugin interceptor="com.github.pagehelper.PageInterceptor"/>，放在 mybatis-config.xml 的 <plugins> 节点内。顺带说一句，这个配置文件的 DTD 地址正确写法是 http://mybatis.org/dtd/mybatis-3-config.dtd，源文档里的 mybatis3 config.dtd 少了一个连字符，会让解析失败。

使用上只有三条纪律：PageHelper.startPage(pageNum, pageSize) 必须紧挨着目标查询，它只对之后的第一条查询生效；结果用 PageInfo 包装，才能拿到总记录数、总页数等信息；两者之间不要再插入别的查询，否则分页参数会被那条查询悄悄吃掉。另外，PageHelper 默认会先执行 count 再执行分页查询，遇到复杂关联 SQL 时可以用 PageHelper.startPage(pageNum, pageSize, false) 跳过 count。

五、与 Spring 整合：SSM 骨架

SSM 就是 Spring + SpringMVC + MyBatis 的组合：SpringMVC 负责 web 层，Spring 负责 Service 与事务，MyBatis 只管 SQL 映射，中间由 mybatis-spring 桥接。工程上通常按用途拆成 applicationContext-dao.xml、applicationContext-service.xml 和 springmvc.xml，其中 SpringMVC 必须扫描独立的子容器，否则很容易把 Service 重复扫进 web 容器导致事务失效。

dao 层的配置是标准三件套：数据源、SqlSessionFactoryBean、MapperScannerConfigurer。后者会扫描指定包下的 Mapper 接口，自动生成代理实现并注册成 bean，从此 Service 里只需 @Autowired 一个接口，不必再手工 getMapper()。

<!-- applicationContext-dao.xml（节选） -->
<context:property-placeholder location="classpath:jdbc.properties"/>

<bean id="dataSource" class="com.alibaba.druid.pool.DruidDataSource" destroy-method="close">
    <property name="driverClassName" value="${jdbc.driver}"/>
    <property name="url" value="${jdbc.url}"/>
    <property name="username" value="${jdbc.username}"/>
    <property name="password" value="${jdbc.password}"/>
</bean>

<!-- 让 Spring 管理 SqlSessionFactory，并加载 MyBatis 全局配置（分页插件写在这里） -->
<bean id="sqlSessionFactory" class="org.mybatis.spring.SqlSessionFactoryBean">
    <property name="dataSource" ref="dataSource"/>
    <property name="configLocation" value="classpath:mybatis/SqlMapConfig.xml"/>
    <property name="typeAliasesPackage" value="com.example.pojo"/>
</bean>

<!-- 扫描 Mapper 接口，批量生成代理对象 -->
<bean class="org.mybatis.spring.mapper.MapperScannerConfigurer">
    <property name="basePackage" value="com.example.dao"/>
    <property name="sqlSessionFactoryBeanName" value="sqlSessionFactory"/>
</bean>

Service 层拿到 Mapper 后，分页写法就非常干净：

@Service
public class BlogServiceImpl implements BlogService {

    @Autowired
    private BlogMapper blogMapper;

    @Override
    public PageInfo<Blog> page(int pageNum, int pageSize) {
        PageHelper.startPage(pageNum, pageSize); // 只作用于紧随其后的第一条查询
        List<Blog> list = blogMapper.selectAll();
        return new PageInfo<>(list);
    }
}

事务由 Spring 的 DataSourceTransactionManager 配合 @Transactional 统一管理，通常配在 Service 方法上。这里有个连锁效果值得注意：只有在一个事务内，多次 Mapper 调用才共用同一个 SqlSession，前面讲的一级缓存才真正发挥作用；脱离事务时每次调用都是新会话，缓存形同虚设。

小结：一级缓存默认开启、随 SqlSession 生灭，命中由 CacheKey 决定，增删改执行即清空，且不能跨会话共享；二级缓存要显式加 <cache/> 才生效，由 CachingExecutor 管理、提交后才写入，适合查询为主且按单表划分 namespace 的场景。分页交给 PageHelper，注意 5.x 用 PageInterceptor 且 startPage 必须紧邻查询。最后用 Spring 把数据源、SqlSessionFactoryBean、Mapper 扫描和事务串起来，一个可用的 SSM 骨架就搭好了。
