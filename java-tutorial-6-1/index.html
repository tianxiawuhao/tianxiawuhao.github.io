JVM 内存结构与对象

Posted on 2026-09-19，5 min read

很多人第一次接触 JVM，都是从"堆、栈、方法区"这三个词开始的：面试能背出这一串名词，可真遇到 OutOfMemoryError 时，却说不清到底是谁满了。这一章把运行时数据区、对象创建与内存布局串成一条线，讲清"内存在哪、对象怎么来、引用怎么找对象"。适合能写 Java 代码、想补虚拟机基础，或总分不清 JVM 内存结构与 Java 内存模型（JMM）的读者。

一、运行时数据区：五块内存，两种归属

《Java 虚拟机规范》把虚拟机管理的内存划分为若干区域，合称运行时数据区。划分它们的依据有两条：生命周期是否与线程一致，以及是否被所有线程共享。

线程私有的三块：

  • 程序计数器（Program Counter Register）：一块很小的内存，存放当前线程正在执行的字节码行号。处理器一个时刻只执行一条线程的指令，线程切换后要靠它回到正确的位置，所以每个线程都必须有独立的一份。它是唯一一个规范没有规定任何 OutOfMemoryError 的区域。
  • 虚拟机栈：描述 Java 方法执行的内存模型。每次方法调用就压入一个栈帧，栈帧里放着局部变量表、操作数栈、动态链接和方法返回地址；方法返回则出栈。规范为它规定了两种异常：线程请求的栈深度超过允许值，抛 StackOverflowError；栈可以动态扩展却申请不到内存，抛 OutOfMemoryError。
  • 本地方法栈：作用和虚拟机栈类似，区别是它为 native 方法服务。HotSpot 直接把两者合并实现，所以单独讨论它的场景不多。

线程共享的两块：

  • 堆：虚拟机管理的最大的内存区域，启动时创建，用来存放对象实例和数组，也是垃圾收集器的主战场，按分代划分为新生代与老年代。堆里没有内存完成实例分配、且堆无法再扩展时，抛 OutOfMemoryError。
  • 方法区：存放已被加载的类信息、运行时常量池等。JDK 7 及以前它由永久代实现（受 -XX:MaxPermSize 约束）；JDK 8 起改为元空间（Metaspace），改用本地内存，由 -XX:MaxMetaspaceSize 约束。另外，字符串常量池在 JDK 7 就已经挪进了堆，所以涉及 intern() 的题目要按版本分开回答。

还有直接内存：它不属于运行时数据区，NIO 的 DirectByteBuffer 会大量使用，受本机总内存限制——这也是"堆没满却 OOM"的常见来源。

二、一个对象从 new 到可用

写下 Person p = new Person(); 这一行，虚拟机在背后做了六件事。

  1. 类加载检查：先看 new 指令的参数能否在常量池中定位到该类的符号引用，并确认这个类已被加载、解析和初始化；没有的话，先触发类加载。
  2. 分配内存：对象需要多大，在类加载完成后就已完全确定。若堆内存规整，用指针碰撞，把分界指针向空闲一侧挪动对象大小的距离；若内存碎片化，就用空闲列表，从列表里挑一块足够大的划出去。用哪种，取决于垃圾收集器是否带压缩整理能力。
  3. 处理并发：并发分配会出现"指针还没改完，另一个线程已经用旧指针分配"的情况。两种解法：对分配动作用 CAS 加失败重试保证原子性；或者给每个线程预先划一块 TLAB（本地线程分配缓冲），在 TLAB 内分配不需要同步，只有 TLAB 用完、申请新的时才加锁。
  4. 内存清零：把分配到的空间初始化为零值。这正是成员变量不赋初值也能直接使用的原因。
  5. 设置对象头：写入哈希码（多数实现延迟到调用 hashCode 时才计算）、GC 分代年龄、锁状态标志、类型指针等。到这一步，对象在虚拟机眼里已经存在了。
  6. 执行构造器：调用 <init>，按顺序执行成员变量赋值、普通代码块和构造方法。这时对象才真正可用。

顺便把两个容易混的名字分开：<clinit> 是类构造器，由静态变量赋值语句和 static 代码块合并生成，在类初始化阶段执行，虚拟机会保证它被正确加锁同步，多个线程同时初始化一个类时只有一个线程执行；<init> 是实例构造器，每 new 一次执行一次。下面的例子把两者的执行时机摊开：

public class InitOrder {
    static int staticField = init("静态变量赋值");
    static { System.out.println("静态代码块"); }

    int instanceField = init("实例变量赋值");
    { System.out.println("普通代码块"); }

    InitOrder() { System.out.println("构造方法"); }

    static int init(String tag) { System.out.println(tag); return 1; }

    public static void main(String[] args) {
        System.out.println("--- 第一次 new ---");
        new InitOrder();
        System.out.println("--- 第二次 new ---");
        new InitOrder();
    }
}

三、对象的内存布局与访问定位

对象在堆里长什么样？以 HotSpot 为例，可分为三个区域。

  • 对象头：包含 Mark Word 和类型指针。Mark Word 存对象自身的运行时数据，如哈希码、GC 分代年龄、锁状态标志、偏向线程 ID 等；类型指针指向方法区中该类的元数据，虚拟机靠它确定"这个对象是哪个类的实例"。如果对象是数组，对象头里还要多存一个数组长度。
  • 实例数据：真正存放字段内容的部分。父类定义的字段在前，子类定义的在后；HotSpot 默认会做字段重排，让相同宽度的字段尽量排在一起，以减少填充浪费。
  • 对齐填充：不是必然存在，也没有业务含义，只起占位作用。HotSpot 要求对象起始地址按 8 字节对齐，实例数据没凑够 8 字节整数倍时补几个字节，所以对象大小总是 8 的倍数。

引用怎么定位到对象，主流有两条路：句柄方式会在堆里划出一块句柄池，引用存句柄地址，句柄再分别指向对象实例和类型数据，好处是对象被移动时只需改句柄；直接指针方式让引用直接存对象地址，省掉一次间接寻址。HotSpot 采用直接指针，因为对象访问极其频繁，积少成多的定位开销很可观。

栈和堆的配合，用一段递归就能直观感受到栈帧的消耗：

public class StackDepth {
    private int depth = 0;

    public void recurse() {
        depth++;
        recurse();
    }

    public static void main(String[] args) {
        StackDepth demo = new StackDepth();
        try {
            demo.recurse();
        } catch (StackOverflowError e) {
            System.out.println("stack depth = " + demo.depth);
        }
    }
}

单线程下无论栈帧太大还是栈容量太小，抛出的都是 StackOverflowError；只有栈扩展时申请不到内存才是 OutOfMemoryError。StackOverflowError 属于 Error，但可以被捕获，示例就靠它打印深度。栈容量用 -Xss 调整，调大能撑更深，但每个线程都占内存，线程多时反而更容易 OOM。

四、三个容易答错的坑

坑一：Java 里只有值传递

实参传给形参的永远是一份副本。基本类型复制的是值本身；引用类型复制的也是值，只不过这个值恰好是一个地址。于是两种现象同时成立：在方法里修改对象的字段，外部能看到，因为形参和实参指向同一个对象；在方法里执行 person = new Person() 让形参改指向，外部看不到，因为改的只是副本里的地址。

public class PassByValue {
    static class Person {
        String name;
        Person(String name) { this.name = name; }
    }

    static void changeField(Person p) { p.name = "改字段"; }

    static void reassign(Person p) { p = new Person("方法内的新对象"); }

    public static void main(String[] args) {
        Person p = new Person("原对象");
        changeField(p);
        System.out.println(p.name);   // 改字段
        reassign(p);
        System.out.println(p.name);   // 仍然是 改字段
    }
}

顺便纠正一个流传很广的说法：局部变量重新赋值并不是"去栈里找有没有相同字面量，找到就指过去"。int age = 50; age = 40; 只是同一个局部变量槽里的值被改写；字面量复用只发生在字符串常量池这类场景，与 int 局部变量无关。

坑二：JVM 内存结构不等于 Java 内存模型

JVM 内存结构是运行时数据区的物理划分，即本章前几节讲的堆、栈、方法区。Java 内存模型（JMM，见 JSR-133）则并不真实存在，它是一套抽象规范，用来屏蔽硬件与操作系统的访问差异，解决多线程共享内存通信时的原子性、可见性和有序性问题，落地为 volatile、synchronized、final 与 java.util.concurrent 包。被问"内存模型"时，先确认对方问的是哪一个。

坑三：静态变量并不在方法区（JDK 8 起）

JDK 8 用元空间取代永久代之后，类的元数据放在元空间（本地内存），而静态变量是随 Class 对象一起存放的，Class 对象在堆里。所以"静态变量存在方法区/永久代"这句话只在 JDK 7 及以前成立。

五、小结

把本章压成一条线：线程私有程序计数器、虚拟机栈、本地方法栈；线程共享堆与方法区（JDK 8 起方法区以元空间实现元数据，静态变量随 Class 对象在堆里）；直接内存在运行时数据区之外。对象创建流程是"类加载检查 → 分配内存（指针碰撞或空闲列表，并发靠 CAS 或 TLAB）→ 清零 → 写对象头 → 执行 <init>"，布局是"对象头 + 实例数据 + 对齐填充"，访问走直接指针。参数传递只有值传递，引用传的是地址值的副本。
