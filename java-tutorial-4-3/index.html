Hibernate 映射与查询

Posted on 2026-09-19，7 min read

上一章我们把 Hibernate 跑了起来：能拿到 Session，能存能取。但真正决定一个 ORM 项目好不好维护的，只有两件事——实体类怎么和表对上号，以及查询怎么写。本章就解决这两件事：先用 JPA 注解把表、主键、外键关系映射清楚，再掌握 HQL 这门面向对象的查询语言，最后弄清一级缓存为什么能让两次 get() 只发一条 SQL、以及它什么时候根本不救你。适合已经会建 Session、跑通第一个增删改查的读者。

映射注解与主键策略

先守住持久化类的几条基本规范：必须有无参构造方法（Hibernate 底层靠反射实例化）；属性私有、提供公有 getter/setter；能不用基本类型就不用，工资这种字段用 Double 而不是 double，才能把「忘记录入」的 null 和「被扣完了」的 0 区分开；必须有一个与主键对应的 OID；尽量不要用 final 修饰类，否则延迟加载产生不了代理子类；习惯上实现 Serializable。

@Entity
@Table(name = "cst_customer")
public class Customer implements Serializable {

    private static final long serialVersionUID = 1L;

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "cust_id")
    private Long custId;

    @Column(name = "cust_name", length = 32, nullable = false)
    private String custName;

    @Column(name = "cust_level")
    private String custLevel;

    // 无参构造 + getter/setter 省略
}

@Entity 声明这是实体类，类名与表名一致时 @Table 可以省略；@Column 用于属性名和列名对不上的情况。要注意命名策略：Spring Boot 默认会把 custId 隐式转成 cust_id，但纯 Hibernate 下这个转换依赖 physical naming strategy，不确定时就显式写 @Column，别靠猜。

主键分两类：把有业务含义的字段当主键叫自然主键（如用客户姓名），一旦业务允许重名就得改表结构；不具业务含义的叫代理主键，通常是一个整数 id，这是推荐做法。@GeneratedValue 的 strategy 有四种取值：IDENTITY 依赖数据库自增列，简单但 Hibernate 无法批量插入；SEQUENCE 用序列，Oracle、PostgreSQL 上首选，可配 @SequenceGenerator，默认 allocationSize=50，想让主键连续不跳号就设成 1；TABLE 用一张序列表模拟，跨数据库但性能最差；AUTO 交给方言决定——在 Hibernate 5.x 上连 MySQL 时它往往走 hibernate_sequence 表而不是自增，所以明确要自增就写 IDENTITY。如果项目还在用 hbm.xml，对应写法是 <generator class="native"/>，可选值有 identity、sequence、native、uuid、assigned、increment，其中 native 表示由方言自动在 identity 和 sequence 之间选。

一对多与多对多关联映射

做关联映射按四步走：先确定两张表是一对多还是一对多、多对多，再在数据库里建好外键或中间表，然后在实体类里用集合或引用描述关系，最后写映射注解。以客户和联系人为例，一个客户有多个联系人，所以在「一」的一方放集合，在「多」的一方放引用：

@Entity
@Table(name = "cst_customer")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long custId;

    @OneToMany(mappedBy = "customer",
            cascade = CascadeType.PERSIST,
            fetch = FetchType.LAZY)
    private Set<LinkMan> linkMans = new HashSet<>();
}

@Entity
@Table(name = "cst_linkman")
public class LinkMan {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long lkmId;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "lkm_customer_id")
    private Customer customer;
}

关键点是谁维护外键。多方（LinkMan）持有外键列，所以由它维护；一方用 mappedBy = "customer" 表示「这个集合只是映射，不负责写外键」，等价于 XML 时代的 inverse="true"。很多笔记里保存一对多会多发一条 UPDATE（先插联系人、再把外键补上），原因正是漏了这一步；把维护权交给多方后，只按 LinkMan 的外键插入即可。另外 @ManyToOne 默认是 EAGER，务必显式改成 LAZY，否则查一批联系人会连带把每个客户都查出来。

多对多用中间表实现，两个实体各持一个集合，被动的一方同样用 mappedBy：

@Entity
@Table(name = "sys_user")
public class SysUser {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long userId;

    @ManyToMany
    @JoinTable(name = "user_role",
            joinColumns = @JoinColumn(name = "user_id"),
            inverseJoinColumns = @JoinColumn(name = "role_id"))
    private Set<SysRole> roles = new HashSet<>();
}

@Entity
@Table(name = "sys_role")
public class SysRole {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long roleId;

    @ManyToMany(mappedBy = "roles")
    private Set<SysUser> users = new HashSet<>();
}

保存时遵循「先主表、后从表」：没有级联就手动先 save 客户再 save 联系人；配了 cascade = CascadeType.PERSIST 就只保存一方。但级联不等于自动维护双向内存关联，两端都要 set，否则 flush 后从集合里取不到对象。删除同理：删除「一」的一方，Hibernate 默认先把从表外键置为 null 再删主表（多发一条 UPDATE）；要连子记录一起删就配 CascadeType.REMOVE 或 orphanRemoval = true。多对多的 REMOVE 会一路删掉关联对象本身，生产上慎用。

HQL 与 QBC 查询

HQL 是面向对象的查询语言：写类名和属性名，不写表名和列名，因此 from Customer 里的 Customer 是实体类名，条件里的 custName 是属性名。它不支持 select *，写 from Customer 就等价于查全部。参数一律用命名占位符加 setParameter，旧笔记里的 setString(0, "%李%") 这种按位置设值在 Hibernate 5.2 已标记过时，到 Hibernate 6 已被移除，不要再用。

// 条件查询 + 排序 + 分页
String hql = "from Customer where custName like :name and custLevel = :level order by custId desc";
List<Customer> list = session.createQuery(hql, Customer.class)
        .setParameter("name", "%李%")
        .setParameter("level", "普通客户")
        .setFirstResult(0)      // 起始索引，从 0 开始
        .setMaxResults(10)      // 每页条数
        .list();

// 聚合：确定只有一行一列时才能用 uniqueResult()
Long total = session.createQuery("select count(c) from Customer c", Long.class)
        .uniqueResult();

// 投影：只取部分字段，实体类要有对应参数的构造方法
List<Customer> part = session.createQuery(
        "select new com.example.domain.Customer(c.custId, c.custName) from Customer c",
        Customer.class).list();

list() 返回集合，uniqueResult() 返回唯一结果，setFirstResult() 与 setMaxResults() 配合实现分页。至于 QBC（session.createCriteria() + Restrictions + Projections）：源笔记把它称作「Hibernate 的核心查询对象」，这在今天已经过时了——Criteria 自 Hibernate 5.2 起被标注为 @Deprecated，Hibernate 6 中已删除。新项目请改用 HQL、JPA 标准的 CriteriaBuilder（session.getCriteriaBuilder()）或 QueryDSL，只有维护老代码时才需要认识 DetachedCriteria 这类离线查询对象。

一级缓存、快照与二级缓存

Hibernate 的一级缓存就是 Session 缓存：只要 Session 没关闭，同一 OID 只会有一个持久化对象实例。所以在同一个 Session 里连续两次 session.get(Customer.class, 2L)，第二次不会再发 SQL，而且两次拿到的是同一个对象引用，这是判断命中缓存最直接的证据。它同时也是脏检查的基础：查询时 Hibernate 会复制一份数据放进快照，事务提交（flush）时按 OID 比对缓存对象与快照，属性变了就自动发 UPDATE——所以持久态对象改完属性不需要手动调 update()。

这里必须纠正源笔记的一个说法：笔记称调用 Query 的 list()、iterator() 也会先查一级缓存。实际上 list() 每次都会执行 SQL，只是返回的实体实例会复用 Session 中同 OID 的对象；真正能靠缓存省掉查询的是按 OID 加载实体的路径（get()、load()，以及 iterate() 在拿到 ID 之后逐条装载实体的那一步）。iterate() 先发一条查 ID 的 SQL，再逐个按 OID 命中缓存，缓存没预热时就是典型的 N+1，别为了「用缓存」而改用它。一级缓存随 Session 的关闭而释放，clear() 只清数据不销毁对象。

二级缓存则是 SessionFactory 级别、可跨 Session 共享，因此必须显式开启：配置 hibernate.cache.use_second_level_cache=true、指定缓存提供者（Ehcache、JCache、Redis 等），再在实体上用 @Cache(usage = CacheConcurrencyStrategy.READ_WRITE) 声明。它只缓存按 ID 装载的实体和集合，且要到事务提交时才真正写入，回滚不会留下脏缓存。查询缓存（hibernate.cache.use_query_cache=true 加 setCacheable(true)）的失效条件很苛刻，默认不要开。

常见坑与小结

最后把最容易踩的几点收在一起：实体类的集合字段要用 HashSet 或 List 初始化，别留 null；双向关联只 set 一端会导致外键为空或出现多余的 UPDATE，两端都要维护；集合端写了 mappedBy 就不要再加 @JoinColumn；重写 equals()/hashCode() 时不要拿自增主键算哈希值，因为瞬时对象的主键还是 null、保存后又会变，集合里放这种对象会「丢元素」；配了 hibernate.current_session_context_class=thread 后，getCurrentSession() 拿到的 Session 在事务提交后由 Hibernate 自动关闭，不要再手动 close()；排查性能时先看有没有 N+1，@ManyToOne 该 LAZY 就 LAZY，需要一次性取回就用 join fetch。

小结：映射决定持久层的地基——实体与表的对应、代理主键的选择、外键由谁维护，写错了后面全是补丁；查询决定效率——HQL 用类名属性名思考问题，参数化设置，分页靠 setFirstResult 与 setMaxResults；缓存是双刃剑——一级缓存白送但只在 Session 内有效，二级缓存要显式开启并接受它的失效规则。下一章我们继续看事务、锁与延迟加载的配合。
