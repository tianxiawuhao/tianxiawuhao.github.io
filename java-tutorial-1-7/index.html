接口、内部类与枚举

Posted on 2026-09-19，8 min read

上一章把类、对象、封装和继承串了起来。Java 的类型系统还有三块拼图没有讲到。接口把“能做什么”从“怎么做”里剥出来，是面向接口编程的起点；内部类让一个类可以藏在另一个类里，写回调和事件监听时几乎绕不开；枚举用类型安全的方式取代满天飞的 static final int 常量。本章以 Java 17/21 为基线（Java 8 仍在广泛使用但已非现行基线），面向已经会写类与对象的读者，把这三块一次讲透，并给出可以照抄的代码模板；凡涉及版本差异的地方都会标出准确边界。

一、接口：一份对外承诺的契约

接口（interface）只描述“有哪些能力”，不关心“能力怎么实现”。一个类通过 implements 声明自己实现了某个接口，就等于签了合同：接口里声明的抽象方法，一个都不能少。

public interface Payable {
    // 接口里的抽象方法默认就是 public abstract，写不写都一样
    double amount();

    // 接口里的字段默认是 public static final，即常量
    String CURRENCY_CNY = "CNY";
}

class Order implements Payable {
    private final double total;
    private final double discount;

    Order(double total, double discount) {
        this.total = total;
        this.discount = discount;
    }

    @Override
    public double amount() {
        return total - discount;
    }
}

这里有两个容易记混的点。第一，接口里的字段不是普通字段，而是常量：编译器会自动补上 public static final，因此必须在声明时赋值，也不能被实现类改写。第二，接口里的方法有一条清晰的版本演进线——Java 8 之前，接口只能声明抽象方法（外加常量），任何方法都不能有方法体；Java 8 引入默认方法与接口静态方法；Java 9 又放开了接口私有方法。也就是说，“接口里绝不能有方法体”这句话在 Java 8 之后就不再成立了。

为什么需要默认方法

接口有一个天生的痛点：一旦发布，就不能再往上加抽象方法。设想 Payable 已经被几百个类实现，此时想给它加一个“是否支持分期”的方法，所有实现类都会编译失败。Java 8 引入的默认方法（default method）就是为这件事准备的：允许在接口里写带方法体的方法，实现类不重写也能用。

public interface Payable {
    double amount();

    // 默认方法：实现类可以原样继承，也可以重写
    default boolean supportInstallment() {
        return amount() >= 1000;
    }

    // 静态方法：属于接口本身，必须用接口名调用
    static Payable zero() {
        return () -> 0;
    }
}

接口静态方法同样自 Java 8 起才有：它属于接口本身，只能用 接口名.方法名() 调用，实现类继承不到。默认方法解决“加方法不破坏已有实现类”，接口静态方法解决“把与接口强相关的工具方法放在它身边”，下面要说的私有方法则解决“默认方法之间怎么复用代码”。

public interface Payable {
    double amount();

    default String describe() {
        return format(amount());               // 调用本接口的私有方法
    }

    default String describeWithCurrency() {
        return format(amount()) + " " + CURRENCY_CNY;
    }

    // Java 9 起（JEP 213）：接口允许 private 方法
    private String format(double value) {
        return String.format("%.2f", value);
    }
}

在 Java 9 之前，两个默认方法想做同一件小事，只能复制粘贴，或者把辅助代码挪进一个多余的 XxxUtil 类——后者会把实现细节暴露成公开 API。接口私有方法（Java 9 起，含 private static）让这段代码留在接口内部，只有接口自己看得见。实践提醒：仍有大量项目停留在 Java 8 或 11，写给别人用的库时，default/static 看齐 Java 8 最保险，private 方法则要求 Java 9 以上；Java 17/21 的新项目可以放心使用。

默认方法不是可有可无的语法糖，JDK 自己就是最大的受益者。Java 8 给 Collection 加上 stream()、forEach()，给 List 加上 sort()、replaceAll()，靠的都是默认方法；没有它，全世界的集合实现类都得跟着改一遍。

默认方法的冲突怎么解

既然接口能带方法体，就必然遇到“两个接口给出了同名默认方法”这种菱形问题。Java 定的规则很清楚，按优先级从高到低只有三条：

  1. 类自己重写的方法最优先。只要实现类里写了自己的方法，接口的默认版本一律被覆盖。
  2. 继承链上更具体的接口优先。如果 B 继承 A 而 B 重写了默认方法，那么同时实现 A、B 的类拿到的是 B 的版本。
  3. 两条支路互不相干时直接编译报错，必须在实现类里显式重写，并用 接口名.super.方法名() 指定要调用哪一个。
interface A {
    default String hello() { return "A"; }
}

interface B {
    default String hello() { return "B"; }
}

class C implements A, B {
    // 不重写就编译失败：class C inherits unrelated defaults for hello()
    @Override
    public String hello() {
        return A.super.hello() + B.super.hello(); // 输出 AB
    }
}

接口 vs 抽象类

两者都不能被实例化，也都可以声明抽象方法，但用途不同。接口表达的是“具备什么能力”，可以多实现，适合给互不相关的类打上同一个能力标签；抽象类表达的是“是什么”，只能单继承，适合承载子类共用的字段和部分实现。经验法则是：先想清楚子类是“是一个 X”还是“能做 X”，前者用抽象类，后者用接口。还有一个较新的能力值得知道：Java 17 起（JEP 409，密封类与密封接口在 Java 17 正式转正）接口可以声明为 sealed，并用 permits 列出允许的实现者；在那之前接口完全开放，任何人写个类都能实现它。设计需要受控扩展的框架 API 时，sealed interface 比“文档里写一句请勿实现”有效得多。

二、内部类：写回调和事件监听的基本功

把一个类写在另一个类的内部，它就是内部类，外层那个类叫外部类。内部类的价值在于表达“一个事物离不开另一个事物”的关系，比如人和心脏、订单和订单明细。分开写成两个平级类，这种依赖关系就体现不出来；此外，内部类还能访问外部类的私有成员。

静态嵌套类与非静态内部类

按 static 修饰与否，成员内部类分成两类，创建方式不同：

public class Outer {
    private int value = 10;

    // 非静态内部类：隐含持有外部类对象引用
    class Inner {
        int read() {
            return value; // 可以直接用外部类的私有实例字段
        }
    }

    // 静态嵌套类：不持有外部类对象引用
    static class Nested {
        int calc() {
            return 1;
        }
    }

    void use() {
        Inner in = new Inner();          // 外部类内部，可直接 new
        Nested ne = new Nested();
        in.read();
        ne.calc();
    }
}

class Entry {
    public static void main(String[] args) {
        Outer outer = new Outer();
        Outer.Inner in = outer.new Inner();  // 必须先有外部类对象
        Outer.Nested ne = new Outer.Nested(); // 静态嵌套类不依赖对象
    }
}

从外部创建非静态内部类对象要用 outer.new Inner() 这种略显古怪的语法，原因就在于它必须绑定一个外部类实例。静态嵌套类不需要外部对象，因此在只需要“一个挂在命名空间下的工具类”时，应该优先选它。

这里有一个流传很广的说法需要纠正：“非静态内部类绝对不能有静态成员”只在 JDK 16 之前成立。在 JDK 15 及更早（JLS 8.1.3），内部类里声明静态字段、静态方法、静态初始化块都是编译错误，唯一的例外是 static final 修饰的常量（基本类型或 String 字面量）。JDK 16 起（JEP 395，随记录类一起放宽），这条限制被取消：内部类可以像普通类一样声明静态字段、静态方法、静态嵌套类型和静态初始化块。只是静态成员依旧不依赖外部实例，语义上仍要心里有数。实践提醒：当前大量生产项目仍跑在 JDK 8 或 JDK 11 上，写代码时按旧规则来更保险。如果确实需要静态成员，把它提升为静态嵌套类或独立类，意图也更清楚。

顺带解释“非静态内部类为什么不能有静态方法”（JDK 16 之前的那条限制）背后的常见误答。网上常说“静态方法调用时外部类可能还没加载”，这是错的。类初始化时机由 JVM 规范明确列出（new、读写静态字段、调用静态方法，以及反射、父类初始化、启动类等）；调用内部类静态方法时必然已经触发初始化。真正的理由是它与实例绑定的语义冲突，而不是加载顺序。

局部内部类与匿名内部类

写在方法体里的类叫局部内部类，作用范围仅限该方法。日常代码里高频出现的是它的简写形式——匿名内部类：一边定义子类或实现类，一边直接创建对象，用一次就丢。

interface Greeting {
    void say(String name);
}

public class Demo {
    public static void main(String[] args) {
        // 匿名内部类：定义 Greeting 的实现类并立刻创建对象
        Greeting g = new Greeting() {
            @Override
            public void say(String name) {
                System.out.println("Hello, " + name);
            }
        };
        g.say("Java");
    }
}

使用匿名内部类有几个必须记住的限制。第一，它没有类名，因此不能定义构造方法，也无法复用。第二，它只能继承一个类或实现一个接口。第三，在方法内访问局部变量时，该变量必须是 final 或“事实上的 final”（effectively final）；Java 8 起不再强制写 final 关键字，但值不能改。如果接口是函数式接口（只有一个抽象方法），Java 8 起可以改写成 Lambda：Greeting g = name -> System.out.println("Hello, " + name);，比匿名内部类更短。但需要多个方法，或需要让 this 指向内部类自身时，匿名内部类仍然不可替代（Lambda 里的 this 指向外层实例，不是 Lambda 自身）。如果匿名类里装的是“一组不可变数据 + 少量行为”，还可以看看 Java 16 起的 record：记录类可以声明在类内部或方法内部（嵌套 record、局部 record），样板代码比匿名类少得多。

三、枚举：把常量收进类型里

在枚举出现之前，表示“订单状态”这类有限取值，通常靠一组常量：

public class OrderStatus {
    public static final int CREATED = 0;
    public static final int PAID = 1;
    public static final int SHIPPED = 2;
}

这种写法的毛病很致命。pay(int status) 的入参是 int，传 999 编译器也放行；两个语义完全不同的常量集还可能撞值；想遍历所有状态、想给状态加个中文描述，都得额外写一堆代码。枚举把“取值范围”变成类型本身，编译器替你把关。

带字段和方法的枚举

枚举常量本质上是枚举类的静态实例，所以枚举可以像普通类一样有字段、构造方法和方法，只是构造方法只能是私有的（写不写 private 效果一样）。

public enum OrderStatus {
    CREATED(0, "已创建"),
    PAID(1, "已支付"),
    SHIPPED(2, "已发货");

    private final int code;
    private final String label;

    // 枚举的构造方法只能是 private，且不能用 new 调用
    OrderStatus(int code, String label) {
        this.code = code;
        this.label = label;
    }

    public int getCode() { return code; }
    public String getLabel() { return label; }

    // 常量级方法体：每个常量可以给出各自的实现
    public boolean cancellable() {
        return this == CREATED;
    }

    public static OrderStatus ofCode(int code) {
        for (OrderStatus s : values()) {
            if (s.code == code) {
                return s;
            }
        }
        throw new IllegalArgumentException("未知状态码: " + code);
    }
}

枚举常量如果带自己的方法体（如上面把 cancellable() 写成匿名子类形式），编译后每个常量都会成为枚举类的一个匿名子类实例，这一点在阅读反编译结果时经常遇到。

常用方法与惯用法

  • values()：返回所有常量组成的数组，常用于 for 遍历。注意每次调用都会克隆一份数组，放进循环条件里反复调用会成为性能坑。
  • valueOf(String)：按常量名取实例，名字不存在时抛 IllegalArgumentException；名字写错属于编码错误，不要用它做用户输入的容错解析。
  • name() 与 ordinal()：分别返回声明名和声明顺序（从 0 开始）。ordinal() 依赖书写顺序，不要把它持久化到数据库，也不要用它做业务判断，用自定义的 code 字段更稳。
  • switch 支持枚举：case 后直接写常量名，不用加类名前缀。
  • 比较用 == 而不是 equals()：每个常量在 JVM 中只有一个实例，== 既安全又更快，还能避免空指针。
  • 枚举实现了 Comparable 与 Serializable，并且天然是单例，因此用单元素枚举写单例（《Effective Java》推荐做法）可以天然防住反射和序列化破坏。

枚举与常量类的取舍可以概括为：枚举编译后是 final class（并继承 java.lang.Enum），不可被继承，取值收敛、类型安全、可遍历、可带行为。但枚举常量在类加载时就全部实例化，如果取值成千上万、还需要频繁增删，那么枚举并不合适，此时用配置或数据库表更合理。

四、常见坑速查

  • 接口字段当变量用：接口里的字段是 public static final 常量，实现类里写 CURRENCY_CNY = "USD" 会直接编译失败。
  • 记错接口方法的版本边界：接口的 default 与 static 方法自 Java 8 才有，接口 private 方法自 Java 9 才有；给仍跑在 Java 8 上的项目写公共库时，这三档要分清楚。
  • 以为默认方法能覆盖 Object 的方法：接口不能提供 equals、hashCode、toString 的默认实现，写了也编译不过，这些方法只能由类提供。
  • 在静态方法里 new 非静态内部类：非静态内部类需要外部实例，静态上下文里没有 this，必须先 new Outer() 再 outer.new Inner()。
  • 匿名内部类里改局部变量：被匿名内部类捕获的局部变量必须是事实上的 final，想“改”就用只有一个元素的数组或 AtomicInteger 之类的持有对象。
  • 用 ordinal() 存库或比对：调整常量声明顺序就会让历史数据错位，一律用自己定义的业务编码。
  • 在循环条件里调用 values()：每次都克隆数组，改成先取出一次再遍历。

五、小结

接口定义“能做什么”，从 Java 8 起还允许用默认方法平滑演进，冲突时按“本类优先、子接口次之、否则显式指定”处理。内部类适合表达强依赖关系：非静态内部类持有外部实例，并由此获得访问私有成员的便利，代价是必须先有外部对象；静态嵌套类更轻，更适合工具型嵌套。匿名内部类是一次性的子类或实现类写法，函数式接口场景下可以让位给 Lambda。枚举把有限取值升级为一个类型，配合私有构造、字段和自定义方法，能同时解决类型安全、可遍历和可携带行为三个问题，但要注意 ordinal() 与 values() 的使用边界。下一章进入常用类库，看看 String、包装类与日期时间这些出场率最高的 API。
