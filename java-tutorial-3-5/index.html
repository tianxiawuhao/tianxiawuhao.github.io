3.5 Ajax 与前后端交互

Posted on 2026-09-19，6 min read

上一章讲了怎样让浏览器把页面渲染得漂漂亮亮，但那些页面上的数据从哪来？如果每换一个用户名、每翻一页列表，都要让整个页面重新加载一次，用户会看到白屏闪烁，服务器也要重复传输导航栏、页脚、CSS 这些根本没必要重发的字节。本章要解决的就是这件事：让 JavaScript 在后台悄悄发一次 HTTP 请求，拿到数据后只更新页面的一小块。这就是 Ajax（Asynchronous JavaScript and XML）。你会依次看清原生 XMLHttpRequest 的四步流程、现代写法 fetch 与 axios 的取舍，最后解释那道几乎人人都会撞上的墙——同源策略与 CORS。如果你已经会写 HTML/CSS 和一点 JavaScript，但还说不清“请求发出去了为什么被浏览器拦住”，本章正适合你。

一、Ajax 到底改变了什么

传统网页的交互模型是“提交—跳转—重新渲染”：表单 action 指向一个 Servlet，点提交后浏览器把整个文档换掉。Ajax 把这条链路拆成两半，请求依旧由浏览器发出，但响应不再交给浏览器去替换文档，而是交给一段 JavaScript 回调函数，由它决定把数据塞进哪个 <div>。浏览器地址栏不动、页面不闪、上下文不丢，这就是“局部刷新”。

这条链路的三个角色需要记牢：请求由 Ajax 引擎（也就是 XMLHttpRequest 对象）发送；服务器照旧处理并返回数据；数据的落点由回调函数里的 DOM 操作决定。理解了这个分工，后面所有框架的 API 就都只是包装形式的差异而已。

需要提前澄清一个常见误解：名字里的 XML 是历史遗留。今天的接口绝大多数返回 JSON，XMLHttpRequest 这个类名和 XML 已经没有必然关系。

二、原生 XMLHttpRequest：四步与两个坑

原生写法只有四步：创建对象 → open 打开连接 → send 发送 → 监听响应。下面是一个用户名唯一性校验的完整例子（对应后端接口 GET /api/users/exists?username=...）：

function checkUsername(input) {
  // 1. 创建对象
  var xhr = new XMLHttpRequest();
  // 2. 打开连接：方法、URL、是否异步
  xhr.open('GET', '/api/users/exists?username=' + encodeURIComponent(input.value), true);
  // 3. 先注册回调，再发送
  xhr.onreadystatechange = function () {
    if (xhr.readyState === 4) {
      if (xhr.status >= 200 && xhr.status < 300) {
        document.getElementById('username_msg').textContent = xhr.responseText;
      } else {
        document.getElementById('username_msg').textContent = '请求失败：' + xhr.status;
      }
    }
  };
  xhr.send(); // 4. GET 请求参数已拼在 URL 上，send 不传参
}

这里有两处值得单独强调。第一，onreadystatechange 必须在 send() 之前绑定，否则请求若很快返回，回调可能来不及注册就被触发，页面表现为“偶尔没反应”。第二，readyState === 4 只说明请求结束，不代表成功，必须同时判断 status；把条件写成 status == 200 会漏掉 201、204 这些同样合法的成功响应，使用范围判断更稳妥。

POST 请求要多做一步：把参数从 URL 挪进请求体，并用 setRequestHeader 声明编码方式，否则服务端按默认字符集解码，中文参数就变成了乱码。流程依旧是先 open('POST', 路径, true)，紧接着设置请求头，再把 'nickname=' + 值 作为 send() 的实参发出，最后在 onreadystatechange 里判断 readyState 与 status，把响应写进目标元素。这里有两个细节必须核对。一是请求头的准确拼写是 application/x-www-form-urlencoded，中间那两个连字符缺一不可，写成 application/x-www-formurlencoded 是不合法的。二是参数值要先经 encodeURIComponent 编码，否则 &、=、空格等字符会破坏请求体结构，GET 请求把参数拼在 URL 上时同理。GET 与 POST 在 Ajax 里的差别并不神秘：GET 把参数放在 URL 上，只适合查询且受长度限制；POST 把参数放在请求体里，适合提交与修改。接口该用哪个方法由语义决定，而不是由“哪个更方便”决定。至于网上老教程里那段 window.XMLHttpRequest ? ... : new ActiveXObject('Microsoft.XMLHTTP') 的兼容判断，是为 IE5/IE6 准备的，今天可以放心删掉，直接 new XMLHttpRequest() 即可。

三、fetch 与 axios：现代写法怎么选

fetch 是 ES6 之后浏览器内置的 API（不是库，无需引入），它返回 Promise，配合 async/await 写起来比回调清爽得多。但要记住一个关键差异：fetch 只在网络层面失败时才 reject，HTTP 的 404、500 对它来说都是“成功完成”的请求，必须自己检查 response.ok。另外，response.json() 返回的也是 Promise，漏写 await 会得到一个 Promise 对象而不是数据——这是新手最常见的 bug。

async function login(username, password) {
  try {
    const res = await fetch('/api/login', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      credentials: 'include', // fetch 默认不带 cookie，需要显式声明
      body: JSON.stringify({ username: username, password: password })
    });
    if (!res.ok) {
      throw new Error('HTTP ' + res.status);
    }
    const data = await res.json(); // 别忘了 await
    console.log(data);
  } catch (e) {
    console.error('登录失败', e);
  }
}

axios 是第三方库，浏览器端底层同样是 XMLHttpRequest（在 Node.js 里则用 http 模块，所以它并非“只是 XHR 的封装”）。它的优势在于工程化的细节都替你做好了：

  • 自动把 JSON 响应转成对象；
  • 非 2xx 状态码直接 reject；
  • 拦截器统一加 token 与处理错误；
  • 并发请求接口；
  • 可取消、可设超时。

换成 fetch，这些都要自己封装一层。

const api = axios.create({
  baseURL: '/api',
  timeout: 5000
});

// 响应拦截器：把 data 直接抛给调用方，统一处理错误
api.interceptors.response.use(
  function (response) { return response.data; },
  function (error) {
    console.error('接口异常', error.response && error.response.status);
    return Promise.reject(error);
  }
);

api.post('/login', { username: 'tom', password: '123456' })
  .then(function (data) { console.log(data); })
  .catch(function (err) { console.error(err); });

关于常被引用的“fetch 不支持中断和超时”这一说法，需要更新：现代浏览器已经支持 AbortController 中断请求，也可用 AbortSignal.timeout(5000) 设置超时，只是比 axios 的 timeout 配置啰嗦。真正仍然成立的短板是无法原生获取上传/下载进度，需要进度条时应改用 XMLHttpRequest 的 upload.onprogress。选型建议很直接：小项目或不想引依赖就用 fetch，中大型项目、需要拦截器和统一错误处理就用 axios；jQuery 的 $.ajax 只是历史写法，新项目不必再引入整个 jQuery。另外，$.ajax 支持 JSONP 这件事容易误导——JSONP 靠的是动态插入 <script> 标签，与 XMLHttpRequest 无关，且只支持 GET，今天应该用 CORS 取代它。

四、跨域与 CORS：请求为什么被拦住

当页面地址与接口地址的协议、域名、端口三者中任意一项不同，浏览器就判定为跨域，并施加同源策略限制。注意“被拦住”的准确含义：请求通常已经发出、服务器也处理了，只是响应被浏览器拦下不交给 JavaScript。所以看到 CORS 报错时，先去后端加响应头，而不是怀疑前端代码写错了。

解决方案是 CORS（跨域资源共享），由服务器通过响应头声明允许哪些来源访问。简单请求（GET、POST 配少量安全头）只需一个 Access-Control-Allow-Origin；带自定义头、Content-Type: application/json 或 PUT/DELETE 的请求，浏览器会先发一次 OPTIONS 预检请求，服务器需应答 Access-Control-Allow-Methods、Access-Control-Allow-Headers。若前端要带 cookie，前后端都得开启凭证：前端 credentials: 'include'，后端 Access-Control-Allow-Credentials: true。Spring Boot 中集中配置最省事：

@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("http://localhost:5173") // 前端开发服务器地址
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowedHeaders("*")
                .allowCredentials(true)
                .maxAge(3600); // 预检结果缓存 1 小时，减少 OPTIONS 请求
    }
}

最后一个高频陷阱：allowCredentials(true) 不能与 allowedOrigins("*") 同时使用，浏览器会直接拒绝，必须写明具体来源（或用 allowedOriginPatterns）。开发阶段还可以用前端代理（Vite 的 server.proxy）把 /api 转发到后端，让浏览器认为请求同源，从而绕开跨域——但这只是开发便利，生产环境仍需服务端正确配置 CORS。

小结

Ajax 的本质是“用 JavaScript 发请求、用回调更新局部 DOM”，XMLHttpRequest 是这套机制的原生引擎，fetch 与 axios 是两种更好的书写方式。记住以下四条要点：

  • onreadystatechange 要在 send() 前绑定，并同时校验 status；
  • fetch 不会因 404/500 而 reject，且 response.json() 必须 await；
  • axios 用拦截器和 timeout 省掉大量样板代码；
  • 跨域由服务端 CORS 响应头解决，带 cookie 时不能把允许来源写成 *。

把这几点落实到代码里，前后端联调时绝大多数“数据拿不到”的问题都能自己定位。
