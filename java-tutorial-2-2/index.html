多表查询与子查询

Posted on 2026-09-19，6 min read

上一章我们把数据规范地存进了多张表里。规范化的代价是：一次业务问题往往横跨好几张表。比如“列出每部影片的片名和主演姓名”，片名在 film 表，姓名在 actor 表，两者的关系存在 film_actor 表——单表查询再强也答不出来。本章讲清楚三件事：多张表怎么用 连接（JOIN）拼成一张宽表、一个查询怎么嵌进另一个查询成为 子查询、统计类需求怎么用 GROUP BY / HAVING 与 UNION 得到结果。读完这一章，你应该能独立写出三表以上的关联查询，并在“写得对”的基础上判断“写得快不快”。本章适合已经会写单表 SELECT、准备处理真实业务查询的读者。

一、连接查询：把多张表拼成一张宽表

连接的本质是按关联条件把两张表的行做配对。配对方式不同，结果集也不同，这是最容易出错的地方。

内连接（INNER JOIN）只保留两边都能配对上的行。下面两种写法完全等价，第一种是早期常用的“逗号 + WHERE”，第二种是显式的 JOIN ... ON，推荐后者：关联条件与过滤条件一眼可区分。

-- 写法一：隐式连接（逗号 + WHERE），不推荐
SELECT f.title, a.first_name, a.last_name
FROM film AS f, film_actor AS fa, actor AS a
WHERE f.film_id = fa.film_id AND fa.actor_id = a.actor_id;

-- 写法二：显式内连接，推荐
SELECT f.title, a.first_name, a.last_name
FROM film AS f
JOIN film_actor AS fa ON fa.film_id = f.film_id
JOIN actor AS a       ON a.actor_id = fa.actor_id
WHERE f.release_year = 2006
ORDER BY f.title;

外连接会保留某一侧的全部行，另一侧没配上就填 NULL。LEFT JOIN 保留左表全部行，RIGHT JOIN 保留右表全部行。“找出没有下过单的用户”这类需求就是左外连接的典型用法：左表全体保留，右表匹配不上必然是 NULL。外连接常与分组统计配合，统计时要写 COUNT(fa.film_id) 而不是 COUNT(*)：COUNT(*) 统计结果集行数，外连接补出的 NULL 行会被算成 1，没参演过的演员就显示为 1；而 COUNT(列名) 忽略 NULL，结果才是期望的 0。

坑一：把外连接的条件写进 WHERE。外连接中 ON 决定“怎么配对”，WHERE 在配对完成后过滤。若把右表的条件写进 WHERE，那些被补成 NULL 的行会因 NULL = 值 为 UNKNOWN 而被滤掉，LEFT JOIN 直接退化成 INNER JOIN。正确做法是把右表条件放进 ON：

-- 需求：每个演员只统计 2006 年之后的参演影片数，没参演的一律显示 0
SELECT a.actor_id, COUNT(fa.film_id) AS film_cnt
FROM actor AS a
LEFT JOIN film_actor AS fa
       ON fa.actor_id = a.actor_id
      AND fa.last_update >= '2006-01-01'   -- 右表条件必须放在 ON 里
GROUP BY a.actor_id
ORDER BY film_cnt DESC;

坑二：以为 MySQL 支持全外连接。FULL OUTER JOIN 是 SQL 标准语法，Oracle、PostgreSQL 支持，但 MySQL 至今不提供该语法。在 MySQL 里要“两边都保留”，只能把左外连接与右外连接的结果用 UNION 合并。坑三：列名歧义。多表连接时若两张表有同名列（如都叫 actor_id），SELECT * 和未加表别名的列引用都会报 Column 'xxx' is ambiguous；解决办法是每张表都起别名，并始终用 别名.列名 引用。另外，显式 JOIN ... ON 与 JOIN ... USING(列名) 等价，但 USING 要求两表关联列同名，且结果集中该列只出现一次，条件复杂时仍应使用 ON。

二、子查询：把结果当条件或当表用

子查询（subquery）就是出现在 WHERE、FROM 或 SELECT 里的另一条 SELECT。按返回形状分三类：返回单个值的标量子查询、返回一列的列子查询（配 IN、ANY、ALL 使用）、返回一张临时表的表子查询（写在 FROM 里，也叫派生表，必须起别名）。

两个最常用的谓词是 IN 与 EXISTS。IN 判断某个值是否落在子查询返回的集合里；EXISTS 判断子查询是否“至少返回一行”，为真则主查询当前行被保留。EXISTS 的威力在于关联子查询：子查询里可以引用外层的列，因此它天生能表达“某一行是否存在对应记录”这种逐行判断。下面第一条查询里 fa.actor_id = a.actor_id 这个“引用外层”的关联条件就是关键，缺了它 EXISTS 会退化成无意义的“子查询结果非空”。

-- 取集合：IN + 列子查询
SELECT a.actor_id, a.first_name
FROM actor AS a
WHERE a.actor_id IN (SELECT fa.actor_id FROM film_actor AS fa);

-- 判存在：EXISTS + 关联子查询（子查询引用外层的 a.actor_id）
SELECT a.actor_id, a.first_name
FROM actor AS a
WHERE EXISTS (SELECT 1 FROM film_actor AS fa WHERE fa.actor_id = a.actor_id);

-- 反向需求：从未参演过任何影片的演员，用 NOT EXISTS 而非 NOT IN
SELECT a.actor_id, a.first_name
FROM actor AS a
WHERE NOT EXISTS (SELECT 1 FROM film_actor AS fa WHERE fa.actor_id = a.actor_id);

坑一：NOT IN 遇到 NULL 会返回空集。若子查询结果含 NULL，x NOT IN (..., NULL) 等价于 x <> NULL，结果为 UNKNOWN 而非 TRUE，所有行都被滤掉，查询静默返回 0 行，极难排查。结论：只要外层是“不存在”语义，优先写 NOT EXISTS，或给子查询补上 WHERE 列 IS NOT NULL。

坑二：把子查询改写成连接时忽略“一对多”。若一个演员对应多行 film_actor，改写后的连接会把结果放大成多行，必须加 DISTINCT 去重，或直接保留 EXISTS（存在性判断天然不产生重复）。坑三：迷信“子查询一定慢”。这条经验已经过时：MySQL 5.6 起引入 semi-join、materialization、firstmatch 等优化，很多 IN 子查询会被自动改写成半连接，效率与手写 JOIN 相当。真正该做的是用 EXPLAIN 看执行计划，而不是凭直觉改写。

三、分组统计：GROUP BY 与 HAVING

GROUP BY 按一个或多个列把行切成若干组，聚合函数（COUNT、SUM、AVG、MAX、MIN）在每组内部计算。选出的非聚合列原则上都必须出现在 GROUP BY 中：MySQL 5.7 起默认开启 ONLY_FULL_GROUP_BY，违反即报错；5.7 之前的宽松模式会“随便挑一行”返回，结果不确定，这是老项目升级后才暴露的隐性 bug。

过滤条件分两处写：分组前对原始行的过滤用 WHERE，分组后对聚合结果的过滤用 HAVING。子句书写顺序为 WHERE → GROUP BY → HAVING → ORDER BY，而执行顺序是 FROM/JOIN → WHERE → GROUP BY → 聚合 → HAVING → SELECT → ORDER BY → LIMIT；理解了执行顺序，就不会再问“为什么 WHERE 里不能用聚合函数”。GROUP BY 同时是最简洁的去重手段：SELECT DISTINCT name FROM t 与 SELECT name FROM t GROUP BY name 结果相同，但后者还能顺带输出聚合值。

SELECT a.actor_id,
       a.first_name,
       COUNT(*) AS film_cnt
FROM actor AS a
JOIN film_actor AS fa ON fa.actor_id = a.actor_id
WHERE a.last_update >= '2006-01-01'   -- 分组前过滤原始行
GROUP BY a.actor_id, a.first_name      -- 非聚合列必须全部出现
HAVING COUNT(*) > 10                   -- 分组后过滤聚合结果
ORDER BY film_cnt DESC;

若统计性能不佳，常见的优化是“先聚合到派生表再连接”：派生表里每个演员只剩一行，与外层连接时不会产生重复，也更容易走上索引，避免 MySQL 在分组时使用临时表和文件排序。

四、UNION：把两个结果集纵向拼起来

连接是横向加列，UNION 是纵向加行。参与合并的各 SELECT 必须列数相同、类型兼容，结果列名以第一个 SELECT 为准。UNION 会去重（内部要做排序或哈希，代价更高），UNION ALL 直接追加、不去重，因此确定没有重复或允许重复时一律用 UNION ALL。它也是上一节“MySQL 模拟全外连接”的落地手段：把左外连接与右外连接的结果合并，去重工作由 UNION 自动完成，无需手写 DISTINCT。

还要注意 ORDER BY 的位置：它作用于合并后的最终结果，必须写在最后一个 SELECT 之后；想对某个分支单独排序，得先用括号包起来再加 LIMIT，否则语法直接报错。UNION 与连接可以共存，但一条 SQL 里同时出现多层嵌套、多个 UNION 时，可读性会迅速下降，此时更推荐拆成临时表或分步查询。

五、小结

本章的主线是一条判断链：先看需求要不要跨表——跨表就用连接，且要问清“匹配不上的行要不要留”，要留就用外连接，并注意右表条件写在 ON 而不是 WHERE；再看需求是“取集合”还是“判存在”——取集合用 IN，判存在用 EXISTS 关联子查询，反向判断用 NOT EXISTS 而非 NOT IN；最后看需求是否涉及统计——按维度的明细放 GROUP BY，聚合结果的过滤放 HAVING，非聚合列必须全部出现在 GROUP BY 中，纵向合并结果集用 UNION ALL。把这三步固定成写 SQL 的习惯，绝大多数多表查询都能一次写对。至于“哪种写法更快”，答案永远在执行计划里：用 EXPLAIN 看连接顺序、是否命中索引、有没有出现临时表与文件排序，再决定是否改写——而不是凭“子查询慢”的印象提前优化。

最后一句经验之谈：先用 EXPLAIN 确认瓶颈，再动手改写 SQL。同一条需求把 IN 改成 JOIN 未必更快，给连接列与分组列补上合适的索引往往收益更大。多看几次执行计划里的 type、key、rows、Extra 四列，你对“哪句 SQL 慢”的判断就会逐渐从感觉变成证据。
