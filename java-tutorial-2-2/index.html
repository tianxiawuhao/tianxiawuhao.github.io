多表查询与子查询

Posted on 2026-09-19，4 min read

前面几章我们把单张表的增删改查讲完了，可真实业务里数据几乎从不放在一张表：用户、订单、商品各自成表，靠关联字段串起来。本章解决的就是「数据分散在多张表时怎么查」这个问题——包括连接查询（JOIN）、子查询、分组过滤和结果集合并。适合已经会写 SELECT ... FROM 单表 WHERE ...、想跨到多表查询的读者。读完后你应该能判断一条需求该用 JOIN 还是子查询，并避开最常见的两个坑：笛卡尔积和重复行。

一、多表查询与内连接：先理解笛卡尔积

最朴素的「多表查询」是在 FROM 后面并列写两张表：

-- 笛卡尔积：A 的每一行与 B 的每一行两两组合
select * from A, B;

-- 加上连接条件后，只留下关联字段匹配上的组合
select A.A_ID, A.A_NAME, B.B_PRICE
from A, B
where A.A_ID = B.A_ID;

-- 显式内连接：关联条件写在 on 里（推荐，语义更清晰）
select A.A_ID, A.A_NAME, B.B_PRICE
from A inner join B on A.A_ID = B.A_ID;

第一条语句的结果行数 = A 的行数 × B 的行数，这个结果集叫笛卡尔积，几乎总是没有业务意义的，只是多表连接的「原料」。真正有用的是在连接之后补上过滤条件，把无意义的组合剔除掉。上面前两种写法的区别只在连接条件的位置，结果一致；但推荐 inner join ... on，因为它让 on 专门描述「两张表怎么关联」、where 专门描述「要过滤出哪些行」，两件事分开后，后续再叠加业务条件不容易出错。多个表连接时依次追加 join ... on ... 即可，比如「列出每部影片的片名和主演姓名」要连接影片表、影片演员关系表和演员表三张表，就是两个 join 串联。另外要注意，内连接会丢掉「在另一张表里找不到匹配」的行：A 表里的 banana 在 B 表没有价格记录，内连接的结果里就没有它。

二、左外连接、右外连接与全外连接

如果需求是「以左表为主，右表没有匹配也要把左表的行留下」，就要用外连接。左外连接以左表为基准表（驱动表），右表匹配不上的字段用 NULL 补齐，因此它不会丢行，只会多出 NULL：

-- 左外连接：banana 在 B 表没有匹配，B 表字段为 NULL，但这一行仍然保留
select * from A left join B on A.A_ID = B.A_ID;

-- MySQL 模拟全外连接：左右外连接结果合并去重
select * from A left join B on A.A_ID = B.A_ID
union
select * from A right join B on A.A_ID = B.A_ID;

右外连接正好相反，以右表为基准表，保留右表全部记录，左表匹配不上则补 NULL。工程上更常用的技巧是：统一只用 left join，把右外连接改写成调换两张表位置的左外连接，SQL 可读性和可维护性都更好。

三、子查询：in、exists 与关联子查询

子查询就是把一条 SQL 的查询结果当作另一条查询的参数，可以出现在 where、from（派生表）、select 等位置。最常用的是 in 和 exists：

-- in：外层条件落在子查询返回的列表里
select * from A where A_ID in (select A_ID from B);

-- not in：不在列表里。注意子查询结果中若含 NULL，not in 会整体返回空集
select * from A where A_ID not in (select A_ID from B);

-- exists：子查询能查到行就保留外层这一行
select * from A where exists (select 1 from B where B.A_ID = A.A_ID);

这里有三个容易出错的点，务必记牢：

  • exists 后面应当是关联子查询，子查询里要用外层表的列做条件（如上例的 B.A_ID = A.A_ID）。如果写成 exists (select A_ID from B) 这种不带关联条件的子查询，它对外层每一行都恒为真，实际效果约等于「B 表非空就返回 A 表全部数据」，通常不是你要的结果；同理，not exists 缺少关联条件会直接返回空集。
  • not in 遇到 NULL 会「踩空」：只要子查询结果里有一个 NULL，整个条件对任何值都不成立，结果集为空。相关需求建议改用 not exists。
  • exists 只关心子查询有没有结果，因此子查询里写 select 1 就够，不必写 select *。

子查询与 join 的取舍

很多场景下 in 子查询可以改写成 join，而且往往更快——优化器更擅长为连接选择驱动表和索引。但改写时必须确认关联键是不是一对多。例如 select * from t where t.id in (select t1.tid from t1)，直接改写成 select id from t join t1 on t.id = t1.tid，当 t1 中同一个 tid 出现两次时，结果就会把同一条 t 记录返回两次；而 in 在语义上天然去重。此时要么补 distinct，要么改用 exists，这是实际开发中最常见的数据重复来源之一。反过来，子查询也并非总是慢：在只需判断「存在与否」时，exists 往往能提前结束扫描。

四、分组过滤：where、group by 与 having

group by 把行按列值分组，常配合聚合函数使用；它同时是一个简易去重手段，select name from employee group by name 等价于 select distinct name from employee。分组之后的过滤条件必须用 having，因为 where 在分组前执行，无法引用聚合结果。逻辑执行顺序为 where → group by → having → order by：

-- 统计每个员工的签到总次数，只看总数大于 5 的，并按总数倒序
select name, sum(singin) as total
from employee_tbl
where id <> 1
group by name
having sum(singin) > 5
order by total desc;

两个规范必须遵守。第一，聚合函数要写具体的列，sum(*) 是错误写法，聚合函数的参数只能是列名或表达式，只有 count(*) 是统计行数的特例。第二，select 列表里出现的非聚合列都应当出现在 group by 中；MySQL 5.7 起默认开启 only_full_group_by，不满足这一点的 SQL 会直接报错，而不是像老版本那样随机取一行。至于分组键的选择，原则是尽量用被过滤、被索引覆盖的列，能显著减少临时表和文件排序。

五、union 与 union all，以及本章小结

union 用于把多条 select 的结果上下拼接成一个结果集（是「加行」，不是 join 的「加列」）。两者差别只有一处：union 合并后去重，因此需要额外排序，开销更大；union all 不去重，直接拼接，效率更高。所以能确定两侧结果不会重复时，优先写 union all。

使用时还有三条约束：参与合并的各条 select 列数必须相同、对应列的数据类型要兼容（不能一边是名字字符串、一边是价格数字），结果集的列名以第一条 select 为准；而 order by、limit 写在整条语句最后，作用于合并后的整体结果，不是某一条 select。

多表查询的核心是把「关联」和「过滤」分开想：on 负责两张表怎么对上，where 负责留下哪些行，having 负责过滤分组后的结果。记住四条判断规则：内连接只留匹配行，外连接保留基准表全部行并用 NULL 补齐，MySQL 没有 full outer join 要用 union 模拟；子查询改写成 join 时必须先确认关联键是否一对多，否则会凭空多出重复行；not in 遇到 NULL 会返回空集，改用 not exists 更安全；union 去重、union all 不去重，不确定是否有重复时先核对再决定。把这些边界情况摸清，后面学习索引与执行计划优化时会顺畅很多。
