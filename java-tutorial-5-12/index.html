代码重构与规范

Posted on 2026-09-19，6 min read

代码能跑只是最低标准。真正决定成本的是三个月后你还能不能读懂它、敢不敢改它。如果一段业务逻辑隔了一个季度再回来看，需要花半小时才能弄明白，这份“隐形账单”在写下它的那天就已经记上了。本章讲的是一整套让代码保持可改的习惯。第一步说清重构的定义与动手时机，第二步落到命名和分层这类每天都要做的动作，第三步给出识别坏味道与最常用重构手法的路径，第四步交代现代 Java 写法（Optional / Stream / var / 字符串格式化）的适用边界，最后补齐两件最容易被忽视、一旦出事却最贵的事——日志规范与异常规范。适合已经能独立写业务、开始接手别人代码，或需要给团队定规矩的读者。

一、重构：不改变可观察行为，只改结构

重构（Refactoring）的定义是：对软件内部结构的一种调整，目的是在不改变软件可观察行为的前提下，提高其可理解性、降低其修改成本。它既不是加功能，也不是修 Bug，唯一的验收标准是“下一次改动需要动的地方更少”。正因为要求行为不变，重构的第一步永远是先有可靠的测试环境。没有测试就大改结构，等于闭着眼睛拆承重墙；有了测试，每次小改都能立刻验证行为未变。这也是“以微小步伐修改程序”的底气——步伐越小，出错时越容易定位。

什么时候动手？三次法则给了很实用的答案：第一次做某件事时只管去做，第二次做类似的事时可以去做，第三次再做同样的事就应该重构，也就是“事不过三”。它的另一面是：不要一开始就追求完美设计。软件开发无法预先设计，最初不可能穷举所有变化，合理做法是先用简单的设计起步，等变化真的发生时再重构到位。

从这个角度看，重构就是在适当的位置插入间接层、在不需要时移除间接层，而间接层的价值不外乎四点：允许逻辑共享、把意图与实现分开、隔离变化、封装条件逻辑。

两个边界必须记住。其一，当现有代码已经过于混乱时，应当重写而不是重构。其二，为了可读性，重构有时会让性能略降，不必在写代码时过度纠结性能，真正要盯住的只是那一小部分关键代码。另外，如果重构改动了已发布的接口，就必须同时维护新旧两个接口——保留旧接口转调新接口，并用 @Deprecated 标记旧接口、说明替代方案。结论很直接：除非真有必要，不要过早发布接口。

二、命名与分层：最便宜也最有效的规范

命名不产生任何运行时开销，却直接决定代码能否自解释，是性价比最高的一项规范。类名用 UpperCamelCase（DO、BO、DTO、VO 这类缩写例外），方法名、参数名、成员变量、局部变量统一用 lowerCamelCase，常量全部大写且单词间用下划线分隔，例如 MAX_STOCK_COUNT。抽象类以 Abstract 或 Base 开头，异常类以 Exception 结尾，测试类以被测类名开头、Test 结尾。包名统一小写、单数，点分隔符之间只有一个自然语义的英文单词。

反过来，这些做法一律禁止：用下划线或美元符号开头、结尾（_name、name$）；拼音与英文混用，甚至直接用中文命名；把 AbstractClass 缩写成 AbsClass、把 condition 缩写成 condi——这类缩写严重降低可读性。数组定义写 String[] args，不要写 String args[]。POJO 中布尔类型属性不要加 is 前缀，否则部分 RPC 或序列化框架在反向解析时会“以为”属性名是 deleted，导致属性取不到甚至抛异常。

分层命名让调用方不看实现就能猜到行为。Service 与 DAO 层统一约定：取单个对象用 get 前缀，取多个用 list，取统计值用 count，插入用 save 或 insert，删除用 remove 或 delete，修改用 update。领域模型则约定：数据对象 xxxDO（xxx 为数据表名）、传输对象 xxxDTO、展示对象 xxxVO；POJO 是它们的统称，不要命名成 xxxPOJO。

命名之外，分层还划定职责边界。以异常处理为例：DAO 层捕获 Exception 后转换成 DAOException 抛出，不打印日志；Service 层捕获并记录出错日志，且尽量带上参数信息，相当于保护案发现场。Web 层已在顶层，绝不应继续往上抛异常，而应转到友好错误页并给出用户能理解的提示；开放接口层则把异常转换成错误码和错误信息返回。这样每层都知道自己该做什么，日志也不会在多层重复打印。

三、识别坏味道，再用小步手法改掉

坏味道（Code Smell）不是 Bug，而是“将来会变贵”的信号。最典型的两类是重复代码（Duplicated Code）和过长函数（Long Function）。重复代码要分场景处理，最常用的手法有四种。同一个类的两个函数有相同表达式，用提炼函数（Extract Method）把重复部分抽出来。两个互为兄弟的子类有相同表达式时，先做 Extract Method，再把函数上移到超类（Pull Up Method）。只有部分相同时，先分离出相同部分与差异部分，再用模板方法（Form Template Method）。若是两个毫不相关的类出现重复代码，则用提炼类（Extract Class）把重复部分提取到独立类中。

手法要小步走：改一点、跑一次测试，不要一次改五个文件再一起验证。下面用一段计费代码演示两个最常用的手法——以查询取代临时变量（Replace Temp with Query）与提炼函数（Extract Method）。

// 重构前：临时变量阻碍提炼，条件分支埋在长函数里
double price() {
    double basePrice = quantity * itemPrice;
    double discountFactor;
    if (basePrice > 1000) {
        discountFactor = 0.95;
    } else {
        discountFactor = 0.98;
    }
    return basePrice * discountFactor;
}

// 重构后：临时变量变成查询方法，条件逻辑拆成独立函数
private double basePrice() {
    return quantity * itemPrice;
}

private double discountFactor() {
    return basePrice() > 1000 ? 0.95 : 0.98;
}

double price() {
    return basePrice() * discountFactor();
}

这里有一个容易忽略的顺序问题：Replace Temp with Query 往往是 Extract Method 之前必不可少的一步。原因在于局部变量会让代码难以提炼：只要临时变量还在，抽出来的函数就得靠参数传递它。同理，当条件表达式过长时，可以用分解条件表达式（Decompose Conditional）把 if、then、else 三段分别提炼成函数，让主流程读起来像一句话。

四、日志规范：留证据，而不是刷屏

日志是线上排查唯一的现场记录，但写错方式会比不写更糟。第一，用门面，不用实现。应用中不要直接调用 Log4j、Logback 的 API，而应依赖 SLF4J 的 API。这样日志实现可以替换，各类的日志处理方式也保持统一。Spring Boot 3.x 的默认组合就是 SLF4J 2.x 门面 + Logback 1.4/1.5 实现，通常不需要额外配置；Log4j 1.x 已停止维护（EOL），只作为“不要选它”的历史注脚存在。

与日志同类的还有 System.out.println：它没有级别、没有时间戳、没有上下文，在生产环境属于禁止项。临时调试用完就删，需要长期保留的信息一律落到日志门面。

第二，用占位符，别拼字符串。trace、debug、info 级别的输出必须使用条件输出形式或占位符方式。原因很实在：如果写成 log.debug("symbol: " + symbol)，即便当前级别是 warn、这条日志根本不会打印，字符串拼接依然会执行；symbol 是对象时还会调用 toString()，白白浪费资源。只有需要复杂计算时才用 isDebugEnabled() 包一层。

第三，分类与分级。扩展日志按 appName_logType_logName.log 命名，logType 可取 stats、desc、monitor、visit 等，logName 写日志描述，好处是看文件名就知道它属于哪个应用、什么类型、什么目的。错误日志与业务日志分开存放，便于查看和监控。

日志文件建议至少保存 15 天，因为有些异常以“周”为频次发生。生产环境禁止输出 debug 日志，有选择地输出 info；用户输入参数错误适合用 warn 记录；error 只记录系统逻辑出错、异常这类重要信息。日志重复打印的根因是 appender 的叠加，在 Logback 里等价于把 logger 的 additivity 设为 false（<logger name="..." additivity="false">），log4j2 同理；Log4j 1.x 时代的 log4j.xml 配置方式已随实现一起过时，Spring Boot 3.x 项目的配置文件是 logback-spring.xml。

private static final Logger log = LoggerFactory.getLogger(OrderService.class);

public Order findById(Long id) {
    // 只是简单参数，用占位符即可，不拼接字符串
    log.debug("查询订单, id={}", id);

    // 需要组装复杂信息时才判断级别，避免无谓计算
    if (log.isDebugEnabled()) {
        log.debug("查询订单详情, id={}, trace={}", id, buildTrace());
    }

    try {
        return orderDao.selectById(id);
    } catch (DAOException e) {
        // 带上参数，保护案发现场；异常对象放最后一个参数，保留完整堆栈
        log.error("查询订单失败, id={}", id, e);
        throw new OrderQueryException("查询订单失败, id=" + id, e);
    }
}

五、现代 Java 写法：Optional、Stream、var 与字符串取舍

语言本身在往前跑，很多曾经要靠约定维持的写法已经有了更好的替代。Java 17 是当前的长期支持版本，下面四条是日常最常遇到的取舍。

Optional 用来表达“这里可能没有”，不是用来替代一切 null。它最适合做方法的返回值，让“可能为空”成为签名的一部分；不适合做字段、方法参数或放进集合，那只会多一层包装。取值时用 orElse / orElseGet / orElseThrow 给出兜底策略，而不是 get()——Optional.get() 为空时照样抛 NoSuchElementException，等于换个名字的 NPE。还要注意 orElse 的实参无论是否命中都会先求值，带副作用的兜底必须用 orElseGet(Supplier)。

Stream 适合“转换—过滤—收集”这类无状态流水线。集合的遍历与变换优先用 Stream，代码更短也更难写出下标越界；但不要为了用而用：需要下标、需要提前跳出、需要复用中间变量时，普通 for 循环反而更清楚。流里要保持无副作用，在 forEach 中修改外部集合一类写法应当避免；耗时较长的流处理（尤其并行流）不要占用 Web 请求线程，IO 密集任务交给线程池，并行流默认用的是公共 ForkJoinPool。

// 传统写法：多层判空 + 手工收集
public List<String> activeNames(List<User> users) {
    List<String> result = new ArrayList<>();
    if (users != null) {
        for (User user : users) {
            if (user != null && user.isActive()) {
                String name = user.getName();
                if (name != null && !name.isEmpty()) {
                    result.add(name.trim());
                }
            }
        }
    }
    return result;
}

// 现代写法：用 Stream 表达“过滤 + 映射 + 收集”，用 Optional 兜住单值缺失
public List<String> activeNames(List<User> users) {
    return Optional.ofNullable(users).orElseGet(List::of).stream()
            .filter(Objects::nonNull)
            .filter(User::isActive)
            .map(User::getName)
            .filter(StringUtils::hasText)
            .map(String::trim)
            .toList();                      // Java 16+ 的 Stream.toList()
}

// 单值场景：把“可能没有”写进返回值，而不是返回 null
public Optional<User> findById(Long id) {
    return Optional.ofNullable(userDao.selectById(id));
}

// 调用方：有副作用的兜底要用 orElseGet，否则无论命中与否都会执行
User user = userService.findById(id)
        .orElseGet(() -> User.guest());

var 的适用范围很窄：只用于局部变量，且右边必须自解释。Java 10 引入局部变量类型推断，var 不是动态类型，编译期类型就已固定。它可以用在局部变量声明、for / for-each 的循环变量、try-with-resources 的资源和 lambda 参数（需显式标注类型时写 (var a, var b)）；不能用于字段、方法参数、返回值类型，也不能写 var x = null 或先声明后赋值。用与不用只有一条标准：读代码的人能否一眼看出类型——var orders = new HashMap<String, List<Order>>(); 右边已写全，用 var 只是省掉重复；而 var result = service.handle(request); 抹掉了关键信息，应当写出类型。团队若没有统一约定，把 var 限制在“右侧构造函数或静态工厂显式给出类型”的场景最安全。

String.format 还是字符串拼接？按场景选：一两段拼接直接用 + 更易读（Java 9 起 + 由 invokedynamic / StringConcatFactory 实现，不必再担心早期版本循环拼接的性能问题）；需要统一格式（补零、金额、日期模板）或文案要抽到常量与配置文件时用 String.format，代价是每次调用都要解析格式串，所以别放进热点循环；循环里累积文本用 StringBuilder，拼接集合元素用 String.join。日志输出永远优先占位符 log.info("id={}, name={}", id, name)，而不是先格式化再传字符串——级别关闭时占位符不产生格式化开销。

// 好：简单拼接 + 日志占位符
String key = "order:" + orderId;
log.info("订单已创建, id={}, amount={}", orderId, amountFen);

// 好：格式模板集中管理（补零、金额展示）
private static final String ORDER_NO_FORMAT = "TW%08d";
String orderNo = String.format(ORDER_NO_FORMAT, seq);

// 不好：热点循环里反复 format；日志里先拼好再传
for (Order order : orders) {
    log.debug("处理订单 " + order.getId());     // 级别关闭时拼接照样执行
}
// 改成
for (Order order : orders) {
    log.debug("处理订单, id={}", order.getId());
}

六、异常规范：不吞、不滥用、分层兜底

异常处理写不好，往往比不处理更危险，因为它会把故障现场悄悄抹掉。不要大段代码 try-catch。把一大段代码整体包进 try 里是不负责任的做法。catch 时要分清稳定代码与非稳定代码。稳定代码指无论如何都不会出错的代码，例如纯内存计算、已校验过的参数拼接；只把真正非稳定的部分（IO、网络、数据库、第三方调用）包住，并尽可能区分异常类型，分别做对应处理。

不要吞异常。catch 之后什么都不做，等于把现场销毁。至少要记录日志，或转换成业务异常继续向上传递，并且必须保留原始异常作为 cause，例如 throw new OrderQueryException(msg, e)。如果不带 e，异常链就断了，排查时只剩一句“查询失败”，看不到根因。还有两种“看起来很勤快、其实在销毁现场”的写法要一并清掉：e.printStackTrace()（输出到标准错误流，绕过日志配置，生产环境等于丢失现场且污染容器输出）应改为 log.error("...", e)；catch (Exception e) {} 这类只 catch 不处理则属于上面说的“吞异常”。不要用异常做流程控制。异常的代价主要在构造时填充堆栈信息，把它当 if-else 使用既慢又难读。

资源必须释放，底层异常不要外泄。优先使用 try-with-resources（JDK 7 引入 AutoCloseable 后成为标准写法，JDK 9 起还可以在括号里复用已声明的 effectively final 变量），由编译器生成关闭逻辑。沿用 finally 手工关闭时，不要在 finally 里 return，因为这会吞掉 try 中尚未抛出的异常。对外接口也不要直接抛 SQLException、IOException 这类底层异常，那会让调用方被迫依赖你的具体实现，应转换成自定义业务异常（类名以 Exception 结尾）再抛出。异常消息本身用字符串拼接通常无伤大雅（异常只在出错路径上构造），但拼进 log.error 就回到上一节的占位符问题：日志参数一律交给 {}，只有异常对象放最后一个参数。

七、小结

本章收束成六条约定。重构是在不改变可观察行为的前提下降低修改成本，用三次法则决定时机，小步加测试保证安全，改动已发布接口要保留旧接口并标记 @Deprecated。命名与分层是最廉价的可读性投入，靠 get/list/count 与 DO/DTO/VO 这类约定让代码自解释；坏味道出现时用提炼函数、以查询取代临时变量等手法小步改掉。日志要用 SLF4J 门面、占位符与明确的分级分类；异常要小范围捕获、区分类型、带上原始 cause，分层兜底而不是层层重复打印。现代写法这四条同样是约定的一部分：Optional 只做返回值、Stream 只在表达力更强时用、var 以“类型自解释”为界、格式化在 + / format / StringBuilder 之间按场景选。把这六件事固定成团队约定，代码才会越改越顺，而不是越改越贵。下一章回到 JVM，从运行时数据区开始，看这些代码在虚拟机里究竟落在哪块内存。
