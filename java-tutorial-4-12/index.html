4.12 Dubbo 与 RPC

Posted on 2024-09-28，9 min read

前面几章一直在写 Spring Boot 应用，代码越写越多，却始终跑在一个进程里：改一个订单模块，整个应用都要重新发布；订单模块的流量涨了十倍，只能把整个应用一起扩容。把系统拆成若干独立的服务，是绕不过去的一步。可拆分之后，第一个问题就来了：原来一行 orderService.getById(1L) 就能拿到的数据，现在这段代码跑在另一台机器上，要如何调用它？本章就从这个疑问出发，讲清 RPC 的原理、Dubbo 的架构与一次远程调用的完整链路，再用一个最小示例把它真正跑起来，最后给出 Dubbo 与 Spring Cloud 的选型建议。适合已经会用 Spring Boot、正准备做服务拆分的读者。

一、RPC：让远程调用看起来像本地调用

本地方法调用之所以简单，是因为调用方和被调用方在同一个地址空间里：编译器把方法地址写进指令，CPU 跳过去执行就行。一旦跨进程、跨机器，“跳过去”这件事就没了，只剩下一条能传字节的网络连接。RPC（Remote Procedure Call，远程过程调用）要做的，就是把这条字节流包装得足够像一次本地调用。

拆开看，一个 RPC 框架至少要解决四件事。

第一是代理。只声明接口、不写实现类时，调用方拿到的其实是一个由框架生成的“桩”（stub）。它用 JDK 动态代理或字节码生成技术实现同一个接口，方法一旦被调用就被拦截下来，转而组装请求参数，而不是真的执行业务逻辑。这就是“像本地调用”的来源——语法上确实是接口方法调用，语义上已经被换成了网络操作。

第二是序列化。参数对象在内存里是对象，出了网卡必须是字节。把对象转成字节叫序列化，转回来叫反序列化。Dubbo 的 dubbo 协议默认使用 Hessian2，也可以换成 Fastjson2、Kryo、Protobuf 等。序列化决定了跨语言能力与报文大小，是 RPC 性能的关键一环。

第三是传输。客户端把请求写到连接上，服务端解码、按接口名和方法名找到实现类、反射执行，再把返回值沿同一条链路写回。这一层要处理粘包拆包、超时、心跳、线程模型，是框架最“重”的部分。

第四是寻址。服务提供者的地址会变：上线、下线、扩容、机房迁移。所以调用方不能把地址写死在配置里，而要向注册中心订阅地址列表，并在每次调用前按负载均衡算法挑一台。

这里要纠正一个常见的误解：RPC 不是某一个具体协议，而是一套“调用语义 + 治理能力”的抽象。Dubbo 底层可以挂载 dubbo、rmi、hessian、http、rest、grpc 等多种协议。所以“用 Dubbo 就等于二进制长连接”并不准确——dubbo 协议默认是单连接长连接，但 hessian、rmi、http 等协议走的是短连接。

与 REST 风格对比：Dubbo 这类二进制 RPC 报文小、连接复用率高、自带服务治理，但要求调用双方共享同一份接口定义（通常是同一个 API 依赖包），耦合更紧。HTTP + JSON 更通用、跨语言、易调试，代价是报文体积和解析开销更大。两者不是替代关系，而是“内部高频调用”与“对外开放接口”的分工。

二、Dubbo 的角色与一次调用的完整链路

Dubbo 的架构只有五个角色，记住它们，整套框架就好理解了：

  • Provider：暴露服务的提供方；
  • Consumer：调用远程服务的消费方；
  • Registry：服务注册与发现的注册中心；
  • Monitor：统计调用次数与调用耗时的监控中心；
  • Container：服务运行容器，负责启动、加载、运行 Provider。

一次服务的完整生命周期按官方定义的 0～5 步走：

  1. 容器启动并加载 Provider；
  2. Provider 启动时向注册中心注册自己提供的服务；
  3. Consumer 启动时向注册中心订阅自己需要的服务；
  4. 注册中心把提供者地址列表返回给 Consumer，并在地址变更时基于长连接推送新列表；
  5. Consumer 从地址列表中按软负载均衡算法选一台调用，失败则换一台重试；
  6. Consumer 与 Provider 各自在内存中累计调用次数和耗时，定时每分钟上报给监控中心。

这段流程里有三个容易被忽略的细节。其一，地址推送是基于长连接的订阅机制，而不是消费方定时轮询，因此服务上下线能在秒级感知。其二，Consumer 会把地址列表缓存在本地，注册中心整体故障时已有调用关系仍然可用，这正是“注册中心宕机不等于系统不可用”的原因。其三，失败换一台重试属于集群容错（Failover），不是负载均衡本身；负载均衡只负责“选哪一台”，重试是选失败之后的补救动作。

如果用 ZooKeeper 作注册中心，服务信息是一棵目录树，路径形如 /dubbo/com.example.order.api.OrderService/providers、/consumers、/routers、/configurators。提供者启动时在 providers 下创建临时节点，进程异常退出后会话超时，节点被 ZooKeeper 自动删除，消费方随即收到变更，服务由此自动下线。

注册中心的选型绕不开 CAP：ZooKeeper 遵循 CP，网络分区时可能短暂拒绝服务；Eureka 遵循 AP；Nacos 的临时实例走 Distro 协议（AP），持久实例走 Raft（CP）。对服务发现而言，可用性通常比强一致更重要，所以 Dubbo 也支持 Nacos 作为注册中心，配置写法是 dubbo.registry.address=nacos://127.0.0.1:8848。

三、动手：一个最小的 Dubbo 服务

工程上建议拆成三个 Maven 模块：order-api 只放接口和 DTO，order-provider 与 order-consumer 都依赖它。三个模块必须引用同一版本的 api 包，这是 Dubbo 项目最容易踩的坑，后面还会细说。下面基于 Spring Boot 与 Dubbo 3.x 演示，注意包名已是 org.apache.dubbo。

先写接口和实现。接口在 api 模块，实现类放在 provider 模块，用 @DubboService 暴露服务并声明版本号：

// order-api：只有接口，没有实现
package com.example.order.api;

public interface OrderService {
    OrderDTO getById(Long id);

    // DTO 必须实现 Serializable，字段省略
    class OrderDTO implements java.io.Serializable {
        private Long id;
        private String status;
        public Long getId() { return id; }
        public void setId(Long id) { this.id = id; }
        public String getStatus() { return status; }
        public void setStatus(String status) { this.status = status; }
    }
}

// order-provider：实现并暴露服务
package com.example.order.provider;

import com.example.order.api.OrderService;
import org.apache.dubbo.config.annotation.DubboService;

@DubboService(version = "1.0.0", timeout = 3000, retries = 0)
public class OrderServiceImpl implements OrderService {

    @Override
    public OrderDTO getById(Long id) {
        OrderDTO dto = new OrderDTO();
        dto.setId(id);
        dto.setStatus("PAID");
        return dto;
    }
}

provider 的配置文件里要声明应用名、注册中心、协议，以及注解扫描的包路径。扫描包配错时服务不会报错，只是“注册不上”，排查起来很费时间：

# order-provider/src/main/resources/application.yml
dubbo:
  application:
    name: order-provider
  registry:
    address: zookeeper://127.0.0.1:2181
    # 本地联调时注册中心未就绪也不阻塞启动
    check: false
  protocol:
    name: dubbo
    port: 20880
  scan:
    base-packages: com.example.order.provider

# 消费方换成 application.name: order-consumer，其余一致

消费方用 @DubboReference 注入接口。注意它注入的不是 Spring 容器里的 Bean，而是框架生成的代理对象，因此同一个接口在消费方不需要任何实现类：

package com.example.order.consumer;

import com.example.order.api.OrderService;
import org.apache.dubbo.config.annotation.DubboReference;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class OrderController {

    @DubboReference(version = "1.0.0", loadbalance = "leastactive")
    private OrderService orderService;

    @GetMapping("/order/{id}")
    public OrderService.OrderDTO order(@PathVariable Long id) {
        return orderService.getById(id);
    }
}

依次启动 ZooKeeper（或 Nacos）、provider、consumer，访问 http://localhost:8080/order/1 就能拿到结果。再用 dubbo-admin 查看服务列表，可以看到 OrderService 的提供者与消费者、版本号和地址。请特别注意：老教程里常见的 com.alibaba 依赖坐标、@Service / @Reference 注解和 code.alibabatech.com 的 XML 命名空间，从 Dubbo 2.7 起都已迁移到 org.apache.dubbo 与 dubbo.apache.org。照抄旧文档会直接启动失败。

四、负载均衡、集群容错与 SPI 扩展

服务提供者通常不止一台，Dubbo 内置了五种负载均衡策略，通过 loadbalance 属性或 @DubboReference(loadbalance = "random") 指定：

  • random：默认值，按权重随机，调用量越大分布越均匀；
  • roundrobin：按权重轮询，但慢节点会积压请求；
  • leastactive：优先选活跃调用数最少的节点，能让慢机器少接活，是实战中较稳的选择；
  • consistenthash：让相同参数始终落到同一台机器，适合带本地缓存或有状态的服务；
  • shortestresponse：选预估响应最快的节点，但它在统计窗口内可能把流量集中到个别节点。

集群容错策略由 cluster 属性决定：

  • failover：默认值，失败后换一台重试，默认 retries=2，也就是最多请求三次；
  • failfast：失败立即报错，适合非幂等的写操作；
  • failsafe：出现异常直接返回空结果，适合写审计日志这类不影响主流程的调用；
  • failback：失败后记录并定时重发；
  • forking：并行调用多台、取最先返回的结果，代价是资源成倍消耗；
  • broadcast：广播给所有提供者，常用于刷新本地缓存。

这里有一个必须记住的结论：failover 的 retries 默认是 2，意味着一次调用可能被执行三次。如果服务端方法不是幂等的（比如“扣减库存”），重试会造成重复扣减。正确做法是在提供者上对写接口显式设置 retries = 0，并由业务侧做幂等（唯一流水号、去重表）。超时同理，默认 timeout=1000 毫秒，超过就抛 TimeoutException 并触发重试，慢接口务必按 P99 调大该值，否则会出现“服务端还在执行、客户端已重试”的重复调用。

Dubbo 的扩展能力由 SPI 机制提供。它与 JDK 自带的 SPI 有三个明显区别：

  • 按需加载：JDK SPI 会一次性实例化所有实现，Dubbo 则用 ExtensionLoader 按名字取用；
  • 支持 IoC 与 AOP：扩展点可以直接注入其他扩展；
  • 支持 Adaptive 自适应：通过 @SPI、@Adaptive、@Activate 注解，在运行时根据 URL 参数决定用哪个实现。

自定义扩展的配置文件放在 META-INF/dubbo/ 目录下（框架内部的扩展放在 META-INF/dubbo/internal/），内容是“名字=实现类全限定名”。正因为所有协议、序列化、负载均衡、注册中心都是扩展点，Dubbo 才能做到“换个注册中心只改一行配置”。

五、Dubbo 与 Spring Cloud 怎么选，以及常见坑

两者的定位并不对等。Dubbo 是服务间调用的 RPC 框架，核心是高性能通信与内置的负载均衡、容错、路由、限流降级等治理能力。Spring Cloud 则是微服务解决方案的集合，它用 Spring Boot 把配置中心、网关、服务发现、熔断、链路追踪等成熟组件封装成一套开箱即用的技术栈。一句话概括：Dubbo 精于“服务怎么调”，Spring Cloud 长于“微服务体系怎么搭”。

网上流传的一些对比结论已经过时，需要纠正。第一，“Spring Cloud 的注册中心只能用 Eureka 或自研”不成立：Consul、ZooKeeper、Etcd、Nacos 都有官方或成熟的集成。Spring Cloud Netflix 早已进入维护模式，Eureka 2.x 也已停止开发，生产环境更常见的是 Nacos 或 Consul。第二，“Dubbo 已停止维护、无人接管”的说法同样是老黄历。Dubbo 在 2017 年 7 月恢复维护，2018 年捐给 Apache 基金会，2019 年成为 Apache 顶级项目，2.7 与 3.x 版本持续迭代，包名也从 com.alibaba 迁移到 org.apache.dubbo。第三，“Dubbo 只能长连接”不准确，见前文的协议部分。

真正需要权衡的是这几点：

  • 通信方式：Dubbo 默认二进制长连接、性能好，适合内部高频小报文调用；Spring Cloud 默认 HTTP + JSON，通用、易调试、跨语言友好，但报文更大。
  • 接口约束：Dubbo 依赖共享 API 包，天然强约束接口，升级时要协调版本；Spring Cloud 靠 URL 约定，松散但容易失控。
  • 生态完整度：需要配置中心、网关、链路追踪时，Spring Cloud 集成成本更低；Dubbo 则要自行拼装，或与 Spring Cloud Alibaba 组合使用。

实践中常见的形态是“Spring Cloud Alibaba + Nacos + Dubbo”：注册与配置交给 Nacos，服务间调用交给 Dubbo。此外，Dubbo 3.x 推出的 Triple 协议基于 HTTP/2，兼容 gRPC，可穿透网关并支持跨语言，正在弥合两者的边界。

最后是几个高频踩坑点：

  • 接口包版本不一致是最常见的事故源：provider 与 consumer 引用了不同版本的 api 包，轻则反序列化失败，重则 NoSuchMethodError，多模块工程应统一用 BOM 管理版本；
  • 非幂等接口开启重试会导致数据重复；
  • 超时设置过小会引发无效重试与雪崩；
  • 只暴露接口不暴露实现（api 包里带了实现类）会造成类冲突；
  • @DubboService 扫描包配错则表现为服务启动成功但注册不上，应先用 dubbo-admin 确认服务是否出现在注册中心，再回头查配置。

小结

RPC 的本质是把“方法调用”编码成“字节流传输”，再用代理、序列化、传输、寻址四件事把细节藏起来。Dubbo 用 Provider、Consumer、Registry、Monitor、Container 五个角色，串起服务的注册、订阅、调用与监控。负载均衡、集群容错与 SPI 扩展在它这里都是可插拔的能力。选型时不必陷入框架之争：Dubbo 擅长服务间的高性能调用与治理，Spring Cloud 擅长提供一整套微服务基础设施，二者可以组合使用。写代码时优先记住两条铁律——api 包保持同一版本，非幂等接口关闭重试。
