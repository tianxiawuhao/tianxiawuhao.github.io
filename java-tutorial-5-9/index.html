文件上传下载

Posted on 2026-09-19，7 min read

文件上传看着只是「把文件从浏览器送到服务器」，落到工程里却会牵出三条不同的技术路线：小文件用表单直传，大文件必须切片加断点续传，海量文件则要交给对象存储。本章按这三条路线展开。先讲清 multipart 请求长什么样，以及 Servlet 端怎么解析；再讲大文件为什么必须切片、切片如何还原、断点记录存在哪里；最后对比 MinIO、OSS、七牛云这类对象存储的接入与选型。适合会写 Servlet、Spring Boot 接口但还没系统处理过上传需求的读者。

一、上传请求为什么不能当普通表单处理

普通表单把字段拼成 a=1&b=2 的键值对，服务端用 request.getParameter() 就能取值。文件是二进制数据，塞不进这种文本编码，于是改用 multipart/form-data：浏览器把请求体切成若干段，段间用 --boundary 分隔，每段先写 Content-Disposition 头说明属于哪个字段、文件名是什么，空行之后才是数据。因此一个上传请求里同时装着普通字段和文件字节流。

要触发这种编码，表单必须同时满足三个条件：提交方式为 post；enctype 必须是 multipart/form-data（不写则默认只传一个文件名）；<input type="file"> 必须带 name，否则浏览器根本不发送该字段。

<form action="/upload" method="post" enctype="multipart/form-data">
  <input type="file" name="file">
  <input type="submit" value="上传">
</form>

正因为请求体是 MIME 分段结构，直接读 request.getInputStream() 手工切分非常痛苦。Servlet 3.0（2009 年）之前，唯一的通用解法是引入 Apache Commons FileUpload；此后容器把 multipart 解析内置了，request.getPart() 就能直接拿到文件。所以下面先讲旧式写法，再讲现行写法——两段代码都值得会读，因为前者在老系统里仍大量存在。

二、Servlet 端接收：从 Commons FileUpload 到原生 Part

旧式写法：工厂 + 解析器两步走（老系统仍在用）

Commons FileUpload 的现行版本是 1.5 / 1.6（2023 年以后），它从 1.1 起依赖 commons-io，两个 jar 都要引入。用法是固定的四步：先建 DiskFileItemFactory 设置缓冲区大小和临时目录，再用它构造 ServletFileUpload 并设置大小限制，然后 parseRequest() 拿到 List<FileItem>，最后逐个判断 isFormField()——true 是普通字段，false 才是文件。sizeThreshold 决定「小于阈值留内存、超过则落临时文件」，默认只有 10K，实际项目一般调到 1MB 左右。这段代码里的 javax.servlet 包名在 Tomcat 10+ 已改为 jakarta.servlet，迁移时只换 import。

@WebServlet("/upload")
public class UploadServlet extends HttpServlet {

    private final File repoDir = new File("/data/upload");

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        // 不是 multipart 请求就直接拒绝，避免解析器抛异常
        if (!ServletFileUpload.isMultipartContent(req)) {
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "not multipart");
            return;
        }
        DiskFileItemFactory factory = new DiskFileItemFactory();
        factory.setSizeThreshold(1024 * 1024);                                  // 超过 1MB 落临时文件
        factory.setRepository(new File(System.getProperty("java.io.tmpdir")));  // 临时目录
        ServletFileUpload upload = new ServletFileUpload(factory);
        upload.setHeaderEncoding("UTF-8");         // 解决中文文件名乱码
        upload.setFileSizeMax(100L * 1024 * 1024); // 单文件上限 100MB
        upload.setSizeMax(500L * 1024 * 1024);     // 整个请求上限 500MB

        try {
            List<FileItem> items = upload.parseRequest(req);
            for (FileItem item : items) {
                if (item.isFormField()) {
                    System.out.println(item.getFieldName() + " = " + item.getString("UTF-8"));
                    continue;
                }
                // 用 UUID 前缀保证文件名唯一，防止同名覆盖
                String name = UUID.randomUUID() + "-" + FilenameUtils.getName(item.getName());
                item.write(new File(repoDir, name));  // 流式写入，不在内存里拼 byte[]
            }
            resp.getWriter().write("ok");
        } catch (Exception e) {
            throw new ServletException("upload failed", e);
        }
    }
}

现行写法：Servlet 3.0+ 原生 Part（Tomcat 10+ 用 jakarta.servlet）

从 Servlet 3.0 起容器自己就会解析 multipart，只需在 Servlet 上声明 @MultipartConfig，再用 request.getPart(字段名) 取文件，不必再引第三方解析库。下面这段同时处理了本章最容易出事的一点：文件名来自客户端，永远不可信。它可能包含 ../、Windows 的 ..\、绝对路径甚至空字节，直接拼进 new File(dir, name) 就能写到目录之外，这就是路径穿越（Path Traversal）。正确做法是只取文件名部分、再做规范化，并校验最终路径仍落在仓库目录内。

@WebServlet("/upload")
@MultipartConfig(
        fileSizeThreshold = 1024 * 1024,      // 超过 1MB 落磁盘临时文件
        maxFileSize = 100L * 1024 * 1024,     // 单文件上限 100MB，默认 -1 即不限
        maxRequestSize = 500L * 1024 * 1024,  // 整个 multipart 请求上限
        location = "/data/tmp")               // 临时目录，必须容器可写
public class UploadServlet extends HttpServlet {

    private static final Path REPO = Path.of("/data/upload").toAbsolutePath().normalize();

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        Part part = req.getPart("file");     // 参数是表单字段名，不是文件名
        if (part == null) {
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "missing file");
            return;
        }
        // getSubmittedFileName() 完全由客户端提供，先剥离目录再规范化
        String raw = part.getSubmittedFileName();
        String name = Path.of(raw == null ? "" : raw).getFileName().toString();
        if (name.isBlank() || name.contains("..")) {
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "bad filename");
            return;
        }
        Path target = REPO.resolve(UUID.randomUUID() + "-" + name).normalize();
        if (!target.startsWith(REPO)) {      // 双保险：规范化后仍须落在仓库内
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "path traversal");
            return;
        }
        Files.createDirectories(REPO);
        try (InputStream in = part.getInputStream()) {
            Files.copy(in, target, StandardCopyOption.REPLACE_EXISTING);
        } finally {
            part.delete();                   // 清理容器落下的临时文件，要在流关闭之后
        }
        resp.getWriter().write("ok");
    }
}

几个版本细节要留意：Part.getSubmittedFileName() 是 Servlet 3.1 才加入的，Servlet 3.0 时代只能自己解析 Content-Disposition 头；Part.getName() 返回的是字段名而非文件名，别把两者搞混。请求超过 maxFileSize / maxRequestSize 时容器会抛 IllegalStateException（Tomcat 常表现为 500 或 413），要在过滤器或 @ControllerAdvice 里翻译成友好错误，而不是让它冒到用户面前。

Spring Boot 3.x：MultipartFile 与上限配置

Spring Boot 里不必手工解析，用 MultipartFile 接收即可，底层走的就是上面那套容器原生解析。同样地，getOriginalFilename() 返回的是客户端字符串，不能直接当路径用：要么经 Paths.get(name).getFileName() 清洗，要么干脆忽略原名、只用自己生成的 UUID 落盘，把原名存进数据库供展示。上限在 application.yml 里配置：

spring:
  servlet:
    multipart:
      max-file-size: 100MB        # 单文件上限，默认 1MB
      max-request-size: 500MB     # 整个请求上限，默认 10MB
      file-size-threshold: 1MB    # 超过阈值落磁盘，默认 0 表示一律落盘
      location: /data/tmp         # 临时目录，不配则用容器默认

内嵌 Tomcat 还有两个容易混淆的开关：server.tomcat.max-post-size（默认 2MB）管的是 application/x-www-form-urlencoded 的请求体，对 multipart/form-data 不生效——上传上限以 max-file-size / max-request-size 为准；server.tomcat.max-swallow-size（默认 2MB）决定请求被拒后容器愿意读掉多少剩余字节，它小于 max-request-size 时超限请求会直接断连而不是返回 413，排错时要一起看。反向代理另有 nginx 的 client_max_body_size，链路上任何一环截断，前端看到的都是失败。

下载：把文件流写回响应

下载只需设置 Content-Disposition: attachment 响应头，再把文件流拷进 response.getOutputStream()。中文名不要再写成 filename=URLEncoder.encode(name)——+ 号与百分号大小写会让部分浏览器解码失败，现行做法是按 RFC 5987/6266 写成 filename*=UTF-8''%E4%B8%AD%E6%96%87.pdf（URLEncoder.encode(name, StandardCharsets.UTF_8) 之后把 + 换成 %20），并同时给一个纯 ASCII 的 filename 兜底。

三、大文件：切片上传与断点续传

把 100MB 塞进一个请求，问题不只是慢：上传越久丢包重传概率越高，失败就得从头再来；用户看不到进度，也不敢刷新；nginx 默认还会以 413 Request Entity Too Large 直接拒掉（需调 client_max_body_size）。思路是把一个请求拆成多个：前端用 Blob.slice() 把文件切成固定大小的分片（File 继承自 Blob，文件对象本身就有 slice 方法），逐片上传，服务端按序拼回。单片失败只重传那一片，进度也天然可以按「已完成片数 / 总片数」计算。

要能正确还原，每个分片请求至少带三个信息：文件唯一标识（context）、分片序号、总分片数。context 可以用「文件名 + 大小 + 修改时间」拼出来，成本极低；也可以算内容哈希，更可靠但大文件计算量大。最关键的一点是合并时必须按序号排序后再追加，绝不能依赖请求到达顺序——并发上传时到达顺序本来就是乱的。

const CHUNK = 5 * 1024 * 1024; // 每片 5MB

function slice(file, size = CHUNK) {
  const chunks = [];
  let start = 0;
  while (start < file.size) {          // 注意是 file.size，不是 file.length
    chunks.push(file.slice(start, start + size));
    start += size;
  }
  return chunks;                        // 必须返回结果，否则调用方拿不到分片
}

// 文件级唯一标识：名称 + 大小 + 修改时间
const context = `${file.name}-${file.size}-${file.lastModified}`;
const chunks = slice(file, CHUNK);
const uploaded = new Set(JSON.parse(localStorage.getItem(context) || "[]"));

const tasks = chunks.map((blob, index) => {
  if (uploaded.has(index)) return Promise.resolve();   // 已传过的分片跳过
  const fd = new FormData();
  fd.append("context", context);
  fd.append("chunk", index);                            // 分片序号，合并时按它排序
  fd.append("total", chunks.length);
  fd.append("file", blob);
  return fetch("/upload/chunk", { method: "POST", body: fd }).then(() => {
    uploaded.add(index);
    localStorage.setItem(context, JSON.stringify([...uploaded]));  // 记进度，支持断点续传
  });
});

Promise.all(tasks).then(() => fetch("/upload/merge", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ context, total: chunks.length })
}));

断点续传的本质就是「记录已成功的分片，下次只传没传过的」。记录可放 localStorage（简单，清缓存即失效），也可放服务端（可靠、可跨设备，多一个查询接口）。服务端一般把分片先落到 context 目录，收到 merge 后按序号拼接并清理分片。别忘了给分片设有效期：客户端一直不调合并接口时，这些碎片必须被定时清理，否则磁盘会被垃圾分片吃满。

四、文件最终放哪里：本地目录还是对象存储

单机部署写本地目录可行，但要做到三点：

  • 存储目录不能位于 Web 容器可直接访问的路径下，否则能绕过鉴权直接下载；
  • 文件名必须唯一，用 UUID 或哈希生成；
  • 按日期或哈希打散到多级子目录，因为单目录文件上千后查找和列目录性能会明显下降。

一旦有多台应用服务器，本地目录立刻失效：A 机上传、请求被负载均衡打到 B 机就会 404。这时要把文件抽成独立存储层。

选型上，FastDFS 是轻量级专用分布式文件系统，对文件不分块（因此没有分片合并开销），适合图片等小文件。HDFS 则相反，靠牺牲延迟换吞吐，适合批量大文件。MinIO 兼容 S3 协议，通用性好、部署简单，大文件用 putObject 会自动分片。需要精细控制时，可用 createMultipartUpload、uploadPart、completeMultipartUpload 手动完成，本质与前端切片是同一套模型。云服务（阿里 OSS、七牛云、腾讯云）接口风格类似，都提供 SDK、断点续传和直传凭证，业务侧只保存 object key，因此建议从第一天起就按「库里只存 key、访问时拼 URL」设计，换存储实现时改动最小。

MinIO Java SDK 现行大版本为 8.x / 9.x（坐标 io.minio:minio），对超过 5MB 的对象 putObject 会自动切成 multipart 上传，业务代码不必自己切片；stream(in, size, -1) 的第三个参数是分片大小，-1 表示用默认值，只有在长度完全未知时才写成 stream(in, -1, 10L * 1024 * 1024) 并显式给出分片大小。阿里云 OSS、腾讯云 COS、AWS S3 除了各自 SDK，也提供 S3 兼容端点，基于 S3 API 写的代码基本可以平移，这正是本地用 MinIO、线上换云存储的常见做法。

// MinIO：accessKey / secretKey 必须来自配置或环境变量，绝不能硬编码进代码库
MinioClient client = MinioClient.builder()
        .endpoint("http://127.0.0.1:9000")
        .credentials(accessKey, secretKey)
        .build();

if (!client.bucketExists(BucketExistsArgs.builder().bucket("demo").build())) {
    client.makeBucket(MakeBucketArgs.builder().bucket("demo").build());
}

try (InputStream in = new FileInputStream("/data/a.png")) {
    client.putObject(PutObjectArgs.builder()
            .bucket("demo")
            .object("2024/06/uuid-a.png")   // 用日期前缀打散，object key 即唯一路径
            .stream(in, fileSize, -1)       // 长度未知时传 -1
            .contentType("image/png")
            .build());
}

五、常见坑与小结

最常踩的几处如下：

  • 文件名一律当不可信输入：MultipartFile.getOriginalFilename()、Part.getSubmittedFileName()、FileItem.getName() 都来自客户端，可能带 ../、绝对路径或空字节，必须只取 basename 再规范化校验，否则就是路径穿越漏洞；
  • 大小限制必须在服务端做（max-file-size / maxFileSize / setFileSizeMax），前端校验只是体验优化；
  • 中文名乱码：老写法靠 setHeaderEncoding("UTF-8")（Commons FileUpload 专用）或 request.setCharacterEncoding；Tomcat 10+ 的原生解析默认按 UTF-8 处理，一般不必再手工设置；
  • 超限请求前端只看到连接被重置而不是 413 时，检查 server.tomcat.max-swallow-size 是否小于 max-request-size，以及 nginx 的 client_max_body_size；
  • 临时文件必须调 FileItem.delete() 清理，且要在流关闭之后，否则文件被占用删不掉；
  • 只校验扩展名不可靠（后缀可以随便改），服务端要结合内容嗅探做类型与后缀白名单；
  • 上传前先判是否 multipart：老写法用 ServletFileUpload.isMultipartContent(req)，原生写法可检查 request.getContentType() 是否以 multipart/ 开头（Spring MVC 由 MultipartResolver 统一判断）；
  • AK/SK 与 uploadToken 属于密钥，写死在源码里等同泄露，必须外置配置；
  • 合并要按序号排序，成功后清理分片目录。

另外，Commons FileUpload（1.5/1.6）、FastDFS 属于较早期的技术栈，新项目优先选云对象存储或 MinIO / S3 SDK v2（坐标 software.amazon.awssdk:s3），前端拿服务端签发的临时凭证直传，还能省掉一次中转带宽；上传成功后数据库只存 object key，把「文件」与「访问 URL」解耦。

小结：文件上传的复杂度不在「写文件」，而在请求格式、体积和存储位置这三件事。小文件用 multipart/form-data 加 MultipartFile 直传；大文件必须切片，用文件标识加分片序号保证可还原，用已传分片记录实现断点续传，并给分片设过期清理；文件量一大就交给对象存储，数据库只留 key。把这三层分清楚，上传功能基本就不会再出线上问题了。
