文件上传下载

Posted on 2026-09-19，7 min read

文件上传看着只是「把文件从浏览器送到服务器」，落到工程里却会牵出三条不同的技术路线：小文件用表单直传，大文件必须切片加断点续传，海量文件则要交给对象存储。本章按这三条路线展开：先讲清 multipart 请求长什么样、Servlet 端怎么解析；再讲大文件为什么必须切片、切片如何还原、断点记录存在哪里；最后对比 MinIO、OSS、七牛云这类对象存储的接入与选型。适合会写 Servlet / Spring Boot 接口、但还没系统处理过上传需求的读者。

一、上传请求为什么不能当普通表单处理

普通表单把字段拼成 a=1&b=2 的键值对，服务端用 request.getParameter() 就能取值。文件是二进制数据，塞不进这种文本编码，于是改用 multipart/form-data：浏览器把请求体切成若干段，段间用 --boundary 分隔，每段先写 Content-Disposition 头说明属于哪个字段、文件名是什么，空行之后才是数据。所以一个上传请求里同时装着普通字段和文件字节流。

要触发这种编码，表单必须同时满足三个条件：提交方式为 post；enctype 必须是 multipart/form-data（不写则默认只传一个文件名）；<input type="file"> 必须带 name，否则浏览器根本不发送该字段。

<form action="/upload" method="post" enctype="multipart/form-data">
  <input type="file" name="file">
  <input type="submit" value="上传">
</form>

正因为请求体是 MIME 分段结构，直接读 request.getInputStream() 手工切分非常痛苦，工程上统一交给 Apache Commons FileUpload 解析，它在 1.1 之后依赖 commons-io，两个 jar 都要引入。

二、Servlet 端接收：工厂 + 解析器两步走

用法是固定的四步：先建 DiskFileItemFactory 设置缓冲区大小和临时目录，再用它构造 ServletFileUpload 并设置大小限制，然后 parseRequest() 拿到 List<FileItem>，最后逐个判断 isFormField()——true 是普通字段，false 才是文件。sizeThreshold 决定「小于阈值留内存、超过则落临时文件」，默认只有 10K，实际项目一般调到 1MB 左右。

@WebServlet("/upload")
public class UploadServlet extends HttpServlet {

    private final File repoDir = new File("/data/upload");

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        // 不是 multipart 请求就直接拒绝，避免解析器抛异常
        if (!ServletFileUpload.isMultipartContent(req)) {
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "not multipart");
            return;
        }
        DiskFileItemFactory factory = new DiskFileItemFactory();
        factory.setSizeThreshold(1024 * 1024);                                  // 超过 1MB 落临时文件
        factory.setRepository(new File(System.getProperty("java.io.tmpdir")));  // 临时目录
        ServletFileUpload upload = new ServletFileUpload(factory);
        upload.setHeaderEncoding("UTF-8");         // 解决中文文件名乱码
        upload.setFileSizeMax(100L * 1024 * 1024); // 单文件上限 100MB
        upload.setSizeMax(500L * 1024 * 1024);     // 整个请求上限 500MB

        try {
            List<FileItem> items = upload.parseRequest(req);
            for (FileItem item : items) {
                if (item.isFormField()) {
                    System.out.println(item.getFieldName() + " = " + item.getString("UTF-8"));
                    continue;
                }
                // 用 UUID 前缀保证文件名唯一，防止同名覆盖
                String name = UUID.randomUUID() + "-" + FilenameUtils.getName(item.getName());
                item.write(new File(repoDir, name));  // 流式写入，不在内存里拼 byte[]
            }
            resp.getWriter().write("ok");
        } catch (Exception e) {
            throw new ServletException("upload failed", e);
        }
    }
}

Spring Boot 里不必手工解析，直接用 MultipartFile 接收即可，底层是同一套逻辑，spring.servlet.multipart.max-file-size 对应单文件上限。下载更简单：设置 Content-Disposition: attachment; filename=... 响应头，把文件流拷进 response.getOutputStream()，中文名做 URL 编码。

三、大文件：切片上传与断点续传

把 100MB 塞进一个请求，问题不只是慢：上传越久丢包重传概率越高，失败就得从头再来；用户看不到进度，也不敢刷新；nginx 默认还会以 413 Request Entity Too Large 直接拒掉（需调 client_max_body_size）。思路是把一个请求拆成多个：前端用 Blob.slice() 把文件切成固定大小的分片（File 继承自 Blob，文件对象本身就有 slice 方法），逐片上传，服务端按序拼回。单片失败只重传那一片，进度也天然可以按「已完成片数 / 总片数」计算。

要能正确还原，每个分片请求至少带三个信息：文件唯一标识（context）、分片序号、总分片数。context 可以用「文件名 + 大小 + 修改时间」拼出来，成本极低；也可以算内容哈希，更可靠但大文件计算量大。最关键的一点是合并时必须按序号排序后再追加，绝不能依赖请求到达顺序——并发上传时到达顺序本来就是乱的。

const CHUNK = 5 * 1024 * 1024; // 每片 5MB

function slice(file, size = CHUNK) {
  const chunks = [];
  let start = 0;
  while (start < file.size) {          // 注意是 file.size，不是 file.length
    chunks.push(file.slice(start, start + size));
    start += size;
  }
  return chunks;                        // 别忘了把结果返回出去
}

// 文件级唯一标识：名称 + 大小 + 修改时间
const context = `${file.name}-${file.size}-${file.lastModified}`;
const chunks = slice(file, CHUNK);
const uploaded = new Set(JSON.parse(localStorage.getItem(context) || "[]"));

const tasks = chunks.map((blob, index) => {
  if (uploaded.has(index)) return Promise.resolve();   // 已传过的分片跳过
  const fd = new FormData();
  fd.append("context", context);
  fd.append("chunk", index);                            // 分片序号，合并时按它排序
  fd.append("total", chunks.length);
  fd.append("file", blob);
  return fetch("/upload/chunk", { method: "POST", body: fd }).then(() => {
    uploaded.add(index);
    localStorage.setItem(context, JSON.stringify([...uploaded]));  // 记进度，支持断点续传
  });
});

Promise.all(tasks).then(() => fetch("/upload/merge", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ context, total: chunks.length })
}));

断点续传的本质就是「记录已成功的分片，下次只传没传过的」。记录可放 localStorage（简单，清缓存即失效），也可放服务端（可靠、可跨设备，多一个查询接口）。服务端一般把分片先落到 context 目录，收到 merge 后按序号拼接并清理分片。别忘了给分片设有效期：客户端一直不调合并接口时，这些碎片必须被定时清理，否则磁盘会被垃圾分片吃满。

四、文件最终放哪里：本地目录还是对象存储

单机部署写本地目录可行，但要做到三点：存储目录不能位于 Web 容器可直接访问的路径下（否则能绕过鉴权直接下载）、文件名必须唯一（UUID 或哈希）、按日期或哈希打散到多级子目录（单目录文件上千后查找和列目录性能明显下降）。一旦有多台应用服务器，本地目录立刻失效——A 机上传、请求被负载均衡打到 B 机就 404，于是要把文件抽成独立存储层。

选型上，FastDFS 是轻量级专用分布式文件系统，对文件不分块（因此没有分片合并开销），适合图片等小文件；HDFS 相反，靠牺牲延迟换吞吐，适合批量大文件；MinIO 兼容 S3 协议，通用性好、部署简单，大文件用 putObject 会自动分片，需要精细控制时用 createMultipartUpload / uploadPart / completeMultipartUpload 手动完成，本质与前端切片是同一套模型。云服务（阿里 OSS、七牛云、腾讯云）接口风格类似，都提供 SDK、断点续传和直传凭证，业务侧只保存 object key，因此建议从第一天起就按「库里只存 key、访问时拼 URL」设计，换存储实现时改动最小。

// MinIO：accessKey / secretKey 必须来自配置或环境变量，绝不能硬编码进代码库
MinioClient client = MinioClient.builder()
        .endpoint("http://127.0.0.1:9000")
        .credentials(accessKey, secretKey)
        .build();

if (!client.bucketExists(BucketExistsArgs.builder().bucket("demo").build())) {
    client.makeBucket(MakeBucketArgs.builder().bucket("demo").build());
}

try (InputStream in = new FileInputStream("/data/a.png")) {
    client.putObject(PutObjectArgs.builder()
            .bucket("demo")
            .object("2024/06/uuid-a.png")   // 用日期前缀打散，object key 即唯一路径
            .stream(in, fileSize, -1)       // 长度未知时传 -1
            .contentType("image/png")
            .build());
}

五、常见坑与小结

最常踩的几处：中文文件名乱码要靠 setHeaderEncoding("UTF-8") 或 request.setCharacterEncoding 解决；临时文件必须调 FileItem.delete() 清理，且要在流关闭之后，否则文件被占用删不掉；只校验前端传的扩展名不可靠，服务端要限制大小并做类型与后缀白名单；上传前先判 isMultipartContent；AK/SK 与 uploadToken 属于密钥，写死在源码里等同泄露，必须外置配置；合并要按序号排序，成功后清理分片目录。另外，Commons FileUpload、FastDFS 属于较早期的技术栈，新项目优先选云对象存储或 MinIO + S3 SDK，前端拿服务端签发的临时凭证直传，还能省掉一次中转带宽。

小结：文件上传的复杂度不在「写文件」，而在请求格式、体积和存储位置这三件事。小文件用 multipart/form-data 加 MultipartFile 直传；大文件必须切片，用文件标识加分片序号保证可还原，用已传分片记录实现断点续传，并给分片设过期清理；文件量一大就交给对象存储，数据库只留 key。把这三层分清楚，上传功能基本就不会再出线上问题了。
