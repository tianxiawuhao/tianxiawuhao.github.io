Docker 批量操作脚本

Posted on 2022-09-13，10 min read

批量操作容器的脚本几乎每个运维都写过，但绝大多数“踩坑事故”也都出在这里：变量取空导致误删、xargs 分词把镜像名拆散、prune 一把梭删光缓存。本文把常用的批量写法整理成可直接复制运行的脚本，并在每一处标出风险点。所有示例在 bash + Docker 20.10 及以上版本验证写法，镜像名与容器名请按自己的环境替换。

一、批量下载 Docker 镜像并批量导入导出到其它地方

起因：我需要下载一批镜像，但目标 Linux 机器无法访问外网，因此计划在另一台可访问外网的机器上完成全部镜像下载，再批量导出、导入到目标机器。

1、编写一个脚本 images.sh：

#!/bin/bash
# 批量拉取镜像清单，pull 失败的镜像会单独记录，便于重跑
set -uo pipefail

images=(
  docker.io/cockpit/kubernetes:latest
  docker.io/openshift/origin-haproxy-router:v3.11
  docker.io/openshift/origin-node:v3.11
  docker.io/openshift/origin-control-plane:v3.11
  docker.io/openshift/origin-deployer:v3.11.0
  docker.io/openshift/origin-pod:v3.11.0
  docker.io/openshift/origin-web-console:v3.11
  docker.io/openshift/origin-docker-registry:v3.11
  docker.io/openshift/origin-metrics-server:v3.11
  docker.io/openshift/origin-console:v3.11
  quay.io/coreos/etcd:v3.2.22
  quay.io/coreos/kube-state-metrics:v1.3.1
  quay.io/coreos/kube-rbac-proxy:v0.3.1
  docker.io/grafana/grafana:5.2.1
)

: > failed.txt
for imageName in "${images[@]}"; do
  echo "===== pulling $imageName ====="
  if ! docker pull "$imageName"; then
    echo "$imageName" | tee -a failed.txt
  fi
done

if [ -s failed.txt ]; then
  echo "以下镜像拉取失败，可重跑本脚本补齐："
  cat failed.txt
  exit 1
fi
echo "全部镜像拉取完成"

要点：for imageName in "${images[@]}" 必须给数组加双引号并写成 ${images[@]}，写成 ${images[*]} 或省略引号时镜像名一旦含空格就会被拆成多个参数；把失败项写入 failed.txt 后，重跑脚本即可补拉，不必从头再来。

2、授予执行权限：

chmod +x images.sh

3、执行脚本并打印日志，当然也可以直接执行：

bash images.sh 2>&1 | tee images.log
# 或后台执行并把标准输出、标准错误都写入日志
nohup ./images.sh > log.file 2>&1 &

下载完成后，用格式化输出核对镜像清单（比 grep -v REPOSITORY 过滤表头更可靠，也不会误伤名字里含 REPOSITORY 的镜像）：

docker images --format "table {{.Repository}}	{{.Tag}}	{{.ID}}	{{.Size}}"

4、一键导出所有镜像到 openshift.tar 包：

# 先把 “仓库:标签” 清单落盘，便于核对，也能复用到 docker save
docker images --format "{{.Repository}}:{{.Tag}}" | grep -v '^<none>' > image-list.txt
wc -l image-list.txt && head image-list.txt

# 再批量导出（参数用引号包裹，避免文件名含空格时被拆开）
docker save -o openshift.tar $(cat image-list.txt)

# 体积太大时压缩后再传输，通常能省一半以上
gzip -1 openshift.tar        # 生成 openshift.tar.gz

5、将 tar 包拷贝到目标服务器上，执行 load 导入命令：

scp openshift.tar.gz root@10.0.0.22:/opt/
# 目标机上导入：gzip 压缩包可直接交给 docker load，无需先解压
docker load -i openshift.tar.gz

# 导入后核对镜像是否齐全（与 image-list.txt 对比）
docker images --format "{{.Repository}}:{{.Tag}}" | sort > loaded.txt
sort image-list.txt | diff - loaded.txt && echo "镜像清单一致"

补充三点经验：docker save/load 会保留镜像的仓库名与标签，而 docker export/import 只导出容器文件系统、丢标签丢元数据，镜像搬家请用 save/load；导出前确认磁盘剩余空间至少是镜像总体积的 2～3 倍；docker save 不支持 --filter，需要“只导出某个仓库的镜像”时，只能先用 docker images --filter 生成清单再传给 save。

二、将当前运行状态的容器导出为镜像保存起来

起因：我通过官方教程快速部署了一个由一个容器协作支撑的平台。我需要修改前端页面，而成本高的方案是下载官方源码，重新改造、编译、打包镜像；那样太繁琐，于是我直接进入容器内部修改；运行正常后，把容器当前状态提交为自己的镜像保存下来，以后再部署就无需重新修改了。

# 建议同时写清作者与提交信息，方便日后回溯这次改动
docker commit -a "jgq" -m "modify frontend page" 163950a65bfb \
  registry.cn-hangzhou.aliyuncs.com/jgqk8s/jgq-console:v3.1.1

# 提交出的新镜像确认无误后，推送私有仓库
docker push registry.cn-hangzhou.aliyuncs.com/jgqk8s/jgq-console:v3.1.1

docker commit 命令参数

参数 描述
-a, --author string 作者。
-c, --change list 应用 Dockerfile 指令来创建镜像。
-m, --message string 提交信息。
-p, --pause 提交期间暂停容器（默认为 true）。

用 -c 可以在提交时顺手改掉一些配置，例如暴露端口、改启动命令、加环境变量：

docker commit \
  -c 'EXPOSE 80' \
  -c 'ENV APP_ENV=prod' \
  -c 'CMD ["/opt/app/bin/start.sh"]' \
  -m "add expose and env" 163950a65bfb myapp/console:v3.1.2

使用 docker commit 必须注意：它不会保存挂载出来的数据卷内容（volume 里的数据仍在宿主机上），也不会重新执行构建流程，因此镜像无法复现、体积容易膨胀；它适合应急修复和现场取证，长期方案仍然是把改动回写到 Dockerfile 重新构建。提交前建议先 docker diff 163950a65bfb 看一眼改了哪些文件，避免把临时文件、日志、密钥一并打进镜像。

三、批量停止、删除与清理

这一节的每条命令都会真正改变运行状态，请遵守一个共同原则：先列出清单，人工确认无误，再执行。

1、按名称前缀批量停止容器

# --filter "name=..." 是正则匹配且默认不锚定，^/web- 才能只命中 web- 开头的容器
docker ps --filter "name=^/web-" --format "table {{.Names}}	{{.Status}}"
docker ps -q --filter "name=^/web-" > /tmp/stop-list.txt
cat /tmp/stop-list.txt

# 确认后优雅停止（-t 15 表示最多等 15 秒再强杀）
xargs -r -a /tmp/stop-list.txt docker stop -t 15

2、按标签批量删除容器

docker run -d --label app=demo --name demo-1 nginx:alpine
docker run -d --label app=demo --name demo-2 nginx:alpine

# 先看清单：-a 才能包含已退出的容器
docker ps -a --filter "label=app=demo" --format "{{.Names}} {{.Status}}"

# 删除容器并连带删除其匿名卷（-v），不删除具名卷
docker ps -aq --filter "label=app=demo" | xargs -r docker rm -v

3、批量删除镜像

# 只删“悬空镜像”（无标签的中间层），最安全
docker images -q --filter "dangling=true" | xargs -r docker rmi

# 按仓库名批量删标签：先列出来确认，再删
docker images --format "{{.Repository}}:{{.Tag}}" | grep '^myapp/' > /tmp/rmi-list.txt
cat /tmp/rmi-list.txt
xargs -r -a /tmp/rmi-list.txt docker rmi

# 镜像正被容器占用会报 conflict，先确认是哪个容器在用
docker ps -a --filter ancestor=myapp/console:v3.1.1

4、批量清理：prune 的三种力度

# 安全档：停止的容器、未使用的网络、悬空镜像、构建缓存
docker container prune -f
docker network prune -f
docker image prune -f
docker builder prune -f

# 时间档：只清理创建超过 7 天（168h）的未使用镜像
docker image prune -a --filter "until=168h" -f

# 危险档：删除所有未被任何容器使用的镜像（含带标签的），执行前务必 docker images 存档
docker images > /tmp/images-before-prune.txt
docker system prune -a -f

docker system prune -a 是最容易被误用的一条：它会把当前没有容器在用的镜像全部删除，下次部署又要重新拉取。生产机器上建议只用时间档 + --filter，并且保留 /tmp/images-before-prune.txt 以便追溯。

四、批量导出日志、打标签与推送

1、批量导出容器日志

#!/bin/bash
# 按容器名逐个导出最近 2000 行日志，文件名做安全化处理
set -uo pipefail
mkdir -p ./logs
date_str=$(date +%F)
# 用 --format 提取纯名字，避免表头混进循环
docker ps -a --format '{{.Names}}' | while read -r name; do
  [ -z "$name" ] && continue
  safe_name=$(echo "$name" | tr '/: ' '___')
  docker logs --tail 2000 --timestamps "$name" > "./logs/${safe_name}-${date_str}.log" 2>&1
  echo "exported $name -> logs/${safe_name}-${date_str}.log"
done
ls -lh ./logs

2、清理日志：先确认路径，再按大小裁剪

# 日志占空间通常来自 json-file 驱动的容器日志，先看谁最大
du -sh /var/lib/docker/containers/*/*-json.log 2>/dev/null | sort -h | tail

# 正确做法：清空文件而不是删除文件（删除会让 Docker 继续写已删除的 inode，空间不释放）
: > /var/lib/docker/containers/<容器ID>/<容器ID>-json.log

# 更彻底的做法：给 Docker 配置日志轮转，然后重建容器
# /etc/docker/daemon.json
# {
#   "log-driver": "json-file",
#   "log-opts": { "max-size": "50m", "max-file": "3" }
# }
systemctl restart docker

3、批量打标签并推送

#!/bin/bash
# 把本地 myapp/* 镜像统一加上私有仓库前缀后推送
set -uo pipefail
registry="registry.cn-hangzhou.aliyuncs.com/jgqk8s"

docker login "$registry"

docker images --format "{{.Repository}}:{{.Tag}}" | grep '^myapp/' | grep -v '<none>' > /tmp/push-list.txt
while IFS= read -r src; do
  dst="${registry}/${src#myapp/}"
  docker tag "$src" "$dst"
  docker push "$dst"
done < /tmp/push-list.txt

逐行 while read 而不是 xargs -n1 -P4，是为了让推送顺序可控、日志可读；确实需要并发时用 xargs -r -n1 -P4 -a /tmp/push-list.txt -I{} docker push "{}"，并确保 docker login 已经完成。

五、脚本安全写法与常用参数

批量脚本出事，几乎都逃不出下面这几类问题：

  • 命令替换取空：docker rm $(docker ps -aq) 在没有容器时会展开成 docker rm 而安全报错，但换成 rm -rf $(ls ...) 就可能是灾难。习惯写法是 xargs -r（空输入不执行）或 [ -z "$list" ] && exit 0 提前判断。
  • 引号缺失：变量一律写 "$var"，数组写 "${arr[@]}"；单引号内不做展开，双引号内才展开，例如 '{{.Names}}' 必须用单引号，否则会被 shell 当成通配符。
  • xargs 分词：默认按空白分词，且会把引号当普通字符，名字含空格时必然拆错。用 NUL 分隔最稳：docker ps -aq --filter "name=^/web-" | xargs -0 -r docker rm 需配合 --format "{{.ID}}"，或直接用 xargs -r -a 文件。
  • 过滤器误解：--filter "name=x" 是正则子串匹配，web 会命中 web-1 也会命中 myweb，所以要写 name=^/web-；docker rm、docker logs、docker save 都不支持 --filter，必须先由 docker ps/images 生成清单。
  • 无预演直接删：把目标清单先写到 /tmp/xxx-list.txt，cat 一遍确认，再交给 xargs 执行；生产机上动手前先 docker ps -a > backup.txt 留快照。
  • 脚本头：set -euo pipefail 能尽早暴露错误，但它会让“某一条 pull 失败即整脚本退出”，批量容错场景改用 set -uo pipefail 并自行判断返回值。

最后附上本文涉及命令的高频参数速查：

docker ps -a -q              # 只输出容器 ID（-a 含已退出），配合 xargs 使用
docker ps --filter "name=^/web-" --filter "status=exited"
docker ps --format "{{.Names}}	{{.Status}}	{{.Image}}"
docker rm -f -v               # -f 强杀删除（不走优雅停机），-v 删除匿名卷
docker rmi -f                 # 强删镜像，被容器占用时会报 conflict
docker image prune -a --filter "until=168h"   # 按时间裁剪未使用镜像
docker system df             # 查看镜像/容器/卷/缓存占用
docker logs --tail 200 --timestamps --since 1h <容器名>
docker history <镜像>         # 查看镜像层，排查 commit 带来的体积膨胀
