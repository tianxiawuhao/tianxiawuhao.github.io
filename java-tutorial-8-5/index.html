Storm 与实时计算

Posted on 2026-09-19，10 min read

上一章的 Flink 用窗口、状态与 Checkpoint 回答“怎么把无界数据切成有界再算”。Storm 走的是更直接的一条路：数据来一条就立刻处理，没有批次的概念，也没有“等窗口攒满再触发”的等待。它由 Twitter 在 2011 年开源，2014 年成为 Apache 顶级项目。它是流处理领域第一个被广泛使用的计算框架，也是后来 Flink、Structured Streaming 设计的参照物。本章面向已经会写 Java、了解 Kafka 与 HDFS 的读者，讲清 Storm 的核心模型——拓扑（Topology）、Spout、Bolt、流分组与 ack 可靠性机制。最后把 Storm、Spark Streaming、Flink 放在一起对比，帮助读者在新项目里做出选择。示例基于 Storm 2.x（1.x 同样适用），包名统一为 org.apache.storm.*。

一、Storm 的定位：常驻运行的拓扑

理解 Storm 最快的方式是拿它和 MapReduce 对照。MapReduce 作业有明确的开始与结束：读一批输入、算完、退出。Storm 的作业叫 Topology，它一旦提交就常驻在集群里，除非显式 kill，否则会一直等待数据，这正是“实时”的前提。

数据在拓扑里以 Tuple 为单位流动。Tuple 是一组有序的值，配合字段名（Fields）使用，取字段时可以按位置下标，也可以按名字。一条条 Tuple 组成无界的 Stream。整张计算图由两类组件构成。Spout 是数据的入口，负责从 Kafka、MQ、Socket 或自定义数据源读取并向下游发射。Bolt 是处理单元，做过滤、解析、聚合、join、写库等任意逻辑，也可以继续向下游发射。Spout 和 Bolt 统称 component（组件）。

运行时的层级也要分清。一个 component 的并行度决定它有多少个 Task 实例，Task 被分配到 Executor（线程）里执行，若干 Executor 又跑在同一个 Worker（JVM 进程）中。每个 Worker 是一个 JVM，内部为每个 Task 起线程，另外默认还有一个 Acker 线程。它们共享同一个进程的资源，因此 nextTuple() 里一旦阻塞，受影响的不只是这一个 Spout。集群侧则由 Nimbus（主节点，负责分配与调度）、Supervisor（工作节点，负责起停 Worker）和 ZooKeeper（保存状态与心跳）组成。Nimbus 并不是运行期的单点瓶颈，它挂掉后已运行的拓扑照常工作，只是不能提交新拓扑。

二、Spout 与 Bolt：怎么写一个组件

Spout 通常继承 BaseRichSpout，要实现的钩子只有三个。open() 在启动时拿到 SpoutOutputCollector 并做初始化。nextTuple() 被框架在独立线程里不停调用，用来发射数据。declareOutputFields() 声明流的字段名。可靠的数据源还要实现 ack() 与 fail() 两个回调。下面的例子把“取数据”和“发数据”分开：后台线程负责往阻塞队列里放，nextTuple() 只做非阻塞的取出与发射。

import org.apache.storm.spout.SpoutOutputCollector;
import org.apache.storm.task.TopologyContext;
import org.apache.storm.topology.OutputFieldsDeclarer;
import org.apache.storm.topology.base.BaseRichSpout;
import org.apache.storm.tuple.Fields;
import org.apache.storm.tuple.Values;

import java.util.Map;
import java.util.concurrent.ArrayBlockingQueue;

public class SentenceSpout extends BaseRichSpout {
    private SpoutOutputCollector collector;
    private final ArrayBlockingQueue<String> queue = new ArrayBlockingQueue<>(1024);

    @Override
    public void open(Map<String, Object> conf, TopologyContext context,
                     SpoutOutputCollector collector) {
        this.collector = collector;
        // 真实项目在这里启动 Kafka 消费线程，把消息塞进 queue
    }

    @Override
    public void nextTuple() {
        String sentence = queue.poll();
        if (sentence == null) {
            try {
                Thread.sleep(10);   // 空转必须让出 CPU，绝不在这里阻塞等待
            } catch (InterruptedException ignored) {
                Thread.currentThread().interrupt();
            }
            return;
        }
        // 第二个参数是 msgId：它既是 ack 的根 id，也是 fail 重放时的标识
        collector.emit(new Values(sentence), sentence);
    }

    @Override
    public void ack(Object msgId) {
        // 整棵元组树处理成功，此时才提交 Kafka 位点
    }

    @Override
    public void fail(Object msgId) {
        // 处理失败或超时，把这条消息重新入队
    }

    @Override
    public void declareOutputFields(OutputFieldsDeclarer declarer) {
        declarer.declare(new Fields("sentence"));
    }
}

Bolt 继承 BaseRichBolt，核心是 execute(Tuple input)，每来一条 Tuple 调用一次。处理完必须显式调用 collector.ack(input)（可靠模式下）或 collector.fail(input)。向下游发射时，要用 collector.emit(input, new Values(...)) 这种带父 Tuple 的重载，把新 Tuple 挂到输入 Tuple 上。这一步叫 anchoring（锚定），是可靠性机制的根基。若用不带 input 的重载发射，新 Tuple 就成了孤儿，它失败不会导致上游重放。

import org.apache.storm.task.OutputCollector;
import org.apache.storm.task.TopologyContext;
import org.apache.storm.topology.OutputFieldsDeclarer;
import org.apache.storm.topology.base.BaseRichBolt;
import org.apache.storm.tuple.Fields;
import org.apache.storm.tuple.Tuple;
import org.apache.storm.tuple.Values;

import java.util.Map;

public class SplitBolt extends BaseRichBolt {
    private OutputCollector collector;

    @Override
    public void prepare(Map<String, Object> conf, TopologyContext context,
                        OutputCollector collector) {
        this.collector = collector;
    }

    @Override
    public void execute(Tuple input) {
        String sentence = input.getStringByField("sentence");
        for (String word : sentence.split(" ")) {
            if (!word.isEmpty()) {
                collector.emit(input, new Values(word, 1L));  // 锚定到输入 Tuple
            }
        }
        collector.ack(input);
    }

    @Override
    public void declareOutputFields(OutputFieldsDeclarer declarer) {
        declarer.declare(new Fields("word", "count"));
    }
}

组件之间靠流分组（Stream Grouping）连接，它决定上游发射的 Tuple 发给下游的哪个 Task。常用的有几种。shuffleGrouping 随机轮询，用于无状态处理与负载均衡。fieldsGrouping 按指定字段哈希，保证同一个 key 永远进同一个 Task，做计数、去重、会话聚合时必须用它。allGrouping 广播给所有 Task，适合下发配置或全局过滤。globalGrouping 全部发给编号最小的 Task。localOrShuffleGrouping 优先同 Worker 内转发，能省一次网络传输。directGrouping 由上游自己指定目标 Task，必须搭配 emitDirect 和直接流（direct stream）声明。

把组件装配起来的是 TopologyBuilder，提交前用 Config 设定并行度与可靠性开关。setSpout/setBolt 的第二个参数是并行度（Task 数），Config.setNumWorkers 是 Worker 进程数，两者不要混淆。并行度 4、Worker 数 2 表示 4 个 Task 分摊到 2 个 JVM。

import org.apache.storm.Config;
import org.apache.storm.LocalCluster;
import org.apache.storm.StormSubmitter;
import org.apache.storm.topology.TopologyBuilder;
import org.apache.storm.tuple.Fields;

public class WordCountTopology {
    public static void main(String[] args) throws Exception {
        TopologyBuilder builder = new TopologyBuilder();
        builder.setSpout("sentence-spout", new SentenceSpout(), 2);
        builder.setBolt("split-bolt", new SplitBolt(), 4)
               .shuffleGrouping("sentence-spout");
        builder.setBolt("count-bolt", new WordCountBolt(), 4)
               .fieldsGrouping("split-bolt", new Fields("word"));  // 同一个词进同一个 Task

        Config conf = new Config();
        conf.setNumWorkers(2);
        conf.setNumAckers(1);                    // 每个 Worker 的 acker 线程数
        conf.setMaxSpoutPending(1000);           // 未 ack 的在途 Tuple 上限，即背压阈值
        conf.put(Config.TOPOLOGY_MESSAGE_TIMEOUT_SECS, 30);  // 元组树超时，默认 30 秒

        if (args.length > 0 && "local".equals(args[0])) {
            LocalCluster cluster = new LocalCluster();      // 本地模式，方便调试
            cluster.submitTopology("word-count", conf, builder.createTopology());
            Thread.sleep(60_000);
            cluster.shutdown();
        } else {
            StormSubmitter.submitTopology("word-count", conf, builder.createTopology());
        }
    }
}

三、ack 与元组树：Storm 怎么做到不丢

Storm 的可靠性不是靠重发整个批次，而是靠元组树 + acker 校验。Spout 发射时给 Tuple 分配一个 64 位根 id，下游每次锚定发射都会把父 Tuple 的 id 一起带上，于是从根到叶子构成一棵树。acker 任务为每棵树维护一个 64 位校验值：收到新 Tuple 就把它的 id 异或进去，收到 ack 再异或一次，同一个 id 异或两次会相互抵消。当整棵树的校验值归零，说明所有分支都处理完了，acker 才回调 spout.ack()。只要有分支没 ack，超过 TOPOLOGY_MESSAGE_TIMEOUT_SECS（默认 30 秒）就判定超时，回调 spout.fail() 让 Spout 重放这条消息。因此 Storm 默认提供的是 at-least-once（至少一次）语义：不丢，但可能重复。

代价与开关都要清楚：acker 会带来额外网络与 CPU 开销（经验值 10%~20% 吞吐）。如果数据源本身可重放，或业务允许丢少量数据，把 Config.setNumAckers(0) 关掉 ack 就能换回一部分吞吐。反过来，想拿到 exactly-once（精确一次），要用 Trident 这层更高阶的 API，它把流切成小批并管理状态与事务；也可以在写入端做幂等与去重。另外要注意，可靠性是“全链路”的。Spout 开了 ack、中间某个 Bolt 却忘了 ack，或用不带 input 的 emit，该 Tuple 就会一直等到超时并被无条件重放，表现为计数偏大、下游重复写。Trident 里还有 ICommitterBolt 与 CheckpointSpout 等机制负责事务性提交。常用场景下 ack 三元组（emit 带 msgId、锚定发射、显式 ack）已经够用。

运行与运维命令如下。storm jar 提交时把 main 类写在拓扑 jar 之后，附加参数会传给 main。

# 提交拓扑（-c 可覆盖 Config 里的任意配置项）
storm jar word-count.jar com.example.WordCountTopology -c topology.workers=4

# 查看运行中的拓扑与各组件延迟、吞吐
storm list
storm ui

# 调整已提交拓扑的并行度（改代码重发会中断，rebalance 不会）
storm rebalance word-count -n 4 -e sentence-spout=4 -e count-bolt=8

# 关闭拓扑并等待 30 秒让在途数据跑完
storm kill word-count -w 30

四、Storm、Spark Streaming、Flink 怎么选

三者的本质差别在计算模型。Storm 是逐条处理的真流系统，延迟可低到毫秒级，API 也最底层。它的状态要自己维护（比如用一个 Map 存计数），容错只有 at-least-once，需要额外用 Trident 才能做到精确一次。强项是延迟极低、模型简单、易于理解。Spark Streaming 是微批（micro-batch）：按 batch interval（通常秒级）把流切成 RDD 序列（DStream），因此延迟下限就是批间隔，换来的是复用 Spark 生态与 SQL 能力。Spark 2.0 之后官方主推 Structured Streaming，DStream API 已进入维护状态。Flink 则是真流 + 事件时间 + 水位线 + Checkpoint 状态，原生提供 exactly-once，同时把批与流统一到一套 API 上，今天新项目的默认选择基本是它。

落到选型上：新项目做实时计算，优先 Flink。如果只是从 Kafka 到 Kafka 的轻量转换、过滤、路由，Kafka Streams 或 Flink SQL 更省运维。只有在维护存量系统、或者对延迟极度敏感且业务逻辑很简单的管道上，Storm 才仍是合理选项。要提醒的是，网上不少“Storm 是流处理唯一答案”的结论来自 2013—2016 年的资料。那时 Flink 尚未成熟，这个前提今天已经不存在了。

五、常见坑

  • 在 nextTuple() 里阻塞。它和 Bolt 的 execute()、acker 线程共处一个 Worker 进程。一旦在 nextTuple() 里做同步 RPC 或 take() 阻塞读取，整个 Worker 的吞吐都会塌掉。正确做法是“后台线程取数据 + 队列 + 非阻塞 poll”。
  • 分组选错。计数、去重类 Bolt 用 shuffleGrouping 会得到每个 Task 各自的局部结果，总量对不上，必须用 fieldsGrouping 按 key 分组。
  • 漏 ack 或漏锚定。表现为超时重放与结果翻倍，排查方法是在 UI 上看某组件的 failed 与 capacity 指标。
  • maxSpoutPending 设置不当。太小压不满下游吞吐，太大则一超时就一大片重放（重放风暴）；它同时也是 Storm 的背压手段。
  • 版本与包名混淆。1.0 之前所有类都在 backtype.storm 包下，之后统一迁到 org.apache.storm，抄十年前的代码会直接编译不过。

小结：Storm 用“Spout 进、Bolt 算、流分组连、Tuple 流”四个概念搭出常驻的流式 DAG。它用元组树与 acker 换来 at-least-once 的可靠性，用 Trident 换来精确一次。它的价值在今天更多是理解流处理的原点：延迟、状态、容错、背压这几个问题，Storm 都给出了第一代答案，而 Flink 与 Structured Streaming 则在这些答案上补齐了事件时间与状态一致性。读到这里，读者应该能写出并提交一个带可靠性与背压配置的 Storm 拓扑，也能说清它在什么场景下该被 Flink 取代。
