list、set、map等集合类线程不安全的问题及解决方法

Posted on 2021-09-03，4 min read

在单线程里，ArrayList、HashSet、HashMap 用起来都很顺手；一旦多个线程同时读写，它们就可能抛异常、丢数据，甚至让 CPU 打满。下面分别看 List、Set、Map 的问题根因与解决方案。

List

ArrayList 不是线程安全类，在多线程同时写的情况下，可能抛出 java.util.ConcurrentModificationException 异常。下面这段代码可以稳定复现：多个线程一边 add，一边 println(list) 触发迭代输出。

private static void listNotSafe() {
    List<String> list = new ArrayList<>();
    for (int i = 1; i <= 30; i++) {
        new Thread(() -> {
            list.add(UUID.randomUUID().toString().substring(0, 8));
            System.out.println(Thread.currentThread().getName() + "\t" + list);
        }, String.valueOf(i)).start();
    }
}

典型输出（线程名与异常出现的时机不固定，多次运行结果不同，也可能只丢失元素而不抛异常）：

3	[5f2b1c7a]
1	[9c0d4e6b, 5f2b1c7a]
Exception in thread "7" java.util.ConcurrentModificationException
	at java.base/java.util.ArrayList$Itr.checkForComodification(ArrayList.java:1013)
	at java.base/java.util.ArrayList$Itr.next(ArrayList.java:963)
	at java.base/java.util.AbstractCollection.toString(AbstractCollection.java:456)
7	[9c0d4e6b, 5f2b1c7a, a71e0f34]

为什么会这样？根因有三处：

  1. modCount 版本号与 fail-fast 迭代器。ArrayList 内部维护 modCount，记录结构性修改次数；迭代器创建时把它保存为 expectedModCount，每次 next() 前调用 checkForComodification() 比较，一旦发现被别人改过就立刻抛 ConcurrentModificationException。这就是上面堆栈里出现的检查方法。它只是「快速失败」，用于尽早暴露问题，本身并不能保证线程安全。
  2. add() 的 size 自增不是原子操作。add() 会先 elementData[size] = e，再 size = size + 1。两个线程可能读到相同的 size，后写入的把先写入的覆盖掉，最终数组里元素个数少于 add 的次数——这正是「丢数据」的由来。
  3. 扩容与数据搬运不安全。数组容量不足时调用 grow()，先算出新容量并 Arrays.copyOf 出新数组，再赋值给 elementData。多个线程同时扩容时，各自基于自己读到的旧数组复制，后设置的那个数组会覆盖前一个，期间写入的元素就消失了。同理，HashMap 在 JDK 7 的并发扩容中，头插法会让链表成环，后续 get() 落到环上就出现 CPU 100% 的死循环；JDK 8 改为尾插法后成环问题消失，但并发 put 仍然会覆盖丢数据。

解决方法有三种：

  1. 使用 Vector。Vector 把几乎所有方法都标了 synchronized，单次操作安全，但所有线程抢同一把锁、锁粒度最粗，性能差，属于遗留类，新代码不推荐。
  2. 使用 Collections.synchronizedList() 转换。它返回一个 SynchronizedList 包装类，内部方法用 synchronized (mutex) 加锁，改造存量代码成本最低。代价是：遍历时仍然要自己加锁，否则依旧可能抛 ConcurrentModificationException。 
    List<String> list = Collections.synchronizedList(new ArrayList<>());
// 遍历必须手动同步
synchronized (list) {
    for (String s : list) {
        System.out.println(s);
    }
}
  3. 使用 java.util.concurrent.CopyOnWriteArrayList（推荐）。这是 JUC 的类，通过写时复制实现读写分离：写操作先加锁，复制出一个新数组，在新数组上修改，最后把引用指向新数组；读操作直接读当前引用，完全不加锁。其 add() 源码如下： 
    public boolean add(E e) {
    final ReentrantLock lock = this.lock;
    lock.lock();
    try {
        //得到旧数组
        Object[] elements = getArray();
        int len = elements.length;
        //复制新数组，长度 +1
        Object[] newElements = Arrays.copyOf(elements, len + 1);
        //设置新元素
        newElements[len] = e;
        //设置新数组
        setArray(newElements);
        return true;
    } finally {
        lock.unlock();
    }
}

因此 CopyOnWriteArrayList 读多写少时非常划算，但每次写都要复制整个数组，内存占用和写开销都大；而且迭代器拿到的是创建那一刻的数组快照，属于弱一致（weakly consistent），迭代期间看不到新加入的元素，也不会抛 ConcurrentModificationException。

Set

跟 List 类似，HashSet 和 TreeSet 都不是线程安全的，与之对应的有 CopyOnWriteArraySet。这个类底层维护了一个 CopyOnWriteArrayList，所有能力都委托给它：

private final CopyOnWriteArrayList<E> al;
public CopyOnWriteArraySet() {
    al = new CopyOnWriteArrayList<E>();
}

由于底层是数组，add() 需要遍历已有元素判重，因此它只适合元素数量较小的场景；元素很多时，add 的 O(n) 判重会拖慢写入。

也可以使用 Collections.synchronizedSet() 转换成线程安全类，取舍与 synchronizedList 相同：单次操作安全，复合操作和遍历仍需自行加锁。

说到 Set 就离不开 HashMap：HashSet 底层是用 HashMap 实现的。既然 HashMap.put() 需要传两个参数，而 HashSet.add() 只传一个参数，这是为什么？实际上 HashSet.add() 就是调用 HashMap.put()，只不过 Value 被写死了，是一个 private static final Object 常量对象：

private static final Object PRESENT = new Object();

public boolean add(E e) {
    return map.put(e, PRESENT) == null;
}

所以 Set 的元素全部存放在 HashMap 的 key 上，只用 key 承载数据、value 只是一个占位符，这也解释了为什么 HashSet 同样受 HashMap 线程安全问题的影响。

Map

HashMap 不是线程安全的，Hashtable 是线程安全的，但是跟 Vector 类似，所有方法都用同一把锁，太重量级。所以并发场景下应使用 ConcurrentHashMap，它通过更细粒度的并发控制来提升性能：JDK 8 之后放弃了 JDK 7 的分段锁（Segment），改为 CAS + synchronized 只锁当前桶，读操作基本无锁，并发度大幅提升。

使用 ConcurrentHashMap 时有两个容易踩的点：一是不允许 null 键和 null 值，否则抛 NullPointerException，迁移老代码时要注意；二是 size()、isEmpty() 返回的是瞬时估计值，不能拿它做「先判断再操作」的依据。此外，ConcurrentHashMap 的迭代器是弱一致的，遍历过程中不会抛 ConcurrentModificationException，但也可能看到或看不到并发修改的部分结果。

如果需要按 key 排序的并发 Map，TreeMap 没有对应线程安全实现，应该用 ConcurrentSkipListMap：它基于跳表（SkipList）实现，读操作无锁，写操作平均 O(log n)，天然支持有序遍历、范围查询（subMap、headMap、tailMap）以及 ceilingKey、floorKey 等导航方法。

import java.util.*;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentSkipListMap;
import java.util.concurrent.CopyOnWriteArrayList;
import java.util.concurrent.CopyOnWriteArraySet;

public class ContainerNotSafeDemo {
    public static void main(String[] args) {
        listNotSafe();
        setNoSafe();
        mapNotSafe();
    }

    private static void mapNotSafe() {
        //Map<String,String> map=new HashMap<>();
        Map<String, String> map = new ConcurrentHashMap<>();
        for (int i = 1; i <= 30; i++) {
            new Thread(() -> {
                map.put(Thread.currentThread().getName(), UUID.randomUUID().toString().substring(0, 8));
                System.out.println(Thread.currentThread().getName() + "\t" + map);
            }, String.valueOf(i)).start();
        }
    }

    private static void setNoSafe() {
        //Set<String> set=new HashSet<>();
        Set<String> set = new CopyOnWriteArraySet<>();
        for (int i = 1; i <= 30; i++) {
            new Thread(() -> {
                set.add(UUID.randomUUID().toString().substring(0, 8));
                System.out.println(Thread.currentThread().getName() + "\t" + set);
            }, String.valueOf(i)).start();
        }
    }

    private static void listNotSafe() {
        //List<String> list=new ArrayList<>();
        List<String> list = new CopyOnWriteArrayList<>();
        for (int i = 1; i <= 30; i++) {
            new Thread(() -> {
                list.add(UUID.randomUUID().toString().substring(0, 8));
                System.out.println(Thread.currentThread().getName() + "\t" + list);
            }, String.valueOf(i)).start();
        }
    }

    // 有序并发 Map：需要按 key 排序时用它替代 TreeMap
    private static void sortedMap() {
        Map<String, String> map = new ConcurrentSkipListMap<>();
        map.put("b", "2");
        map.put("a", "1");
        System.out.println(map); // {a=1, b=2}
    }
}

线程安全集合的复合操作陷阱

换用线程安全集合只解决了「单次操作原子性」，并不等于整段业务逻辑安全。经典的反例是「先判断再操作」：

// 错误：check-then-act，两步之间存在竞态窗口
if (!map.containsKey(key)) {
    map.put(key, value);   // 两个线程可能同时判断为 false，后写入的覆盖先写入的
}

// 正确：使用 ConcurrentHashMap 提供的原子复合方法
map.putIfAbsent(key, value);
map.computeIfAbsent(key, k -> loadFromDb(k));
map.merge(key, 1L, Long::sum);

同理，对 CopyOnWriteArrayList 做「存在就更新、不存在就新增」这类逻辑，也需要在外部加锁，或者干脆改用 ConcurrentHashMap 承载。再如「遍历时删除元素」，即使集合本身线程安全，也应该用迭代器的 remove()，或者收集待删除元素后统一处理，不要在增强 for 循环里直接调用集合的 remove()。

一句话总结取舍：读多写少用 CopyOnWriteArrayList / CopyOnWriteArraySet；高并发键值场景用 ConcurrentHashMap；需要有序并发用 ConcurrentSkipListMap；改造老代码、并发量不大时用 Collections.synchronizedXxx，但一定要记得给遍历和复合操作补上同步。
