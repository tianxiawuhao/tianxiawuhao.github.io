计算机基础

Posted on 2026-09-19，5 min read

面试里最容易被追问、又最容易被轻视的一块，就是「计算机基础」：网络分层、TCP 握手、HTTP 状态码、进程与线程、死锁。它们和具体框架无关，却决定了你能否把一个线上问题从应用层追到传输层。这一章把 Java 后端面试最常考的几组基础概念串成一条线，适合已经会写业务代码、但答题时只能背结论而说不清过程的人阅读。

一、先建立分层视角：一个请求到底经过了什么

网络通信的复杂度靠「分层」来拆解：每一层只对上一层负责，向下封装、向上解封。常见的参考模型有两套：OSI 分七层，教学和排障时更常说的是 TCP/IP 五层模型——应用层、传输层、网络层、数据链路层、物理层。

各层的分工可以这样记：应用层为具体程序提供服务，单位是报文，HTTP、DNS、SMTP 都在这一层；传输层为「主机中的进程」提供端到端服务，主角只有 TCP 和 UDP；网络层为主机之间提供传输服务，把数据封装成分组；数据链路层负责同一段链路上的传输，把分组封装成帧；物理层只管比特流的传输与调制。

一个容易被忽略的细节是：路由器只需要下三层（网络层、链路层、物理层），因为它处在网络核心，不为主机中的进程或应用程序提供服务。理解这一点，就能解释为什么「ping 通了但服务访问不了」往往出在传输层以上。

数据向下传递时逐层加首部（或尾部），向上传递时逐层拆掉，这个过程叫封装与解封。以一次 HTTPS 请求为例，浏览器发出的 HTTP 报文会被 TCP 加上首部、被 IP 再加上首部、被链路层封装成帧，最终变成物理线路上的电信号或光信号：

GET /java-tutorial-9-9/ HTTP/1.1      # 应用层：请求行，包含方法、路径、协议版本
Host: example.com                     # 应用层：必须携带的首部字段
User-Agent: Mozilla/5.0
Accept: text/html

HTTP/1.1 200 OK                       # 应用层：状态行，状态码 + 原因短语
Content-Type: text/html; charset=utf-8
Content-Length: 1024

<!DOCTYPE html>                     # 下面是报文实体主体
<html lang="zh-CN">...</html>

二、传输层：TCP 的可靠交付靠什么保证

TCP 与 UDP 的区别几乎是必考题。UDP 无连接、尽最大努力交付、没有拥塞控制、面向报文，支持一对一、一对多、多对多，适合 DNS 查询、音视频这类更看重时延的场景；TCP 面向连接、提供可靠交付、有流量控制和拥塞控制、面向字节流，且一条连接只能是点对点，适合文件传输、页面请求这类不能丢数据的场景。

TCP 的「可靠」不是单一机制，而是四件事叠加：序号与确认号给字节流编号并确认；超时重传按加权平均往返时间 RTTs 推算超时时间 RTO，收不到确认就重传；滑动窗口让发送方在未收到确认时也能连续发送，接收方只在窗口内最后一个按序到达的字节处确认，发送方由此推断之前的字节均已到达；流量控制通过确认报文中的窗口字段约束发送速率，窗口置 0 则发送方停止发送。

连接建立采用三次握手：客户端发送 SYN=1、ACK=0、序号 x；服务端同意后回复 SYN=1、ACK=1、确认号 x+1、序号 y；客户端再回复确认号 y+1，连接建立。为什么必须是三次而不是两次？因为网络中可能滞留一个早已失效的连接请求，若只有两次握手，服务端收到这个旧请求就会直接建立连接并等待数据，白白浪费资源；有了第三次握手，客户端会直接忽略这个旧请求的确认，连接不会建立。

释放连接需要四次挥手，原因是 TCP 是全双工的：A 发送 FIN 后，B 先回确认，此时进入半关闭状态，B 仍可继续发送尚未传完的数据，等 B 的数据发完才发送自己的 FIN。A 收到后进入 TIME-WAIT 状态并等待 2MSL，一是为了保证最后一个确认能到达（否则 B 会重发 FIN），二是让本次连接中产生的所有报文在网络中消失，避免影响下一个新连接。

拥塞控制由慢开始、拥塞避免、快重传、快恢复四个算法配合完成，发送方维护拥塞窗口 cwnd：慢开始阶段 cwnd 从 1 开始按轮次翻倍（1、2、4、8……），当 cwnd 达到慢开始门限 ssthresh 后转入拥塞避免，每轮只加 1；出现超时则把 ssthresh 降为 cwnd 的一半并重新慢开始；若收到三个重复确认，说明只是个别报文段丢失而非网络拥塞，立即重传丢失报文段（快重传），并令 ssthresh = cwnd / 2、cwnd = ssthresh 直接进入拥塞避免（快恢复）。要注意「慢」指的是初始值设得小，而不是增长速度慢。

三、应用层：HTTP 的方法、状态码与 HTTPS

HTTP 请求报文的第一行是请求行，包含方法字段。GET 获取资源、HEAD 只取首部不返回主体、POST 传输实体主体、PUT 上传（会整体替换资源）、PATCH 做部分修改、DELETE 删除资源、OPTIONS 查询资源支持的方法、CONNECT 为代理建立隧道、TRACE 追踪路径（易受 XST 攻击，实际很少使用）。

响应报文第一行是状态行，状态码按首位分五类：1XX 信息性、2XX 成功、3XX 重定向、4XX 客户端错误、5XX 服务端错误。需要重点区分的是几个重定向：301 永久重定向，302 临时重定向，303 明确要求改用 GET 获取资源，307 也是临时重定向但要求不改变原来的请求方法，304 表示资源未修改、可以直接使用本地缓存。

HTTPS 并不是一种新协议，而是 HTTP 先与 TLS（早期是 SSL）通信，再由 TLS 与 TCP 通信。它因此同时具备三种能力：加密（防窃听）、认证（防伪装）、完整性保护（防篡改）。其加密方式是混合的：握手阶段用非对称加密安全地协商出一个会话密钥，之后用对称加密传输数据，从而兼顾安全与性能；服务端身份则通过 CA 签发的数字证书来证明，客户端拿到证书后用其中的公钥验证数字签名，确认对方身份无误。

四、操作系统：进程、线程与死锁

进程与线程的根本区别在于：进程是操作系统资源分配的基本单位，线程是处理机调度和执行的基本单位。同一进程内的线程共享地址空间和资源，但各自拥有独立的运行栈和程序计数器；进程之间地址空间相互独立，因此进程切换开销更大，但也更健壮——一个进程崩溃在保护模式下不影响其他进程，而一个线程崩溃会导致整个进程退出。线程不能独立运行，必须依附于进程。

线程数通常远多于 CPU 核心数，操作系统通过分配时间片轮转执行。一个线程的时间片用完、切换到另一个线程之前，需要保存当前任务的状态，下次切回时再加载，这个过程就是上下文切换。它需要可观的处理器时间，是内核中开销较大的操作之一，因此「线程越多吞吐越高」是错误直觉。

死锁是多个线程互相持有并等待对方资源、在没有外力介入时都无法推进的状态。它需要同时满足四个必要条件：互斥条件、请求与保持条件、不可剥夺条件、循环等待条件。避免死锁的思路就是破坏其中任意一个条件——最实用的是破坏循环等待条件，让所有线程按同一固定顺序申请资源，释放时逆序释放：

public class OrderedLockDemo {
    private static final Object LOCK_A = new Object();
    private static final Object LOCK_B = new Object();

    /** 统一按 LOCK_A -> LOCK_B 的顺序加锁，破坏循环等待，因此不会死锁 */
    static void transfer(boolean forward) {
        Object first = forward ? LOCK_A : LOCK_B;
        Object second = forward ? LOCK_B : LOCK_A;
        synchronized (first) {
            System.out.println(Thread.currentThread().getName() + " 持有第一把锁");
            synchronized (second) {
                System.out.println(Thread.currentThread().getName() + " 持有第二把锁");
            }
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> transfer(true), "线程-1");
        Thread t2 = new Thread(() -> transfer(false), "线程-2");
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("两个线程都正常结束，没有死锁");
    }
}

把上面代码里的加锁顺序改成相反的（一个先锁 LOCK_A 再锁 LOCK_B，另一个反过来），两个线程就可能各持一把锁并互相等待，程序将永久挂起——这正是死锁最小的复现模型。此外，守护线程不能依赖 finally 块清理资源：一旦所有用户线程结束，JVM 会直接退出，守护线程的 finally 可能根本得不到执行；同理，setDaemon(true) 必须在 start() 之前调用，否则会抛出 IllegalThreadStateException。

五、这些基础在真实工程里怎么用

基础知识的价值在于解释现象，线上排查往往是逐层展开的：先看 HTTP 状态码确认服务是否正常，再用 telnet host port 确认端口监听与握手能否完成，然后用 ping 看链路连通性，最后用 top -H -p <pid> 找出 CPU 占用最高的线程，把线程号转成十六进制后在 jstack <pid> 输出中搜索对应 nid，即可定位到具体代码。

常见误判也源于基础不牢：把 304 当成请求失败、把 302 当成永久跳转、认为 HTTPS 全程使用非对称加密、认定「线程池越大并发越高」、以为丢给守护线程的任务一定会执行完。

六、小结

本章围绕「一个请求从浏览器到服务器」这条主线，梳理了三组面试高频基础：网络分层与封装解封、TCP 的可靠交付与三次握手四次挥手、HTTP 的方法与状态码以及 HTTPS 的混合加密；同时补齐了进程与线程的区别、上下文切换的开销和死锁的四个必要条件与规避手段。复习时不要背结论，而应能对着一次抓包或 jstack 输出把每层发生了什么讲清楚。
