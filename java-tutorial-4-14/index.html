4.14 权限框架

Posted on 2024-10-03，5 min read

系统里一旦出现“登录”，你迟早会撞上两个问题：你是谁（身份验证，Authentication）和你能干什么（授权，Authorization，也叫访问控制）。很多项目把这两件事揉进拦截器里手写，结果越写越乱：改密码规则要动登录逻辑，加角色要改好几处判断。本章把它们拆开讲清，并以 Spring Security 为主线，串起过滤器链、方法安全、Shiro 的 Realm 与 JWT 的取舍。适合已能写 Spring Boot 接口、正打算给项目加权限控制，或要应付“认证与授权怎么实现”这类面试题的读者。

一、认证与授权：两个必须分开的问题

认证回答“你是谁”，产出可信的身份对象；授权回答“你能不能访问这个资源”，输入是身份、资源与规则。框架把二者拆成两套接口，是因为变化频率不同：认证方式可能从密码换成短信、扫码、单点登录，授权规则则通常只是角色表在变，混写会让任何一边的变化牵连另一边。

Spring Security 里认证的总入口是 AuthenticationManager，它只有一个方法：

public interface AuthenticationManager {
    Authentication authenticate(Authentication authentication)
            throws AuthenticationException;
}

它做三件事之一：通过则返回已认证的 Authentication；失败抛 AuthenticationException；无法判断则返回 null。返回 null 表示该 Provider 不处理这种凭证，最终仍由上层抛异常。实际干活的是 ProviderManager，它把请求分派给一组 AuthenticationProvider：

public interface AuthenticationProvider {
    Authentication authenticate(Authentication authentication)
            throws AuthenticationException;
    // 注意：不是 Class<?>，而是 Class<? extends Authentication>
    boolean supports(Class<? extends Authentication> authentication);
}

Provider 只处理它 supports() 认领的 Authentication 子类型，认不出就跳过，因此一个应用能同时支持表单登录、Remember-Me、Token 等多种机制。全部 Provider 返回 null 时交给父（parent）Manager，父为空则抛异常。

二、授权：AccessDecisionManager 与投票器

认证通过后进入授权环节，核心接口是 AccessDecisionManager，它的经典签名是：

void decide(Authentication authentication, Object object,
        Collection<ConfigAttribute> configAttributes)
        throws AccessDeniedException, InsufficientAuthenticationException;

object 是泛化的“被保护资源”，Web 请求和 Java 方法都算；ConfigAttribute 是描述规则的字符串，最常见的就是 ROLE_ADMIN 这类角色名。Manager 只负责委托给一组 DecisionVoter 投票。默认实现 AffirmativeBased 只要有一票通过就放行，另有 ConsensusBased 少数服从多数、UnanimousBased 必须全票通过。自定义授权通常是增加 Voter，而不是重写 Manager；规则里写 SpEL，如 hasRole('FOO')，同样依靠一个能解析表达式的 Voter 实现。

三、Web 层：过滤器链是怎么装进去的

Spring Security 在 Web 层基于 Servlet 过滤器：先由 DelegatingFilterProxy 注册到容器（注册名固定为 springSecurityFilterChain），再委托给同名的 FilterChainProxy Bean。它内部可持有多条过滤器链，按顺序匹配路径，第一个匹配上的链独占处理。默认的 Spring Boot 应用通常有 6 条过滤器链：第一条放行静态资源，最后一条匹配 /**。兜底链内含认证、授权、异常处理等约 11 个过滤器。要加规则，可以继承 WebSecurityConfigurerAdapter（Security 5.7 之前的主流写法），也可以注册 SecurityFilterChain Bean。Boot 2.7 起推荐后者，并用 @Order 把它排在兜底链之前。下面这段是前一种写法：

@Configuration
@Order(SecurityProperties.BASIC_AUTH_ORDER - 10)
public class ApiSecurityConfig extends WebSecurityConfigurerAdapter {
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http.antMatcher("/api/**")          // 决定整条 FilterChain 是否生效
            .authorizeRequests()            // 以下才是细粒度授权规则
            .antMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated();
    }
}

最容易犯的错是把两个层级的匹配器搞混：antMatcher() 决定“这条链管不管这个请求”，antMatchers() 决定“链内部这个路径要什么权限”。另一个坑是 Boot 会自动注册容器里所有 Filter Bean，自定义安全过滤器会被执行两遍，应改用 FilterRegistrationBean 关闭自动注册再手动加进安全链。

四、方法安全、上下文与 Shiro 的对照

Web 安全管“哪些 URL 谁能进”，方法安全管“哪个 Service 方法谁能调”，粒度更细。在启动类加 @EnableGlobalMethodSecurity，Security 5.6 及以上推荐改用 @EnableMethodSecurity，之后即可在方法上打注解：

@Service
public class OrderService {
    @Secured("ROLE_USER")
    public String secure() {
        return "Hello Security";
    }

    @PreAuthorize("#userId == authentication.principal.id or hasRole('ADMIN')")
    public Order find(Long userId) {
        return orderMapper.selectById(userId);
    }
}

被拒绝时抛 AccessDeniedException。方法安全靠 AOP 代理，同类内部自调用不走代理，注解会失效，这是最常见的“加了注解却没生效”的原因。当前用户存在 SecurityContext 中，SecurityContextHolder 底层是 ThreadLocal。控制器里可用 @AuthenticationPrincipal User user 拿到类型安全的当前用户，但任务丢进 @Async 线程池后上下文就断了。此时需要用 DelegatingSecurityContextExecutorService 之类的包装传递上下文。

如果不想引入 Spring Security，可以选更轻量的 Apache Shiro。它同样分离认证与授权，但一切围绕 Realm 展开。实现 doGetAuthenticationInfo()，返回 SimpleAuthenticationInfo(principal, credentials, realmName)；再用 doGetAuthorizationInfo() 返回角色与权限。散列规则由 HashedCredentialsMatcher 统一配置，散列规则必须与入库时完全一致，否则永远认证失败。URL 规则写在 filterChainDefinitionMap 里，顺序敏感，anon 在前、authc 兜底：

Map<String, String> filterChainDefinitionMap = new LinkedHashMap<>();
filterChainDefinitionMap.put("/login", "anon");
filterChainDefinitionMap.put("/druid/**", "anon");
filterChainDefinitionMap.put("/logout", "logout");
filterChainDefinitionMap.put("/**", "authc");   // 兜底规则必须放最后

shiroFilterFactoryBean.setFilterChainDefinitionMap(filterChainDefinitionMap);
shiroFilterFactoryBean.setLoginUrl("/login");
shiroFilterFactoryBean.setSuccessUrl("/index");

它使用 LinkedHashMap 而不是 HashMap，正是为了保住这个顺序。JWT 解决的是“服务端无状态”与“跨域、多端”问题，本身只承载身份声明，不解决授权。Token 里塞角色只能做粗粒度判断，且过期前无法撤销，生产上一般配短有效期加刷新令牌，或叠加 Redis 黑名单。

五、小结

把本章压缩成几句话。认证与授权要分开：认证入口是 AuthenticationManager，授权入口是 AccessDecisionManager 加一组 Voter。Web 安全由 FilterChainProxy 组织的多条过滤器链实现，匹配到的第一条链独占生效。方法安全靠 AOP，只在外部调用时有效；当前用户存在 SecurityContextHolder 的 ThreadLocal 里，跨线程必须显式传递。选型上，Spring Boot 项目优先 Spring Security，追求轻量可选 Shiro，JWT 只是携带身份凭证的手段，不是权限方案。
