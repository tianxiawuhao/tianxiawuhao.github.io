7.7 Docker Compose 与编排

Posted on 2024-12-15，7 min read

上一章已把一个 Java 应用装进镜像跑了起来。但真实项目很少只有一个容器：Spring Boot 后端要连 MySQL、用 Redis 做缓存，前面还得有 Nginx 做反向代理和静态资源。如果继续手工敲 docker run，很快会撞上三件事：命令参数越来越长、散落在聊天记录里；容器之间的网络要手动建、手动连；换一台机器部署时所有命令得重拼一遍，还容易漏掉某个环境变量。Compose 正是为解决这件事而生：用一份 YAML 声明“我要哪些服务、它们怎么组网、数据放哪、谁先启动”，再用一条命令把整套环境拉起来。本章面向已经会写 Dockerfile、会用 docker run 的读者。内容上会讲清 Compose 的定位、文件怎么写、常用命令、四个最容易踩的坑，以及它和 Kubernetes 的边界；末尾顺带把镜像分发到私有仓库这条链路补完。

一、Compose 的定位：单机多容器编排

所谓“编排”（orchestration），指的不是“把容器跑起来”，而是描述一组容器之间的关系：谁依赖谁、怎么互相发现、副本要几个、挂了要不要重启、发布时怎么替换。这个概念在容器生态里出现得很早。最早叫 Fig 的项目就允许在配置文件里定义各容器的副本数等编排参数，被 Docker 公司收购后改名为 Compose，并在很长时间里是 Docker 生态中最受欢迎的项目之一。

但必须先把 Compose 的范围讲清楚：它管理的是一个 Docker 环境，通常就是一台宿主机（也可以是 docker context 指向的远端 Docker）。它不负责跨主机调度、节点故障自愈和滚动升级，那些是 Swarm、Kubernetes 这类集群编排系统的事。判断标准很简单：单机放得下、不需要零停机发布，Compose 就是性价比最高的选择；一旦需要多机容灾或自动扩缩容，就该换 Kubernetes，而不是硬把 Compose 用到集群上。

还有一处版本差异必须分清：早期的 docker-compose（V1，Python 写的独立可执行文件）已停止维护，现在的 Compose V2 是 docker CLI 的插件，命令是 docker compose——中间是空格，不是连字符。两者配置文件基本兼容，但如果你照着老教程敲 docker-compose 提示找不到命令，原因就在这里。文件名推荐 compose.yaml，旧的 docker-compose.yml 仍被识别。

还有一处老教程最常见的残留：文件第一行的 version: "3.8"。它属于 Compose V1 时代的 schema 版本声明，自 Compose V2 起已废弃。留着不会报错，但 docker compose config/up 会打印 "the attribute version is obsolete" 之类的警告并忽略它。新文件按 Compose Specification 写即可：顶层只要有 services，不需要 version；要固定项目名用顶层 name: myapp（等价于命令行的 -p myapp）；要复用片段则用 x- 前缀的自定义字段配 YAML 锚点。Compose V1（Python 写的 docker-compose 独立可执行文件，最后一版是 1.29.x）自 2023 年年中起停止维护，只会在老机器上见到。顺带说一句，V2 的定位越来越偏"单机与开发"：--profile 能按场景隔离服务组，docker compose watch（2.22+）在源码变更时自动同步或重建，这些都不需要任何集群。

二、一份 compose.yaml 是怎么写的

Compose 文件是声明式的：你描述“最终要什么状态”，而不是“依次执行哪些命令”。下面这份配置是 Java 后端 + MySQL + Redis + Nginx 的最小可用编排，建议先整体读一遍，再逐段看说明。

# compose.yaml
services:
  mysql:
    image: mysql:8.0
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}   # 从同目录 .env 读取
      MYSQL_DATABASE: appdb
    volumes:
      - mysql-data:/var/lib/mysql                   # 命名卷，容器删了数据还在
    healthcheck:
      # $$ 表示把 $ 原样传给容器，避免被 Compose 提前插值
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-p$$MYSQL_ROOT_PASSWORD"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 30s
    networks: [backend]

  redis:
    image: redis:7-alpine
    restart: unless-stopped
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis-data:/data
    networks: [backend]

  app:
    build: .                                      # 用当前目录的 Dockerfile 构建
    image: 192.168.184.141:5000/app:1.0.0         # 同时打上私仓标签，便于 push
    restart: unless-stopped
    environment:
      SPRING_PROFILES_ACTIVE: prod
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/appdb   # 主机名就是服务名
      SPRING_REDIS_HOST: redis
    depends_on:
      mysql:
        condition: service_healthy                # 等健康检查通过，而非只等启动
      redis:
        condition: service_started
    networks: [backend, frontend]

  nginx:
    image: nginx:1.25-alpine
    restart: unless-stopped
    ports:
      - "80:80"                                   # 只有它对外暴露端口
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on: [app]
    networks: [frontend]

volumes:
  mysql-data:
  redis-data:

networks:
  backend:
  frontend:

几个关键点：services 下的每个键（mysql、app…）既是服务名，也自动成为该容器在网络里的 DNS 名。Compose 会为项目创建一张默认网络，同网络内直接用服务名互访，所以 jdbc:mysql://mysql:3306/appdb 里的 mysql 不需要你去查容器 IP：手工 docker run 时代靠 docker inspect 找 IP 的做法在这里彻底不需要了。Nginx 转发同理：

# nginx/default.conf
server {
    listen 80;
    server_name _;

    location / {
        proxy_pass http://app:8080;              # app 是 compose.yaml 里的服务名
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

ports 是“宿主机端口:容器端口”，只给需要被外部访问的服务写，容器之间的互访不需要 ports。数据持久化用命名卷（mysql-data 写在顶层 volumes 里声明），比绑定宿主机目录更可移植，也避免了挂载多级目录时的权限问题。

另外两个容易混的字段是 build 与 image。build: . 表示用当前目录的 Dockerfile 现场构建；再写一个 image，相当于给构建结果命名，docker compose push 才知道该推到哪个地址。只写 image 则直接拉取现成镜像。

配置项多的服务不必把变量全塞进 environment，可以用 env_file: [app.env] 从文件读取，让 YAML 保持清爽。两者的分工与优先级要记牢。env_file 指向的是宿主机上的文件，其中的键值对会被注入容器进程的环境；environment 则是直接写在 YAML 里的键值对。同一个变量两处都定义时以 environment 为准（它覆盖 env_file），所以常见做法是"默认值放 env_file、需要显式覆盖的放 environment"。还要区分第三层：供 Compose 插值使用的同目录 .env（给 ${VAR} 取值）和 env_file 不是一回事——前者影响 YAML 文本，后者影响容器内部环境。改完用 docker compose config 看插值后的最终配置，用 docker compose exec app env | grep SPRING 确认容器里真正生效的值。

另外两个 V1 遗留字段值得单独提一句。links 已经废弃。它早期靠把"容器名 → IP"写进 /etc/hosts 实现互访，而同一网络里服务名本来就是 DNS 名，所以 links 在 V2 中会被忽略并告警，直接用服务名即可。确实需要额外主机名时改用网络别名，即在服务的 networks 下写 backend:，再跟一行 aliases: [db, mysql-primary]。同理 container_name 也尽量别写：它让容器名无法随项目名隔离，还会挡住扩副本（--scale），需要固定前缀交给顶层 name: 或 -p 更合适。

三、日常命令：从 up 到 down

记住五条命令就能覆盖九成场景。up 负责构建、创建、启动，down 负责按相反顺序清理。

docker compose up -d                  # 构建/拉取镜像并后台启动全部服务
docker compose up -d --build app      # 代码改了，只重建并重启 app
docker compose ps                     # 只看本项目（而非全机）的容器
docker compose logs -f --tail=100 app # 跟踪某个服务的日志
docker compose exec app sh            # 进入运行中的容器（bash 不一定装了）

docker compose config                 # 校验语法，并打印插值后的最终配置
docker compose restart nginx          # 只重启一个服务
docker compose stop                   # 停容器，不删
docker compose down                   # 停并删容器与网络，命名卷保留
docker compose down -v                # 连命名卷一起删，数据库数据不可恢复
docker compose -p myapp up -d         # 指定项目名，隔离容器名与网络

项目名默认取 compose.yaml 所在目录名，它决定容器名前缀（目录名-app-1）和网络名（目录名_default）。同一台机器上要跑两套互不干扰的环境时，用 -p 显式指定，而不是去改端口。

排障则优先靠日志和配置展开：docker compose logs 会把多个服务的日志按时间混排并加上服务名前缀，比逐个 docker logs 方便得多，配合 -f 跟踪、--tail=N 限制行数即可。如果改完配置行为仍不符合预期，先跑一遍 docker compose config 看插值后的最终结果，再判断是配置写错还是应用自身的问题。

四、四个最常见的坑

1. depends_on 不等于“就绪”。默认的 depends_on: [mysql] 只保证启动顺序：MySQL 进程拉起来了，但数据库初始化可能还要几十秒，此时 app 连过去照样报连接失败。正确做法是给依赖方加 healthcheck，再用 condition: service_healthy。注意 restart: unless-stopped 只能让崩掉的容器反复重启，不能替代就绪等待。

2. 数据没落盘，或 down 时误删。不写 volumes 的数据库，数据只存在容器可写层，docker compose down 后全部消失。反过来，down -v 会删除命名卷，调试时很方便，生产上等同于删库，务必确认后再敲。

3. 变量插值的两层含义。Compose 会先把文件里的 ${VAR} 用宿主机环境变量或同目录 .env 文件替换，然后才把结果交给容器；而容器内的 shell 变量则需要 $$ 转义后原样传入（上面 healthcheck 就是这么写的）。把密码放在 .env 里并加进 .gitignore，不要把明文提交到仓库。

4. 私有仓库的镜像拉不到。上一章已把镜像推到私有仓库，Compose 里要用它，必须在 image 字段写完整地址仓库地址/镜像名:标签。若私仓走 HTTP 而非 HTTPS，宿主机得先在 /etc/docker/daemon.json 里声明 insecure-registries——每一个要拉取该镜像的节点都要配，否则报 "http: server gave HTTP response to HTTPS client"。

# /etc/docker/daemon.json —— 信任 HTTP 私有仓库（改完必须重启 docker）
# { "insecure-registries": ["192.168.184.141:5000"] }
sudo systemctl restart docker

docker login 192.168.184.141:5000     # 有认证的私仓需要先登录
docker compose build app
docker compose push app               # 推送到 image 字段里写的私仓地址
# 不用 compose 也可以：
# docker tag app:1.0.0 192.168.184.141:5000/app:1.0.0
# docker push 192.168.184.141:5000/app:1.0.0

# 目标机器上：先改好 daemon.json，再拉取启动
docker compose pull && docker compose up -d

顺带纠正一个常见混淆：registry-mirrors 是加速拉取公共镜像的镜像站，insecure-registries 是信任你自己的 HTTP 私仓，两者用途不同，可以同时存在于同一个 daemon.json 里。

五、什么时候该上 Kubernetes

Compose 的边界很清晰：它的世界是单机。而 Kubernetes 提供的是另一层能力。它把若干节点组成集群，用 Pod/Deployment 管理副本数与滚动升级，用 Service 做稳定的服务发现与负载均衡，用探针在实例不健康时自动剔除重建。Kubernetes 之所以成为容器编排的事实标准，正是因为它把“编排”从“定义一组容器的关系”提升到了“定义整个集群期望状态”的层次；Compose+Swarm 的组合则止步于更轻量的场景。

版本上也要对齐现状。今天说的 Kubernetes 是 1.28 及以上的版本线，其中有两处关键变化：

  • 1.24 起 dockershim 已被移除，运行时统一走 CRI，即 containerd 或 CRI-O；
  • 1.27 起内置的云厂商 in-tree provider 也退场。

所以"K8s 节点上必须先装 Docker"这类老说法早已不成立。镜像仍是同一份 OCI 镜像，照样用 docker build 构建、docker compose push 推送。从 Compose 迁移时也不必推翻重写：kompose convert 能把现有 compose.yaml 转成 Deployment/Service/ConfigMap 清单，作为迁移起点。之后再人工补上探针、资源 requests/limits、Ingress 与 HPA——这些概念在 Compose 里根本不存在。

落地建议：个人项目、测试环境、单机部署的小型服务，用 Compose 就够了，一份 YAML 交给运维即可。当出现“要部署到三台以上机器”“发布时不能停服”“流量涨了要自动扩容”这类需求时，才值得引入 Kubernetes 的复杂度。不要为了用而用。

小结：Compose 用一份声明式 YAML 解决了单机多容器的组网、依赖顺序、数据持久化和一键启停，核心机制是服务名即 DNS 名与项目级隔离的默认网络。日常用 docker compose up -d / ps / logs / exec / down 五条命令即可，注意 V2 的命令是 docker compose。最容易踩的坑是 depends_on 只保证启动顺序，要靠 healthcheck 加 condition: service_healthy 才能真正等待就绪；down -v 会删数据卷；私仓镜像必须带完整仓库前缀并让每个节点信任它。把它当“单机编排”用，它就是最省心的一环；需要多机调度与自愈时，再交给 Kubernetes。
