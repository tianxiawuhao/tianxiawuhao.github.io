线上问题排查实战

Posted on 2026-09-19，8 min read

线上应用出问题，往往不是“代码写错了”这么简单：服务突然没响应、CPU 被打满、日志刷出 OutOfMemoryError、接口 P99 从 80ms 涨到 3s，而手上只有一台能 SSH 的机器和一个进程号。上一章把 JDK 自带的诊断工具逐个过了一遍，本章把它们放进真实的排查流程：在没有 Arthas、没有监控大盘的兜底场景下，仅靠 JDK 自带命令行工具，把“症状”一步步收敛到“某一行代码”。JDK 自带工具（jps/jstat/jmap/jstack）几乎是排查现场唯一一定存在的武器，即使日常使用 Arthas 或 JProfiler，理解它们输出的字段也仍然是基本功。阅读本章只需要会写 Java 多线程代码、能在 Linux 上敲命令。

一、先分诊：把症状映射到工具

排查最忌一上来就 dump 全堆。先按症状选工具，能省掉大量时间：

  • CPU 飙高：top -Hp <pid> 找到最耗 CPU 的线程，再用 jstack 看这个线程在干什么。
  • 进程卡死 / 请求全部挂起：jstack <pid> 直接看有没有 Found one Java-level deadlock，或大量线程 BLOCKED (on object monitor)。
  • 内存缓慢上涨、频繁 Full GC：jstat -gc <pid> 1000 观察回收后老年代是否回落；不回落就是泄漏，再 jmap dump 堆用 MAT 看支配树。
  • 突发 OOM：看错误类型（堆 / 元空间 / 直接内存 / GC overhead），带上 -XX:+HeapDumpOnOutOfMemoryError 抓现场。
  • 接口变慢但 CPU 不高：多半是锁竞争或下游阻塞，用 jstack 连打三次，看同一批线程是否停在同一个方法上。

第一步永远是先拿进程号。用 JDK 自带的 jps 比 ps -ef | grep java 更省事，它只列 JVM 进程，还能顺便看到主类名或 jar 名：

[root@node01 ~]# jps -l
6219 org.apache.catalina.startup.Bootstrap
7080 jdk.jcmd/sun.tools.jps.Jps
# 6219 就是目标进程，下面统一用这个 pid

同时查看 GC 的总体趋势，判断问题出在内存还是别处。jstat 的用法是 jstat [-命令选项] [vmid] [间隔时间/毫秒] [查询次数]：

[root@node01 ~]# jstat -gc 6219 1000 5
 S0C    S1C    S0U    S1U      EC       EU        OC         OU        MC       MU     YGC  YGCT   FGC  FGCT    GCT
9216.0 8704.0  0.0   2560.0 62976.0  2361.6   33792.0    20434.9   23808.0 23196.1   7  0.244    1  1.078    1.323

字段含义要记牢：S0C/S1C/EC/OC/MC 是各区域的容量（Capacity，单位 KB），S0U/S1U/EU/OU/MU 是使用量（Used），YGC/YGCT 分别是新生代 GC 次数和累计耗时（秒），FGC/FGCT 对应 Full GC，GCT 是总 GC 时间。判断标准很简单：连续观察 OU（老年代使用量）是否在每次 Full GC 后都降不下去——降不下去才叫泄漏，能降下去只是分配速率高，应该去调大堆或优化对象创建。这一条能挡掉一半的误判。

二、CPU 飙高：从线程号到代码行

CPU 高是最常见的线上告警，排查路径固定三步：找进程、找线程、翻译线程号。

先让 top 以线程粒度显示，找出占用 CPU 最高的线程 ID（注意是线程 ID，不是进程 ID）：

# -H 显示线程，-p 只看目标进程
[root@node01 ~]# top -Hp 6219
  PID USER  PR  NI  VIRT   RES  %CPU %MEM   TIME+ COMMAND
 6236 root  20   0 4.1g  512m  98.7  2.1  12:31.44 java
# 6236 是十进制线程号，jstack 输出里的 nid 是十六进制，需要转换
[root@node01 ~]# printf '%x\n' 6236
185c

然后在 jstack 输出里搜 nid=0x185c，就能看到这个线程当时的完整调用栈：

[root@node01 ~]# jstack 6219 | grep -A 20 "nid=0x185c"
"http-nio-8080-exec-5" #37 prio=5 os_prio=0 tid=0x00007f5c2c0e7000 nid=0x185c runnable [0x00007f5c1c8f7000]
   java.lang.Thread.State: RUNNABLE
        at com.example.order.PriceService.calcTotal(PriceService.java:88)
        at com.example.order.OrderController.submit(OrderController.java:41)
        at java.lang.Thread.run(Thread.java:748)

栈顶那行 PriceService.java:88 就是嫌疑点。这里有个常被忽略的关键点：RUNNABLE 不等于“在算 CPU”，socket 读、文件读同样是 RUNNABLE。所以单次快照只能给出线索，正确做法是间隔几秒连打 3 次 jstack：如果同一个方法始终出现在最耗 CPU 那个线程的栈顶，才能确认它就是热点。确认之后也不要急着改代码，先想清楚它属于哪种情况：

  • 死循环或正则回溯：栈顶停在同一个方法不动，通常伴随 CPU 100% 且无内存增长。
  • 锁自旋 / 反复重试：栈顶可能是 synchronized 或 CAS 相关的 JDK 内部方法，要往下看业务帧。
  • 序列化 / 加解密 / 大循环：栈顶是 JDK 方法（如 java.util.Arrays.copyOf），要结合 jstack 里的业务帧找调用方。

三、死锁：用 jstack 画出环形等待

死锁的现场特征非常好认：应用“没挂但也不干活”，日志停止输出，线程数稳定，CPU 反而不高。先看一段必然死锁的代码——两个线程以相反顺序获取同一对锁：

public class TestDeadLock {
    private static final Object obj1 = new Object();
    private static final Object obj2 = new Object();

    public static void main(String[] args) {
        new Thread(new Task(obj1, obj2), "t1").start();
        new Thread(new Task(obj2, obj1), "t2").start();
    }

    private static class Task implements Runnable {
        private final Object first;
        private final Object second;

        Task(Object first, Object second) {
            this.first = first;
            this.second = second;
        }

        @Override
        public void run() {
            synchronized (first) {
                System.out.println(Thread.currentThread().getName() + " 拿到第一把锁");
                try {
                    // 停顿 2 秒，保证两个线程都能先拿到各自的第一把锁
                    Thread.sleep(2000);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return;
                }
                synchronized (second) {
                    System.out.println(Thread.currentThread().getName() + " 拿到第二把锁");
                }
            }
        }
    }
}

跑起来后只会打印两行“拿到第一把锁”，然后永远卡住。此时执行 jstack <pid>，重点看输出末尾的自动分析结论：

Found one Java-level deadlock:
=============================
"t1":
  waiting to lock monitor 0x00007f5c2c0e7000 (object 0x00000000f655dc40, a java.lang.Object),
  which is held by "t2"
"t2":
  waiting to lock monitor 0x00007f5c2c0e9000 (object 0x00000000f655dc50, a java.lang.Object),
  which is held by "t1"

Java stack information for the threads listed above:
===================================================
"t1":
        at TestDeadLock$Task.run(TestDeadLock.java:33)
        - waiting to lock <0x00000000f655dc40> (a java.lang.Object)
        - locked <0x00000000f655dc50> (a java.lang.Object)
"t2":
        at TestDeadLock$Task.run(TestDeadLock.java:33)
        - waiting to lock <0x00000000f655dc50> (a java.lang.Object)
        - locked <0x00000000f655dc40> (a java.lang.Object)
Found 1 deadlock.

读法就三行：每个线程下面 waiting to lock 是它想要的锁，locked 是它已经持有的锁；两个线程各自锁住对方下一步要用的锁，环就闭合了。如果 jstack 没有自动给出死锁结论（Found one Java-level deadlock），不代表没有死锁——它只能识别 synchronized 监视器构成的环，ReentrantLock 之间的循环等待不会出现在这里。这种情况需要按“持有 / 等待”两列在输出里手动连线，或者用 jcmd <pid> Thread.print -l 打出更全的锁信息。

修法永远是统一加锁顺序（在本例中让两个线程都先锁 obj1），或者改用带超时的 tryLock(timeout)，让等待方主动放弃。千万不要靠调大线程池或重启来“解决”死锁：重启只是把环清掉，代码里的顺序问题还在，下次流量一上来照样复现。

四、内存溢出与泄漏：dump 下来看支配树

先纠正一个旧习惯：网上很多老资料推荐用 jhat 分析堆 dump，但 jhat 早在 JDK 9 就已被移除，JDK 8 上它也早已过时，正确选择是 Eclipse MAT 或 VisualVM（JDK 9 起需要单独下载）。定位泄漏的标准流程分四步。

第一步，确认是溢出还是泄漏。溢出（OOM）是“确实装不下了”，泄漏是“该回收的没回收”。前者看错误类型，后者靠 jstat -gc 观察 OU 是否逐轮抬高。

第二步，把堆 dump 出来。两种方式，线上优先第二种：

# 方式一：手动 dump（:live 只抓存活对象，会触发一次 Full GC，线上慎用）
jmap -dump:format=b,file=/tmp/dump.hprof 6219
jmap -dump:live,format=b,file=/tmp/dump.hprof 6219

# 方式二：启动参数，OOM 时自动落盘（推荐）
java -Xms512m -Xmx512m \
     -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/data/dump -jar app.jar

# 补充：先看对象数量排名，快速找嫌疑类
jmap -histo:live 6219 | head -20

jmap -histo 输出里，[C 是 char[]、[B 是 byte[]、[I 是 int[]，[Ljava.lang.Object; 是对象数组。如果看到 [C 或 byte[] 的 instances 与 bytes 异常庞大，基本可以直接怀疑“大字符串 / 大文件内容被长期持有”，这是最常见的一类泄漏。

第三步，用 MAT 打开 hprof。不要一上来就逐个类翻实例，先看它生成的 Leak Suspects 报告和 Dominator Tree（支配树）。支配树按“谁占住的内存最多”排序，并且只保留真正的持有者，比单纯的引用列表直观得多。顺着支配树从 Thread → ThreadLocal / HashMap → 业务对象一路展开，通常三五层就能找到那个本该被释放、却被静态集合或缓存扣住的容器。

第四步，区分正常与异常。如果确认是业务需要（比如合理的本地缓存），就调大 -Xmx，并把缓存换成有容量上限的实现（Caffeine / LRU）；如果是 bug，就修持有逻辑。把 -Xmx 调大只是买时间，泄漏的斜率不变，早晚还会 OOM。

另外提醒两类容易被忽略的 OOM。java.lang.OutOfMemoryError: Metaspace 通常来自动态生成类（CGLIB 代理、Groovy 脚本反复编译），需要限制缓存并设置 -XX:MaxMetaspaceSize。OutOfMemoryError: Direct buffer memory 来自 NIO 的 ByteBuffer.allocateDirect，堆 dump 里看不到，只能靠 -XX:MaxDirectMemorySize 和 Native Memory Tracking（-XX:NativeMemoryTracking=summary 配合 jcmd <pid> VM.native_memory）来查。

五、生产案例集：五个真实 Bug 的定位过程

前面几节讲的是「用什么工具、看什么指标」，这一节换成具体案例。下面五个问题都来自真实生产环境，每个案例的结构都是「现象 → 排查 → 根因 → 修复」，覆盖了空指针、集合契约、缓存、懒加载与前端异常五类高频故障。它们的共同点是：报错信息往往指向错误的位置，真正的根因在上一层。

案例一：自动拆箱导致的 NullPointerException

现象：一个「判断贷款记录是否生成合同」的接口偶发 500，日志只有一行 NullPointerException，堆栈指在 if 判断那一行上，而那一行看起来只是比较大小。

// 出问题的代码：字段在类里声明为 Integer
Integer contractGeneration = loanRecordFromDB.getContractGeneration();
// 当 contractGeneration 为 null 时，下面这行会抛 NullPointerException
if (contractGeneration == 0) {
    return JsonResult.fail("尚未生成合同");
}

排查：这行没有方法调用、也没有明显的空引用，为什么还会 NPE？关键在于 contractGeneration 是包装类型 Integer，而 0 是基本类型 int。Java 的 == 在「包装类型与基本类型」比较时会触发自动拆箱，底层实际执行的是 contractGeneration.intValue() == 0；当字段为 null 时，intValue() 直接抛 NPE。数据库里这个字段允许为空，历史数据中确实存在 null，所以只在部分记录上复现。

修复：把判断改成空安全的写法，并明确「null 代表什么」这一业务语义。

// 写法一：先判空再比较（推荐，语义最清楚）
if (contractGeneration == null || contractGeneration == 0) {
    return JsonResult.fail("尚未生成合同");
}

// 写法二：用常量在前，避免另一个方向的 NPE（"x".equals(y) 的惯用法同理）
if (Integer.valueOf(0).equals(contractGeneration)) {
    return JsonResult.fail("尚未生成合同");
}

经验：三条规则可以避开这一类问题。

  • 包装类型之间比较值必须用 equals：== 比的是引用，只有 -128~127 的缓存区间会「碰巧」相等。
  • 包装类型与基本类型比较前先判空，或者直接用 Objects.equals(a, b)。
  • 能定成基本类型或给默认值就不要用包装类型：比如统计计数字段在数据库里设 NOT NULL DEFAULT 0，从源头消灭 null。

此外 JSONNull 是同一类问题：某些 JSON 库解析出的 null 是它自己的 JSONNull 对象而不是 Java null，用 obj == null 判断不出来，必须调用 JSONObject.isNull(key) 或 obj.isNull()。

案例二：HashSet 去重失效与顺序依赖

现象：明明用 HashSet 做了去重，结果列表里依然出现重复元素；或者去重后的顺序每次都不同，导致分页数据错乱。

排查：去重依赖 hashCode() 与 equals()。如果实体类只重写了其中一个（IDE 自动生成时手动删掉了一部分），或者用了 Lombok 但没加 @EqualsAndHashCode，就会出现「哈希不同但内容相同」的元素全部被保留。顺序问题则是因为 HashSet 基于哈希表，迭代顺序与插入顺序无关；HashMap 在 JDK 8 之后虽然大体按哈希桶顺序，但扩容后会重新分布。

修复：按「是否需要保序」选择容器。

// 去重且保序：LinkedHashSet 保留插入顺序
Set<String> ordered = new LinkedHashSet<>(list);

// 按业务字段去重且保留第一条：用 Map 而不是 Set
Map<String, Order> unique = new LinkedHashMap<>();
for (Order order : orders) {
    unique.putIfAbsent(order.getOrderNo(), order);   // 已存在则不覆盖，保留先出现的
}
List<Order> result = new ArrayList<>(unique.values());

经验：实体类作为 Set/Map 的 key 时，必须同时重写 hashCode 与 equals（Lombok 用 @EqualsAndHashCode，注意默认会包含所有字段，业务主键场景应显式指定 of = "orderNo"）；需要顺序一律用 LinkedHashMap / LinkedHashSet，需要排序用 TreeMap。还有一个隐蔽的坑：作为 key 的对象在放入集合后被修改了参与哈希的字段，会导致再也查不到它——所以 key 最好是不可变对象。

案例三：缓存该放什么、怎么失效

现象：接口 99.95% 的响应在几十到几百毫秒，但每天总有少量请求超过 1 秒甚至 5 秒，重放同样的请求报文却又是毫秒级返回。日志显示慢请求集中在高峰期，且都消耗在数据库查询上。

排查思路：手动重放正常 → 说明不是数据量或 SQL 本身的问题，而是数据库在高峰期有压力（大量写影响读、锁竞争、内存不足导致索引换出）。既然慢请求占比只有万分之几，做全量缓存投入产出比不高，于是先按「调用量 × 数据变化频率」筛选出值得缓存的接口，再逐个决定失效策略。

筛选与失效策略可以整理成一张判断表：

  • 字典表、配置类数据（国家、币种、费率）：读多写极少 → 缓存，用主动刷新（后台改配置时直接删缓存），可以设长过期时间兜底。
  • 热点业务数据（首页推荐、商品详情）：读多写少但要准 → 缓存，用过期失效 + 写时删除，过期时间取业务能容忍的脏数据窗口（如 5 分钟）。
  • 强一致要求的数据（账户余额、库存）：不缓存，或只在极短时间（秒级）内缓存，并接受「缓存与库不一致」的风险由业务补偿。
  • 个性化、低命中率数据（按用户维度的查询）：缓存命中率太低，占用内存却不省数据库 → 不缓存。

结论与经验：缓存决策的依据是「读频率、写频率、一致性容忍度」三个维度，不是「这个接口慢就缓存」。落地时还要配套三件事：

  • 空值缓存：防止缓存穿透，把查询不到的结果也缓存一个短过期时间的空标记。
  • 过期时间加随机抖动：避免同一时刻大批 key 同时失效造成缓存雪崩。
  • 监控命中率：命中率长期低于 50% 的缓存应当直接下掉，它在浪费内存。

案例四：懒加载异常与会话丢失

现象：接口偶尔报 LazyInitializationException: could not initialize proxy - no Session，尤其在做数据导出、异步任务时必现。

排查：JPA/Hibernate 的关联对象默认是懒加载，只有在 EntityManager（Session）打开期间才能去数据库补数据。而事务结束后 Session 就被关闭了，此时再访问 order.getItems() 就会抛这个异常。异步线程、定时任务、@Async 方法里尤其容易触发，因为它们运行在事务边界之外。

// 出问题的写法：事务方法返回实体，调用方在外面访问懒加载字段
@Transactional(readOnly = true)
public Order findOrder(Long id) {
    return orderRepository.findById(id).orElseThrow();   // 返回时事务已结束
}

// 调用方（无事务）：Session 已关闭，下面这行会抛 LazyInitializationException
order.getItems().size();

修复：按推荐程度排序有四种方案。

  • 一是查询时就取到需要的数据（JOIN FETCH 或 @EntityGraph），这是最干净的做法，一次 SQL 解决问题。
  • 二是用 DTO 在事务内完成转换，把实体转成不含懒加载代理的普通对象再返回。
  • 三是把访问懒加载字段的逻辑放进事务内（在 service 层组装好结果）。
  • 四才是延长 Session 生命周期（OpenEntityManagerInViewFilter / spring.jpa.open-in-view=true）。
// 方案一：查询时一次取回关联数据
public interface OrderRepository extends JpaRepository<Order, Long> {

    @Query("select o from Order o join fetch o.items where o.id = :id")
    Optional<Order> findWithItemsById(@Param("id") Long id);
}

// 方案二：在事务内转成 DTO
@Transactional(readOnly = true)
public OrderDto findOrderDto(Long id) {
    Order order = orderRepository.findById(id).orElseThrow();
    return new OrderDto(order.getNo(), order.getItems().size());   // 事务内访问，安全
}

经验：open-in-view 是 Spring Boot 默认开启的「兜底开关」，它确实能消除这个异常，但代价是把数据库连接一直持有到视图渲染完成，高并发下会迅速耗尽连接池。正确策略是：明确关掉 spring.jpa.open-in-view=false，强制自己在 service 层把数据组装完——让异常在开发阶段暴露，好过在生产高峰期连接池被打满。

案例五：前端资源加载失败引发的「重复刷新」

现象：登录页偶发反复自动刷新，用户看到页面闪动几下后才正常，后端日志显示登录接口被连续调用多次。

排查：这类问题的入口通常在前端而不是后端。先看浏览器 Network 面板：如果 favicon.ico 返回 404 或 500，而页面里有拦截器（axios 响应拦截器 / 全局 window.onerror）把「任意请求失败」当作「登录态失效」来处理，就会触发「跳登录 → 重新加载 → 又失败」的循环。另一个常见触发源是静态资源 CDN 报错，同样被统一错误处理逻辑误判。

修复：一是补上 favicon（放在站点根目录或显式声明 <link rel="icon">），并从源头治理静态资源 404。二是修正错误处理逻辑，只对业务接口的 401/403 做跳转，静态资源与第三方请求的失败不应影响登录态判断。三是给跳转加防抖，避免短时间内重复触发。

经验：遇到「前端反复刷新/重复请求」类问题时，排查顺序应该是「打开 Network 看哪个请求失败了 → 看错误处理逻辑把它当成了什么 → 再看后端」。反过来只从后端查接口调用次数，很容易在错误的方向上浪费大量时间。

六、常见坑与小结

把这五个案例的结论压缩成一张速查表：

  • 包装类型比较：值比较一律 equals 或 Objects.equals；与基本类型比较前判空；数据库字段尽量设默认值。
  • 集合去重与顺序：重写 equals 必须同时重写 hashCode；需要保序用 LinkedHashSet/LinkedHashMap；key 不要用可变对象。
  • 缓存决策：按「读频率、写频率、一致性容忍度」三维判断，不是「慢就缓存」；配套空值缓存、过期抖动与命中率监控。
  • 懒加载：优先 JOIN FETCH 或事务内转 DTO；open-in-view 应显式关闭，用它兜底会拖垮连接池。
  • 前端反复刷新：先看 Network 里失败的是哪个请求，再检查统一错误处理是否误判了静态资源失败。

五条经验的共同点是先定位「真正出错的那一层」再动手改。NPE 的堆栈指向 if 行，根因是自动拆箱；慢请求看起来是数据库问题，根因是高峰期资源竞争；懒加载异常报在调用方，根因是事务边界；页面刷新看起来是后端接口问题，根因在前端错误处理。定位方法其实很朴素：缩小范围（能否稳定复现）、对比变量（哪个条件不同）、看证据（日志、堆栈、网络面板），把这三步做扎实，大多数线上问题都能在一小时内收敛。

最后把容易翻车的地方集中列一下：

  • 生产环境执行 jmap -dump 会 STW（:live 还会额外触发 Full GC），大堆上可能停顿数秒甚至更久。上线前就应该给 JVM 配好 +HeapDumpOnOutOfMemoryError，不要等出事再手动 dump。
  • dump 文件可能和堆一样大（几个 G 很常见），先确认磁盘空间，传输时记得压缩，不要把服务器磁盘写满引发二次故障。
  • 只抓一次线程快照就下结论。单次 jstack 只是瞬间切片，必须多次采样、纵向对比，才能区分“一直卡住”和“碰巧路过”。
  • jstack 看不到 ReentrantLock 死锁，需要 jcmd <pid> Thread.print -l 或自己分析锁依赖。
  • 错把“GC 频繁”当成“内存泄漏”。判断标准只有一个：Full GC 后老年代能不能降下来。

小结一下本章的排查骨架：先分诊（症状 → 工具），再采样（多次而非一次），后定位（栈顶方法 / 支配树对象），最后回到代码修根因。CPU 高就用 top -Hp 加 jstack 翻译线程号；卡死就用 jstack 找环形等待，修法是统一加锁顺序；内存问题先用 jstat 分清溢出与泄漏，再用 jmap dump、MAT 看支配树。把这套流程走熟，就有了不依赖任何外部监控也能救火的能力。工具输出的每一个字段，都对应着 JVM 运行时的一块真实内存或一条真实线程，理解它们比记住命令更重要。
