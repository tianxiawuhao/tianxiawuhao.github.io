7.4 Shell 脚本与定时任务

Posted on 2026-09-19，6 min read

应用部署上线只是开始：日志每天在涨、备份每周要做、健康检查每分钟都该有人看一眼。这些事没有技术含量，却极其消耗人力。本章解决的就是“让机器自己按时干活”：先写一个能上生产的 Shell 脚本，再用 crontab 把它挂到时间轴上。本章适合已经会在 Linux 上敲 ls、cd、tar、grep 的 Java 开发者，所有示例都可以在测试机上直接运行。

一、Shell 脚本的最小可用骨架

Shell 脚本的本质，就是把平时逐条敲的命令存成文件、按顺序执行。第一行是 shebang，告诉系统用哪个解释器；接着用 set -euo pipefail 把三种常见事故变成显式失败。命令出错就退出（-e），用到未定义变量就报错（-u），管道中任一环失败则整条管道算失败（pipefail）。生产脚本不加这三个开关，最容易出现“脚本返回 0，其实什么也没干”的假成功。

变量的规则只有两条，却常被忽略：赋值时等号两边不能有空格（A=1 对，A = 1 会被当成执行命令 A）；引用时尽量写成 "${VAR}"，因为 $VAR 遇空格会断词。$(命令) 取命令输出，位置参数 $1 是第一个参数、$# 是参数个数、$0 是脚本名。

引号的差别要分清楚：单引号里的一切都原样保留，双引号里变量和 $(命令) 仍会被展开，所以拼路径、拼 SQL 这类场景用双引号。$? 是上一条命令的退出码（0 表示成功），脚本里可以用它做分支判断。脚本不生效时，先不要急着改逻辑：用 bash -n script.sh 查语法，再用 bash -x script.sh 把每条命令和展开后的变量打印出来，问题基本一目了然。

#!/bin/bash
set -euo pipefail

APP_HOME=/opt/myapp
LOG_DIR="${APP_HOME}/logs"
TODAY="$(date +%F)"

# 参数校验：缺失就给出用法并退出
if [ "$#" -lt 1 ]; then
  echo "用法: $0 <环境> [保留天数]" >&2
  exit 1
fi

ENV_NAME="$1"
KEEP_DAYS="${2:-7}"   # 第二个参数没传时默认为 7

echo "环境=${ENV_NAME} 日志目录=${LOG_DIR} 保留=${KEEP_DAYS} 天 日期=${TODAY}"

再补两点现代 bash 的写法：

  • 遍历一组路径时用数组，而不是把多个值拼进一个字符串。arr=(a b c) 定义、arr+=(d) 追加、"${arr[@]}" 展开——这里的双引号不能省，省了等于把每个元素按空格重新断词，等于白用数组。取长度写 ${#arr[@]}，下标从 0 开始；关联数组要 bash 4.0 以上（Rocky 9 与 Ubuntu 22.04 自带的都是 bash 5.1，够用）。
  • shebang 用 #!/usr/bin/env bash 比写死 #!/bin/bash 更能适应不同发行版。把 set -euo pipefail 升级成 set -Eeuo pipefail，再配一条 trap ... ERR，函数内部出错时也能打印出错位置，脚本"失败得响亮"且留下现场。
#!/usr/bin/env bash
set -Eeuo pipefail
trap 'echo "[ERR] ${BASH_SOURCE[0]}:${LINENO} 执行失败" >&2' ERR

# 数组：批量处理日志，元素里的空格不会被拆开
logs=()
for f in /var/log/myapp/*.log; do
  [ -e "$f" ] || continue          # 通配符没匹配到时会留下字面量，必须判存在
  logs+=("$f")
done
echo "共 ${#logs[@]} 个日志文件"

for f in "${logs[@]}"; do           # 必须加引号，否则含空格的文件名会被拆成多个参数
  gzip -f "$f"
done

# 关联数组（bash 4+）：按服务名计数
declare -A counter=([nginx]=3 [mysql]=0)
printf 'nginx=%s mysql=%s\n' "${counter[nginx]}" "${counter[mysql]}"

二、流程控制与函数

判断条件用 if，字符串和文件比较靠 [ ]（或 bash 增强版 [[ ]]）。多分支用 case 比一长串 elif 清楚；遍历用 for，逐行读取文件用 while read。这里有个容易忽略的点：[ ] 是命令，所以方括号内侧必须有空格，[ -d "$dir" ] 才对。

遍历文件时有一个经典反例：for f in $(ls) 会把带空格的文件名拆成两段。正确写法是 for f in "$LOG_DIR"/*.log，或者更稳妥地逐行读取 while IFS= read -r line; do ...; done < list.txt。其中 IFS= 保证行首行尾的空格不被吃掉，-r 保证反斜杠不被解释。

函数用 名字() { ... } 定义，函数内的临时变量加 local 避免污染全局。函数返回值只能表示 0–255 的退出码（0 表示成功），想“返回字符串”就用 echo 输出、调用方用 $(函数名) 接住。

#!/bin/bash
set -euo pipefail

# 返回 0 表示健康，非 0 表示异常
check_service() {
  local name="$1"
  if systemctl is-active --quiet "$name"; then
    echo "[OK] ${name} 正在运行"
    return 0
  fi
  echo "[FAIL] ${name} 未运行" >&2
  return 1
}

case "${1:-status}" in
  status)
    for svc in nginx mysqld; do
      check_service "$svc" || true   # 单个服务失败不中断整体检查
    done
    ;;
  restart)
    systemctl restart nginx
    ;;
  *)
    echo "未知参数: $1" >&2
    exit 2
    ;;
esac

三、crontab：五个时间字段加一条命令

crond 是 Linux 上的定时任务守护进程，每分钟醒来一次，检查有没有到点的任务。任务分两类：用户级任务用 crontab -e 编辑，文件实际存在 /var/spool/cron/用户名；系统级任务写在 /etc/crontab 或 /etc/cron.d/ 下。两者的区别是系统级每行多一个用户名字段。

日常管理只需要四个选项。crontab -l 列出任务、crontab -e 编辑任务、crontab -r 删除全部任务、crontab -u 用户名 -e 由 root 代管他人任务。谁能使用 crontab 由两个白名单/黑名单文件决定：/etc/cron.allow 里列出的用户才允许使用，/etc/cron.deny 里列出的用户被禁止。两者同时存在时以 allow 为准，都不存在时默认只有 root 能用。此外，/etc/cron.daily、/etc/cron.hourly 这些目录是靠 run-parts 批量执行的。它只运行文件名中不含点的可执行文件，所以放进去的脚本不要写成 clean.sh。

用户级 crontab 每行六个字段：分 时 日 月 周 命令。分钟 0–59，小时 0–23，日 1–31，月 1–12，星期 0–7（0 和 7 都表示周日）。五个时间字段支持四种写法：* 任意值、1,15 列表、8-11 范围、*/10 步长（每 10 分钟）。另外，星期和日两个字段是“或”的关系：写了“4 号”又写了“周一”，则 4 号和每周一都会执行，这是新手最常误判的一条规则。

步长（*/n）的语义要核准：它不是"从现在起每隔 n 个单位"，而是"从该字段的最小值开始、按 n 递增"。所以分钟位 */2 就是 0、2、4…58 分，正好是"每 2 分钟"；小时位 */2 是 0、2、4…22 点，间隔均匀但起点固定在 0 点。真正容易踩的是日位：*/2 展开成 1、3、5…31 号，遇到只有 30 天的月份会在月初出现"隔一天"的错位，跨月并不是均匀的"每隔一天"。还有一个细节：当 n 不能整除字段宽度时最后一跳会变短，例如分钟位 */7 得到 0、7、…、56，56 分到下一小时的 0 分只隔 4 分钟。要"每 2 分钟"就用分钟位 */2，别指望日位。

邮件投递由 MAILTO 控制，它是可以写在 crontab 顶部（或任务行之前）的环境变量：MAILTO="" 表示任务输出直接丢弃、不投递；MAILTO="ops@example.com" 表示把任务的标准输出与报错当邮件发出去。后者有两个常被忽略的前提。宿主机要装好并运行 MTA（Rocky 9 最小化安装默认不带 postfix/sendmail，Ubuntu 22.04 也常常只有占位），否则邮件连队列都进不去。而且只有"有输出"时才会发信，写了 >/dev/null 2>&1 的任务永远不会有邮件。生产上更推荐 MAILTO="" 关掉邮件，把输出重定向进日志文件交给 logrotate（或 systemd timer 的 OnFailure=）来告警。注意 MAILTO 只影响输出投递，不影响任务是否执行；任务所用 shell 由 SHELL 决定，默认是 /bin/sh——Ubuntu 22.04 的 /bin/sh 是 dash，[[ ]]、数组、source 都不认，所以任务行最好只调用 #!/usr/bin/env bash 的脚本，或显式写 SHELL=/bin/bash。部分实现（如 RHEL/Rocky 上的 cronie）还支持 CRON_TZ=Asia/Shanghai 指定时区，免得服务器仍是 UTC 时按错误时间跑。

# 分 时 日 月 周   要执行的命令
*/5 * * * *  /opt/myapp/bin/health-check.sh >> /var/log/myapp/health.log 2>&1
0 3 * * *    /opt/myapp/bin/clean-logs.sh prod 7 >/dev/null 2>&1
30 4 * * 0   /opt/myapp/bin/backup.sh
0 2 1 * *    /opt/myapp/bin/report.sh

几点约定值得记牢。第一，任务里一律写绝对路径。第二，命令输出要么追加到日志文件，要么丢进 /dev/null；否则 crond 会把每次输出当邮件发给你，日积月累塞满邮件队列。第三，crontab -l 可以随时导出当前任务做备份，误删了用 crontab 备份文件 恢复。CentOS 7 以后 crond 由 systemd 管理，重启用 systemctl restart crond。改完 /etc/crontab 只需 systemctl reload crond；而用 crontab -e 保存的任务会立即生效，不必重启。

四、实战：每天凌晨清理日志

日志清理是定时任务最典型的用途。核心命令是 find：-type f 只要普通文件，-name "*.log" 限定后缀，-mtime +7 表示修改时间在 7 天以前。先加 -print 预览删除清单，确认无误再让它删除；线上脚本建议保留 -print，把删掉的文件名记进日志，事后可追溯。

-mtime 的 +/- 一定要记准，写反了就是灾难。-mtime n 的规则是"把文件年龄向下取整成整天数，再与 n 比较"。-mtime +7 是第 8 天及更早（年龄大于 7×24 小时），正是"删掉 7 天前的旧日志"；-mtime 7 只匹配年龄落在 7～8 天那一档。而 -mtime -5 是年龄小于 5 天，也就是刚刚写入的最新文件——如果照抄成 find "$LOG_DIR" -name "*.log" -mtime -5 -delete，删掉的正是你还要用的当前日志，这是这类脚本最惨的一种写法。另外两点：-mtime 以 24 小时取整，边界不精确，要卡到分钟用 -mmin +$((KEEP_DAYS*1440))；-delete 会隐含 -depth，删除失败会直接报错退出，线上仍建议保留 -print 先预览。

#!/bin/bash
set -euo pipefail

LOG_DIR="${1:-/var/log/myapp}"
KEEP_DAYS="${2:-7}"

[ -d "$LOG_DIR" ] || { echo "目录不存在: ${LOG_DIR}" >&2; exit 1; }

# 文件锁：上一次清理没跑完时直接跳过，避免两个进程同时删
exec 9>"/tmp/clean-logs.lock"
flock -n 9 || { echo "上一次清理仍在执行，本次跳过" >&2; exit 0; }

# 先归档 3 天前的日志，再删除超期的
find "$LOG_DIR" -type f -name "*.log.1" -mtime +3 -exec gzip -f {} \;
find "$LOG_DIR" -type f -name "*.log" -mtime +"$KEEP_DAYS" -print -delete

echo "$(date '+%F %T') 清理完成，${LOG_DIR} 保留最近 ${KEEP_DAYS} 天"

脚本写好后先用 bash -n 做语法检查，再手动跑一遍确认输出，最后才交给 crontab。任务行可以写成 0 3 * * * /opt/myapp/bin/clean-logs.sh /var/log/myapp 7，凌晨三点执行，与业务高峰错开。

五、systemd timer：cron 的现代替代

现代发行版都自带 systemd（Rocky 9 是 systemd 252，Ubuntu 22.04 是 249），同一件事有更"原生"的做法：systemd timer。它不是要淘汰 cron，而是把定时任务纳入 systemd 的统一管理，换来几项 cron 给不了的能力。输出自动进 journald（journalctl -u 直接查，不用自己接日志），Persistent=true 会在关机期间错过的任务于开机后补跑一次（anacron 的现代替代），还可以声明 After=/Requires= 依赖、用 MemoryMax=/CPUQuota= 限制资源，失败时还能用 OnFailure= 拉起告警单元。

timer 由两个单元文件组成：.service 说明"做什么"，.timer 说明"什么时候做"。下面把第四节的日志清理改造成 timer，触发效果与 0 3 * * * 等价。

# /etc/systemd/system/clean-logs.service
[Unit]
Description=清理应用日志

[Service]
Type=oneshot
User=appuser
ExecStart=/opt/myapp/bin/clean-logs.sh /var/log/myapp 7
# /etc/systemd/system/clean-logs.timer
[Unit]
Description=每天 03:00 清理应用日志

[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true          # 关机期间错过的任务，开机后补跑一次
RandomizedDelaySec=5m    # 抖动，避免多台机器同一秒同时开跑
Unit=clean-logs.service

[Install]
WantedBy=timers.target
sudo systemctl daemon-reload
sudo systemctl enable --now clean-logs.timer   # 启动且开机自启
systemctl list-timers --all                    # 看下次触发时间与上次结果
journalctl -u clean-logs.service --since today # 运行日志
systemd-analyze calendar '*-*-* 03:00:00'      # 先验证 OnCalendar 表达式再上线

怎么选：习惯 cron 五个字段、任务轻量且只在一台机器上，继续用 cron 完全没问题；需要补跑、要留结构化日志、要与其它 systemd 单元编排依赖，或本机本来就用 systemd 管服务，就写 timer。两者都以本机时区为准，服务器上先 timedatectl 确认时区，能省掉一大批"为什么凌晨三点变成了上午十一点"的排查。

需求cron / crontabsystemd timer
时间表达五个字段加 */nOnCalendar= 日历表达式
错过补跑要靠 anacronPersistent=true
运行日志自己重定向加 logrotatejournald，journalctl -u
失败告警依赖 MAILTO 与 MTAOnFailure= 拉起告警单元
资源限制无MemoryMax= 等 cgroup 选项

六、常见坑与排查思路

  • 手动能跑、cron 不跑：九成是环境变量。crond 启动任务时给的是一份极简环境：不加载 /etc/profile，也不加载 ~/.bashrc，PATH 通常只有 /usr/bin:/bin。这也解释了为什么在 crontab 里写 source ~/.bashrc 往往毫无作用——多数发行版的 ~/.bashrc 开头就是"非交互式 shell 直接 return"的判断（case $- in *i*) ;; *) return;; esac），而 cron 起的正是非交互式 shell，source 进去等于什么都没做。可靠的做法有三层：任务行与脚本里一律用绝对路径；需要 Java 环境就在脚本里写死 export JAVA_HOME=/usr/local/jdk 并把 $JAVA_HOME/bin 加进 PATH；确实要读 profile，就在脚本开头显式 source /etc/profile 并紧跟一句 echo "$PATH" 验证。更省事的办法是在 crontab 顶部直接声明 SHELL=/bin/bash 与 PATH=/usr/local/bin:/usr/bin:/bin，一次生效、所有任务共用。
  • 任务行里直接写 bash 语法：cron 执行任务的默认 shell 由 SHELL 决定，不写就是 /bin/sh，而 Ubuntu 22.04 的 /bin/sh 指向 dash，[[ ]]、数组、source 这些 bash 扩展在这里都不存在。把逻辑放进带 #!/usr/bin/env bash 的脚本、任务行只调用脚本，是唯一不会踩这个坑的写法。
  • 命令里有 %：crontab 把未转义的 % 当换行符，date '+%F' 会写坏任务。要写成 date '+\%F'，或者把逻辑放进脚本、任务行只调用脚本。
  • 输出不收口：不重定向就会收到一堆 cron 邮件。习惯写法是 >/dev/null 2>&1，需要留痕时改成 >> /var/log/xxx.log 2>&1。
  • 任务不生效：确认 crond 在运行（systemctl status crond）。再确认 crontab 文件名与用户一致（如 /var/spool/cron/root 要有结尾换行），同时确认 /etc/cron.deny 没有把自己挡在外面。日志在 /var/log/cron，用 tail -f /var/log/cron 边等边看最直接。
  • 别乱按：crontab -r 会删掉当前用户的全部任务且没有回收站，它和 crontab -e 在键盘上只差一个键。删之前先执行 crontab -l > ~/cron.bak。

最后补一条排查套路。搞不清是脚本问题还是 cron 问题时，把任务行临时换成 * * * * * date >> /tmp/cron-test.log 观察一分钟。日志出现说明 crond 正常，问题在脚本或环境变量；日志不出现，就要去看 /var/log/cron 和 crond 进程本身。crond 每分钟检查一次任务表，用 crontab -e 新建的任务通常一分钟内就会生效，不需要重启服务。

小结：一个靠谱的自动化任务由三部分组成。脚本本身要“失败得响亮”，也就是 set -euo pipefail、参数校验和文件锁。任务行要“说得清楚”，即绝对路径与明确的重定向。时间字段要“想明白边界”，注意星期与日的或关系和 */n 的实际含义。掌握这几条，日志清理、定时备份、健康巡检这类工作就可以彻底交给机器，只需在出问题时看一眼日志。下一章会把这套脚本能力用到容器与镜像的构建流程里。
