k8s-ingress安装使用

Posted on 2022-06-03，39 min read

1. Nginx Ingress 安装

Kubernetes 生态里有两个名字极为接近、却由不同团队维护的项目，安装前必须先分清，否则很容易出现「控制器装好了，注解却不生效」的问题。

本文演示的是 NGINX 官方维护的 nginx-ingress（仓库 nginxinc/kubernetes-ingress），它的配置注解前缀是 nginx.org/，并额外提供 VirtualServer、VirtualServerRoute 等 CRD；社区版 ingress-nginx（仓库 kubernetes/ingress-nginx）的注解前缀是 nginx.ingress.kubernetes.io/。两者互不通用，后文在用到注解的地方会分别标注。

下面开始安装 Nginx Ingress Controller。控制器安装方式包含两种：DaemonSets 和 Deployments。

  • DaemonSets：通过 hostPort 方式暴露 80 和 443 端口，每个节点（或指定节点）运行一个控制器副本，节点之间完全对等；
  • Deployments：容器只声明 containerPort，再通过 NodePort 类型的 Service 暴露控制器端口，配合外部负载均衡实现高可用。

除此之外，还需要部署Namespace，ServiceAccount，RBAC，Secrets，Custom Resource Definitions等资源，如下开始部署。

2. Ingress 资源定义

上面已经安装了一个 Nginx Ingress Controller 控制器。有了 Ingress 控制器后，我们就可以定义 Ingress 资源来实现七层负载转发了，大体上 Ingress 支持三种使用方式：1. 基于虚拟主机转发；2. 基于虚拟主机 URI 转发；3. 支持 TLS 加密转发。

这里要先建立一个关键认识：Ingress 资源本身不会转发任何流量，它只是一份声明式的规则；真正监听 80/443、解析规则并代理请求的是 Ingress Controller。两者的关系如下图所示。

Controller 通过 IngressClass（1.18 引入，1.19 起稳定）判断某个 Ingress 是否归自己处理。旧写法是在 Ingress 注解里写 kubernetes.io/ingress.class: nginx，该注解自 1.18 起已被废弃但仍向后兼容；新集群请统一使用 spec.ingressClassName。注意 kubernets.io/ingress.class（少一个 e）是常见拼写错误，写了不会报错，但任何控制器都不会识别——这正是「Ingress 创建成功却完全不生效」的典型原因。

3、上述两个步骤已创建了一个 Service，接下来定义一个 Ingress 对象，把流量转发到 ingress-demo 这个 Service；通过 spec.ingressClassName 指定由 IngressClass nginx 对应的控制器来处理这条规则

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nginx-ingress-demo
spec:
  ingressClassName: nginx
  rules:
  - host: www.test.cn
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ingress-demo
            port:
              number: 80

不过这套「改配置 + reload」的机制在集群规模较大、变更频繁时会成为瓶颈：每次变更都要重新渲染全部配置并触发一次 reload，reload 虽然能平滑处理连接，但仍有额外的资源开销。

面向微服务的大规模动态场景，可以考虑 Traefik、Envoy、Istio 等专为频繁变更设计的负载均衡或服务网格组件，它们在超大规模、超高频变更下更有优势；但在单纯的七层代理性能上，相比 Nginx、HAProxy 仍有一定差距。

关于 rewrite-target：该注解属于社区版 ingress-nginx，含义是把 path 匹配到的前缀替换成注解值。例如 path: /news 搭配 rewrite-target: / 时，请求 /news/a 会被改写成 /a，请求 /news 变成 /；若使用本文安装的 NGINX 官方 nginx-ingress，等价写法是 nginx.org/rewrites: "serviceName=service-1 rewrite=/;"。纯前缀重写在 ingress-nginx 中更推荐写成 path: /news(/|$)(.*) 加 rewrite-target: /$2，避免 /newsletter 这类同前缀路径被误匹配。

四层负载均衡无法识别 HTTPS 请求，而当前大部分业务都要求以 HTTPS 方式接入。Ingress 支持通过 Secret 存放证书与私钥来实现 HTTPS 接入，同时还能把 HTTP 请求自动跳转到 HTTPS。

这里要明确加密范围：客户端到 Ingress Controller 之间是 HTTPS，Controller 到后端 Service 默认仍然是 HTTP。也就是说 TLS 在 Controller 处终止，这样既满足了浏览器侧的加密要求，也避免了给每个后端应用单独配置证书。

7. Nginx Ingress 高级功能

7.1 定制化参数

Ingress Controller 提供了基础的反向代理功能。如果需要定制 Nginx 的特性或参数，要通过 ConfigMap 和 Annotations 两类配置来实现，两者的作用范围不同。

ConfigMap 用于指定整个控制器的基础参数，修改后会被所有 Ingress 对象继承；Annotations 只作用于某一个具体的 Ingress 对象，冲突时优先级高于 ConfigMap。

7.1.1 ConfigMap 自定义参数

安装nginx ingress controller时默认会包含一个空的ConfigMap，可以通过ConfigMap来自定义nginx controller的默认参数，如下以修改一些参数为例：

1、 定义ConfigMap参数

kind: ConfigMap
apiVersion: v1
metadata:
  name: nginx-config
  namespace: nginx-ingress
data:
  proxy-connect-timeout: "10s"
  proxy-read-timeout: "10s"
  proxy-send-timeout: "10"
  client-max-body-size: "3m"

7.1.2 Annotations 自定义参数

ConfigMap定义的是全局的配置参数，修改后所有的配置都会受影响，如果想针对某个具体的ingress资源自定义参数，则可以通过Annotations来实现，下面开始以实际的例子演示Annotations的使用。

1、修改ingress资源，添加annotations的定义,通过nginx.org组修改了一些参数，如proxy-connect-timeout，调度算法为round_robin（默认为least _conn）

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nginx-ingress-demo
  annotations:
    nginx.org/proxy-connect-timeout: "30s"
    nginx.org/proxy-send-timeout: "20s"
    nginx.org/proxy-read-timeout: "20s"
    nginx.org/client-max-body-size: "2m"
    nginx.org/fail-timeout: "5s"
    nginx.org/lb-method: "round_robin" 
spec:
  ingressClassName: nginx
  rules:
  - host: www.happylau.cn
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ingress-demo
            port:
              number: 80

2、 重新应用ingress对象并查看参数配置情况

# 输出示例：注解会体现在 Ingress 的注解列表，并作用到生成的 nginx.conf
[root@node-1 nginx-ingress]# kubectl describe ingress nginx-ingress-demo | grep -A6 Annotations

由上面的演示可知，Annotations 的优先级高于 ConfigMap，且只影响某一个具体的 Ingress 资源；两者的定义方式相近但并不等价：部分 ConfigMap 参数无法通过 Annotations 设置，反过来 Annotations 支持的部分参数在 ConfigMap 中也不存在。

按用途划分，常用的可配置项大致有五类：

  • 通用参数：proxy-connect-timeout、proxy-read-timeout、client-max-body-size、keepalive 等；
  • 日志：access-log、error-log、log-format 等；
  • 请求头部：proxy-set-header、X-Forwarded-* 系列头的透传与覆盖；
  • 认证与安全：basic-auth-secret、ssl-redirect、allow/deny 访问控制等；
  • upstream（后端）：lb-method 负载均衡算法、fail-timeout、max-fails、max-conns、next-upstream 等。

具体参数是否同时支持 ConfigMap 与 Annotations，请以下文对照表为准：ConfigMap and Annotations（社区版 ingress-nginx 的注解见 Annotations）。

8 Ingress 常见问题排查（404 / 502）

Ingress 的问题有个共同特点：配置不报错，但请求就是不通。排查时先分清是「规则没生效」还是「规则生效了但后端不可用」——前者通常返回 404，后者通常返回 502。

8.1 返回 404 Not Found

404 表示请求根本没被正确路由，常见原因有四类：

  • Ingress 没有被任何控制器接管：spec.ingressClassName 与实际 IngressClass 不一致，或注解里的 kubernetes.io/ingress.class 拼写错误，控制器会直接忽略这条规则，请求落到默认后端并返回 404。
  • 域名不匹配：请求的 Host 与 rules[].host 不一致。声明了 host 的规则只匹配该域名，直接用节点 IP 访问通常匹配不上。
  • 路径不匹配：pathType 与路径写法不匹配。Prefix 按前缀匹配，Exact 要求完全相等；rewrite-target 会在转发前改写路径，后端拿到的已不是原始路径。
  • 后端应用自身返回 404：Controller 已经完成转发，但应用没有对应资源（常见于路径被重写后访问了不存在的文件）。此时 Controller 的访问日志里会有一条 404 记录。
# 1. 确认 Ingress 是否被控制器接管、规则与后端是否符合预期
kubectl get ingress -A
kubectl describe ingress nginx-ingress-demo

# 2. 查看控制器日志中是否有该 Ingress 的 AddedOrUpdated 事件
kubectl logs -n nginx-ingress -l app=nginx-ingress --tail=100

# 3. 检查控制器最终生成的 nginx 配置（nginx -T 会打印完整配置）
kubectl exec -it <controller-pod> -n nginx-ingress -- nginx -T | grep -A5 server_name

8.2 返回 502 Bad Gateway

502 说明 Controller 已经匹配到规则并把请求发给了 upstream，但 upstream 没有正常响应。按下面的顺序排查：

  • Endpoints 为空：Service 的 selector 与 Pod 的 labels 不匹配、Pod 未就绪（readinessProbe 未通过）、或 targetPort 指向了 Pod 上不存在的端口名，都会导致 upstream 中没有任何 server。
  • 端口写错：backend.service.port.number 要填 Service 暴露的端口，而不是容器的端口，两者的映射在 Service 的 targetPort 上完成。
  • 后端只监听 127.0.0.1：容器内进程若绑定在回环地址上，来自 Pod 外部的请求必然连接失败。
  • 协议不匹配：后端是 HTTPS 却按 HTTP 代理（或反之）。ingress-nginx 需要 nginx.ingress.kubernetes.io/backend-protocol: "HTTPS"，nginx-ingress 对应 nginx.org/backend-protocol。
  • 超时过短：大请求体或慢接口会触发 proxy-read-timeout，表现为间歇性的 502/504，可放到 ConfigMap 或注解里调大。
# 从链路末端往前查：先确认 Pod，再确认 Endpoints，最后看配置文件
kubectl get pods -o wide
kubectl describe svc ingress-demo
kubectl get endpoints ingress-demo
kubectl exec -it <controller-pod> -n nginx-ingress -- cat /etc/nginx/conf.d/default-nginx-ingress-demo.conf

一个实用的判断技巧：404 看规则，502 看后端。404 时重点核对 IngressClass、host、pathType 与 rewrite 规则；502 时重点核对 Endpoints、端口与后端协议。两侧都确认无误后，再检查 Controller 的 reload 是否成功——配置存在语法错误时新配置不会生效，但旧配置仍在运行，因此现象会非常隐蔽。
