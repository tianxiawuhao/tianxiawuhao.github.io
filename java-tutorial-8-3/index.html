Spark 核心

Posted on 2026-09-19，9 min read

用 Hadoop MapReduce 写过一个 WordCount，就能体会它的两个硬伤：几乎每一步都要落盘，迭代算法只能反复启动作业。Spark 把中间结果尽量留在内存里，并提供了更接近函数式编程的 API，让「分布式计算」写起来像操作本地集合。本章只讲 Spark 的核心：RDD 抽象、Transformation 与 Action 的区别、DAG 与宽窄依赖、Shuffle 的代价，以及 Spark SQL 与常用调优手段。适合已经会 Java、了解 HDFS 与 MapReduce 基本概念的读者；示例基于 Spark 3.5.x，本地用 local[*] 就能跑通。

一、RDD：Spark 的核心抽象

RDD 是 Resilient Distributed Dataset（弹性分布式数据集）的缩写，注意「弹性」不是「伸缩」。一个 RDD 由五部分描述：一组分区（partition）、作用在每个分区上的计算函数、对其他 RDD 的依赖列表、可选的分区器（Partitioner，决定某个 key 落到哪个分区）以及数据的优先位置（用于数据本地性调度）。

源资料里常说「RDD 是只读集合」，更准确的说法是不可变（immutable）：RDD 本身不能原地修改，所有「修改」都是算子生成的新 RDD，新旧 RDD 之间靠血缘（lineage）相连。某个分区因节点故障丢失时，Spark 顺着血缘重算这一个分区即可恢复，这才是「弹性」和容错的真正含义，而不是把数据存了三份。

一个 Spark 应用由一个 Driver 进程发起：Driver 里的 SparkContext 向集群管理器（YARN、Kubernetes 或 Standalone）申请资源，在每台 Worker 上启动 Executor，Executor 内以 Task 为单位并行计算各个分区。这里有两条约定的纪律：传给算子的闭包函数以及它引用的外部对象必须可序列化；同一个 JVM 中同时只能有一个活跃的 SparkContext，因此 Spark 2.0 之后统一用 SparkSession 作为入口，内部再去管理那个唯一的 context。

还有一条贯穿全章的规则：惰性求值。Transformation 只记录「要做什么」，并不会立刻执行；只有遇到 Action，Spark 才把这条计算链提交成作业。

二、算子：Transformation 与 Action

算子分两类。Transformation 从已有 RDD 生成新 RDD，是惰性的，例如 map、filter、flatMap、mapPartitions、distinct、union、join、reduceByKey；Action 把结果返回 Driver 或写入外部存储，会触发真正的计算，例如 count、collect、take、reduce、foreach、saveAsTextFile。源资料把 reduceByKey 和 saveAsTextFile 一起称作「动作」，这是错的：reduceByKey 是 Transformation，而且是会产生 Shuffle 的宽依赖，只有 saveAsTextFile 这类才是 Action。

import org.apache.spark.SparkConf;
import org.apache.spark.api.java.JavaPairRDD;
import org.apache.spark.api.java.JavaRDD;
import org.apache.spark.api.java.JavaSparkContext;
import scala.Tuple2;

import java.util.Arrays;

public class WordCount {
    public static void main(String[] args) {
        SparkConf conf = new SparkConf()
                .setAppName("WordCount")
                .setMaster("local[*]");   // 集群提交时删掉这行，改由 spark-submit 指定 master
        JavaSparkContext sc = new JavaSparkContext(conf);

        JavaRDD<String> lines = sc.textFile(args[0]);
        JavaPairRDD<String, Integer> counts = lines
                .flatMap(line -> Arrays.asList(line.split("\\s+")).iterator())
                .filter(word -> !word.isEmpty())
                .mapToPair(word -> new Tuple2<>(word, 1))
                .reduceByKey(Integer::sum);        // Transformation：只记录血缘

        counts.saveAsTextFile(args[1]);            // Action：到这里才真正提交作业
        sc.stop();
    }
}

同样能完成分组统计，reduceByKey 和 groupByKey 的代价却差很多：reduceByKey 会先在 map 端做一次局部聚合（相当于 MapReduce 的 Combiner），只有聚合后的结果进入 Shuffle；groupByKey 则把所有 value 原样拉到 reduce 端再自己遍历，键对应的数据量一大就容易 OOM。所以能用 reduceByKey、aggregateByKey、combineByKey 的场景，就不要用 groupByKey 再 mapValues。

调试时可以先用 toDebugString() 把血缘和分区数打印出来，它比反复猜测「这一行到底触发几个作业」直观得多；也可以对照 Spark UI 的 Stages 页面，看看每个 Stage 的 Task 数是否等于分区数。另一个新手常犯的错误是：同一个 RDD 被多个 Action 重复使用时忘了 cache()，于是 Spark 每次都从头重算整条血缘，表现就是「同一段代码第二次跑依然那么慢」。

三、DAG、宽窄依赖与 Shuffle

Action 触发后，DAGScheduler 从结果 RDD 倒推整条血缘，得到一张有向无环图（DAG），再按依赖类型切分 Stage。依赖分两种：

  • 窄依赖（narrow dependency）：每个父分区最多被一个子分区使用，如 map、filter、flatMap、mapPartitions、union、coalesce(false)。父分区和子分区可以做流水线（pipeline）合并，在同一个 Task 里顺序执行，不需要跨节点搬数据。
  • 宽依赖（wide dependency，也叫 Shuffle Dependency）：一个子分区依赖全部父分区，如 reduceByKey、groupByKey、sortByKey、repartition、distinct，以及未做协同分区的 join。数据必须按 key 重新分发，这就是 Shuffle。

Spark 切 Stage 的规则很简单：遇到宽依赖就切一刀，一段连续的窄依赖会被合并进同一个 Stage。Stage 内部按分区数量拆成一堆 Task 并行执行，所以「一个 Job 由若干 Stage 组成，一个 Stage 由若干 Task 组成」。Shuffle 之所以昂贵，是因为它同时做了三件重活：map 端把数据按分区排序后写到本地磁盘（先生成索引文件，再生成数据文件），reduce 端通过网络拉取（fetch）属于自己分区的数据，全程还要反复序列化与反序列化。MapReduce 被诟病「不擅长 DAG 计算」，正是因为它的每个依赖都要落盘并重新起作业，而 Spark 用内存缓存加上 DAG 调度，把窄依赖的中间结果留在了内存和流水线里。

理解了这一点，调优就有了方向：减少不必要的 Shuffle、让 Shuffle 的数据量更小、让每个分区的数据量更均匀。例如 spark.sql.shuffle.partitions 默认 200，数据量小的时候会产生大量几百 KB 的小分区，白白增加调度开销；数据量很大而分区数没跟上，单个 Task 又会因为内存装不下而溢写甚至 OOM。

四、Spark SQL：从 RDD 到 DataFrame 与 DataSet

源资料说「每个数据库表被当做 RDD，Spark SQL 查询被转换为 Spark 操作」，这个描述在本章要纠正：Spark SQL 的核心抽象是 DataFrame（即 Dataset[Row]）与强类型的 DataSet，它们带有 schema（列名与类型），SQL 语句和 DSL 会先被 Catalyst 优化器转成逻辑计划，经过谓词下推、列裁剪、常量折叠等规则优化，再由 Tungsten 生成字节码，最终才落到 RDD 上执行。这正是结构化 API 通常比手写 RDD 更快的原因：RDD 里的 lambda 对 Spark 而言是黑盒，优化器无从下手，而 DataFrame 上的过滤、投影、聚合都是可知的。

import org.apache.spark.sql.Dataset;
import org.apache.spark.sql.Row;
import org.apache.spark.sql.SparkSession;

public class SalesByCity {
    public static void main(String[] args) {
        SparkSession spark = SparkSession.builder()
                .appName("SalesByCity")
                .master("local[*]")
                .getOrCreate();

        Dataset<Row> sales = spark.read()
                .option("header", "true")
                .option("inferSchema", "true")   // 生产环境建议显式指定 schema，避免多扫一遍文件
                .csv("data/sales.csv");
        sales.createOrReplaceTempView("sales");

        spark.sql("SELECT city, SUM(amount) AS total " +
                  "FROM sales GROUP BY city ORDER BY total DESC")
             .show(20);

        spark.stop();   // 复用同一 Session 时可省略，进程退出前记得关闭
    }
}

注意 SparkSession 已经是 Spark 2.0 之后唯一入口，旧的 SQLContext、HiveContext 都已被取代；用 Java 写 Spark SQL 时需要 spark-sql_2.13 依赖，只有 spark-core 是不够的。

五、常见坑与调优清单

第一类坑来自闭包。在 foreach 里给 Driver 的计数器变量 count++ 是无效的：闭包被序列化后发到 Executor，改的是各自副本，Driver 上永远看不到累加结果。跨节点的共享变量只有两种正确姿势——只读的广播变量（Broadcast，适合把小字典、小表发给每个 Executor）和只支持累加的累加器（Accumulator，适合统计脏数据条数）。

import org.apache.spark.broadcast.Broadcast;
import org.apache.spark.util.LongAccumulator;

import java.util.Map;

SparkConf conf = new SparkConf()
        .setAppName("Tuning")
        .set("spark.serializer", "org.apache.spark.serializer.KryoSerializer")
        .set("spark.sql.shuffle.partitions", "400")            // 默认 200，按数据量调整
        .set("spark.sql.autoBroadcastJoinThreshold", "20m");   // 默认 10m，小表自动广播
JavaSparkContext sc = new JavaSparkContext(conf);

// 广播变量：每个 Executor 只传一份，只读
Map<String, String> dict = loadCityDict();
Broadcast<Map<String, String>> bc = sc.broadcast(dict);

// 累加器：Executor 端只能 add，driver 端用 value() 读取
LongAccumulator badLines = sc.sc().longAccumulator("badLines");

sc.textFile("hdfs:///log/*.log")
  .filter(line -> {
      if (line.split(",").length < 5) {   // 字段数不足，记为脏数据
          badLines.add(1L);
          return false;
      }
      return true;
  })
  .map(line -> bc.value().getOrDefault(line.split(",")[0], "unknown") + "," + line)
  .saveAsTextFile("hdfs:///out/cleaned");

System.out.println("脏数据行数 = " + badLines.value());

第二类坑来自数据规模。Driver 内存远小于集群，collect() 会把整个 RDD 拉到 Driver，动辄 OOM，想看样本请用 take(n) 或 DataFrame 的 show()。所有 key 分布极度不均（数据倾斜）时，少数 Task 拖慢整个 Stage，常见解法是给热 key 加随机前缀打散后两阶段聚合；Spark 3.x 的自适应查询执行（AQE，spark.sql.adaptive.enabled 默认开启）也能自动合并小分区并处理部分倾斜。此外，cache()/persist(MEMORY_AND_DISK) 只在该 RDD 会被多次复用时才值得，用完记得 unpersist()；saveAsTextFile 的目标目录必须不存在，否则直接抛 FileAlreadyExistsException。

提交方式也容易踩坑：代码里硬编码了 setMaster("local[*]")，再用 spark-submit --master yarn 提交，最终以代码里的 master 为准，作业其实跑在本地；正确做法是代码里不写 master，交给提交命令决定。写出结果时每个分区对应一个 part 文件，分区数过多会产生大量小文件，必要时在写出前用 coalesce() 收敛分区，它只做分区合并、不产生 Shuffle。

第三类坑来自版本与环境。本地调试时日志满屏 INFO，Spark 3.x 要改的是 $SPARK_HOME/conf/log4j2.properties（源资料里的 log4j.properties 是 Spark 1.x 的写法，log4j 1.x 早已停止维护）；Windows 上跑本地模式需要 winutils.exe、hadoop.dll 并配置 HADOOP_HOME。依赖版本也要对齐：源资料给出的 spark-core_2.10 + Spark 1.6.0 + JDK 1.7 是十年前的老组合，Scala 2.10 已不再维护；新项目应当选用 Spark 3.5.x（需 JDK 8/11/17），Scala 侧用 2.13 或 2.12，即 spark-core_2.13、spark-sql_2.13，Java 8 以上的 lambda 语法才能正常编译。

本章把 Spark 的骨架串了一遍：RDD 是不可变、可分区、靠血缘容错的数据集；算子分惰性的 Transformation 和触发计算的 Action；DAG 在宽依赖处切 Stage，Shuffle 的磁盘与网络开销是性能的主要矛盾；DataFrame/DataSet 与 Spark SQL 让优化器有了发挥空间；调优则围绕减少 Shuffle、均衡分区、广播小表和正确使用共享变量展开。把这几点记住，再去看 Spark 的监控页面和任务日志，就不会只见参数不见原理了。
