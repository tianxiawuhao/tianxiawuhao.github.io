Zookeeper 分布式协调

Posted on 2026-09-19，9 min read

分布式系统里有一类问题不属于任何单个服务，却谁都需要：谁当主节点、配置怎么统一刷新、多个节点如何抢同一把锁、某个服务下线了别人怎么立刻知道。这类问题统称为分布式协调，Zookeeper 就是为解决它们而生的中间件。它是 Google Chubby 的开源实现，也是 Hadoop 生态的协调基础。本章讲清它的数据模型与四种节点类型，再讲半数机制与 ZAB 选举、Watch 的通知语义。之后用完整的代码把分布式锁、配置中心和 Master 选举做出来，最后回答一个高频面试题：为什么现在不推荐用 Zookeeper 做服务注册中心。学完这一章，9-6 分布式面试题里的协调类问题就有落点了。

Zookeeper 是什么：四个原语

分布式系统的子模块往往不是孤立的，它们需要互相协作：配置要一致、状态要同步、主节点要唯一。Zookeeper 提供的就是这样一套「协调原语」，客户端基于它组合出上层能力。它主要支撑四件事：

  • 命名服务：用层次化的目录结构登记资源，形如 /app/service/instance-1，作用类似 DNS。
  • 配置管理：把配置集中存在某个节点上，变更时通知所有客户端动态刷新，无需重启。
  • 分布式锁：用临时顺序节点实现互斥，会话断开自动释放，不会像 Redis 锁那样因超时而误释放。
  • 集群管理：登记成员、感知上下线、在 Leader 宕机后自动选主。

要理解它为什么能承担这些职责，先要接受一个前提：Zookeeper 是 CP 系统。按 CAP 定理，分布式系统在网络分区时只能在一致性与可用性之间二选一：Zookeeper 选择保证一致性——当集群中多数派节点不可达时，少数派一侧会拒绝服务而不是返回可能过期的数据。这个特性对「选主和锁」是必须的（两个主节点会带来灾难），但在另一些场景下会成为缺点，本章最后一节会展开。

数据模型与四种节点类型

Zookeeper 的数据结构是一棵树，每个节点叫 znode。它像文件系统，但有两点不同：每个节点都可以挂数据（不只是叶子节点），以及节点有类型。

节点类型由「是否持久」和「是否带序号」两个维度组合成四种：

  • 持久节点（PERSISTENT）：会话结束后依然存在，用来存放配置、目录结构。
  • 临时节点（EPHEMERAL）：会话断开就自动删除，这是服务注册与存活探测的基础——进程挂了，会话超时，节点消失，别人立刻知道它下线了。注意临时节点不能有子节点。
  • 持久顺序节点（PERSISTENT_SEQUENTIAL）：创建时自动在名字后补一个 10 位自增序号，如 order-0000000001，常用于生成全局有序编号。
  • 临时顺序节点（EPHEMERAL_SEQUENTIAL）：分布式锁的标准做法，既保证唯一有序，又能在客户端崩溃时自动清理。

客户端 API 只有几个：create、delete、exists、getData、setData、getChildren，每个都有同步与异步两种版本。所有写操作都会带一个 zxid（事务 ID），它单调递增，是判断数据新旧的依据——后面讲选举时会用到它。

另一件必须记牢的事是 Watch 是一次性的：客户端在 getData、getChildren 或 exists 时可以顺手注册监听，节点变化后服务端推送一次事件，然后这个监听就失效了，要持续监听必须重新注册。此外事件只告诉「什么变了」，不告诉「变成什么」，客户端收到通知后需要自己重新读取数据。这直接决定了写代码的方式：通知处理函数里必须重新 getData 并再次注册 Watch，否则只能收到第一次变更。

集群架构：一个 Leader、多个 Follower、半数可用

集群的关键机制是半数机制：只要超过一半的节点存活，集群就能提供服务。3 台机器可以容忍 1 台故障，5 台可以容忍 2 台，即「可用台数 = n + 1」（n 为一半）。这也是集群部署奇数台的原因：4 台和 3 台一样只能容忍 1 台故障，多出来的那台只增加成本不增加容错；而 2 台的容错能力是 0（两台都必须存活才能凑出多数派），所以官方建议最少部署 3 台。生产环境通常从 3 台起步，重要系统用 5 台。

「多数派」还有一个部署上的含义：如果机房之间网络断开，只有包含多数派节点的那一侧能继续服务，另一侧会整体不可用。所以跨机房部署 Zookeeper 时，必须保证任意时刻至少有一个分区里有多数派节点，否则会出现「集群还活着但就是连不上」的事故。

ZAB 协议与选主规则

Zookeeper 靠 ZAB（Zookeeper Atomic Broadcast）协议在集群间同步数据并选出 Leader。选举分两种情况。

全新集群的选举很简单：没有历史数据时，谁的 myid 大谁当 Leader。以 5 台机器（myid 为 1～5）依次启动为例。1 启动时只有自己，无法形成多数派，保持 LOOKING 状态。2 启动后两者比较，2 的 id 大，但只有 2 票、未过半，仍无法选出。3 启动后，1、2、3 三台中 3 最大且已获得三票（超过半数 2.5），3 成为 Leader。4、5 之后启动只能当 Follower。

运行一段时间后的重新选举要复杂一些，投票内容变成 (myid, zxid) 的组合，规则有三条优先级：

  1. 先比逻辑时钟（epoch），时钟小的那一轮选举结果直接忽略，只认最新一轮；
  2. 时钟相同时比 zxid（数据 id），数据更新的节点胜出——这一条保证了选举出的 Leader 一定拥有最完整的数据，不会丢已提交的事务；
  3. zxid 也相同时比 myid，id 大的胜出，用于避免平票。

面试里常问「为什么选举要比较 zxid 而不只是比 myid」：因为一个数据落后的节点当上 Leader，会导致已经提交的写操作回滚丢失，破坏 Zookeeper 保证的一致性语义。

典型用法：分布式锁、配置中心与 Master 选举

把上面的机制组合起来，就能实现分布式协调的几个经典场景，每一种都有对应的节点类型与 Watch 用法。

分布式锁：临时顺序节点 + 只监听前一个

所有客户端在 /locks 下创建临时顺序节点，然后取回全部子节点排序，判断自己是不是最小的：是则拿到锁，否则只监听排在自己前一个的节点。

import java.util.Collections;
import java.util.List;
import java.util.concurrent.CountDownLatch;
import org.apache.zookeeper.CreateMode;
import org.apache.zookeeper.WatchedEvent;
import org.apache.zookeeper.Watcher;
import org.apache.zookeeper.ZooDefs;
import org.apache.zookeeper.ZooKeeper;

public class DistributedLock {

    private static final String LOCK_ROOT = "/locks";
    private final ZooKeeper zk;
    private String currentPath;      // 本次抢锁创建的临时顺序节点

    public DistributedLock(String connectString) throws Exception {
        CountDownLatch connected = new CountDownLatch(1);
        this.zk = new ZooKeeper(connectString, 30_000, event -> {
            if (event.getState() == Watcher.Event.KeeperState.SyncConnected) {
                connected.countDown();
            }
        });
        connected.await();
        if (zk.exists(LOCK_ROOT, false) == null) {
            zk.create(LOCK_ROOT, new byte[0], ZooDefs.Ids.OPEN_ACL_UNSAFE, CreateMode.PERSISTENT);
        }
    }

    /** 加锁：抢不到就只监听前一个节点，避免惊群 */
    public void lock() throws Exception {
        // 1. 创建临时顺序节点，例如 /locks/lock-0000000007
        currentPath = zk.create(LOCK_ROOT + "/lock-", new byte[0],
                ZooDefs.Ids.OPEN_ACL_UNSAFE, CreateMode.EPHEMERAL_SEQUENTIAL);

        while (true) {
            List<String> children = zk.getChildren(LOCK_ROOT, false);
            Collections.sort(children);                    // 序号即创建顺序
            String current = currentPath.substring(LOCK_ROOT.length() + 1);
            if (children.get(0).equals(current)) {
                return;                                    // 自己最小，拿到锁
            }
            // 2. 只监听排在自己前面一个节点，它删除时再醒过来重试
            String prev = children.get(children.indexOf(current) - 1);
            CountDownLatch latch = new CountDownLatch(1);
            zk.exists(LOCK_ROOT + "/" + prev, event -> {
                if (event.getType() == Watcher.Event.EventType.NodeDeleted) {
                    latch.countDown();
                }
            });
            latch.await();
        }
    }

    /** 释放锁：删除自己的节点；若进程崩溃，会话超时后由服务端自动删除 */
    public void unlock() throws Exception {
        if (currentPath != null) {
            zk.delete(currentPath, -1);
            currentPath = null;
        }
    }
}

工程上还要给 unlock() 加一层保护：如果会话已经过期、节点被服务端自动删除，再调用 delete 会抛 KeeperException.NoNodeException。把它当作「锁已经不在了」的正常情况吞掉，而不是让异常冒到业务层。

这段实现里有三个设计要点值得说明。为什么用临时节点：客户端崩溃后会话超时，节点被服务端自动删除，锁自然释放，不会死锁；这也是它比 Redis 锁更稳的地方——Redis 锁通常要设过期时间，过期时间短了业务没跑完就误释放，长了又有死锁风险。为什么只监听前一个：如果所有等待者都监听锁节点本身，锁一释放就会同时唤醒几十上百个客户端来抢，形成「惊群」；只监听前一个节点，任意时刻只有一个客户端被唤醒，把竞争压力降到了最低。为什么要循环重试：Watch 是一次性的，且可能因为会话重连而丢失事件，所以唤醒后要重新判断自己是不是最小，而不是直接认为拿到了锁。

配置中心：读 + Watch + 重新注册

import java.nio.charset.StandardCharsets;
import org.apache.zookeeper.Watcher;
import org.apache.zookeeper.ZooKeeper;

/** 配置动态刷新：读取配置并持续监听变更 */
public class ConfigCenter {

    private static final String CONFIG_PATH = "/config/app1";
    private final ZooKeeper zk;
    private volatile String config;

    public ConfigCenter(ZooKeeper zk) {
        this.zk = zk;
    }

    public void watchConfig() throws Exception {
        // 关键：每次读取都重新注册 Watch，否则只能收到一次变更通知
        byte[] data = zk.getData(CONFIG_PATH, event -> {
            if (event.getType() == Watcher.Event.EventType.NodeDataChanged) {
                try {
                    watchConfig();                 // 重新读取并再次注册
                } catch (Exception e) {
                    System.out.println("配置刷新失败: " + e.getMessage());
                }
            }
        }, null);
        this.config = data == null ? "" : new String(data, StandardCharsets.UTF_8);
        System.out.println("当前配置: " + config);
    }
}

Master 选举与集群成员感知

Master 选举的写法与分布式锁几乎一致：所有候选节点在 /election 下创建临时顺序节点，序号最小的即为主，其余监听自己前一个节点。主节点挂掉后会话超时、节点自动删除，下一个节点被唤醒并成为新主。集群成员管理则更简单：每个服务实例启动时在 /services/order 下创建临时节点登记自身地址，其他服务用 getChildren 拿到全部实例列表并注册 Watch，实例上下线时就能及时感知。

关于命名服务与全局 ID 补一句：利用持久顺序节点的自增序号可以生成全局有序编号，但性能很低，因为每个 ID 都要写一次 Zookeeper。生产环境生成分布式 ID 应该用雪花算法或号段模式，顺序节点只适合「需要严格有序且频率不高」的命名场景。

注册中心之争：为什么现在不推荐用 Zookeeper

Dubbo 早期默认用 Zookeeper 做注册中心，所以很多人默认「注册中心就该用 ZK」。但从 CAP 角度分析，这个选择并不理想。

Zookeeper 是 CP 系统：网络分区发生时，处于少数派一侧的节点会直接断开、拒绝服务（因为无法与多数派通信，无法保证数据一致）。而注册中心需要的是 AP：服务消费者拿到一份「三秒前的服务列表」远好过「一个错误」——过期的地址最多导致一次请求失败重试，而查不到任何地址会让整个调用链直接不可用。

实践中还有一个更隐蔽的问题：Zookeeper 客户端在会话超时后会认为「节点不存在」，而下线事件的通知又有延迟，容易造成消费者与注册中心的信息不一致。这也解释了为什么后来 Nacos、Eureka、Consul 这类以 AP 为主的注册中心更受欢迎——它们允许短暂的数据不一致，换取更高的可用性。

不过要说清楚的是，「不适合做注册中心」不等于「不该用 Zookeeper」。它最擅长的恰恰是那些必须强一致的协调场景：选主、分布式锁、元数据管理。而且 Hadoop、HBase、Kafka（2.8 版本前）、SolrCloud、Dubbo 的 ZK 注册模式都深度依赖它，在这些生态里它是既定的基础设施而非可选项。选型时的判断标准是：要强一致的协调 → ZK 或 etcd；要高可用的服务发现与配置 → Nacos；只是简单加锁 → Redis 更轻。

小结：Zookeeper 用一棵树 + 四种节点类型 + 一次性 Watch + 半数派选举，支撑起了分布式协调的四类原语。要记住的关键点有四条：临时节点是「进程存活」的载体、顺序节点是「排队」的载体、Watch 一次性所以必须重新注册、多数派存活才可用所以集群部署奇数台。理解这四条，再看任何基于 ZK 的框架（Dubbo、Kafka、HBase）的实现都会清晰很多。
