jar包内类动态加载

Posted on 2022-01-04，13 min read

网关、流程引擎这类系统里经常需要把「组件」做成可插拔的：编译好一个 jar 丢到指定目录，运行时按需加载、实例化、执行，替换 jar 之后还要能生效。在 Java 里这件事只有一个入口——类加载器。本文记录一套实际用过的实现：用自定义的 URLClassLoader 加载指定目录下的组件 jar，用 Class.forName(name, true, loader) 拿到 ICmpt 实例并缓存，卸载时关闭加载器。

先把几个容易混淆的 API 分清楚，后面的代码才好读：

  • ClassLoader.loadClass(String)：走双亲委派，只做「加载」，默认不执行静态初始化（内部等价于 loadClass(name, false)）。
  • Class.forName(String)：等价于「用调用者自己的类加载器加载并初始化」。也就是说它只能看到调用方加载器及其父加载器可见的类，插件 jar 里的新类用它加载不到。
  • Class.forName(String name, boolean initialize, ClassLoader loader)：显式指定加载器，是插件化的正确入口；initialize=true 会立刻执行静态代码块。
  • ServiceLoader.load(Class) 与 SPI：面向「一个接口 + 多个实现」的发现机制，靠 META-INF/services 描述文件工作，默认使用线程上下文类加载器（TCCL）。

类加载器遵守双亲委派模型：收到加载请求先交给父加载器，父加载器加载不到（抛 ClassNotFoundException）才回落到自己的 findClass。插件化之所以绕不开这个模型，是因为「打破」它的三类典型场景恰好都出现在这里。

还有一个必须记住的前提：跨类加载器强转，要求接口由共同的父加载器加载。组件 jar 里的实现类由 CmptClassLoader 定义，而它实现的 ICmpt 接口来自宿主公共模块、由 App 加载器加载；由于 CmptClassLoader 的 parent 就是 App 加载器，委派保证了 ICmpt 在 JVM 中只有一份，(ICmpt) instance 才不会抛 ClassCastException。反过来，如果把接口一起打进插件 jar，就会出现「同一个接口被两个加载器各加载一份」的经典错误。

实体对象

组件定义来自数据库，字段里最关键的是 fullQualifiedName（入口类全限定名）、version 和 code：前者决定要加载哪个类，后两者决定从哪个目录取 jar，也一起构成缓存的 key。

服务接口只有三个方法：取实例、刷新缓存、删除实例。getCmptInstance 的语义是「缓存优先，未命中时动态加载」，也就是说类加载器不是启动时批量创建的，而是第一次用到某个组件时才建。注意 refreshCmptInstanceCache 在下面实现里是个空桩，方法名比行为更有想象空间。

方法接口

public interface ICmptService {
    /**
     * 根据组件类名和版本从缓存中获取组件,如果不存在则尝试动态加载组件类，实例化并刷新缓存后再获取，还是不存在则返回null；
     * 另外配置更新会有单独的线程刷新缓存。
     *
     * @return
     */
    ICmpt getCmptInstance(final CmptDef cmptDef);

    /**
     * 刷新API关联的组件配置信息
     *
     * @param apis
     * @param ignoreRefreshTime
     * @return
     */
    boolean refreshCmptInstanceCache(List<Api> apis, boolean ignoreRefreshTime);

    /**
     * 删除组件实例缓存
     *
     * @param fullQualifiedName
     * @param code
     */
    void removeCmpt(final String fullQualifiedName, final Float version, final String code);
}

这个方法有两个分支，正好对应两种加载方式：

  • dynamicLoadCmptClass=true：走 CmptClassLoaderUtil.newInstance，用自定义加载器从 jar 目录加载，支持热插拔；
  • 否则走 Class.forName(name) 加 newInstance()，用的是当前类的加载器，因此只能加载已经在应用 classpath 上的组件——换掉 jar 不会生效，也无法卸载。

这段代码里有几个点值得先标记出来，后面「工具类」一节会展开：

  • Class.newInstance() 从 Java 9 起被标记为 deprecated：它只能调用 public 无参构造，还会把构造器抛出的受检异常原样「穿透」。新代码应写 clazz.getDeclaredConstructor().newInstance()。
  • 前一个 if (null != cmpt) 分支做了 instanceof AbstractCmpt 判断，但后面注册观察者时直接强转 (AbstractCmpt) cmpt，没有判断——如果某个组件不是 AbstractCmpt 的子类，这里会抛 ClassCastException。
  • removeCmpt 里先显式调用 cmpt.destroy()，随后 CmptInstanceHolder.removeEntry 内部又 destroy() 了一次，destroy 必须写成幂等的。
  • 卸载时传给 CmptClassLoaderManager.unLoadJar 的是 getJarPath(cmptDef)（jar 路径），而管理类内部 map 的 key 是 IdCmptDef，两者对不上：卸载实际上不会生效，加载器会一直留在静态 map 里。这是本文代码里最典型的一个类加载器泄漏点。
  • 方法整体加了 synchronized，加载慢时会阻塞同一个 service 实例上的其他调用；用「按类名加锁 + 双重检查」会更好。

方法实现

@Service
public class CmptServiceImpl implements ICmptService {
    private static Logger logger = LoggerFactory.getLogger(CmptServiceImpl.class);

    @Value("${cmpt.dynamicLoadCmptClass}")
    private boolean dynamicLoadCmptClass;

    @Autowired
    private ICmptDefService cmptDefService;

    @Override
    public synchronized ICmpt getCmptInstance(final CmptDef cmptDef) {
        ICmpt cmpt = CmptInstanceHolder.getInstance().getCmpt(cmptDef.getFullQualifiedName(), cmptDef.getVersion(), cmptDef.getCode());
        if (null == cmpt) {
            if (logger.isDebugEnabled()) {
                logger.debug("反射拿到实例>>> " + cmptDef.getFullQualifiedName());
            }
            if (this.dynamicLoadCmptClass) {
                cmpt = CmptClassLoaderUtil.newInstance(cmptDef);
            } else {
                try {
                    Class clazz = Class.forName(cmptDef.getFullQualifiedName());
                    cmpt = (ICmpt) clazz.newInstance();
                } catch (Exception e) {
                    e.printStackTrace();
                }
            }
            if (null != cmpt) {
                if (cmpt instanceof AbstractCmpt) {
                    //设置版本号
                    ((AbstractCmpt) cmpt).setVersion(cmptDef.getVersion());
                    ((AbstractCmpt) cmpt).setIdCmptDef(cmptDef.getIdCmptDef());
                }
                CmptInstanceHolder.getInstance().addEntry(cmpt, cmptDef.getFullQualifiedName(), cmptDef.getVersion(), cmptDef.getCode());
            }
        } else {
            if (logger.isDebugEnabled()) {
                logger.debug("缓存拿到实例>>> " + cmptDef.getFullQualifiedName());
            }
        }
        if (null != cmpt) {
            ApplicationContext context = SpringContextHolder.getContext();
            if (null != context) {
                ZkClient zkClient = context.getBean(ZkClient.class);
                if (null != zkClient) {
                    BaseListener listener = zkClient.getListener();
                    listener.addObserver((AbstractCmpt) cmpt);
                }
            }
        }
        return cmpt;
    }

    @Override
    public boolean refreshCmptInstanceCache(List<Api> apis, boolean ignoreRefreshTime) {
        return false;
    }

    @Override
    public synchronized void removeCmpt(final String fullQualifiedName, final Float version, final String code) {
        ICmpt cmpt = CmptInstanceHolder.getInstance().getCmpt(fullQualifiedName, version, code);
        if (null != cmpt) {
            ApplicationContext context = SpringContextHolder.getContext();
            if (null != context) {
                ZkClient zkClient = context.getBean(ZkClient.class);
                if (null != zkClient) {
                    BaseListener listener = zkClient.getListener();
                    listener.deleteObserver((AbstractCmpt) cmpt);
                }
            }
            cmpt.destroy();
            CmptDef cmptDef = CmptDefHolder.getInstance().getCmptDef(fullQualifiedName, version, code);
            if (null == cmptDef) {
                cmptDef = new CmptDef();
                cmptDef.setFullQualifiedName(fullQualifiedName);
                cmptDef.setVersion(version);
                cmptDef.setCode(code);
            }
            //删除引用实体
            CmptInstanceHolder.getInstance().removeEntry(fullQualifiedName, version, code);
            cmpt = null;

            String jarPath = CmptClassLoaderUtil.getJarPath(cmptDef);
            if (logger.isDebugEnabled()) {
                logger.debug("尝试卸载jar包: " + jarPath);
            }
            CmptClassLoaderManager.unLoadJar(jarPath);
        }
        CmptInstanceHolder.getInstance().removeEntry(fullQualifiedName, version, code);
    }
}

工具类

下面这几个类合起来是一套最小可用的插件类加载框架，职责分别是：CmptInstanceHolder 缓存实例、CmptClassLoaderUtil 拼路径并创建实例、CmptClassLoaderManager 管理加载器的创建与卸载、CmptClassLoader 是加载器本体、LoadClassUtil 是更早一版的反射工具（含一条已被淘汰的「把 jar 挂到 App 加载器」的路子）。

主线流程是：拼出 jar 绝对路径 → 新建（或复用）CmptClassLoader → Class.forName(name, true, loader) 加载并初始化类 → newInstance() 后强转为 ICmpt → 放进静态缓存。每一环都有各自的坑，分别在下面几个小节里说明。

组件实例缓存

这是一个饿汉式静态单例加 ConcurrentHashMap 的实例缓存。addEntry 先 removeEntry 再 put，保证覆盖时旧实例被销毁；removeEntry 在移除后会调用 destroy()，用来释放组件持有的线程、连接等资源。

要特别注意的是：这个单例由 App 加载器加载，它的静态字段会一直存活到 JVM 结束。只要 map 里还留着某个插件实例，实例 → 插件的 Class → 定义它的 CmptClassLoader 这条引用链就断不掉；而「加载器不可达」是类卸载的前提（见上图），于是 jar 里的类会一直留在 Metaspace 里。插件化系统里「每次重载内存都涨一点」，绝大多数都是这类静态缓存加加载器没释放造成的。

/**
 * 组件配置缓存持有者
 */
public class CmptInstanceHolder {
    private static CmptInstanceHolder cmptInstanceHolder = new CmptInstanceHolder();
    //API所关联的组件配置缓存 key: fullQualifiedName    value: ICmpt
    private Map<String, ICmpt> cmpts = new ConcurrentHashMap<>();

    private CmptInstanceHolder() {
    }

    public static CmptInstanceHolder getInstance() {
        return CmptInstanceHolder.cmptInstanceHolder;
    }

    /**
     * 根据类名加版本从缓存中获取组件实例,如果不存在直接返回null；
     *
     * @return
     */
    public ICmpt getCmpt(final String fullQualifiedName, final Float version, String code) {
        final String key = buildKey(fullQualifiedName, version, code);
        return this.cmpts.get(key);
    }

    /**
     * 添加对象
     */
    public void addEntry(final ICmpt cmpt, final String fullQualifiedName, final Float version, final String code) {
        if (cmpt == null || StringUtils.isEmpty(fullQualifiedName) || StringUtils.isEmpty(code)) {
            return;
        }
        final String key = buildKey(fullQualifiedName, version, code);
        removeEntry(fullQualifiedName, version, code);
        this.cmpts.put(key, cmpt);
    }

    private String buildKey(final String fullQualifiedName, Float version, final String code) {
        return fullQualifiedName + "." + version + code;
    }

    public void removeEntry(final String fullQualifiedName, final Float version, final String code) {
        ICmpt remove = this.cmpts.remove(buildKey(fullQualifiedName, version, code));
        if (null != remove) {
            remove.destroy();
        }
    }

    /**
     * 获取所有的组件实例
     * @return
     */
    public Map<String, ICmpt> getAllCmpts(){
        return this.cmpts;
    }
}

jar 路径与 jar 内资源

getJarPath 用字符串拼接出「app.home + cmpt.location / code / version / 入口类简名_版本.jar」。拼路径更稳妥的写法是 Paths.get(appHome, location, code, version, fileName)，由 File 负责分隔符；用字符串拼时也尽量避免手工塞 /，否则在不同平台上很容易多出或少掉分隔符。

示例里的 FileUtil.fixFileName 做了两种归一化，都有副作用：

  • 第一个 replaceAll 的参数是正则，用两个反斜杠匹配一个反斜杠，写法正确但不直观；
  • 第二个 replaceAll("//", "/") 把连续斜杠压成一个。对普通文件路径无害，但它同样会破坏 file:///tmp/a.jar（变成 file:/tmp/a.jar）和 Windows 的 UNC 路径（//server/share 被压成 /server/share）。只在真正的本地文件路径上做这种归一化才安全。

另外 LoadClassUtil 里调用了 FileUtil.fileInfo(jarPath)，但本节列出的 FileUtil 只有 fixFileName 一个方法——把散落的代码片段拼起来复用时要补上这个方法，否则编译不过。

jar 内的资源只能用类加载器读，不能用 new File(path)：jar 里的条目不是文件系统路径。前导斜杠的含义也要分清：

// Class 版本：以 / 开头表示从 classpath 根开始找
InputStream in1 = getClass().getResourceAsStream("/cmpt/default.properties");
// Class 版本：不以 / 开头表示相对当前类的包目录
InputStream in2 = getClass().getResourceAsStream("default.properties");
// ClassLoader 版本：路径一律相对 classpath 根，不能写前导 /
InputStream in3 = loader.getResourceAsStream("cmpt/default.properties");
// 只在本加载器（自己的 jar）里找，不委派父加载器
URL own = ((URLClassLoader) loader).findResource("cmpt/default.properties");
// getResource 会先委派父加载器；jar 文件句柄被缓存会导致 Windows 上无法覆盖 jar
URL url = loader.getResource("cmpt/default.properties");
if (url != null) {
    URLConnection conn = url.openConnection();
    conn.setUseCaches(false);
    try (InputStream in = conn.getInputStream()) {
        // 读取资源
    }
}

两个容易踩的点：getResource/getResourceAsStream 是父加载器优先的，如果宿主的 classpath 上正好有同名资源，插件 jar 里的那一份读不到，这种场景要改用 findResource；另外把 jar 里的资源读成 InputStream 时要记得关闭，getResourceAsStream 返回的流同样占用 jar 的文件句柄。

public class CmptClassLoaderUtil {

    private static Logger logger = LoggerFactory.getLogger(CmptClassLoaderUtil.class);

    public static ICmpt newInstance(final CmptDef cmptDef) {
        ICmpt cmpt = null;
        try {
            final String jarPath = getJarPath(cmptDef);
            logger.info("尝试载入jar包,jar包路径: " + jarPath);
            //加载依赖jar
            CmptClassLoader cmptClassLoader = CmptClassLoaderManager.loadJar(cmptDef.getIdCmptDef(), jarPath, true);
            // 创建实例
            if (null != cmptClassLoader) {
                cmpt = LoadClassUtil.newObject(cmptDef, ICmpt.class, cmptClassLoader);
            } else {
                logger.error("加载组件jar包失败! jarPath: " + jarPath);
            }
        } catch (Exception e) {
            logger.error("组件类加载失败，请检查类名和版本是否正确。ClassName=" + cmptDef.getFullQualifiedName() + ", Version=" + cmptDef.getVersion());
            e.printStackTrace();
        }
        return cmpt;
    }

    public static String getJarPath(final CmptDef cmptDef) {
        StringBuffer sb = new StringBuffer();
        sb.append(AppConfigUtil.getValue("app.home"));
        sb.append(AppConfigUtil.getValue("cmpt.location"));
        sb.append("/");
        //开发中关闭多级目录,不好部署
        sb.append(cmptDef.getCode());
        sb.append("/");
        sb.append(cmptDef.getVersion());
        sb.append("/");
        String[] split = cmptDef.getFullQualifiedName().split("\\.");
        sb.append(split[split.length - 1]);
        sb.append("_");
        sb.append(cmptDef.getVersion());
        sb.append(".jar");
        if (logger.isDebugEnabled()) {
            logger.debug("构建jar包路径: " + sb.toString());
        }
        return sb.toString();
    }

}

加载器的创建与卸载

CmptClassLoaderManager 用一个静态 map 管理「组件定义 ID 到加载器」的映射，loadJar(..., isReloadJar) 中 isReloadJar=true 表示每次都新建加载器。这里有两处需要修正：

  • key 不一致：加载时以 IdCmptDef 为 key，卸载时 CmptServiceImpl.removeCmpt 传的却是 jar 路径，unLoadJar 找不到对应加载器。而它的返回值只表示「过程没有抛异常」——即使什么都没删到也返回 true，调用方无法察觉，加载器就永久留在了静态 map 里。
  • 先卸后载、没有回滚：null == classLoaderMap.get(id) || unLoadJar(id) 先把旧加载器关掉，再去加载新 jar；如果新 jar 损坏、路径写错或入口类缺失，addURL 返回 false，最终返回 null——旧组件也已经不可用了。更稳的顺序是：先建新加载器并验证入口类能加载出来，再替换 map 中的旧值并关闭旧加载器。

close() 是 URLClassLoader 从 Java 7 起实现的方法，作用是关闭该加载器打开的 jar 文件句柄（内部 JarFile 缓存），关闭后不能再用它加载新的类或资源；但已加载到 JVM 中的类不会因此被卸载，类卸载仍然取决于可达性与 GC。所以「卸载插件」是两件事：释放文件句柄（close），以及切断所有强引用后等 GC 回收类（map 移除、缓存清理、线程停止）。

/**
 * 类加载器管理, 加载, 卸载jar包
 */
public class CmptClassLoaderManager {

    private static final Logger logger = Logger.getLogger(CmptClassLoaderManager.class);

    private static Map<String, CmptClassLoader> classLoaderMap = new ConcurrentHashMap<>();

    private CmptClassLoaderManager() {
    }

    /**
     * 载入Jar包, 判断是否重新载入Jar包
     *
     * @param fileName
     * @param isReloadJar
     * @return
     */
    public static CmptClassLoader loadJar(String IdCmptDef, String fileName, boolean isReloadJar) {
        fileName = FileUtil.fixFileName(fileName);
        CmptClassLoader cmptClassLoader = classLoaderMap.get(IdCmptDef);
        if (isReloadJar || null == cmptClassLoader) {
            if (logger.isDebugEnabled()) {
                logger.debug("从文件载入jar组件");
            }
            return loadJar(IdCmptDef, fileName);
        } else {
            if (logger.isDebugEnabled()) {
                logger.debug("从缓存载入jar组件");
            }
            return cmptClassLoader;
        }
    }

    /**
     * 载入Jar包, 以新Jar包载入
     *
     * @param fileName
     * @return 返回一个类加载器
     */
    private static CmptClassLoader loadJar(String IdCmptDef, String fileName) {
        CmptClassLoader loader;
        try {
            boolean exists = new File(fileName).exists();
            if (exists) {
                if (null == classLoaderMap.get(IdCmptDef) || unLoadJar(IdCmptDef)) {
                    loader = new CmptClassLoader();
                    boolean loadJar = loader.addURL(fileName);
                    if (loadJar) {
                        classLoaderMap.put(IdCmptDef, loader);
                        return loader;
                    } else {
                        loader.close();
                    }
                }
            } else {
                throw new IllegalArgumentException("传入参数错误,文件不存在! file: " + fileName);
            }
        } catch (Exception e) {
            logger.error("",e);
        }
        return null;
    }

    public static boolean unLoadJar(String IdCmptDef) {
        boolean unLoadJar = false;
        if (logger.isDebugEnabled()) {
            logger.debug("请求卸载jar包: " + IdCmptDef);
        }
        try {
            CmptClassLoader loader = classLoaderMap.remove(IdCmptDef);
            if (null != loader) {
                loader.close();
            }
            unLoadJar = true;
        } catch (Exception e) {
            logger.error("",e);
        }
        return unLoadJar;
    }

    /**
     * 获取组件定义对应的实例的类加载器
     *
     * @param idCmptDef
     * @return
     */
    public static ClassLoader getCmptClassLoader(String idCmptDef) {
        return classLoaderMap.get(idCmptDef);
    }
}

public class FileUtil {

CmptClassLoader 的用法与坑

CmptClassLoader 继承 URLClassLoader，没有重写 loadClass，因此完全遵守双亲委派：插件类先在父加载器（App）里找，找不到才在本 jar 内找。这带来一个副作用——如果插件 jar 自带了与宿主 classpath 同名的库（比如另一个版本的 fastjson），实际生效的是父加载器里的那一份，插件的依赖版本被无声地忽略。要让插件自带的依赖优先，就得像 Tomcat 那样重写 loadClass 实现「子优先」，并显式列出必须先委派的包（java.、javax.、宿主接口所在的包等）。

addURL 里的反射代码其实可以删掉：URLClassLoader.addURL 是 protected 方法，写在子类中直接调用即可；而它绕道取内部字段 ucp 再强转成 sun.misc.URLClassPath，在 JDK 9 及以上会撞上模块化的强封装（java.net 并未 open 给 unnamed 模块，需要 --add-opens java.base/java.net=ALL-UNNAMED），从 JDK 16 起默认直接抛 InaccessibleObjectException。同理，finalize() 里调用 close() 也不可靠：finalize 自 JDK 9 起被弃用、JDK 18（JEP 421）起可以被禁用，对象还可能被「复活」；释放加载器应该由显式的 close() 加 map 移除来完成，不要指望 GC 帮你收尾。

findParentClassLoader() 借 logger.getClass().getClassLoader() 拿父加载器同样脆弱：如果这里的 Logger 是 java.util.logging.Logger，它位于 java.base、由启动类加载器加载，getClassLoader() 返回 null，方法会直接抛运行时异常。应该明确写成 CmptClassLoader.class.getClassLoader()，或者按插件化惯例取 Thread.currentThread().getContextClassLoader()。

把上面几点落到代码上，大致是这样：

public class CmptClassLoader extends URLClassLoader {
    static {
        // 注册后可并行加载类，减少多线程首次加载时的锁竞争
        ClassLoader.registerAsParallelCapable();
    }

    public CmptClassLoader(URL[] urls, ClassLoader parent) {
        super(urls, parent);
    }

    // addURL 是 protected，子类直接调用即可，无需反射 sun.misc.URLClassPath
    public void addJar(Path jar) throws MalformedURLException {
        addURL(jar.toUri().toURL());
    }

    @Override
    protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
        // 示例：仅对插件包「子优先」，其余仍走双亲委派
        if (name.startsWith("org.example.plugin.")) {
            synchronized (getClassLoadingLock(name)) {
                Class<?> c = findLoadedClass(name);
                if (c == null) {
                    try {
                        c = findClass(name);
                    } catch (ClassNotFoundException ignored) {
                        // 本 jar 里没有，交给父加载器
                    }
                }
                if (c != null) {
                    if (resolve) {
                        resolveClass(c);
                    }
                    return c;
                }
            }
        }
        return super.loadClass(name, resolve);
    }
}

/**
 * 类加载器终极版, 加载, 卸载jar包
 */
public class CmptClassLoader extends URLClassLoader {

    private static final Logger logger = Logger.getLogger(CmptClassLoader.class);

    CmptClassLoader(URL[] urls, ClassLoader parent) {
        super(urls, parent);
    }

    CmptClassLoader(URL[] urls) {
        super(urls);
    }

    CmptClassLoader(URL[] urls, ClassLoader parent, URLStreamHandlerFactory factory) {
        super(urls, parent, factory);
    }

    CmptClassLoader() {
        super(new URL[]{}, findParentClassLoader());
    }

    /**
     * 载入Jar
     *
     * @param fileName
     * @return
     */
    boolean addURL(String fileName) {
        try {
            URL url = new File(fileName).toURL();
            URLClassPath ucp = this.getUCP();
            ucp.addURL(url);
        } catch (Exception e) {
            e.printStackTrace();
            return false;
        }
        return true;
    }

    /**
     * 定位当前父类加载器
     *
     * @return
     */
    private static ClassLoader findParentClassLoader() {
        ClassLoader parent = logger.getClass().getClassLoader();
        if (parent == null) {
            throw new RuntimeException("无法获取当前父加载器!");
        }
        return parent;
    }

    private URLClassPath getUCP() {
        URLClassPath ucp = null;
        try {
            Field declaredField = URLClassLoader.class.getDeclaredField("ucp");
            declaredField.setAccessible(true);
            Object o = declaredField.get(this);
            ucp = (URLClassPath) o;
        } catch (IllegalAccessException e) {
            e.printStackTrace();
        } catch (NoSuchFieldException e) {
            e.printStackTrace();
        }
        return ucp;
    }

    @Override
    protected void finalize() throws Throwable {
        super.finalize();
        this.close();
    }
}

反射工具类的坑

LoadClassUtil 是这个功能更早的一版实现，核心思路是「把 jar 路径反射塞进应用类加载器的扫描列表」，这样 Class.forName(name) 就能找到插件类。这条路子写起来最短，代价却很明确：

  • 插件类由 App 加载器定义，而 App 加载器在整个 JVM 生命周期内一直可达，插件类永远无法卸载，替换 jar 也不会生效（类已经加载过了）；
  • URLClassLoader.addURL 是 protected，只能靠 setAccessible(true) 反射调用，JDK 9 之后受模块化限制，JDK 16 起默认失败；
  • 插件依赖全部挂到 App 加载器上等于放弃了隔离，插件之间、插件与宿主之间的同名类会互相顶掉。

也正因为这些限制，才有了后面的 CmptClassLoader：加载器自己持有 jar 的 URL，卸载时才有东西可回收。另外两个细节：newObject(String className) 用的是 Class.forName(className)（调用者的加载器），要加载插件类必须用三参数版本传 loader；invokeMethod 里 o.getClass().getMethod(methodName, args.getClass()) 传进去的是 Object[].class，只有「形参恰好是一个 Object[]」的方法才匹配得上，代码注释也承认了这个缺陷。按实参类型匹配的写法是：

Class<?>[] types = Arrays.stream(args)
        .map(a -> a == null ? Object.class : a.getClass())
        .toArray(Class[]::new);
Method method = o.getClass().getMethod(methodName, types);
return method.invoke(o, args);

顺带一提，SPI 也是插件化的常用入口：把实现类全限定名写进 jar 内的 META-INF/services/接口全限定名 文件，宿主用 ServiceLoader.load(ICmpt.class, loader) 遍历。它比自定义加载器省事，但要注意 ServiceLoader 默认用线程上下文类加载器——插件场景必须显式传 loader，否则要么找不到实现，要么因为用了另一个加载器而强转失败。

/**
 * 类加载器工具类
 */
public class LoadClassUtil {
    private final static LoadClassUtil LOAD_JAR_UTIL = new LoadClassUtil();
    private static Logger logger = LoggerFactory.getLogger(LoadClassUtil.class);

    private LoadClassUtil() {
    }

    /**
     * 载入jar包
     * 将jar包路径添加到系统类加载器扫描类和资源的文件列表里
     *
     * @param fileName jar绝对路径
     * @return
     */
    public static boolean loadJar(String fileName) {
        try {
            if (strNotNull(fileName) && fileExists(fileName)) {//(ClassLoader要与当前程序同一个loader)
                getMethod().invoke(LOAD_JAR_UTIL.getClass().getClassLoader(), getURL(fileName));//添加路径URL
                //getMethod().invoke(Launcher.getLauncher().getClassLoader(), getURL(fileName));//添加路径URL
                return true;
            } else {
                throw new IllegalArgumentException("传入参数错误,文件或不存在! file: " + fileName);
            }
        } catch (Exception e) {
            logger.error("",e);
        }
        return false;
    }

    /**
     * 判断字符串不为空
     *
     * @param str
     * @return
     */
    private static boolean strNotNull(String str) {
        return null != str && !str.equals("");
    }

    private static boolean fileExists(String fileName) {
        return new File(fileName).exists();
    }

    /**
     * 拿到添加扫描类和资源的路径URL的方法
     *
     * @return
     * @throws NoSuchMethodException
     */
    private static Method getMethod() throws NoSuchMethodException {
        Method method = URLClassLoader.class.getDeclaredMethod("addURL", URL.class);
        // 破解方法的访问权限
        method.setAccessible(true);
        return method;
    }

    /**
     * 得到一个URL
     *
     * @param fileName
     * @return
     * @throws MalformedURLException
     */
    private static URL getURL(String fileName) throws MalformedURLException {
        return new File(fileName).toURI().toURL();
    }

    /**
     * 创建对象实例
     *
     * @param className 全限定名
     * @return
     */
    public static Object newObject(String className) {
        try {
            return Class.forName(className).newInstance();
        } catch (Exception e) {
            logger.error("",e);
        }
        return null;
    }

    /**
     * 创建转换类型后的对象实例
     *
     * @param className 全限定名
     * @param tClass    返回类型
     * @param <T>
     * @return
     */
    public static <T> T newObject(String className, Class<T> tClass) {
        try {
            return (T) Class.forName(className).newInstance();
        } catch (Exception e) {
            logger.error("",e);
        }
        return null;
    }

    /**
     * 创建转换类型后的对象实例
     *
     * @param cmptDef 组件定义->全限定名
     * @param tClass    返回类型
     * @param loader    类加载器
     * @param <T>
     * @return
     */
    public static <T> T newObject(CmptDef cmptDef, Class<T> tClass, ClassLoader loader) {
        try {
            String className = cmptDef.getFullQualifiedName();
            Object newInstance = Class.forName(className, true, loader).newInstance();
            return (T) newInstance;
        } catch (Exception e) {
            String jarPath = CmptClassLoaderUtil.getJarPath(cmptDef);
            logger.error("创建组件实例失败! className=" + cmptDef.getFullQualifiedName() + " jarPath=" + jarPath);
            logger.error("创建出错组件:" + cmptDef.getName() + cmptDef.getVersion() + " ,文件信息:" + FileUtil.fileInfo(jarPath));
            try {
                Class<?> aClass = loader.loadClass(cmptDef.getFullQualifiedName());
            } catch (ClassNotFoundException e1) {
                e1.printStackTrace();
                logger.error("类未载入:" + cmptDef.getFullQualifiedName());
            }
        }
        return null;
    }

    /**
     * 执行对象的方法
     *
     * @param o          实例对象
     * @param methodName 方法名称
     * @param args       形参
     * @return
     */
    public static Object invokeMethod(Object o, String methodName, Object... args) {
        try {
            Object invoke;
            if (null == args || args.length == 0) {//有缺陷,如果形参是任意Object,但传入参数是null,无法得到形参类型,得到有参的方法.
                Method method = o.getClass().getMethod(methodName);
                invoke = method.invoke(o);
            } else {
                Method method = o.getClass().getMethod(methodName, args.getClass());
                invoke = method.invoke(o, args);
            }
            return invoke;
        } catch (Exception e) {
            logger.error("",e);
        }
        return null;
    }

}

最后是组件与宿主之间的契约。组件实现类放在插件 jar 里，接口 ICmpt 放在宿主的公共模块里、由 App 加载器加载——这正是前面反复强调的「接口由父加载器加载」。execute 的参数把请求、配置、流程节点和上下文都显式传进来，而不是让组件持有状态，这是对的：缓存的组件实例会被多个线程共享，实现应当尽量无状态。

小结与避坑清单

把上面的内容压成一份可操作的清单。

加载方式怎么选

  • 类在应用 classpath 上、启动时就要用：Class.forName(name) 或直接 new，最简单。
  • 类在运行时才出现的 jar 里：Class.forName(name, true, loader) 或 loader.loadClass(name)，并且 loader 必须是能看见那个 jar 的加载器。
  • 只想加载、不想触发静态初始化：Class.forName(name, false, loader)。
  • 「一个接口 + 多个第三方式实现」：用 SPI，实现类全限定名写进 META-INF/services/<接口全限定名>；JDK 9 以上的模块也可以写 provides ... with ...。插件场景用 ServiceLoader.load(ICmpt.class, loader)，不要依赖 TCCL。
  • 需要读 jar 内资源：一律走 getResourceAsStream，注意前导斜杠的含义和父加载器优先的查找顺序。

热加载与卸载

  • 已加载的类无法「替换」，热加载 = 新建加载器加载新 jar，再让旧加载器变得不可达。
  • 缓存 key 必须带版本（本文用全限定名 + 版本 + code），否则拿到的还是旧实例。
  • 卸载的三个前提要同时满足：实例不可达、加载器不可达、类没有被强引用（ThreadLocal、静态字段、未结束的线程、DriverManager 注册的驱动、日志 appender、ServiceLoader 的 provider 缓存等）。
  • 卸载时先显式 close() 释放 jar 句柄，再从所有静态 map 里移除；不要依赖 finalize。
  • 组件实现尽量无状态：实例通常被缓存并被多线程共享，请求相关的数据通过方法参数传入。
  • 排障时先打印 obj.getClass() 和 obj.getClass().getClassLoader()：同一个接口被两个加载器各加载一份时，强转会抛 ClassCastException，而报错信息通常不会告诉你加载器不同。

本文示例代码的已知问题

  • CmptServiceImpl.removeCmpt 传给 unLoadJar 的是 jar 路径，而 map 的 key 是 IdCmptDef，卸载不生效，加载器泄漏。
  • destroy() 被调用两次（显式一次、removeEntry 内一次），需要幂等。
  • 注册观察者处的 (AbstractCmpt) cmpt 缺少 instanceof 判断。
  • refreshCmptInstanceCache 是空实现，固定返回 false。
  • FileUtil 缺少 LoadClassUtil 里用到的 fileInfo；CmptClassLoader 依赖 sun.misc.URLClassPath，在 JDK 9 以上要改成直接调用 addURL，否则这段代码编译、运行都会失败。
  • invokeMethod 的变参匹配有缺陷，修正写法见上文。
