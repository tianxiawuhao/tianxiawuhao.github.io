分布式与微服务面试题

Posted on 2026-09-19，7 min read

本章面向准备中高级 Java 后端面试的读者。单机时代靠数据库 ACID 就能把数据管明白；一旦服务被拆成几十个进程、数据被分成若干分片，事务、服务寻址、流量治理就全成了新问题。本章串起面试中出现频率最高的四块内容：CAP 与 BASE、分布式事务落地方案、注册中心与服务发现、限流熔断与降级。目标是让你能说清“为什么这么设计”，以及“它在什么场景下会失效”。

一、CAP 与 BASE：一致性到底怎么取舍

先说结论：CAP 不是“三选二”。

CAP 是 2000 年 Eric Brewer 提出的猜想，2002 年被 MIT 的 Seth Gilbert 和 Nancy Lynch 证明。它说的是：一个分布式系统在发生网络分区时，无法同时保证一致性（Consistency，所有节点看到同一份数据）和可用性（Availability，每个请求都能拿到非错的响应）。分区容错性（Partition tolerance）不是可选项。只要服务跨网络部署，网络中断、丢包、超时就是客观事实，P 必须接受。所以真正的取舍是：分区发生的那一刻，你要 C 还是要 A；没有分区的时候，C 和 A 可以同时成立。

证明思路很直观：N1、N2 各存一份 V0，两者之间网络断了，客户端把 N1 改成 V1。此时另一个客户端来读 N2，要么返回过期的 V0（牺牲一致性），要么阻塞等待网络恢复（牺牲可用性）。Brewer 本人在 2012 年专门写文章澄清了“三选二”的误读，这一点在面试里是加分项。

实践中更常引用 BASE 理论。它由 eBay 架构师 Dan Pritchett 总结，是对 CAP 中 C 与 A 的权衡结果：

  • Basically Available（基本可用）：允许损失部分可用性，但不是系统不可用。比如大促时响应时间从 0.5 秒退化到 2 秒，或者把部分用户引流到降级页面。
  • Soft state（软状态）：允许数据存在中间状态，即副本同步可以滞后。
  • Eventually consistent（最终一致性）：经过一段时间同步后，所有副本最终达到一致。

要注意，BASE 不是“不要一致性”，而是把强一致换成“最终一致 + 对账补偿”，代价是业务必须能接受中间态，并且要有幂等、重试、对账兜底。

还有两个过时说法要纠正。一是“Spring Cloud 满足 AP，Dubbo 和 ZooKeeper 满足 CP”——Dubbo 是 RPC 框架，不定义一致性语义。CP/AP 形容的是它依赖的注册中心：Eureka 走 AP；ZooKeeper 走 CP，靠 ZAB 多数派写入，脑裂时少数派拒绝服务；Nacos 则可按实例类型切换。二是“CAP 就是三选二”，前面已经说明，P 不是可选项，取舍只发生在分区期间。

旧答案 → 现状：注册中心的选型变了。旧笔记默认“Eureka 是 Spring Cloud 标配”，这在今天要加限定。Eureka 1.x 早已进入维护模式，2.x 未开源，Spring Cloud 2020 之后的新项目更常选 Nacos（注册与配置一体、支持 AP/CP 切换、有中文社区与国产化落地）或 Consul（多数据中心、健康检查成熟）。Eureka 仍是自建 AP 注册中心的有效选项，尤其是已有大量遗留服务时，但面试答“为什么用 Eureka”要能说出 AP 取舍，而不是“Spring Cloud 自带”。

二、分布式事务：五种方案怎么选

分布式事务的本质是：一次业务操作跨越了多个数据源，每个数据源只能保证自己的本地事务，谁来保证整体一致？下面五种方案覆盖了绝大多数面试题。

1. 两阶段提交（2PC / XA）。事务协调者先向所有参与者发 prepare，等全部回复 yes 后再发 commit；任何一个回复 no 就全体 rollback。MySQL 从 5.0 起 InnoDB 引擎就支持 XA 事务，SQL Server 2005、Oracle 7 也支持。它的优点是强一致语义清晰，缺点是同步阻塞、协调者是单点，而且 commit 阶段如果部分参与者成功、协调者宕机，会出现数据不一致。所以它只适合参与者少、事务短、并发低的场景。

2. 补偿事务（TCC）。把一次操作拆成 Try（检测并预留资源）、Confirm（确认提交）、Cancel（回滚释放）三段，由业务代码实现补偿。它不依赖数据库的 XA，性能比 2PC 好，但一致性更弱，因为 Confirm 和 Cancel 本身也可能失败，必须靠重试和幂等兜底。它的三个经典坑是：空回滚，即 Try 没执行成功却收到了 Cancel；悬挂，即 Cancel 比 Try 先到，之后 Try 又把资源冻住；幂等，即同一笔 Confirm 被重试多次。

public interface AccountTccService {

    /** Try：检查余额并冻结资源；必须可重复执行 */
    boolean tryFreeze(String txId, String userId, long amount);

    /** Confirm：把冻结金额真正扣掉；只要 Try 成功就必须最终成功 */
    boolean confirm(String txId, String userId, long amount);

    /** Cancel：释放冻结金额；必须幂等，且要能处理空回滚 */
    boolean cancel(String txId, String userId, long amount);
}

3. 本地消息表。思路来自 eBay：在业务库里额外建一张消息表，业务写操作和插入消息记录放在同一个本地事务里提交；然后由定时任务或 MQ 把未发送、发送失败的消息重投，消费方处理成功后标记完成。这样就把分布式事务拆成了一串本地事务，实现简单、可用性高。代价是消息表耦合进业务库，消费端必须做幂等，还需要对账补账逻辑。这是实际业务里最常用的方案。

4. MQ 事务消息。以 RocketMQ 为例，流程分三步：先发一条对消费者不可见的半消息（Prepared）；再执行本地事务；最后根据本地事务结果向 Broker 发送 commit 或 rollback。如果 Broker 长时间没收到确认，会回调生产者的 check 接口反查本地事务状态，决定投递还是丢弃。注意 RabbitMQ 这类 MQ 不提供同等语义，Kafka 的事务只在 Kafka 内部生效，不能用来协调外部数据库。

5. Saga 事务模型。由 H.Garcia-Molina 等人提出，把长事务拆成多个本地短事务顺序执行，任何一步失败就按相反顺序调用各步的补偿操作。它没有 2PC 的阻塞问题，适合长流程（订车、订酒店、订机票），但缺乏隔离性，中间状态对外可见，需要“语义锁”等手段防止脏读，工程上通常由工作流引擎驱动。

选择上可以记一句话：参与者少、要求强一致、并发低，用 2PC；业务能定义补偿动作、要求较高性能，用 TCC；只想解决“本地写库 + 发消息”的一致性问题，优先本地消息表或 MQ 事务消息；流程特别长，用 Saga。

三、注册中心与服务发现

为什么需要注册中心？因为云环境下实例的 IP 和端口是动态的，扩容、缩容、重启都会改变它们。如果消费者把地址写死在配置文件里，就没法弹性伸缩。

注册中心负责三件事：服务提供者启动后注册自己的地址；消费者订阅并拿到一份可用实例列表；注册中心通过心跳或租约做健康检查，把失联实例剔除并推送给消费者。Java 生态里常见的有 ZooKeeper、Eureka、Nacos、Consul。

面试常考的是一致性取舍。ZooKeeper 使用 ZAB 协议，写操作需要多数派确认，属于 CP：分区时少数派节点无法提供服务，好处是列表不会出现“已经下线的实例还在里面”。Eureka 各节点对等复制，属于 AP：分区时仍能读写，但可能拿到过期列表，所以消费者侧必须配合重试和超时。Nacos 同时支持两种模式，临时实例走 AP、持久化实例走 CP，这是它比前两者更常被选用的原因之一。

消费者拿到实例列表后要选一个来调用，这就是负载均衡。随机、轮询最简单，但机器性能不齐时容易打偏。一致性哈希把节点和数据都映射到一个 0 到 2^32 - 1 的哈希环上，每个 key 顺时针找到第一个节点。节点增减时只有环上相邻的一小段数据需要迁移，容错性和扩展性都很好。它的缺点是节点少时容易数据倾斜，所以通常给每个物理节点挂几百个虚拟节点来均摊。

四、限流、熔断与降级

这三个词经常被混着说，其实职责不同。限流保护的是自己，控制入口流量不超过处理能力；熔断保护的是调用方，当依赖服务持续失败时快速失败，避免线程被耗尽；降级是兜底手段，出问题时返回兜底数据或关闭非核心功能。

限流算法有四类，各有取舍：

  • 固定窗口计数器：实现最简单，但窗口边界处可能瞬间放过两倍流量。
  • 滑动窗口：把时间切成细粒度格子并滚动统计，平滑了边界问题。
  • 漏桶：以恒定速率放行，溢出请求被丢弃，适合需要绝对平滑的场景。
  • 令牌桶：按固定速率往桶里放令牌，桶容量允许一定程度的突发流量，是最常用的选择。
public final class TokenBucketLimiter {

    private final long capacity;          // 桶容量，决定允许多大的突发
    private final double ratePerSecond;   // 每秒补充的令牌数
    private double tokens;
    private long lastRefillNanos;

    public TokenBucketLimiter(long capacity, double ratePerSecond) {
        this.capacity = capacity;
        this.ratePerSecond = ratePerSecond;
        this.tokens = capacity;           // 初始装满，允许一次突发
        this.lastRefillNanos = System.nanoTime();
    }

    public synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        double elapsed = (now - lastRefillNanos) / 1_000_000_000.0;
        lastRefillNanos = now;
        tokens = Math.min(capacity, tokens + elapsed * ratePerSecond);
        if (tokens >= 1.0) {
            tokens -= 1.0;
            return true;
        }
        return false;
    }
}

上面的实现只适合单机。集群限流要用 Redis，把“取令牌 + 扣减”写成一段 Lua 脚本交给 Redis 单线程原子执行，否则并发下会超卖。

熔断器是一个状态机。关闭状态下正常放行并统计失败率；失败率超过阈值就切到打开状态，直接拒绝请求；等待一段时间后进入半开状态，放少量探针请求，成功就恢复关闭，失败就继续打开。统计窗口通常按调用次数或按时间切片。

CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .slidingWindowType(CircuitBreakerConfig.SlidingWindowType.COUNT_BASED)
    .slidingWindowSize(20)                            // 统计最近 20 次
    .minimumNumberOfCalls(10)                         // 至少 10 次才计算失败率
    .failureRateThreshold(50.0f)                      // 失败率超过 50% 就打开
    .waitDurationInOpenState(Duration.ofSeconds(10))  // 10 秒后进入半开
    .permittedNumberOfCallsInHalfOpenState(5)         // 半开放行 5 次探针
    .build();

CircuitBreaker breaker = CircuitBreaker.of("payment", config);

public String pay(String orderId) {
    Supplier<String> supplier =
            CircuitBreaker.decorateSupplier(breaker, () -> remotePay(orderId));
    try {
        return supplier.get();
    } catch (CallNotPermittedException e) {
        return "FALLBACK";   // 已熔断，直接降级，不再打后端
    } catch (Exception e) {
        return "FALLBACK";   // 业务异常也走兜底
    }
}

这一块最常见的坑有三个。一是熔断只统计异常、不统计慢调用，下游“不报错但很慢”时线程池照样被拖垮，应该同时配置慢调用比例阈值。二是失败后立刻重试，重试流量又把刚恢复的服务打挂，形成重试风暴，所以重试要加退避和次数上限。三是降级逻辑没有开关，线上出故障时改不了行为。

五、小结

把这一章压缩成几句话。CAP 的真相是“分区发生时在 C 和 A 之间选一个”，BASE 是工程上更常用的答案。分布式事务没有银弹：2PC 强一致但阻塞；TCC 灵活，但要处理空回滚、悬挂和幂等；本地消息表与 MQ 事务消息追求最终一致且最实用；Saga 适合长流程。注册中心要按 CP/AP 取舍：选 CP 就接受分区时不可用，选 AP 就必须容忍过期列表并配合重试。限流、熔断、降级是三件不同的事，分别守住入口、出口和兜底，任何一个都需要幂等、退避和可动态开关的配置来配合。回答面试题时，先说清楚它解决什么问题、在什么条件下会失效，比背出定义更有说服力。
