9.7 消息队列与缓存面试题

Posted on 2025-01-29，5 min read

消息队列与缓存是 Java 后端面试出镜率最高的两个中间件话题。很多人能背出“解耦、异步、削峰”与“穿透、击穿、雪崩”，却说不清为什么会丢消息、为什么双写一定有不一致窗口。本章把两者放在一起讲，因为它们解决的其实是同一类问题：用一层中间存储换取解耦与性能，同时必须为这层存储的丢失、重复、失效买单。目标是把“为什么需要 → 怎么做 → 常见坑”讲成一条完整逻辑链。

一、为什么需要消息队列

解耦：A 产生一条数据，下游 B、C、D 都要用。若 A 直接同步调用三个接口，下游新增、下线、超时、重试全要 A 维护。改成 A 只投递一条消息，谁需要谁订阅。

异步：A 本地写库 3ms，B、C、D 分别 300ms、450ms、200ms，串行总延迟约 953ms；改为投递 3 条消息（约 5ms），响应降到 8ms 量级。

削峰：MQ 作为缓冲池，让下游按自身能力匀速消费。但削峰的前提是峰值总量能在可接受时间内消化完，否则只是推迟崩溃。

代价也要说清：可用性降低，MQ 挂了链路就断；复杂度升高，带来一致性问题、重复消费、可靠投递等新课题。回答“MQ 有什么缺点”时不要只说“复杂”，要落到具体问题上。

二、消息队列四大经典问题

1. 消息丢失：分三段兜底

生产者端用 confirm 模式，吞吐远高于 transaction 模式：进入 confirm 后每条消息获得唯一投递序号，Broker 落盘成功回 ACK，失败回 NACK，据此重发。Broker 端靠持久化：交换机、队列声明 durable，消息 deliveryMode 置为 2。只设 deliveryMode 而不设队列 durable，重启后队列消失，消息照样丢。消费端改成手动 ACK，业务处理成功后再确认。这里有一处版本变化：旧答案常提“镜像队列（mirrored classic queue）”，它在 RabbitMQ 3.9 起被废弃、3.13 已不推荐，4.0 起被彻底移除。以 3.13+ 为基线应改用 Quorum 队列：它基于 Raft 复制，天生具备 quorum 持久化与自动故障转移，声明时队列类型设为 quorum。ha-mode 一类的镜像策略参数也不再配置。

channel.confirmSelect();
channel.queueDeclare("order.queue", true, false, false, null);
channel.basicPublish("", "order.queue",
        MessageProperties.PERSISTENT_TEXT_PLAIN,
        "order-0001".getBytes(StandardCharsets.UTF_8));
if (!channel.waitForConfirms(5000)) {
    throw new IllegalStateException("未被 Broker 确认，需重发");
}

2. 重复消费：用幂等，而不是“保证只消费一次”

重复的根因是 ACK 在网络上丢了，Broker 重投。标准答案不是“怎么不重复”，而是承认重复不可避免，把消费端做成幂等：消息带全局唯一 ID，消费前用 Redis SET NX 去重；或把写入设计成天然幂等，例如 INSERT ... ON DUPLICATE KEY UPDATE、状态机单向流转；再用数据库唯一索引兜底。若用 Kafka，还要带上两点现状：

  • 其一，重复的来源不止 ACK 丢失：位点提交时机同样会引入重复。消费位点存放在内部主题 __consumer_offsets（默认 50 个分区），自动提交可能在业务处理完成前就推进位点，手动提交又可能重复，所以幂等始终是最后一道防线。
  • 其二，生产者幂等只覆盖一段链路：Kafka 0.11 起生产者可开启幂等（enable.idempotence=true，Kafka 3.x 已默认开启）。配合 acks=all 与 min.insync.replicas>=2 能消除重试导致的重复，但它只覆盖“生产者 → Broker”这一段，端到端仍需消费端幂等。
String key = "mq:consumed:" + orderNo;               // 业务唯一键
Boolean first = redis.opsForValue()
        .setIfAbsent(key, "1", Duration.ofHours(24)); // 底层即 SET NX
if (!Boolean.TRUE.equals(first)) {
    return;                                           // 重复消息，直接丢弃
}
try {
    orderService.handle(payload);
} catch (Exception e) {
    redis.delete(key);                                // 失败释放标记，允许重投
    throw e;
}

注意去重标记与业务处理并非原子。若标记已写入而进程崩溃，重投会被误判为重复，造成漏消费。高一致性场景应把去重记录与业务数据放进同一本地事务，或用“处理中 → 已完成”两阶段状态。

3. 顺序性：把并行改成串行

一个队列被多个消费者订阅时，消息按 round-robin 分发，无法保证处理顺序。做法只有两条：一个队列只对应一个消费者，用多队列换并发；或消费者内部维护内存队列，按 key 取模分发，每个内存队列单线程处理。Kafka、RocketMQ 是“同一 partition 内有序”，因此要用订单号之类做分区键，保证同一订单的消息落同一分区。

4. 积压：先扩容消费能力，再确认消息还在不在

顺序是：先修消费者、恢复速度，停掉现有消费者；再临时新建 partition 数量为原来 10 倍的 topic，用一个只转发的消费者把积压数据均匀写入；接着用 10 倍机器并行消费；完事恢复原架构。坑在于：若 Broker 配了消息 TTL，积压超过 TTL 的消息会被清理，那就是丢数据而非积压，只能低峰期从数据库捞出来补投。队列快写满且业务允许丢时，可先快速消费丢弃保住可用性，事后再补。

三、缓存穿透、击穿、雪崩

三个名字很像，成因完全不同，混淆是最常见的失分点。

穿透：数据在缓存和数据库都不存在，缓存永不命中。常用两种解法：

  • 一是缓存空值并设短 TTL（如 30 秒），否则大量伪造 key 会把缓存撑爆；
  • 二是前置布隆过滤器，用大 bitmap 拦截“一定不存在”的 key。代价是有误判率，且标准布隆过滤器不支持删除（需要删除能力时可用布谷鸟过滤器，如 RedisBloom 的 CF.DEL，代价是空间占用与误判语义不同）。

击穿：数据在数据库存在，但某个热点 key 恰好过期，大量并发请求同时回源。它与雪崩的区别是“并发查同一条数据”。解法是互斥锁，只让一个请求回源重建缓存，其余短暂等待后重试。

雪崩：大批 key 同一时刻集中失效，或缓存服务整体不可用。要分因应对：

  • key 集中过期：在基础 TTL 上叠加随机值打散。
  • 服务宕机：应对策略分三段。
    • 事前靠高可用（主从 + 哨兵或 Redis Cluster）；
    • 事中靠本地缓存与限流降级（Sentinel、Resilience4j 兜流量）。Hystrix 自 2018 年底进入维护模式、Spring Cloud 2020 起已移除对它的集成，新项目不应再选；
    • 事后快速恢复（开启持久化，避免冷启动打穿数据库）。
private static final long BASE_TTL = 1800;   // 基础 TTL 30 分钟
private static final Random RANDOM = new Random();

String cached = redis.opsForValue().get(key);
if (cached != null) {
    return "-".equals(cached) ? null : parse(cached); // 空值占位直接返回
}
Order order = orderMapper.selectById(orderId);
if (order == null) {
    redis.opsForValue().set(key, "-", Duration.ofSeconds(30)); // 防穿透
    return null;
}
long ttl = BASE_TTL + RANDOM.nextInt(300);   // 防雪崩：随机抖动
redis.opsForValue().set(key, toJson(order), Duration.ofSeconds(ttl));
return order;

四、双写一致性与 Redis 高可用

只要同时写缓存和数据库，就一定存在不一致窗口，工程上追求的是把窗口压到足够小。常用组合是 Cache Aside：先更新数据库，再删除缓存，而不是更新缓存。删除优于更新，是因为并发更新缓存容易出现“后写的旧值覆盖先写的新值”；删除则让下一次读请求自然回源。这条路径仍存在“回源读到旧值、写缓存晚于删除”的极小窗口，加固手段是延迟双删或订阅 binlog（如 Canal）异步失效。要求极高一致性时，可把读写串行化到内存队列，代价是吞吐大幅下降。

持久化：RDB 是某时刻全量快照，文件紧凑、恢复快，但两次快照之间的数据会丢；AOF 记录写命令，用 appendfsync everysec 折中。混合持久化是 4.0 引入的第三种形态：AOF 重写时先把当前数据以 RDB 格式写成前导（aof-use-rdb-preamble yes，该开关自 Redis 7.0 起默认开启），之后的增量仍按 AOF 追加，兼顾恢复速度与丢失窗口。这里要纠正两处老答案：

  • 一是“RDB 是 Redis 默认持久化方式”至今仍然成立：appendonly 在 Redis 7.x 乃至 8.x 的默认值依旧是 no，网上“7.0 起 AOF 已默认开启”的说法不准确。7.0 真正改的是 AOF 的实现形式：变为 multi-part（base 文件 + incr 文件 + manifest 统一管理），并默认使用 RDB 前导。
  • 二是 AOF 并非“只记录命令、文件一定更大”：混合持久化下 base 部分就是紧凑的二进制 RDB。

面试时把这两点带版本说清，比只背结论稳得多。

内存淘汰：内存不足时 noeviction 直接对写命令报错；缓存场景常用 allkeys-lru，只淘汰设了过期时间的 key 则用 volatile-lru、volatile-random、volatile-ttl；4.0 以后还有 LFU 系列（allkeys-lfu、volatile-lfu），对访问频率差异大的热点数据比 LRU 更准。要区分“过期删除策略”（惰性删除 + 定期抽样）与“内存淘汰策略”（内存写满时牺牲谁）。

分布式锁：正确的加锁方式是用一条原子命令完成“加锁 + 过期”，并写入客户端唯一标识；解锁时校验标识后用 Lua 删除，避免误删他人的锁。

// 加锁：SET key value NX EX 30，避免 SETNX 与 EXPIRE 之间宕机造成死锁
String requestId = UUID.randomUUID().toString();
Boolean locked = redis.opsForValue()
        .setIfAbsent("lock:order:1001", requestId, Duration.ofSeconds(30));
if (!Boolean.TRUE.equals(locked)) {
    throw new IllegalStateException("获取锁失败");
}
// 解锁：先比较 value 再删除，用 Lua 保证原子性
String unlockLua = "if redis.call('get', KEYS[1]) == ARGV[1] "
        + "then return redis.call('del', KEYS[1]) else return 0 end";
redis.execute(new DefaultRedisScript<>(unlockLua, Long.class),
        Collections.singletonList("lock:order:1001"), requestId);

锁的过期时间必须大于业务最长执行时间，否则业务没跑完锁就释放，其他线程会同时进入临界区。单机 Redis 主从切换时锁可能丢失，安全性要求高时应用 RedLock，或换用 ZooKeeper、etcd。

五、小结

MQ 的价值是解耦、异步、削峰，代价是可用性与复杂度。四大问题按环节拆解：丢失靠 confirm + 持久化 + 手动 ACK 兜底，重复靠消费端幂等，顺序靠单队列单消费者或按 key 分区，积压先确认消息是否被 TTL 清理再扩容消费。缓存要分清穿透（两边都没有）、击穿（热点 key 过期）、雪崩（大批 key 同时失效或服务不可用）。一致性上用 Cache Aside 先更新库再删缓存，接受窗口极小而非为零。再补上持久化选型、淘汰策略与原子加锁，把成因、方案、代价都讲清楚，面试深度就已超过多数候选人。
