Spring AOP 与事务

Posted on 2026-09-19，9 min read

前面几章把对象交给了 Spring 容器、把持久化交给了 Hibernate。但日志、权限校验、事务这类逻辑，几乎每个 Service 方法里都要写一遍：它们不属于任何一条业务规则，却横着穿过所有业务代码。AOP 就是为解决这件事而生的——把这些横切关注点抽成一个切面，在不修改业务代码的前提下织入执行流程；Spring 的声明式事务，本质上正是这套机制最重要的应用。这一章从动态代理讲起，把切面配置、通知类型、事务传播与隔离级别讲到能动手写，最后集中排掉「@Transactional 不生效」这类最常见的坑。内容面向已经会写 Service/DAO、被事务不生效折腾过的 Java 开发者。

一、AOP 的两层地基：横切关注点与动态代理

AOP（Aspect-Oriented Programming，面向切面编程）不是 OOP 的替代，而是补充。术语要先分清。切面（Aspect）是横切关注点被模块化后的对象，通知（Advice）是切面里真正干活的方法，切点（Pointcut）是「在哪些方法上生效」的匹配规则。连接点（JoinPoint）是程序执行中可以插入通知的时机，如方法调用前、正常返回后、抛出异常后。目标（Target）是被通知的原始对象，代理（Proxy）是目标对象被织入通知后对外暴露的对象。织入（Weaving）则是把切面接到目标上的动作。切点是筛选条件，连接点是被筛出来的记录，一个切点可以匹配多个连接点。

Spring AOP 不修改字节码，它靠运行期动态代理完成「织入」，因此有两条必须记住的边界。JDK 动态代理基于接口：只能为实现了接口的类生成代理，代理对象与目标对象是「兄弟」关系（实现同一接口），所以拿到代理后要用接口类型接收。CGLIB 通过生成目标类的子类来增强：不需要接口，但无法代理 final 类、final 方法和 private 方法，也增强不了构造器。目标类有接口时 Spring 默认用 JDK 代理，没有接口时自动改用 CGLIB；Spring Boot 把 proxyTargetClass 默认为 true，即优先使用 CGLIB。当所有通知都写对了、注入实现类类型却报错时，问题往往就出在这里。

二、动手写切面：五种通知与切入点表达式

依赖上引入 aspectjweaver 即可（Maven 一个坐标搞定。网上常见的 aspectjrt.jar、aspectjtools.jar、org.aspectj.matcher.jar 逐个导包，是早期手动管理依赖的产物）。再通过 @EnableAspectJAutoProxy（XML 中为 <aop:aspectj-autoproxy/>）开启支持，然后写切面类。这里要特别区分 @After 与 @AfterReturning：前者相当于 finally，方法抛异常也会执行；后者只在方法正常返回后执行，并能通过 returning 取到返回值。坊间常见的错法是把 @AfterReturning 称作「方法执行后增强」、把 @After 说成「后置通知」，甚至写出并不存在的注解 @AfterRunning，这些说法都不对。

package com.demo.aop;

import org.aspectj.lang.JoinPoint;
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.*;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;

@Order(1)        // 数值越小优先级越高；也可以用 <aop:aspect order="1"/>
@Aspect         // 声明这是一个切面
@Component      // 交给 IoC 容器管理
public class LoggingAspect {

    @Before("execution(* com.demo.service..*.*(..))")
    public void before(JoinPoint jp) {
        System.out.println("前置通知：" + jp.getSignature().getName());
    }

    @AfterReturning(pointcut = "execution(* com.demo.service..*.*(..))", returning = "result")
    public void afterReturning(Object result) {
        System.out.println("返回通知，返回值 = " + result);
    }

    @AfterThrowing(pointcut = "execution(* com.demo.service..*.*(..))", throwing = "ex")
    public void afterThrowing(Exception ex) {
        System.out.println("异常通知：" + ex.getMessage());
    }

    @After("execution(* com.demo.service..*.*(..))")
    public void after() {
        System.out.println("最终通知：无论是否抛异常都会执行");
    }

    @Around("execution(* com.demo.service..*.*(..))")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return pjp.proceed();   // 必须调用，否则目标方法不会执行
        } finally {
            System.out.println("耗时 " + (System.currentTimeMillis() - start) + " ms");
        }
    }
}

切入点表达式就是切面的「查询条件」，完整语法为 execution([修饰符] 返回类型 声明类型?.方法名(参数) [throws 异常])，其中返回类型不能省。举个例子，execution(public com.demo...AOPoperations.addC(String,String)) 就漏了返回类型，AspectJ 会把 com.demo...AOPoperations 当成返回类型；正确写法是 execution(public * com.demo...AOPoperations.addC(String, String))。另外，execution(* set(..)) 只能匹配名字恰好叫 set 的方法，要匹配所有 set 开头的方法得写 execution(* set*(..))。记住两个通配符：* 匹配任意字符，.. 在包路径中表示当前包及其子包、在参数列表中表示任意个任意类型参数。所以 execution(* com.demo.service..*.*(..)) 表示 service 包及子包下所有类的所有方法。XML 形式的装配如下：

<?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xmlns:aop="http://www.springframework.org/schema/aop"
       xsi:schemaLocation="http://www.springframework.org/schema/beans
           http://www.springframework.org/schema/beans/spring-beans.xsd
           http://www.springframework.org/schema/aop
           http://www.springframework.org/schema/aop/spring-aop.xsd">

    <!-- 开启 AspectJ 注解支持，容器会为匹配的 Bean 自动生成代理 -->
    <aop:aspectj-autoproxy/>

    <bean id="loggingAspect" class="com.demo.aop.LoggingAspect"/>
    <bean id="userService" class="com.demo.service.impl.UserServiceImpl"/>
</beans>

三、声明式事务：@Transactional 背后还是那个代理

事务是逻辑上一组操作。要么全部成功、要么全部失败，具备原子性、一致性、隔离性、持久性（ACID）。Spring 把事务管理抽象成三个接口：PlatformTransactionManager 真正管理事务，JDBC/MyBatis 用 DataSourceTransactionManager、Hibernate 用 HibernateTransactionManager。TransactionDefinition 描述事务定义，即隔离级别、传播行为、是否只读、超时时间；TransactionStatus 保存事务运行中的状态，如是否存在保存点、是否已完成。@Transactional 做的事，就是让 Spring 为标注它的 Bean 生成代理，在方法进入前开启事务、正常返回后提交、抛出异常时回滚。

@Service
public class AccountServiceImpl implements AccountService {

    @Autowired
    private AccountDao accountDao;

    @Transactional(propagation = Propagation.REQUIRED,
                   isolation = Isolation.READ_COMMITTED,
                   rollbackFor = Exception.class,   // 受检异常也要回滚
                   timeout = 5)
    @Override
    public void transfer(int fromId, int toId, double money) throws Exception {
        if (money <= 0) {
            throw new IllegalArgumentException("金额必须为正");
        }
        accountDao.out(fromId, money);
        accountDao.in(toId, money);            // 这里失败，上面的扣款一并回滚
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void writeLog(String msg) {          // 独立事务：主事务回滚也不影响日志
        // ...
    }
}

默认回滚规则必须记牢：只对 RuntimeException 和 Error 回滚，受检异常默认不回滚。上面 transfer 声明了 throws Exception，所以必须写 rollbackFor = Exception.class；只在个别异常上例外，用 noRollbackFor。readOnly = true 只是给驱动的提示，并不会强制禁止写操作，用在查询方法上帮助优化。

XML 方式在老项目里很常见，骨架如下。这里有个几乎人人踩过的细节：事务通知是 Advisor 而不是 Aspect，必须用 <aop:advisor> 织入；写成 <aop:aspect> 会要求 ref 指向普通对象并按方法名匹配，配错在启动阶段就会失败。

<!-- 1. 事务管理器：DataSourceTransactionManager 必须注入数据源 -->
<bean id="transactionManager"
      class="org.springframework.jdbc.datasource.DataSourceTransactionManager">
    <property name="dataSource" ref="dataSource"/>
</bean>

<!-- 2. 事务通知：声明哪些方法、用什么传播行为 -->
<tx:advice id="txAdvice" transaction-manager="transactionManager">
    <tx:attributes>
        <tx:method name="transfer" propagation="REQUIRED" rollback-for="java.lang.Exception"/>
        <tx:method name="find*" propagation="SUPPORTS" read-only="true"/>
        <tx:method name="*" propagation="REQUIRED"/>
    </tx:attributes>
</tx:advice>

<!-- 3. 织入切入点：事务是 Advisor，必须用 aop:advisor -->
<aop:config>
    <aop:pointcut id="txPointcut" expression="execution(* com.demo.service..*.*(..))"/>
    <aop:advisor advice-ref="txAdvice" pointcut-ref="txPointcut"/>
</aop:config>

<!-- 4. 若改用注解方式：加这一行即可，等价于 @EnableTransactionManagement -->
<tx:annotation-driven transaction-manager="transactionManager"/>

四、传播行为、隔离级别与事务失效场景

传播行为回答的是「当前方法被调用时，已有事务怎么办」。REQUIRED（默认）有则加入、无则新建；REQUIRES_NEW 挂起当前事务、另开独立事务，适合写日志这类「主事务回滚也不能丢」的操作。SUPPORTS 有则加入、无则以非事务方式运行；NOT_SUPPORTED 挂起当前事务、自己不使用事务；MANDATORY 要求必须已有事务，NEVER 要求必须没有事务，两者不满足都会抛异常；NESTED 在当前事务内开一个保存点，内层回滚不影响外层。注意 NESTED 依赖 JDBC 保存点，DataSourceTransactionManager 支持，而 JPA 的 JpaTransactionManager 不支持。

隔离级别用来解决并发读问题：READ_UNCOMMITTED 会脏读。READ_COMMITTED 能防脏读，但可能不可重复读；REPEATABLE_READ 能防不可重复读，MySQL 的默认级别还靠间隙锁挡住了大部分幻读；SERIALIZABLE 最安全也最慢。Spring 的 Isolation.DEFAULT 表示交给数据库默认值，多数业务不需要显式指定，但要知道自己正在用什么。

最后是最实用的一节：事务为什么不生效。①自调用——同一个类里用 this.methodB() 调用标注了事务的 methodB，走的是原始对象而非代理对象，事务根本不会开启，这是头号原因；可注入自身、拆到另一个 Bean，或改用 AspectJ 织入解决。②方法不是 public——基于代理的 @Transactional 只对 public 方法生效。private、protected、包可见的方法即使加了注解也不会被增强（private/final 方法在 CGLIB 下同样无法覆写）。③Bean 没交给容器——自己 new 出来的对象不在容器里，代理无从生成。④异常被吞——方法内 try/catch 吃掉了异常，代理感知不到失败；确需捕获时用 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() 手动标记回滚。⑤抛的是受检异常却忘了 rollbackFor。⑥事务跨线程——事务信息存在 ThreadLocal 里，新起的线程不在同一事务中。⑦数据库或表引擎不支持事务，例如 MySQL 的 MyISAM 表，怎么配都不会回滚。

小结

AOP 用动态代理把横切逻辑织进业务方法：切点决定「在哪里织」，通知决定「什么时候做什么」。声明式事务是这套机制最重要的应用，@Transactional 是否生效，取决于「有没有走代理」和「异常有没有按规则抛出来」。动手时先确认代理类型与接收类型是否匹配，再核对传播行为、隔离级别与回滚规则，最后用自调用、非 public、异常被吞这三项自查不生效问题，大部分故障都能当场定位。另外，不同 Spring / Spring Boot 版本对 proxyTargetClass 默认值、以及 NESTED 在各持久化技术下的支持范围存在差异，升级框架时请以对应版本文档为准。
