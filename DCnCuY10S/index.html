切面链实现

Posted on 2022-10-26，2 min read

业务代码里最容易被写死的，是「上传前记日志、上传前鉴权、上传后清理」这类横切逻辑。把它们逐个 if 进业务方法，改一次需求就要动所有入口。更干净的做法是把手写的切面串成一条链：每个切面只管自己的事，调用完 chain.next() 把控制权交出去，业务逻辑作为链尾的回调被包在最里面。本文先讲清这套 切面链 的实现，再对照 Spring AOP 的 Advisor 匹配与排序、动态代理的选择条件，以及自调用绕过代理这类真实踩坑点。

一、切面链要解决什么问题

目标很朴素：一个服务方法被调用时，允许任意多个「切面」按顺序插手，且插手的数量和顺序可以在运行时增删。为此需要三个角色：

  • 切面接口：约定切面如何被调用，以及如何把调用继续向下传递；
  • 切面链：持有切面集合的迭代器，负责「把请求交给下一个切面」；
  • 链尾回调：真正的业务逻辑，链走完后执行。

这三者构成的其实是责任链模式的一个变体：与前缀式责任链不同的是，这里的每个切面在调用 chain.next() 之后还能继续执行代码，因此它天然具备「环绕通知」的能力 —— next() 之前是前置逻辑，next() 之后是后置逻辑。

二、切面接口的设计

/**
 * 服务切面接口，用来干预服务
 */
public interface ServiceAspect {


    /**
     * 上传，成功返回文件信息，失败返回 null
     */
    default ServiceInfo serviceAround(ServiceAspectChain chain, ServiceInfo serviceInfo) {
        return chain.next(serviceInfo);
    }
}

关键点在于 serviceAround 是一个 default 方法，默认实现就是「我什么都不做，直接交给下一个」。这样只关心部分逻辑的切面不必实现全部方法，接口后续新增能力也不会立刻打破已有实现类。

三、切面链的实现

/**
 * 服务的切面调用链
 */
@Getter
@Setter
public class ServiceAspectChain {

    private ServiceAspectChainCallback callback;
    private Iterator<ServiceAspect> aspectIterator;

    public ServiceAspectChain(Iterable<ServiceAspect> aspects, ServiceAspectChainCallback callback) {
        this.aspectIterator = aspects.iterator();
        this.callback = callback;
    }

    /**
     * 调用下一个切面(遍历执行最后一个)
     */
    public ServiceInfo next(ServiceInfo serviceInfo) {
        if (aspectIterator.hasNext()) {//还有下一个
            return aspectIterator.next().serviceAround(this,serviceInfo);
        } else {
            return callback.run(serviceInfo);
        }
    }
    }

这里有两个细节值得说明。第一，ServiceAspectChain 只持有一个 Iterator<ServiceAspect>，链的推进状态就藏在这个迭代器里：next() 每被调用一次就前进一格，走不动时执行 callback。这意味着链是一次性的，同一个实例第二次 next() 会直接掉到业务回调，前面所有切面都被跳过。所以正确用法是每次服务调用都 new 一条链，而切面对象本身做成无状态单例，这与 Spring 中 @Aspect 默认 singleton 的约束是同一个道理。

第二，数据只能顺着 ServiceInfo 或显式上下文传递。LogServiceAspect 在调用前后打印日志时，接收的是链传递下来的同一个 serviceInfo，切面无法把自己的临时状态挂在链上并指望下一个切面读到 —— 链里只有迭代器和回调两个字段，没有请求级状态槽。这既避免了并发串数据，也限制了下游切面对参数的重写能力：想改参数，只能在 next() 之前构造新的 serviceInfo 传入。

四、链尾回调与业务侧用法

/**
 * 切面调用链结束回调
 */
public interface ServiceAspectChainCallback {
    ServiceInfo run(ServiceInfo serviceInfo);
}

private CopyOnWriteArrayList<ServiceAspect> aspectList;
private ServiceInfo serviceInfo;

//处理切面
new ServiceAspectChain(aspectList,(_serviceInfo) -> {
    //业务逻辑
    return _serviceInfo;
}).next(serviceInfo);

业务侧只认识两件事：切面列表和「真正的活儿」。把业务逻辑写成 lambda 传给 ServiceAspectChain，再调用一次 next() 启动整条链，调用方完全不需要知道中间有几个切面。

五、一个具体切面：日志

/**
 * 接口实现,使用切面打印日志
 */
@Slf4j
@Component
public class LogServiceAspect implements ServiceAspect {

    @Override
    public serviceInfo serviceAround(ServiceAspectChain chain,ServiceInfo serviceInfo) {
        log.info("上传文件 before -> {}",serviceInfo);
        serviceInfo = chain.next(serviceInfo);
        log.info("上传文件 after -> {}",serviceInfo);
        return serviceInfo;
    }

}

六、两处容易忽略的实现缺陷

上面两段代码直接抄进项目是编译不过的，问题出在两个很小的地方。

其一是多余的右花括号。ServiceAspectChain 类体内已经用 next() 方法的右括号收尾，末尾又多出一个 }，编译器会直接报「class, interface, or enum expected」。删掉即可。

其二是大小写不一致。ServiceAspect 接口和链中声明的返回类型都是 ServiceInfo，而 LogServiceAspect 的实现签名写成了小写的 serviceInfo。Java 是大小写敏感的语言，这既不是合法的返回类型，也不构成对接口方法的重写 —— 即使补上 @Override，编译期就会失败。修正后的实现如下：

/**
 * 接口实现,使用切面打印日志（修正版）
 */
@Slf4j
@Component
public class LogServiceAspect implements ServiceAspect {

    @Override
    public ServiceInfo serviceAround(ServiceAspectChain chain, ServiceInfo serviceInfo) {
        log.info("上传文件 before -> {}", serviceInfo);
        // 关键：把控制权交给下一个切面，返回值可能已被下游改写
        ServiceInfo result = chain.next(serviceInfo);
        log.info("上传文件 after -> {}", result);
        return result;
    }
}

这里刻意把返回值单独接收再打印，而不是像原实现那样把 chain.next() 的结果重新赋给入参 serviceInfo。两者行为一致，但复用入参名会让「前置日志打印的是入参、后置日志打印的是返回值」这一事实变得难以察觉，排障时容易误判。

七、运行时增删切面与顺序

切面列表用 CopyOnWriteArrayList 承载，是为了让「服务调用正在遍历切面」与「配置中心热更新增删切面」这两件事可以并发进行而不抛 ConcurrentModificationException。它的语义是写时复制：每次增删都复制整个数组，读操作无锁。切面的数量通常是十几个量级、变更频率极低，这个取舍完全合理；反过来，如果把它用在频繁写入的场景，复制开销就会失控。

{
    //获得切面 List
    List<ServiceAspect> list = new CopyOnWriteArrayList<>();

    //增加
    LogServiceAspect aspect = new LogServiceAspect();
    list.add(aspect);

    //删除
    list.remove(aspect);

    //条件删除
    list.removeIf(item -> item instanceof LogServiceAspect);
}

需要明确的是：这份列表的插入顺序就是切面的执行顺序，且没有任何排序机制。谁先被 add，谁就在链的最外层，它的前置逻辑最先执行、后置逻辑最后执行。这在只有日志切面时无所谓，一旦混入鉴权、事务、幂等、限流，顺序就变成了正确性问题 —— 这正是下一节 Spring AOP 用 @Order 显式表达的东西。

八、对照 Spring AOP 的切面链

手写切面链是「把切面集合按顺序串起来」，Spring AOP 做的是同一件事，只是链的构建被拆成了两个阶段：先按切点匹配筛选，再按优先级排序。

阶段一：匹配。容器启动时，Spring 为每个候选 Bean 找出所有可用的 Advisor（可以理解为「切点 + 通知」的组合）。Advisor 的 getPointcut() 决定它是否作用于当前类、当前方法，getAdvice() 才是真正要执行的通知。方法级匹配的判定大致是：类匹配（ClassFilter.matches）与当前是否处于代理创建阶段，再逐层叠加方法匹配（MethodMatcher.matches）。运行时匹配（isRuntime() 为真）的切点无法在启动期定论，Enter 每次调用都需要重新判断，性能更差，因此能静态匹配就不要写成依赖参数的动态匹配。

阶段二：排序。筛选出的 Advisor 会被整理成一条通知链，顺序由 @Order（或实现 Ordered / PriorityOrdered）决定，数值越小越靠外。Spring 自己注册的事务通知 BeanFactoryTransactionAttributeSourceAdvisor 默认顺序是 Ordered.LOWEST_PRECEDENCE，也就是最内层 —— 这一点在第九节会成为一个具体的坑。

上图的回溯路径解释了一个常被忽略的事实：切面的进入顺序与退出顺序严格相反。这也决定了资源释放必须写在 finally 里，而不是写在 chain.next() 之后的普通语句里 —— 一旦下游抛异常，后者根本不会被执行。

九、JDK 动态代理与 CGLIB 的选择条件

切面链再完美，也得有东西把方法调用拦下来，这就是代理。DefaultAopProxyFactory 的规则可以概括为一句话：目标类实现了接口就优先用 JDK 动态代理，否则回退到 CGLIB，并且从 Spring 4.x 起 CGLIB 代理不再要求目标类有默认构造函数（objenesis 负责实例化）。proxyTargetClass = true 则强制走 CGLIB。

两者的能力边界差别很大：JDK 动态代理基于接口生成实现类，代理对象与目标对象是兄弟关系，只能通过接口类型引用，因此注入时必须按接口注入，注入实现类会报类型不匹配；CGLIB 通过继承目标类生成子类，代理对象是目标类的子类型，可以按类注入，但代价是不能代理 final 类，也不能代理 final 方法 —— final 方法无法被覆写，通知会静默失效，既不报错也不生效。

还有两个容易混淆的限制：一是 private 方法与 static 方法都不在代理范围内；二是自调用（this 调用）不经过代理。原因很直接：代理对象持有的只是目标对象引用，外部调用先进代理，但目标对象内部执行 this.b() 时，this 就是真实对象自己，JVM 直接在虚方法表里解析，代理没有任何介入机会。表现上就是 a() 上的事务、日志生效，a() 内部调用的 b() 上同样的注解却完全失效。

解法有三种，思路都是「让调用重新穿过代理」：

  • AopContext.currentProxy()：需要开启 @EnableAspectJAutoProxy(exposeProxy = true)，代理会把自身放入 AopContext 的 ThreadLocal，代码里用 ((XxxService) AopContext.currentProxy()).b() 调用。缺点是业务代码绑定了 Spring API，且该调用栈必须仍处于代理内部。
  • 注入自身：@Autowired 注入自己（或注入 ObjectProvider<Self>），容器给出的是代理而非 this，调用它即可。这是侵入性最低的写法，但要注意 @Lazy 兜底循环依赖。
  • AspectJ 编译期 / 加载期织入：通知直接织进字节码，不存在代理边界，自调用同样生效，连 private 方法也能被通知。代价是引入 aspectj-maven-plugin 或 -javaagent，构建链路更重。

顺带澄清一个常见误解：@Transactional 失效时，人们首先怀疑「是不是没用 CGLIB」，实际上默认代理模式下自调用导致的失效占比远高于 final 类。排查时先用 AopUtils.isAopProxy(bean) 与断点确认拿到的引用到底是不是代理，比盲目切换 proxyTargetClass 有效得多。

十、@Around 中 proceed 的语义

回到切面链，chain.next() 与 Spring @Around 中的 ProceedingJoinPoint.proceed() 是同一个东西：它既是「执行下一个切面或目标方法」的开关，也是这条链上唯一的返回值出口。

由此派生三条必须记住的规则：

  • 不调用 proceed() 就等于短路。目标方法不会执行，可以返回默认值、缓存值或直接抛异常。限流、幂等、缓存命中都靠这个特性实现，但用得不当会造成「业务没跑却没报错」的诡异现象。
  • 调用多次 proceed() 会重复执行目标方法。带参数重试时要特别小心：重试次数与事务、幂等性叠加后极易造成重复写库。
  • 返回值的取舍权在切面手里。proceed() 的返回值如果被丢弃、被包装或返回 null，调用方拿到的就是切面给的版本，而非目标方法的真实结果。这与前面手写链中「把 chain.next() 结果重新赋给入参」的写法风险一致。
@Slf4j
@Aspect
@Component
public class UploadLogAspect {

    @Around("execution(* com.example.service.UploadService.upload(..))")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            Object result = pjp.proceed();      // 下行：进入下一个切面/目标方法
            log.info("upload ok, cost={}ms", System.currentTimeMillis() - start);
            return result;                      // 必须是 proceed 的返回值
        } catch (Throwable e) {
            log.error("upload failed, cost={}ms", System.currentTimeMillis() - start, e);
            throw e;                            // 不要吞异常，否则事务回滚判定会失真
        } finally {
            // 释放型逻辑放这里：无论正常返回还是抛异常都会执行
            MDC.clear();
        }
    }
}

关于异常传播，务必记住两点。一是不要为了「日志好看」而 catch (Exception e) { return null; }：异常被吞掉后，@Transactional 认为方法正常返回，会提交事务，本该回滚的脏数据就落库了；同时调用方拿到 null，错误在更远的地方才暴露，排查成本成倍增加。二是 finally 里不要 return 或抛异常，它会覆盖 try 中的返回值与异常，让真正的失败原因彻底消失。

十一、事务切面与自定义切面的顺序坑

顺序问题的核心只有一条：值越小越靠外，越靠外的切面前置逻辑越先执行、后置逻辑越后执行。据此可以推导出几个典型场景的正确排法：

  • 事务要包住业务，也要包住自定义切面里的写操作：事务通知在最内层（默认就是如此），意味着自定义切面若在 proceed() 之后写库，这次写入其实已经跑出了事务边界，不会被回滚。要让它进事务，就得把自定义切面排在事务之外 —— 但这会带来新问题：切面自身抛异常时事务无法感知。
  • 鉴权与限流必须在事务之外：否则校验失败也开了事务，白白占用连接；更重要的是，鉴权异常如果发生在事务内部，可能触发一次无意义的回滚流程。
  • 缓存切面的顺序最讲究：读缓存应在事务之外，避免为了命中缓存去开事务；而缓存失效（删除缓存）若要和数据库写保持一致，就必须处于同一个事务边界内，或改用先提交后删除 + 延迟双删等补偿策略。

实践中还有两个高频坑。其一，用 @Order 排自定义切面时不写数值，默认是 Ordered.LOWEST_PRECEDENCE，与事务通知同层，此时先后顺序取决于 Advisor 的注册顺序，在不同 Spring 版本或不同配置下可能变化。其二，同一个切面类里多个 @Around 方法之间没有可依赖的顺序，需要明确先后时应当拆成多个 @Aspect 类并显式标注 @Order。

最后提示一个排查技巧：拿不准实际顺序时，不要靠猜。在切面入口打印一次日志，或直接调试 ReflectiveMethodInvocation 的 interceptorsAndDynamicMethodMatchers 字段，就能看到这条链上真实的 Advisor 排列。

十二、小结

  • 手写切面链的本质是责任链 + 链尾回调，chain.next() 兼具「下行的开关」和「返回值的唯一出口」两重语义。
  • 链的推进状态在迭代器里，链必须一次一建；切面本身应保持无状态。
  • 列表的插入顺序就是执行顺序，手写链没有排序机制，顺序即正确性。
  • Spring AOP 把这件事规范化为「Advisor 匹配 → 按 @Order 排序 → 代理拦截」，值越小越靠外。
  • 有接口优先 JDK 动态代理，否则 CGLIB；final 类、final 方法、private 方法、static 方法都不在代理范围内。
  • 自调用绕过代理是最高频的失效原因，解法是 AopContext、注入自身或 AspectJ 织入。
  • 环绕通知中异常要原样抛出，释放逻辑写进 finally，顺序拿不准就用日志验证而不是猜。
