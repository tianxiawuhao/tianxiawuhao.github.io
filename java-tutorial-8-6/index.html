8.6 Kafka 消息中间件

Posted on 2025-01-01，9 min read

前面几章处理的数据，要么来自本地文件，要么来自数据库。但在真实系统里，日志、埋点、订单变更这些数据是持续不断产生的，而且往往有好几个下游同时要用：实时风控要、离线数仓要、搜索索引也要。如果让每个业务都直接连业务库，数据库会被拖垮，上下游也被死死耦合在一起。Kafka 就是为这类问题而生的分布式消息中间件。本章面向已经会写 Java、但还没在生产环境用过消息队列的读者，目标是讲清 Kafka 的核心模型（分区、副本、消费组、offset、事务），并能写出可运行的生产者与消费者代码。

版本基线（3.x）：本章以 Kafka 3.x 为准，客户端与 broker 尽量保持同大版本。3.x 同时支持 ZooKeeper 与 KRaft 两种部署模式，其中 KRaft 自 3.3（3.3.1）起可用于生产；ZooKeeper 模式在 4.0 中已被移除，新集群直接用 KRaft 即可。4.0 起 broker / Connect / 命令行工具要求 JDK 17，客户端与 Kafka Streams 要求 JDK 11。文中保留的旧写法（0.9 之前的 offset 存储、2.8 之前的 --zookeeper）只作演进对照，不要再照抄。

一、Kafka 是什么：一个分布式提交日志

Kafka 由 LinkedIn 开发并于 2010 年捐献给 Apache 基金会，用 Scala 和 Java 编写。它最容易被误解的一点是：Kafka 本质不是一个“消息队列”，而是一个分布式、可分区的、多副本的提交日志（commit log）。消息不是被消费掉就删除，而是按配置的保留时间（如 7 天）或保留大小统一清理，因此同一个 topic 可以被多个业务反复读取，互不影响。

几个必须记住的术语：

  • Broker：一个 Kafka 服务节点。多台 broker 组成集群，每台 broker 上可以承载多个 topic 的分区。
  • Topic：消息的逻辑类别，类似数据库里的表。
  • Partition：topic 的物理分片，是并行与有序的基本单位。分区内部消息严格有序，分区之间不保证顺序。
  • Offset：消息在分区内的唯一递增编号，消费者用它记录自己读到哪儿了。
  • Replica：分区的副本。每个分区有一个 leader 副本和若干 follower 副本，读写只走 leader，follower 负责同步以备故障切换。
  • Consumer Group：消费者组。同一条消息，在同一个组内只会被一个消费者处理；不同组之间各自独立消费全量消息（组内是单播，组间是广播）。

Kafka 的高吞吐来自几处设计：分区带来的水平扩展、批量发送与批量拉取、利用操作系统的 page cache 而不自己维护缓存、以及用 sendfile 零拷贝把日志文件直接送到网卡。日志追加写也保证了每个分区的读写都是 O(1) 的常数时间操作，性能基本与数据总量无关。

二、分区与副本：并行度和可靠性的来源

2.1 分区决定了并行度上限

请记住一条约束：同一个消费组内，一个分区同一时刻只能被一个消费者线程消费。这条约束是 Kafka 不需要给消息加锁、从而获得高吞吐的根本原因，但它也直接推出了实践中的容量规划规则：

  • 消费者数 < 分区数：部分消费者要承担多个分区，负载不均；
  • 消费者数 = 分区数：最理想，每个消费者正好对应一个分区；
  • 消费者数 > 分区数：多出来的消费者线程会一直空闲，纯属浪费。

所以真正的扩容手段是先加分区，再加消费者，而且两者要一起加。分区数可以作为 topic 参数在线增加，但只能增加不能减少，并且增加分区会导致分区内消息的哈希落点变化，因此分区数最好在创建时就把未来一两年的量估足。

2.2 副本与 ISR

每个分区可以配置多个副本（replication factor）。副本中只有一个 leader 对外提供读写，其余 follower 持续向 leader 拉取数据。为了让“同步”有一个明确的判定标准，Kafka 引入了 ISR（In-Sync Replicas，同步副本集合）：只有跟得上 leader 进度的副本才在 ISR 里。落后太多的副本会被踢出 ISR，追上后再加回来。当 leader 所在 broker 宕机时，controller 会从 ISR 中选一个新 leader；如果 ISR 空了，说明没有副本能保证数据完整，此时只能等待 ISR 成员恢复。

需要特别纠正一个常见说法——“备份数为 n 就允许 n-1 个节点失败”：这句话只描述了数据不丢的容灾能力。如果同时宕机的副本数超过容忍范围，虽然集群还能读，但已经写入却未同步的消息会丢失。要保证不丢，必须让 acks 和 ISR 判定配合起来，下一节会讲。

三、上手：创建主题并读写消息

先创建主题。这里要注意版本差异：Kafka 2.8 起 kafka-topics.sh 的 --zookeeper 参数已被废弃，应改用 --bootstrap-server（4.0 中已彻底移除）。原因在于所有管理类命令都改从 broker 获取元数据。broker 无论跑在 ZooKeeper 模式还是 KRaft 模式下，都能通过 bootstrap 地址应答。而 --zookeeper 是绕过 broker 直连 ZooKeeper 读元数据的老路子，在 KRaft 模式下根本不存在 ZooKeeper 可连。消费者组、位移等命令同理，见 kafka-consumer-groups.sh --bootstrap-server。

# 创建 3 个分区、2 个副本的主题（副本数不能超过 broker 数）
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic order-events \
  --partitions 3 --replication-factor 2

# 查看主题详情，确认 Leader 与 Isr 分布
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic order-events

# 命令行消费，--from-beginning 表示从最早的消息开始读
kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic order-events --from-beginning

Java 侧的依赖（Maven）。Kafka 客户端版本应与 broker 大版本尽量接近，且序列化器必须与消息类型匹配：

<dependency>
  <groupId>org.apache.kafka</groupId>
  <artifactId>kafka-clients</artifactId>
  <version>3.6.1</version>
</dependency>

下面是生产者示例。三种发送方式都演示了：发完不管、同步等待、异步回调。注意 acks=all 表示 leader 要等 ISR 中所有副本确认，是可靠性最高的设置；若追求吞吐可降到 1，但 leader 刚写入就宕机时可能丢消息。

public class OrderProducer implements Closeable {

    private final KafkaProducer<String, String> producer;

    public OrderProducer(String bootstrapServers) {
        Properties props = new Properties();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, bootstrapServers);
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,
                StringSerializer.class.getName());
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
                StringSerializer.class.getName());
        // 可靠性优先：等所有 ISR 副本确认
        props.put(ProducerConfig.ACKS_CONFIG, "all");
        // 幂等：重试不会造成重复写入（要求 acks=all、未开启重试无限次）
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
        this.producer = new KafkaProducer<>(props);
    }

    /** key 相同的消息一定进入同一分区，从而保证同一订单的事件有序 */
    public void send(String orderId, String payload) {
        ProducerRecord<String, String> record =
                new ProducerRecord<>("order-events", orderId, payload);
        producer.send(record, (metadata, exception) -> {
            if (exception != null) {
                // 生产中应记录日志并进入重试/死信逻辑，切勿只打印
                System.err.println("send failed: " + exception.getMessage());
            } else {
                System.out.printf("topic=%s partition=%d offset=%d%n",
                        metadata.topic(), metadata.partition(), metadata.offset());
            }
        });
    }

    @Override
    public void close() {
        producer.close(Duration.ofSeconds(10));
    }
}

消费者的基本形态是一个“拉取循环”。Kafka 消费者采用 poll 模式，没有数据时会阻塞等待，因此必须在循环里正确处理唤醒与提交。

Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "order-analytics");
props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG,
        StringDeserializer.class.getName());
props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
        StringDeserializer.class.getName());
// 自动提交会"先提交后处理"，处理失败就丢消息；生产环境建议手动提交
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);

try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {
    consumer.subscribe(List.of("order-events"));
    while (true) {
        ConsumerRecords<String, String> records =
                consumer.poll(Duration.ofMillis(500));
        for (ConsumerRecord<String, String> record : records) {
            handle(record);          // 先业务处理
        }
        consumer.commitSync();       // 处理成功后再提交位移
    }
}

3.1 offset 存到哪里

消费者的位移（offset）表示“下一条要读的消息编号”。早期版本把位移写在 ZooKeeper 上，而 ZooKeeper 的频繁写入是低效的。Kafka 0.9 起默认改为提交到内部主题 __consumer_offsets。该主题是 compact 类型的日志，以「消费组 + topic + 分区」为 key，只保留每个 key 的最新值，既好扩展又能快速恢复。如果查资料时看到“offset 存在 ZooKeeper”，那基本是 0.9 之前的老内容。

提交方式的选择直接决定消息语义：自动提交可能丢消息（提交后处理失败），先处理后提交则是“至少一次”（处理成功但提交失败会重复）。想要“恰好一次”，要么让业务处理本身幂等，要么使用下一节的事务。

四、可靠性：从 acks 到事务

4.1 生产者不丢消息的三个条件

只设置 acks=all 还不够，它必须与 broker 端的 min.insync.replicas 联合判断：当 ISR 中的副本数少于该值时，broker 会直接拒绝写入并抛错，而不是“假装成功”。典型配置是 replication.factor=3、min.insync.replicas=2、acks=all：允许一个副本故障，同时保证每条被确认的消息至少存在于两个副本上。此外，还要配合足够大的 delivery.timeout.ms 和重试次数，否则重试还没成功，超时就已经把消息判死了。

4.2 消费组的再平衡

以下情况会触发 Rebalance：消费者加入或离开、订阅的 topic 分区数变化、以及消费者长时间未发送心跳被判定为失联。Rebalance 期间整个组会短暂停止消费，所以频繁 Rebalance 是线上最常见的故障之一。两个实用的规避手段：把 max.poll.interval.ms（两次 poll 之间允许的最大处理时间）调大，避免单批处理过慢被踢出组；给消费者设置稳定的 group.instance.id 使用静态成员，让短暂的进程重启不触发全组重平衡。

4.3 事务与恰好一次

在 0.11 版本之前，Kafka 只能做到“至少一次”。0.11 引入了幂等生产者与事务 API：用同一个 transactional.id 跨会话标识一个生产者实例，broker 会对该实例的写入做去重，并把多次发送与位移提交打包成一个原子事务。

// 事务要求：acks=all、enable.idempotence=true、且设置唯一的 transactional.id
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-tx-1");
// 注意：只读未提交事务时用 read_committed，默认的 read_uncommitted 会看到未提交数据
props.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");

producer.initTransactions();
try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("order-events", orderId, payload));
    // 把消费位移也纳入同一事务，实现"消费-处理-生产"的精确一次
    producer.sendOffsetsToTransaction(offsets, "order-analytics");
    producer.commitTransaction();
} catch (ProducerFencedException | OutOfOrderSequenceException e) {
    producer.close();                 // 此类异常不可恢复，必须重建生产者
} catch (KafkaException e) {
    producer.abortTransaction();      // 其他异常回滚并重试
}

需要强调：事务只保证 Kafka 内部的原子性，如果下游写的是 MySQL，跨系统的恰好一次要靠两阶段提交或本地事务表来兜底。另外 transactional.id 必须每个生产者实例唯一，重复会导致旧实例被“隔离”（fenced）而报错。

五、部署模式：ZooKeeper 与 KRaft 对照

Kafka 早期把「元数据」全部外包给 ZooKeeper，broker 本身几乎无状态。托管在 ZooKeeper znode 里的内容包括：

  • topic 与分区列表；
  • 副本分配；
  • ISR 变更；
  • controller 选举；
  • ACL。

代价是要多维护一套 ZooKeeper 集群，而且元数据规模一大（几十万分区），controller 启动时的全量加载就成了瓶颈。KRaft（KIP-500）把元数据收回到 Kafka 自己内部：用内置的 Raft 仲裁取代 ZooKeeper。元数据以日志 + 快照的形式存在内部主题 __cluster_metadata 中；controller 与 broker 可以合并在同一进程（process.roles=broker,controller），也可以分开部署。

演进时间线：

  • 2.8 引入 KRaft 作为实验特性；
  • 3.3（3.3.1）起 KRaft 可用于生产；
  • 3.5 起提供 ZooKeeper → KRaft 的迁移能力，并在此后版本逐步成熟；
  • 4.0 起 ZooKeeper 模式被彻底移除，KRaft 成为唯一模式。

因此 3.x 是最后一个「两种模式都支持」的版本线，新集群没有理由再选 ZooKeeper。

维度ZooKeeper 模式（≤ 3.x）KRaft 模式（2.8 实验 → 3.3 生产可用 → 4.0 起唯一）
元数据存储外部 ZooKeeper 集群的 znodeKafka 内部 __cluster_metadata 日志 + 快照
controller 选举经 ZooKeeper 抢占式选主Raft 仲裁选举，多数派在线即可
需部署的组件Kafka broker + 独立 ZooKeeper 集群只需 Kafka（controller 是其中一种角色）
关键配置zookeeper.connect=zk:2181process.roles、node.id、controller.quorum.voters
首次启动先起 ZooKeeper，再起 broker先 kafka-storage.sh format 格式化日志目录，再起 broker
管理命令--zookeeper（2.8 起废弃，4.0 移除）→ --bootstrap-server只能用 --bootstrap-server

KRaft 单节点的最小启动流程（3.x 的 config/kraft/server.properties）：

# 1. 生成集群 ID（幂等，同一集群用同一个）
KAFKA_CLUSTER_ID=$(kafka-storage.sh random-uuid)

# 2. 格式化日志目录，写入集群 ID 与元数据目录
kafka-storage.sh format -t "$KAFKA_CLUSTER_ID" -c config/kraft/server.properties

# 3. 启动 broker（controller 与 broker 同进程）
kafka-server-start.sh config/kraft/server.properties
# config/kraft/server.properties 的关键几行
process.roles=broker,controller
node.id=1
# 仲裁投票者列表；生产建议 3 个 controller，写成 1@h1:9093,2@h2:9093,3@h3:9093
controller.quorum.voters=1@localhost:9093
listeners=PLAINTEXT://:9092,CONTROLLER://:9093
log.dirs=/var/lib/kafka/data

对照之下，ZooKeeper 模式除了 server.properties 里的 zookeeper.connect，还要额外起一个 ZooKeeper 进程（zookeeper-server-start.sh config/zookeeper.properties）。若在老集群上排查「controller 是谁」，KRaft 下可用 kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status 查看仲裁状态，这比翻阅 ZooKeeper 的 /controller 节点直观得多。需要强调的是：客户端代码（生产者、消费者、AdminClient）与部署模式无关，无论集群用哪种模式，Java 侧都只是连 bootstrap.servers，本章的示例代码不需要任何改动。

六、常见坑与小结

上线前请对照这几条：

  1. key 为 null 导致乱序：不指定 key 时消息会轮询进各分区，同一实体的先后顺序就丢了。要顺序就按业务主键做 key。
  2. 消费堆积：先看是分区数不足还是单条处理太慢，前者加分区并同步加消费者（数量对齐分区数），后者优化处理逻辑或改为批量处理。
  3. 把提交位移当成“处理完成”：手动提交务必放在业务处理成功之后，并小心批内部分失败——此时应记录失败明细，而不是整批提交或整批重来。
  4. 副本数与 min.insync.replicas 配置矛盾：若 min.insync.replicas 大于实际可用副本数，写入会被全面拒绝，可用性骤降。
  5. 照抄老教程的参数：--zookeeper 已废弃（4.0 移除），应统一用 --bootstrap-server。消费者位移自 0.9 起不再存 ZooKeeper，而在 __consumer_offsets。自定义 partitioner.class 自 2.4 起进入废弃演进（2.4 KIP-480 粘性分区 → 3.3 KIP-794 均匀粘性分区，相关实现类已标记 @Deprecated）。新代码不要再显式指定它；需要按键均匀分布时用 partitioner.ignore.keys=true。另外新集群应直接建 KRaft 模式，ZooKeeper 模式已是遗留路径。

小结：Kafka 用“分区”解决吞吐与有序，用“ISR 副本 + acks + min.insync.replicas”解决不丢。它还用“消费组 + offset 提交”解决多下游并行消费，用“幂等生产者 + 事务”解决重复。把这四条记住，再结合自己的分区数、副本数和消费位点提交策略，就能搭出一个既跑得快、又不丢数据的消息链路。下一章看看流式处理框架如何消费这些数据做实时计算。
