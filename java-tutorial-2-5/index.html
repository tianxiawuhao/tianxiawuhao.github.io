2.5 JDBC 与连接池

Posted on 2026-09-19，8 min read

前面几章已经把 SQL 写顺了，但业务代码最终要通过 Java 去执行 SQL。本章解决三个递进的问题：怎么用 JDBC 安全地执行 SQL；怎么让多条 SQL 要么全成功、要么全失败；怎么避免每次请求都新建一次数据库连接、把数据库拖垮。本章适合已经会写基本 SQL、准备写第一个 DAO 的读者；只记得 Statement 和 conn.close() 也没关系，读完应当能写出可用于生产的数据库访问层。

一、JDBC 的最小闭环与 PreparedStatement

JDBC 是 JDK 提供的一套数据库访问规范，驱动（MySQL 的 mysql-connector-j、Oracle 的 ojdbc）负责把规范翻译成具体数据库的协议。一次查询的固定动作是：注册/加载驱动 → 用 URL、用户名、密码拿到 Connection → 创建语句对象 → 执行并处理 ResultSet → 关闭资源。现代驱动通过 SPI 自动注册，通常不必再写 Class.forName("com.mysql.cj.jdbc.Driver")。

真正容易写错的是语句对象的选择。用字符串拼接 SQL 会引入 SQL 注入：用户输入 ' OR '1'='1 就能把条件改写成恒真。PreparedStatement 使用 ? 占位符，参数通过 setXxx 绑定，驱动会把参数当作纯数据而非 SQL 语法，从根本上堵住注入。此外，同一条 SQL 重复执行时，数据库可以复用执行计划，性能也更好。所以除了极少数动态表名、动态排序字段（这类无法参数化的部分必须用白名单校验），都应该用 PreparedStatement。

public class JdbcDemo {
    private static final String URL = "jdbc:mysql://localhost:3306/day06_db"
            + "?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai";

    public static List<String> findNamesAbove(double money) {
        String sql = "select name from account where money > ?";
        List<String> names = new ArrayList<>();
        // try-with-resources：Connection、Statement、ResultSet 都是 AutoCloseable
        try (Connection conn = DriverManager.getConnection(URL, "root", "root");
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setDouble(1, money);
            try (ResultSet rs = ps.executeQuery()) {
                while (rs.next()) {
                    names.add(rs.getString("name"));
                }
            }
        } catch (SQLException e) {
            throw new RuntimeException("查询账户失败", e);
        }
        return names;
    }
}

这段代码里的驱动与 URL 参数，几乎每一条在 8.x 时代都换过写法。驱动类名：Connector/J 5.1.x 写 com.mysql.jdbc.Driver，8.x 换成 com.mysql.cj.jdbc.Driver（8.0.x 里旧类名多数还保留但会打印弃用告警，不要依赖它）。JDBC 4.0（Java 6）起驱动通过 SPI（META-INF/services/java.sql.Driver）自动注册，Class.forName("com.mysql.cj.jdbc.Driver") 通常可以省，只有自定义类加载器或老容器才需要显式加载。URL 参数同样换了名字，旧笔记里的写法与现行写法的对照如下：

用途旧写法（Connector/J 5.1.x 时代）现行写法（8.x，MySQL 8.0/8.4）与常见坑
加密连接useSSL=false、requireSSL=true、verifyServerCertificate=falsesslMode=DISABLED|PREFERRED|REQUIRED|VERIFY_CA|VERIFY_IDENTITY：8.0.13 起三个旧参数合并为 sslMode（默认 PREFERRED），旧名仍被接受但已弃用。生产上写 DISABLED 等于明文传密码，至少用 REQUIRED，要校验证书则用 VERIFY_CA 或 VERIFY_IDENTITY。
时区serverTimezone=Asia/ShanghaiconnectionTimeZone=Asia/Shanghai：8.0.23 起改用新名，旧名仍可用但已弃用。它只影响驱动端的时区换算；要让服务端会话时区一起变，还需加 forceConnectionTimeZoneToSession=true。写错时区，取出的 TIMESTAMP 会整体偏移几小时。
字符集useUnicode=true&characterEncoding=utf8characterEncoding=UTF-8：8.x 默认即 UTF-8，通常可省。注意 utf8 在服务端实为 utf8mb3，存 emoji 会报 Incorrect string value；库、表、列与连接字符集要一起改成 utf8mb4。

批量写入rewriteBatchedStatements=true（一直有效）仍然推荐。不开这个参数时 addBatch() 只是循环发送单条 SQL，打开后驱动才会合并成多值 INSERT，批量插入的提速非常明显。

二、事务：把多条 SQL 绑成一个原子操作

转账是最经典的例子：A 扣 100、B 加 100，如果扣款成功而加款失败，钱就凭空消失了。事务就是把这两条 update 包成一个不可分割的工作单元，要么都生效，要么都撤销。数据库事务必须满足 ACID，四项缺一不可：

  • 原子性（Atomicity）：操作全做或全不做；
  • 一致性（Consistency）：事务前后数据都满足业务约束；
  • 隔离性（Isolation）：并发事务互不干扰；
  • 持久性（Durability）：提交后的改动不会因故障丢失。

JDBC 默认是“自动提交”：每条 SQL 执行完立刻提交。手动控制事务只需三步——setAutoCommit(false) 开启，成功后 commit()，异常时 rollback()。要注意三点。一是 setAutoCommit(false) 之后执行的语句并不会自动落库，忘记 commit() 就等于没执行。二是回滚必须放在 catch 中，且 rollback() 自身也可能抛异常。三是事务边界必须落在同一个 Connection 上，这也是后面讲连接池时要格外小心的原因。

public void transfer(String from, String to, double money) {
    String out = "update account set money = money - ? where name = ?";
    String in  = "update account set money = money + ? where name = ?";
    Connection conn = null;
    try {
        conn = DriverManager.getConnection(URL, "root", "root");
        conn.setAutoCommit(false);          // 1. 开启事务
        try (PreparedStatement ps1 = conn.prepareStatement(out);
             PreparedStatement ps2 = conn.prepareStatement(in)) {
            ps1.setDouble(1, money);
            ps1.setString(2, from);
            ps1.executeUpdate();

            ps2.setDouble(1, money);
            ps2.setString(2, to);
            ps2.executeUpdate();
        }
        conn.commit();                       // 2. 全部成功才提交
    } catch (SQLException e) {
        if (conn != null) {
            try {
                conn.rollback();             // 3. 任一步失败则整体撤销
            } catch (SQLException ignored) {
                // 回滚失败同样要记录日志
            }
        }
        throw new RuntimeException("转账失败", e);
    } finally {
        if (conn != null) {
            try {
                conn.close();
            } catch (SQLException ignored) {
            }
        }
    }
}

事务的提交为什么能扛住断电？关键在于数据库是先写日志、再改数据文件：执行事务时先把重做（redo）日志落盘，真正改数据页则可以延后。崩溃重启后，数据库根据日志做 undo（撤销未提交的事务）或 redo（重放已提交的事务），从而把数据恢复到一致状态。这也是“日志文件往往比数据文件还大”的原因。另外，Oracle 默认不自动提交、MySQL 默认自动提交，所以迁移数据库时事务代码要重新确认一遍行为。

并发会带来三类问题。脏读读到了别的事务未提交的数据。不可重复读指同一个事务里两次读同一行结果不同，因为别人 update 并提交了。幻读指两次范围查询的记录条数不同，因为别人 insert 或 delete 并提交了。SQL 标准用四个隔离级别来权衡：read uncommitted、read committed、repeatable read、serializable，级别越高一致性越强、并发性能越差。默认值是重点：MySQL 默认 repeatable read，Oracle 默认 read committed。可以用 select @@transaction_isolation; 查看（MySQL 5.7.20 之前是 @@tx_isolation，该变量在 8.0 中已移除），用 set session transaction isolation level ... 修改。需要注意的是，具体行为由存储引擎实现决定，InnoDB 的 repeatable read 借助间隙锁在很大程度上也避免了幻读，所以“MySQL 可重复读挡不住幻读”这句话对 InnoDB 并不严谨。

三、连接池：为什么不能每次都 new 一个连接

建立一个数据库连接需要 TCP 握手、身份认证、初始化会话，代价远高于执行一条简单 SQL。高并发下“一次请求一个连接”，数据库会先被连接创建拖垮。连接池的思路是提前创建若干连接并缓存起来，用的时候借、用完还，把创建成本摊薄到整个运行期。它同时还能充当流量阀门：池大小固定，超出阈值的请求排队，避免把数据库压死。

自己实现一个连接池有两个关键点：用容器（如 LinkedList）保存空闲连接；由于业务代码习惯调用 conn.close()，需要返回一个代理对象，用动态代理把 close() 改写成“归还连接”，而不是真的关闭物理连接。理解了这一点，就明白为什么用第三方池时 close() 依然可以放心调用。

生产上基本不再手写，主流选择是 Druid 与 HikariCP。Druid 由阿里开源，当前主线是 1.2.x，参数丰富（initialSize、minIdle、maxActive、maxWait、testWhileIdle、filters 等）、自带监控页面，国内项目见得多。HikariCP 以轻量和低延迟著称，从 Spring Boot 2.x 起就是默认连接池（3.x 仍然如此）。其中 4.x 支持 Java 8，5.x 及以后要求 Java 11 起，Java 17 项目直接用 5.x/6.x 系列即可。以 Druid 为例，用配置文件加载：

// druid.properties
// driverClassName=com.mysql.cj.jdbc.Driver
//     （5.1.x 时代写 com.mysql.jdbc.Driver；8.x 驱动经 SPI 自动注册，这一项也可由 URL 推断）
// url=jdbc:mysql://localhost:3306/day06_db?connectionTimeZone=Asia/Shanghai&characterEncoding=UTF-8
//     （旧写法 serverTimezone=Asia/Shanghai&useUnicode=true&characterEncoding=utf8，参数名已弃用）
// username=root
// password=root
// initialSize=5       初始连接数
// minIdle=5           最小空闲连接
// maxActive=20        最大活跃连接
// maxWait=3000        获取连接的最长等待毫秒数
// filters=stat        内置监控统计，配合 /druid/index.html 查看

public class DruidUtils {
    private static final DataSource DATA_SOURCE;

    static {
        try (InputStream in = DruidUtils.class.getClassLoader()
                .getResourceAsStream("druid.properties")) {
            Properties props = new Properties();
            props.load(in);
            DATA_SOURCE = DruidDataSourceFactory.createDataSource(props);
        } catch (Exception e) {
            throw new ExceptionInInitializerError(e);
        }
    }

    public static DataSource getDataSource() {
        return DATA_SOURCE;
    }
}

换成 HikariCP 时，核心参数名不同：jdbcUrl、username、password、maximumPoolSize、minimumIdle、connectionTimeout、idleTimeout、maxLifetime，与 Druid 的对应关系是 url ↔ jdbcUrl、maxActive ↔ maximumPoolSize、minIdle ↔ minimumIdle、maxWait ↔ connectionTimeout（默认 30 秒）。配置方式从 Properties 换成 HikariConfig，或直接 new 一个 HikariDataSource；驱动类名同样可以省（5.x/6.x 对应 8.x 的 com.mysql.cj.jdbc.Driver，由 SPI 注册）。HikariCP 官方给出的经验值是把 maximumPoolSize 取成与 CPU 核数相关的小值（常见起点 10 左右），池子并不是越大越好：连接数超过数据库的处理能力后，多出来的连接只会带来线程上下文切换与锁竞争。另外 maxLifetime 应比数据库侧的 wait_timeout 略小，否则会借到已被服务端断开的“死连接”，报出 Communications link failure 这类错误（具体配合策略见第六节）。

四、连接池是怎么实现的：手写一个最小池

上一节解释了为什么要有池，这一节把它拆开实现一遍。目的不是让你在生产代码里手写池（生产上直接用 HikariCP 或 Druid，参数见上一节），而是为了看懂三件事：池容量是怎么被控制的、close() 为什么能变成归还、空闲连接是怎么被回收的。看懂这三件事，第三方池的参数表就不再是一堆名词。

4.1 三个必须解决的问题

  • 容量：同时最多借出多少个连接？超出的线程是排队、报错还是继续新建？
  • 归还：业务代码写的是 conn.close()，池必须把“关闭”翻译成“放回队列”。
  • 回收：空闲太久的连接要物理关闭，否则数据库侧的 wait_timeout 会先把它掐掉，池里留着一堆死连接。

4.2 用动态代理改写 close()

关键点是：不能把真实的 Connection 直接交给业务。真实连接一旦 close()，物理连接就没了；而业务代码（尤其是 try-with-resources 和各种框架）已经习惯“用完就 close”。所以池返回一个代理对象：它和真实连接实现同一个 Connection 接口，业务看不出区别，但每个方法调用都会先经过 InvocationHandler.invoke()。在 invoke() 里判断方法名，拦截 close 并改成“归还到队列”，其余方法原样转发给真实连接。

这正是 JDK 动态代理的典型用法：Proxy.newProxyInstance(类加载器, 接口数组, InvocationHandler) 在运行期生成一个实现指定接口的类，不必为 Connection 的几十个方法逐个写包装类。下面三段代码合起来是一个完整可编译的最小池（已在 JDK 21 上跑通：容量到顶时按超时排队抛异常、close() 后连接被复用、只有 pool.close() 才真正关闭物理连接）。先看字段、构造方法与借出逻辑：

public class SimpleConnectionPool {
    private final String url, user, password;
    private final int maxSize, minIdle;
    private final long borrowTimeoutMs, maxIdleMs;
    private final ArrayBlockingQueue<PooledConnection> idle;      // 空闲连接队列
    private final AtomicInteger total = new AtomicInteger();       // 已创建的物理连接数
    private final ScheduledExecutorService evictor;                // 空闲回收线程
    private volatile boolean closed = false;

    public SimpleConnectionPool(String url, String user, String password,
                                int maxSize, int minIdle,
                                long borrowTimeoutMs, long maxIdleMs) {
        this.url = url; this.user = user; this.password = password;
        this.maxSize = maxSize; this.minIdle = Math.min(minIdle, maxSize);
        this.borrowTimeoutMs = borrowTimeoutMs; this.maxIdleMs = maxIdleMs;
        this.idle = new ArrayBlockingQueue<>(maxSize);           // 队列容量 = 池上限
        this.evictor = Executors.newSingleThreadScheduledExecutor(r -> {
            Thread t = new Thread(r, "conn-pool-evictor");
            t.setDaemon(true);                                     // 守护线程，不挡 JVM 退出
            return t;
        });
        this.evictor.scheduleWithFixedDelay(this::evictIdle, 30, 30, TimeUnit.SECONDS);
    }

    /** 借连接：先拿空闲的，没有就新建，到上限就在队列上排队等归还。 */
    public Connection getConnection() throws SQLException {
        if (closed) throw new SQLException("连接池已关闭");
        long deadline = System.nanoTime() + TimeUnit.MILLISECONDS.toNanos(borrowTimeoutMs);
        while (true) {
            PooledConnection p = idle.poll();                      // 1. 有没有空闲的
            if (p != null) return wrap(p);
            if (total.incrementAndGet() <= maxSize) {              // 2. 没到上限就建一个
                try {
                    return wrap(new PooledConnection(
                            DriverManager.getConnection(url, user, password)));
                } catch (SQLException e) {
                    total.decrementAndGet();                       // 建失败要退还名额
                    throw e;
                }
            }
            total.decrementAndGet();                               // 名额已满，退回去排队
            long remain = deadline - System.nanoTime();
            if (remain <= 0) {
                throw new SQLException("获取连接超时（" + borrowTimeoutMs + " ms），池上限 " + maxSize);
            }
            try {
                p = idle.poll(remain, TimeUnit.NANOSECONDS);       // 3. 阻塞等待别人归还
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();                // 别吞掉中断标志
                throw new SQLException("等待连接时被中断", e);
            }
            if (p != null) return wrap(p);
        }
    }

    /** 关键一步：交给业务的是代理对象，不是真实连接。 */
    private Connection wrap(PooledConnection pooled) {
        return (Connection) Proxy.newProxyInstance(
                Connection.class.getClassLoader(),
                new Class<?>[]{Connection.class},                 // 代理要实现 Connection 全部方法
                new PooledConnectionHandler(pooled));
    }

接下来是代理的处理逻辑，也是整套实现的核心。注意 close 被拦下来做归还，released 保证幂等，而 default 分支把其余方法全部转发给 pooled.raw：

    private class PooledConnectionHandler implements InvocationHandler {
        private final PooledConnection pooled;
        private boolean released;                                  // 保证只归还一次

        PooledConnectionHandler(PooledConnection pooled) { this.pooled = pooled; }

        @Override
        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            switch (method.getName()) {
                case "close":
                    release();                                     // 魔法在这里：close() = 归还
                    return null;
                case "isClosed":
                    return released;                               // 归还后对业务来说就是“已关闭”
                case "toString":
                    return "PooledConnection[" + pooled.raw + "]";
                case "hashCode":
                    return System.identityHashCode(proxy);
                case "equals":
                    return proxy == args[0];
                default:
                    break;
            }
            if (released) throw new SQLException("连接已归还，不能继续使用");
            try {
                // 其余几十个方法（prepareStatement / createStatement / setAutoCommit / getMetaData ...）
                // 一律转发给真实连接；不转发，业务拿到的就是个空壳。
                return method.invoke(pooled.raw, args);
            } catch (InvocationTargetException e) {
                throw e.getTargetException();                      // 还原真实异常，否则 catch(SQLException) 匹配不上
            }
        }

        private void release() {
            if (released) return;                                  // 幂等：try-with-resources 可能重复 close()
            released = true;
            try {
                reset(pooled.raw);                                 // 复位事务状态，别让下一个借用者继承脏状态
            } catch (SQLException e) {
                closePhysical(pooled);                            // 连接已经坏了，别再放回池里
                return;
            }
            pooled.lastReturnedAt = System.currentTimeMillis();
            if (closed || !idle.offer(pooled)) closePhysical(pooled);
        }
    }

    /** 归还前复位：未提交的事务回滚，autoCommit 打开。 */
    private void reset(Connection raw) throws SQLException {
        if (!raw.getAutoCommit()) {
            raw.rollback();
            raw.setAutoCommit(true);
        }
    }

最后是空闲回收与关闭。closePhysical() 是全类中唯一调用 raw.close() 的地方，也是“包一层”与“真关闭”的唯一出口：

    private void closePhysical(PooledConnection pooled) {
        total.decrementAndGet();
        try { pooled.raw.close(); } catch (SQLException ignored) { }   // 真正的关闭只发生在这里
    }

    /** 空闲回收 + 探活：够久没用的物理关闭，但至少保留 minIdle 个。 */
    private void evictIdle() {
        if (closed) return;
        long now = System.currentTimeMillis();
        for (int i = 0, n = idle.size(); i < n; i++) {
            PooledConnection p = idle.poll();
            if (p == null) return;
            boolean expired = now - p.lastReturnedAt > maxIdleMs;
            if (expired && total.get() > minIdle) {
                closePhysical(p);
            } else if (!isAlive(p.raw)) {                          // 探活失败的死连接也淘汰
                closePhysical(p);
            } else {
                idle.offer(p);                                     // 还回去，下一轮再看
            }
        }
    }

    private boolean isAlive(Connection raw) {
        try {
            return raw.isValid(1);                                 // JDBC 4；老驱动可执行 validationQuery: select 1
        } catch (SQLException e) {
            return false;
        }
    }

    public int idleCount() { return idle.size(); }
    public int borrowedCount() { return total.get() - idle.size(); }

    public void close() {                                          // 池自己关闭时才批量关物理连接
        closed = true;
        evictor.shutdownNow();
        PooledConnection p;
        while ((p = idle.poll()) != null) closePhysical(p);
    }

    private static class PooledConnection {
        final Connection raw;                                      // 真实连接
        volatile long lastReturnedAt = System.currentTimeMillis();  // 上次归还时间，回收线程用
        PooledConnection(Connection raw) { this.raw = raw; }
    }
}

4.3 为什么包装后的 Connection 必须把其他方法委托给真实连接

这是动态代理部分最容易写错、也最需要理解的一点。代理对象只是一个“实现接口的空壳”，它自己不懂任何数据库逻辑，prepareStatement()、createStatement()、getMetaData() 这些方法在代理里没有任何实现。如果只拦截 close、其他方法返回 null，业务侧第一行 conn.prepareStatement(sql) 就会 NPE。所以规则是：只改写需要改写的那个方法（close），其余一律用 method.invoke(pooled.raw, args) 原样转发给真实连接。代理与真实连接是“外壳与内核”的关系，不是替代关系。

具体有五个坑：

  • 异常必须拆包。反射调用把真实方法抛出的异常包在 InvocationTargetException 里，若原样往外抛，业务写的 catch (SQLException) 永远匹配不上，只会看到一个 UndeclaredThrowableException，栈信息也难读。要 throw e.getTargetException() 把真实异常还原出来。
  • equals/hashCode/toString 也要处理。这三个是 Object 上的方法，不处理就会转发到真实连接，导致同一个代理对象放进 Set 或做 Map 的 key 时行为诡异（代理与自身比较都可能失败）。示例里用 identity 语义实现：equals 比较引用、hashCode 取 System.identityHashCode(proxy)。
  • 归还前要复位状态。业务如果开着事务就 close()（或忘了 commit()），连接回到池里时自动提交仍是关的，下一个借用者会莫名其妙地“在事务里”执行 SQL，甚至把上一个事务的修改一起提交。所以归还前 rollback() 并把 setAutoCommit(true) 设回去。真实池做得更多：还会重置只读标记、隔离级别和会话变量。
  • close() 必须幂等。try-with-resources 和框架的 finally 可能重复关闭，重复归还会让同一个对象在队列里出现两次，被两个线程同时使用。用 released 标志挡住第二次。
  • 归还后要继续拦截。连接已经还回队列、可能已被别的线程借走，此时旧引用再调用方法就会造成两个线程共用一条连接。示例里 released 为真时直接抛异常，把这种 bug 暴露在调用点，而不是让它变成难以复现的数据错乱。

4.4 容量与借出超时：ArrayBlockingQueue 的 poll(timeout)

队列 idle 装空闲连接，计数器 total 记录已创建的物理连接总数（含借出中的）。getConnection() 按顺序做三件事：先 poll() 捞一个空闲的；没有空闲且 total 未到上限就新建一条；已经到上限就在队列上 poll(remain, NANOSECONDS) 阻塞等待别人归还，累计等到 borrowTimeoutMs 仍未拿到就抛异常。这里刻意用 AtomicInteger 而不是 idle.size() 判断上限：正在创建的连接还没进队列，只按队列长度判断会让并发线程集体超额创建。

几个实现细节值得记住：

  • 等待时间要从 deadline 算剩余量，而不是每轮重新等满一个超时，否则借不到连接时会一直等下去。
  • InterruptedException 要先恢复中断标志再抛出，不要吞掉，否则线程池的取消信号会丢失。
  • 归还用非阻塞的 offer()，失败时直接物理关闭，避免归还线程被卡住，也顺手兜住了连接泄漏。

这套“队列 + 超时”的模型也可以换成 synchronized 加 wait()/notifyAll() 手写，语义一样，但 ArrayBlockingQueue 已经把这些封装好，更不容易写错。

把参数名对上第三方池，读配置就不再陌生：示例里的 maxSize 对应 Druid 的 maxActive、HikariCP 的 maximumPoolSize；borrowTimeoutMs 对应 maxWait 与 connectionTimeout；maxIdleMs 对应 minEvictableIdleTimeMillis 与 idleTimeout。区别只在于真实池用更精细的数据结构（分段锁、连接状态机）扛住了高并发。

4.5 空闲回收与探活

用一个 daemon 线程按固定间隔扫描空闲队列：空闲时间超过 maxIdleMs 且总数高于 minIdle 的连接物理关闭并让 total 减一；其余连接用 isValid()（老驱动可以退回执行 select 1）探活，失效的直接淘汰。这就是 Druid 的 timeBetweenEvictionRunsMillis 加 testWhileIdle、HikariCP 的 idleTimeout 加 keepaliveTime 在做的事。两个注意点：回收线程只处理空闲队列，绝不能去动正在被业务使用的连接；isValid 会走一次网络往返，间隔太小反而增加数据库负担，几十秒一次是常见量级。

五、C3P0 与 DBUtils：老项目的常见组合

先把现状说清楚：新项目不必采用这一节的技术。连接池用 HikariCP（Spring Boot 2.x 起是默认实现）或 Druid，数据访问层用 MyBatis、Spring 的 JdbcTemplate 或 JPA。Spring Boot 只要引入 spring-boot-starter-jdbc，HikariCP 与 JdbcTemplate 就已经就位。C3P0 与 commons-dbutils 的意义在于“接手老项目时一定会遇到”：2010 年代前后的 SSH 与早期 SSM 项目里，ComboPooledDataSource 加 QueryRunner 是极常见的组合。读懂它们是为了改得动老代码，而不是为了新项目选型。

5.1 C3P0：ComboPooledDataSource 的基本配置

C3P0 的入口是 ComboPooledDataSource（Maven 坐标 com.mchange:c3p0）。版本上长期停留在 0.9.5.x（0.9.5.5 是 2019 年前后最常用的版本），之后只有 0.10.x、0.11.x 等低频维护版本，不同版本之间参数基本兼容。配置可以纯代码写，也可以交给 c3p0-config.xml。代码方式如下：

public class C3p0Utils {
    private static final ComboPooledDataSource DS = new ComboPooledDataSource();

    static {
        try {
            DS.setDriverClass("com.mysql.cj.jdbc.Driver");   // 8.x 驱动可省，由 SPI 自动注册
            DS.setJdbcUrl("jdbc:mysql://localhost:3306/day06_db"
                    + "?characterEncoding=utf8&connectionTimeZone=Asia/Shanghai");
            DS.setUser("root");
            DS.setPassword("root");
            DS.setInitialPoolSize(5);        // 启动时先建几条
            DS.setMinPoolSize(5);
            DS.setMaxPoolSize(20);           // 上限，相当于 Druid 的 maxActive
            DS.setAcquireIncrement(5);       // 不够用时一次补几条
            DS.setCheckoutTimeout(3000);     // 借出等待上限，毫秒，相当于 maxWait
            DS.setMaxIdleTime(1800);         // 空闲多久后回收，单位是【秒】，注意不是毫秒
            DS.setIdleConnectionTestPeriod(60);       // 每 60 秒探活一次，单位是【秒】
            DS.setPreferredTestQuery("select 1");     // 探活语句，必须配
        } catch (PropertyVetoException e) {
            throw new ExceptionInInitializerError(e);
        }
    }

    public static DataSource getDataSource() {
        return DS;
    }
}

参数与上一节的池、以及 Druid/HikariCP 一一对得上：maxPoolSize 对 maxActive 与 maximumPoolSize，checkoutTimeout 对 maxWait 与 connectionTimeout，maxIdleTime 对 minEvictableIdleTimeMillis 与 idleTimeout，preferredTestQuery 对 validationQuery 与 connectionTestQuery。最容易踩的坑是单位：C3P0 的 maxIdleTime、idleConnectionTestPeriod 按秒，checkoutTimeout 按毫秒，写错一个数量级就会出现“连接怎么都不回收”或“一借就超时”。

配置文件方式更常见，文件必须叫 c3p0-config.xml 并放在 classpath 根目录：

<c3p0-config>
  <default-config>
    <property name="driverClass">com.mysql.cj.jdbc.Driver</property>
    <property name="jdbcUrl">jdbc:mysql://localhost:3306/day06_db</property>
    <property name="user">root</property>
    <property name="password">root</property>
    <property name="initialPoolSize">5</property>
    <property name="minPoolSize">5</property>
    <property name="maxPoolSize">20</property>
    <property name="checkoutTimeout">3000</property>
    <property name="maxIdleTime">1800</property>
    <property name="preferredTestQuery">select 1</property>
  </default-config>
</c3p0-config>

XML 里可以写多个命名配置（<named-config name="mysql"> 这种形式），再用 new ComboPooledDataSource("mysql") 按名字加载，多数据源场景靠的就是它；不写名字则使用 default-config。

5.2 commons-dbutils：QueryRunner 与 ResultSetHandler

DBUtils 解决的是 JDBC 样板代码：拿连接、建 Statement、遍历 ResultSet、在 finally 里关三个对象、再把结果映射成 Java 对象。它把流程拆成两个角色：QueryRunner 负责连接与资源关闭（内部就是 DataSource.getConnection() 用完 close()，所以它天然和连接池配合，而池的代理保证了这里的 close() 是归还），ResultSetHandler 负责把结果集变成对象。版本上常用 1.7（坐标 commons-dbutils:commons-dbutils:1.7，2017 年发布后基本没再更新），API 从 1.6 起没有大变化。

四个最常用的 Handler 是：BeanHandler<T> 把单行结果变成一个 JavaBean（列名要与属性名对得上）；BeanListHandler<T> 把多行结果变成 List<T>；ScalarHandler<T> 只取单行单列，适合 count(*)、max(id) 这类聚合；MapListHandler 把多行结果变成 List<Map<String,Object>>，列名做 key，适合列不固定的报表查询。此外还有 MapHandler（单行 Map）、ArrayHandler（单行数组）、KeyedHandler（按某列做成 Map），用法同构，需要时查一眼即可。

// QueryRunner 是无状态的，可以做成单例复用
QueryRunner runner = new QueryRunner(C3p0Utils.getDataSource());

// 1. 单行 → 对象：BeanHandler，列名要能对上属性名
Account one = runner.query("select id, name, money from account where id = ?",
        new BeanHandler<>(Account.class), 1L);

// 2. 多行 → List：BeanListHandler
List<Account> list = runner.query("select id, name, money from account where money > ?",
        new BeanListHandler<>(Account.class), 1000);

// 3. 单值（count / max / sum）：ScalarHandler
Long count = runner.query("select count(*) from account", new ScalarHandler<Long>());

// 4. 多行 → List<Map>：MapListHandler，列名做 key
List<Map<String, Object>> rows = runner.query(
        "select id, name, money from account", new MapListHandler());

// 增删改用 update，返回影响行数；同样的写法支持 batch(...) 批处理
int updated = runner.update("update account set money = money + ? where id = ?", 100, 1L);

用法上有三点要注意。第一是参数顺序：query(sql, handler, params...)，Handler 排在参数前面，写反了编译期就能发现。第二是 BeanHandler 靠反射按列名匹配属性，数据库的 snake_case 列名对不上 Java 的驼峰属性（create_time 对不上 createTime），需要传一个配置了 GenerousBeanProcessor 或自定义 RowProcessor 的构造器；这一点也是后来 MyBatis 的 mapUnderscoreToCamelCase 更省事的原因。第三是别混用：QueryRunner 只传 DataSource 时由它自己管理连接，如果同时又手工 getConnection() 再 runner.query(conn, ...)，很容易出现连接双重关闭或事务落在两条连接上的问题（事务与池的配合见第六节）。

5.3 迁移到现代栈时的对应关系

接手老项目后如果要替换，最省事的路径是“先补测试、再逐个 API 平移”，而不是推倒重写。常见对应关系如下。

老写法（C3P0 / DBUtils）现代对应写法

checkoutTimeout / maxPoolSize / maxIdleTime / preferredTestQueryconnectionTimeout / maximumPoolSize / idleTimeout / connectionTestQuery

new BeanHandler<>(Account.class)BeanPropertyRowMapper.newInstance(Account.class)，或 MyBatis 的 resultType

new ScalarHandler<Long>()jdbcTemplate.queryForObject(sql, Long.class)

还有一个现实约束：C3P0 在高并发下的表现明显不如 HikariCP，等待队列与探活策略都更粗糙。所以“只换连接池实现”通常是老项目里性价比最高、风险最低的一步改造。而替换 DBUtils 会动到每个 DAO 方法，建议配合集成测试分批推进。注意两者的收益是独立的：只换池不换 DAO 层，也能立刻拿到更好的并发表现与更清晰的监控指标。

六、常见坑与落地建议

第一，事务与连接池配合失误。最典型的写法是 Service 层开了事务，DAO 层却各自从池里取新连接，结果两条 SQL 落在两个连接上，回滚只回滚了其中一条。解决办法是让 Service 统一获取连接并透传给 DAO；若不想改方法签名，可用 ThreadLocal 把连接绑定到当前线程，由同一个工具类提供取连接与释放连接的方法。但必须成对释放，否则线程复用时会拿到脏连接。

第二，不归还连接。异常路径上漏掉 close()，池里的连接会被逐渐耗尽，表现是请求卡在获取连接处直至超时。统一用 try-with-resources 或 finally 释放，且把 Connection、Statement、ResultSet 都关掉。

第三，在事务里做长耗时操作。事务持有行锁期间若去做远程调用或大批量计算，会显著放大锁等待。原则是让事务尽量短：先做参数校验和远程调用，再开事务写库。

第四，批处理写法。循环逐条 executeUpdate() 意味着 N 次网络往返，改成 addBatch() 累积、executeBatch() 一次提交，并配合 setAutoCommit(false) 与 rewriteBatchedStatements=true（MySQL）可成倍提速。注意批处理量大时要分段提交，避免一次性撑爆内存。

第五，池参数与数据库超时不对齐。maxLifetime（HikariCP 默认 30 分钟）要明显小于服务端的 wait_timeout：MySQL 8.0/8.4 默认是 28800 秒（8 小时），一般够用。但云数据库常把它调到 100～300 秒，这时必须同步调小 maxLifetime（例如取 wait_timeout 的 50%～80%）。否则连接在池里“看起来还活着”，一借出去就报 Communications link failure。Druid 侧对应的是 testWhileIdle 加 validationQuery=SELECT 1，再配 timeBetweenEvictionRunsMillis 定期探活；HikariCP 侧可以打开 keepaliveTime，再用 leakDetectionThreshold（例如 10000 毫秒）把忘记归还连接的代码位置打印出来。

小结

本章的主线是“安全执行 → 原子提交 → 高效复用”。用 PreparedStatement 参数化，杜绝 SQL 注入；用 setAutoCommit(false) 加 commit()/rollback() 把多条 SQL 绑成事务，并记住 MySQL 默认 repeatable read、Oracle 默认 read committed；用 Druid 或 HikariCP 复用连接，注意池大小的经验取值和 maxLifetime 与数据库超时的配合。至于跨服务、跨库的分布式事务，本质是把“一个本地事务”扩展成“多个本地事务加一套补偿或协调机制”，需要先理解 2PC/XA、TCC、本地消息表这些方案在一致性与可用性之间的取舍，本章不展开，留到分布式章节。
