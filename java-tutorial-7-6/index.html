Java 教程

Docker 基础

Posted on 2026-09-19，6 min read

把 Java 应用交给运维部署时，最常听到的一句话是"在我机器上是好的"：同一份 jar 包，到测试机上却因为 JDK 版本、时区、系统库不同而报错。Docker 要解决的就是这件事——把应用和它依赖的运行时、配置一起打包成不可变镜像，在任何装了 Docker 的机器上以一致方式启动。本章面向会写 Java、但没系统用过 Docker 的读者，讲清镜像与容器的关系、常用命令、Dockerfile 怎么写，以及数据卷和网络这两个绕不开的问题。

一、镜像与容器：一次构建，到处运行

传统虚拟化在硬件层模拟出一台完整机器，每台虚拟机都装一个完整内核，启动动辄几十秒。容器在操作系统层隔离：共用宿主机内核，只隔离进程空间、文件系统和网络，启动常在 1 秒以内。代价是容器内的程序必须和宿主机内核兼容——Linux 容器跑不了 Windows 程序。

理解 Docker 的关键是分清两个词。镜像是一堆只读层的叠加，通过联合文件系统（现在默认 overlay2 驱动）挂载成统一的文件系统视角，你只看到一个完整根目录，看不到底下的分层。容器则在镜像最上面再叠一个可写层：容器 = 镜像 + 读写层。这个定义没说容器一定要运行——docker create 后容器就存在，只是进程没启动；docker start 才为它创建独立进程空间并跑起进程。由此能解释几个易混命令：

  • docker run 相当于 docker create + docker start；
  • docker ps 只列运行中的，docker ps -a 才列全部（含已退出）；
  • docker commit 把容器可写层固化成只读层，即把容器"拍"成镜像，调试方便但正式交付该用 Dockerfile 重建；
  • docker rm 删容器连同可写层（仅非运行态可删），docker rmi 删镜像只读层。

镜像和容器都存在宿主机 /var/lib/docker 下，容器写入的文件落在可写层，容器一删数据就没了——这正是后面要讲数据卷的原因。

二、上手：安装、加速与常用命令

官方建议在 Ubuntu 上安装，生产上 CentOS 7 及以上也很常见。装完第一件事是配镜像加速，否则从 Docker Hub 拉镜像极慢：

# 安装依赖与 Docker CE
sudo yum install -y yum-utils device-mapper-persistent-data lvm2
sudo yum-config-manager --add-repo https://mirrors.aliyun.com/docker-ce/linux/centos/docker-ce.repo
sudo yum install -y docker-ce

# 配置镜像加速器（/etc/docker/daemon.json）
# { "registry-mirrors": ["https://docker.mirrors.ustc.edu.cn"] }

sudo systemctl enable --now docker   # 开机自启并立即启动
docker info                          # 确认 Registry Mirrors 已生效
docker -v

日常命令按"镜像 → 容器"两条线记：

docker search mysql          # 搜索镜像
docker pull mysql:8.0        # 拉取，尽量指定具体 tag
docker images                # 查看本地镜像
docker rmi 镜像ID             # 删除镜像

docker run -d --name app -p 8080:8080 -e TZ=Asia/Shanghai myapp:1.0
docker ps                    # 只看运行中的
docker logs -f app           # 跟踪日志
docker exec -it app /bin/bash   # 进入运行中的容器
docker stop app && docker rm app

两个参数必须记牢：-e 传环境变量，如 MySQL 的 MYSQL_ROOT_PASSWORD；docker exec 往运行中的容器再起一个进程，退出它不影响容器，而 docker attach 接到主进程上，退出可能把容器一起带走，排查问题优先用 exec。另外 -p 是宿主机端口:容器端口，写反是新手最高频的失误。

三、Dockerfile：把构建过程写成代码

Dockerfile 描述"如何从基础镜像构建新镜像"，每条指令生成一层，指令越少层越薄，镜像越小。常用指令：FROM 指定基础镜像且必须是第一条；RUN 在构建时执行命令；COPY/ADD 把宿主机文件复制进镜像，优先用 COPY，ADD 额外支持解压本地压缩包和从 URL 下载，除非确实要解压否则别用；WORKDIR 设工作目录并对其后的 RUN、CMD、COPY 生效；ENV 设环境变量，构建期与运行期都可见，ARG 只在构建期有效；EXPOSE 只是声明端口，对外映射仍靠 -p；CMD 与 ENTRYPOINT 都只取最后一条，区别是前者会被 docker run 后跟的命令覆盖而后者不会，常见组合是 ENTRYPOINT 写可执行程序、CMD 写默认参数。

下面是 Java 应用的典型 Dockerfile，用多阶段构建分开编译与运行环境，最终镜像不含 Maven 和源码：

# ---------- 构建阶段 ----------
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /build
# 先只复制 pom，利用层缓存，避免改代码就重新下载依赖
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B clean package -DskipTests

# ---------- 运行阶段 ----------
FROM eclipse-temurin:17-jre
WORKDIR /app
ENV TZ=Asia/Shanghai JAVA_OPTS="-Xms256m -Xmx512m"
COPY --from=builder /build/target/app.jar /app/app.jar
EXPOSE 8080
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar /app/app.jar"]
docker build -t myapp:1.0 .
docker run -d --name app -p 8080:8080 -e JAVA_OPTS="-Xmx1g" myapp:1.0

末尾那个点表示"以当前目录为构建上下文"，省略或写错都会报错。上下文里别放 target/、.git/ 这类大目录，用 .dockerignore 排除，否则每次构建都要打包上传给守护进程。

四、数据卷与网络：让数据活下来，让容器能互通

容器删了数据就没，但数据库、日志、上传的文件必须留下来，这时用数据卷：

# 绑定挂载：直接映射宿主机目录，适合开发时共享代码/配置
docker run -d --name mynginx -p 80:80 -v /usr/local/myhtml:/usr/share/nginx/html nginx

# 命名卷：由 Docker 管理，落在 /var/lib/docker/volumes 下，生产首选
docker run -d --name mysql -p 3306:3306 -e MYSQL_ROOT_PASSWORD=123456 \
  -v mysql-data:/var/lib/mysql mysql:8.0

# 匿名卷：只声明容器内路径，名字随机，不方便复用
docker run -d --name redis -v /data redis

用 -v 有两点要当心。一是 CentOS 7 的 SELinux 会让挂载目录权限不足，可加 --privileged=true，更规范的是给宿主机目录加 :z/:Z 标签。二是把宿主机目录挂到镜像里本有内容的路径（如 nginx 的 html 目录），宿主机内容会整体遮住容器内该目录，镜像里的默认文件看不到，这是正常行为不是 bug。

网络上，Docker 默认给容器分配 bridge 网络的独立 IP，容器间可用 IP 通信但 IP 会变。推荐自建 bridge 网络，同网络容器可直接用容器名互访，这也是 docker-compose 与服务发现的基础：

docker network create app-net
docker run -d --name mysql --network app-net -e MYSQL_ROOT_PASSWORD=123456 mysql:8.0
docker run -d --name app --network app-net -p 8080:8080 myapp:1.0
# 此时 app 里用 jdbc:mysql://mysql:3306/... 就能连上，无需知道 IP
docker network inspect app-net   # 查看网络内的容器与 IP

五、常见坑与最佳实践

  • 容器一退出就没了：容器生命周期绑定在主进程（PID 1）上，主进程结束容器就停。用 -d 让主进程常驻，别让它是个执行完就退出的脚本。
  • 信号传不到 Java 进程：CMD java -jar app.jar 这种 shell 写法会让 /bin/sh 成为 PID 1，docker stop 发来的 SIGTERM 不会转发给 Java，只能等超时被强杀。改用 exec 形式 CMD ["java","-jar","app.jar"]，并确保 Java 侧真的处理了 SIGTERM。
  • 镜像越滚越大：合并 RUN 并清理包管理缓存；多阶段构建只留运行期文件；基础镜像选 -jre、-slim 甚至 alpine（alpine 用 musl libc，个别依赖 glibc 的组件不兼容）。
  • 用 latest 标签：latest 随上游漂移，同一份 Dockerfile 今天明天构建结果可能不同，生产一律锁明确版本。
  • 构建缓存蒙人：改了代码却没变化，先怀疑缓存；依赖安装与源码复制分两步 COPY，必要时加 --no-cache。
  • 把密码写进 Dockerfile：ENV、ARG 都会留在镜像历史里，docker history 一看便知，密钥应在运行时用 -e、挂载配置或 secrets 注入。
  • 一个容器塞多个服务：一容器一主进程，数据库与 Web 应用分容器并用网络互联，才好独立扩缩容。

六、小结

Docker 用"只读层叠加 + 一层可写层"的模型把应用与依赖打包成可移植镜像，从而消除环境差异。记住三条主线：镜像是模板、容器是它的运行实例，删容器连带删掉可写层数据；docker run = create + start，-p 宿主机端口在前、-e 传环境变量；持久化用命名卷或 -v，容器互通自建 bridge 网络并用容器名寻址。构建侧回到 Dockerfile：指令即分层，多阶段构建能显著瘦身，CMD 用 exec 形式才能正确接收停机信号。理顺这些后，下一章接着看私有仓库与持续集成，把"构建—推送—部署"串成自动流水线。
