Servlet、JSP 与 MVC

Posted on 2026-09-19，9 min read

在 Spring Boot 里写一个 @RestController，请求就自动落到方法上了；很多人用了几年也没想明白「请求到底是谁接的、放在哪儿、页面上的数据从哪来」。这一章就把这层魔法拆开：先讲 Servlet 这个最底层的 HTTP 入口，再讲转发与重定向的区别、会话与作用域、JSP 与 EL 的取值规则，最后用 MVC 把 Servlet + JSP 组装成一个像样的分层结构——你会发现 Spring MVC 的 DispatcherServlet 只是把这套手工流程做成了框架。适合已经会写 Java SE、能看懂 XML 与 HTTP 基础的读者。

Servlet：HTTP 请求的 Java 入口

浏览器只会说 HTTP，看不懂 Java 对象。Servlet 就是 Servlet 容器（Tomcat、Jetty 等）与你的 Java 代码之间的契约：容器负责解析 HTTP 报文、为每个请求开线程，然后把封装好的 HttpServletRequest、HttpServletResponse 交给你的代码，你只管写业务逻辑并决定输出什么。

一个 Servlet 的完整生命周期只有三个阶段，全部由容器调度，你无法手工 new 出来用：

生命周期：init / service / destroy

容器启动时（或第一次收到请求时）创建唯一的 Servlet 实例并调用 init()；此后每个请求对应一个线程调用一次 service()；应用卸载或容器关闭时调用 destroy()。三个方法在 Servlet 接口中定义，但实际开发几乎不直接实现接口，而是继承 HttpServlet——它已经把 service() 写好，按请求方法分派到 doGet、doPost 等方法。

package com.example.web;

import javax.servlet.ServletException;
import javax.servlet.annotation.WebServlet;
import javax.servlet.http.HttpServlet;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.io.PrintWriter;

// Servlet 3.0 起可用注解注册；等价于 web.xml 中的  + 
@WebServlet(name = "hello", urlPatterns = "/hello", loadOnStartup = 1)
public class HelloServlet extends HttpServlet {

    @Override
    public void init() throws ServletException {
        // 只执行一次：适合读取配置、初始化连接池
        System.out.println("init 一次，实例被容器长期持有");
    }

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        doPost(req, resp);   // GET/POST 逻辑一致时互相调用，避免重复代码
    }

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        // 输出中文必须先设置编码，且要在 getWriter() 之前
        resp.setContentType("text/html;charset=UTF-8");
        String name = req.getParameter("name");
        try (PrintWriter out = resp.getWriter()) {
            out.println("<h1>hello, " + (name == null ? "guest" : name) + "</h1>");
        }
    }

    @Override
    public void destroy() {
        // 只执行一次：释放 init 中申请的资源
    }
}

关键点：Servlet 在容器中通常只有一个实例，但会被多个线程并发调用。所以不要在 Servlet 里定义可变的成员变量来存请求数据——那份数据属于所有用户。要保存请求数据，要么放进方法内的局部变量，要么放进 request 域。这是初学者最容易写出「A 用户看到 B 用户数据」的地方。

若用 web.xml 注册（Servlet 3.0 之前的唯一方式，或需要集中管理映射时），等价配置是：

<servlet>
  <servlet-name>hello</servlet-name>
  <servlet-class>com.example.web.HelloServlet</servlet-class>
  <!-- 值越小启动越早；写了它就等于容器启动时创建实例并调用 init() -->
  <load-on-startup>1</load-on-startup>
</servlet>
<servlet-mapping>
  <servlet-name>hello</servlet-name>
  <!-- 一个 Servlet 可映射多个 URL；通配符只有 "*.扩展名" 和 "/路径/*" 两种形式 -->
  <url-pattern>/hello</url-pattern>
</servlet-mapping>

转发还是重定向：一次请求与两次请求

Servlet 处理完数据后通常要把用户带到另一个页面。这里有两个看起来差不多、语义却完全不同的 API。

请求转发（forward）发生在服务器内部：当前 Servlet 把同一个 request 对象交给另一个资源继续处理，浏览器只发了一条请求，地址栏不会变。

// 转发：以 "/" 开头时，路径相对当前 Web 应用根目录
req.setAttribute("msg", "登录成功");
req.getRequestDispatcher("/WEB-INF/views/home.jsp").forward(req, resp);
return;   // 转发后必须结束当前方法，避免响应被二次提交

请求重定向（redirect）是服务器告诉浏览器再去访问另一个地址：响应状态码 302，Location 头里是目标 URL，浏览器发起第二条请求。

// 重定向：以 "/" 开头时，路径相对整个站点的根目录，所以务必拼上项目路径
resp.sendRedirect(req.getContextPath() + "/login");
return;

两条规则决定了选哪个：需要保留 request 域里的数据、想让地址栏停在当前 URL，就用转发；想让地址栏变成新地址、避免用户刷新导致表单重复提交，就用重定向。业界常说的 PRG（Post-Redirect-Get）模式，就是在表单提交成功后重定向到结果页，刷新时浏览器只会重新 GET 结果页，不会把订单再提交一遍。

还有几个容易记混的细节：转发只能回到同一个 Web 应用内的资源，重定向可以跳到别的应用甚至别的站点（绝对 URL）；转发是容器内部调用，重定向多一次网络往返，性能略差但语义更干净；转发不能修改响应状态码之后再转，一旦响应已经提交（response.isCommitted() 为真）两者都会抛 IllegalStateException。

会话与作用域：数据放在哪儿

转发能共享 request 域，但重定向之后就丢了——因为那是两个 request 对象。HTTP 本身无状态，要跨请求记住「这个人已登录」，必须靠 Session。

机制很朴素：第一次调用 req.getSession() 时，容器创建一个 HttpSession 并生成唯一 ID，通过 Set-Cookie: JSESSIONID=... 写给浏览器；此后浏览器每次请求都带上这个 Cookie，容器据此找到对应的 Session 对象。

// 登录成功后把用户放进会话
HttpSession session = req.getSession();          // 不存在则创建
User user = userService.login(username, password);
if (user != null) {
    session.setAttribute("loginUser", user);     // 值必须是可序列化的对象
    resp.sendRedirect(req.getContextPath() + "/index");
} else {
    req.setAttribute("msg", "用户名或密码错误");
    req.getRequestDispatcher("/login.jsp").forward(req, resp);  // 转发才能把 msg 带过去
}

// 注销：销毁会话
req.getSession().invalidate();

Java Web 里一共有四个数据作用域，从小到大是 page（仅当前 JSP）、request（一次请求，可跨转发）、session（一个用户会话）、application（整个 Web 应用，即 ServletContext）。四者的读写方法完全一样（setAttribute / getAttribute / removeAttribute），区别只在存活时间与可见范围。选作用域的原则是「范围尽可能小」：能放 request 就不要放 session，否则服务器内存会随在线用户数一起涨。

JSP 与 EL：视图层的取值方式

JSP 本质上是「写起来像 HTML 的 Servlet」——容器会把 .jsp 文件翻译成 Servlet 源码再编译成 class（Tomcat 放在 work 目录，可自行查看）。这解释了 JSP 的两个特点：第一次访问慢（要翻译编译），以及页面里天然可用 request、session、application、out、pageContext 等内置对象。

老教程里的 JSP 常用 <% %> 脚本片段，现在不推荐：它让页面无法被前端直接预览，也容易把业务逻辑写进视图。推荐用 EL 表达式取值，用 JSTL 标签做循环和判断。

<%@ page contentType="text/html;charset=UTF-8" pageEncoding="UTF-8" %>
<%@ taglib prefix="c" uri="http://java.sun.com/jsp/jstl/core" %>
<!DOCTYPE html>
<html>
<body>
  <!-- EL 取 Bean 属性：等价于 request.getAttribute("user").getName() -->
  <p>欢迎，${user.name}</p>

  <!-- 显式指定作用域，避免同名属性互相干扰（EL 默认按 page→request→session→application 顺序查找） -->
  <p>会话中的用户：${sessionScope.loginUser.name}</p>

  <!-- empty 判断 null 或空集合；三元表达式做兜底 -->
  <p>${empty user.nickname ? "匿名" : user.nickname}</p>

  <!-- JSTL 迭代，配合 EL 输出列表 -->
  <ul>
    <c:forEach items="${books}" var="book" varStatus="st">
      <li>${st.count}. ${book.title} —— ${book.price}</li>
    </c:forEach>
  </ul>
</body>
</html>

EL 有三个必须记住的行为。第一，${x} 的求值过程相当于 pageContext.findAttribute("x")，会依次在四个作用域中查找，命中即返回；找不到时返回空字符串而不是 null，所以页面上不会出现「null」字样，但也因此很难察觉变量名写错。第二，${user.name} 实际调用的是 getName()，所以实体类必须有符合 JavaBean 规范的 getter。第三，EL 的算术、比较、逻辑运算符和 empty、三元表达式都可用，但页面里只做展示与简单判断，真正的业务逻辑应该留在 Java 层。

安全提醒：会话 ID 依赖 Cookie，一旦被窃取就等于账号被盗用。生产环境应给会话 Cookie 加 HttpOnly、Secure，登录成功后调用 req.changeSessionId() 更换会话 ID 以防会话固定攻击，并把 web.xml 的 <session-timeout> 设置为一个合理值。

MVC 分层：把 Servlet 和 JSP 组装起来

早期 JSP 里代码、SQL、HTML 混在一起（所谓 Model 1），改一个字段要翻三个地方。Servlet/JSP 规范 0.92 版给出了 Model 2 架构，也就是今天说的 MVC：

Model 模型承担业务与数据（JavaBean、Service、DAO）；View 视图只负责展示（JSP、HTML）；Controller 控制器接收请求、调用模型、选择视图（Servlet）。这样 HTML 工程师改外观时不必碰后端逻辑，Java 工程师改逻辑时也不必担心页面。

// 一个典型的 Controller Servlet：只做「取参数 → 调 Service → 选视图」三件事
@WebServlet("/book/*")
public class BookServlet extends HttpServlet {

    private final BookService service = new BookServiceImpl();   // 无状态，可安全复用

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        String action = req.getPathInfo() == null ? "/list" : req.getPathInfo();
        if ("/list".equals(action)) {
            req.setAttribute("books", service.findAll());
            // 页面放在 /WEB-INF/views 下，浏览器无法直接访问，必须经 Controller 转发
            req.getRequestDispatcher("/WEB-INF/views/book-list.jsp").forward(req, resp);
        } else {
            resp.sendError(HttpServletResponse.SC_NOT_FOUND);
        }
    }
}

这套结构一旦手写多了，就会发现每个 Servlet 都在重复同样的动作：解析 URL、找方法、准备数据、选视图。Spring MVC 做的事正是把这套流程抽象出来——它注册的唯一一个 Servlet（DispatcherServlet，映射到 /）充当前端控制器：请求先到它，它问 HandlerMapping「这个 URL 归谁管」，再通过 HandlerAdapter 调用你写的 @Controller 方法，拿到 ModelAndView 后交给 ViewResolver 解析成真正的视图并渲染。你写的 @RequestMapping 方法，本质上就是过去那些 doGet 里的分支。

理解了这一层，就理解了两件事：为什么 Spring Boot 3 / Jakarta EE 9 之后包名从 javax.servlet 变成了 jakarta.servlet——因为 Servlet 这个接口被捐给了 Eclipse 基金会并改名，写代码时用错包名会直接编译失败；以及为什么 /WEB-INF 下的 JSP 必须转发才能访问——那是容器的安全约定，不是框架的限制。

小结

本章的主线只有一条：请求从容器进入 Servlet，就近放在合适的域里，再由视图读取渲染。Servlet 由容器调度，一生只有一次 init 和一次 destroy，但 service 会被多线程并发调用，因此实例不能存请求数据；转发是服务器内部的一次请求（request 域有效、地址栏不变），重定向是让浏览器再发一次请求（地址栏改变、可跨应用，适合 PRG 防重复提交）；跨越重定向的数据要放 Session，四个作用域按「够用就好」的原则从 page 往 application 选；JSP 用 EL 与 JSTL 取值、避免脚本片段，${x} 会按四个域顺序查找且取不到时返回空串。最后，MVC 把这些零散的规则固化成「模型 / 视图 / 控制器」的分工，而 Spring MVC 的 DispatcherServlet 只是把这套手工流程标准化了。下一章我们进入 Spring 的 IoC 与 AOP，看它如何接管对象的创建与装配。
