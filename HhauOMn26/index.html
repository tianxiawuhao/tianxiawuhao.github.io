k8s资源操作

Posted on 2022-06-04，16 min read

0.概览：资源对象与操作路径

kubectl 的所有操作都可以归结为三件事：描述期望状态（YAML/命令）→ 提交给 API Server → 控制器把实际状态逼近期望状态。下图把常用资源对象、常见操作入口和排障路径放在一张图里，后文按这张图的顺序展开。

1.资源类型

资源分类 类型 具体资源
名称空间级别 工作负载型资源 Pod(pod:k8s 系统中可以创建和管理的最小单元)
名称空间级别 工作负载型资源 ReplicaSet(rs:用来确保容器应用的副本数始终保持在用户定义的副本数)
名称空间级别 工作负载型资源 Deployment(deploy:为 Pod 和 ReplicaSet 提供声明式定义，支持滚动更新与回滚)
名称空间级别 工作负载型资源 StatefulSet(sts:为了解决有状态服务的问题)
名称空间级别 工作负载型资源 DaemonSet(ds:保证每个（或指定）节点上都运行一个 Pod，如日志采集、网络插件)
名称空间级别 工作负载型资源 Job(job:负责批处理任务，即仅执行一次的任务，保证一个或多个 Pod 成功结束)

3.1 元数据查询与输出格式

kubectl version -o yaml            # 客户端与服务端版本（v1.24 起不再显示 --short 之外的旧格式）
kubectl api-resources              # 所有资源类型、短名称、是否需要命名空间
kubectl api-versions               # 集群支持的所有 apiVersion 分组，写 YAML 前先查
kubectl cluster-info dump          # 导出集群信息，用于离线分析
kubectl get --raw /readyz?verbose  # 探活各组件（1.19 起 /healthz 细化为 /livez /readyz）
kubectl get componentstatuses      # 组件状态；1.19 起该接口被标记弃用，优先用上面的 /readyz
kubectl get pod -o wide            # 附加信息：IP、节点、镜像等
kubectl get pod -o yaml            # 完整对象定义（也可用 -o json）
kubectl get pod myapp-pod -o jsonpath='{.status.podIP}'          # 只取某个字段
kubectl get pod -A --no-headers | wc -l                          # 统计 Pod 数量
kubectl get pod -w                 # 持续观察变化（watch）
kubectl explain svc.spec.ports --recursive                        # 查字段结构，写 YAML 的利器
kubectl completion bash > /etc/bash_completion.d/kubectl          # 补全，能少打很多错命令
kubectl -v=6 get pod               # 打开详细日志，排查 kubectl 本身的问题

小技巧：任何 get 都可以用 --custom-columns 定制表格，例如 kubectl get pod -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName,IP:.status.podIP；对象太长时用 kubectl get pod myapp-pod -o yaml --show-managed-fields=false 去掉 managedFields，可读性更好。

4.进入pod启动的容器

命令名 作用
kubectl exec -it podName -n nsName /bin/sh 进入容器
kubectl exec -it podName -n nsName /bin/bash 进入容器

4.1 命令写法要点

kubectl exec -it myapp-pod -n default -- /bin/sh      # 推荐：容器无 bash 时用 sh，-- 用于分隔 kubectl 参数与容器内命令
kubectl exec -it myapp-pod -n default -- /bin/bash    # 容器内有 bash 时才能用
kubectl exec -it myapp-pod -n default -c sidecar -- sh   # 多容器 Pod 必须指定 -c 容器名
kubectl exec myapp-pod -- env                         # 不进容器也能看环境变量
kubectl exec myapp-pod -- ls /etc/config              # 一次性执行命令并看输出

-it 是 --stdin --tty 的缩写，只在交互式排查时需要；写脚本或做探活时不要加，否则会因为没有 TTY 而报错。生产环境的基础镜像（如 distroless）常常没有 shell，此时可用 kubectl debug 挂一个临时容器进去排查：kubectl debug -it myapp-pod --image=busybox:1.36 --target=myapp。

6.核心资源对象与 YAML 骨架

下面给出工作中最常用的几个对象的 YAML 骨架。所有对象都以 apiVersion/kind/metadata/spec 四段式为骨架，字段名大小写敏感，不能用 Tab 缩进，同一层级缩进必须对齐。

6.1 命名空间

apiVersion: v1
kind: Namespace
metadata:
  name: dev
  labels:
    env: dev

kubectl create namespace dev          # 等价于上面用 YAML 声明式创建
kubectl config set-context --current --namespace=dev   # 把当前上下文默认命名空间切到 dev
kubectl config view --minify --output 'jsonpath={..namespace}'  # 查看当前默认命名空间

6.2 Pod

apiVersion: v1                       # Pod 属于核心组，apiVersion 就是 v1
kind: Pod
metadata:
  name: myapp-pod
  namespace: default                 # 省略则落到 default
  labels:
    app: myapp
    env: dev
spec:
  containers:
  - name: myapp
    image: registry.cn-beijing.aliyuncs.com/google_registry/myapp:v1
    imagePullPolicy: IfNotPresent    # 默认：镜像 tag 为 latest 时是 Always，否则是 IfNotPresent
    ports:
    - name: http
      containerPort: 8080
      protocol: TCP
    env:
    - name: APP_ENV
      value: "dev"
    resources:
      requests:                      # 调度依据：kube-scheduler 按 requests 找足够大的节点
        cpu: 100m
        memory: 128Mi
      limits:                        # 运行时上限：超内存会被 OOMKill，超 CPU 会被节流
        cpu: 500m
        memory: 256Mi
    readinessProbe:                  # 就绪探针：决定 Pod 是否进入 Endpoints（能否接流量）
      httpGet:
        path: /healthz
        port: http
      initialDelaySeconds: 5
      periodSeconds: 10
    livenessProbe:                   # 存活探针：失败则重启容器
      tcpSocket:
        port: 8080
      initialDelaySeconds: 15
      periodSeconds: 20
  restartPolicy: Always              # Pod 级字段，与 containers 同级

生产中很少直接创建「裸 Pod」：裸 Pod 删掉就没了，也不会自愈。业务负载一般交给 Deployment（无状态）、StatefulSet（有状态）、DaemonSet（每节点一份）或 Job/CronJob（批处理）管理。

6.3 Deployment

apiVersion: apps/v1                  # Deployment 在 apps 组，注意不是 extensions/v1beta1
kind: Deployment
metadata:
  name: myapp-deployment
  namespace: default
spec:
  replicas: 3
  revisionHistoryLimit: 10           # 保留多少个 ReplicaSet 供回滚
  selector:                          # 必填且创建后不可改，必须匹配 template 的 labels
    matchLabels:
      app: myapp
  strategy:
    type: RollingUpdate              # 另一种是 Recreate（先全删再建，会中断服务）
    rollingUpdate:
      maxUnavailable: 1              # 滚动过程中最多几个副本不可用（可以是 25%）
      maxSurge: 1                    # 滚动过程中最多超出 replicas 几个（可以是 25%）
  template:
    metadata:
      labels:
        app: myapp
        version: v1
    spec:
      containers:
      - name: myapp
        image: registry.cn-beijing.aliyuncs.com/google_registry/myapp:v1
        ports:
        - containerPort: 8080
        readinessProbe:
          httpGet:
            path: /healthz
            port: 8080

kubectl create deployment myapp-deployment --image=nginx:1.27 --replicas=3 --dry-run=client -o yaml > myapp-deployment.yaml
kubectl apply -f myapp-deployment.yaml
kubectl get deploy,rs,pod -l app=myapp -o wide

6.4 Service

Service 通过标签选择器找到后端 Pod，并为其提供固定 ClusterIP 和 DNS 名。四种类型：ClusterIP（仅集群内，默认）、NodePort（每节点开一个 30000-32767 的端口）、LoadBalancer（云厂商 LB）、ExternalName（CNAME 到外部域名）。

apiVersion: v1
kind: Service
metadata:
  name: myapp-svc
  namespace: default
spec:
  type: ClusterIP
  selector:                          # 与 Pod 的 labels 对应，写错则 Endpoints 为空
    app: myapp
  ports:
  - name: http
    port: 80                         # Service 暴露的端口
    targetPort: 8080                 # 容器实际监听端口，可直接写端口名 http
    protocol: TCP

kubectl expose deployment myapp-deployment --name=myapp-svc --port=80 --target-port=8080 --type=ClusterIP
kubectl get svc myapp-svc -o wide
kubectl get endpoints myapp-svc    # Endpoints 为空说明 selector 不匹配或 Pod 未就绪（kubectl get endpointslices 亦可）

6.5 Ingress

Service 是四层（TCP/UDP）负载均衡，Ingress 是七层（HTTP/HTTPS）路由规则，可以按域名和路径转发，必须配合 Ingress Controller（如 ingress-nginx、Traefik）才能生效。

apiVersion: networking.k8s.io/v1     # 1.19 起使用该版本，extensions/v1beta1 已废弃
kind: Ingress
metadata:
  name: myapp-ingress
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx            # 替代已废弃的 kubernetes.io/ingress.class 注解
  tls:
  - hosts:
    - myapp.example.com
    secretName: myapp-tls            # 提前创建好的 tls 类型 Secret
  rules:
  - host: myapp.example.com
    http:
      paths:
      - path: /
        pathType: Prefix             # 必填：Prefix（前缀）或 Exact（精确）
        backend:
          service:
            name: myapp-svc
            port:
              number: 80

kubectl get ingress -A
kubectl describe ingress myapp-ingress      # 看 Rules / Events，排 404、502 的常用入口
kubectl get pods -n ingress-nginx           # 确认 Controller 本身在跑

6.6 ConfigMap 与 Secret

# 从字面量创建 ConfigMap
kubectl create configmap app-config --from-literal=APP_ENV=dev --from-literal=LOG_LEVEL=info
# 从文件/目录创建（键名就是文件名）
kubectl create configmap app-config --from-file=./application.yaml
# 从字面量创建 Secret（键值对形式）
kubectl create secret generic db-secret --from-literal=username=root --from-literal=password='S3cr3t!'
# 从文件创建 docker-registry 类型 Secret，用于拉私有镜像
kubectl create secret docker-registry regcred --docker-server=registry.cn-beijing.aliyuncs.com \
  --docker-username=user --docker-password=pass --docker-email=me@example.com
kubectl get secret db-secret -o jsonpath='{.data.password}' | base64 -d   # 只是编码，不是加密

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: dev
  application.yaml: |               # 竖线表示保留换行的多行文本
    server:
      port: 8080
---
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:                         # stringData 写明文，提交时自动转成 data 的 base64
  username: root
  password: "S3cr3t!"

# 在 Pod 中以「环境变量」或「文件」两种方式消费配置
spec:
  containers:
  - name: myapp
    image: myapp:v1
    envFrom:
    - configMapRef:
        name: app-config            # 整个 ConfigMap 变成环境变量
    - secretRef:
        name: db-secret
    env:
    - name: DB_PASSWORD             # 只取 Secret 中的某一个键
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: password
    volumeMounts:
    - name: config-volume
      mountPath: /etc/config
      readOnly: true
  volumes:
  - name: config-volume
    configMap:
      name: app-config              # 挂载后 /etc/config/application.yaml 就是上面的内容
      items:
      - key: application.yaml
        path: application.yaml

以 volume 方式挂载的 ConfigMap/Secret 更新后，容器内的文件会在约 1 分钟内（kubelet 同步周期 + 缓存 TTL）自动更新；以环境变量方式注入的不会更新，必须重启 Pod 才生效。修改 ConfigMap 后可用 kubectl rollout restart deployment/myapp-deployment 触发一次滚动重启。

6.7 PV、PVC 与 StorageClass

PV 是集群里的实际存储资源（集群级对象），PVC 是用户对存储的申请（命名空间级对象），两者按 容量 + accessModes + storageClassName 匹配绑定，Pod 只挂载 PVC。

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: standard
provisioner: kubernetes.io/aws-ebs    # 换成实际环境的 CSI 驱动，如 diskplugin.csi.alibabacloud.com
reclaimPolicy: Delete                 # Delete：PVC 删除后自动回收 PV；Retain：保留数据需人工处理
volumeBindingMode: WaitForFirstConsumer   # 等 Pod 调度后再建卷，避免跨可用区挂载失败
allowVolumeExpansion: true
---
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-nfs-10g
spec:
  capacity:
    storage: 10Gi
  accessModes:
  - ReadWriteOnce                     # RWO 单节点读写；ROX 多节点只读；RWX 多节点读写（需共享存储）
  persistentVolumeReclaimPolicy: Retain
  storageClassName: standard
  nfs:                                # 生产更常用 CSI，这里以 NFS 为例便于理解
    server: 172.16.1.120
    path: /data/nfs
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: myapp-pvc
  namespace: default
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
  storageClassName: standard          # 省略且集群有默认 StorageClass 时会动态供给

spec:
  containers:
  - name: myapp
    image: myapp:v1
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: myapp-pvc

kubectl get pv                     # STATUS: Available / Bound / Released / Failed
kubectl get pvc -A
kubectl describe pvc myapp-pvc     # Pending 时看 Events，一般是没匹配到 PV 或 StorageClass 不存在
kubectl get storageclass

7.声明式与命令式

kubectl 有三类操作方式，理解了它们的关系，就知道什么时候该用哪个命令：

方式典型命令特点与适用场景
命令式对象配置kubectl create/delete -f xxx.yaml从一个 YAML 创建或删除对象。语义是「动作」：对象已存在时 create 直接报 AlreadyExists，不报错就继续用
命令式命令kubectl run/expose/scale/set image/label直接对活动对象做动作，快捷、适合调试和应急；不可复现，不产生可版本化的配置
声明式对象配置kubectl apply -f xxx.yaml只描述「期望的最终状态」，kubectl 做三方合并后决定创建还是更新，可反复执行（幂等），适合 CI/CD 与 GitOps

7.1 apply、create 与 replace 的区别

命令对象不存在对象已存在说明
apply创建按 last-applied-configuration 做三方合并更新（增量）推荐日常使用；用 -f 可指向文件、目录或 URL
create创建报错 AlreadyExists需要 --save-config 才会记录上次配置，否则后续 apply 会告警
replace报错 NotFound用新文件整体替换，未写到的字段会被清空危险：容易误删字段，部分字段不可变时会直接失败
patch报错只改指定字段（strategic/merge/json patch）小改动、脚本化修改时很实用
 
# 不真正执行，只把客户端生成的 YAML 打印出来，用于「命令转配置」
kubectl create deployment web --image=nginx --replicas=2 --dry-run=client -o yaml > web.yaml
# 走一次服务端校验（需要集群连通），提前发现字段错误
kubectl apply -f web.yaml --dry-run=server
# 查看某对象的差异与最近一次配置
kubectl diff -f web.yaml
kubectl get deploy web -o yaml | grep -A5 last-applied-configuration
# 只改一个字段
kubectl patch deployment web -p '{"spec":{"replicas":5}}'

常见坑：先用 create 再用 apply 会提示 missing last-applied-configuration annotation，此时用 kubectl apply -f xxx.yaml --force 或先 delete 再 apply。另外 kubectl apply 不带 -f 不会读 stdin 以外的任何输入，目录模式下只处理 .yaml/.yml/.json。

8.滚动更新与回滚

Deployment 的更新本质是「新建一个 ReplicaSet，逐步把副本从旧 RS 迁到新 RS」。相关命令如下：

命令 作用
kubectl apply -f myapp-deployment-v2.yaml 通过配置文件滚动升级
kubectl set image deploy/myapp-deployment myapp=registry.cn-beijing.aliyuncs.com/google_registry/myapp:v3 通过命令只改镜像触发滚动升级（注意容器名 myapp 要写对）
kubectl rollout status deploy/myapp-deployment 阻塞观察本次滚动是否完成
kubectl rollout history deploy/myapp-deployment 查看历史版本号（REVISION）
kubectl rollout pause / resume deploy/myapp-deployment 暂停/恢复滚动，用于金丝雀式分批发布
kubectl rollout restart deploy/myapp-deployment 不改镜像只重启（常用于让新 ConfigMap/Secret 生效）
kubectl rollout undo deploy/myapp-deployment
kubectl rollout undo deploy myapp-deployment		 回滚到上一个版本
kubectl rollout undo deploy/myapp-deployment --to-revision=2 回滚到指定历史版本 
kubectl rollout status deploy/myapp-deployment --timeout=120s
kubectl rollout undo deploy/myapp-deployment
kubectl get rs -l app=myapp            # DESIRED/CURRENT/READY 能看出新旧 RS 的交替过程
kubectl describe deploy myapp-deployment | tail -20   # Events 里能看到 ScalingReplicaSet 记录

# 保证滚动更新可用的三个要点：就绪探针、maxUnavailable、revisionHistoryLimit
spec:
  revisionHistoryLimit: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0       # 先扩容再缩容，做到零中断（副本数少时更稳）
      maxSurge: 1
  template:
    spec:
      containers:
      - name: myapp
        image: myapp:v2
        readinessProbe:       # 没有就绪探针时，新 Pod 一 Running 就会被加进 Endpoints 接流量
          httpGet: {path: /healthz, port: 8080}
          initialDelaySeconds: 5

回滚只能回滚到本次 apply/set image 之前的模板。如果改动是通过 kubectl edit 直接改的，同样会生成新 RS 与 Revision，因此可以回滚；但如果是修改了 ConfigMap 内容，则 rollout undo 无效，需要回退 ConfigMap 并重启。

8.1 动态伸缩

命令 作用
kubectl scale deploy myapp-deployment --replicas=5 按名字动态伸缩
kubectl scale --replicas=8 -f myapp-deployment-v2.yaml 按 YAML 文件里声明的对象伸缩
kubectl autoscale deploy myapp-deployment --min=2 --max=10 --cpu-percent=60 创建 HPA，按 CPU 利用率自动扩缩容 
kubectl get hpa                                  # 依赖 metrics-server，否则 TARGETS 显示 unknown
kubectl top pod -l app=myapp                     # 同样需要 metrics-server（旧版本曾用 heapster，已废弃）

HPA 的 --cpu-percent 是相对 requests 计算的：Pod 没写 resources.requests.cpu 时，HPA 拿不到分母，会显示 unknown/60% 而无法扩容。

8.2 探针与资源限制

探针作用失败后果
readinessProbe容器是否准备好接收流量从 Service Endpoints 中摘除，不重启容器
livenessProbe容器是否还活着按 restartPolicy 重启容器
startupProbe启动慢的应用是否已启动完成在它成功前，存活/就绪探针都不生效，避免慢启动被误杀
 
spec:
  containers:
  - name: myapp
    image: myapp:v1
    resources:
      requests: {cpu: 100m, memory: 128Mi}
      limits: {cpu: "1", memory: 512Mi}   # CPU 单位是核，1 等价于 1000m；内存建议用 Mi/Gi
    startupProbe:                          # 最多等 30×5=150 秒启动时间
      httpGet: {path: /healthz, port: 8080}
      failureThreshold: 30
      periodSeconds: 5
    livenessProbe:
      httpGet: {path: /healthz, port: 8080}   # httpGet 支持 path/port/host/scheme/httpHeaders
      initialDelaySeconds: 10                 # 有 startupProbe 时可不写
      periodSeconds: 10
      timeoutSeconds: 3
      failureThreshold: 3                     # 连续失败 3 次判定为失败，默认就是 3
    readinessProbe:
      exec:                                   # exec 方式：命令返回 0 视为成功
        command: ["/bin/sh", "-c", "curl -sf http://localhost:8080/healthz"]
      periodSeconds: 5

资源单位说明：CPU 用 m（千分之一核），100m=0.1 核；内存用 Mi/Gi（1024 进制）或 M/G（1000 进制）。requests 影响调度与 HPA 分母，limits 是硬上限：内存超限 OOMKilled（退出码 137），CPU 超限被节流。可以再配合 LimitRange（给命名空间设默认 requests/limits）与 ResourceQuota（限制命名空间总量）。

9.命名空间与标签选择器

kubectl get ns                                   # 查看有哪些命名空间
kubectl create namespace test
kubectl config set-context --current --namespace=test
kubectl get pod -n kube-system                   # 指定命名空间
kubectl get pod -A                               # 所有命名空间
kubectl delete ns test                           # 会级联删除命名空间内所有资源，慎用
kubectl get ns test -o jsonpath='{.status.phase}'   # Active / Terminating

标签（label）是键值对，用于选择与分组；注解（annotation）同样键值对，但用于存放工具和控制器读取的元信息，不能被选择器匹配。

kubectl get pod -A --show-labels
kubectl get pod -l 'app=myapp,env in (dev,test)'    # 集合式：in / notin / exists
kubectl get pod -l 'env!=prod'                      # 注意：不满足与不存在都会被选中
kubectl get pod -l app=myapp --show-labels -o wide
kubectl label nodes k8s-node01 zone=north           # 为节点打标签
kubectl label pod podName -n nsName role-name=test
kubectl label pod podName -n nsName role-name=dev --overwrite   # 改标签值必须加 --overwrite
kubectl label pod podName -n nsName role-name-             # 删除标签要用「键名+减号」
kubectl label nodes k8s-node01 zone-                 # 删除节点上的标签
kubectl annotate pod podName -n nsName note=hello --overwrite

# 节点亲和与 Pod 反亲和：比 nodeSelector 更灵活的选择方式
spec:
  nodeSelector:
    zone: north
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: kubernetes.io/os
            operator: In
            values: [linux]
    podAntiAffinity:                        # 同一 Deployment 的副本尽量分散到不同节点
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          topologyKey: kubernetes.io/hostname
          labelSelector:
            matchLabels:
              app: myapp

标签选择器写错的典型症状：kubectl get pods -l app=myapp 明明有 Pod 却查不到（键或值打错），或者 Service 的 Endpoints 为空。Deployment 的 spec.selector 一旦创建就不能修改，需要改就只能删掉重建。

10.排障命令

命令用途
kubectl get pod -o wide看 IP、所在节点、重启次数，快速定位「重启多」「Pending」
kubectl describe pod <name>看事件（Events）、探针失败原因、调度失败原因、挂载失败原因
kubectl logs <pod> [-c 容器] [-f] [--tail=100] [--previous]看标准输出日志；--previous 看被重启掉的上一实例日志
kubectl exec -it <pod> -- sh进容器排查网络、配置、进程
kubectl get events --sort-by=.lastTimestamp按时间顺序看集群事件，注意要带 -A 或 -n
kubectl port-forward svc/myapp-svc 8080:80把 Service/端口转发到本地，绕过 Ingress 直接验证服务
kubectl top pod/node看资源用量，需 metrics-server
kubectl cp与容器互拷文件，例如 kubectl cp myapp-pod:/tmp/dump.log ./dump.log
kubectl api-resources查资源名、短名称（如 deploy/svc/ing）、是否命名空间级
kubectl explain pod.spec.containers查字段含义与类型，替代翻文档
 
# 1. 容器起不来看 describe 的 Events 与 Last State
kubectl describe pod myapp-pod | sed -n '/Events:/,$p'
# 2. 容器内进程崩溃看上一次的日志
kubectl logs myapp-pod --previous --tail=200
# 3. 多容器 Pod 必须指定容器名
kubectl logs myapp-pod -c sidecar --tail=100
# 4. 镜像拉取失败（ImagePullBackOff）先确认 Secret 与镜像地址
kubectl get pod myapp-pod -o jsonpath='{.spec.imagePullSecrets[*].name}'
# 5. 集群内 DNS / 连通性排查
kubectl run tmp-shell --rm -it --image=busybox:1.36 --restart=Never -- sh
#    nslookup myapp-svc.default.svc.cluster.local
#    wget -qO- http://myapp-svc.default.svc.cluster.local
# 6. 查看所有命名空间的异常 Pod（非 Running / 非 Succeeded）
kubectl get pod -A --field-selector=status.phase!=Running,status.phase!=Succeeded
# 7. 只看最近的 Warning 事件
kubectl get events -A --field-selector type=Warning --sort-by=.lastTimestamp | tail -20
# 8. 本地直接访问 Service，跳过 Ingress 定位是应用问题还是入口问题
kubectl port-forward svc/myapp-svc 8080:80
# 9. 强制删除卡在 Terminating 的 Pod（确认确实要强删时再用）
kubectl delete pod myapp-pod -n default --grace-period=0 --force

排障顺序建议：先 get -o wide 看状态 → 再 describe 看 Events 找到「谁在拒绝」→ 再看 logs 判断应用自身问题 → 最后用 exec/port-forward 从容器内部和集群内部验证。90% 的问题在 describe 的 Events 里已经有答案。

12.状态

状态名 含义
Running 运行中
Error 异常，无法提供服务
Pending 准备中，暂时无法提供服务
Terminating 结束中，即将被移除
Unknown 未知状态，多发生于节点宕机
PullImageBackOff 镜像拉取失败

必须存在的属性

metadata Object 元数据对象, 固定值就写metadata
metadata.name String 元数据对象的名字, 比如命名Pod的名字
metadata.namespace String 元数据对象的命名空间
Spec Object 详细定义对象, 固定值就写Spec
spec.containers[] list Spec对象的容器列表定义, 是个列表
spec.containers[].name String 容器的名字

小结与操作路径：写 YAML 或用命令生成期望状态 → kubectl apply -f 提交 → kubectl get/describe 观察是否达到期望 → 升级用 set image 或新 YAML + rollout status，出问题 rollout undo → 排障按 describe → logs → exec/port-forward → events 的顺序走。

kubectl explain pod 可以查看资源的字段模板，kubectl explain pod.spec.containers 查看更细的字段说明，字段是否必填、类型是什么都写得很清楚，比翻文档更快。
