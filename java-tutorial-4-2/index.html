Struts2 与 OGNL

Posted on 2026-09-19，9 min read

在 Servlet/JSP 里，Action 处理完数据要带回页面，只有一条路：request.setAttribute(...)，页面再用 EL 表达式取。Struts2 换了一套模型：数据默认放进值栈（ValueStack），页面用 OGNL 表达式取值。理解值栈与 OGNL，是看懂 <s:property>、<s:iterator>，以及拦截器为什么能改参数、做校验的前提。本章先与 Servlet 域模型做对比，再讲值栈的读写与查找顺序、OGNL 中 #、%、$ 三个符号和集合操作，最后落到拦截器的编写与 struts.xml 配置。适合已经能跑通一个 Struts2 Action、却对"页面里为什么能直接写 username"心存疑惑的读者。

一、从 Servlet 的域模型到值栈

Servlet 的思路是"把数据放进域，再按键取值"：数据存在 request、session、application 等作用域里，EL 按域查找，键名就是全部线索。Struts2 的思路是"把数据放到一棵可导航的对象图上，再按路径取值"，承担这棵树的就是 OGNL。

OGNL 全称 Object-Graph Navigation Language（对象图导航语言），是 Struts2 默认的表达式语言（此外还支持 EL、JSTL、Groovy 等）。它有两个关键概念：

  • 根对象（root）：在 Struts2 中就是值栈。它的实现类 OgnlValueStack 内部持有一个 List（CompoundRoot）存放一组对象，第一个元素叫栈顶对象。访问根对象的属性不需要前缀，直接写属性名。
  • 上下文（Context）：一个 Map 结构（实现了 java.util.Map），在 Struts2 中的实现是 ActionContext，里面挂着 request、session、application、attr、parameters 等对象。访问上下文中的对象必须加 # 前缀。

与 Servlet 最大的差别在于：当前 Action 对象会被框架自动压入值栈栈顶，所以 Action 里带 getter 的属性，页面直接写属性名就能取到，不必再 setAttribute。另外，Struts2 用 StrutsRequestWrapper 包装了 request，重写 getAttribute()：先在 request 域找，找不到就回落到 valueStack.findValue(name)。这就是为什么老代码里 ${username} 也能取到值栈中的数据——但这一回落只在 Struts2 的过滤器链内有效，脱离框架就不成立。

把两种模型并排看，差别只有一句话：Servlet 靠“键名”定位数据，键名重复、作用域弄混就会取错；OGNL 靠“路径”定位数据，路径写全了就不会有歧义。代价是路径依赖对象结构，# 前缀、下标、栈序都是路径的一部分，所以 Struts2 的页面比 JSP+EL 更难随手看懂，调试时也更依赖 <s:debug/>。理解了这一点，遇到“值明明放了却取不到”时，第一反应应该是查栈序与 # 前缀，而不是反复重写 setAttribute。

二、值栈的读写与查找顺序

取到值栈的入口是 ActionContext.getContext().getValueStack()。往对象栈（root）里放数据有两种方式：push(Object) 匿名入栈，栈顶直接是那个对象；set(String, Object) 有名入栈，本质是构造一个单键 Map 再压栈，所以取值时要写 [0].top.key。此外 ActionContext.put(k, v) 放的是上下文而不是 root，取值必须加 #。

public class ValueStack1Action extends ActionSupport {
    private String username;                         // 有 getter 的属性随 Action 一起入栈

    @Override
    public String execute() {
        ValueStack vs = ActionContext.getContext().getValueStack();
        vs.push("anonymous");                        // 匿名入栈：栈顶是一个 String
        vs.set("nickname", "Curry");                 // 有名入栈：栈顶是一个单键 Map
        ActionContext.getContext().put("password", "123456"); // 放上下文，不属于 root
        this.username = "Kobe";                      // Action 已在栈中，属性直接可取
        return SUCCESS;
    }

    public String getUsername() { return username; }
    public void setUsername(String username) { this.username = username; }
}

取值规律可以概括成两句话：不加 #，先搜对象栈（从栈顶往下），找不到再搜上下文栈，命中即停；加了 #，只搜上下文栈。这意味着同名属性一定被栈顶对象遮蔽——Action 的 username 会压住 ActionContext 里的同名键，排查"取值取错"时先看栈序。按下标可以直接定位：[0].top 是栈顶，[1].top 是第二个元素。开发期在页面放一个 <s:debug/>，即可看到完整的值栈与上下文快照。

三、OGNL 语法要点：#、%、$ 与集合操作

三个符号各有分工。# 用于访问上下文（#request、#session、#application、#attr、#parameters）和就地构造集合；其中 #attr 按 page→request→session→application 的顺序查找，#parameters 取到的是数组，通常要写 [0]。% 用于把"被标签当成普通字符串"的文本强制按 OGNL 解析，典型场景是表单回显 value="%{username}"；反过来写成 %{'hello'} 则表示这是字面量。$ 主要出现在配置文件与国际化资源里，用于把值栈中的值拼进字符串。

OGNL 还能直接调用方法、构造集合，并对集合做筛选投影：? 取全部符合条件的元素，^ 取第一个，$ 取最后一个，this 代表当前迭代元素。这些能力让"价格大于 35 的书"这类需求可以只写在页面表达式里。

OGNL 与 EL 的能力边界也值得记一笔：EL 只能从四个域里按键取值，而 OGNL 支持调用对象方法（如 name.length()）、访问静态成员、构造 List 与 Map、用 in / not in 判断元素是否存在，以及用 ?、^、$ 做投影筛选。功能强带来的是风险：OGNL 表达式可能被注入执行，因此升级 Struts 版本、关闭静态方法访问、不在表达式里拼接用户输入，是使用它时需要同时守住的三条纪律。

静态方法与静态字段的写法是 @类全名@方法名，例如 @java.lang.String@format('foo %s','bar')。这里必须提醒版本差异：出于安全考虑，Struts 2.3.20 起 struts.ognl.allowStaticMethodAccess 默认为 false，2.5 起该开关被移除，静态方法访问默认不可用；网上大量老笔记里的 @@PI 简写更是依赖隐式包名，不要照抄。最后，在 JSP 里 OGNL 必须配合 Struts 标签才能显示数据，而在 Java 代码中可以直接用 Ognl.getValue(expr, context, root) 求值。

四、拦截器：Struts2 的调用链

拦截器（Interceptor）是 Struts2 的核心机制之一，它在 Action 执行前后插入逻辑，本质是沿一条调用链的 AOP 式环绕。它和 Servlet 过滤器容易混：过滤器基于 Servlet 规范、依赖 Servlet 容器、能过滤所有请求（页面、Servlet、静态资源）；拦截器基于 Struts2 自己的 ActionInvocation 调用链、不依赖 Servlet 容器、只作用于 Action 调用（以及结果渲染）。也正因如此，拦截器能通过 invocation.getInvocationContext() 拿到值栈与 ActionContext，直接操作值栈——这是过滤器做不到的。

写一个拦截器有三种方式：实现 Interceptor 接口，重写 init()、intercept()、destroy()（注意方法名是 intercept，不是 interceptor，源笔记此处有拼写错误）；继承 AbstractInterceptor，只需重写 intercept()，最常用；继承 MethodFilterInterceptor，重写 doIntercept()，并可通过 includeMethods / excludeMethods 精确控制拦截哪些方法，灵活度最高。

// 方式二：继承 AbstractInterceptor，最常用
public class LoginInterceptor extends AbstractInterceptor {
    @Override
    public String intercept(ActionInvocation invocation) throws Exception {
        Object user = ActionContext.getContext().getSession().get("user");
        if (user == null) {
            return "login";                  // 不调用 invoke()，直接返回结果码，中断后续调用链
        }
        String result = invocation.invoke(); // 放行：进入下一个拦截器或 Action
        return result;                       // 返回途中仍是本拦截器的代码，可做后置处理
    }
}

// 方式三：继承 MethodFilterInterceptor，可按方法名放行
public class LogInterceptor extends MethodFilterInterceptor {
    @Override
    protected String doIntercept(ActionInvocation invocation) throws Exception {
        System.out.println("调用 Action：" + invocation.getProxy().getActionName());
        return invocation.invoke();
    }
}
<struts>
  <package name="default" namespace="/" extends="struts-default">
    <interceptors>
      <!-- 1. 声明拦截器与拦截器栈 -->
      <interceptor name="loginInterceptor" class="cn.itcast.interceptor.LoginInterceptor"/>
      <interceptor-stack name="myStack">
        <interceptor-ref name="loginInterceptor"/>
        <interceptor-ref name="defaultStack"/> <!-- 自定义栈里务必带上默认栈 -->
      </interceptor-stack>
    </interceptors>

    <!-- 2. 本包所有 Action 默认走 myStack -->
    <default-interceptor-ref name="myStack"/>

    <action name="book_*" method="{1}" class="cn.itcast.action.BookAction">
      <result name="login">/login.jsp</result>
      <result>/book.jsp</result>
    </action>
  </package>
</struts>

defaultStack 里已经打包了日常需要的拦截器，常见的有：params 负责把请求参数注入 Action 属性；modelDriven 支持模型驱动传参；conversionError 把类型转换错误写进 fieldError；validation 执行字段校验；workflow 依据校验结果决定流程是否继续；fileUpload 处理文件上传。它们按固定顺序排列，顺序本身就承载语义——例如 workflow 必须在 validation 之后才能读到错误信息并中断。自定义拦截器插进这个序列时，务必想清楚放在 params 之前还是之后：放在之前，Action 属性尚未注入，读到的全是默认值。

配置分局部与全局两种。局部是在 <action> 内写若干 <interceptor-ref>，只对该 Action 生效；全局是用 <interceptor-stack> 把自定义拦截器与 defaultStack 组装成一个栈，再由包的 <default-interceptor-ref> 指定。执行顺序遵循"先声明先执行、返回时逆序"，因此日志、计时类拦截器常放在栈的前面或后面以获得想要的耗时口径。

五、常见坑与易混点

  • 显式引用拦截器会让包的默认栈失效。只要在 <action> 里写了任意一个 <interceptor-ref>，Struts 就不再套用包的 default-interceptor-ref，必须手动补一行 <interceptor-ref name="defaultStack"/>；否则 params、validation、workflow 等拦截器全部缺席，表现为"请求参数注不进 Action"或"校验不生效"。
  • 拦截器里不调用 invoke() 就必须自己返回结果码，且该 Action 要有同名的 <result>，否则页面 404 或抛异常。
  • 同名属性取错，多半是栈序问题。值栈是"查找"而非覆盖，栈顶 Object 的属性优先于 set() 进去的 Map，更优先于上下文栈。
  • 静态方法访问默认关闭（2.3.20 起默认 false，2.5 起开关移除），不要沿用老笔记里的写法；确有需要应在服务端显式放开并评估 OGNL 注入风险。
  • 过滤器与拦截器的边界：需要拦截 JSP、图片、所有 URL 时用过滤器或 Spring MVC 的 HandlerInterceptor；只需在 Action 调用链上做参数注入、校验、登录检查时用 Struts2 拦截器。

小结：Struts2 把"域 + 键"的取数方式换成了"值栈 + OGNL 路径"。记住三点即可上手：数据放值栈（push、set，或直接给 Action 加 getter），取数据不加 # 走对象栈、加 # 走上下文，拦截器是围绕 Action 调用的可配置调用链——一旦在 Action 里显式引用了拦截器，别忘了把 defaultStack 带回来。理解了这一层，<s:property> 为什么能直接写属性名、以及参数注入为什么突然失灵，就都成了同一个问题的两面。
