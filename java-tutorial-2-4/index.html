2.4 MySQL 高阶

Posted on 2026-09-19，4 min read

很多教程讲 MySQL 停在“会写 CRUD”，但线上事故往往不是语法错误，而是慢查询拖垮连接池、机器掉电后主从数据对不上。本章先讲清 InnoDB 与三种日志“为什么快、为什么不容易丢”，再落到慢查询定位与执行计划分析，最后给出索引改写套路和分库分表的分寸。本章适合已能写基本 SQL、准备把数据库用进生产的读者。

一、存储引擎：默认为什么是 InnoDB

MySQL 是插件式的：同一个服务器可以挂载不同存储引擎，建表时用 ENGINE= 指定，SHOW ENGINES; 可以查看支持列表。老教材常提 MyISAM，今天真正要掂量的是两者的取舍。

  • InnoDB：支持事务（ACID）、行级锁、MVCC、外键和崩溃恢复；索引即数据，主键索引的叶子节点直接存整行，因此叫聚簇索引；辅助索引的叶子只存主键值，查非索引列就要“回表”。
  • MyISAM：不支持事务，也没有行锁（只有表锁）；索引与数据分开存放，辅助索引直接指向数据地址；崩溃后表可能损坏，需要 REPAIR TABLE 修复。它只在只读、少并发的场景里略微省资源，MySQL 8.0 连系统表都已换成 InnoDB。

所以今天的引擎选型基本等价于回答一个问题：要不要事务和并发写。要，就用 InnoDB。聚簇索引还能推出一个直接结论——主键要短且递增（例如自增 BIGINT）。随机主键会让插入落在索引中间，引发页分裂和额外的 IO；业务上唯一的字段（手机号、订单号）加唯一索引即可，不必硬做主键。

二、redo、undo 与 binlog：一次提交到底写了什么

不少人背过 WAL，却说不清三种日志各管什么。按所在层次划分：redo log 与 undo log 属于 InnoDB 引擎层，binlog 属于 MySQL Server 层。

  • redo log（重做日志）：记录“某个数据页被改成了什么样”，属于物理逻辑日志，以循环写的方式写在固定大小的文件组里。事务修改先写 redo 并落盘，脏页可以慢慢刷回表空间——这就是 WAL（先写日志，再写数据）。它解决的是崩溃恢复：断电重启后，把已提交但还没刷进表空间的数据补回来。
  • undo log（回滚日志）：记录数据的旧版本，支撑两件事——事务回滚，以及 MVCC 的快照读。快照读沿版本链找到对当前事务可见的版本，所以普通 SELECT 不用加锁。长事务会一直拖住旧版本，导致 undo 膨胀、历史版本读变慢。
  • binlog（归档日志）：Server 层的逻辑日志，记录执行过什么语句或行发生了哪些变化，用于主从复制和按时间点恢复。格式有 STATEMENT、ROW、MIXED，生产环境推荐 ROW，能避免函数、随机值带来的主从不一致。

一次提交并不是“写完一个文件就结束”，而是两阶段提交：先把 redo 写成 prepare 状态，再写 binlog，最后把 redo 改成 commit。这样崩溃恢复时能对照两本账，不会出现“主库有、从库没有”或反过来的情况。

持久性最终由两个参数把关：innodb_flush_log_at_trx_commit=1 表示每次提交都把 redo 刷到磁盘；sync_binlog=1 表示每次提交都把 binlog 刷到磁盘。两者都为 1 是金融级配置，代价是每次提交至少两次磁盘同步，吞吐明显下降；放宽到 2 或 0 可以提速，但崩溃时可能丢掉最近若干个事务。

-- 查看日志与刷盘相关参数
SHOW VARIABLES LIKE 'innodb_log_file_size';
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'sync_binlog';
SHOW VARIABLES LIKE 'binlog_format';

-- 排查长事务：它会让 undo 越堆越大
SELECT trx_id, trx_state, trx_started, trx_rows_modified
FROM information_schema.innodb_trx
ORDER BY trx_started;

三、慢查询日志与 EXPLAIN：先定位，再动手

优化的第一步是测量，不是凭感觉改 SQL。慢查询日志会把执行时间超过 long_query_time（单位是秒，可以写小数）的语句记下来，它默认是关闭的。

这里有两个容易踩的坑。其一，long_query_time 是全局动态变量，SET GLOBAL 只对之后建立的连接生效，当前连接要么重连，要么再补一句 SET SESSION long_query_time = 0.5;。其二，log_queries_not_using_indexes 只负责“额外记录没走索引的语句”，它不能代替 slow_query_log = ON 去开启慢日志；把它误当开关，是排查时最常见的空转。

SET GLOBAL slow_query_log = ON;
SET GLOBAL slow_query_log_file = '/var/log/mysql/mysql-slow.log';
SET GLOBAL long_query_time = 0.5;   -- 设成 0 会记录所有语句，磁盘很快写满
SET GLOBAL log_queries_not_using_indexes = ON;

-- 日志很长，交给工具按总耗时聚合，不要肉眼翻
-- mysqldumpslow -s t -t 10 /var/log/mysql/mysql-slow.log
-- pt-query-digest /var/log/mysql/mysql-slow.log

拿到可疑 SQL 后，在它前面加 EXPLAIN 查看执行计划，字段虽多，日常只需盯四列。type 是访问类型，效率大致为 const > eq_ref > ref > range > index > ALL，出现 ALL（全表扫描）或 index（扫整棵索引树）就要警惕。key 是真正用上的索引；如果 possible_keys 有值而 key 为 NULL，说明索引没被采纳，多半与列类型、函数包裹或数据分布有关。rows 是优化器估算的扫描行数，统计信息过期时会严重失真，MySQL 8.0.18 起可用 EXPLAIN ANALYZE 看真实值。Extra 信息量最大：Using filesort 表示排序没走索引，Using temporary 表示用了临时表，Using index 表示覆盖索引无需回表，Using index condition 表示索引条件下推（ICP）生效。

EXPLAIN 输出逐列解读

先看上面四列是快速判断的抓手，但排查复杂语句时得把整行读全。传统格式（EXPLAIN 或 EXPLAIN FORMAT=TRADITIONAL）每个表一行，固定十二列，含义如下。

  • id：查询块的编号。id 相同表示同层、按从上到下的顺序执行；id 不同则数值越大越先执行（先算子查询，再喂给外层）；id 为 NULL 说明这一行是 UNION RESULT 之类的合并结果，没有对应的真实表。
  • select_type：这一行属于哪种查询块，常见取值如下：
    • SIMPLE：不含子查询和 UNION。
    • PRIMARY：最外层。
    • SUBQUERY：SELECT 列表或 WHERE 里的非相关子查询。
    • DEPENDENT SUBQUERY：相关子查询，会随外层每一行重算，最需要警惕。
    • DERIVED：FROM 里的派生表（通常被物化）。
    • UNION／UNION RESULT：对应集合运算。
    • MATERIALIZED：子查询被物化成临时表。
  • table：这一行访问的表名。<derived2> 表示引用 id=2 的派生表，<subquery3> 是物化子查询，它们都是临时结果，不是真实表。
  • partitions：分区裁剪后真正命中的分区；未分区表恒为 NULL。这里的 NULL 与“有没有走索引”无关，别误读。
  • type：访问类型，判断效率最直接的列，取值阶梯见下一小节。
  • possible_keys：理论上可选的索引，仅供参考。它为 NULL 说明没有可用索引，基本只能全表扫。
  • key：优化器实际选用的索引；为 NULL 说明最终没用索引。possible_keys 有值而 key 为 NULL，常见原因是列类型或字符集不一致、条件被函数包裹、或优化器估算全表扫更便宜。
  • key_len：索引中被使用的字节数，可用来判断组合索引用到了前几列。在 utf8mb4 下 VARCHAR(n) 大致占 4n 字节，再加 2 字节长度（可空列还要加 1 字节空标志位），因此可空的 VARCHAR(10) 约为 43 字节。这是按规则推算的经验值，实际以字段定义和官方说明为准。
  • ref：与 key 做等值比较的对象，可能是常量 const、另一表的列（库名.表名.列名）或函数结果。
  • rows：优化器估算的每步需扫描行数，来自采样统计，不是精确计数。统计信息过期会严重失真，可用 ANALYZE TABLE 更新。单看 rows 大不一定坏，要和下一列一起看。
  • filtered：按条件过滤后预计留下的百分比（0～100）。rows 与 filtered 相乘才是这一步估算的输出行数：rows=1000、filtered=1 意味着扫一千行只留十行，很值得考虑把过滤列纳入索引。
  • Extra：优化器的补充说明，信息量最大，常见取值见后文。

type 取值阶梯：system 到 ALL

访问类型按效率大致排成一条阶梯：system > const > eq_ref > ref > range > index > ALL。这里的“好”指扫的行数少、回表少，不等于绝对耗时。

  • system：表里只有一行（典型是只有一行的系统表或常量表），是 const 的特例，最快。
  • const：通过主键或唯一索引做等值查询，最多命中一行，优化器甚至能在执行前把它替换成常量，只读一次。
  • eq_ref：多表连接时，被驱动表用主键或非空唯一索引做等值匹配，每行只对应一行。这是连接里能达到的最好类型。
  • ref：用普通（非唯一）索引做等值匹配，可能命中多行。日常优化最常见的目标就是把 ALL 变成 ref。
  • range：索引上的范围扫描，对应 BETWEEN、>、<、IN、LIKE 'abc%' 等条件。IN 最终落成 range 还是 ref 取决于优化器估算，不必死记。
  • index：扫描整棵索引树，只是比 ALL 少读了数据页，常见于覆盖索引。行数一多仍然是坏消息，别因为它“用上了索引”就放心。
  • ALL：全表扫描，没有可用索引或优化器认为索引不划算。大表上出现 ALL 是首要消灭目标。

除阶梯上的取值外，还可能出现 index_merge（两个索引取并集或交集）、ref_or_null、unique_subquery、index_subquery、fulltext 等，它们不属于这条从好到差的简单排序，含义以官方文档 EXPLAIN 输出一节为准。

Extra 常见取值

  • Using index：覆盖索引，查询要的列都在索引里，不需要回表，通常是最好的信号之一。
  • Using where：存储引擎取回行之后，Server 层还要再过滤一遍。它本身不是问题，但若同时 type=ALL，说明过滤发生在读完整个表之后，代价很高。
  • Using index condition：索引条件下推（ICP）生效，部分过滤已在存储引擎的索引层完成，减少了回表。原理见上一篇的索引一节。
  • Using filesort：无法利用索引顺序完成 ORDER BY／GROUP BY，需要额外排序。名字里的 file 不代表一定落磁盘，但排序集合大时开销明显。
  • Using temporary：为完成查询建了内部临时表，常见于 GROUP BY、DISTINCT、UNION。MySQL 8.0 的内存临时表默认用 TempTable 引擎（internal_tmp_mem_storage_engine），溢出才落盘，所以看到它不必惊慌，但要结合行数判断。
  • Using join buffer (hash join)／(Block Nested Loop)：被驱动表没有可用索引，只能把驱动表的数据放进连接缓冲里配对。MySQL 8.0.18 起对等值连接引入哈希连接，8.0.20 起进一步用它替代块嵌套循环；看到这个值，优先考虑给被驱动表的连接列加索引。
  • Using index for group-by／Using index for skip scan：前者说明 GROUP BY 直接用上了索引；后者是 8.0.13 起的索引跳跃扫描，组合索引前导列没出现在条件里时也可能用上索引。
  • Impossible WHERE／Zero limit／Select tables optimized away：条件恒假、LIMIT 0、或结果能由索引与统计信息直接得出，都不会真正扫数据。

EXPLAIN ANALYZE 与 FORMAT=JSON

EXPLAIN 给出的始终是估算，统计信息一失真，rows 就可能差几个数量级。MySQL 8.0.18 起提供 EXPLAIN ANALYZE：它真正执行语句，输出树形结构，把每一步的估算值与实测值并排给出。

-- 8.0.18+：真实执行，给出 actual time / actual rows / loops
EXPLAIN ANALYZE
SELECT o.id, o.amount, u.name
FROM orders AS o
JOIN t_user AS u ON u.id = o.user_id
WHERE o.created_at >= '2024-01-01'
ORDER BY o.created_at
LIMIT 100;

-- 输出形如（TREE 格式，节选）：
-- -> Limit: 100 row(s)  (actual time=0.42..0.51 rows=100 loops=1)
--     -> Nested loop inner join  (cost=120.5 rows=98) (actual time=0.05..0.44 rows=100 loops=1)
--         -> Filter: (o.created_at >= '2024-01-01')  (actual time=0.03..0.30 rows=100 loops=1)
--             -> Table scan on o  (actual time=0.02..0.20 rows=5000 loops=1)
--         -> Index lookup on u using PRIMARY (id=o.user_id)  (actual time=0.001..0.001 rows=1 loops=100)

读 EXPLAIN ANALYZE 有两种基本判断：

  • 估算显著小于实测（例如预估 100 行、实测 10 万行）：说明统计信息不准或条件相关性被低估，优化器很可能因此选错索引、选错连接顺序。
  • 实测行数正常但耗时很高：就要看 loops 被放大的那一步。嵌套循环里某层的 loops 很大，它单次的开销会被乘成大数目。

要注意 EXPLAIN ANALYZE 会真的执行语句（含多表写语句也会执行），8.0.18 最初只支持 SELECT，后续版本才逐步扩展到多表 UPDATE／DELETE，可用范围以官方为准；分析慢语句时也应避开业务高峰。

EXPLAIN ANALYZE 目前只输出 TREE 格式。要机器可读、信息更全的结果，用 FORMAT=JSON：

-- 键值结构，含 cost_info、used_columns、attached_condition 等，便于脚本采集与对比
EXPLAIN FORMAT=JSON
SELECT id, name FROM t_user WHERE name = 'tom';

-- 输出节选：
-- {
--   "query_block": {
--     "select_id": 1,
--     "cost_info": { "query_cost": "0.35" },
--     "table": {
--       "table_name": "t_user",
--       "access_type": "ref",
--       "possible_keys": ["idx_name"],
--       "key": "idx_name",
--       "used_key_parts": ["name"],
--       "key_length": "102",
--       "ref": ["const"],
--       "rows_examined_per_scan": 1,
--       "filtered": "100.00",
--       "using_index": true
--     }
--   }
-- }

-- 8.0 也支持 TREE 格式，比传统表格更直观
EXPLAIN FORMAT=TREE
SELECT id, name FROM t_user WHERE name = 'tom';

-- 想看不属于自己的连接正在跑什么，可按连接 id 查它的执行计划
EXPLAIN FOR CONNECTION 12345;

三种格式各有用处：传统格式适合人眼一行行扫；JSON 适合脚本采集与版本间对比，cost_info 里有 read_cost、eval_cost、prefix_cost 等细项，used_columns 能直接看出是否覆盖索引；TREE 与 ANALYZE 适合顺着嵌套层次往下找瓶颈。JSON／TREE 的字段随版本仍在增加，具体字段名以官方文档为准。

四、常见改写套路与分库分表的分寸

执行计划暴露问题之后，多数慢查询都落在下面几类：

  • 函数包住索引列：WHERE DATE(create_time) = '2024-01-01' 会让索引失效，改成范围条件 create_time >= '2024-01-01' AND create_time < '2024-01-02'。
  • 前导模糊匹配：LIKE '%abc' 用不上 B+ 树的有序性，只能全扫；LIKE 'abc%' 才可以走索引。
  • 组合索引的最左前缀：索引 (a, b, c) 能服务 a、a+b、a+b+c，跳过 a 直接用 b 用不上。把等值条件放前面、范围条件放最后，能多用到一列。
  • 深分页：LIMIT 1000000, 20 要先扫掉前一百万行。改用“记住上次位置”的游标写法 WHERE id > ? ORDER BY id LIMIT 20，或先只查主键再回表关联。
  • 子查询改连接：不少 IN (子查询) 可以改写成 JOIN，但要先确认关联键是不是一对多，否则结果会被放大，必要时用 DISTINCT 或 EXISTS。
  • 计数别混用：COUNT(*) 统计所有行，COUNT(col) 跳过该列为 NULL 的行。想一次算出多个条件下的行数，用 SUM(col = 值) 或 COUNT(IF(条件, 1, NULL))，而不是把条件塞进 COUNT() 里硬凑。

当索引、SQL、缓存、读写分离都做过仍然撑不住，才轮到分库分表。垂直拆分按业务把宽表、大库切小；水平拆分按分片键（如用户 ID 取模或按时间范围）把行分散到多个库表。代价也很实在：跨分片 JOIN 和聚合要在应用层拼装，全局唯一 ID 得另想办法（号段模式、雪花算法），跨分片分页和事务都变复杂，扩容还要迁移数据。因此分片键一旦定下就很难改，务必选“查询必带、分布均匀”的列。

五、触发器：能放应用层就别放数据库

触发器（trigger）是绑定在表上的、由 INSERT／UPDATE／DELETE 自动触发的一段 SQL。它和存储过程最大的区别是没有显式调用点：只要那条语句执行了，触发器就一定执行。先看怎么写，再看该不该用。

建一个触发器：before/after × insert/update/delete

一个触发器由三件事唯一确定：时机（BEFORE 或 AFTER）、事件（INSERT／UPDATE／DELETE）和表，三乘二共六种组合。MySQL 8.0 里同一张表的同一时机＋事件可以挂多个触发器，用 FOLLOWS／PRECEDES 指定先后顺序。

触发器体里靠 NEW 和 OLD 访问数据行：NEW 是即将写入（或已写入）的新行，OLD 是更新前（或已删除）的旧行。可用性很好记：INSERT 只有 NEW，DELETE 只有 OLD，UPDATE 两者都有。BEFORE 触发器里可以给 NEW.列 赋值，从而改写即将写入的值（这是 MySQL 的扩展用法）；AFTER 触发器里 NEW／OLD 只读。任何情况下 OLD 都不能被改写。

-- 目标：新增用户时写日志、更新时补时间戳、删除前先归档
CREATE TABLE t_user (
  id         BIGINT         NOT NULL AUTO_INCREMENT,
  name       VARCHAR(32)    NOT NULL,
  balance    DECIMAL(10, 2) NOT NULL DEFAULT 0.00,
  updated_at DATETIME       DEFAULT NULL,
  PRIMARY KEY (id)
) ENGINE = InnoDB;

CREATE TABLE user_log (
  id      BIGINT      NOT NULL AUTO_INCREMENT,
  user_id BIGINT      NOT NULL,
  action  VARCHAR(16) NOT NULL,
  note    VARCHAR(64) DEFAULT NULL,
  PRIMARY KEY (id)
) ENGINE = InnoDB;

-- 触发器体里有分号，命令行客户端会把它当成语句结束，
-- 所以先用 DELIMITER 临时换一个分隔符（DELIMITER 是客户端命令，不是 SQL 语句）
DELIMITER $$

CREATE TRIGGER trg_user_after_insert
AFTER INSERT ON t_user
FOR EACH ROW
BEGIN
  INSERT INTO user_log (user_id, action, note)
  VALUES (NEW.id, 'INSERT', CONCAT('name=', NEW.name));
END$$

-- BEFORE UPDATE：给 NEW 赋值，等于在写库前统一补默认值
CREATE TRIGGER trg_user_before_update
BEFORE UPDATE ON t_user
FOR EACH ROW
BEGIN
  SET NEW.updated_at = NOW();
END$$

-- BEFORE DELETE：把要删的行先归档（此时 OLD 可用、NEW 不可用）
CREATE TRIGGER trg_user_before_delete
BEFORE DELETE ON t_user
FOR EACH ROW
BEGIN
  INSERT INTO user_log (user_id, action, note)
  VALUES (OLD.id, 'DELETE', CONCAT('balance=', OLD.balance));
END$$

DELIMITER ;

-- 触发并验证
INSERT INTO t_user (name, balance) VALUES ('tom', 100.00);
UPDATE t_user SET balance = 120.00 WHERE name = 'tom';
DELETE FROM t_user WHERE name = 'tom';
SELECT * FROM user_log ORDER BY id;   -- INSERT、DELETE 各一条

SHOW TRIGGERS;                        -- 查看当前库的所有触发器
DROP TRIGGER trg_user_after_insert;   -- 删除触发器
JDBC 里不要写 DELIMITER。DELIMITER 只在 mysql 命令行客户端里有效，服务器根本不认识它。用 JDBC 时把整条 CREATE TRIGGER ... BEGIN ... END 作为一个字符串交给 Statement.execute 即可，驱动会当成单条语句发送，不需要分隔符。另外要注意：触发器不能读写触发它的那张表——在 t_user 的触发器里再写 t_user 会报 1442 错误，但操作其他表不受限。

为什么“能用应用层就别用触发器”

触发器语法不难，难的是长期维护。下面几条是实践中最常被抱怨的，足以构成默认不用它的理由。

  • 隐式执行，调用方看不见：应用代码里只有一句 INSERT INTO t_user，实际却动了三张表、还改了字段值。读代码根本判断不出副作用从哪来，接手的人最容易踩。
  • 难排查：触发器里出错，报错信息指向触发它的那条语句，堆栈里没有业务上下文；日志、监控、链路追踪通常也覆盖不到数据库内部这一层。
  • 难测试、难版本管理：触发器不在应用代码仓库的主流程里，容易被漏进发布脚本；单元测试也绕不开它，只能连真库跑。
  • 放大事务与锁：触发器在同一个事务内执行，额外写的表会把事务拉长、把锁范围扩大，死锁概率随之上升，而主语句看起来只是一次简单写入。
  • 复制风险：基于语句的复制（STATEMENT）会把原语句发到从库，让触发器在从库再执行一次。一旦其中用到 NOW()、RAND()、UUID() 这类非确定性函数，主从数据就可能不一致（生产推荐 ROW 格式正有这层原因）。触发器还带 DEFINER，主从账号权限不一致时也可能执行失败。具体行为随 binlog 格式与版本而异，以官方文档为准。
  • 能力受限：不能改触发自己的表，难以单步调试，也无法像应用代码那样方便地做灰度、回滚与单元测试。

更推荐的做法是把这些逻辑放回应用层：在同一个事务里显式写日志表，或用 ORM／AOP 统一拦截，好处是逻辑可见、可测、可回滚，还能顺手带上 traceId 之类的上下文。触发器留下的合理场景不多，主要是改不动应用代码的遗留系统，以及必须由数据库独立保证的审计与强约束。若确实要用，至少做到：只做简单、确定性、单表的事，避免跨表联锁，把定义写进版本化的迁移脚本，并在主从上验证复制行为。

小结

本章的两个关键词是层次和证据。存储引擎决定能力边界：InnoDB 用 redo 保证崩溃不丢，用 undo 支撑回滚与 MVCC，用 binlog 负责复制与恢复，两阶段提交让两本账对得上。性能问题则靠慢查询日志定位、靠 EXPLAIN 取证据，再对症改写 SQL 与索引组合。先把单机单表做到位，分库分表永远是最后一张牌。
