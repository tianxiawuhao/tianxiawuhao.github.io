MySQL 高阶

Posted on 2026-09-19，5 min read

前面的章节已经能让数据库"把结果查对"了；但真实项目里，数据库往往不是败在 SQL 语法上，而是败在"慢"和"怕丢"上：上线三个月后接口突然变慢、表涨到几千万行翻页要好几秒、机器断电后数据到底有没有落盘。本章先用慢查询日志和执行计划定位问题，再用 InnoDB 的三大日志解释为什么它既快又不容易丢数据，最后给出几类常见慢查询的改写套路。适合已会写基本 SQL、准备把数据库用进生产环境的读者。

一、慢查询日志：先找出慢在哪条 SQL

优化的第一步永远是测量，而不是凭感觉改 SQL。MySQL 自带的慢查询日志（slow query log）会把执行时间超过 long_query_time 的语句记录下来。

注意两点：long_query_time 的单位是秒（可带小数，如 0.5）；它是全局动态变量，SET GLOBAL 对已存在的连接不生效，当前连接需再执行一次 SET SESSION 或重连。最小可用配置如下：

-- 查看当前配置
SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';

-- 打开慢查询日志并指定文件（MySQL 8.0 也支持 SET GLOBAL slow_query_log = ON）
SET GLOBAL slow_query_log = ON;
SET GLOBAL slow_query_log_file = '/var/log/mysql/mysql-slow.log';

-- 只记录超过 0.5 秒的语句；设成 0 会把所有语句都写进去，磁盘很快被写满
SET GLOBAL long_query_time = 0.5;

-- 额外记录"没走索引"的语句，排查隐式全表扫描时很有用
SET GLOBAL log_queries_not_using_indexes = ON;

日志很长，别用肉眼读：轻量场景用官方自带的 mysqldumpslow，更常见的是 Percona Toolkit 的 pt-query-digest。分析时盯三个指标：Calls（执行次数，多且慢的优先）、Rows examine（扫描行数，越大 IO 越重）、以及它与 Rows sent 的比值（差距悬殊说明索引命中率低）。

二、EXPLAIN：判断索引到底有没有用上

定位到可疑 SQL 后，在它前面加 EXPLAIN 就能看到执行计划。字段虽多，日常只需看几个：

  • type：访问类型，效率大致是 system > const > eq_ref > ref > range > index > ALL。ALL 是全表扫描，出现就要警惕；index 虽走了索引，但等价于扫整棵索引树，也不理想。
  • possible_keys 与 key：前者是候选索引，后者是真正选中的。possible_keys 有值而 key 为 NULL，说明有索引却没被采用，多与列类型、函数包裹或数据分布有关。
  • key_len：实际用到的索引字节数。对组合索引 (a, b, c) 可反推用上了几列；它只统计 WHERE 用到的部分，排序与分组不计入。
  • rows：优化器估算的扫描行数（不是精确值，统计信息过期时会失真），可配合 EXPLAIN ANALYZE（MySQL 8.0.18 起）看真实执行数据。
  • Extra：信息量最大的一列。Using filesort（排序没走索引）与 Using temporary（用了临时表）同时出现通常要重点优化；Using index 表示覆盖索引、无需回表；Using index condition 表示索引条件下推（ICP）生效。
-- 在语句前加 EXPLAIN 即可，不会真正返回数据
EXPLAIN SELECT id, title FROM film WHERE release_year = 2006 ORDER BY title;

-- id 列越大越先执行；id 相同则自上而下执行；id 为 NULL 表示这是结果集（如 UNION 结果）
-- 重点关注：type、key、rows、Extra 四列

三、InnoDB 的三大日志：为什么它又快又不丢

InnoDB 把数据页缓存进缓冲池（buffer pool），读写先在内存完成。可每次提交都把脏页刷回磁盘，随机 IO 慢到无法接受；只改内存，断电又会全丢。InnoDB 的答案是"先顺序写日志，再慢慢刷数据页"，即预写日志（WAL）——这正是 redo log 的职责。

redo log 记录的是数据页的物理修改。事务提交时只保证 redo 落到磁盘，脏页由后台线程择机刷盘；数据库重启后，把 redo 里已提交但还没刷盘的改动重放一遍，数据就回来了。它是固定大小文件组成的环形结构，容量约为 innodb_log_file_size × innodb_log_files_in_group；写满后会被迫同步刷脏页，表现为性能抖动。刷盘时机由 innodb_flush_log_at_trx_commit 控制：1（默认）每次提交都刷盘；0 靠后台线程每秒刷，崩溃可能丢约 1 秒；2 只写入操作系统缓存，机器掉电才会丢。

undo log 记录修改前的旧值，承担三件事：事务回滚时恢复数据、为 MVCC 提供历史版本（让一致性读不必加锁）、崩溃恢复时回滚未提交事务。它存放在 undo 表空间，长事务会让 undo 无法及时清理，是典型隐患。

binlog 是 Server 层的归档日志，记录逻辑变更（STATEMENT 记 SQL、ROW 记行变更、MIXED 自动选择），用于主从复制与时间点恢复；sync_binlog = 1 才能保证每次提交都落盘。

存储引擎层有 redo、Server 层有 binlog，两份必须一致，否则主从会分叉，于是有了两阶段提交（2PC）：写 redo 并标记 prepare → 写 binlog 并刷盘 → 写 redo 的 commit 标记。若在第二步前崩溃，重启时事务处于 prepare 且 binlog 无对应记录则回滚，binlog 已完整写入则提交。

四、四类常见慢查询的改写套路

1. 深分页：别让 OFFSET 越翻越慢

LIMIT 100000, 10 会先取出并丢弃前 10 万行，翻得越深越慢，而且 ORDER BY 一旦用不上索引还会叠加文件排序。推荐游标分页（记住上一页最后一行，用主键过滤）：

-- 慢：每翻一页都要丢弃前面所有行
SELECT id, title FROM film ORDER BY id LIMIT 100000, 10;

-- 快：记住上一页最后一个 id，主键索引可以直接定位到起点
SELECT id, title FROM film WHERE id > 100000 ORDER BY id LIMIT 10;

-- 若必须指定页码，可先用覆盖索引只取出主键，再回表关联
SELECT f.id, f.title
FROM film f
JOIN (SELECT id FROM film ORDER BY id LIMIT 100000, 10) AS t ON f.id = t.id;

游标分页的前提是排序键唯一且稳定（通常是主键）；排序列有重复值时要加主键做二级排序（ORDER BY create_time, id），否则会漏行或重复。

2. 大表批量更新：拆小、限流、别长事务

对千万级表执行不带条件的 UPDATE，会长时间持有大量行锁、阻塞其他业务，还让 undo 与 redo 持续膨胀。正确做法是按主键分批推进：

-- 每次只改 1000 行，提交后由业务侧（或脚本）循环调用，直到影响行数为 0
UPDATE t_order
SET status = 2
WHERE status = 1
ORDER BY id
LIMIT 1000;

外部循环中每批之间留点间隔（如 SELECT SLEEP(0.05)），给主从复制和其他事务喘息时间；分批语句必须带 ORDER BY id，否则可能反复更新同一批行。

3. 子查询改 JOIN：先确认是不是一对多

很多子查询可改写成 JOIN 以获得更好的执行计划，但改写前必须确认关联关系：若是一对多（一个订单对应多条明细），JOIN 会把主表行复制多份，必须用 DISTINCT 或 EXISTS 去重，漏了就是"结果集悄悄变多"的事故。

4. COUNT 与 GROUP BY 的取舍

COUNT(*) 统计行数，COUNT(col) 只统计该列非 NULL 的行数，两者在有 NULL 时结果不同，别混用。统计多个年份的数量时，与其查两次再拼结果，不如一次 GROUP BY 让索引帮忙：

-- 推荐：一次扫描，按年份分组返回
SELECT release_year, COUNT(*) AS cnt
FROM film
WHERE release_year IN (2006, 2007)
GROUP BY release_year;

-- 不推荐：两次独立查询，还要在应用层对齐年份
SELECT COUNT(*) FROM film WHERE release_year = 2006;
SELECT COUNT(*) FROM film WHERE release_year = 2007;

另外，GROUP BY 尽量只用同一张表的列、并让分组列有索引，执行计划里就不会出现 Using temporary 和 Using filesort，大表上差距明显。

小结

本章的主线是"先量后调，再懂原理"：用慢查询日志锁定可疑 SQL，用 EXPLAIN 确认 type、key、rows、Extra 四列，避免凭直觉改 SQL；理解 redo log（崩溃恢复）、undo log（回滚与 MVCC）、binlog（复制与恢复）以及两阶段提交，才能在调参数时知道自己在拿什么换什么；深分页、批量更新、子查询改写这几类套路则可以当成检查清单直接套用。优化的收益永远集中在少数几条语句上，找到它们比盲目加索引重要得多。
