Spring Cloud 微服务

Posted on 2026-09-19，6 min read

单体应用拆成微服务之后，最先撞上的不是业务问题，而是"怎么找到对方"。订单服务要调用库存服务，库存服务有三台机器，IP 和端口随时可能变；改一个数据库连接串，要挨个服务改配置、重新打包、重启。本章围绕注册中心、配置中心、声明式调用、客户端负载均衡和容错限流这五件事，把 Spring Cloud 微服务的最小可用拼图讲清楚。适合已经能写 Spring Boot 项目、准备做服务拆分的读者。

一、为什么需要注册中心与配置中心

没有注册中心时，调用方只能把被调方地址写死在配置里，靠 Nginx 或 F5 转发。服务一多就有两个痛点：地址散落在几十份配置里，扩容一台机器要通知所有调用方；某台实例已经挂了，调用方仍然把请求发过去，只能靠超时自己发现。注册中心解决这两件事——服务启动时上报自己的地址并周期性发送心跳，调用方拉取可用实例列表并在本地缓存，实例下线或心跳超时后被剔除。配置中心则解决另一半：把配置从代码仓库搬出来集中存放、分环境管理、改完动态生效，服务重启次数大幅下降。简单说，注册中心管"人在哪"，配置中心管"怎么干活"。

二、Eureka：服务注册与发现

Eureka 分服务端（Eureka Server，即注册中心）和客户端（Eureka Client，即各微服务）。先在父工程导入 Spring Cloud 依赖管理，再在注册中心工程引入 spring-cloud-starter-netflix-eureka-server，启动类加 @EnableEurekaServer：

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>Finchley.SR1</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

注册中心的配置要点是单机模式下不要注册自己、也不拉取注册表；客户端则相反，要开启注册与发现，并给实例一个唯一 ID，避免多实例互相覆盖：

# 服务端：单机部署，自身就是注册中心
eureka:
  client:
    register-with-eureka: false
    fetch-registry: false
    service-url:
      defaultZone: http://localhost:50101/eureka/
  server:
    enable-self-preservation: false   # 开发阶段便于观察实例剔除
    eviction-interval-timer-in-ms: 60000

---
# 客户端：微服务侧配置，多个注册中心地址用逗号分隔
eureka:
  client:
    register-with-eureka: true
    fetch-registry: true
    service-url:
      defaultZone: http://localhost:50101/eureka/
  instance:
    prefer-ip-address: true
    ip-address: 127.0.0.1
    instance-id: ${spring.application.name}:${server.port}

注意配置项用 kebab-case（register-with-eureka）。老资料常见驼峰写法，Spring Boot 的宽松绑定仍能识别，但官方推荐小写加连字符。客户端默认每 30 秒心跳续约，服务端 90 秒收不到心跳即认为失效，每 60 秒执行一次剔除；当 15 分钟内心跳失败比例低于 85% 时进入自我保护模式，暂停剔除实例，防止网络抖动清空整个注册表。代价是调用方可能拿到已下线的实例，所以客户端必须配好重试或熔断。生产环境应至少部署两个 Eureka Server 并互相注册。

三、Nacos：注册中心兼配置中心

Nacos 把注册中心与配置中心合二为一，同时兼容 Dubbo 和 Spring Cloud 生态，是当前国内项目更常见的选择，支持 AP/CP 两种一致性模式与集群部署（集群一致性由 Raft 协议保证）。接入只需一个配置类 starter，且文件名必须是 bootstrap.yml：

spring:
  application:
    name: nacos-config
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848   # 注册中心地址
      config:
        server-addr: 127.0.0.1:8848   # 配置中心地址
        file-extension: yml

为什么不能用 application.yml？因为 bootstrap 的加载优先级更高：应用启动时要先拉到远端配置，才能拿到端口、数据源等信息完成后续初始化，晚了就来不及。

Nacos 里一条配置由 Namespace（环境隔离）、Group（默认 DEFAULT_GROUP）和 Data ID 共同定位，Data ID 的拼装规则是：

\[ \text{DataId} = \text{prefix} - \{profile\} . \{file\text{-}extension\} \]

prefix 默认取 spring.application.name，可用 spring.cloud.nacos.config.prefix 覆盖；profile 取 spring.profiles.active（注意是 profiles，复数）；extension 由 file-extension 指定，常用 properties 与 yaml/yml。profile 为空时中间的连字符一并消失，Data ID 退化成 prefix.file-extension，例如 nacos-config.yml；指定 profile 后变成 nacos-config-dev.yml。写错一个字符，客户端就会因拉不到配置而启动失败。读取并支持热更新，只需类上同时加 @RefreshScope：

@SpringBootApplication
@EnableDiscoveryClient
@RestController
@RefreshScope
public class NacosConfigApplication {

    public static void main(String[] args) {
        SpringApplication.run(NacosConfigApplication.class, args);
    }

    // 对应 Nacos 中 nacos-config.yml 的 nacos.config 项
    @Value("${nacos.config}")
    private String config;

    @RequestMapping("/getValue")
    public String getValue() {
        return config;
    }
}

在 Nacos 控制台修改配置后再次访问 /getValue 就能读到新值，无需重启。

四、Feign：声明式远程调用与客户端负载均衡

有了注册中心，调用方还得自己拼 URL。Spring Cloud 提供了两条路：RestTemplate 加 @LoadBalanced，或者 Feign。Ribbon 是客户端负载均衡器，从注册中心拿到实例列表后在调用方本地按算法选一台（默认轮询）；与服务端负载均衡（Nginx、F5）相比，少了一次转发。引入 Eureka 客户端依赖时会自动带上 Ribbon，给 RestTemplate 加上 @LoadBalanced 即可用服务名当主机名：

@Bean
@LoadBalanced
public RestTemplate restTemplate() {
    return new RestTemplate(new OkHttp3ClientHttpRequestFactory());
}

// 把服务名当域名来写，其余与普通调用一致
ResponseEntity<CmsPage> entity = restTemplate.getForEntity(
        "http://XC-SERVICE-MANAGE-CMS/cms/page/get/5a754adf6abb500ad05688d9",
        CmsPage.class);

Feign 更进一步，把远程调用封装成接口，底层依然整合 Ribbon 做负载均衡、整合 Hystrix 做容错。使用三步：加 spring-cloud-starter-openfeign 依赖、定义接口、启动类加 @EnableFeignClients。原理是动态代理：启动时 Spring 扫描所有 @FeignClient 接口并生成代理对象；调用方法时，代理根据方法上的 @GetMapping 等注解拼出请求地址，从注册中心选取实例后发起 HTTP 请求并解析响应。接口上可用 fallback 指定降级实现，请求失败时返回兜底值：

@FeignClient(name = "nacos-provide", fallback = RemoteHystrix.class)
public interface RemoteClient {

    @GetMapping("/helloNacos")
    String helloNacos();
}

两个容易踩的坑：方法只要带参数，就必须在 @PathVariable("id")、@RequestParam("name") 里显式写出参数名，不能像 Controller 那样省略；返回值若是自定义复杂对象，该类必须有可访问的无参构造函数，否则反序列化失败。另外老资料里的 @FeginClient 是拼写错误，正确拼写为 Feign；name 与 value 等价，指定的是注册中心里的服务名而非域名。

五、容错与限流：别让一个服务拖垮全站

服务之间互相依赖，一个下游接口变慢，上游线程就会堆积，最终整条链路雪崩。Hystrix 用舱壁模式为每个依赖服务分配独立线程池，某个依赖出问题只影响它自己；失败率达到阈值时断路器打开，直接走上面那套 fallback 降级逻辑而不再发起真实调用。Hystrix 已停止新功能开发，新项目一般直接选 Sentinel，思路一致：熔断、降级、线程隔离、实时监控。

限流放在网关层更划算：Spring Cloud Gateway 或 Zuul 统一承接外部流量，可按路由维度按 QPS 限流，把超量请求快速拒绝，避免压力穿透到后端；Zuul 的过滤器机制还能顺带做鉴权和日志。无论选哪套，都要记住一条原则——调用方永远不能假设被调方一定活着，超时时间、重试次数与降级返回值必须显式配置，默认值通常不适合线上。

小结

本章串起 Spring Cloud 微服务的五块拼图：注册中心（Eureka / Nacos）解决"服务在哪"，配置中心（Nacos Config + bootstrap.yml + @RefreshScope）解决配置集中管理与热更新，Feign 用动态代理把远程调用写成接口，Ribbon / Spring Cloud LoadBalancer 在调用方本地做负载均衡，Hystrix / Sentinel 用熔断降级与限流防止故障蔓延。落地时记住三条：服务名与 Data ID 必须与配置严格一致；配置项统一用 kebab-case；生产环境至少把注册中心与网关做成高可用，并为每一次跨服务调用设置超时和降级。
