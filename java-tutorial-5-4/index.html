设计模式：创建型

Posted on 2026-09-19，7 min read

写业务代码时，我们大部分时间都在new对象：new ArrayList<>()、new HashMap<>()、new User()。可一旦对象的构造过程变复杂——要读配置、要连数据库、要保证全局只有一个、要按固定顺序装配十几个字段——把new散落在业务代码里就会变成灾难：改一处构造逻辑要翻遍全项目，测试时又没法替换实现。GoF 的 23 种设计模式中，专门解决"对象从哪来、怎么造"的那一类叫创建型模式，共五种：工厂方法、抽象工厂、单例、建造者、原型。本文面向已经会写 Java 类与接口、但还没系统接触设计模式的读者，用最小可运行示例讲清它们的意图、写法与常见坑，读完你应该能判断"这段代码该不该上模式"。

单例模式：保证一个类只有一个实例

单例的意图是"保证一个类仅有一个实例，并提供一个访问它的全局访问点"，典型场景是配置中心、连接池、缓存、序列号生成器。实现只有三个要素：构造方法私有化（外部无法new）、类内部自己持有唯一实例（用private static字段）、暴露一个静态方法返回该实例。

写法上有一条演进路线，值得按顺序理解：饿汉式在类加载时就创建，简单且线程安全；懒汉式延迟创建，但"先判断再创建"不是原子操作，多线程下会造出两个对象；给getInstance()整个加synchronized虽然安全，却让每次读取都要抢锁；双重检查锁定（DCL）把锁缩小到创建那一刻，但实例字段必须用volatile修饰——否则指令重排可能让另一个线程拿到"引用已赋值、构造却未完成"的半成品对象，这一点在 Java 5 修正内存模型之后才真正成立。生产代码里更推荐下面两种免锁写法。

// 写法一：静态内部类（延迟加载 + 由 JVM 保证线程安全）
public final class ConfigHolder {
    private ConfigHolder() {}

    private static class Holder {
        private static final ConfigHolder INSTANCE = new ConfigHolder();
    }

    public static ConfigHolder getInstance() {
        return Holder.INSTANCE;
    }
}

// 写法二：枚举（《Effective Java》推荐，天然防反射与反序列化破坏）
public enum ConfigEnum {
    INSTANCE;

    public String get(String key) {
        return System.getProperty(key);
    }
}

常见坑有三个：反射可以强行调用私有构造方法，需要在构造方法里加"已初始化就抛异常"的守卫；实现Serializable后反序列化会生成新对象，必须补一个readResolve()返回INSTANCE（枚举天然免疫）；分布式或多类加载器环境下，"单例"只在单个 JVM/类加载器内成立，跨进程要靠外部存储。另外不要把所有工具类都做成单例，无状态的方法用静态方法即可。

工厂模式家族：把创建逻辑从调用方剥离

工厂模式的核心是"创建对象时不向客户端暴露创建逻辑，而是通过一个共同的接口指向新对象"。它有三种常见形态，抽象程度依次升高：

简单工厂（也叫静态工厂方法）用一个具体工厂类加if/switch决定造哪个产品，调用方只传类型标识；它不是 GoF 的独立模式，通常被看作工厂方法的一种特例。工厂方法把每个产品的创建延迟到各自的工厂子类，新增产品只需新增一对类，符合开闭原则。抽象工厂面向"产品族"：一个工厂接口负责创建一系列相关对象（比如同一套皮肤下的按钮和文本框），保证客户端始终只使用同一族产品，但新增一种产品就要改动所有工厂实现。Java 标准库里的Executors.newFixedThreadPool()、Calendar.getInstance()、NumberFormat.getInstance()都属于工厂方法的实际应用。

public interface Logger {
    void log(String message);
}

public class ConsoleLogger implements Logger {
    @Override public void log(String message) {
        System.out.println("[console] " + message);
    }
}

public class FileLogger implements Logger {
    private final String path;
    public FileLogger(String path) { this.path = path; }
    @Override public void log(String message) {
        // 省略真实写文件逻辑，便于示例编译运行
        System.out.println("[file:" + path + "] " + message);
    }
}

// 简单工厂：调用方不关心构造细节
public final class LoggerFactory {
    private LoggerFactory() {}

    public static Logger create(String type) {
        if ("file".equalsIgnoreCase(type)) {
            return new FileLogger("app.log");
        }
        if ("console".equalsIgnoreCase(type)) {
            return new ConsoleLogger();
        }
        throw new IllegalArgumentException("不支持的日志类型: " + type);
    }
}

坑在于不要把工厂做成"万能上帝类"：产品种类少、创建逻辑只有一行new时，直接new或写一个静态工厂方法就够了，硬套模式只会让类数量成倍增加。另外简单工厂里的字符串标识最好用枚举替代，避免拼写错误在运行期才暴露。

建造者模式：分步装配复杂对象

当一个对象的构造参数很多、其中一部分可选、或者各个部件必须按固定顺序组装时，构造函数会退化成"一长串参数列表"，调用方根本记不住第 4 个参数是true还是false。建造者模式把"构建过程"与"最终表示"分离：建造者负责一步步提供部件，导演（可选）负责决定装配顺序，最后build()产出完整对象。它的关键差别在于——工厂关心"创建哪一个产品"，建造者关心"怎样一步步拼装这个产品"。

public final class HttpRequest {
    private final String url;
    private final String method;
    private final int timeoutMs;
    private final boolean retry;

    private HttpRequest(Builder builder) {
        this.url = builder.url;
        this.method = builder.method;
        this.timeoutMs = builder.timeoutMs;
        this.retry = builder.retry;
    }

    public static class Builder {
        private final String url;          // 必填项放构造方法
        private String method = "GET";     // 可选项给默认值
        private int timeoutMs = 3000;
        private boolean retry = false;

        public Builder(String url) { this.url = url; }

        public Builder method(String method) { this.method = method; return this; }
        public Builder timeoutMs(int timeoutMs) { this.timeoutMs = timeoutMs; return this; }
        public Builder retry(boolean retry) { this.retry = retry; return this; }

        public HttpRequest build() {
            if (timeoutMs <= 0) {
                throw new IllegalStateException("超时时间必须为正数");
            }
            return new HttpRequest(this);
        }
    }

    public static void main(String[] args) {
        HttpRequest request = new HttpRequest.Builder("https://example.com")
                .method("POST")
                .timeoutMs(5000)
                .build();
        System.out.println(request.url + " " + request.method + " " + request.timeoutMs);
    }
}

链式调用返回this，让代码接近自然语言，也不必记住参数顺序。StringBuilder是常被引用的例子，它通过append()逐步累积再toString()，思想一致，只是产物是字符串而非领域对象。坑有两处：一是build()里必须做参数校验，否则非法状态会被带进对象；二是当对象只有两三个字段时，建造者带来的 Builder 内部类纯属噪音，直接用构造方法或静态工厂更清晰。Lombok 的@Builder能自动生成这套代码，但它会顺带把构造方法私有化，需要配合@AllArgsConstructor等一起考虑。

原型模式：用拷贝代替重复创建

原型模式"用原型实例指定创建对象的种类，并通过拷贝这些原型创建新对象"。当对象创建代价高昂（一次高成本查询、复杂计算）或需要大量相似对象时，先准备好原型再克隆，比每次重新new并赋同样的值更快、也更省代码。Java 的实现方式是实现Cloneable接口并重写Object.clone()。

import java.util.ArrayList;
import java.util.List;

public class Report implements Cloneable {
    private String title;
    private List<String> rows = new ArrayList<>();

    public Report(String title) { this.title = title; }

    public void addRow(String row) { rows.add(row); }

    @Override
    public Report clone() {
        try {
            Report copy = (Report) super.clone();      // 浅拷贝：rows 仍指向同一个 List
            copy.rows = new ArrayList<>(this.rows);    // 手动深拷贝引用字段
            return copy;
        } catch (CloneNotSupportedException e) {
            throw new AssertionError("实现了 Cloneable 不该走到这里", e);
        }
    }

    public static void main(String[] args) {
        Report prototype = new Report("月报");
        prototype.addRow("一月");

        Report copy = prototype.clone();
        copy.addRow("二月");                            // 不影响原型
        System.out.println(prototype.rows.size());      // 输出 1
    }
}

坑集中在"拷贝深度"上：super.clone()是浅拷贝，只复制字段的值，引用类型字段仍指向同一个对象，忘记手动复制就会让"副本"的修改串到原型上，这类 Bug 极难排查，集合与数组最容易中招（数组的clone()同样是浅拷贝元素引用）。此外有两个语义陷阱：clone()不调用构造方法，跳过构造就意味着绕过校验逻辑，final字段也无法被重新赋值，所以不可变类、含不变式校验的类不适合走这条路；Object.clone()是protected的，不重写为public就无法跨包调用。实践中更推荐"拷贝构造方法"（new Report(other)）或静态工厂Report.copyOf(other)，语义明确、不受Cloneable束缚；需要真正深拷贝时才考虑序列化或 JSON 往返。

选型建议与常见坑

选型可以按问题倒推：要控制实例数量，用单例；要把"造什么"和使用者解耦，用工厂；要解决"一堆可选参数 + 固定装配顺序"，用建造者；创建代价高且需要大量相似副本，用原型。五个模式并非互斥，框架代码中经常组合出现，例如工厂内部返回单例、建造者的产物由工厂创建。几条通用经验：不要为了模式而模式，先能读懂、再谈解耦；模式解决的是变化点，如果一段逻辑永远不会变，抽象就是纯粹的负担；所有创建型模式都会增加类的数量，因此必须在文档里写清"为什么需要"，否则后来者只会觉得代码绕。

小结：创建型模式回答的是"对象怎么来"。单例用私有构造加静态访问点守住唯一性，推荐静态内部类或枚举写法；工厂把创建逻辑收拢到一处，简单工厂够用时不必上抽象工厂；建造者用链式调用收拾臃肿的构造函数，代价是多一个内部类；原型用拷贝换取性能，但必须想清楚拷贝深度、构造绕过与Cloneable的语义限制。把这四个判断标准记住，再回头看框架源码，你会发现大多数"看不懂的类结构"都能对号入座。
