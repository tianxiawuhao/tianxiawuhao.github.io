Posted on 2023-04-10，25 min read

七、数据类型

PGSQL 支持的类型非常丰富，大多数类型都能在 MySQL 中找到对应关系。

名称 说明 对比MySQL
布尔类型 boolean，标准的布尔类型，只能存储true，false MySQL中虽然没有对应的boolean，但是有替换的类型，数值的tinyint类型，和PGSQL的boolean都是占1个字节。
整型 smallint（2字节），integer（4字节），bigint（8字节） 跟MySQL没啥区别。
浮点型 decimal，numeric（和decimal一样一样的，精准浮点型），real（float），double precision（double），money（货币类型） 和MySQL基本也没区别，MySQL支持float，double，decimal。MySQL没有这个货币类型。
字符串类型 varchar(n)（character varying），char(n)（character），text 这里和MySQL基本没区别。PGSQL存储的varchar类型，可以存储一个G。MySQL好像存储64kb（应该是）。
日期类型 date（年月日），time（时分秒），timestamp（年月日时分秒）（time和timestamp可以设置时区） 没啥说的，和MySQL基本没区别。MySQL有个datetime。
二进制类型 bytea-存储二进制类型 MySQL也支持，MySQL中是blob
位图类型 bit(n)（定长位图），bit varying(n)（可变长度位图） 就是存储0，1。MySQL也有，只是这个类型用的不多。
枚举类型 enum，跟Java的enum一样 MySQL也支持。
几何类型 点，直线，线段，圆………… MySQL没有，但是一般开发也用不到
数组类型 在类型后，追加[]，代表存储数组 MySQL没有~~~
JSON类型 json（存储JSON数据的文本），jsonb（存储JSON二进制） 可以存储JSON，MySQL8.x也支持
ip类型 cidr（存储ip地址） MySQL也不支持~

八、PostgreSQL基本操作&数据类型

8.1 单引号和双引号

在PGSQL中，写SQL语句时，单引号用来标识实际的值。双引号用来标识一个关键字，比如表名，字段名。

-- 单引号写具体的值，双引号类似MySQL的``标记，用来填充关键字
-- 下面的葡萄牙会报错，因为葡萄牙不是关键字
select 1.414,'卡塔尔',"葡萄牙";

8.2 数据类型转换

第一种方式：只需要在值的前面，添加上具体的数据类型即可

-- 将字符串转成位图类型
select bit '010101010101001';

第二种方式：也可以在具体值的后面，添加上 ::类型 ，来指定

-- 数据类型
select '2011-11-11'::date;
select '101010101001'::bit(20);
select '13'::int;

第三种方式：使用CAST函数

-- 类型转换的完整写法
select CAST(varchar '100' as int);

8.3 布尔类型

布尔类型很简单，可以存储三个值：true、false、null。

-- 布尔类型的约束没有那么强，true，false大小写随意，他会给你转，同时yes，no这种他也认识，但是需要转换
select true,false,'yes'::boolean,boolean 'no',True,FaLse,NULL::boolean;

boolean 类型在做 AND/OR 逻辑操作时的结果如下：

字段A 字段B a and b a or b
true true true true
true false false true
true NULL NULL true
false false false false
false NULL false NULL

8.4 数值类型

8.4.1 整型

整型比较简单，主要就是三个：

  • smallint、int2：2字节

  • integer、int、int4：4字节

  • bigint、int8：8字节

一般情况下用 integer 即可；如果要存主键（比如雪花算法生成的长整型），就用 bigint；想节约空间，可根据情况选用 smallint。

8.4.2 浮点型

浮点类型主要关注两个（其实本质是一个）：

  • decimal(n,m)：本质就是numeric，PGSQL会帮你转换

  • numeric(n,m)：PGSQL本质的浮点类型

针对浮点类型的数据，就使用 numeric

8.4.3 序列

MySQL 的主键自增基于 auto_increment 实现，MySQL 中并没有序列对象。

PGSQL和Oracle十分相似，支持序列：sequence。

PGSQL可没有auto_increment。

序列的正常构建方式：

create sequence laozheng.table_id_seq;
-- 查询下一个值
select nextval('laozheng.table_id_seq');
-- 查询当前值
select currval('laozheng.table_id_seq');

默认情况下，sequence 的起始值是 1，每次调用 nextval 递增 1，最大值可达 9223372036854775807。

如果插入的数据比较多，可以指定 CACHE 大小：一次性预计算 20 个后续值，调用 nextval 时直接从缓存取值、无需重复计算，效率会有一点点提升。

序列大多数的应用，是用作表的主键自增效果。

-- 表自增
create table laozheng.xxx(
    id int8 default nextval('laozheng.table_id_seq'),
    name varchar(16)
);
insert into laozheng.xxx (name) values ('xxx');
select * from laozheng.xxx;

上面的写法没有问题，但用起来比较麻烦。

PGSQL 提供了 serial 这类序列相关类型，可以在声明表结构时直接指定，从而方便地实现自增主键。

bigserial相当于给bigint类型设置了序列实现自增。

  • smallserial

  • serial

  • bigserial

-- 表自增（爽）
create table laozheng.yyy(
    id bigserial,   
    name varchar(16)
);
insert into laozheng.yyy (name) values ('yyy');

在drop表之后，序列不会被删除，但是序列会变为不可用的状态。
因为序列在使用serial去构建时，会绑定到指定表的指定列上。

如果是单独构建序列，再构建表，使用传统方式实现，序列和表就是相对独立的。

8.5 字符串类型

字符串类型用的是最多的一种，在PGSQL里，主要支持三种：

  • character（就是MySQL的char类型），定长字符串。（最大可以存储1G）

  • character varying（varchar），可变长度的字符串。（最大可以存储1G）

  • text：长度不受限制的超长字符串（PostgreSQL 中最大 1GB）。

操作没什么说的，但是字符串常见的函数特别多。

字符串拼接一定要使用 || 操作符。

其他的函数，可以查看 http://www.postgres.cn/docs/12/functions-string.html

8.6 日期类型

在PGSQL中，核心的时间类型，就三个。

  • timestamp（时间戳，覆盖 年月日时分秒）

  • date（年月日）

  • time（时分秒）

在PGSQL中，声明时间的方式。

只需要使用字符串正常的编写 yyyy-MM-dd HH:mm:ss 就可以转换为时间类型。

直接在字符串位置使用之前讲到的数据类型转换就可以了。

当前系统时间 ：

  • 可以使用 now() 获取当前系统时间

    select timestamp 'now';
-- 直接查询now，没有时区的概念
select time with time zone 'now' at time zone '08:00:00'

  • 也可以使用 current_timestamp 获取（与 now() 等价，推荐使用）

日期类型的运算

  • date 类型直接做 +、- 运算时，默认单位是天。

  • date + time = timestamp

    select date '2011-11-11' + time '12:12:12' ;

  • 可以针对timestamp使用interval的方式进行 +，-操作，在查询以时间范围为条件的内容时，可以使用

    select timestamp '2011-11-11 12:12:12' + interval '1day' + interval '1minute' + interval '1month';

8.7 枚举类型

枚举类型 MySQL 其实也支持，只是用得少；PGSQL 同样支持。

可以把枚举声明为表的字段类型，从而给字段加上很强的约束。

-- 声明一个星期的枚举，值自然只有周一~周日。
create type week as enum ('Mon','Tues','Sun');
-- 声明一张表，表中的某个字段的类型是上面声明的枚举。
drop table test;
create table test(
    id bigserial ,
    weekday week
);
insert into test (weekday) values ('Mon');
insert into test (weekday) values ('Fri');

8.9 JSON&JSONB类型

MySQL 8.x 也支持 JSON，但支持得不够好：查询时基本无法为 JSON 字段建索引。

PGSQL支持JSON类型以及JSONB类型。

JSON和JSONB的使用基本没区别。

抛开 JSON 类型不谈，JSON 本质上就是一个字符串；比如在 MySQL 5.7 不支持 JSON 的情况下可以用 text，但字符串类型无法校验 JSON 格式，也没办法只取某个 key 对应的 value。

JSON和JSONB的区别：

  • JSON类型无法构建索引，JSONB类型可以创建索引。

  • JSON类型的数据中多余的空格会被存储下来。JSONB会自动取消多余的空格。

  • JSON类型甚至可以存储重复的key，以最后一个为准。JSONB不会保留多余的重复key（保留最后一个）。

  • JSON会保留存储时key的顺序，JSONB不会保留原有顺序。

JSON中key对应的value的数据类型

JSON PGSQL
String text
number numeric
boolean boolean
null (none) 
[
  {"name": "张三"},
  {"name": {
      "info": "xxx"
    }}

]

操作JSON：

上述的四种JSON存储的类型：

select '9'::JSON,'null'::JSON,'"laozheng"'::JSON,'true'::json;
select '9'::JSONB,'null'::JSONB,'"laozheng"'::JSONB,'true'::JSONB;

JSON数组

select '[9,true,null,"我是字符串"]'::JSON;

JSON对象

select '{"name": "张三","age": 23,"birthday": "2011-11-11","gender": null}'::json;
select '{"name": "张三","age": 23,"birthday": "2011-11-11","gender": null}'::jsonb;

构建表存储JSON

create table test(
    id bigserial,
    info json,
    infob jsonb
);
insert into
  test
(info,infob)   
  values 
('{"name":            "张三"              ,"age": 23,"birthday": "2011-11-11","gender": null}',
'{"name":               "张三"             ,"age": 23,"birthday": "2011-11-11","gender": null}')
select * from test;


构建索引的效果

create index json_index on test(info);
create index jsonb_index on test(infob);

JSON还支持很多函数。可以直接查看 http://www.postgres.cn/docs/12/functions-json.html 函数太多了，不分析了。

8.10 复合类型

复合类型就好比 Java 中的对象：比如 User 与表做映射，User 中还有个人信息对象，就可以用复合类型来映射这部分个人信息。

public class User{
   private Integer id;
   private Info info;
}

class Info{
   private String name;
   private Integer age;
}

按照上面的情况，将Info构建成一个复合类型

-- 构建复合类型，映射上Info
create type info_type as (name varchar(32),age int);
-- 构建表，映射User
create table tb_user(
    id serial,
    info info_type
);
-- 添加数据
insert into tb_user (info) values (('张三',23));
insert into tb_user (info) values (('露丝',233));
insert into tb_user (info) values (('jack',33));
insert into tb_user (info) values (('李四',24));
select * from tb_user;

8.11 数组类型

数组还是要依赖其他类型，比如在设置住址，住址可能有多个住址，可以采用数组类型去修饰字符串。

PGSQL中，指定数组的方式就是[]，可以指定一维数组，也支持二维甚至更多维数组。

构建数组的方式：

drop table test;
create table test(
    id serial,
    col1 int[],
    col2 int[2],
    col3 int[][]
);
-- 构建表指定数组长度后，并不是说数组内容只有2的长度，可以插入更多数据
-- 甚至在你插入数据，如果将二维数组结构的数组扔到一维数组上，也可以存储。
-- 数组编写方式
select '{{how,are},{are,you}}'::varchar[];
select array[[1,2],[3,4]];
insert into test (col1,col2,col3) values ('{1,2,3}','{4,5,6}','{7,8,9}');
insert into test (col1,col2,col3) values ('{1,2,3}','{4,5,6}',array[[1,2],[3,4]]);
insert into test (col1,col2,col3) values ('{1,2,3}','{4,5,6}','{{1,2},{3,4}}');
select * from test;

如果要存储字符串数组，而数组内容中带有双引号或大括号时怎么办？

-- 如果存储的数组中的值，有单引号怎么办？
-- 使用两个单引号，作为一个单引号使用
select '{''how''}'::varchar[];
-- 如果存储的数组中的值，有逗号怎么办？(PGSQL中的数组索引从1开始算，写0也是从1开始算。)
-- 用双引号将数组的数据包起来~
select ('{"how,are"}'::varchar[])[2];
-- 如果存储的数组中的值，有双引号怎么办？
-- 如果要添加双引号，记得转义。
select ('{"\"how\",are"}'::varchar[])[1];

数组的比较方式

-- 包含
select array[1,2] @> array[1];
-- 被包含
select array[1,2] <@ array[1,2,4];
-- 是否有相同元素
select array[2,4,4,45,1] && array[1];

8.12 JSON 与 JSONB 的常用操作

JSONB 把 JSON 解析成二进制结构并去掉多余空格、重复 key，因此能建立索引、也能用操作符直接按 key 取值；JSON 只是原样保存文本。正因为如此，实际项目里几乎都用 JSONB。

先看四种基本结构在 JSON 中的映射关系：

-- 字符串、null、布尔、数字都是合法的 json 值
select '9'::json, 'null'::json, '"laozheng"'::json, 'true'::json;
-- 同样的字面量转成 jsonb，语义一致
select '9'::jsonb, 'null'::jsonb, '"laozheng"'::jsonb, 'true'::jsonb;
-- 数组
select '[9,true,null,"我是字符串"]'::jsonb;
-- 对象
select '{"name": "张三","age": 23,"gender": null}'::jsonb;

建一张同时保存 json 与 jsonb 的表，对比查询写法：

drop table if exists tb_json_test;
create table tb_json_test(
    id bigserial primary key,
    info json,
    infob jsonb
);
insert into tb_json_test (info, infob) values (
    '{"name":   "张三",  "age": 23, "tags": ["a","b"], "gender": null}',
    '{"name":   "张三",  "age": 23, "tags": ["a","b"], "gender": null}'
);
-- json 按文本原样保存，jsonb 会去掉多余空格
select info, infob from tb_json_test;

-- -> 取出的是 json/jsonb，->> 取出的是 text
select infob -> 'name' as j_name,
       infob ->> 'name' as t_name
from tb_json_test;
-- #> / #>> 按路径取嵌套值
select infob #>> '{tags,0}' as first_tag from tb_json_test;
-- 判断顶层是否包含指定键值对
select * from tb_json_test where infob @> '{"age": 23}';
-- 查询某个键是否存在：? 针对字符串，?| 任一存在，?& 全部存在
select * from tb_json_test where infob ? 'tags';
select * from tb_json_test where infob ?| array['tags','gender'];
-- 修改与删除键
update tb_json_test set infob = infob || '{"city":"杭州"}'::jsonb where id = 1;
update tb_json_test set infob = infob - 'gender' where id = 1;
select infob from tb_json_test;

JSONB 的索引需要 GIN：数组包含、键存在（@>、? ）这类操作符才能走索引；而 info 这种 json 类型只能建 B-tree 且基本用不上，这也是强调"JSON 无法建索引"的原因。

-- json 列只能建普通索引，实际查询很难命中
create index idx_json_test_info on tb_json_test(info);
-- jsonb 列建 GIN 索引，@>、?、?|、?& 都能用上
create index idx_json_test_infob on tb_json_test using gin(infob);
explain select * from tb_json_test where infob @> '{"age": 23}';

如果只想按某个固定 key 的取值查询，也可以给该表达式单独建 B-tree 索引：

-- 只针对 name 这个键建表达式索引，等值/范围查询都能命中
create index idx_json_test_infob_name on tb_json_test((infob ->> 'name'));
explain select * from tb_json_test where infob ->> 'name' = '张三';

8.13 范围类型与 UUID 类型

范围类型（range）用来表达"一段区间"，比如会议时间段、票价区间、IP 段。内置的有 int4range、int8range、numrange、tsrange、tstzrange、daterange，区间的开闭用 []、() 表示。

-- 左闭右开：包含下界、不包含上界
select '[1,10)'::int4range;
-- 判断元素或区间是否被包含
select '[1,10)'::int4range @> 5;
select '[1,10)'::int4range @> '[2,3]'::int4range;
-- 区间是否重叠
select '[1,10)'::int4range && '[5,20)'::int4range;
-- 交集、并集、差集
select '[1,10)'::int4range * '[5,20)'::int4range;
select '[1,10)'::int4range + '[10,20)'::int4range;
-- 上下界
select lower('[1,10)'::int4range), upper('[1,10)'::int4range);

-- 日程表：同一间会议室的时间段不允许重叠，可用排他约束兜底
drop table if exists booking;
create table booking(
    id bigserial primary key,
    room_id int not null,
    period tsrange not null,
    exclude using gist (room_id with =, period with &&)
);
insert into booking (room_id, period)
values (1, '[2024-01-01 09:00, 2024-01-01 10:00)');
-- 与上一条时间段重叠，会被排他约束拒绝
insert into booking (room_id, period)
values (1, '[2024-01-01 09:30, 2024-01-01 11:00)');
-- 查询与指定时间有交集的预订
select * from booking where period && '[2024-01-01 09:15, 2024-01-01 09:45)'::tsrange;

UUID 类型占 16 字节，比用 varchar(36) 存字符串更省空间、比较也更快。如果只用 UUID 做唯一标识、并不要求随机分布，更推荐用 gen_random_uuid()；PostgreSQL 13 起该函数已内置在核心中，更早的版本需要执行 create extension if not exists "uuid-ossp"; 后使用 uuid_generate_v4()。

create table tb_uuid(
    id uuid primary key default gen_random_uuid(),
    name varchar(32)
);
insert into tb_uuid (name) values ('张三'), ('李四');
select * from tb_uuid;
-- uuid 之间可以直接比较大小、参与排序
select * from tb_uuid order by id;

UUID 的取值是随机的，作为主键时写入位置分散，容易造成 B-tree 页分裂和索引膨胀，所以在写入量大的表上，更常见的做法是"自增 bigint 做聚簇主键 + 额外一列 uuid 做业务唯一标识"。

9.2 触发器

触发器（Trigger）是由事件触发的一种存储过程

当对表执行 insert、update、delete、truncate 操作时，会触发对应的 Trigger（具体看创建触发器时指定的事件）

构建两张表，学生信息表，学生分数表。

在删除学生信息的同时，自动删除学生的分数。

先构建表信息，填充数据

create table student(
    id int,

    ON table_name
    [ FROM referenced_table_name ]
    [ NOT DEFERRABLE | [ DEFERRABLE ] [ INITIALLY IMMEDIATE | INITIALLY DEFERRED ] ]
    [ REFERENCING { { OLD | NEW } TABLE [ AS ] transition_relation_name } [ ... ] ]
    [ FOR [ EACH ] { ROW | STATEMENT } ]
    [ WHEN ( condition ) ]
    EXECUTE { FUNCTION | PROCEDURE } function_name ( arguments )

where event can be one of:

    INSERT
    UPDATE [ OF column_name [, ... ] ]
    DELETE
    TRUNCATE

9.6 物化视图

前面说过普通视图，本质就是一个SQL语句，普通视图并不会在本地磁盘存储任何物理数据。

每次查询视图都是执行这个SQL。效率有点问题。

物化视图从名字上就可以看出来，必然是要持久化一份数据的。使用套路和视图基本一致。这样一来查询物化视图，就相当于查询一张单独的表。相比之前的普通视图，物化视图就不需要每次都查询复杂SQL，每次查询的都是真实的物理存储地址中的一份数据（表）。

物化视图因为会持久化到本地，完全脱离原来的表结构。

而且物化视图是可以单独设置索引等信息来提升物化视图的查询效率。

但有好处就有坏处：更新时间不太好把控——更新频繁会对数据库造成不小压力，更新不频繁又会导致数据延迟、实时性变差。

如果要更新物化视图，可以采用触发器的形式，当原表中的数据被写后，可以通过触发器执行同步物化视图的操作。或者就基于定时任务去完成物化视图的数据同步。

下面看一下语法。

干活！

-- 构建物化视图
create materialized view mv_test as (select id,name,price from test);
-- 操作物化视图与操作表的方式没什么区别。
select * from mv_test;
-- 操作原表时，对物化视图没有任何影响
insert into test values (4,'月饼',50,10);
-- 直接写入物化视图（不允许）会报错
insert into mv_test values (5,'大阅兵',66);

物化视图如何从原表同步数据呢？

PostgreSQL 对物化视图提供全量刷新（REFRESH）与并发刷新（REFRESH ... CONCURRENTLY）两种方式。

全量刷新语法没有额外限制，直接执行即可：

-- 查询物化视图当前数据
select * from mv_test;
-- 全量刷新物化视图
refresh materialized view mv_test;
-- 再次查询物化视图数据
select * from mv_test;

并发刷新需要物化视图上有唯一索引，用于识别数据行；刷新期间不阻塞对原表的查询。

-- 查询物化视图当前数据
select * from mv_test;
-- 并发刷新：物化视图还没有唯一索引，因此这里会报错
refresh materialized view concurrently mv_test;
-- 给物化视图添加唯一索引。
create unique index index_mv_test on mv_test(id);
-- 添加唯一索引后再次并发刷新
refresh materialized view concurrently mv_test;
-- 再次查询物化视图数据
select * from mv_test;
-- 并发刷新期间不阻塞查询；修改原表后再次刷新即可看到最新数据

update test set name = '汤圆' where id = 5;
insert into test values (5,'猪头肉',99,40);
select * from test;

十三、索引类型与执行计划

13.1 B-tree 索引、部分索引与表达式索引

B-tree 是 PostgreSQL 的默认索引，适用面最广：等值比较、范围比较、排序以及唯一约束都靠它完成。索引在磁盘上是一棵平衡的多路搜索树，查找复杂度是 O(log n)（对数级别），所以即使表有上亿行，定位一条记录也只需要读取几层页面。

在使用 B-tree 之前，先要理解哪些写法会让索引失效，这比背语法更重要。

drop table if exists tb_account;
create table tb_account(
    id bigserial primary key,
    username varchar(64) not null,
    age int not null,
    city varchar(32),
    status varchar(16) not null default 'active',
    balance numeric(12,2) not null default 0,
    created_at timestamp not null default current_timestamp
);
insert into tb_account (username, age, city, status, balance)
select 'user_' || g, 20 + (g % 30), '城市' || (g % 10), 'active', g * 1.5
from generate_series(1, 100000) as g;
analyze tb_account;

-- 唯一索引：可以承担唯一约束的职责
create unique index uk_tb_account_username on tb_account(username);
-- 普通索引
create index idx_tb_account_age on tb_account(age);

-- 能命中索引：列上直接做等值比较
explain select * from tb_account where age = 30;
-- 能命中索引：范围查询
explain select * from tb_account where age between 30 and 40;
-- 无法命中索引：列被函数包裹，idx_tb_account_age 用不上
explain select * from tb_account where age + 1 = 31;
-- 无法命中索引：隐式类型转换，age 被转成 text 比较
explain select * from tb_account where age::text = '30';
-- 无法命中索引：like 以通配符开头
explain select * from tb_account where username like '%user_1%';
-- 索引失效时，把条件改写成对列本身的操作即可
explain select * from tb_account where age = 30;

如果某条查询的过滤条件长期固定，可以只把满足条件的行放进索引，这样的索引叫部分索引（partial index），体积更小、维护代价更低。反过来，如果查询条件本身就是对列做计算，可以把这个表达式做成表达式索引。

-- 部分索引：只索引未删除的订单；where 条件必须与查询中的条件匹配才会被使用
drop table if exists tb_order;
create table tb_order(
    id bigserial primary key,
    user_id int not null,
    amount numeric(12,2) not null,
    is_delete boolean not null default false,
    created_at timestamp not null default current_timestamp
);
create index idx_tb_order_alive on tb_order(user_id) where is_delete = false;
explain select * from tb_order where user_id = 10 and is_delete = false;

-- 表达式索引：建的时候要写两遍括号，查询写法必须与索引表达式完全一致
create index idx_tb_order_month on tb_order((date_trunc('month', created_at)));
explain select * from tb_order where date_trunc('month', created_at) = date '2024-01-01';

-- 索引并非越多越好：每个索引都会占空间，并拖慢 insert/update/delete
select pg_size_pretty(pg_relation_size('idx_tb_account_age')) as index_size;
-- 找出长期未被使用的索引（需要先开启统计收集）
select relname, indexrelname, idx_scan
from pg_stat_user_indexes
where idx_scan = 0
order by relname;

13.2 GIN、GiST、BRIN 与索引选型

PostgreSQL 内置的索引方法各有分工，选错方法等于没建索引。

drop table if exists tb_article;
create table tb_article(
    id bigserial primary key,
    title varchar(128) not null,
    tags text[] not null,
    content text not null,
    price_range numrange,
    created_at timestamp not null default current_timestamp
);
insert into tb_article (title, tags, content, price_range)
values ('PostgreSQL 索引', array['pg','index','gin'],
        'PostgreSQL 支持多种索引方法', '[1,100)');

-- GIN：为数组、jsonb、全文检索这类"一个字段多个值"的类型准备
create index idx_tb_article_tags on tb_article using gin(tags);
explain select * from tb_article where tags @> array['pg'];
-- GIN 也能加速全文检索
create index idx_tb_article_content on tb_article
    using gin(to_tsvector('simple', content));
explain select * from tb_article
    where to_tsvector('simple', content) @@ to_tsquery('simple', 'PostgreSQL');

-- GiST：几何、范围、以及需要排他约束的场景
create index idx_tb_article_price on tb_article using gist(price_range);
explain select * from tb_article where price_range && '[50,60)'::numrange;

-- BRIN：只记录每个数据块的取值范围，体积非常小
-- 只有当数据在物理上大致按该列有序时才有效（例如按时间顺序写入的日志表）
create index idx_tb_article_created_brin on tb_article using brin(created_at);
-- Hash：只支持等值查询，通常被 B-tree 覆盖，实际很少使用
create index idx_tb_article_title_hash on tb_article using hash(title);

选型可以按下面的顺序判断。

  • 等值、范围、排序、唯一约束：直接用默认的 B-tree。
  • 字段里存的是数组、jsonb，或用全文检索：用 GIN。
  • 几何类型、范围类型，或需要"区间不重叠"这类排他约束：用 GiST。
  • 超大表且数据天然按某列递增（时间、自增 ID）：用 BRIN，索引体积可能只有 B-tree 的百分之几。
  • 只有等值查询、且值分布离散：才考虑 Hash。

13.3 用 EXPLAIN 看懂执行计划

索引建好了，但到底用没用上，要靠执行计划确认。explain 只输出估算结果，explain analyze 会真正执行并给出实际耗时与行数；explain (analyze, buffers) 还能看到读了多少数据块。

explain (analyze, buffers, costs off)
select * from tb_account where age = 30;

-- 常见的扫描节点，效率由高到低大致为：
-- Index Only Scan 仅索引扫描：查询列都在索引里，不用回表
-- Index Scan      索引扫描：先在索引定位，再回表取数据
-- Bitmap Index Scan + Bitmap Heap Scan：先收集候选行号再批量回表
-- Seq Scan        全表扫描：没有可用索引，或优化器认为走索引更慢
-- 两个重要指标：
--   rows：优化器"估算"的行数；如果与实际行数相差很大，先执行 analyze 更新统计信息
--   actual time / actual rows：真实耗时(毫秒)与真实行数

-- 估算明显失真时更新统计信息
analyze tb_account;
-- 查看某列的数据分布，直方图能帮助判断优化器的估算依据
select * from pg_stats where tablename = 'tb_account' and attname = 'age';

十四、MVCC 与隔离级别

14.1 MVCC 是怎么实现的

PostgreSQL 用多版本并发控制（MVCC）解决读写冲突：更新一行时并不会原地覆盖旧数据，而是写入一个新的行版本，旧版本仍然保留在数据文件中。每个事务在开始时拿到一个快照，只读取对自己可见的版本。

每行记录都带有几个系统列：xmin 是创建该版本的事务号，xmax 是删除或更新该版本的事务号（未被删除时为 0）。判断可见性的规则是：xmin 对应的事务已提交、且早于当前快照，同时 xmax 为空或对应事务不可见，这行数据才可见。

这套机制带来的最大好处是"读不阻塞写、写不阻塞读"：读操作只读快照，不需要等待写事务释放锁，也就不会出现脏读。代价是旧版本需要靠 VACUUM 清理，所以 MVCC 与 VACUUM 是配套的一对概念。

14.2 四种隔离级别

隔离级别 脏读 不可重复读 幻读 序列化异常
Read Uncommitted PG 中不会发生 可能 可能 可能
Read Committed（默认） 不可能 可能 可能 可能
Repeatable Read 不可能 不可能 不可能 可能
Serializable 不可能 不可能 不可能 不可能

PostgreSQL 实际上只实现三种隔离级别：指定 Read Uncommitted 会自动按 Read Committed 处理。各隔离级别的差异在于取快照的时机：Read Committed 每条语句开始时取一个新快照，所以同一事务内前后两次查询可能看到不同结果；Repeatable Read 只在事务的第一条语句取一次快照，之后整个事务都复用这个快照。

-- 查看与设置当前事务的隔离级别
show transaction_isolation;
begin transaction isolation level repeatable read;
select * from tb_account where id = 1;
commit;

-- 在同一个连接内修改默认隔离级别
set session characteristics as transaction isolation level serializable;
set default_transaction_isolation = 'read committed';

需要特别注意的是写冲突的处理方式。在 Read Committed 下，两个事务同时更新同一行时，后到的事务会等待，等前者提交后重新读取最新版本再尝试更新；而在 Repeatable Read 下，后到的事务会直接失败并报 could not serialize access due to concurrent update，必须由应用回滚整个事务后重试。

PostgreSQL 的 Serializable 是基于快照的串行化（SSI）：它通过跟踪事务之间读写依赖形成的环来发现异常，一旦发现就中止其中一个事务，报 could not serialize access due to read/write dependencies among transactions。这和 MySQL 的 Serializable（主要靠加锁）是两种不同的实现思路。

十五、VACUUM、autovacuum 与表膨胀

15.1 为什么需要 VACUUM

前面说到 UPDATE 会产生新版本、DELETE 只是把旧版本标记为删除，这些不再被任何事务需要的版本叫作死元组（dead tuple）。它们占据的空间不会自动释放，日积月累表就会膨胀，扫描时要读的页面越来越多，查询自然变慢。

-- 回收死元组空间：可以与业务并发执行，通常不把空间归还操作系统
vacuum tb_account;
-- 回收空间并更新统计信息
vacuum analyze tb_account;
-- 重写整表并把空间归还操作系统，需要排他锁，执行期间阻塞读写
vacuum full tb_account;
-- 只更新统计信息
analyze tb_account;

-- 查看表的死元组数量、上次清理时间与自动清理次数
select relname, n_live_tup, n_dead_tup, last_vacuum, last_autovacuum, vacuum_count
from pg_stat_user_tables
where relname = 'tb_account';
-- 查看表与索引占用的空间
select pg_size_pretty(pg_total_relation_size('tb_account')) as total_size;
-- 查看当前数据库中的长事务；长事务会拖住回收水位，导致死元组无法清理
select pid, state, xact_start, now() - xact_start as duration, left(query, 60) as query
from pg_stat_activity
where xact_start is not null
order by xact_start;

15.2 autovacuum 的触发条件与调优

正常情况下不需要手工执行 VACUUM，autovacuum 后台进程会按阈值自动触发。对某张表来说，当死元组数量超过下面这个值时就会启动清理：

某个表的触发阈值 = autovacuum_vacuum_threshold（基准行数，默认 50） + autovacuum_vacuum_scale_factor（放大比例，默认 0.2）× 表的活元组数。

默认 autovacuum_vacuum_threshold 为 50、autovacuum_vacuum_scale_factor 为 0.2，也就是说一张 1000 万行的表要累积到约 200 万行死元组才会被清理，这在写入频繁的表上显然太迟，需要针对单表调小比例。

-- 全局参数（修改后需要 reload；autovacuum 相关参数属于 sighup 级别）
-- autovacuum = on                                  -- 总开关
-- autovacuum_vacuum_threshold = 50                 -- 基准阈值
-- autovacuum_vacuum_scale_factor = 0.2             -- 按表大小放大的比例
-- autovacuum_naptime = 1min                        -- 巡检间隔
-- autovacuum_max_workers = 3                       -- 工作进程数

-- 针对写入频繁的单表单独调优：死元组达到 1 万行或 5% 就触发
alter table tb_order set (
    autovacuum_vacuum_scale_factor = 0.05,
    autovacuum_vacuum_threshold = 10000,
    autovacuum_analyze_scale_factor = 0.02
);
-- 查看表上生效的存储参数
select relname, reloptions from pg_class where relname = 'tb_order';
-- 手工清理并输出每个阶段的详细信息，便于排查清理慢的原因
vacuum (verbose) tb_order;

如果表已经严重膨胀，vacuum full 又不能在业务高峰期执行，可以使用 pg_repack 这类扩展：它以在线方式重建表并切换文件，只在收尾阶段持有极短的排他锁。

十六、WAL 与归档

16.1 WAL 的作用与查看方式

WAL（Write-Ahead Log，预写式日志）是 PostgreSQL 保证持久性和崩溃恢复的基础。它的核心原则是：数据页的任何修改，必须先把对应的日志记录刷到 WAL 文件，之后才允许把脏页写回数据文件。这样即使数据库进程或主机在任意时刻断电，重启后也能用 WAL 把已提交的事务重放出来。

WAL 文件位于数据目录的 pg_wal（PostgreSQL 10 之前叫 pg_xlog）下，默认每个 16MB，写满一个就切换到下一个。检查点（checkpoint）会把内存中的脏页刷盘，并记录一个位置（LSN），崩溃恢复只需要从最近一次检查点开始重放，从而缩短恢复时间。因此 checkpoint 间隔太短会导致频繁刷盘、影响性能，太长则会让恢复变慢、WAL 占用变多。

-- 查看当前 WAL 的写入位置（LSN）与最近一次检查点信息
select pg_current_wal_lsn();
select * from pg_control_checkpoint();
-- 查看 WAL 相关参数
show wal_level;          -- minimal / replica / logical，默认 replica
show max_wal_size;
show min_wal_size;
show checkpoint_timeout;
show archive_mode;

16.2 开启归档与时间点恢复

只靠 WAL 循环写入，旧日志被覆盖后就再也找不回来了。开启归档（archive_mode）后，PostgreSQL 会在每个 WAL 段写满并切换时，把它交给 archive_command 指定的命令保存到别处，这些归档再加上一份基础备份，就能把数据库恢复到任意时间点。

-- 修改 postgresql.conf（需要重启生效的参数：archive_mode）
-- wal_level = replica
-- archive_mode = on
-- archive_command = 'test ! -f /var/lib/pgsql/12/archive/%f && cp %p /var/lib/pgsql/12/archive/%f'

-- 手工触发一次 WAL 切换，验证归档是否配置成功
select pg_switch_wal();
-- 查看归档统计：成功、失败的数量以及最近归档的文件
select * from pg_stat_archiver;
-- 列出 pg_wal 目录大小，判断是否需要调整 max_wal_size
select pg_size_pretty(sum(size)) from pg_ls_waldir();

做时间点恢复时，把基础备份解压到数据目录，在 postgresql.conf 或 postgresql.auto.conf 中配置 restore_command，再指定恢复目标，启动后数据库就会重放归档日志：

-- 恢复配置示例（写在 postgresql.auto.conf 中）
-- restore_command = 'cp /var/lib/pgsql/12/archive/%f %p'
-- recovery_target_time = '2024-01-01 12:00:00'
-- recovery_target_action = 'promote'

十七、函数、触发器与权限管理

17.1 PL/pgSQL 函数与 CALL

9.2 节已经用过 PL/pgSQL 的触发器函数，这里把普通函数补全。函数体用美元引用（dollar quoting，如 $$ ... $$）包起来，好处是函数体内部的单引号不需要再做转义；$$ 也可以写成 $body$ 这种带标签的形式，当函数体内部还要嵌套美元引用时用标签区分会更清晰。

create or replace function fn_add(a int, b int) returns int as $$
begin
    return a + b;
end;
$$ language plpgsql;

-- 带出参的函数，调用时用 select
create or replace function fn_user_total(uid int, out total numeric)
as $$
begin
    select coalesce(sum(balance), 0) into total from tb_account where id = uid;
end;
$$ language plpgsql;

select fn_add(1, 2);
select fn_user_total(1);
-- 查看函数定义
select proname, pg_get_functiondef(oid) from pg_proc where proname = 'fn_add';

函数适合"有返回值、需要嵌入 SQL 中使用"的场景；如果只是执行一段过程、不需要返回值，可以用存储过程配合 call 调用，过程内部还允许提交或回滚事务。

create or replace procedure sp_reset_balance(uid int) as $$
begin
    update tb_account set balance = 0 where id = uid;
    commit;
end;
$$ language plpgsql;

call sp_reset_balance(1);

17.2 触发器的完整套路

触发器的构成是"触发时机 + 事件 + 粒度 + 触发器函数"。9.2 节里的级联删除示例已经演示过 after delete ... for each row，下面补充行级触发器里最常用的几个要点。

-- 在删除学生之前记录日志：before 行级触发器可以直接返回 old 阻止删除
create table if not exists student_del_log(
    id bigserial primary key,
    student_id int,
    deleted_at timestamp default current_timestamp
);

create or replace function fn_log_student_delete() returns trigger as $$
begin
    insert into student_del_log (student_id) values (old.id);
    return old;
end;
$$ language plpgsql;

drop trigger if exists trg_student_delete_log on student;
create trigger trg_student_delete_log
before delete on student
for each row
execute function fn_log_student_delete();

select * from student;
delete from student where id = 2;
select * from student_del_log;

需要记住的几点：行级触发器会为每一行执行一次，数据量大时开销明显；before 触发器返回 old 或 new 才会继续执行原操作，返回 null 表示跳过这一行；new 在 delete 事件中为 null，old 在 insert 事件中为 null；语句级触发器用 for each statement，每个语句只执行一次。

17.3 Schema 组织与权限管理

当多个业务共用同一个数据库时，可以用 schema 做命名空间隔离，避免表名冲突，权限也能按 schema 授予。

-- 建立专用的 schema 与登录角色
create schema if not exists app;
create role app_rw login password 'ChangeMe_123';
create role app_ro login password 'ChangeMe_456';

-- 允许使用（进入）该 schema，否则连表名都无法解析
grant usage on schema app to app_rw, app_ro;
-- 现有对象的权限
grant select, insert, update, delete on all tables in schema app to app_rw;
grant select on all tables in schema app to app_ro;
grant usage, select on all sequences in schema app to app_rw;
-- 之后新建的对象也自动套用同样的权限
alter default privileges in schema app
    grant select, insert, update, delete on tables to app_rw;
alter default privileges in schema app
    grant select on tables to app_ro;

-- 让角色默认先在 app 下搜索对象
alter role app_rw set search_path = app, public;
-- 查看权限
select table_schema, table_name, privilege_type, grantee
from information_schema.role_table_grants
where grantee in ('app_rw', 'app_ro');

落到表级或列级的授权、以及属主变更也很常用：

grant select (username, city) on tb_account to app_ro;   -- 只开放部分列
revoke delete on tb_account from app_rw;                  -- 收回权限
alter table tb_account owner to app_rw;                   -- 变更属主，属主拥有全部权限
-- 查看某张表上的全部授权
select * from information_schema.table_privileges where table_name = 'tb_account';

另外，PostgreSQL 15 起 public schema 默认不再允许所有用户创建对象（pg_database_owner 才有 CREATE 权限），因此在新版本上给业务角色建对象时，需要显式 grant create on schema app to app_rw;，并且建议让业务对象都落在专用 schema 中，而不是 public。
