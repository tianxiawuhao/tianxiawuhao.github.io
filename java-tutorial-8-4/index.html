Flink 流处理

Posted on 2026-09-19，8 min read

前面的章节里，数据大多是「一次算完」的批处理：输入固定、跑一遍出结果。但真实业务里更多的是无界数据流——用户点击、订单支付、设备心跳、日志埋点，它们不会结束，而且会因为网络与上游系统而乱序到达。本章面向已经会写 Java、也用过 MapReduce 或 Spark 批处理的读者，讲清楚 Flink 的 DataStream API 如何用「时间 + 窗口 + 状态」这套抽象处理无界流，以及 Checkpoint 与反压这两个决定作业能否长期稳定运行的机制。读完你应该能写出一个带事件时间窗口、可容错重启的 Flink 作业，并知道出问题时先看哪里。

为什么流处理需要一整套新抽象

批处理的世界里，"什么时候的数据"不需要讨论：一次运行只处理一个确定的数据集，结果稳定可重放。流处理则必须回答两个批处理不会遇到的问题。第一是时间归属：一条消息的"发生时间"（事件时间）和它被 Flink 处理的时间（处理时间）可能相差几秒到几小时，如果按处理时间统计"每分钟成交额"，那么上游一次积压就会把两个不同时刻的数据算进同一个窗口，结果无法复现，重跑作业还会得到不同答案。第二是跨事件的记忆：无界流上无法"等全部数据到齐再算"，所以必须把中间结果保存下来，这就是状态；而作业一旦失败重启，状态必须能从某个一致点恢复，否则计数会重复或丢失。窗口解决的问题是"把无界切成有界来聚合"，状态解决的问题是"在无界中记住东西"，Checkpoint 解决的则是"记住的东西如何不丢"。这三者构成了流处理的核心。

DataStream 程序的骨架

一个 Flink 作业的代码结构始终是 Source → Transformation → Sink：从数据源读取，经过若干算子转换，最后写出到外部系统。与批处理最大的差别是算子默认是有状态且长期运行的，算子之间通过数据流传递记录，而不是靠返回值串联。下面这段代码搭出一个最小可运行的骨架，并注册了事件时间与水位线（Watermark），后续小节都在它上面展开。

import org.apache.flink.api.common.eventtime.WatermarkStrategy;
import org.apache.flink.api.common.serialization.SimpleStringSchema;
import org.apache.flink.connector.kafka.source.KafkaSource;
import org.apache.flink.connector.kafka.source.enumerator.initializer.OffsetsInitializer;
import org.apache.flink.streaming.api.datastream.DataStream;
import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;

public class BrowseJob {
    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env =
                StreamExecutionEnvironment.getExecutionEnvironment();
        // Checkpoint 是容错的前提，生产环境必须开启（间隔 10s，精确一次）
        env.enableCheckpointing(10_000);
        env.getCheckpointConfig()
           .setCheckpointingMode(CheckpointingMode.EXACTLY_ONCE);

        KafkaSource<String> source = KafkaSource.<String>builder()
                .setBootstrapServers("kafka-1:9092")
                .setTopics("user-browse")
                .setGroupId("browse-job")
                .setStartingOffsets(OffsetsInitializer.latest())
                .setValueOnlyDeserializer(new SimpleStringSchema())
                .build();

        DataStream<String> raw = env.fromSource(
                source,
                // 水位线策略：从 JSON 的 eventTime 字段取时间戳，容忍 5 秒乱序
                WatermarkStrategy.<String>forBoundedOutOfOrderness(
                        java.time.Duration.ofSeconds(5))
                    .withTimestampAssigner((json, ts) -> parseEventTime(json)),
                "kafka-source");

        raw.keyBy(BrowseJob::parseUserId)
           .window(org.apache.flink.streaming.api.windowing.assigners
                   .TumblingEventTimeWindows.of(java.time.Duration.ofMinutes(1)))
           .reduce((a, b) -> a.price >= b.price ? a : b)
           .print();

        env.execute("user-browse-top-per-minute");
    }
}

时间语义、水位线与窗口

三种时间与水位线的作用

Flink 支持三种时间语义：事件时间（数据自身携带的发生时间）、处理时间（算子所在机器的系统时间）和摄入时间（进入 Flink 的时间）。只有事件时间能保证结果可复现，因此生产作业几乎都选它。需要注意的是，TimeCharacteristic 与 env.setStreamTimeCharacteristic(...) 这套全局设置从 Flink 1.12 起已被废弃并在 1.14 移除：现在时间语义由你用哪种 WindowAssigner（或用 KeyedProcessFunction 处理时间戳）直接决定，使用 TumblingEventTimeWindows 即事件时间，不需要也不应该再去设置全局语义。

水位线是一个随时间单调递增的特殊标记，含义是"事件时间小于该值的记录应该都到齐了"。分配器收到一条记录时取 max(已见最大时间戳 - 乱序容忍时长, 当前水位线) 得到新水位线；默认每 200ms 向下游发送一次。理解一句话就够了：窗口由水位线推进触发，而不是由记录到达触发。这也解释了两个经典现象：乱序容忍时长设得越大，结果越准但延迟越高；如果某个分区长时间没有数据，水位线会卡住，导致所有窗口都不输出——这正是 withIdleness 要解决的场景。

窗口类型与选择

窗口把无界流切成有限集合再聚合，常用的有四类。滚动窗口（Tumbling）按固定长度、首尾相接、互不重叠，适合"每 5 分钟统计一次"；滑动窗口（Sliding）长度与步长分开配置，窗口之间会重叠，适合"每 1 分钟看过去 5 分钟"的平滑指标；会话窗口（Session）按活动间隙切分，一段时间没有数据就关闭，适合用户行为分析；全局窗口（Global）把所有数据放进一个窗口，必须自定义触发器，否则永不触发（很多初学者写出"作业不输出"的代码，根因就在这里）。与批处理按分区聚合类似，keyBy 之后的窗口是每个 key 一份窗口实例，不同用户互不干扰，这也是窗口能与状态配合的前提。

窗口函数与状态：增量聚合 vs 全量聚合

窗口函数决定窗口内的元素怎么算，分为两类。增量聚合函数每来一条记录就更新一次中间结果，不保存原始数据，内存开销与记录数无关，代表是 ReduceFunction 和 AggregateFunction；全量聚合函数在窗口触发时拿到该窗口全部元素再计算，代表是 ProcessWindowFunction，它的优势是能访问窗口元数据（起止时间、状态）并任意输出，代价是需要缓存整个窗口的数据。工程上的最优解是两者结合：window(...).aggregate(aggFunction, processWindowFunction)，先用增量聚合把数据量压下来，再用 ProcessWindowFunction 补上 Key 与窗口时间等上下文。

// 增量聚合：求每个用户窗口内的平均单价，只维护 (条数, 总额) 两个 long
public class AvgPriceFunction
        implements AggregateFunction<Browse, long[], Double> {

    @Override
    public long[] createAccumulator() {
        return new long[]{0L, 0L};          // {count, sum}
    }

    @Override
    public long[] add(Browse value, long[] acc) {
        acc[0]++;
        acc[1] += value.getPrice();
        return acc;
    }

    @Override
    public long[] merge(long[] a, long[] b) {   // 会话窗口或合并窗口时才会调用
        a[0] += b[0];
        a[1] += b[1];
        return a;
    }

    @Override
    public Double getResult(long[] acc) {
        // 必须转成 double 再除，否则整数相除会把 13.33 截成 13
        return acc[0] == 0L ? 0.0 : (double) acc[1] / acc[0];
    }
}
// 增量聚合 + 全量聚合：拿到平均值的同时，补充 Key 和窗口时间
raw.keyBy(Browse::getUserId)
   .window(TumblingEventTimeWindows.of(Duration.ofMinutes(1)))
   .aggregate(new AvgPriceFunction(),
              new ProcessWindowFunction<Double, String, String, TimeWindow>() {
                  @Override
                  public void process(String key, Context ctx,
                          Iterable<Double> elements, Collector<String> out) {
                      Double avg = elements.iterator().next();  // 只会有一条结果
                      out.collect(String.format("user=%s [%d, %d) avg=%.2f",
                              key, ctx.window().getStart(), ctx.window().getEnd(), avg));
                  }
              })
   .print();

这里有两个必须避开的坑。一是累加器的复用语义：Flink 会把累加器对象保存在状态里，add 方法可能被连续调用并复用同一个对象，因此要更新后返回该对象（上面的写法），千万不要每次都 new 一个新累加器并在其中 += 后返回，那会导致中间结果丢失。二是不要修改输入元素：ReduceFunction 里若直接改 value1 的字段并返回，在重试或重放时会出现难以复现的错误，应当返回原对象引用而非就地修改。

窗口能算出结果，靠的是状态在背后兜底。状态分两类：Keyed State（ValueState、ListState、MapState 等，只能用在 keyBy 后的算子里，天然按 key 隔离）和 Operator State（如 Kafka Source 的分区偏移量，按算子并行子任务分配）。状态必须有状态后端承载：旧版本的 MemoryStateBackend、FsStateBackend、RocksDBStateBackend 三选一，从 Flink 1.13 起统一为 HashMapStateBackend 与 EmbeddedRocksDBStateBackend 两种，env.setStateBackend(...) 的配置方式也随之改变。数据量超过内存、或需要增量 Checkpoint 时选 RocksDB，其余情况 HashMap 更简单也更快。

Checkpoint、重启策略与反压

Checkpoint 是 Flink 容错的核心：JobManager 定期向所有算子注入屏障（Barrier），屏障随数据流一起流动，算子收到屏障时把自身状态快照上传到分布式存储。所有算子都完成快照后，这次 Checkpoint 才算成功，作业失败重启时会从最近一次成功的快照恢复。这带来两个直接结论：Checkpoint 间隔决定了故障时的重算量（间隔 10 分钟就最多重算 10 分钟的数据），而状态大小决定了 Checkpoint 耗时（这也是大状态作业要开 RocksDB 增量 Checkpoint 的原因）。生产环境还应配置重启策略与外部化 Checkpoint，前者让作业自动拉起，后者在作业被取消后仍保留快照用于恢复。语义方面，EXACTLY_ONCE 保证状态不重不漏，但端到端精确一次还需要 Sink 支持事务或幂等写入，Sink 不支持时只能退化为 AT_LEAST_ONCE。

反压（Backpressure）是流处理中最常见的"看起来卡住了"。Flink 基于信用机制做流控：下游算子的输入缓冲区写满后，会停止向上游发送信用，上游随之减速，压力最终传导到 Source——这正是期望行为，说明系统在自我保护，而不是 bug。真正要排查的是反压的根源算子：在 Flink UI 的作业图中，反压会显示在首个高反压算子上，通常是它下游有同步阻塞操作（比如在算子内调用外部 HTTP 或 JDBC）。常见治理手段包括提高瓶颈算子的并行度、把同步 IO 换成 Async I/O、为热点 key 做两阶段聚合（先加随机前缀打散再二次聚合）、以及给状态配好 RocksDB 与本地磁盘。另外，数据倾斜是窗口作业的隐形杀手：个别 key 的数据量远超其他 key，会让单个并行子任务独自背下整个作业的压力，此时应先看各子任务的 records 与 bytes 指标是否严重不均，再决定加盐还是拆分逻辑。

小结

本章的脉络可以压缩成一条链：无界流无法等数据到齐，所以用窗口把流切成有界；窗口要算得准，必须有事件时间与水位线来界定"数据到齐"；窗口之间要记住中间结果，就用到状态，状态又分增量聚合与全量聚合两种取舍；状态要能故障恢复，靠的是Checkpoint 与重启策略；而作业长期运行时的性能问题，多半通过反压现象暴露出来，治理思路是找到瓶颈算子而不是盲目加资源。动手时建议按这个顺序验证：先用 print() 确认水位线在推进、窗口在触发，再逐步换成生产级 Sink，最后才去调并行度与状态后端。
