Maven 构建与依赖管理

Posted on 2026-09-19，8 min read

前面的章节里，我们用 javac 和 java 就能把单个 Java 文件跑起来。但只要项目开始依赖第三方 jar，手工下载、拷贝到 lib 目录、再手工往 classpath 里加路径的做法就会迅速失控：换一台机器就跑不起来，两个库依赖同一个包的不同版本会打架，升级一个库要通知所有用它的项目组重新拷一遍。Maven 解决的就是这类工程问题——它用「约定优于配置」把目录结构、依赖获取、构建流程固定下来，全部收拢到一份 pom.xml 里。本章面向已经会写 Java、但还没系统用过构建工具的读者，讲清四件事：坐标与仓库、生命周期、依赖范围与冲突、多模块与私服。读完之后，你应该能独立看懂一个真实企业项目的 pom.xml 并知道每条 mvn 命令背后发生了什么。

一、坐标与仓库：Maven 到哪里去找那个 jar

Maven 的第一个核心概念是坐标。它把「一个构件（artifact）」抽象成三个必填字段：groupId 是组织或团队的唯一标识，通常写成反过来的域名，也就是包名；artifactId 是项目自身的唯一标识，一般就是项目名；version 是版本号。三者组合起来，就能在整个仓库体系中唯一锁定一个构件。可选的第四个字段是 packaging，表示打包类型，常见取值有 jar（普通 Java 项目）、war（Web 项目）和 pom（只做聚合与继承的父工程）。name、description 只是给人看的显示信息，不参与构件定位。

有了坐标，仓库的目录结构就是确定的。构件在仓库中的路径遵循固定规则：groupId 中的每一个点都要换成一层目录，然后是 artifactId、version，最后是 artifactId-version.packaging。比如 org.springframework:spring-context:4.2.4.RELEASE 会落在 org/springframework/spring-context/4.2.4.RELEASE/spring-context-4.2.4.RELEASE.jar。注意源笔记把这条规则写成「groupId/artifactId/version」，容易让人误以为 org.springframework 是一层目录，实际是两层，这一点在手工排查仓库文件时经常要用到。

仓库分三类。本地仓库是磁盘上的一个目录，位置由 conf/settings.xml 中的 <localRepository> 指定，默认在用户主目录下的 .m2/repository；Maven 总是先找本地仓库，找不到才去远程下载，并顺手缓存到本地。中央仓库是 Maven 官方维护的公共仓库，地址写在 Maven 内置的「超级 POM」里。私服则是公司内部搭的仓库服务（常用 Nexus 或 Artifactory），它既能代理中央仓库加速下载，也能存放公司自己的内部构件和涉密构件。此外，JBoss、Spring 等厂商还有自己的仓库，「中央仓库什么都有」是个误解。

<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>

  <!-- 三个坐标：唯一确定一个构件 -->
  <groupId>com.example.shop</groupId>
  <artifactId>shop-service</artifactId>
  <version>1.0-SNAPSHOT</version>
  <packaging>jar</packaging>

  <properties>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>
</project>

二、生命周期：一条命令背后的阶段链

Maven 有三套相互独立的生命周期，每套由若干阶段（phase）组成，我们在命令行敲的命令名其实就是某个阶段的名称。

clean 生命周期负责清理，只有三个阶段：pre-clean、clean、post-clean，其中 clean 会删除上一次构建生成的 target 目录。default 生命周期是构建的核心，阶段最多，需要记住的主干顺序是：validate → compile → test → package → install → deploy。中间还夹着 process-resources（复制资源文件到 target）、test-compile（编译测试代码）、integration-test、verify 等阶段，它们大多由插件绑定执行，平时不必逐个关注。site 生命周期负责生成站点文档。

这里有一条贯穿始终的规则：执行某个阶段时，它前面在同一生命周期中的所有阶段都会被执行。所以 mvn post-clean 会连带跑掉 pre-clean 和 clean；而 mvn install 之所以既编译又测试又打包，正是因为 install 排在它们后面。这就是所谓的「Maven 一步构建」。三套生命周期彼此独立，mvn clean 不会触发任何编译，而 mvn clean install 才会先清理再完整构建一遍——这是日常最常用的组合。

# 只编译：源码编译到 target/classes
mvn compile

# 清理后完整构建，并把构件装进本地仓库（其他项目才能依赖它）
mvn clean install

# 跳过测试执行（测试代码仍会编译）
mvn clean package -DskipTests

# 连测试代码都不编译（慎用，容易把编译不过的测试带上线）
mvn clean package -Dmaven.test.skip=true

# 查看构建产物：target/ 下的 jar
ls target

几个阶段要分清：compile 把 src/main/java 编译到 target/classes；test 先编译测试代码再运行测试，测试代码不打包；package 产出 jar 或 war，文件名形如 artifactId-version.jar；install 把包安装到本地仓库供其他项目依赖；deploy 才是把包上传到远程仓库（私服）。很多团队在私服上拉不到同事刚提交的构件，往往就是只跑了 package 没跑 deploy。

三、依赖范围与依赖冲突

在 <dependencies> 中声明一个 <dependency>，除了三个坐标还可以写 <scope>，它决定这个依赖在编译、测试、运行三个阶段是否可见，以及是否会被打进最终的包。compile 是默认值，三个阶段都可见，也会被打包；provided 在编译和测试时可见，但不打包，因为运行环境已经提供（典型例子是 servlet-api，Tomcat 自己带着）；runtime 在编译时不可见，测试和运行时可见并会被打包，典型例子是 JDBC 驱动——代码里只出现 java.sql.* 接口，驱动实现类由反射加载，所以不需要在编译期出现；test 只在测试的编译与运行期可见，不打包，JUnit 就是这一类；system 需要额外写 <systemPath> 指向本机磁盘上的 jar，它不参与依赖传递，跨机器构建必然失败，属于不推荐甚至已被弃用的用法。

源笔记把 runtime 描述为「编译不需要，打包运行时需要」，这个说法不够准确：runtime 的依赖在测试期是可见的，而且在打包时会被放进 lib，真正的判定标准是「编译期不可见、运行期可见」，而不是「不打包」。

Maven 还会自动引入依赖的依赖，这叫传递依赖。这也带来了冲突：A 依赖 B 和 C，B 依赖 log4j 1.2.15，C 依赖 log4j 1.2.17，最终只能有一个版本胜出。Maven 的调解规则有两条：一是最短路径优先，离本项目层级更近的版本获胜；二是路径长度相同时先声明者优先，即写在 <dependencies> 中更靠前的那个生效。要注意，依赖传递默认会跨越任意层数，所以「传递依赖」不是「只传一层」。

需要精确控制时有两个手段。<exclusions> 用来斩断某条传递链路，常见于排除旧版日志实现或重复的 mail 包；<optional>true</optional> 表示这个依赖不向下传递，比如 A 依赖 B、B 依赖 C，若 C 被标为可选，则 A 不会自动拿到 C。排查冲突时不要靠猜，直接跑 mvn dependency:tree 打印依赖树，或用 dependency:tree -Dincludes=log4j:log4j 只看某个构件的来源。

<dependencies>
  <dependency>
    <groupId>junit</groupId>
    <artifactId>junit</artifactId>
    <version>4.13.2</version>
    <scope>test</scope>
  </dependency>

  <dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-context</artifactId>
    <version>4.2.4.RELEASE</version>
    <!-- 排除传递进来的旧版日志包，避免与项目内版本冲突 -->
    <exclusions>
      <exclusion>
        <groupId>commons-logging</groupId>
        <artifactId>commons-logging</artifactId>
      </exclusion>
    </exclusions>
  </dependency>
</dependencies>

四、多模块聚合、继承与私服

项目变大之后，一个 war 里塞下所有代码并不现实。Maven 的做法是多模块：父工程只负责组织，不写业务代码，它的 packaging 是 pom，用 <modules> 列出子模块；子模块用 <parent> 声明继承关系。继承的好处是子模块可以省掉 groupId 和 version，只写自己的 artifactId，从而保证整个项目版本一致。

与继承配套的另一个元素是 <dependencyManagement>。它只声明版本，不真正引入依赖：在父工程里把各依赖的版本锁定，子模块引用时只写 groupId 和 artifactId 即可，避免同一构件在不同模块里出现不同版本。这也是新手最容易误解的一点——只在父工程写了 dependencyManagement 而子模块不引用，就不会引入任何依赖。

聚合的另一个直接收益是构建命令的简化：对父工程执行一次 mvn clean install，Maven 会按模块间的依赖顺序依次构建所有子模块，不必逐个目录去执行。子模块互相依赖却报「找不到构件」，根因通常不是代码问题，而是被依赖的模块没有 install 到本地仓库。

当团队需要共享构件时，就该让私服登场了。私服的地址配置在 settings.xml 的 <mirrors> 和 <profiles> 中，而上传所需的账号密码放在 <servers> 里，通过 <id> 与 pom.xml 的 <distributionManagement> 对应。需要区分清楚：settings.xml 是这台机器上 Maven 工具的全局配置（仓库位置、镜像、凭证），pom.xml 是某个工程的构建描述，两者职责不同，不要混用。

<!-- 父工程 pom.xml：聚合 + 版本锁定 -->
<project>
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.example.shop</groupId>
  <artifactId>shop-parent</artifactId>
  <version>1.0-SNAPSHOT</version>
  <packaging>pom</packaging>

  <modules>
    <module>shop-service</module>
    <module>shop-web</module>
  </modules>

  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>org.springframework</groupId>
        <artifactId>spring-context</artifactId>
        <version>4.2.4.RELEASE</version>
      </dependency>
    </dependencies>
  </dependencyManagement>
</project>

<!-- 子模块 pom.xml：继承父工程，只需写 artifactId -->
<parent>
  <groupId>com.example.shop</groupId>
  <artifactId>shop-parent</artifactId>
  <version>1.0-SNAPSHOT</version>
  <relativePath>../pom.xml</relativePath>
</parent>
<artifactId>shop-web</artifactId>

五、几个高频的坑

第一，本地仓库里出现 *.jar.lastUpdated 文件，说明上次下载中断了，这个构件不可用；删掉这些 -lastUpdated 文件后重新构建即可。第二，SNAPSHOT 表示开发中的快照版本，同一个版本号的内容可能被反复覆盖，Maven 会按策略检查更新；正式发布应使用不带 SNAPSHOT 的固定版本号，否则线上构建结果不可复现。第三，命令行工具已不再支持源笔记中的 mvn archetype:create，该目标在 Maven 3 中已被移除，创建工程应使用 mvn archetype:generate；同样，早期的 mvn eclipse:eclipse、tomcat:run 等做法也已被现代 IDE 与插件取代，了解即可，不必照抄。第四，在 IDE 中修改 pom.xml 后一定要重新导入或刷新 Maven 项目，否则 IDE 的类路径还是旧的，会出现「代码没错但编译报红」的现象。

小结一下：坐标（groupId、artifactId、version）加上 packaging 决定了构件在仓库中的唯一位置，本地仓库、中央仓库、私服构成了构件的获取链路；三套相互独立的生命周期把构建流程标准化，记住「执行某阶段会先执行它前面的阶段」，就能推理出任意一条 mvn 命令的行为；<scope> 控制依赖的可见范围与是否打包，传递依赖的冲突由最短路径优先和先声明优先两条规则调解，必要时用 exclusions 与 optional 精确干预；多模块工程用 <parent>、<modules> 与 <dependencyManagement> 实现聚合、继承与版本统一，对父工程执行一次 mvn clean install 即可构建全部模块。把这几条理顺，再看企业里的 pom.xml 就不会迷路了。
