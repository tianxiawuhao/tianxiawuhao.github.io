Node.js 与构建工具

Posted on 2026-09-19，7 min read

前面几章我们都是「一个 HTML 文件、几个 script 标签」地写页面。这种写法在小 demo 里没问题，可一旦页面分成十几个 JS 文件，就会同时冒出三个麻烦：文件之间靠全局变量通信、互相污染；script 的引入顺序稍微写错就报「undefined」；想用 Less、TypeScript 或还没被浏览器支持的新语法，浏览器直接不认。要解决这些工程化问题，就需要三样东西——一个能跑构建脚本的运行时（Node.js）、一个能下载并锁定第三方库的包管理器（npm），以及一个把源代码翻译、合并成浏览器可运行产物的构建工具（webpack / Vite）。本章就把这条链路一次讲清：从安装 Node、认识 package.json，到模块规范、打包器和脚手架的分工。适合已经会写 HTML/CSS/JS、但还没自己初始化过一个前端工程的读者。

一、为什么前端需要 Node.js 和 npm

先纠正一个常见误解：Node.js 不是「后端的 JavaScript 框架」，而是一个让 JavaScript 脱离浏览器运行的运行时。它把 Chrome 的 V8 引擎抽出来，补上了文件读写、网络、进程等系统能力。这件事对前端的意义在于：webpack、Vite、ESLint 这些工具本身就是 JavaScript 程序，它们需要读写磁盘、遍历依赖、开本地服务器，浏览器里做不到，所以必须跑在 Node 上。换句话说，你可以不写一行后端代码，但机器上必须有 Node 才能做现代前端开发。

npm（Node Package Manager）随 Node 一起安装，是 JS 生态的包管理器，作用相当于 Java 世界的 Maven：声明依赖、下载依赖、执行脚本。一个工程的身份证明就是根目录下的 package.json，其中 dependencies 是运行时依赖，devDependencies 是只在开发/构建阶段使用的依赖（打包器、编译器、测试框架都属于这一类），scripts 里则是可复用的命令别名。

  • npm i <包名>：安装到 dependencies；npm i -D <包名> 等价于 --save-dev，装到开发依赖。命令行里只有一两个包时，务必分清这两者，否则生产环境会白白装上几百 MB 的构建工具。
  • npm i：按 package.json 还原全部依赖；npm ci 严格按 package-lock.json 安装，适合 CI 环境，速度更快、结果可复现。
  • npm run <脚本名>：执行 scripts 中定义的命令，例如 npm run dev。局部安装的命令行工具（如 webpack）只有通过 npm run 或 npx 才能被找到，直接敲 webpack 会提示找不到命令。

国内下载慢是因为默认仓库在国外，可以换成淘宝镜像。这里要提醒一句：很多老笔记里写的 https://registry.npm.taobao.org 已于 2022 年停止服务，现在应使用 https://registry.npmmirror.com；cnpm 是镜像提供的替代客户端，能在不改全局配置的情况下加速，但它生成的目录结构与官方 npm 并不完全一致，遇到「本地能跑、同学那边装不上」的怪问题时，优先换回 npm 或 pnpm 复现。

# 1. 安装 Node.js（推荐 LTS 版本），安装后 node 与 npm 一起可用
node -v
npm -v

# 2. 查看当前 registry，并永久切换为国内镜像（老地址 registry.npm.taobao.org 已废弃）
npm config get registry
npm config set registry https://registry.npmmirror.com

# 3. 初始化工程并安装依赖
npm init -y                     # 生成 package.json
npm i vue                        # 运行时依赖
npm i -D webpack webpack-cli     # 开发依赖，-D 即 --save-dev

# 4. 查看全局包安装位置（Windows 上非管理员权限常需要改到用户目录）
npm config get prefix
npm ls --depth=0                 # 只看顶层依赖

还有两条纪律：node_modules 体积巨大且可由 lock 文件还原，永远不要提交进仓库（写进 .gitignore）；package-lock.json 则必须提交，它锁定了整棵依赖树的精确版本，是团队协作结果一致的前提。

二、模块化：CommonJS 与 ES Modules

早期前端靠多个 script 标签拼装代码，是同步加载：文件一多，顺序不能错，前一个文件报错后面的全部不执行，而且所有顶层变量都挂在全局对象上。模块化要解决的就是「每个文件有自己的作用域，需要什么显式引入，对外只暴露指定接口」。今天的 JavaScript 有两套主流模块规范。

CommonJS 是 Node.js 的模块规范，用 module.exports 导出、require() 引入。它在运行时加载：require 执行完才拿到一个对象，因此加载顺序可以写在条件语句里，但也无法在编译期做静态优化；同一个模块被多次 require 只会执行一次（单例），导出的是值的拷贝。

ES Modules（ESM） 是 ES6 引入的语言级模块规范，用 export / export default 导出、import 引入。import 语句会被提升到模块顶部，在编译阶段就确定依赖关系，因此要求是静态的：不能用变量或表达式拼模块名，也不能写在 if 里。导出的接口与模块内部变量是动态绑定，模块内部后来改了值，引入方看到的就是新值——这一点与 CommonJS 的「值拷贝」正好相反。在 Node 里写 ESM 需要文件后缀用 .mjs，或在 package.json 中声明 "type": "module"。

顺便澄清概念上的混淆：AMD 是 RequireJS 推广的浏览器端异步模块规范，CMD 是国人玉伯的 SeaJS 提出的规范，CommonJS 才是 Node 的服务端规范，三者不是同一件事；UMD 则是为了兼容 AMD、CommonJS 和全局变量三种环境而写的通用包装。至于「浏览器不支持 import」这个说法也已经过时：现代浏览器支持 <script type="module"> 原生加载 ESM（要求带 ./ 的完整路径并配 MIME 类型），只是裸模块名（import Vue from 'vue'）和 Less、TypeScript 等非 JS 资源，浏览器依然处理不了——这正是打包器的舞台。

// ---------- math.js：CommonJS 写法 ----------
function add(a, b) {
  return a + b;
}
const PI = 3.14159;
module.exports = { add, PI };      // 也可以用 exports.add = add

// ---------- main.js ----------
const { add, PI } = require('./math.js'); // 只执行一次，多次 require 拿到同一份缓存
console.log(add(1, 2), PI);

// ---------- math.mjs：ESM 写法 ----------
export function multiply(a, b) {
  return a * b;
}
export default { name: 'math' };   // 一个模块只能有一个默认导出

// ---------- main.mjs ----------
import math, { multiply } from './math.mjs'; // 默认导出不带大括号，具名导出必须带
console.log(multiply(2, 3), math.name);

三、webpack：打包器到底做了什么

webpack 是静态模块打包器。它从一个入口文件出发，递归分析 import/require，构建出一张依赖关系图（dependency graph），再把这些模块合并成一到多个 bundle，最后只用一个 script 标签引入即可。围绕这条主线，它有三个扩展点：

  • loader：把非 JS 资源和高级语法转成能进依赖图的模块，例如 css-loader、less-loader、babel-loader、vue-loader。loader 在 module.rules 中按 test 匹配文件、从右到左执行。
  • plugin：介入构建的整个生命周期，做 loader 做不到的事，如 HtmlWebpackPlugin（按模板生成 HTML 并自动注入 bundle）、MiniCssExtractPlugin（抽出独立 CSS 文件）。
  • devServer + devtool：前者提供本地开发服务器、热更新（HMR）与自动刷新，后者通过 source map 让打包后的代码仍能对应到源文件，从而在 Chrome 里打断点调试。

安装时有两点容易踩坑。第一，webpack 从 4.0 起把命令行拆到了独立的 webpack-cli，只装 webpack 会提示找不到命令，必须两个一起装；第二，优先本地安装（-D）而不是全局安装 -g，全局安装会把版本锁死在一台机器上，不同项目需要不同大版本时就会冲突。此外，网上流传的 webpack 3.x + webpack-dev-server 2.x 教程已明显过时：当前主线是 webpack 5，开发服务器也已更名为 webpack serve，旧参数 --inline 在新版本中已被移除，照抄会直接报参数错误。

// webpack.config.js —— webpack 5 写法
const path = require('path');
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  mode: 'development',                    // development 不压缩、带完整报错；production 会自动压缩
  entry: './src/main.js',                 // 唯一的入口，依赖图从这里长出来
  output: {
    path: path.resolve(__dirname, 'dist'),// __dirname 是配置文件所在目录，避免相对路径歧义
    filename: 'build.[contenthash].js',   // 内容哈希：内容变了文件名才变，便于浏览器缓存
    clean: true                           // 每次构建前清空 dist
  },
  module: {
    rules: [
      { test: /\.css$/, use: ['style-loader', 'css-loader'] } // 从右到左执行
    ]
  },
  plugins: [
    new HtmlWebpackPlugin({ template: './public/index.html' }) // 按模板生成 HTML 并自动注入 bundle
  ],
  devtool: 'eval-source-map',             // 开发期映射回源码，可在源码里打断点
  devServer: { port: 5008, open: true, hot: true } // 启动：npx webpack serve
};

四、脚手架与 Vite：把配置交给工具链

手写 webpack 配置能帮你理解原理，但每个新项目都从零配一遍并不划算。脚手架就是「预置好目录结构、构建配置和默认依赖」的项目模板，一条命令就能得到可运行的工程骨架。Vue 官方早期提供 Vue CLI（内部封装 webpack），现在已进入维护状态，推荐改用 create-vue，它生成的工程基于 Vite。

Vite 与 webpack 的思路不同：webpack 必须先把整张依赖图打包完，开发服务器才能响应请求，项目一大启动就要几十秒；Vite 在开发阶段不打包，而是利用浏览器原生 ESM 按需编译单个模块，并用 esbuild 预构建第三方依赖，因此启动和热更新都在毫秒级；到了生产构建再交给 Rollup 输出优化后的产物。代价是它更依赖现代浏览器（ESM 原生支持）。所以选型可以这样判断：新项目直接 Vite，维护中的老项目（Vue CLI / webpack 配置）继续沿用，不必为了追新重写构建链。

# 方式一：Vue 官方脚手架（基于 Vite），交互式选择 TypeScript / Router / Pinia 等
npm create vue@latest my-app
cd my-app && npm install && npm run dev

# 方式二：更通用的 Vite 模板
npm create vite@latest my-app -- --template vue

# package.json 中 scripts 的典型形态，用 npm run 触发
#   "dev":     "vite",            开发服务器，带 HMR
#   "build":   "vite build",      产出 dist/
#   "preview": "vite preview",    本地预览构建产物

常见坑

  • 依赖装了却用不了：多数是没走 npm run。局部安装的 CLI 不会进入全局 PATH，用 npx webpack 也可以。
  • 改完配置不生效：webpack.config.js、vite.config.js 以及依赖的变更都需要重启开发服务器，HMR 只处理源码。
  • 路径写法：配置里用 path.resolve(__dirname, 'dist') 这类绝对路径，别依赖启动目录；Windows 与 Linux 的路径分隔符不同，拼接交给 path。
  • 版本混用：webpack 4/5 与 webpack-cli 的版本要配套；跟着老教程装 webpack 3，就等于放弃了当前所有文档和插件。
  • Vue CLI 与 Vite 的配置不通用：vue.config.js 里的 devServer 写法不能直接搬到 vite.config.js，迁移时按官方文档逐项对照。

五、小结

本章把前端工程化的地基串了起来：Node.js 提供运行环境，让构建工具能在浏览器之外跑起来；npm 负责依赖声明、安装与命令编排，package.json 与 lock 文件是团队协作的契约；模块规范决定了代码如何拆分与引用，CommonJS 服务于 Node 的运行时加载，ESM 是语言标准并支持静态分析与动态绑定；webpack 以入口为起点构建依赖图、用 loader 和 plugin 完成转译与优化，用 devServer 与 source map 换取开发体验；Vite 与脚手架则把配置收敛成模板，让开发阶段免于打包。理解这条链路之后，再看到脚手架自动生成的一堆配置文件，你就知道每一行大概在解决什么问题了。下一章我们会在这个工程骨架之上，进入组件化开发的具体实践。
