MyBatis 基础

Posted on 2026-09-19，5 min read

上一章用 JdbcTemplate 简化了 JDBC 的样板代码，但 SQL 仍是 Java 里的字符串：条件拼接容易出错，结果集还要手写 RowMapper 逐列取值。MyBatis 换了个思路——把 SQL 搬进 XML 映射文件，由框架负责参数设置与结果封装。本章用一张 tb_user 单表，把「配置 → CRUD → 参数传递 → 结果映射 → 动态 SQL」讲通。

一、为什么需要 MyBatis

手工 JDBC 查一个用户，要写加载驱动、取连接、创建 PreparedStatement、逐个 setXxx 设参、循环 ResultSet 取值，再在 finally 里关闭三层资源；真正属于业务的只有一行 SQL。归纳起来是四个问题：资源管理繁琐、参数与结果靠手搬、SQL 与 Java 耦合、没有缓存复用。

MyBatis 解决的是「自动设参 + 自动映射」：SQL 写在映射文件里，返回值直接声明成 POJO 或 List。它不隐藏 SQL，因此灵活可控，代价是常用 SQL 要自己写。互联网业务因此多选 MyBatis，模型复杂、看重开发速度的项目常选 Hibernate/JPA。

二、两个配置文件与 SqlSessionFactory

配置只有两份。全局配置文件（习惯叫 mybatis-config.xml）管数据源、事务与设置项，并登记映射文件；映射文件（如 UserMapper.xml）写 SQL、参数类型和结果封装类型，一条 SQL 对应一个 statement。

启动时用 SqlSessionFactoryBuilder 读全局配置，构建 SqlSessionFactory；每次操作再从工厂开一个 SqlSession。这可类比 DataSource 与 Connection：工厂长期存活，会话用完必须关闭。

<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE configuration
  PUBLIC "-//mybatis.org//DTD Config 3.0//EN"
  "http://mybatis.org/dtd/mybatis-3-config.dtd">
<configuration>
  <!-- 引入外部配置，之后用 ${key} 引用 -->
  <properties resource="jdbc.properties" />

  <settings>
    <!-- 开启驼峰映射：user_name 自动对应 userName -->
    <setting name="mapUnderscoreToCamelCase" value="true" />
  </settings>

  <environments default="development">
    <environment id="development">
      <transactionManager type="JDBC" />
      <dataSource type="POOLED">
        <property name="driver" value="${driver}" />
        <property name="url" value="${url}" />
        <property name="username" value="${username}" />
        <property name="password" value="${password}" />
      </dataSource>
    </environment>
  </environments>

  <mappers>
    <mapper resource="mapper/UserMapper.xml" />
  </mappers>
</configuration>

全局配置的子元素顺序是强制的：properties → settings → typeAliases → typeHandlers → plugins → environments → mappers。顺序写反会直接报错。映射文件本身是 XML，SQL 里的 &lt;、&amp; 必须写成实体引用。

三、CRUD 与 Mapper 动态代理

原始写法是 UserDaoImpl 持有 SqlSession，再调用 selectOne("UserDaoMapper.queryUserById", id) 这类 API，statement 字符串硬编码在 Java 里。动态代理让「只写接口 + 映射文件」成为可能。

它有四条约定：namespace 等于接口全限定名；statement 的 id 等于方法名；resultType 与返回的元素类型一致；参数类型与接口方法一致（parameterType 通常可省略）。

public interface UserMapper {
    User queryUserById(Long id);
    List<User> queryUserAll();
    int insertUser(User user);
    int updateUser(User user);
    int deleteUserById(Long id);
}

调用时只需 UserMapper mapper = sqlSession.getMapper(UserMapper.class);，随后像调普通接口一样使用。自增主键可用 useGeneratedKeys="true" 加 keyProperty="id" 回写到入参对象，插入后直接 user.getId() 就能拿到。

#{} 与 ${} 的区别是重点。#{} 生成 JDBC 的 ? 占位符并预编译，参数不会被当成 SQL 语法，能防注入，应作为默认选择；${} 是纯字符串替换，只适合拼表名、列名、排序字段，接用户输入等于开注入口子。

参数个数决定写法。单参数时 #{} 里的名字可以随便写；多参数会被放进 Map，默认键是 arg0/arg1 和 param1/param2，必须用 @Param("userName") 显式命名，否则报 Parameter 'userName' not found。稳妥做法是都给参数加 @Param。

四、结果映射与动态 SQL

字段名与属性名不一致是高频故障：库中是 user_name，POJO 是 userName，属性就会一直是 null。解法有三：全局开启驼峰映射，一次配置全局受益；在 SQL 里写 user_name as userName 起别名；或用 resultMap 自定义映射。

第三种写法用 <id> 指定主键，再用 <result column="user_name" property="userName"/> 指定不一致的列。配合 autoMapping="true"，其余同名列会自动匹配。它最重，但也是唯一能表达一对多、多对一关联的写法。

<resultMap id="userMap" type="cn.itcast.mybatis.pojo.User" autoMapping="true">
  <id column="id" property="id" />
  <result column="user_name" property="userName" />
</resultMap>

<select id="search" resultMap="userMap">
  select * from tb_user
  <where>
    <if test="userName != null and userName.trim() != ''">
      and user_name like concat('%', #{userName}, '%')
    </if>
    <if test="age != null">
      and age = #{age}
    </if>
  </where>
</select>

<select id="queryByIds" resultMap="userMap">
  select * from tb_user where id in
  <foreach collection="ids" item="id" open="(" separator="," close=")">
    #{id}
  </foreach>
</select>

动态 SQL 用 OGNL 表达式驱动标签，替代手写字符串拼接。<if test="..."> 按条件追加片段，判空写 userName != null and userName.trim() != ''；<where> 自动去掉开头多余的 and，条件全不成立时不生成 where；<set> 用于 update，自动去掉尾部多余逗号；<choose>/<when>/<otherwise> 只命中第一个成立的分支；<foreach> 遍历集合，用 open/separator/close 拼出 in (...)。

几个必须记住的坑：openSession() 默认不自动提交，增删改后要调用 commit()，否则数据悄悄丢失；模糊查询建议写 concat('%', #{name}, '%')，不要把 % 与 #{} 拼在一起；一级缓存默认开启且无法关闭，作用域是同一个 SqlSession，增删改或 clearCache() 会清空；二级缓存默认关闭，需在映射文件加 <cache/>，且要求 POJO 实现 Serializable，数据在会话提交或回滚后才写入。

小结

MyBatis 的价值不在「替你写 SQL」，而在划清 SQL 与 Java 的边界。全局配置管数据源与映射登记，映射文件管 SQL 与结果封装，Mapper 接口靠动态代理免去实现类，#{} 保证参数安全，动态标签让条件拼接可读可维护。掌握两份配置文件、四条动态代理约定、#{} 与 ${} 的取舍、resultMap 与动态标签的组合，就足以应付绝大多数单表 CRUD 与条件查询。下一章把 MyBatis 交给 Spring 管理，去掉手工创建 SqlSessionFactory 的样板代码。
