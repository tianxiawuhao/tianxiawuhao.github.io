类加载机制

Posted on 2026-09-19，8 min read

你写下的 .java 文件编译后只是磁盘上的 .class 二进制文件，它是怎么变成方法区里的运行时结构、变成能被 new 的 Class 对象的？本章讲清三件事：类加载的完整生命周期、双亲委派模型解决的问题、以及如何用自定义类加载器实现热部署。适合想弄明白 ClassNotFoundException、NoClassDefFoundError 背后机制的读者。

一、类加载的完整生命周期

Java 与 C/C++ 最大的区别之一是：编译期只做语法与符号层面的检查，真正的链接工作被推迟到运行期。JVM 需要在运行时把外部 .class 文件读进来，经过一系列处理转化为内存中的数据结构，这条链路就叫类加载过程。

从类被加载进内存到被卸载出内存，一个类的生命周期包括五个阶段：加载、链接、初始化、使用、卸载。其中链接又细分为验证、准备、解析三个子阶段。加载、验证、准备、解析、初始化这五步通常按顺序开始，但解析阶段为了支持动态绑定（多态），可能在初始化之后才发生。

各阶段做的事可以这样记：

  • 加载：通过类的全限定名获取二进制字节流；把字节流中的静态存储结构转化为方法区的运行时数据结构；在内存中生成一个代表该类的 java.lang.Class 对象，作为方法区数据的访问入口。字节流来源不限于文件，也可以是网络、JAR、动态代理生成，这一点正是自定义加载器的入口。
  • 验证：文件格式、元数据、字节码、符号引用四项校验，确保字节流不危害虚拟机。
  • 准备：为静态字段在方法区分配内存并设 零值。static int a = 10; 在准备阶段后 a 是 0，赋成 10 是初始化阶段的事；只有 static final 常量会在准备阶段直接赋为指定值。
  • 解析：把常量池中的符号引用替换为直接引用（指针、相对偏移量或句柄）。
  • 初始化：执行编译器生成的类构造器 <clinit>() 方法。

初始化阶段是唯一被《Java 虚拟机规范》严格规定「何时必须发生」的阶段，主要触发时机包括：使用 new 实例化对象、读写静态字段、调用静态方法、反射调用、初始化子类时必须先初始化其父类，以及 JDK 7 之后 java.lang.invoke.MethodHandle 解析结果为 REF_getStatic / REF_putStatic / REF_invokeStatic 且对应类未初始化时。此外，虚拟机启动时指定的主类（含 main 方法的类）必须先初始化——注意是「指定的主类」，不是随便哪个类。

关于 <clinit>()，有四个容易考的细节：

  1. 它由编译器收集静态字段赋值与静态代码块语句合并生成，顺序由源码书写顺序决定。因此静态块只能读取写在它之前的静态字段，之后的字段可赋值不可读。
  2. 虚拟机保证子类的 <clinit>() 执行前，父类的 <clinit>() 已执行完毕（接口不要求先执行父接口的）。
  3. <clinit>() 不是必须的：没有静态赋值也没有静态块的类，编译器可以不生成它。
  4. 虚拟机会对 <clinit>() 加锁同步：多线程同时初始化一个类时，只有一个线程执行，其余线程阻塞等待。这个锁也带来了著名的坑——静态块里做耗时操作或死锁，会导致其他线程长时间阻塞。

与 <clinit>() 相对的是实例构造器 <init>()，即构造方法，它在 new 时调用。两者名字相似，触发时机完全不同。

二、类加载器与「类相等」的判定

类加载阶段中「通过全限定名获取二进制字节流」这个动作，由类加载器（ClassLoader）实现。这里有个关键结论：一个类在 JVM 中的唯一性，由「类本身」和「加载它的类加载器」共同确定。每个类加载器都拥有独立的类名称空间，因此判断两个类是否「相等」（equals、isAssignableFrom、instanceof）的前提是它们由同一个类加载器加载。

这也是「同一个 .class 被两个加载器各加载一次，得到两个不同的 Class 对象，互相强转就抛 ClassCastException」的原因——在 JVM 眼里它们就是两个类。

从虚拟机视角看，类加载器只有两种：启动类加载器（Bootstrap ClassLoader，由 C++ 实现，是虚拟机自身的一部分）和其他所有由 Java 实现、继承自 java.lang.ClassLoader 的加载器。从开发者视角看，JDK 8 及以前常见的是三层结构：

  • 启动类加载器：加载 JAVA_HOME/lib 目录，或被 -Xbootclasspath 参数指定路径中的类。它在 Java 代码里拿不到，String.class.getClassLoader() 返回 null。
  • 扩展类加载器：由 sun.misc.Launcher$ExtClassLoader 实现，加载 JAVA_HOME/lib/ext 目录，或被 java.ext.dirs 系统属性指定路径中的类库。
  • 应用程序类加载器：由 sun.misc.Launcher$AppClassLoader 实现，加载用户类路径 classpath 上的类。它通常是程序中的默认加载器。

版本差异要特别注意：JDK 9 引入模块化后，扩展类加载器已被移除，lib/ext 目录与 java.ext.dirs 不再生效，取而代之的是平台类加载器（PlatformClassLoader），它加载的也不再是 ext 目录，而是平台模块。JDK 11 之后启动类加载器也改由 Java 实现（jdk.internal.loader.ClassLoaders$BootClassLoader），但它对上层依然表现为 null。

三、双亲委派模型

类加载器之间不是继承关系，而是组合关系：每个加载器通过 getParent() 持有父加载器引用，setParent() 可以指定。这种层次关系就是双亲委派模型，它在 JDK 1.2 引入。它不是强制约束，JVM 规范并未要求，只是推荐实现方式。

工作过程可以概括为一句话：收到加载请求先交给父加载器，父加载器加载不了，子加载器才自己加载。

  1. 类加载器收到请求，首先检查自己是否已经加载过该类，有则直接返回缓存的 Class。
  2. 没有缓存，就把请求委派给父加载器。
  3. 每一层都重复上述过程，请求最终到达顶层的启动类加载器。
  4. 父加载器无法完成时（自己的搜索范围内找不到），才回退给子加载器尝试加载。

它解决两个问题：保证核心类库唯一（java.lang.Object 无论谁请求都由启动类加载器加载，不会被重复加载）和防止核心 API 被篡改（自定义一个 java.lang.String 放进 classpath，委派机制会让它永远加载不到）。

实现上，这段逻辑写在 ClassLoader.loadClass() 里，源码骨架如下：

protected Class<?> loadClass(String name, boolean resolve)
        throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // 1. 先查缓存：同一个加载器对同一个类只加载一次
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                if (parent != null) {
                    // 2. 委派给父加载器
                    c = parent.loadClass(name, false);
                } else {
                    // 3. 父加载器为 null，说明父是启动类加载器
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器无法完成，落到下面自己加载
            }
            if (c == null) {
                // 4. 父加载器加载不到，才调用自己的 findClass
                c = findClass(name);
            }
        }
        if (resolve) {
            resolveClass(c);
        }
        return c;
    }
}

由此得出正确姿势：遵守双亲委派就继承 ClassLoader 覆盖 findClass(String name)，在方法里读取字节流并调用 defineClass() 生成 Class；打破双亲委派才覆盖 loadClass(String name)。注意向启动类加载器委派时，父加载器用 null 表示。

四、自定义类加载器：从 findClass 到热部署

下面是一个从指定目录读取 .class 文件的加载器。它遵循双亲委派，只在父加载器找不到时，才去 /tmp/plugins 下找：

public class DirClassLoader extends ClassLoader {

    private final String dir;

    public DirClassLoader(String dir) {
        // 父加载器不传，默认是应用程序类加载器
        super(DirClassLoader.class.getClassLoader());
        this.dir = dir;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        String path = dir + "/" + name.replace('.', '/') + ".class";
        try {
            byte[] bytes = Files.readAllBytes(Paths.get(path));
            // defineClass 把字节数组转成 Class 对象，交给 JVM 校验
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }

    public static void main(String[] args) throws Exception {
        // 同一个类，被两个不同的加载器加载，就是两个不同的 Class
        Class<?> c1 = new DirClassLoader("/tmp/plugins").loadClass("demo.User");
        Class<?> c2 = new DirClassLoader("/tmp/plugins").loadClass("demo.User");
        System.out.println(c1 == c2);                        // false
        System.out.println(c1.getClassLoader() == c2.getClassLoader()); // false
    }
}

理解这个例子，就能理解热部署的原理：老版本应用的 Class 对象无法被卸载（有 GC Root 引用）、也无法被就地替换，那么换一个加载器重新加载一遍，得到新的 Class 就等价于「替换了类」。容器就是这样做的——为每个 Web 应用创建一个独立的 WebAppClassLoader，重启应用时丢弃整个加载器，旧类随之在 GC 中被回收。

Tomcat 的加载器顺序是很有意思的例外：它先尝试自己加载（Web 应用自己的 WEB-INF/classes 与 WEB-INF/lib），失败后再委派给父加载器。这是典型的「打破双亲委派」——因为同一个 Tomcat 里跑多个应用，每个应用需要用自己的版本加载同名的类。但它依然会排除 java.* 等核心包，把核心类强行交给启动类加载器。

最后用一个最小例子验证触发时机——注意静态块的打印在 forName 时就出现了，而不是 newInstance 时：

public class Trigger {
    static { System.out.println("clinit 执行"); }   // 类初始化时执行一次
    public static void hello() { System.out.println("hello"); }

    public static void main(String[] args) throws Exception {
        Class<?> c = Class.forName("Trigger");   // 触发初始化，打印 clinit 执行
        c.getMethod("hello").invoke(null);        // 反射调用静态方法
    }
}

最后是几个高频坑。静态块没执行？ <clinit>() 只在实际使用类时触发，只声明该类型的引用或访问 static final 常量都不会触发初始化。ClassNotFoundException 与 NoClassDefFoundError 混着报？ 前者来自显式加载（Class.forName、loadClass）找不到类；后者常是「类第一次初始化失败」之后再被使用——静态块抛异常会先抛 ExceptionInInitializerError，排查时要往前翻第一条异常。热部署时报 OutOfMemoryError: PermGen space（JDK 8 后是 Metaspace）？ 通常是 ThreadLocal 或静态集合持有旧类引用，使加载器无法回收，其加载的整个类空间一起泄漏，用 jmap/MAT 查 WebAppClassLoader 实例数量是有效切入点。getClassLoader() 返回 null 不是 bug，只说明类由启动类加载器加载（如 String），直接链式调用 getResource 会 NPE。Class.forName(name) 与 loadClass(name) 不等价：前者默认初始化类（静态块执行），后者只加载不初始化；注册 JDBC 驱动要用前者，只做反射分析用后者更轻。

小结

类加载是 JVM 把「静态文件」变成「可执行类型」的唯一入口。记住三句话：生命周期是「加载—链接（验证、准备、解析）—初始化—使用—卸载」，初始化由 <clinit>() 负责，准备阶段只给静态字段零值；类的唯一性由「类 + 加载它的加载器」共同决定，跨加载器的同名类无法互换；双亲委派实现在 loadClass 中，覆盖 findClass 是遵守它，覆盖 loadClass 才是打破它。热部署、容器隔离、JDBC 驱动注册这些看似无关的现象，背后都是这套机制在起作用。
