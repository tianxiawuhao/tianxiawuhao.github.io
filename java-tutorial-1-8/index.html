1.8 常用类库

Posted on 2024-07-03，5 min read

写 Java 程序，大部分时间都在调用 JDK 已经写好的类：拼接字符串、把输入的 “18” 变成数字、算两个日期相差几天、对浮点数取整。这些类的集合就是常用类库（API）。本章挑出出场率最高的几个家族：String 与 StringBuilder、八种基本类型的包装类、所有类的祖先 Object、数学工具 Math、日期时间类。下面讲清它们各自解决什么问题、有哪些必须记住的坑。适合已经会写类和方法、能看懂简单泛型语法的读者。示例以 Java 17/21 为基线（Java 8 仍在广泛使用但已非基线），旧写法会保留并注明被哪个版本取代，版本边界单独标注。

一、String：不可变的字符串

String 的第一个关键性质是不可变：对象一旦创建，内容就再也不能被修改。看上去能改的 replace、substring、toUpperCase 其实都返回一个新对象，原对象纹丝不动。这样设计是因为字符串常被共享：常量池里同一份字面量会被无数处引用，若允许改动就会互相污染。不可变还带来线程安全、hashCode 可缓存等好处，这也是 String 常被选作 HashMap 键的原因。

由此引出两个高频问题。第一，比较内容必须用 equals，因为 == 比较的是引用地址。字面量 “hello” 会被放进字符串常量池复用，所以字面量之间 == 常常为真；而 new String("hello") 会在堆上另开内存，== 立即为假。一旦字符串来自输入、拼接或文件，这种“巧合”就彻底失效。若担心空指针，用 Objects.equals(a, b) 更安全。

第二，不要在循环里用 += 拼接。每次 += 都会新建一个 String 并整体复制旧内容，循环 n 次的总代价是 O(n²)。需要澄清的是，单独一句 a + b + c 会被编译器优化成一次 StringBuilder 拼接，所以“加号一定慢”的说法并不准确。真正的问题出在跨迭代的反复创建。

几个细节也常把人绊住。下标从 0 开始，substring(begin, end) 含 begin 不含 end。另外，split 的参数是正则表达式，按字面量竖线或点号分割要写成 "\\|"、"\\."。JDK 9 起（JEP 254，紧凑字符串）字符串内部由 char[] 改为 byte[] 加编码标记（coder）存储，拉丁字符只占 1 字节，“字符串就是一个 char 数组”的说法已不符合实现。

近年新增的字符串 API 也值得用起来，按加入版本分四类：

  • String.join(分隔符, ...) 自 Java 8 起提供。
  • strip()、stripLeading()/stripTrailing()、isBlank()、repeat(int)、lines() 自 Java 11 起加入。其中 strip() 按 Unicode 空白判断，比只认 ASCII 的 trim() 准确；判断“有没有内容”直接用 isBlank()，不必再写 trim().isEmpty()。
  • formatted(args...) 自 Java 15 起提供，等价于 String.format(this, args) 但更适合链式书写。
  • 多行字面量则用文本块（text block，Java 15 正式转正，JEP 378）：以 """ 加换行开头，缩进自动剥离，省掉满屏的 \n 和加号拼接。

二、StringBuilder：可变的字符缓冲区

反复修改字符串就该换成 StringBuilder。StringBuilder 内部维护一个可扩容的字符数组，append、insert、reverse 直接改缓冲区并返回自身，所以能链式书写 sb.append("a").append(1)。要注意 length() 是已存字符数，capacity() 是缓冲区容量。容量不足时会自动扩容并复制旧内容：无参构造的容量是 16，用字符串构造时是“初始字符串长度 + 16”。注意自 Java 9 起 StringBuilder 内部与 String 一样改用紧凑字节数组（byte[] + coder）存储。但紧凑存储只影响内存占用，length() 与 capacity() 依旧以 char 为单位计数。例如 new StringBuilder("你好").capacity() 在 Java 17/21 上返回 18（2 + 16），而不是底层 UTF-16 数组的 36。能预估长度时，用 new StringBuilder(1024) 可以减少扩容；判断缓冲区是否为空，自 Java 15 起可以直接用 isEmpty()，不必再写 length() == 0。

public class StringBuilderDemo {
    public static void main(String[] args) {
        System.out.println(join(new int[]{1, 2, 3}));   // [1, 2, 3]

        StringBuilder sb = new StringBuilder("helloworld");
        sb.reverse();
        System.out.println(sb.toString());              // dlrowolleh
    }

    // 用 StringBuilder 拼接，避免循环里反复创建 String
    public static String join(int[] arr) {
        StringBuilder sb = new StringBuilder();
        sb.append("[");
        for (int i = 0; i < arr.length; i++) {
            if (i > 0) {
                sb.append(", ");
            }
            sb.append(arr[i]);
        }
        return sb.append("]").toString();
    }
}

StringBuffer 的 API 与它几乎相同，区别是所有方法都加了 synchronized，线程安全但更慢。结论：单线程一律用 StringBuilder，只有确实需要多线程共享同一缓冲区时才考虑 StringBuffer。顺带把“遗留类”这条线一次说清：StringBuffer 属于 JDK 1.0 的遗留类，和它同期的还有集合里的 Vector、Hashtable（把 synchronized 加在每个方法上的“同步集合”），以及最早的迭代接口 Enumeration。Enumeration 已被 Iterator 取代：Iterator 方法名更短、支持 remove()，并与增强 for 循环和整个集合框架配套。新代码的对应关系是 Vector→ArrayList、Hashtable→HashMap、Enumeration→Iterator（通常直接写 for-each）、StringBuffer→StringBuilder；确需并发安全时改用 java.util.concurrent 下的 ConcurrentHashMap、CopyOnWriteArrayList 等，或 Collections.synchronizedXxx 包装。淘汰“同步集合”的理由不只是“有锁就慢”：它们只保证单个方法原子，复合操作照样要外部加锁，等于锁得更重、吞吐更低（下一章集合框架会细讲）。

三、包装类：基本类型与对象之间的桥

八种基本类型不是对象，不能放进集合、不能调用方法、也无法表示“没有值”，于是每种都有一个对应的包装类：byte→Byte、short→Short、int→Integer、long→Long、float→Float、double→Double、char→Character、boolean→Boolean。它们主要做三件事：字符串转基本类型（Integer.parseInt("18")）、基本类型转字符串（String.valueOf(18)）、提供常量与工具方法（Integer.MAX_VALUE）。从 JDK 5 起两者可自动转换，即自动装箱与自动拆箱。自动装箱写 Integer i = 10;，编译器会调用 Integer.valueOf(10)；自动拆箱写 int n = i;，会调用 i.intValue()。

Integer a = 127, b = 127;
Integer c = 128, d = 128;
System.out.println(a == b);        // true，命中 -128~127 的缓存
System.out.println(c == d);        // false，超出缓存范围
System.out.println(c.equals(d));   // true，比较内容才可靠

Integer mayBeNull = null;
// int x = mayBeNull;              // 自动拆箱，运行时报 NullPointerException
int y = mayBeNull == null ? 0 : mayBeNull;
System.out.println(y);             // 0

这里有一个已经过时的写法必须点名：new Integer(127)（以及 new Double(...)、new Long(...)、new Boolean(...) 等同族构造方法）。这些包装类构造方法自 Java 9 起被弃用，随后又被标记为“待删除”（deprecated for removal，即计划在将来的版本中移除）。要特别注意：“标记为待删除”并不等于“已经移除”——截至 Java 17/21，这些构造方法依然存在，代码照旧能编译，只是会给出 [removal] 警告，真正的移除要等未来的版本。现行写法是静态工厂 Integer.valueOf(127)，或者在需要 Integer 的地方直接写 Integer i = 127; 交给自动装箱。

Integer oldOne = new Integer(127);      // 已弃用：总是新建对象，绕过缓存
Integer newOne = Integer.valueOf(127);  // 现行写法：命中 -128~127 缓存，返回同一实例
Integer boxed = 127;                    // 自动装箱，编译后同样是 Integer.valueOf(127)
System.out.println(oldOne == newOne);   // false：构造方法不复用缓存实例

两者的语义差别正好落在上面那段缓存上：构造方法每次都在堆上另开一个对象，绕过了缓存；valueOf 在缓存区间内返回同一实例。做类型转换时也一样，用 Integer.parseInt/Integer.valueOf，不要用构造方法。

上面的输出暴露了两个陷阱。第一，Integer.valueOf 会缓存 −128 到 127 的对象，区间内 == 恰好为真，超出范围就变成两个新对象，因此包装类的比较永远要用 equals。第二，包装类引用可以为 null，直接参与运算会因自动拆箱触发空指针。

四、Object、Math 与日期时间

Object 是所有类的根父类，所以参数写成 Object 就能接收任意对象。它有三个方法值得关注。toString() 决定对象被打印时的样子，默认是“类名@十六进制哈希”，调试时几乎一定要重写。equals(Object) 默认仍是 ==；重写 equals 就必须同时重写 hashCode，并满足“equals 为真则哈希相同”，否则对象存进 HashSet，或当作 HashMap 的键时，会出现“存进去却查不到”。

Math 里的方法全是静态方法：abs 取绝对值，ceil/floor 分别取上取整与下取整，pow(a, b) 求幂，sqrt 求平方根（别和立方根 cbrt 混淆），max/min 求最值。生成 [min, max] 区间内的随机整数写成 min + (int) (Math.random() * (max - min + 1))，其中 random() 返回 [0.0, 1.0) 的随机数。Math.round 的参数为 double 时返回 long，规则是“加 0.5 后向下取整”，所以 Math.round(-1.5) 得 -1 而非 -2。另外，Math.random() 内部共用一个 java.util.Random 实例，高并发下会有竞争，可以按场景换用：

  • 线程内取随机数用 ThreadLocalRandom.current()（Java 7 起）。
  • Java 17 起（JEP 356）还提供了可插拔的 RandomGenerator 家族，可以按算法名取实现，例如 RandomGeneratorFactory.of("L64X128MixRandom").create()；需要可复现的随机序列时给 create 传种子即可。

日期时间 API 分两代，分界线是 Java 8。旧的一代是 java.util.Date + Calendar + SimpleDateFormat（JDK 1.0/1.1 的遗留设计），坑很多：Calendar 的月份从 0 开始（1 月是 0），Date.getYear() 返回“年份减 1900”，这些方法本身也早已被标注为弃用。SimpleDateFormat 不是线程安全的——它内部用一个可变的 Calendar 字段保存解析中间状态，作为静态字段被多线程共享会得到错乱结果；因为历史包袱不得不用时，就每次新建实例，或用 ThreadLocal<SimpleDateFormat> 隔离。Java 8 引入的 java.time（JSR-310，含 LocalDate、LocalDateTime、Instant、Duration、ZonedDateTime 等）全部不可变、线程安全，格式化用的 DateTimeFormatter 同样不可变，可以放心声明为 static final 复用——这正是它相对 SimpleDateFormat 最直接的收益。新代码应统一用 java.time；只有对接老接口或老数据库类型时，才用 Date.from(instant)、date.toInstant()、java.sql.Timestamp.valueOf(localDateTime) 这类桥接方法做转换，不要再让 Calendar 出现在新代码里。

import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.format.DateTimeFormatter;
import java.time.temporal.ChronoUnit;

public class DateTimeDemo {
    public static void main(String[] args) {
        LocalDate today = LocalDate.now();
        LocalDate birthday = LocalDate.of(2000, 1, 1);
        System.out.println(ChronoUnit.DAYS.between(birthday, today)); // 活了几天

        // 模式串里 MM 是月份、mm 是分钟，别写反
        DateTimeFormatter fmt = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
        String text = LocalDateTime.now().format(fmt);
        System.out.println(LocalDateTime.parse(text, fmt));
    }
}

若不得不维护旧 API 写的代码，请至少守住三条：Calendar 取月份后自行加 1；SimpleDateFormat 不要作为静态共享字段（需要复用就放进 ThreadLocal）；模式串里 MM 与 mm 要分清。新写的代码直接用 java.time + DateTimeFormatter，这三条坑一个都不会遇到。

五、小结

本章几条主线的共同线索是“什么时候复用、什么时候新建”。String 不可变因而可以安全共享，代价是修改就得新建，于是有了 StringBuilder。基本类型轻量但不是对象，于是有了包装类，代价是缓存造成的 == 假象与拆箱空指针。Object 的默认实现按地址与哈希判断，重写时要成对处理；Math 是纯静态工具；日期时间上，新的 java.time 用不可变换来了线程安全。记住三条纪律即可避开大部分坑：比较内容用 equals、循环拼接用 StringBuilder、日期时间优先 java.time。最后是一条版本纪律：StringBuffer、Vector、Hashtable、Enumeration、SimpleDateFormat 都是 JDK 1.0/1.1 时代的遗留类，新代码一律绕开；包装类构造方法（new Integer(...) 之类）自 Java 9 起弃用，改用 valueOf。下一章进入集合框架，equals 与 hashCode 的约定将成为理解 HashMap 去重与查找的关键。
