基于PostgreSQL的时序数据库TimescaleDB的基本用法和概念

Posted on 2023-04-18，10 min read

时序数据是按时间顺序存储的数据。TimescaleDB 是一个开源的、扩展了 PostgreSQL 的时序数据库扩展。本文详细介绍基于 PostgreSQL 的时序数据库 TimescaleDB 的基本用法和概念，需要的朋友可以参考。

时序数据是指按照时间顺序存储的数据。它在很多领域得到广泛应用，例如物联网、日志分析、金融交易等。为了高效处理时序数据，TimescaleDB应运而生。TimescaleDB是一个开源的、扩展了PostgreSQL的时序数据库扩展，它结合了关系型数据库和时序数据库的优势，提供了更好的时序数据管理和分析能力。

时间序列数据的挑战： 时间序列数据是指按时间顺序收集和记录的数据，如传感器、日志、金融数据等。这类数据在现实生活中广泛存在，但对于传统数据库系统来说，处理大规模和高性能的时间序列数据是一项具有挑战性的任务。

TimescaleDB的出现： TimescaleDB是一个构建在PostgreSQL之上的开源时间序列数据库，它采用了一种创新的方法来解决传统数据库在处理时间序列数据方面的限制。TimescaleDB利用了PostgreSQL的强大功能，并通过扩展超级表的方式提供了更好的性能和可扩展性。

一、TimescaleDB概述

TimescaleDB 是一个以 PostgreSQL 扩展（extension）形式发布的时序数据库：它本身不是一套独立数据库，而是一组补齐了 PostgreSQL 在时序场景下短板的能力。它复用了关系型数据库的事务、SQL、生态与运维工具，并针对时序数据做了两件事——按时间（可选再按空间）自动分区的超表（hypertable），以及会在后台自动维护的连续聚合（continuous aggregate）。

需要先区分两套叫法：官方中文资料里 hypertable 常被译作“超表”，也有“超级表”的译法；它并不等于普通表，但用法上又几乎与普通表一致——这正是它最容易混淆的地方，下一节会专门对比。

版本提示：本文示例以 TimescaleDB 2.x 为准。2.x 与 1.x 在连续聚合的创建语法、保留策略函数、压缩与分布式超表等方面差异较大：1.x 使用 create_continuous_aggregate() 函数创建连续聚合，2.x 改为 CREATE MATERIALIZED VIEW … WITH (timescaledb.continuous)；1.x 用 add_drop_chunks_policy()，2.x 用 add_retention_policy()。阅读老资料时请先确认版本。

二、安装和配置

1. 安装TimescaleDB插件

TimescaleDB 以 PostgreSQL 扩展的形式加载，因此前提是已经装好对应大版本的 PostgreSQL，并具备管理员权限。安装包需要与 PostgreSQL 主版本号严格对应（例如 PostgreSQL 13 用 timescaledb-2-postgresql-13）。以 Debian/Ubuntu 为例：

# 添加 TimescaleDB 官方软件源（2.x）
curl -s https://packagecloud.io/timescale/timescaledb/gpgkey | sudo gpg --dearmor -o /etc/apt/trusted.gpg.d/timescaledb.gpg
echo "deb https://packagecloud.io/timescale/timescaledb/ubuntu/ focal main" | sudo tee /etc/apt/sources.list.d/timescale_timescaledb.list
# 更新软件源并安装与 PostgreSQL 13 匹配的扩展包
sudo apt-get update
sudo apt-get install timescaledb-2-postgresql-13
# 让 PostgreSQL 预加载 TimescaleDB（写入 shared_preload_libraries）
sudo timescaledb-tune --quiet --yes
sudo systemctl restart postgresql

注意两点：一是 timescaledb-postgresql-13 这类不带 2- 的包名属于 1.x 时代的命名，在新安装中已不再使用；二是 shared_preload_libraries 必须包含 timescaledb，否则后台 worker（负责连续聚合刷新、保留策略、压缩策略）不会启动，很多功能会静默失效。

2. 创建TimescaleDB数据库

加载扩展之后的数据库用法与普通 PostgreSQL 数据库无异：

-- 创建数据库并连接（psql 元命令，需在 shell 中执行）
CREATE DATABASE mydatabase;
\c mydatabase
-- 在库中加载 TimescaleDB 扩展
CREATE EXTENSION IF NOT EXISTS timescaledb CASCADE;
-- 查看版本，示例输出：2.11.2
SELECT extversion FROM pg_extension WHERE extname = 'timescaledb';

3. 创建超表（hypertable）

超表是 TimescaleDB 的基本数据管理单元：先按普通表建表（必须含一个时间列），再把它转换成超表。转换之后，写入与查询仍走同一张逻辑表，物理分区由扩展自动维护。以下示例建立一个记录温湿度的超表：

-- 先创建普通表
CREATE TABLE conditions (
    time        TIMESTAMPTZ       NOT NULL,
    location    TEXT              NOT NULL,
    temperature DOUBLE PRECISION  NULL,
    humidity    DOUBLE PRECISION  NULL
);
-- 再转换为超表：按 time 列做时间分区，每 1 天一个 chunk
SELECT create_hypertable('conditions', 'time',
                         chunk_time_interval => INTERVAL '1 day');

create_hypertable(hypertable, time_column_name) 中，第一个参数是表名（可以是 regclass，即字符串形式），第二个参数是时间列名；chunk_time_interval 决定单个 chunk 覆盖的时间跨度，取值范围决定分区粒度。

在 2.x 中，create_hypertable 还有一个常用参数 migrate_data => true，用于把表中原有数据搬进分区结构；从 2.13 起它被标记为弃用（推荐的做法是先建空表再转换）。

超表与普通表的差异

  • 分区方式不同。普通表是一棵堆表；超表由若干 chunk 组成，每个 chunk 都是 _timescaledb_internal schema 下的真实表，默认按时间范围切分，还可以再叠加一维空间分区（如 location），把不同设备/站点的数据分到不同 chunk 上。
  • 约束和索引受限制。超表上的唯一索引/主键必须包含时间分区列（以及所有空间分区列），因为唯一性只能保证在单个 chunk 内。跨 chunk 的全局唯一约束无法建立。
  • UPDATE/DELETE 仍可用但有代价。语法与普通表完全相同，但更新会把行标记为新版本，历史 chunk 一旦被压缩（compressed），其中的行不可再更新，必须先解压。
  • 删除整段时间是廉价操作。按时间删除走 drop_chunks()，直接 DROP 整个 chunk，无需逐行 DELETE 和 VACUUM。
  • 插入有额外开销。写入时需要先定位（或新建）目标 chunk，单行插入的吞吐在极高并发下不如调优良好的原生分区表，批量写入（COPY、多值 INSERT）更能发挥优势。
  • 外键。超表可以作为外键的引用方，但其他表引用超表的外键在 2.x 中长期不完整支持，设计时不要把超表当作被引用的维表。

三、数据写入和查询

1. 超表的分区粒度

分区粒度是超表性能的第一杠杆：chunk 太大，单块索引膨胀、查询要扫描过多数据；chunk 太小，chunk 数量爆炸，规划与元数据开销上升。经验法则是让一个 chunk 装下最近一段时间的活跃数据，使热点 chunk 能整个缓存在内存中，一般让单 chunk 控制在内存的 25% 以内。

-- 建表时指定：按 1 个月一个 chunk
SELECT create_hypertable('conditions', 'time',
                         chunk_time_interval => INTERVAL '1 month');

-- 也可以事后调整（只影响此后新建的 chunk，已有 chunk 不变）
SELECT set_chunk_time_interval('conditions', INTERVAL '7 days');

-- 增加一维空间分区：按 location 把同一个时间区间的数据再切分
SELECT add_dimension('conditions', by_hash('location', 4));

-- 查看当前的分区维度配置
SELECT hypertable_name, column_name, dimension_number,
       time_interval, num_partitions
FROM timescaledb_information.dimensions
WHERE hypertable_name = 'conditions';

需要纠正一个常见误解：add_dimension() 不是“按月增加分区”，它增加的是一维空间分区，且必须在超表为空或者经过专门处理时执行。时间分区的粒度由 create_hypertable 的 chunk_time_interval / set_chunk_time_interval() 控制。

2. 关于多节点与副本

1.x 曾提供基于 attach_data_node 的多节点（分布式超表）能力，2.x 中该功能一直处于社区版实验/受限状态，并在 2.13 起被弃用，官方主推单节点加流复制的部署形态。因此不建议把 attach_data_node 当作“创建副本”的手段：高可用应由 PostgreSQL 自身的流复制、或云托管的副本机制来提供。下面这条语句在 2.13 及以后仅作为历史 API 存在：

-- 2.13 起已弃用的分布式超表 API，不要在新项目中使用
-- SELECT attach_data_node('dn2', 'conditions');

3. 插入数据

向超表插入数据与向普通表插入数据完全一致，批量插入时建议使用多值 INSERT 或 COPY，让每一批数据尽量落在少数几个 chunk 上：

INSERT INTO conditions (time, location, temperature, humidity)
VALUES ('2023-06-29 06:00:00', 'New York', 25.4, 60.2);

4. 更新和删除数据

语法与普通表相同，但要注意历史 chunk 若已被压缩，需要先解压才能改动：

-- 将温度大于 30 的记录统一设为 30.0
UPDATE conditions SET temperature = 30.0 WHERE temperature > 30.0;
-- 删除湿度小于50的记录
DELETE FROM conditions WHERE humidity < 50.0;

5. 时间分桶与聚合

time_bucket(bucket_width, ts) 是 TimescaleDB 提供的核心函数：它把时间戳对齐到固定宽度的桶，语义上等价于“按任意时间粒度做 GROUP BY”，是普通 PostgreSQL 的 date_trunc 无法替代的（后者只支持月、日、小时等固定粒度）。

-- 计算最近一小时每 5 分钟的平均温度
SELECT time_bucket('5 minutes', time) AS bucket,
       AVG(temperature)        AS average_temperature
FROM conditions
WHERE time > NOW() - INTERVAL '1 hour'
GROUP BY bucket
ORDER BY bucket;

-- 指定桶的起点（对齐到整点，而不是默认的 2000-01-01 起算）
SELECT time_bucket('1 hour', time, TIMESTAMPTZ '2023-01-01 00:00:00+08') AS bucket,
       COUNT(*) AS samples
FROM conditions
GROUP BY bucket
ORDER BY bucket;

此外还有 time_bucket_gapfill()（补齐空桶，避免折线图断点）以及 first() / last() / histogram() 等面向时序的聚合函数，都可与 GROUP BY bucket 搭配使用。

6. 查询和过滤数据

过滤数据时使用常规 SQL 即可，关键是把时间条件下推：只有时间列上的范围条件才能触发分区裁剪（chunk pruning），让优化器跳过不相干的 chunk。

-- 会触发分区裁剪：只扫描覆盖该时间段的 chunk
SELECT *
FROM conditions
WHERE time > NOW() - INTERVAL '1 day'
  AND temperature > 25.0;

如果只写 WHERE temperature > 25.0 而不带时间条件，就只能扫描全部 chunk，超表的分区优势会完全消失。

四、连续聚合

连续聚合（continuous aggregate）本质上是一种会被自动增量刷新的物化视图：它把 time_bucket 级别的聚合结果预先算好并物化，查询时只扫描已物化的结果，因此不会随原始数据量线性变慢。它由后台 worker 按策略定时重算最近一段区间，这块工作对应用是透明的。

1. 创建连续聚合（2.x 语法）

-- 第一步：创建带 continuous 选项的物化视图
CREATE MATERIALIZED VIEW conditions_hourly
WITH (timescaledb.continuous) AS
SELECT time_bucket('1 hour', time) AS bucket,
       location,
       AVG(temperature)          AS avg_temperature,
       MAX(temperature)          AS max_temperature
FROM conditions
GROUP BY bucket, location
WITH NO DATA;

注意 timescaledb.continuous 这个选项名，以及 2.x 中不存在 create_continuous_aggregate() 这个函数（那是 1.x 的写法，且其第二个参数必须是字符串形式的查询体，容易写错）。

2. 添加自动刷新策略

视图建好后不会自己更新，需要注册刷新策略（也可用 refresh_continuous_aggregate() 手动补刷历史区间）：

-- 每 30 分钟刷新一次，覆盖 3 小时前到 1 小时前之间的区间
SELECT add_continuous_aggregate_policy('conditions_hourly',
       start_offset      => INTERVAL '3 hours',
       end_offset        => INTERVAL '1 hour',
       schedule_interval => INTERVAL '30 minutes');

-- 手动补刷指定区间（如回填最近 3 天），常用于数据回灌之后
CALL refresh_continuous_aggregate('conditions_hourly',
                                  now() - INTERVAL '3 days',
                                  now());

-- 查看现有策略
SELECT application_name, schedule_interval, config
FROM timescaledb_information.jobs
WHERE proc_name = 'policy_refresh_continuous_aggregate';

end_offset 的作用是留出一段“迟到数据缓冲区”：只有比 now() - end_offset 更早的数据才认为已经稳定，可以安全物化；比它更新的区间属于实时区，查询时由物化结果与原始数据合并计算。因此查询连续聚合时最好显式带上时间条件，否则实时区要靠扫描原始数据补齐，性能会退化。

五、分区管理与存储优化

这一节把超表的日常运维动作集中起来：查看与删除 chunk、压缩、保留策略。

1. 查询所有 chunk

-- 查看 conditions 的所有 chunk 及其时间范围
SELECT hypertable_name, chunk_name,
       range_start, range_end,
       is_compressed
FROM timescaledb_information.chunks
WHERE hypertable_name = 'conditions'
ORDER BY range_start;

2. 删除 chunk

-- 删除 1 个月之前的整块数据（直接 DROP 物理表，秒级完成）
SELECT drop_chunks('conditions', older_than => INTERVAL '1 month');

3. 压缩（compression）

压缩是 2.x 的重点特性，也是与普通表差异最大的地方之一：它不是 PostgreSQL 的行级 TOAST 压缩，而是把一个 chunk 内的数据按列转成批次（batch）存储，配合列内编码（delta-delta、Gorilla、字典编码等），典型压缩率可达 10 倍以上。代价是压缩后的 chunk 只支持读与批量写入，不再支持单行 UPDATE/DELETE。

-- 为超表开启压缩并指定分段列与排序方式
ALTER TABLE conditions SET (
  timescaledb.compress,
  timescaledb.compress_segmentby = 'location',
  timescaledb.compress_orderby   = 'time DESC'
);

-- 自动压缩超过 7 天的 chunk
SELECT add_compression_policy('conditions', INTERVAL '7 days');

-- 也可以手动压缩/解压指定 chunk
SELECT compress_chunk(c => show_chunks('conditions', older_than => INTERVAL '7 days'));
-- SELECT decompress_chunk('_timescaledb_internal._hyper_1_2_chunk');

compress_segmentby 决定数据分段方式，段内再按 compress_orderby 有序存放，因此按 location 过滤的查询在压缩 chunk 上依然高效；反之，如果查询条件既不带 segmentby 列也不带时间范围，压缩会显著拖慢查询。

4. 数据保留策略

保留策略只是“定时执行 drop_chunks”的封装，它由后台作业周期性地删除过期 chunk，因此不会产生大规模 DELETE 带来的膨胀和 VACUUM 压力：

-- 自动删除 90 天前的 chunk
SELECT add_retention_policy('conditions', INTERVAL '90 days');

-- 也可以直接写在超表选项里（2.15 起支持）
ALTER TABLE conditions SET (timescaledb.retention_policy = 'INTERVAL 90 days');

-- 查看、修改、移除策略
SELECT job_id, proc_name, config, schedule_interval
FROM timescaledb_information.jobs
WHERE hypertable_name = 'conditions';

-- SELECT alter_job(1000, schedule_interval => INTERVAL '1 day');
-- SELECT remove_retention_policy('conditions');

部署上还有一个容易忽略的点：连续聚合、压缩、保留策略都依赖 background worker，所以 shared_preload_libraries 必须正确配置，否则策略会注册成功但永远不会执行；此外 TimescaleDB 开源版（Apache-2 许可的部分）与社区版/Timescale Cloud 在部分特性上仍有差异，选型时需要确认目标特性属于哪一档。

六、综合使用示例

1. 创建超表并插入数据

假设我们有一个名为conditions的超表，包含时间、地点、温度和湿度字段。以下示例演示了如何创建该超表，并向其中插入一些数据：

CREATE TABLE conditions (
   time        TIMESTAMPTZ       NOT NULL,
   location    TEXT              NOT NULL,
   temperature DOUBLE PRECISION  NULL,
   humidity    DOUBLE PRECISION  NULL
);
SELECT create_hypertable('conditions', 'time',
                         chunk_time_interval => INTERVAL '1 day');
INSERT INTO conditions (time, location, temperature, humidity)
VALUES
   ('2023-06-29 06:00:00', 'New York', 25.4, 60.2),
   ('2023-06-29 07:00:00', 'New York', 26.8, 58.9),
   ('2023-06-29 08:00:00', 'New York', 28.3, 57.1);

2. 查询最新的N条数据

假设我们想要查询最新的3条温度数据。以下示例演示了如何使用LIMIT子句和ORDER BY子句进行查询：

SELECT *
FROM conditions
ORDER BY time DESC
LIMIT 3;

3. 执行时间范围内的聚合查询

假设我们想要计算过去一小时内每分钟的平均温度。以下示例展示了如何使用时间序列聚合函数和时间戳桶函数进行查询：

SELECT time_bucket('1 minute', time) AS minute,
      AVG(temperature) AS average_temperature
FROM conditions
WHERE time > NOW() - INTERVAL '1 hour'
GROUP BY minute;

补充：以上聚合每次都实时扫描原始数据。如果这类查询是高频的，应改为在连续聚合上查询（见第四节），把计算成本前移到刷新阶段。

七、小结一下

使用 TimescaleDB 可以高效地存储和查询时序数据，并借助连续聚合与分区、压缩、保留策略进一步提高性能和可维护性。与同类数据库相比，TimescaleDB 有一些令人兴奋的特性：

  • 它建立在PostgreSQL之上(目前最好的开源关系数据库)。如果您的项目已经在运行PostgreSQL，Timescale可以重点考虑。
  • 通过熟悉的SQL语法进行查询，从而减少了学习难度。
  • 极快的写入速度——按官方基准，单节点每秒可支撑数十万到数百万行插入（具体取决于硬件与批量大小）。
  • 数十亿行乃至 PB 级数据，对 TimescaleDB 而言也不在话下。
  • 模式非常灵活——既可以使用关系模式，也可以选择无模式（schema-less，如 JSONB 列）。

与 InfluxDB、ClickHouse 的取舍

  • TimescaleDB：优势是与 PostgreSQL 完全同构——事务、外键、JOIN、视图、丰富的扩展（PostGIS、pg_stat_statements）和运维工具都能直接用，写入即可见、无最终一致性问题。适合“业务数据与时序数据要放在一起 JOIN”“团队已有 PG 运维经验”“需要事务与强一致”的场景。短板是高基数场景下的存储压缩比与极限扫描吞吐不如专门的列式引擎，超大规模（数十 TB 以上）时运维复杂度上升。
  • InfluxDB：专用时序引擎，自带采集生态（Telegraf）、类 SQL 的 Flux/InfluxQL 以及降采样与保留策略，开箱即用。适合指标监控（metrics）这类纯时序、Schema 变化少、写入量极大的场景。短板是 JOIN 与分析型 SQL 能力弱，跨度量关联困难，且 3.x 与 2.x 的 API 差异较大。
  • ClickHouse：列式 MPP 引擎，聚合扫描吞吐与压缩率通常最强，适合日志分析、宽表 OLAP 与超大规模明细聚合。短板是不擅长高频单行更新/删除（只能靠异步 Mutation 或 ReplacingMergeTree 折中），缺少真正的事务，点查与“写入后立即可见”的体验不如 PostgreSQL。

粗略的选型建议：需要与业务库强一致地 JOIN、或团队已深度绑定 PostgreSQL，选 TimescaleDB；纯监控指标、追求开箱即用，选 InfluxDB；海量日志或宽表 OLAP、以聚合扫描为主，选 ClickHouse。三者并非互斥，不少架构里 ClickHouse 做分析归档、TimescaleDB 做在线时序与业务关联，也是常见组合。

假设我们有一个名为conditions的超级表，包含时间、地点、温度和湿度字段。以下示例演示了如何创建该超级表，并向其中插入一些数据：

CREATE TABLE conditions (
   time        TIMESTAMPTZ       NOT NULL,
   location    TEXT              NOT NULL,
   temperature DOUBLE PRECISION  NULL,
   humidity    DOUBLE PRECISION  NULL
);
SELECT create_hypertable('conditions', 'time');
INSERT INTO conditions (time, location, temperature, humidity)
VALUES
   ('2023-06-29 06:00:00', 'New York', 25.4, 60.2),
   ('2023-06-29 07:00:00', 'New York', 26.8, 58.9),
   ('2023-06-29 08:00:00', 'New York', 28.3, 57.1);

2. 查询最新的N条数据

假设我们想要查询最新的3条温度数据。以下示例演示了如何使用LIMIT子句和ORDER BY子句进行查询：

SELECT *
FROM conditions
ORDER BY time DESC
LIMIT 3;

3. 执行时间范围内的聚合查询

假设我们想要计算过去一小时内每分钟的平均温度。以下示例展示了如何使用时间序列聚合函数和时间戳桶函数进行查询：

SELECT time_bucket('1 minute', time) AS minute,
      AVG(temperature) AS average_temperature
FROM conditions
WHERE time > NOW() - INTERVAL '1 hour'
GROUP BY minute;
