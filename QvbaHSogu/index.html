OOM

Posted on 2021-09-13，7 min read

OOM 并不是一种异常，而是一族错误：同样是 OutOfMemoryError，报错关键字不同，根因、定位手段和修法完全不同。下面这张图先给出全局分类，再按图中的顺序逐个拆解。

Stack overflow

public class StackOverFlowErrorDemo {
    public static void main(String[] args) {
        StackOverFlowError();
    }

    private static void StackOverFlowError() {
        StackOverFlowError();
    }
}

Exception in thread "main" java.lang.StackOverflowError
	at com.example.interview.oom.StackOverFlowErrorDemo.StackOverFlowError(StackOverFlowErrorDemo.java:14)

递归调用自身方法，不断向栈内压入栈帧，直到撑破栈空间，重复次数不确定（默认约 1 万个栈帧，取决于 -Xss 与每帧大小）。

原因

栈是线程私有的，栈深度由 -Xss（默认约 512KB~1MB）决定。栈溢出不是“内存不够”，而是调用层次太深：无限递归、递归没有正确终止条件、深层嵌套的 JSON/XML 解析都会触发。它与 OutOfMemoryError: unable to create new native thread 恰好相反——前者是单个线程的栈太深，后者是线程数量太多。

定位与复现

异常栈会直接打出重复的调用行，找出第一处“重复出现的自己”就是递归入口；jstack <pid> 可直接看到线程栈的完整调用链。-Xss256k 可以把复现所需递归次数压到更低。

Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
	at com.example.interview.oom.JavaHeapSpaceDemo.main(JavaHeapSpaceDemo.java:18)

字符串常量池与普通对象都位于堆中，循环拼接 String 会产生大量临时对象，一次性申请超大数组则会直接超出剩余空间。

原因

一是真不够用：堆上限（-Xmx）小，而业务峰值对象多，扩容即可；二是内存泄漏：对象被静态集合、缓存、ThreadLocal、监听器等长期引用，GC 无法回收，堆随运行时间单调上涨；三是大对象，如一次性把整张大表或整个文件读进内存。

定位与复现

先用 jstat -gcutil <pid> 1000 观察老年代使用率是否“涨上去就下不来”，再 jmap -histo:live <pid> | head -20 看实例数最多的类，最后 jmap -dump:format=b,file=heap.hprof <pid> 导出堆转储，用 MAT 打开，按 Dominator Tree 与 Leak Suspects 找到持有链；线上不便导出时可用 Arthas 的 heapdump、dashboard 代替。复现参数即上面示例的 -Xmx10m -Xms10m，把它调大后异常消失，说明是容量而非泄漏。

/**
 * @author wuhao
 * @desc -Xmx20m -Xms10m -XX:+PrintGCDetails

该错误由 HotSpot 的 GC 开销判断机制抛出：并行/串行收集器若发现连续多次 GC 中，GC 线程占用 CPU 时间超过 98%，而回收到的堆空间不足 2%，就认定“再 GC 也没有意义”，直接抛出此错误，避免程序在近乎无进展的 GC 上空转。它是 Java heap space 的“近亲”，但触发条件更苛刻，通常意味着堆几乎全满且存活对象极多。

因此示例中把最大堆设得比初始堆大（-Xmx20m -Xms10m）是为了给 GC 留出扩容空间；如果两值相等，堆无法扩张，往往直接变成 Java heap space 异常。

定位与规避

用 jstat -gcutil <pid> 1000 查看 FGC 次数与 FGCT 总耗时，若 Full GC 每秒都在发生且老年代回收后占用不降，即可确认。定位手段与内存泄漏一致（jmap -histo:live + MAT）。参数 -XX:-UseGCOverheadLimit 可以关掉这个检查，但它只是把错误推迟成真正的 Java heap space，属于排查辅助而非解决方案。

allocateDirect 分配的字节缓冲区，中文叫做直接缓冲区（DirectByteBuffer）；用 allocate 分配的 ByteBuffer 叫做堆字节缓冲区（HeapByteBuffer）。

其实根据类名就可以看出，HeapByteBuffer所创建的字节缓冲区就是在jvm堆中的，即内部所维护的java字节数组。而DirectByteBuffer是直接操作操作系统本地代码创建的内存缓冲数组（c、c++的数组）。

HeapByteBuffer 底层其实是 Java 的字节数组，而 Java 字节数组是一个 Java 对象，其内存由 JVM 的堆进行管理，那么不可避免的是 GC 时年轻代的 Eden、Survivor 到老年代的各种复制以及回收……当字节数组比较小的时候还好说，如果是大对象，那么对 JVM 的 GC 来说是一个很大的负担……而使用 DirectByteBuffer，则是把字节数组交给操作系统管理（堆外内存）

原因

直接内存不受 -Xmx 约束，上限由 -XX:MaxDirectMemorySize 决定（未显式设置时默认等于最大堆值）。NIO 网络框架、Netty 的池化缓冲、文件映射都会占用它。常见根因是 DirectByteBuffer 被回收得不够快：它依赖关联的 Cleaner 在 GC 时释放堆外内存，堆内存压力不大时 GC 很少发生，堆外就先被耗尽；也可能是 -Xmx 调得很大而机器物理内存有限。

定位与复现

堆转储里只能看到 java.nio.DirectByteBuffer 这个“壳”，真正的内存量应看 jmap -histo:live <pid> 中的 DirectByteBuffer 数量，以及 JVM 的 Native Memory Tracking（-XX:NativeMemoryTracking=detail 配合 jcmd <pid> VM.native_memory summary）中的 Internal 项；Arthas 的 dashboard 也能看到堆外内存。定位到使用方后，通常是显式设置 -XX:MaxDirectMemorySize 与系统 -Dio.netty.maxDirectMemory 之类的上限，并检查是否有缓冲区未释放。

OutOfMemoryError：Unable to create new native thread

public class UnableToCreateToNativeThreadDemo {
   
    public static void main(String[] args) {
        for (int i = 0; ; i++) {
            System.out.println("================ i=" + i);
            new Thread(() -> {
                try {
                    Thread.sleep(Integer.MAX_VALUE);
                } catch (InterruptedException e) {
                    e.printStackTrace();
                }
            }, "" + i).start();
        }
    }
}

Linux 一般用户最多可以创建 1024 个线程，不要在电脑上随意尝试。注意异常关键字是 new native thread，早期资料中写作 “Unable to create to native thread” 属于笔误，以 JDK 实际输出为准。异常栈中常会附带 pthread_create (1040KB stack) failed: Try again 之类的信息，说明是操作系统层面拒绝创建。

原因

每个 Java 线程都要向操作系统申请一个真实的原生线程，并预留线程栈空间。触顶通常有三个来源：一是代码无界地 new Thread() 或线程池用了 Executors.newCachedThreadPool() 这类无上限队列/无上限线程的实现；二是用户级限制 ulimit -u（默认常见 1024）或 /proc/sys/kernel/threads-max、kernel.pid_max 达到上限；三是 -Xss 过大，导致线程栈把进程虚拟内存提前吃掉。

定位与复现

jstack <pid> | grep -c 'java.lang.Thread.State' 统计线程数，jstack -l <pid> 观察是否大量线程卡在同一段业务代码；系统侧用 ulimit -u、cat /proc/sys/kernel/threads-max、ps -eLf | wc -l 交叉确认。修复方向是改用有界线程池并设置合理的最大线程数与队列，而不是简单调大 ulimit。

原因

Metaspace 存放类的元数据（类结构、方法、常量池引用等），它在 JDK 8 中取代了永久代，位于本地内存而非堆，因此不受 -Xmx 限制。类被不断加载却无法卸载时就会溢出：CGLIB/ByteBuddy/ASM 动态生成代理类（示例中的 Enhancer 且 setUseCache(false)，每次都生成新类）、脚本引擎反复编译、热部署类加载器泄漏，都会持续推高 Metaspace。日志中的 Full GC (Last ditch collection) 说明 JVM 已做最后一次挣扎式回收仍未奏效。

定位与复现

用 jstat -gcutil <pid> 1000 观察 M（Metaspace 使用率）与 MC/MU 容量，持续上涨即确认；jmap -clstats <pid> 列出类加载器及其加载的类数量，能直接找到“谁在造类”；必要时 -verbose:class 或 Arthas 的 classloader、sc 命令辅助。复现参数为 -XX:MetaspaceSize=8m -XX:MaxMetaspaceSize=8m；线上通常设一个合理上限（如 -XX:MaxMetaspaceSize=256m）让它尽早暴露问题，而不是完全不设限导致吃光机器内存。

OutOfMemoryError：PermGen space

JDK 7 及以前的永久代溢出，关键字为 PermGen space，对应参数 -XX:PermSize 与 -XX:MaxPermSize。永久代在堆内、由 GC 管理，存放类的元数据与字符串常量池，容量固定且难以回收。JDK 8 起永久代被移除，元数据移入 Metaspace（本地内存），字符串常量池移入堆，因此新项目看到 PermGen space 基本可以判定为“跑在 JDK 7 或更早的版本上”或“使用了旧版 -XX:PermSize 参数而在 JDK 8 被忽略”。排查思路与 Metaspace 一致，重点是找出不断加载类的元凶。

其他常见类型

除上述类型外，JDK 还定义了 OutOfMemoryError: Requested array size exceeds VM limit（数组长度超过虚拟机允许的上限，通常意味着代码算错了长度）与 OutOfMemoryError: Out of swap space？（物理内存与交换分区都被耗尽，需要看操作系统日志与容器内存限制）。在容器中还要特别注意：JVM 若不识别 cgroup 限制（JDK 8u191 之前），会按宿主机内存计算默认堆大小，从而被 OOM Killer 直接杀死，表现为进程无异常栈地消失，此时应显式设置 -Xmx 或升级 JDK 并启用 -XX:+UseContainerSupport。
