HTTP 协议与浏览器原理

Posted on 2026-09-19，7 min read

HTTP 是浏览器与服务器之间唯一的对话语言。你写的每一个 Servlet、每一次 response.sendRedirect()、每一个 Set-Cookie，最终都要落成一段符合 HTTP 格式的文本。这段文本穿过网络，被浏览器解释成页面、缓存和登录状态。

本章把这条链路讲清楚：一次请求响应长什么样，状态码与缓存头如何决定浏览器的下一步动作。此外还会说明 Cookie 与 Session 怎样在一个无状态协议上拼出“记住我”，并串一遍浏览器从收到字节到画出像素的渲染流程。适合已经能跑通 Hello Servlet、但对“为什么刷新一下就要重新登录”“为什么改了 CSS 页面没变”这类问题还没有答案的读者。

一、一次 HTTP 交互到底交换了什么

HTTP 是基于 TCP 的应用层协议，默认端口 80（HTTPS 为 443），采用“请求—响应”模式：客户端先发一个请求，服务端回一个响应，一问一答。HTTP 本身不保存任何上下文，服务端处理完就“忘记”你是谁，这就是“无状态”。它也是后面 Cookie 与 Session 存在的全部理由。

一个请求由三部分组成：请求行（方法、路径、协议版本）、若干请求头、可选的实体内容（请求体）。响应的结构完全对称：状态行（协议版本、状态码、原因短语）、若干响应头、可选的实体内容。

GET /books/java.html?name=abc&password=xyz HTTP/1.1
Host: localhost:8080
User-Agent: Mozilla/5.0
Accept: text/html,application/xhtml+xml
Referer: http://localhost/links.html
Cookie: JSESSIONID=0CCD096E7F8D97B0BE608AFDC3E1931E

HTTP/1.1 200 OK
Server: Apache-Coyote/1.1
Content-Type: text/html;charset=UTF-8
Content-Length: 2291
Cache-Control: no-cache

<html><body>...</body></html>

请求方法里 GET 与 POST 最常用：GET 把参数拼在 URL 后面，POST 把参数放进请求体；浏览器地址栏回车、点超链接都是 GET，要发 POST 得靠表单或 AJAX。这里有两个流传很广的说法需要纠正。

一是“GET 参数不能超过 1K”。协议并没有规定 URL 长度上限，1K 只是早年某些浏览器与服务器的实现限制；今天常见实现的上限在 2KB 到 8KB 之间，具体取决于浏览器和 Tomcat 的 maxHttpHeaderSize。二是“POST 数据量无限制”。POST 同样受服务端配置约束，Tomcat 默认的表单体积上限是 2MB（maxPostSize，Tomcat 10 起为 maxPostSize 与 maxSwallowSize 配合）。所以结论是：要传大量数据用 POST 更合适，但别以为它没有边界。

二、状态码：服务端给出的结论

状态码是三位十进制数，按首位分五类。1xx 表示请求已收到、还需继续（如 101 切换协议）；2xx 表示成功（200 正常返回，204 成功但无实体内容）。3xx 表示需要客户端再做一步（301 永久重定向、302 临时重定向、304 资源未修改、307/308 保留原方法重定向）。4xx 表示客户端的问题（400 参数错误、401 未认证、403 已认证但无权限、404 资源不存在、405 方法不允许）。5xx 表示服务端出错（500 内部异常、502 网关收到无效响应、503 暂时不可用）。

需要特别注意 3xx：它的含义不是“请求需要进一步细化”，而是“请你换一个地址或使用本地副本”。其中 304 最容易被误解：它不是“资源被移动了”，而是服务端告诉浏览器“你本地缓存的那份还没过期”，因此 304 响应必须不带实体内容。Java 里修改状态码与响应头的方式如下：

// 1. 重定向：302 + Location 响应头
response.sendRedirect(request.getContextPath() + "/welcome.jsp");
return; // 必须 return，否则后面的代码继续写响应，可能抛 IllegalStateException

// 2. 手动指定状态码
response.setStatus(HttpServletResponse.SC_NOT_FOUND); // 404
response.setContentType("text/html;charset=UTF-8");
response.getWriter().println("找不到你要的页面");

// 3. 禁止浏览器缓存当前动态页面：三个头一起用最保险
response.setHeader("Cache-Control", "no-cache, no-store, must-revalidate");
response.setHeader("Pragma", "no-cache");
response.setDateHeader("Expires", 0);

常见坑有两个。一是 sendRedirect() 之后忘记 return，导致响应已经提交又被继续写入。二是用 setDateHeader("Expires", -1) 这类写法，-1 会被格式化成 1969 年的时间；虽然多数浏览器也能理解，但规范做法是传 0 或一个已经过去的时间戳。

三、缓存：把响应留在浏览器

浏览器缓存分两层。“强缓存”直接命中本地副本，不发请求。Cache-Control: max-age=3600 表示这份响应 3600 秒内可以直接用；no-cache 表示可以存但每次都要回源验证；no-store 表示完全不许存（适合含敏感信息的接口）。Expires 是 HTTP/1.0 时代的同类头，值是绝对时间，受客户端本地时钟影响，所以现在以 Cache-Control 为准。

“协商缓存”会发一次请求，但如果资源没变，服务端只回 304 和响应头，不重传正文。浏览器带上 If-Modified-Since（对应 Last-Modified）或 If-None-Match（对应 ETag）询问，服务端比对后决定回 200 还是 304。在 Servlet 里给静态资源加缓存头，最合适的位置是过滤器：

public class CacheFilter implements Filter {
    @Override
    public void doFilter(ServletRequest req, ServletResponse resp, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest request = (HttpServletRequest) req;
        HttpServletResponse response = (HttpServletResponse) resp;
        String uri = request.getRequestURI();
        if (uri.endsWith(".css") || uri.endsWith(".js") || uri.endsWith(".png")) {
            // 静态资源 7 天内直接用本地副本
            response.setHeader("Cache-Control", "max-age=604800");
            response.setDateHeader("Expires", System.currentTimeMillis() + 604800_000L);
        } else {
            // 动态页面走协商缓存
            response.setHeader("Cache-Control", "no-cache");
        }
        chain.doFilter(req, resp);
    }
}

调试时最常踩的坑是“明明改了 CSS，页面却没变”，原因通常是强缓存还没到期。解决办法是在开发阶段给 HTML、CSS、JS 统一发 max-age=0 或 no-cache，在生产环境给静态资源文件名加内容哈希（如 app.9f2c1a.css）实现永久缓存。两者结合，既不牺牲性能，也不用要求用户“按 Ctrl+F5”。

四、Cookie 与 Session：把状态找回来

Cookie 是服务端通过 Set-Cookie 响应头发给浏览器的一小段键值文本。浏览器保存后，在后续对同一站点的请求里通过 Cookie 请求头自动带回。除了 name 与 value，常用属性如下：

  • maxAge：正数为持久 Cookie，负数或默认 ‑1 为会话 Cookie，0 表示删除。
  • path 与 domain：决定这颗 Cookie 能被哪些请求带上，路径需以 / 结尾，domain 需以 . 开头。
  • secure：仅 HTTPS 传输。
  • HttpOnly：禁止 JavaScript 读取，防 XSS 盗取。
  • SameSite：限制跨站携带，防 CSRF。

Cookie 的唯一标识是 domain + path + name，三者任一不同就是两颗不同的 Cookie。同名同域同路径再次 addCookie() 会覆盖旧值，所以“修改”与“删除”都靠覆盖实现，且 path、domain 必须与原 Cookie 完全一致，否则删不掉。

Session 把状态放在服务端，浏览器只保存一个标识。服务端为每个会话创建 HttpSession 对象，并自动下发名为 JSESSIONID 的 Cookie，其值就是 session.getId()。注意几个容易写错的点：request.getSession() 等价于 getSession(true)，会话不存在时会新建；只有 getSession(false) 才可能返回 null。会话 Cookie（maxAge 为 ‑1）的存活范围是整个浏览器进程。同一浏览器的多个标签页、通过链接打开的新窗口都共享同一个 JSESSIONID，因此共享会话。浏览器关闭后再打开才会拿到新会话，不同浏览器、隐私窗口之间也互相独立。

因为 Session 依赖 Cookie，一旦用户禁用 Cookie，就要退化成 URL 重写：把 jsessionid 拼进地址，由 encodeURL() 自动判断是否需要这么做。

// 首次请求后记录登录状态，并显示上次访问时间
HttpSession session = request.getSession();
session.setAttribute("user", loginUser);          // 服务端保存对象，比 Cookie 安全
session.setMaxInactiveInterval(30 * 60);          // 30 分钟无活动即失效（单位：秒）

Cookie last = CookieUtils.getCookieByName(request.getCookies(), "lastVisitTime");
String tip = (last == null) ? "欢迎首次访问" : "你上次访问时间是：" + last.getValue();
Cookie cookie = new Cookie("lastVisitTime", new Date().toLocaleString());
cookie.setMaxAge(30 * 24 * 60 * 60);              // 30 天，写入磁盘的持久 Cookie
cookie.setPath("/");                              // 整个站点可见
cookie.setHttpOnly(true);                         // 禁止 JS 读取
response.addCookie(cookie);

// 会话失效，用于"注销"
session.invalidate();

关于有效期：Cookie 的 maxAge 单位是秒，由浏览器判断；服务端再次读取时只能拿到 name 与 value，path、domain 等属性不会被提交回来。Session 的超时时间可以在 web.xml 中用 <session-timeout> 配置，单位是分钟，而 setMaxInactiveInterval() 的单位是秒，两处别搞混。容器默认值方面，Tomcat 的 conf/web.xml 给的是 30 分钟；也有资料写 20 分钟，属于版本与配置差异，请以本机容器的实际配置为准。

五、多实例部署后的会话共享：Spring Session

「四」里的 HttpSession 是 Servlet 容器提供的：数据默认存在当前 JVM 的堆内存里，只靠 Cookie 里的 JSESSIONID 关联。单机部署看不出问题，一旦把应用部署成多个实例，问题立刻出现——用户第一次请求落在实例 A，Session 建在 A 的内存里；下一次请求被负载均衡分到实例 B，B 找不到这个 JSESSIONID，于是把用户当成未登录，重新发一个会话 ID。表现就是“登录成功，刷新一下又要重新登录”，而且时好时坏。

常见的临时办法是把某个用户固定打到同一台机器上，也就是会话粘滞（sticky session）。它依赖网关或负载均衡器的 hash 规则，代价是：实例重启或缩容时，它承载的会话全部丢失；扩容后新实例分不到流量，热点实例依然热；做灰度发布、滚动更新时几乎必然掉登录态。所以粘滞只能算权宜之计，正解是把会话数据从单机内存搬到所有实例都能访问的共享存储里。

Spring Session 就是官方给出的方案：它用一层 Filter 包装原始的 HttpServletRequest，把 getSession() 的读写重定向到共享存储（Redis、JDBC 等），上层业务代码完全不用改。关键点是：引入依赖并配置后，它自动接管 HttpSession——控制器里拿到的 HttpSession 已由 Spring Session 实现，setAttribute、invalidate 的语义与原来一致。

接入与配置：@EnableRedisHttpSession

以 Redis 为例，依赖只需 spring-session-data-redis（内部通过 spring-boot-starter-data-redis 使用 Lettuce 连接），版本跟随 Spring Boot BOM 管理即可；若是独立管理，这一系列以 3.x 为主，具体补丁版本以官方为准。

<dependency>
    <groupId>org.springframework.session</groupId>
    <artifactId>spring-session-data-redis</artifactId>
    <version>3.x</version>   <!-- 建议交给 Spring Boot BOM 管理，具体版本以官方为准 -->
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>

然后加一个配置类。Boot 3.x 用的是 jakarta.*，注解位置与旧教程里的 javax.* 不同，照抄老代码会直接编译不过：

@Configuration
@EnableRedisHttpSession(maxInactiveIntervalInSeconds = 1800) // 30 分钟无活动过期
public class SessionConfig {

    @Bean
    public RedisSerializer<Object> springSessionDefaultRedisSerializer() {
        // 用 JSON 存会话，见下一小节的取舍
        ObjectMapper mapper = new ObjectMapper();
        mapper.activateDefaultTyping(
                BasicPolymorphicTypeValidator.builder().allowIfBaseType(Object.class).build(),
                ObjectMapper.DefaultTyping.NON_FINAL);
        return new GenericJackson2JsonRedisSerializer(mapper);
    }
}

对应的连接与命名空间配置：

spring:
  data:
    redis:
      host: 127.0.0.1
      port: 6379
      # password: your-password
      database: 0
  session:
    redis:
      namespace: myapp:session   # Redis 中的键前缀，多应用共用一个库时必须区分
      flush-mode: on_save        # 请求结束时统一写回，减少 Redis 往返
server:
  servlet:
    session:
      timeout: 30m               # 容器会话超时兜底；@EnableRedisHttpSession 的显式值优先

启动后可以用 redis-cli 验证：登录一次，执行 keys myapp:session* 应能看到会话键，其类型是 Hash；用一个实例写入、另一个实例读取，应能直接命中。若键没有出现，优先检查是否真的走了 Spring Session 的 Filter（例如自定义 Filter 顺序把它挤到了后面），而不是先怀疑 Redis。

序列化：JDK 序列化与 JSON 序列化的取舍

Spring Session 默认使用 JDK 序列化（JdkSerializationRedisSerializer）。它的优点是接入零成本，任何实现了 Serializable 的对象都能存；缺点是存储内容是二进制，redis-cli 里几乎读不出内容，排障困难，而且对象类结构一旦改动（加字段、改包名）旧会话反序列化就会失败。更麻烦的是它把类名写进字节流，等于给反序列化留了一个攻击面。

生产上更推荐 JSON 序列化，即 GenericJackson2JsonRedisSerializer：值可读、跨语言、跨版本升级时迁移成本低，调试时能直接看到 Session 里有哪些属性。代价是需要在 JSON 里保留类型信息（否则 getAttribute() 还原不出原始类型），因此要开启 Jackson 的 default typing；上面的 BasicPolymorphicTypeValidator 限定了允许反序列化的基类型，不要图省事写成 LaissezFaireSubTypeValidator，那会重新打开反序列化漏洞。另外，存进 Session 的对象需要有无参构造与标准 getter／setter，对象过大时还应评估“是否真的该放进会话”。

两种序列化混用会直接报错，切换时最好清理一次旧会话键（myapp:session*），避免上线后集中出现反序列化异常。

过期时间与 Spring Security 的联动

过期时间有三处会影响结果，优先级从高到低是：@EnableRedisHttpSession(maxInactiveIntervalInSeconds = ...) 的显式值、server.servlet.session.timeout 配置、容器默认值。语义与原生 Session 一致，都是“无活动”而非“绝对时长”：每次请求都会刷新 Redis 键的 TTL。若配置值小于 60 秒，Spring Session 会直接报错，这是为了避免误配把会话瞬间清空。

与 Spring Security 一起使用时，登录态并不以业务对象的形式存在，而是以 SPRING_SECURITY_CONTEXT 为键存进同一个会话。因此只要 Spring Session 生效，SecurityContext 就随之共享，多实例下不会出现“A 实例已登录、B 实例匿名”的问题。要注意两点：一是序列化配置必须能正确处理 SecurityContextImpl 这类对象，JDK 序列化天然支持，切到 JSON 时要确认 default typing 已开启；二是“按用户名强制下线”需要查找到某个用户的全部会话，RedisIndexedSessionRepository 会维护 principal 索引，但它依赖 Redis 的键空间通知，生产环境需要确认该能力可用（部分托管 Redis 会关闭或延迟通知），否则索引不会建立。常用做法是：给会话加 FindByIndexNameSessionRepository.PRINCIPAL_NAME_INDEX_NAME 属性，再通过 findByPrincipalName() 定位并逐个 deleteById()。

最后提醒一句使用边界：Spring Session 解决的是“多实例共享会话”，它不会让会话变成永久存储，也不适合放大量业务数据——会话应当保持小而短命，真正的持久状态仍然放在数据库里。

响应字节流到达浏览器后，先按 Content-Type 里的 charset 解码成字符，然后进入渲染管线。渲染管线分为如下几步：

  • 解析 HTML 生成 DOM 树，解析 CSS 生成 CSSOM 树，两者合并成渲染树（不可见元素如 display:none 不会进入）。
  • 计算每个盒子的位置与大小，这一步叫布局或回流。
  • 填充颜色与文字，即绘制。
  • 按层合成并显示。

理解这条链路就能解释日常现象。<link rel="stylesheet"> 会阻塞渲染，因为浏览器不想先画一版没有样式的页面。普通 <script> 会阻塞 HTML 解析，因为它可能用 document.write 改写文档；加 defer 表示解析完再按顺序执行，加 async 表示下载完就执行且顺序不确定。频繁触发回流与重绘的样式属性（如 width、top）代价远高于只触发合成的属性（如 transform、opacity），这也是动画优先用 transform 的原因。

把这条链路和前面的知识连起来看：一次页面加载就是“缓存判断 → 请求 → 响应 → 渲染”的重复循环。Cookie、状态码、缓存头都在这个循环里各管一段，任何一段理解错了，表现都是“页面看起来不对”，而不是一句清晰的报错。

小结：本章沿着一次真实交互走了一遍。HTTP 用“请求行 + 头 + 体”和“状态行 + 头 + 体”这两段对称的文本承载全部通信；状态码是服务端给出的结论，3xx 要留意 304 不带正文。缓存分为强缓存（Cache-Control / Expires）与协商缓存（Last-Modified / ETag），开发时关缓存，上线后用内容哈希。Cookie 通过 Set-Cookie 与 Cookie 头在客户端存小段文本，其唯一性由 domain、path、name 共同决定，属性错误会导致覆盖和删除失效。Session 把状态放在服务端，只靠 JSESSIONID 关联；getSession() 会创建会话，只有 getSession(false) 才可能返回 null。最后，浏览器按“解析 → 渲染树 → 布局 → 绘制 → 合成”的流程把字节变成像素。把这些环节串起来，再遇到登录态丢失、页面不更新这类问题，你就有了一条可排查的路径。

六、浏览器拿到响应后做了什么

响应字节流到达浏览器后，先按 Content-Type 里的 charset 解码成字符，然后进入渲染管线。渲染管线分为如下几步：

  • 解析 HTML 生成 DOM 树，解析 CSS 生成 CSSOM 树，两者合并成渲染树（不可见元素如 display:none 不会进入）。
  • 计算每个盒子的位置与大小，这一步叫布局或回流。
  • 填充颜色与文字，即绘制。
  • 按层合成并显示。

六、浏览器拿到响应后做了什么

  • 解析 HTML 生成 DOM 树，解析 CSS 生成 CSSOM 树，两者合并成渲染树（不可见元素如 display:none 不会进入）。
  • 计算每个盒子的位置与大小，这一步叫布局或回流。
  • 填充颜色与文字，即绘制。
  • 按层合成并显示。

理解这条链路就能解释日常现象。<link rel="stylesheet"> 会阻塞渲染，因为浏览器不想先画一版没有样式的页面。普通 <script> 会阻塞 HTML 解析，因为它可能用 document.write 改写文档；加 defer 表示解析完再按顺序执行，加 async 表示下载完就执行且顺序不确定。频繁触发回流与重绘的样式属性（如 width、top）代价远高于只触发合成的属性（如 transform、opacity），这也是动画优先用 transform 的原因。

把这条链路和前面的知识连起来看：一次页面加载就是“缓存判断 → 请求 → 响应 → 渲染”的重复循环。Cookie、状态码、缓存头都在这个循环里各管一段，任何一段理解错了，表现都是“页面看起来不对”，而不是一句清晰的报错。

六、浏览器拿到响应后做了什么

小结：本章沿着一次真实交互走了一遍。HTTP 用“请求行 + 头 + 体”和“状态行 + 头 + 体”这两段对称的文本承载全部通信；状态码是服务端给出的结论，3xx 要留意 304 不带正文。缓存分为强缓存（Cache-Control / Expires）与协商缓存（Last-Modified / ETag），开发时关缓存，上线后用内容哈希。Cookie 通过 Set-Cookie 与 Cookie 头在客户端存小段文本，其唯一性由 domain、path、name 共同决定，属性错误会导致覆盖和删除失效。Session 把状态放在服务端，只靠 JSESSIONID 关联；getSession() 会创建会话，只有 getSession(false) 才可能返回 null。最后，浏览器按“解析 → 渲染树 → 布局 → 绘制 → 合成”的流程把字节变成像素。把这些环节串起来，再遇到登录态丢失、页面不更新这类问题，你就有了一条可排查的路径。
