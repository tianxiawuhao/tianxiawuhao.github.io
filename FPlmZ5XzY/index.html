Go语言指针详解

Posted on 2023-02-14，16 min read

与 Java 只提供“引用”不同，Go 语言把指针作为一等类型交给程序员：可以取变量地址，可以通过指针修改原变量，但不能对指针做算术运算（除非使用 unsafe）。它也不同于 C/C++：指针不能越界偏移，指向的对象由垃圾回收器管理，不需要手动 free。Go 语言允许你控制特定集合的数据结构、分配的数量以及内存访问模式，这对于构建运行良好的系统非常重要；做系统编程、操作系统或网络应用时，指针更是绕不开的一环。

指针（pointer）在Go语言中可以被拆分为两个核心概念：

  • 类型指针，允许对这个指针类型的数据进行修改，传递数据可以直接使用指针，而无须拷贝数据，类型指针不能进行偏移和运算。
  • 切片，由指向起始元素的原始指针、元素数量和容量组成。

受益于这样的约束和拆分，Go 语言的指针类型变量既拥有指针高效访问的特点，又不会发生指针偏移，从而避免了非法修改关键数据的问题；同时，垃圾回收也比较容易对不发生偏移的指针进行检索和回收。

切片比裸指针更强大，也更安全：切片访问越界时运行时会抛出 panic 并打印堆栈（index out of range）；而 Go 的指针本身不支持偏移，也就不存在 C 语言那种“指针越界改写相邻内存”的途径——真正危险的只剩解引用 nil 指针（panic：invalid memory address or nil pointer dereference）以及滥用 unsafe。

C/C++中的指针

说到 C/C++ 中的指针，会让许多人“谈虎色变”，尤其是对指针的偏移、运算和转换。

其实，指针正是 C/C++ 语言拥有极高性能的根本所在，操作大块数据和做偏移时既方便又高效。因此，操作系统依然主要用 C 语言及指针特性编写。

C/C++ 中指针饱受诟病的根本原因是指针的运算和内存释放，C/C++ 语言中的裸指针可以自由偏移，甚至可以在某些情况下偏移进入操作系统的核心区域，我们的计算机操作系统经常需要更新、修复漏洞的本质，就是为解决指针越界访问所导致的“缓冲区溢出”的问题。

要明白指针，需要知道几个概念：指针地址、指针类型和指针取值，下面将展开详细说明。

认识指针地址和指针类型

一个指针变量保存的是某个值的内存地址。指针本身占用的字节数只取决于目标平台的字长：32 位平台（如 GOARCH=386）为 4 字节，64 位平台（如 amd64、arm64）为 8 字节，与它所指向的值的大小无关。用 var p *int 声明指针后，其默认值为 nil（空指针），表示“不指向任何变量”。指针变量通常缩写为 ptr。

每个变量在运行时都拥有一个地址，它代表变量在内存中的位置。在变量名前加 & 操作符即可取得该变量的内存地址（取地址操作），格式如下：

ptr := &v   // v 的类型为 T

其中 v 代表被取地址的变量，变量 v 的地址用变量 ptr 接收；ptr 的类型为 *T，称为 T 的指针类型，* 代表指针。注意只能对“可取地址”的值取地址：字面量与常量不行（&42 无法编译），map 元素、接口中取出的值同样不可取地址；例外是复合字面量，&Circle{}、&[]int{1, 2} 都允许直接取地址。

指针实际用法，可以通过下面的例子了解：

package main
import (
    "fmt"
)
func main() {
    var cat int = 1
    var str string = "banana"
    fmt.Printf("%p %p", &cat, &str)
}

运行结果：

0xc042052088 0xc0420461b0

代码说明如下：

  • var cat int = 1，声明整型变量 cat。
  • var str string = "banana"，声明字符串变量 str。
  • fmt.Printf("%p %p", &cat, &str)，使用 fmt.Printf 的动词%p打印 cat 和 str 变量的内存地址，指针的值是带有0x十六进制前缀的一组数据。

提示：变量、指针和地址三者的关系是，每个变量都拥有地址，指针的值就是地址。

从指针获取指针指向的值

当使用&操作符对普通变量进行取地址操作并得到变量的指针后，可以对指针使用*操作符，也就是指针取值，代码如下。

package main
import (
    "fmt"
)
func main() {
    // 准备一个字符串类型
    var house = "Malibu Point 10880, 90265"
    // 对字符串取地址, ptr类型为*string
    ptr := &house
    // 打印ptr的类型
    fmt.Printf("ptr type: %T\n", ptr)
    // 打印ptr的指针地址
    fmt.Printf("address: %p\n", ptr)
    // 对指针进行取值操作
    value := *ptr
    // 取值后的类型
    fmt.Printf("value type: %T\n", value)
    // 指针取值后就是指向变量的值
    fmt.Printf("value: %s\n", value)
}

运行结果：

ptr type: *string
address: 0xc0420401b0
value type: string
value: Malibu Point 10880, 90265

取地址操作符&和取值操作符*是一对互补操作符，&取出地址，*根据地址取出地址指向的值。

变量、指针地址、指针变量、取地址、取值的相互关系和特性如下：

  • 对变量进行取地址操作使用&操作符，可以获得这个变量的指针变量。
  • 指针变量的值是指针地址。
  • 对指针变量进行取值操作使用*操作符，可以获得指针变量指向的原变量的值。

使用指针修改值

通过指针不仅可以取值，也可以修改值。

前面已经演示了使用多重赋值的方法进行数值交换，使用指针同样可以进行数值交换，代码如下：

package main
import "fmt"
// 交换函数
func swap(a, b *int) {
    // 取a指针的值, 赋给临时变量t
    t := *a
    // 取b指针的值, 赋给a指针指向的变量
    *a = *b
    // 将a指针的值赋给b指针指向的变量
    *b = t
}
func main() {
// 准备两个变量, 赋值1和2
    x, y := 1, 2
    // 交换变量值
    swap(&x, &y)
    // 输出变量值
    fmt.Println(x, y)
}

运行结果：

2 1

*操作符作为右值时，意义是取指针的值，作为左值时，也就是放在赋值操作符的左边时，表示 a 指针指向的变量。其实归纳起来，*操作符的根本意义就是操作指针指向的变量。当操作在右值时，就是取指向变量的值，当操作在左值时，就是将值设置给指向的变量。

如果在 swap() 函数中交换操作的是指针值，会发生什么情况？可以参考下面代码：

package main
import "fmt"
func swap(a, b *int) {
    b, a = a, b
}
func main() {
    x, y := 1, 2
    swap(&x, &y)
    fmt.Println(x, y)
}

运行结果：

1 2

结果表明，交换是不成功的。swap() 交换的只是形参 a、b 自身保存的地址，交换后形参的地址确实互换了，但 main 里的 x、y 完全不受影响。可以用卡片来理解：桌上摊开两张写着房子地址的卡片，交换卡片并不会对房子本身做任何改动，只有走进房子换掉里面的东西（*a = *b）才会真正改变原变量。这也说明 Go 的参数传递永远是值传递，传入指针时复制的也只是地址。

示例：使用指针变量获取命令行的输入信息

Go语言内置的 flag 包实现了对命令行参数的解析，flag 包使得开发命令行工具更为简单。

下面的代码通过提前定义一些命令行指令和对应的变量，并在运行时输入对应的参数，经过 flag 包的解析后即可获取命令行的数据。

【示例】获取命令行输入：

package main
// 导入系统包
import (
    "flag"
    "fmt"
)
// 定义命令行参数
var mode = flag.String("mode", "", "process mode")
func main() {
    // 解析命令行参数
    flag.Parse()
    // 输出命令行参数
    fmt.Println(*mode)
}

将这段代码命名为 main.go，然后使用如下命令行运行：

go run main.go --mode=fast

命令行输出结果如下：

fast

代码说明如下：

  • var mode = flag.String("mode", "", "process mode")，通过 flag.String，定义一个 mode 变量，这个变量的类型是 *string。后面 3 个参数分别如下：
    • 参数名称：在命令行输入参数时，使用这个名称。
    • 参数值的默认值：与 flag 所使用的函数创建变量类型对应，String 对应字符串、Int 对应整型、Bool 对应布尔型等。
    • 参数说明：使用 -help 时，会出现在说明中。
  • flag.Parse()，解析命令行参数，并将结果写入到变量 mode 中。
  • fmt.Println(*mode)，打印 mode 指针所指向的变量。

由于之前已经使用 flag.String 注册了一个名为 mode 的命令行参数，flag 底层知道怎么解析命令行，并且将值赋给 mode*string 指针，在 Parse 调用完毕后，无须再从 flag 获取值，直接通过自己注册的 mode 指针（*string）即可拿到最终的值。代码运行流程如下图所示。

创建指针的另一种方法——new() 函数

Go 语言还提供了另一种创建指针变量的方法，格式如下：

new(类型)

一般这样写：

package main

import "fmt"

func main() {
	str := new(string) // *string，指向零值 ""
	*str = "Go语言教程"
	fmt.Println(*str) // Go语言教程
}

new(T) 会为该类型分配内存并清零，返回指向零值的 *T，适用于任意类型（含数组与结构体）：p := new([3]int) 得到的是全部元素为 0 的数组指针。等价的常见写法是取复合字面量的地址 p := &Circle{Radius: 1}，区别是后者可以顺便带上初值。

new 与 make 的区别

最容易混淆的是 new 和 make：共同点是都分配内存，区别在于返回值与适用类型。

对比项new(T)make(T, …)
返回值*T（指针）T 本身，不是指针
适用类型任意类型，如 int、结构体、数组仅 slice、map、chan
初始化程度清零，返回指向零值的指针完成运行时所需的内部初始化（如 slice 的长度与容量、map 的哈希表）
典型写法p := new(bytes.Buffer)s := make([]int, 0, 8)、m := make(map[string]int)

为什么 make 返回的不是指针？因为 slice、map、chan 的底层结构由运行时维护，用户拿到的是内含指针的描述符，本身已经很轻量。反过来 new(map[string]int) 虽然能编译，得到的是指向 nil map 的指针，直接写入 (*p)["k"] = 1 仍会 panic，必须先 *p = make(map[string]int)，所以几乎没有人这样用。

这段输出有两处细节值得留意：第 2 行 %!p(main.A={...}) 是动词用错的结果——%p 只能用于指针，把结构体值 a 直接传进去就会打印这种占位提示，正确写法是 %p 配 &a；另外输出中的地址仅作示例，每次运行都不同，长行折行也不影响结论。还有一处规范问题：示例里的 B{"ptr-str-1"} 是不带字段名的字面量，能编译但 go vet 会提示 composite literal uses unkeyed fields，规范写法是 B{Str: "ptr-str-1"}。

指针接收者与值接收者：方法集规则

Go 没有 C++ 那样的隐式 this，方法的接收者既可写成值也可写成指针，差别不只是性能：

package main

import "fmt"

type Circle struct {
	Radius float64
}

// 值接收者：拿到的是副本，修改不影响调用者
func (c Circle) Area() float64 {
	return 3.14159 * c.Radius * c.Radius
}

// 指针接收者：可以修改原对象
func (c *Circle) Scale(k float64) {
	c.Radius *= k
}

type Shaper interface {
	Area() float64
}

func main() {
	c := Circle{Radius: 1}
	c.Scale(2) // 等价于 (&c).Scale(2)，编译器自动取地址
	fmt.Println(c.Area(), c.Radius) // 3.14159 2

	var s Shaper = c // Circle 实现了 Area（值接收者），合法
	s = &c          // *Circle 的方法集同样包含 Area
	fmt.Println(s.Area())
}

方法集（method set）的规则决定了“谁能调用、谁满足接口”：

方法定义值 T 可调用指针 *T 可调用接口实现
值接收者 func (t T) M()是是T 与 *T 都满足
指针接收者 func (t *T) M()仅当该值可取地址（编译器自动插入 &）是只有 *T 满足

由此可推出两个常见坑：

  • 对只有指针接收者方法的类型写 var s Shaper = Circle{} 会编译失败，提示 Circle does not implement Shaper (Area method has pointer receiver)，改成 &Circle{} 即可。
  • 不可寻址的值不能调用指针接收者方法。例如 m := map[string]Circle{} 时 m["a"].Scale(2) 无法编译（cannot call pointer method on m["a"]），因为 map 元素不可取地址；正确做法是先取出到局部变量，改完再写回：c := m["a"]; c.Scale(2); m["a"] = c。接口中取出的值、函数返回的值同样不可寻址。

实践约定：一个类型的方法集里一旦出现指针接收者，其余方法通常也统一用指针接收者，避免同一个类型的值方法与指针方法混杂；小而不变的值类型（如只含几个字段的坐标点）适合用值接收者。

nil 指针与 panic

Go 的 nil 指针不会像 C 那样读到随机数据，它会在解引用时立即 panic 并结束程序，定位起来要容易得多：

package main

import "fmt"

type Node struct {
	Val  int
	Next *Node
}

func (n *Node) Sum() int {
	total := 0
	for n != nil { // 遍历链表必须判空
		total += n.Val
		n = n.Next
	}
	return total
}

func main() {
	var p *int
	fmt.Println(p == nil) // true
	// fmt.Println(*p)    // panic: invalid memory address or nil pointer dereference
	// *p = 1             // 同样 panic

	n := &Node{Val: 1, Next: &Node{Val: 2}}
	fmt.Println(n.Sum()) // 3

	var empty *Node
	fmt.Println(empty.Sum()) // 0：方法内先判空，nil 接收者本身合法
}

几个容易混淆的点：

  • nil 接收者：用 nil 指针调用方法本身不会 panic，只有当方法内部解引用字段或调用其他需要解引用的方法时才 panic。链表、树、可选配置（*Config）常利用这一点，在方法开头写 if n == nil { return 零值 }。
  • nil 不是万能的零值：nil map 读取返回零值、写入 panic；nil slice 可以 append、len 为 0，但不能索引；向 nil channel 发送或接收会永久阻塞。这些行为与 nil 指针并不相同。
  • “非 nil”不等于“有值”：p != nil 只说明指针有地址，字段仍可能是零值；反向的陷阱是接口的 typed nil——var err error = (*MyErr)(nil) 时 err != nil 成立，判断前要留意接口里装的具体类型。

习惯上，返回指针的函数要么返回有效指针，要么返回 nil 并让调用方检查；对可能为 nil 的入参，在函数入口集中校验并返回错误，比在调用深处 panic 更可控。

指针数组与数组指针

声明读法要记住优先级：数组或切片的 [] 先结合，指针 * 后结合，于是“指针数组”和“数组指针”是两种类型。

package main

import "fmt"

func main() {
	// 指针数组：[3]*int，共 3 个元素，每个元素都是 *int
	pa := [3]*int{}
	x, y, z := 1, 2, 3
	pa[0], pa[1], pa[2] = &x, &y, &z
	*pa[1] = 20
	fmt.Println(x, y, z, *pa[1]) // 1 20 3 20

	// 数组指针：*[3]int，一个指针，指向长度固定为 3 的数组
	arr := [3]int{1, 2, 3}
	var ap *[3]int = &arr
	ap[0] = 100          // 通过数组指针改元素，不必写 (*ap)[0]
	fmt.Println(arr)     // [100 2 3]
	fmt.Println(len(ap)) // 3：数组指针可直接取长度

	// 切片与指针的组合也要分清
	ps := []*int{&x} // 元素为指针的切片
	fmt.Println(*ps[0])

	sp := &[]int{1, 2} // 合法但不常用：*[]int 指向切片描述符
	fmt.Println((*sp)[0])
}

补充两点：Go 1.17 起可以把数组指针转成切片（ap[:]），因此 *[N]T 适合把定长数组交给需要切片的函数；而 *[]T（指向切片的指针）在真实代码中很少见，因为切片本身已经是轻量的描述符，直接传切片即可。

逃逸分析与堆分配

在 C 中返回局部变量的地址是严重错误（函数返回后栈帧失效），但在 Go 中这是完全合法且常见的写法，因为编译器会做逃逸分析（escape analysis）：一旦发现变量的地址“逃出”了函数作用域，就把它分配在堆上，由垃圾回收器管理生命周期，因此不会出现悬垂指针。

package main

import "fmt"

type Point struct{ X, Y int }

// p 逃逸到堆：它的地址被返回了
func NewPoint(x, y int) *Point {
	p := Point{X: x, Y: y}
	return &p
}

// s 留在栈上：地址没有被带出函数
func Sum(ps []Point) int {
	s := 0
	for _, p := range ps {
		s += p.X + p.Y
	}
	return s
}

func main() {
	p := NewPoint(1, 2)
	fmt.Println(*p, Sum([]Point{*p, {3, 4}})) // {1 2} 10
}

查看编译器的判断结果，可以用 -gcflags 打印逃逸分析日志：

go build -gcflags="-m -l" .

输出中会出现 escapes to heap、moved to heap: p 这类提示（行号与具体代码有关）。常见会导致逃逸的场景有：

  • 把局部变量的地址返回，或把它存入全局变量、切片、map、channel；
  • 把值装箱进接口（例如传给 fmt.Println、包装成 error），这是“看不见的堆分配”最常见的来源；
  • 闭包捕获了局部变量，而闭包自身逃出了函数；
  • 对象过大，或大小在编译期无法确定（如 make([]int, n)，n 为变量）。

堆分配不是错误，只是有成本：分配要花时间，回收要占用 GC 的 CPU。优化时先用 go test -bench 配合 -benchmem 量化，再考虑减少指针与接口的使用、复用对象（sync.Pool）或改为传值；不要为了“避免逃逸”写出难以维护的代码。反过来说，把大结构体按值传递会产生拷贝，此时用指针往往更快——结论应由基准测试给出，而不是凭直觉。

unsafe.Pointer 与 uintptr 的边界

标准库 unsafe 提供了绕过类型系统的能力，也是 Go 中唯一能做指针算术的地方，其中两个类型必须分清：

  • unsafe.Pointer：通用指针类型，可与任意类型的指针 *T 相互转换（unsafe.Pointer(p)、(*T)(up)），被垃圾回收器视为有效指针，指向的对象不会被回收。
  • uintptr：只是一个足够宽的整数，GC 不把它当指针，也不会因为它的存在而保留对象。

由此得到一条铁律：不要把 unsafe.Pointer 转成 uintptr 保存起来、过一段时间再转回指针。中间只要有函数调用、内存分配或 GC，原对象就可能被回收或移动，结果是读到垃圾数据甚至崩溃。合法用法只有一种：在同一个表达式内完成“转整数—算偏移—转回指针”，即 unsafe.Pointer(uintptr(unsafe.Pointer(p)) + offset)。

package main

import (
	"fmt"
	"unsafe"
)

type Header struct {
	Magic uint32
	Len   uint32
}

func main() {
	h := Header{Magic: 0x5a5a, Len: 7}

	// 合法：同一个表达式内完成偏移换算
	lenPtr := (*uint32)(unsafe.Pointer(uintptr(unsafe.Pointer(&h)) + unsafe.Offsetof(h.Len)))
	fmt.Println(*lenPtr) // 7

	// 合法：把整块数据当作字节数组读写
	b := (*[8]byte)(unsafe.Pointer(&h))
	fmt.Println(len(b), b[0]) // 8 90

	// 危险：把 uintptr 存起来（仅作反例，不要这样写）
	// u := uintptr(unsafe.Pointer(&h))
	// ... 中间的任何代码都可能触发 GC ...
	// p := (*Header)(unsafe.Pointer(u)) // 原对象可能已被回收或移动
}

0x5a5a 的低字节是 0x5a，即十进制的 90，在小端机器上 b[0] 正是它。此外还要注意：

  • unsafe.Sizeof、unsafe.Offsetof、unsafe.Alignof 是编译期常量求值，安全且常用于了解内存布局；
  • 通过 reflect.Value.Pointer()、UnsafeAddr() 得到的也是 uintptr，若转换后还要继续使用该对象，需要 runtime.KeepAlive(x) 延长它的生命周期；
  • unsafe 会破坏类型安全与可移植性（字节序、对齐、字段布局都依赖具体实现与平台），只在性能关键路径或与 C 交互时使用，并把用法收敛到极小的包内。
