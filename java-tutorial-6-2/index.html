垃圾回收与调优

Posted on 2026-09-19，6 min read

上一章讲了堆里的对象怎么来，这一章接着回答另一半问题：对象什么时候被回收，以及回收时程序为什么会卡一下。GC 不是“配好参数就完事”的黑盒：搞不清对象存活判定、分代假设和收集器差异，就只能对着日志猜。本章从“哪些内存要回收”讲到 G1 与低延迟收集器，再落到日志解读和调优参数，适合已能读懂 JVM 内存结构、想让线上应用少 Full GC、少长停顿的读者。

一、先判断死活：引用计数与可达性分析

程序计数器、虚拟机栈、本地方法栈的生命周期与线程一致，线程结束内存自然归还，不需要 GC 操心；真正需要动态管理的只有堆和方法区。判断对象是否存活有两套思路。

引用计数给每个对象维护一个计数器，被引用加一、引用失效减一，为零即可回收。它实现简单、回收及时，但有一个致命缺陷：无法处理循环引用。下面这段代码里两个对象互相持有对方，即使外部引用全部置空，计数依然不为零，谁也不会被回收。

class Node {
    Node next; // 互相引用形成环
}

public class RefCountTest {
    public static void main(String[] args) {
        Node a = new Node();
        Node b = new Node();
        a.next = b;
        b.next = a;   // a、b 互相引用，引用计数都为 1
        a = null;
        b = null;     // 已不可达，但计数器不为 0
        System.gc();  // 引用计数法回收不了这两个对象
    }
}

主流 JVM 采用的是可达性分析：从一组称为 GC Roots 的根对象出发遍历引用链，走不到的对象判为可回收。可作为 GC Roots 的包括虚拟机栈（栈帧局部变量表）中引用的对象、方法区中类静态属性引用的对象、方法区中常量引用的对象、本地方法栈中 JNI 引用的对象，此外还有被同步锁持有的对象等。

此外还要说清 Java 的四种引用强度：强引用（Object o = new Object()）只要存在就绝不回收；软引用（SoftReference）在将要发生内存溢出前才被列入回收范围；弱引用（WeakReference）只能活到下一次 GC；虚引用（PhantomReference）无法取得对象实例，只用于回收时收到通知。可达性分析基于的正是强引用。对象即使被判不可达，也不是立刻死亡：还会经历一次筛选，若 finalize() 中重新与引用链建立关联，就能逃过本次回收。需要补充的是，finalize() 自 JDK 9 起被标记为废弃、JDK 18 起进一步标记为“将被移除”，不要依赖它做资源清理，应改用 try-with-resources 或 java.lang.ref.Cleaner。

二、三种基础算法与分代收集

收集算法只有三类，区别在“标记之后怎么清”。

  • 标记-清除：标记存活对象后直接回收未标记部分。实现简单、不需要移动对象，但清除后内存碎片严重，且标记与清除都要遍历对象，效率受限。
  • 标记-复制：把空间一分为二，只使用其中一块；回收时把存活对象整体复制到另一块，再清空原空间并交换角色。没有碎片、分配靠指针碰撞极快，代价是可用内存减半，且存活对象多时复制开销大。
  • 标记-整理：标记后把存活对象向一端移动，再清理边界外的空间。解决了碎片问题，但移动对象并更新引用同样昂贵。

没有哪种算法通吃，于是有了分代收集。它的依据是一条经验规律：绝大多数对象朝生夕灭，熬过越多次 GC 的对象越难死。堆因此被划成新生代与老年代，分别施策。HotSpot 中新生代默认按 Eden : Survivor0 : Survivor1 = 8 : 1 : 1 划分，新对象优先在 Eden 分配。Minor GC 时，Eden 与 From Survivor 中的存活对象被复制到 To Survivor，然后清空前两者并交换两个 Survivor 的角色。对象每熬过一次 GC 年龄加一，达到 -XX:MaxTenuringThreshold（默认 15）或 Survivor 空间不足时晋升老年代（G1 下该值只是上限，实际晋升年龄由 G1 按停顿目标自适应决定）。老年代存活率高，适合标记-整理或标记-清除，空间不足时触发 Full GC。大对象（如 new byte[4 * 1024 * 1024]）通常直接进入老年代，避免在 Eden 与 Survivor 间反复复制。

三、收集器的演进：从 Serial 到 G1 与低延迟收集器

算法要有落地实现，HotSpot 的收集器可以按“是否并行、是否并发、作用范围是哪一代”来区分。并行（Parallel）指多条 GC 线程同时工作，但用户线程仍然暂停；并发（Concurrent）指 GC 线程与用户线程同时运行，能显著缩短单次停顿，代价是占用 CPU 并产生浮动垃圾。

  • Serial / Serial Old：单线程收集，收集时必须暂停所有用户线程，也就是 STW（Stop-The-World）。简单高效，适合客户端或小堆场景。
  • ParNew：Serial 的多线程版本，仍作用于新生代，常与 CMS 搭配；CMS 在 JDK 14 被移除后 ParNew 也一并退出，如今只在 JDK 8～13 的历史配置里能见到。
  • Parallel Scavenge / Parallel Old：新生代复制、老年代标记-整理的多线程组合，目标不是最短停顿而是可控吞吐量，可用 -XX:MaxGCPauseMillis 与 -XX:GCTimeRatio 调节。它同样会 STW，只是并行缩短了停顿，并非“不暂停用户线程”。还要记住默认收集器的换代：JDK 8 的 Server 模式默认就是 Parallel Scavenge + Parallel Old，而JDK 9 起默认改为 G1（JEP 248）。旧笔记里“默认串行、要加 -XX:+UseParallelGC 才并行”的说法从 JDK 9 起不再成立，只有明确追求吞吐量时才需要显式选回 Parallel。
  • CMS：以最短停顿为目标的并发收集器，作用于老年代，采用标记-清除算法，流程为初始标记（STW）→ 并发标记 → 并发预清理 → 重新标记（STW）→ 并发清除 → 并发重置。缺点是产生内存碎片、无法处理浮动垃圾，且并发阶段会与应用争抢 CPU。生命周期必须记牢：JDK 9 起废弃（JEP 291）、JDK 14 正式移除（JEP 363）——在 JDK 14 及以后的 JVM 上写 -XX:+UseConcMarkSweepGC 会直接以 Unrecognized VM option 启动失败，而不会悄悄退化成别的收集器。JDK 8 上它仍可用，但已是历史选择，新项目应直接选 G1 或 ZGC。
  • G1：把堆划分为大小相等的 Region，新生代与老年代只是 Region 的逻辑集合，不再要求连续。它维护每个 Region 的回收价值（垃圾占比与回收耗时）列表，在 -XX:MaxGCPauseMillis 的停顿目标下优先回收收益最高的 Region，从而建立可预测的停顿模型。跨 Region 引用靠每个 Region 的 Remembered Set 记录，避免全堆扫描；超过 Region 容量一半的巨型对象放入 Humongous 区，连续 H 区不足时可能被迫 Full GC。G1 的回收模式有 Young GC（Eden 耗尽触发）、Mixed GC（老年代占用达到 -XX:InitiatingHeapOccupancyPercent，默认 45% 时触发，回收全部年轻代加部分老年代）和 Full GC。注意 Mixed GC 不等于 Full GC，它只回收部分老年代 Region。G1 在 JDK 7 引入，JDK 9 起成为默认收集器（JEP 248），因此在 JDK 9+ 的启动命令里 -XX:+UseG1GC 只是显式声明，不写也同样是 G1。
  • ZGC / Shenandoah：面向超大堆与极低延迟，借助染色指针与读屏障把停顿压到毫秒级且与堆大小基本无关，ZGC 的目标停顿在 10ms 以内，适合堆上百 GB 的在线服务。版本演进同样要记：ZGC 在 JDK 11 引入（实验性，需 -XX:+UnlockExperimentalVMOptions -XX:+UseZGC），JDK 15 转正（JEP 377）。到 JDK 17/21 上，直接写 -XX:+UseZGC 即可。JDK 21 起提供分代 ZGC（JEP 439，用 -XX:+ZGenerational 开启），JDK 23 起分代模式成为默认（JEP 474）。Shenandoah 自 JDK 12 引入（实验性）、JDK 15 转正（JEP 379），但并非所有发行版都包含，Oracle JDK 中就没有。实现细节超出本章范围，这里不再展开。

四、打开 GC 日志：从看懂到会调

调优的第一步永远是先观测。启动时打开日志，再压测复现，然后才谈参数。

# JDK 8 及以前的旧写法（已过时，仅作对照）：-XX:+PrintGCDetails 打印详情，
# -XX:+PrintGCDateStamps 加日期戳，-Xloggc 指定日志文件
java -XX:+UseG1GC -Xms2g -Xmx2g \
     -XX:MaxGCPauseMillis=200 \
     -XX:+PrintGCDetails -XX:+PrintGCDateStamps \
     -Xloggc:/var/log/app/gc.log -jar app.jar

# JDK 9+ 的现行写法：JEP 158 统一日志框架后 GC 日志并入 -Xlog
# 旧参数对应关系：-XX:+PrintGC → -Xlog:gc；-XX:+PrintGCDetails → -Xlog:gc*；
# -Xloggc:<file> → -Xlog:gc:file=<file>（-Xloggc 与 -XX:+PrintGCDetails 在 JDK 9 起弃用）
# 日期戳改由 :time,uptime,level,tags 装饰器提供，并可加 filecount/filesize 做日志轮转
# JDK 9 起默认收集器就是 G1，-XX:+UseG1GC 可写可不写
java -XX:+UseG1GC -Xms2g -Xmx2g \
     -XX:MaxGCPauseMillis=200 \
     -Xlog:gc*,gc+heap=info:file=/var/log/app/gc.log:time,uptime,level,tags:filecount=5,filesize=50M \
     -jar app.jar

日志读起来并不难，抓住三段信息即可。第一段是回收类型：GC 表示 Minor/Young GC，Full GC 表示全堆回收。第二段是前后容量：4416K->512K(4928K) 依次表示该区域回收前占用、回收后占用与总容量。第三段是耗时，如 0.0046102 secs，也可以用 [Times: user=... sys=... real=...] 对照用户态、内核态与墙钟时间。下面是一段串行收集器在 JDK 8 上的真实输出（旧格式，保留作对照）：

[GC (Allocation Failure) [DefNew: 4416K->512K(4928K), 0.0046102 secs]
 4416K->1973K(15872K), 0.0046533 secs] [Times: user=0.00 sys=0.00, real=0.00 secs]
[Full GC (Allocation Failure) [Tenured: 10944K->3107K(10944K), 0.0085637 secs]
 15871K->3107K(15872K), [Metaspace: 3496K->3496K(1056768K)], 0.0085974 secs]

换成 JDK 9+ 的统一日志后，字段名不再是 DefNew、Tenured，而是直接给出停顿类型与前后的堆占用，G1 下形如：

[2024-05-01T10:00:00.123+0800][2.345s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 128M->24M(1024M) 12.345ms
[2024-05-01T10:00:05.678+0800][7.890s][info][gc] GC(1) Pause Young (Concurrent Start) (G1 Humongous Allocation) 512M->96M(1024M) 18.234ms
[2024-05-01T10:00:09.012+0800][11.234s][info][gc] GC(2) Pause Remark 640M->640M(1024M) 1.234ms

在此基础上做取舍：追求吞吐量选 Parallel，追求更低平均停顿选 G1，追求极致低延迟且堆巨大再看 ZGC。常用的观察手段包括：用 jstat -gcutil <pid> 1000 实时查看各代占用与 GC 次数，用 jmap -histo:live <pid> 查看对象分布，以及把日志交给 GCeasy 之类工具可视化。

参数方面，常用参数各管一件事：

  • -Xms 与 -Xmx 设成相等可避免堆反复伸缩；
  • -Xmn 或 -XX:NewRatio 控制新生代比例；
  • -XX:SurvivorRatio 调整 Eden 与 Survivor 的比例；
  • -XX:+HeapDumpOnOutOfMemoryError 配合 -XX:HeapDumpPath 保证 OOM 现场可查；
  • G1 下新生代由 -XX:G1NewSizePercent（默认 5%）与 -XX:G1MaxNewSizePercent（默认 60%）自适应控制。-Xmn 与 -XX:NewRatio 主要面向 Parallel、Serial 这类分代固定的收集器，在 G1 下不保证按字面生效，需实测确认。

还要注意 -XX:MaxGCPauseMillis 只是期望值，JVM 会尽力而为但不保证达到；把堆设得过小反而会让 GC 更频繁。

三类常见坑

坑一，把 STW 说成“不影响用户线程”。所有分代收集器的 Minor GC 与 Full GC 都会停顿用户线程，并行只是缩短停顿，并发才有部分阶段与应用同时运行，但仍需初始标记与重新标记两次 STW。用“某收集器完全不暂停”来判断选型一定会踩坑。

坑二，System.gc() 与显式引用。显式调用 System.gc() 可能触发 Full GC，生产代码里应避免；-XX:+DisableExplicitGC 可将其屏蔽，但要注意 NIO 直接内存依赖它回收 DirectByteBuffer，屏蔽后堆外内存可能迟迟不释放。此外，把对象放进静态集合、ThreadLocal 未 remove()、监听器未注销，都会制造长生命周期的强引用，让对象看起来没用了却回收不掉。

坑三，永久代与元空间的版本差异。两者的版本差异可以对照着记：

  • JDK 7 及以前，方法区由永久代实现，受 -XX:MaxPermSize 约束，Perm 满会触发 Full GC。这个参数从 JDK 8 起就已失效（JEP 122 移除永久代）。JDK 8 上写它只会在启动时打印 “Ignoring option MaxPermSize; support was removed in 8.0” 之类的告警后被忽略。JDK 9 及以后则直接以 Unrecognized VM option 'MaxPermSize' 拒绝启动，所以旧启动脚本在升级 JDK 前必须先清掉它；
  • JDK 8 起永久代已被元空间取代，元空间使用本地内存，由 -XX:MaxMetaspaceSize 约束（该参数默认不设上限，只受本机可用内存限制，生产环境建议显式给出上限）。类卸载条件也很严格：该类所有实例已回收、加载它的 ClassLoader 已回收、对应的 Class 对象无引用。

所以看到旧文章里“永久代被写满导致 Full GC”的说法时，要先确认 JDK 版本，在 JDK 8+ 上应排查元空间泄漏（典型是动态生成类、热部署或反射滥用）。

五、小结

这一章的主线是：GC 先解决“谁是垃圾”，再解决“怎么清、什么时候清”。判活用可达性分析，而非引用计数。回收用标记-清除、复制、标记-整理三种基础算法，并靠分代假设把新生代交给复制、老年代交给标记-整理或标记-清除。到了收集器层面：Parallel 换吞吐量；CMS 换低停顿但有碎片；G1 用 Region + RSet + 停顿预测模型兼顾两者；ZGC 面向超大堆的极低延迟。落到实践，先开日志并用 jstat 观测，再调整 -Xms/-Xmx、新生代比例与停顿目标这些参数。最后要牢记：所有分代收集器都有 STW，而显式 System.gc() 调用与长生命周期引用是最常见的两类人为故障。下一章进入具体的线上排查工具与方法。
