Seata 是什么?

Seata 是一款开源的分布式事务解决方案，致力于提供高性能、简单易用的分布式事务服务。Seata 为用户提供 AT、TCC、SAGA 和 XA 事务模式，打造一站式的分布式解决方案。

AT 模式

前提

  • 基于支持本地 ACID 事务的关系型数据库。
  • Java 应用，通过 JDBC 访问数据库。

整体机制

两阶段提交协议的演变：

  • 一阶段：业务数据和回滚日志记录在同一个本地事务中提交，释放本地锁和连接资源。

  • 二阶段：

    • 提交异步化，非常快速地完成。
    • 回滚通过一阶段的回滚日志进行反向补偿。

写隔离

  • 一阶段本地事务提交前，需要确保先拿到 「全局锁」 。
  • 拿不到 「全局锁」 ，不能提交本地事务。
  • 拿 「全局锁」 的尝试被限制在一定范围内，超出范围将放弃，并回滚本地事务，释放本地锁。

以一个示例来说明：

两个全局事务 tx1 和 tx2，分别对 a 表的 m 字段进行更新操作，m 的初始值 1000。

tx1 先开始，开启本地事务，拿到本地锁，更新操作 m = 1000 - 100 = 900。本地事务提交前，先拿到该记录的 「全局锁」 ，本地提交释放本地锁。tx2 后开始，开启本地事务，拿到本地锁，更新操作 m = 900 - 100 = 800。本地事务提交前，尝试拿该记录的 「全局锁」 ，tx1 全局提交前，该记录的全局锁被 tx1 持有，tx2 需要重试等待 「全局锁」 。

tx1 二阶段全局提交，释放 「全局锁」 。tx2 拿到 「全局锁」 提交本地事务。

如果 tx1 的二阶段全局回滚，则 tx1 需要重新获取该数据的本地锁，进行反向补偿的更新操作，实现分支的回滚。

此时，如果 tx2 仍在等待该数据的 「全局锁」，同时持有本地锁，则 tx1 的分支回滚会失败。分支的回滚会一直重试，直到 tx2 的 「全局锁」 等锁超时，放弃 「全局锁」 并回滚本地事务释放本地锁，tx1 的分支回滚最终成功。

因为整个过程 「全局锁」 在 tx1 结束前一直是被 tx1 持有的，所以不会发生 「脏写」 的问题。

读隔离

在数据库本地事务隔离级别 「读已提交（Read Committed）」 或以上的基础上，Seata（AT 模式）的默认全局隔离级别是 「读未提交（Read Uncommitted）」 。

如果应用在特定场景下，必需要求全局的 「读已提交」 ，目前 Seata 的方式是通过 SELECT FOR UPDATE 语句的代理。

SELECT FOR UPDATE 语句的执行会申请 「全局锁」 ，如果 「全局锁」 被其他事务持有，则释放本地锁（回滚 SELECT FOR UPDATE 语句的本地执行）并重试。这个过程中，查询是被 block 住的，直到 「全局锁」 拿到，即读取的相关数据是 「已提交」 的，才返回。

出于总体性能上的考虑，Seata 目前的方案并没有对所有 SELECT 语句都进行代理，仅针对 FOR UPDATE 的 SELECT 语句。

工作机制

以一个示例来说明整个 AT 分支的工作过程。

业务表：product

Field Type Key
id bigint(20) PRI
name varchar(100)
since varchar(100)

AT 分支事务的业务逻辑：

update product set name = 'GTS' where name = 'TXC';

「一阶段」

过程：

  1. 解析 SQL：得到 SQL 的类型（UPDATE），表（product），条件（where name = 'TXC'）等相关的信息。
  2. 查询前镜像：根据解析得到的条件信息，生成查询语句，定位数据。
select id, name, since from product where name = 'TXC';

得到前镜像：

id name since
1 TXC 2014
  1. 执行业务 SQL：更新这条记录的 name 为 'GTS'。
  2. 查询后镜像：根据前镜像的结果，通过 「主键」 定位数据。
select id, name, since from product where id = 1;

得到后镜像：

id name since
1 GTS 2014
  1. 插入回滚日志：把前后镜像数据以及业务 SQL 相关的信息组成一条回滚日志记录，插入到 UNDO_LOG 表中。

  1. 提交前，向 TC 注册分支：申请 product 表中，主键值等于 1 的记录的 「全局锁」 。
  2. 本地事务提交：业务数据的更新和前面步骤中生成的 UNDO_LOG 一并提交。
  3. 将本地事务提交的结果上报给 TC。

「二阶段-回滚」

  1. 收到 TC 的分支回滚请求，开启一个本地事务，执行如下操作。
  2. 通过 XID 和 Branch ID 查找到相应的 UNDO_LOG 记录。
  3. 数据校验：拿 UNDO_LOG 中的后镜与当前数据进行比较，如果有不同，说明数据被当前全局事务之外的动作做了修改。这种情况，需要根据配置策略来做处理，详细的说明在另外的文档中介绍。
  4. 根据 UNDO_LOG 中的前镜像和业务 SQL 的相关信息生成并执行回滚的语句：
update product set name = 'TXC' where id = 1;
  1. 提交本地事务。并把本地事务的执行结果（即分支事务回滚的结果）上报给 TC。

「二阶段-提交」

  1. 收到 TC 的分支提交请求，把请求放入一个异步任务的队列中，马上返回提交成功的结果给 TC。
  2. 异步任务阶段的分支提交请求将异步和批量地删除相应 UNDO_LOG 记录。

TP 角色与全局事务流程

Seata 的全局事务由三个角色协作完成，三者通过长连接交换 RPC 消息：

  • TC（Transaction Coordinator，事务协调者）：独立部署的 Seata Server，维护全局事务与分支事务的状态机，负责生成 XID、管理 lock_table 全局锁、驱动二阶段的全局提交或回滚。
  • TM（Transaction Manager，事务管理者）：定义全局事务的边界，向 TC 发起 begin、commit、rollback，通常由业务入口方法上的 @GlobalTransactional 注解驱动。
  • RM（Resource Manager，资源管理者）：管理分支事务的资源，向 TC 注册分支、上报分支状态，并根据 TC 的指令完成二阶段的提交或回滚。AT 模式的 RM 以数据源代理的形式工作。

一次典型的全局事务时序如下：TM 向 TC 申请开启全局事务并拿到 XID，XID 通过上下文在微服务调用链中传播；每个 RM 在执行本地事务时注册分支、申请全局锁；TM 在业务方法返回后通知 TC 全局提交或回滚，TC 再逐个驱动分支完成二阶段。

常见坑与配置要点

AT 模式把一致性做进了框架，但以下问题仍然需要业务和运维配合处理，它们也是线上事故的高发区。

1. 脏写与镜像校验

二阶段回滚时会先做数据校验：拿 undo_log 中的后镜像（afterImage）与当前数据比较，如果不同，说明该行被全局事务之外的动作修改过。此时盲目按前镜像覆盖就会产生脏写。默认策略是抛出异常并记录，人工介入；根本的解决办法是让所有写路径都进入全局事务，或对外部写入的表显式加全局锁。

2. TCC 的空回滚与悬挂

空回滚指一阶段 Try 没有执行成功（例如网络超时），TC 却发起了 Cancel，此时 Cancel 不能真的去扣减资源，需要先判断「事务是否执行过」；悬挂指 Cancel 比迟到的 Try 先执行，导致 Try 占用的资源永远不会被释放。通用做法是引入事务控制表：Try 执行前先登记并检查是否存在已回滚记录，Cancel 时插入回滚标记，并保证 Try / Confirm / Cancel 三个方法都幂等。

3. 其他高频问题

  • 表必须有主键：AT 依赖主键定位前后镜像，无主键的表无法生成可用的回滚语句。
  • 全局锁粒度：全局锁的锁键取自更新条件里的主键（或唯一索引）。对 update ... where 非主键条件，Seata 提取不到行级锁键，锁键会退化为表名，导致该表的写操作互斥、并发度下降，因此更新条件应尽量带上主键或唯一索引。
  • 全局锁重试：拿不到全局锁时默认按 client.rm.lock.retry-interval（默认 10 ms）重试 client.rm.lock.retry-times（默认 30 次），超出后回滚本地事务并释放本地锁，避免长时间占用连接。
  • 读隔离：只有 SELECT ... FOR UPDATE 会被代理并申请全局锁，普通 SELECT 读到的是未提交数据，对账、金额类场景要自行加锁读取。
  • undo_log 表：需要业务库提前建表并授权；client.undo.log-table 可改名，client.undo.data-validation 控制是否做镜像校验。
  • TC 高可用：单机 file 存储模式仅适合开发环境，生产环境应使用 db 存储模式部署 TC 集群（Seata 1.5+ 另提供 raft 高可用模式；早期版本的 redis 存储模式已在新版本中移除）。

核心配置示例（file.conf / registry.conf 可被 application.yml 覆盖）：

seata:
  enabled: true
  application-id: order-service
  tx-service-group: my_tx_group      # 需与 TC 侧 service.vgroupMapping 对应
  enable-auto-data-source-proxy: true
  data-source-proxy-mode: AT          # AT / XA
  service:
    vgroup-mapping:
      my_tx_group: default            # 事务分组到 TC 集群的映射
    grouplist:
      default: 127.0.0.1:8091
  client:
    rm:
      lock:
        retry-interval: 10            # 全局锁重试间隔，单位 ms
        retry-times: 30               # 全局锁重试次数，超限则回滚本地事务
      table-meta-check-enable: false
      report-success-enable: false
    undo:
      data-validation: true           # 二阶段回滚前是否校验后镜像
      log-serialization: jackson
      log-table: undo_log
  config:
    type: file
  registry:
    type: file

事务模式对比：AT / TCC / SAGA / XA

四种模式解决的是不同约束下的问题，选择依据主要是「一致性强度、业务改造成本、资源是否支持事务型」：

维度 AT TCC SAGA XA
一致性 最终一致 最终一致 最终一致 强一致（数据库级两阶段）
资源要求 关系型数据库 + JDBC 任意资源，需业务提供接口 任意资源，需正向与补偿服务 支持 XA 的数据库
业务侵入 几乎无侵入，框架自动补偿 高，需要实现 Try/Confirm/Cancel 中，需要实现每个服务的补偿逻辑 低，仅需切换数据源代理模式
隔离性 默认全局读未提交，靠全局锁防脏写 由业务在 Try 中预留资源实现 不保证隔离，需要业务容忍中间态 由数据库本地事务隔离级别保证
锁与性能 全局锁只在提交窗口期持有，性能较好 无数据库长事务，但需幂等与防悬挂 一阶段无锁，吞吐高 连接与行锁持有到二阶段，性能最差
典型场景 电商下单扣库存、账户转账 跨库扣减、需要资源预留的资金类业务 长流程、跨公司或遗留系统编排 强一致要求且数据库支持 XA 的存量系统

与其他最终一致方案的关系

  • 本地消息表：业务与消息记录写在同一个本地事务里，再由定时任务投递消息。实现简单、不依赖 TC，但需要自己处理投递重试、幂等与消息堆积，且没有全局锁和统一回滚视图。
  • 最大努力通知：调用方尽力重试通知，接收方提供查询对账接口兜底补偿。只适合对一致性要求不高的通知类场景，失败时需要人工或对账系统介入。
  • Seata AT：把「本地事务 + 回滚日志 + 二阶段驱动」交给框架，业务侧只写本地 SQL，适合数据库均为关系型、希望低侵入获得最终一致的场景；代价是引入 TC 组件与全局锁，并接受默认读未提交的隔离级别。

TCC 模式

回顾总览中的描述：一个分布式的全局事务，整体是 「两阶段提交」 的模型。全局事务是由若干分支事务组成的，分支事务要满足 「两阶段提交」 的模型要求，即需要每个分支事务都具备自己的：

  • 一阶段 prepare 行为
  • 二阶段 commit 或 rollback 行为

根据两阶段行为模式的不同，我们将分支事务划分为 「Automatic (Branch) Transaction Mode」 和 「Manual (Branch) Transaction Mode」。

AT 模式是 Automatic (Branch) Transaction Mode 的缩写，基于 「支持本地 ACID 事务」 的 「关系型数据库」，由 Seata 自动完成 SQL 解析、前后镜像记录与反向补偿，业务代码几乎零侵入：

  • 一阶段 prepare 行为：在本地事务中，一并提交业务数据更新和相应回滚日志记录。
  • 二阶段 commit 行为：马上成功结束，「自动」 异步批量清理回滚日志。
  • 二阶段 rollback 行为：通过回滚日志，「自动」 生成补偿操作，完成数据回滚。

相应的，TCC 模式，不依赖于底层数据资源的事务支持：

  • 一阶段 prepare 行为：调用 「自定义」 的 prepare 逻辑。
  • 二阶段 commit 行为：调用 「自定义」 的 commit 逻辑。
  • 二阶段 rollback 行为：调用 「自定义」 的 rollback 逻辑。

所谓 TCC 模式，是指支持把 「自定义」 的分支事务纳入到全局事务的管理中。

也就是说，TCC 把 AT 中由框架自动完成的一阶段 prepare 与二阶段 commit / rollback，改由业务实现为三个显式接口：Try（一阶段资源检查与预留）、Confirm（二阶段确认，真正提交预留资源）、Cancel（二阶段取消，释放预留资源）。三者都必须幂等，并配合事务控制表解决空回滚与悬挂问题（见上文「常见坑与配置要点」）。

Saga 模式

Saga 模式是 Seata 提供的长事务解决方案，在 Saga 模式中，业务流程中每个参与者都提交本地事务，当出现某一个参与者失败则补偿前面已经成功的参与者，一阶段正向服务和二阶段补偿服务都由业务开发实现。

理论基础：Hector & Kenneth 发表论文《Sagas》（1987）

适用场景

  • 业务流程长、业务流程多
  • 参与者包含其它公司或遗留系统服务，无法提供 TCC 模式要求的三个接口

优势

  • 一阶段提交本地事务，无锁，高性能
  • 事件驱动架构，参与者可异步执行，高吞吐
  • 补偿服务易于实现

缺点

  • 不保证隔离性，中间状态对外可见，需要业务设计可容忍的补偿语义
  • 补偿逻辑需要业务自行实现并保证幂等，正向与补偿接口成对维护成本较高

XA 模式

XA 模式是对数据库原生 XA 协议的封装，Seata 在其中承担 TC 的角色，把多个 XA 资源的分支事务纳入同一个全局事务：

  • 一阶段：RM 执行本地 XA 事务的 XA START / 业务 SQL / XA END / XA PREPARE，连接与锁一直持有到二阶段。
  • 二阶段：TC 根据全局结果通知 RM 执行 XA COMMIT 或 XA ROLLBACK。

XA 的优点是强一致、业务改造量小，适合「服务已是存量系统、只想最小改动拿到分布式事务」的场景；缺点是依赖数据库对 XA 的支持，二阶段结束前连接和行锁不会释放，高并发下性能明显弱于 AT，因此 Seata 官方更推荐优先评估 AT。

小结

Seata 的价值在于把分布式事务的通用部分（事务协调、分支注册、回滚补偿、全局锁）收敛到 TC 与框架层，让业务侧尽量只关心本地事务。选型时先看资源类型与一致性要求：关系型数据库优先 AT；需要资源预留或跨异构资源用 TCC；长流程、跨组织编排用 SAGA；已有 XA 能力且要求强一致再考虑 XA。同时务必针对脏写校验、空回滚、悬挂这三类问题做专项设计与压测。
