设计模式：结构型

Posted on 2026-09-19，8 min read

上一章讲的创建型模式解决「对象怎么来」，实际项目里更常见的麻烦却是「对象怎么拼」。你手上有现成的类：一个第三方支付 SDK、一个只能读InputStream的老工具、一个会打印一堆日志的报表服务，可业务代码需要的是另一套接口、另一种粒度、另一层访问控制。硬改这些类要么改不动（第三方 jar），要么一改就连带炸出一串调用方。GoF 把专门处理「类与对象如何组装成更大结构」的这一类模式叫结构型模式，共七种：适配器、装饰器、代理、外观、桥接、组合、享元。本文面向会写 Java 接口与继承、但还不熟悉设计模式的读者，讲清它们的意图、最小可运行写法，以及最容易混淆之处。读完你应该能判断「这段代码该用哪个结构型模式，还是根本不用」。

一、结构型模式的共同目标：别再靠继承硬堆

结构型模式有两条主线：一是类结构型模式，靠继承来组合接口（典型代表是类适配器，用得少，因为 Java 只支持单继承）；二是对象结构型模式，靠持有引用、组合对象来拼装能力（其余六种基本都属于这一类）。它们共同的对立面是「用继承解决一切」：想给一个类加日志就派生子类，想加缓存再派生一层，想控制权限再来一层——继承是编译期固定的，类的数量会随功能维度相乘而爆炸。

按意图可以把七种模式分成四组记忆：接口不兼容用适配器（Adapter）；想动态加功能或控制访问用装饰器（Decorator）、代理（Proxy）；想简化复杂子系统用外观（Facade）；想处理树形结构或分离多变化维度、复用海量细粒度对象用组合（Composite）、桥接（Bridge）、享元（Flyweight）。下面按这个顺序展开。

二、适配器模式：把不兼容的接口接到一起

适配器的意图是「将一个类的接口转换成客户期望的另一个接口」，让原本因接口不匹配而无法协作的类一起工作。最直观的类比是读卡器：内存卡和笔记本的插槽互不认识，中间加一个读卡器，两边都不用改。你其实每天都在用它——Arrays.asList() 把数组适配成List，InputStreamReader 把字节流适配成字符流，JDK 1.2 起为了兼容旧代码提供的 Enumeration 到 Iterator 的转换工具也属于此类。

实现上有两种主流写法。类适配器让适配器同时继承适配者（Adaptee）并实现目标接口，写起来短，但受单继承限制，一个适配器只能适配一个类；对象适配器改为在内部持有一个适配者实例并委托调用，可以适配适配者的任意子类，也能同时组合多个适配者，是更推荐的写法。注意目标可以是接口也可以是抽象类，并不要求「目标类必须是抽象类」。下面用「播放器只认 mp3，但想播 vlc」这个经典场景演示对象适配器。

// 目标接口：客户端期望的接口
public interface MediaPlayer {
    void play(String audioType, String fileName);
}

// 适配者：功能已经存在，但接口对不上
public class VlcPlayer {
    public void playVlc(String fileName) {
        System.out.println("Playing vlc file. Name: " + fileName);
    }
}

// 对象适配器：实现目标接口，内部持有一个适配者
public class MediaAdapter implements MediaPlayer {
    private final VlcPlayer vlcPlayer = new VlcPlayer();

    @Override
    public void play(String audioType, String fileName) {
        if ("vlc".equalsIgnoreCase(audioType)) {
            vlcPlayer.playVlc(fileName);
        } else {
            throw new IllegalArgumentException("不支持的格式: " + audioType);
        }
    }
}

// 客户端只认 MediaPlayer，完全不知道 VlcPlayer 的存在
public class AdapterDemo {
    public static void main(String[] args) {
        MediaPlayer player = new MediaAdapter();
        player.play("vlc", "demo.vlc"); // Playing vlc file. Name: demo.vlc
    }
}

用适配器要守住一条底线：它是为「正在服役的老系统」打的补丁，不是详细设计阶段的首选。如果两个接口都是你自己的、代码还能改，正确做法是重构接口或改调用方，而不是层层加适配器——系统里到处是「看到调用 A 接口、实际被转成 B 实现」，排查问题会非常痛苦。适配器只做接口转换，别顺手往里塞业务逻辑。

三、装饰器与代理：长得像，目的完全不同

这两个模式的结构图几乎一样：实现目标接口，内部持有同类型的另一个对象，在调用前后插入自己的代码。区别在于意图——装饰器为了增强功能，且能在运行时自由叠加；代理为了控制访问，被代理的对象往往在编译期就写死了。一个实用的区分信号：装饰器的被装饰对象由外部经构造方法传入（谁装饰谁由调用方决定），代理的内部对象往往自己new出来（客户端甚至不知道背后还有真实对象）。Java I/O 就是装饰器：new BufferedReader(new InputStreamReader(new FileInputStream("a.txt"))) 可任意嵌套；而 Spring AOP 代理、RMI 远程代理、MyBatis 的 Mapper 代理，都只是替客户端去访问真实目标。

// ---- 装饰器：构造方法接收被装饰对象，必要时可嵌套多层 ----
public interface ReportService {
    String render(String data);
}

public class HtmlReportService implements ReportService {
    @Override public String render(String data) {
        return "<table>" + data + "</table>";
    }
}

public class LoggingReportService implements ReportService {
    private final ReportService delegate;          // 由外部传入，可自由组合
    public LoggingReportService(ReportService delegate) {
        this.delegate = delegate;
    }
    @Override public String render(String data) {
        long start = System.currentTimeMillis();
        String result = delegate.render(data);     // 转发给被装饰对象
        System.out.println("渲染耗时 " + (System.currentTimeMillis() - start) + "ms");
        return result;
    }
}

// ---- 代理：自己创建真实对象，对客户端隐藏它、并对访问做控制 ----
public class SecureReportProxy implements ReportService {
    private final ReportService real = new HtmlReportService(); // 关系在编译期确定
    private final String role;
    public SecureReportProxy(String role) { this.role = role; }
    @Override public String render(String data) {
        if (!"admin".equals(role)) {
            throw new SecurityException("无权限导出报表");
        }
        return real.render(data);
    }
}

组合使用：new LoggingReportService(new SecureReportProxy("admin")) 先鉴权再计时；反过来写则先计时再鉴权。可见装饰器适合「层层套」，而代理套三层只会让调用链难以追踪。常见坑是：客户端依赖了真实类的特有方法，换成代理后编译失败（代理只保证接口一致）；以及装饰器忘了@Override，方法名写错却静默不生效。

四、外观与组合：化繁为简与部分-整体

外观模式为子系统的一组接口提供统一的入口。比如下单要依次调用库存、优惠、支付、通知四个服务，客户端逐个编排既啰嗦又容易漏步骤，于是抽一个OrderFacade，对外只暴露placeOrder()。它降低客户端与子系统的耦合，代价是外观类容易变成「上帝类」，新增子系统时往往要改外观——所以外观只做编排与转发，不写业务规则。

组合模式把对象组织成树形结构，用来表达「部分-整体」层次，并让客户端对单个叶子和整棵树的使用方式保持一致。文件与目录、菜单与子菜单、组织架构都是它的舞台。实现要点是：树枝节点内部持有一个List保存子节点，并提供add/remove方法。经典实现里叶子和树枝都直接用具体类而不是接口（甚至把add放在基类里对叶子抛异常），这确实违反了依赖倒置与接口隔离原则，属于该模式出名的设计瑕疵——如果在意这一点，可以在基类默认抛出UnsupportedOperationException，把add/remove上提到真正的容器节点。

import java.util.ArrayList;
import java.util.List;

// 组合模式：统一的节点抽象
public abstract class Node {
    protected final String name;
    protected Node(String name) { this.name = name; }
    public abstract int size();  // 叶子返回自身大小，目录返回子节点之和
    public void add(Node child) {
        throw new UnsupportedOperationException("叶子节点不支持添加子节点");
    }
}

public class FileNode extends Node {
    private final int bytes;
    public FileNode(String name, int bytes) { super(name); this.bytes = bytes; }
    @Override public int size() { return bytes; }
}

public class DirNode extends Node {
    private final List<Node> children = new ArrayList<>();
    public DirNode(String name) { super(name); }
    @Override public void add(Node child) { children.add(child); }
    @Override public int size() {
        int total = 0;
        for (Node child : children) {
            total += child.size();   // 递归汇总，客户端不必区分叶子和目录
        }
        return total;
    }
}

外观的坑是「限制不了客户端直接用子系统类」：若代码里既有OrderFacade.placeOrder()又有绕过外观的零散调用，它就退化成摆设。组合的坑是递归深度：树来自用户输入或注册中心时，要限制层级并做环检测，否则一次size()就可能栈溢出。

五、桥接与享元：分离维度、共享对象

桥接模式要解决的问题是「两个独立变化的维度被继承焊在了一起」。假设图形按形状分（圆、方）又按颜色分（红、绿），用继承实现需要「形状数 × 颜色数」个子类；桥接把颜色抽成一个实现接口，形状抽象类里持有该接口，子类数量降为「形状数 + 颜色数」，且两个维度可以各自独立扩展、运行时还能切换实现。JDBC 是它的教科书应用：DriverManager 与统一的Connection/Statement抽象属于抽象部分，各家数据库驱动是实现部分，换数据库不用改业务代码。桥接与策略模式结构相似，区别在目的：策略模式封装的是可互相替换的算法，桥接分离的是抽象与实现两个维度。

享元模式用共享技术支撑大量细粒度对象，核心是把对象状态拆成内蕴状态与外蕴状态：内蕴状态（如颜色、字体）不变，放在共享对象内部；外蕴状态（如坐标）随场景变化，由客户端在调用时传入，不进入共享对象。这样「20 个不同位置的圆」只需要 5 个对象。实现上用HashMap做池子，池子本身必须由工厂统一管理，否则共享无从谈起。

import java.util.HashMap;
import java.util.Map;

// 共享的享元对象：只保存内蕴状态（颜色）
public class Circle {
    private final String color;
    public Circle(String color) { this.color = color; }
    // 外蕴状态（坐标、半径）由客户端传入
    public void draw(int x, int y, int radius) {
        System.out.println("画一个 " + color + " 的圆，圆心(" + x + "," + y + ")，半径 " + radius);
    }
}

// 享元工厂：HashMap 做缓存，负责共享与复用
public class CircleFactory {
    private static final Map<String, Circle> POOL = new HashMap<>();

    public static Circle getCircle(String color) {
        return POOL.computeIfAbsent(color, Circle::new);
    }
}

public class FlyweightDemo {
    public static void main(String[] args) {
        String[] colors = {"red", "green", "blue", "black", "white"};
        for (int i = 0; i < 20; i++) {
            // 20 次取用，实际只创建 5 个 Circle 对象
            Circle circle = CircleFactory.getCircle(colors[i % colors.length]);
            circle.draw(i * 10, i * 5, 5);
        }
        System.out.println("共享对象数：" + 5);
    }
}

享元收益直接，代价是引入全局池：池里的对象应当不可变，否则多线程下内蕴状态会互相污染——把本该作外蕴状态的变量塞进共享对象，正是最常见的错误。String 常量池、连接池、线程池思想相近（严格说连接池共享的是「昂贵资源」，更偏对象池）。

六、小结：先问意图，再选结构

结构型模式都在「不修改既有类」的前提下改变结构，选择时先问「我要解决什么」。接口对不上，用适配器；动态叠加职责，用装饰器（构造方法传入被装饰者，可嵌套）；控制访问或隐藏真实对象，用代理（内部自建目标）；简化一堆子系统的调用，用外观；统一处理树形的部分-整体，用组合；两个独立维度导致子类爆炸，用桥接；海量相似对象吃内存，用享元。也要记住：模式是沟通词汇，不是 KPI——一个if或一次方法提取就能解决的，加抽象只会让后来人多绕弯。下一章进入行为型模式。
