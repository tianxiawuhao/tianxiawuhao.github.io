5.5 设计模式：结构型

Posted on 2024-10-16，6 min read

上一章介绍了创建型模式，解决的是“对象怎么造出来”。这一章换一个角度：对象已经存在、类也已经写好，但它们的结构拧不到一起——旧接口和新系统对不上、继承层次越写越深、客户端要面对十几个子系统类。结构型模式正是处理这类问题的七种套路：适配器、桥接、组合、装饰、外观、享元、代理。本章不堆砌定义，而是按“为什么需要 → 怎么做 → 示例 → 常见坑”的顺序，把最常用的几种讲透，并给出可以直接编译运行的 Java 示例。适合已经会写接口与继承、但面对既有代码改造时不知从哪下手的读者。

结构型模式总览：先分清它们各自对付什么

结构型模式关心的是“类与对象怎么组装”。按意图大致可以分成三组：

  • 接口转换与解耦：适配器（Adapter）把不兼容的接口转成客户端期望的接口；桥接（Bridge）把抽象与实现拆成两个可以独立变化的维度；外观（Facade）为一组子系统提供一个统一入口。
  • 结构复用：装饰器（Decorator）在不改原类的前提下动态叠加职责；代理（Proxy）在访问真实对象前后插入控制逻辑；享元（Flyweight）共享细粒度对象以节省内存。
  • 层次表达：组合（Composite）用树形结构统一对待“单个对象”与“对象容器”。

它们和创建型、行为型的分界线很清楚：创建型管“生”，行为型管“交互与职责分配”，结构型管“拼装关系”。判断该用哪一个，可以先问一句：要解决的是接口对不上、维度太多、访问要受控，还是整体与部分要一视同仁。

适配器与桥接：接入旧代码，拆开两个变化维度

适配器解决的是“东西是好的，就是插不进去”。JDK 里最经典的例子是把老的 Enumeration 适配成 Iterator（Collections.list() 与 Collections.enumeration() 就是这对转换），日常更多见于对接第三方 SDK 或遗留系统。

适配器有两种写法：类适配器用继承被适配者并实现目标接口；对象适配器用组合持有一个被适配者实例。Java 只支持单继承，类适配器因此只能适配一个类，而且要求目标类型是抽象类，扩展余地小，实践中推荐对象适配器。常见的说法“适配器至多只能适配一个适配者类、目标类必须是抽象类”，只在类适配器的语境下成立；对象适配器改用组合，可以同时持有多个被适配者，目标也通常是接口。

// 目标接口：新系统只认这个
public interface Target {
    void request();
}

// 被适配者：已有的、不能改的旧类
class Adaptee {
    public void specificRequest() {
        System.out.println("Adaptee.specificRequest");
    }
}

// 对象适配器：组合而非继承
class ObjectAdapter implements Target {
    private final Adaptee adaptee;

    ObjectAdapter(Adaptee adaptee) {
        this.adaptee = adaptee;
    }

    @Override
    public void request() {
        adaptee.specificRequest(); // 接口转换，也可以顺手补全参数与返回值
    }
}

public class AdapterDemo {
    public static void main(String[] args) {
        Target target = new ObjectAdapter(new Adaptee());
        target.request(); // 输出：Adaptee.specificRequest
    }
}

桥接则是另一种苦恼：一个类有两个独立变化的维度（例如图形既按形状分、又按颜色分），用继承组合会得到 m × n 个子类。桥接把其中一个维度抽成接口，让抽象层持有它，于是子类数量从相乘变成相加，还能在运行时替换实现。JDBC 就是典型：java.sql 的抽象 API 与各厂商驱动实现各自演进，靠 DriverManager 这座“桥”连接；SLF4J 与 Logback/Log4j 的关系同理。

和策略模式的区别常被问起：结构上它们都是“上下文持有接口”，但策略的目的是封装可互换的算法，桥接的目的是分离抽象与实现这两个维度的变化。结构相似不等于意图相同。

装饰器与代理：同样是“包一层”，目的却相反

装饰器和代理的类图几乎一样：装饰者与被装饰者、代理与真实对象都实现同一个接口，都在方法前后插入自定义逻辑。区别只有一句话——装饰器为了增强功能，代理为了控制访问。

  • 装饰器由客户端把原始对象传进构造器，可以层层嵌套、在运行时递归组装，典型如 java.io 的 BufferedReader(new FileReader(...))。
  • 代理通常在代理类内部创建或注入真实对象，客户端并不知道真实对象的存在，关系往往在编译期就定下来了，用于远程调用、延迟加载、权限校验、缓存等场景。
// 装饰器：运行时层层叠加职责
public interface Coffee {
    double cost();
    String name();
}

class SimpleCoffee implements Coffee {
    @Override public double cost() { return 10.0; }
    @Override public String name() { return "美式"; }
}

abstract class CoffeeDecorator implements Coffee {
    protected final Coffee delegate;
    protected CoffeeDecorator(Coffee delegate) { this.delegate = delegate; }
}

class MilkDecorator extends CoffeeDecorator {
    MilkDecorator(Coffee delegate) { super(delegate); }
    @Override public double cost() { return delegate.cost() + 3.0; }
    @Override public String name() { return delegate.name() + " + 牛奶"; }
}

class SugarDecorator extends CoffeeDecorator {
    SugarDecorator(Coffee delegate) { super(delegate); }
    @Override public double cost() { return delegate.cost() + 1.0; }
    @Override public String name() { return delegate.name() + " + 糖"; }
}

Java 还提供了更省事的代理实现：JDK 动态代理（面向接口）和 CGLIB（面向类）。Spring AOP 默认就是“有接口用 JDK 动态代理，无接口用 CGLIB”。

import java.lang.reflect.Proxy;

interface OrderService {
    void create(String id);
}

class OrderServiceImpl implements OrderService {
    @Override public void create(String id) { System.out.println("create " + id); }
}

public class ProxyDemo {
    public static void main(String[] args) {
        OrderService real = new OrderServiceImpl();
        OrderService proxy = (OrderService) Proxy.newProxyInstance(
                OrderService.class.getClassLoader(),
                new Class<?>[]{ OrderService.class },
                (p, method, params) -> {
                    long start = System.nanoTime();
                    Object result = method.invoke(real, params);
                    System.out.println(method.getName() + " 耗时 " + (System.nanoTime() - start) + "ns");
                    return result;
                });
        proxy.create("A001"); // 输出：create A001，随后打印耗时
    }
}

外观、组合与享元：简化、统一与共享

外观是给复杂子系统请一位“前台”。客户端原本要按顺序调用下单、扣库存、发通知三个服务，引入 OrderFacade#placeOrder() 后只需一次调用，依赖从“多对多”变成“客户端对门面”。它的代价是门面容易变成上帝类。有人据此认为外观违反开闭原则，更准确的说法是：新增子系统时通常需要改动门面，但这属于可接受的集中式修改，并不必然违反开闭原则，关键是别把业务逻辑写进门面。

组合让客户端用同一套代码处理文件和文件夹、单个员工和整个部门。要点是叶子和容器实现同一接口，容器内部持有同类型集合，递归自然形成。

import java.util.ArrayList;
import java.util.List;

public interface Node {
    int size();
}

class FileNode implements Node {
    private final int bytes;
    FileNode(int bytes) { this.bytes = bytes; }
    @Override public int size() { return bytes; }
}

class DirNode implements Node {
    private final List<Node> children = new ArrayList<>();
    public void add(Node node) { children.add(node); }
    @Override public int size() {
        int total = 0;
        for (Node child : children) {
            total += child.size(); // 递归，叶子与容器一视同仁
        }
        return total;
    }
}

享元通过共享内部状态、把可变的外部状态交给调用方传入，来支撑海量细粒度对象。文本编辑器中，每个字符复用同一个“字符样式”对象；Integer.valueOf(-128~127) 的缓存与字符串常量池都属于这一思路。需要提醒的是，数据库连接池的目标是复用昂贵的连接，并带有借还与生命周期管理，把它当成享元的教科书例子并不贴切，称之为对象池更准确。

过滤器模式：把「筛选条件」也变成可组合的对象

列表查询里最常见的坏味道，是一串不断变长的条件判断。以员工查询为例，需求从「按性别筛选」变成「按性别 + 婚姻状况」，再变成「性别或婚姻状况」，代码很快就会变成嵌套的 if 与布尔标记组合。过滤器模式（Filter，也叫标准模式 Criteria）把每个筛选条件封成一个对象，再用组合条件把它们串起来，条件本身就成了可以自由拼装的零件。

import java.util.ArrayList;
import java.util.List;

public class Person {
    private final String name;
    private final String gender;         // "MALE" / "FEMALE"
    private final String maritalStatus;  // "SINGLE" / "MARRIED"

    public Person(String name, String gender, String maritalStatus) {
        this.name = name;
        this.gender = gender;
        this.maritalStatus = maritalStatus;
    }

    public String getGender() {
        return gender;
    }

    public String getMaritalStatus() {
        return maritalStatus;
    }

    @Override
    public String toString() {
        return name + "(" + gender + "," + maritalStatus + ")";
    }
}

/** 条件接口：输入一批对象，输出满足条件的子集 */
public interface Criteria {
    List<Person> meetCriteria(List<Person> persons);
}

public class MaleCriteria implements Criteria {
    @Override
    public List<Person> meetCriteria(List<Person> persons) {
        List<Person> result = new ArrayList<>();
        for (Person person : persons) {
            if ("MALE".equalsIgnoreCase(person.getGender())) {
                result.add(person);
            }
        }
        return result;
    }
}

public class SingleCriteria implements Criteria {
    @Override
    public List<Person> meetCriteria(List<Person> persons) {
        List<Person> result = new ArrayList<>();
        for (Person person : persons) {
            if ("SINGLE".equalsIgnoreCase(person.getMaritalStatus())) {
                result.add(person);
            }
        }
        return result;
    }
}

/** 组合条件：把两个条件用「与」或「或」连起来，组合条件本身也是条件 */
public class AndCriteria implements Criteria {
    private final Criteria first;
    private final Criteria second;

    public AndCriteria(Criteria first, Criteria second) {
        this.first = first;
        this.second = second;
    }

    @Override
    public List<Person> meetCriteria(List<Person> persons) {
        return second.meetCriteria(first.meetCriteria(persons));
    }
}

public class OrCriteria implements Criteria {
    private final Criteria first;
    private final Criteria second;

    public OrCriteria(Criteria first, Criteria second) {
        this.first = first;
        this.second = second;
    }

    @Override
    public List<Person> meetCriteria(List<Person> persons) {
        List<Person> result = new ArrayList<>(first.meetCriteria(persons));
        for (Person person : second.meetCriteria(persons)) {
            if (!result.contains(person)) {
                result.add(person);
            }
        }
        return result;
    }
}

组合条件是过滤器模式的精髓：AndCriteria 与 OrCriteria 自己实现了 Criteria，所以可以被继续组合，形成一棵条件表达式树，结构和 WHERE (a AND b) OR c 完全一致。客户端从此只负责「拼条件」，不负责「写循环」。

它和组合模式、责任链模式容易混淆，区分点在于「做什么」：

  • 组合模式表达的是整体与部分构成的树形结构（目录与文件）。
  • 责任链模式是让请求沿着处理者依次传递、直到有人接手；
  • 过滤器模式是对同一批数据反复筛选、逐步收窄结果集。

落到 Java 生态里，Servlet 的 Filter 链、Spring 的 @Conditional、Lambda 的 Predicate 组合（predicate1.and(predicate2).or(predicate3)）都是过滤器思想的具体实现——能用 Predicate 表达的条件组合，就不必手写一套 Criteria 类层次。

常见坑与小结

第一，别为了用模式而用模式。适配器是救火队员，只在接口无法统一时登场；如果项目还在设计阶段，直接重构接口比套适配器更干净。第二，装饰器和代理不要混用职责：既要增强功能又要控制访问时，先想清楚哪一层负责什么，否则嵌套链一深，出问题极难定位。第三，组合模式要防止无限递归：容器允许嵌套自身时，务必保证不会形成环。第四，享元的共享对象必须不可变，否则一处修改会污染所有引用者。

回到主线：结构型模式提供的是一套“拼装词汇”。遇到接口不匹配想到适配器，遇到多维变化想到桥接，遇到访问控制想到代理，遇到功能叠加想到装饰器；遇到子系统太复杂想到外观，遇到树形结构想到组合，遇到对象数量爆炸想到享元。真正要记住的不是类图，而是每个模式背后的那份“变化”——把变化点隔离出来，让其余代码保持稳定，这才是设计模式的价值所在。下一章进入行为型模式，看看对象之间如何分配职责与通信。
