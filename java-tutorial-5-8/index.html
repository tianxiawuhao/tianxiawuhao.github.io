5.8 Excel/PDF 导入导出

Posted on 2026-09-19，8 min read

上一章讲了单元测试与构建规范，再往前几章还讲过 Maven、工具类与日志。工具齐全之后，真实项目里总有一个绕不开的需求：把数据库里的几十万行记录导出成 Excel 交给业务人员，或者把别人发来的 Excel 导进系统。这件事一旦写错 API，代价很直接：一个导出请求就能把 JVM 打挂，一次导入就能让服务反复重启。本章从 POI 的三个 Workbook 讲起，说清大数据量导出、逐行解析导入，以及模板与 PDF 的边界，适合已经会用 Spring MVC 写接口、准备处理真实报表的读者。

先分清三种 Workbook：HSSF、XSSF 与 SXSSF

POI 里操作 Excel 的入口是 Workbook，它的三个实现对应三种完全不同的内存模型。HSSFWorkbook 处理的是 Excel 2003 及更早的 .xls（BIFF8 格式），它受格式本身限制：单表最多 65536 行、256 列。XSSFWorkbook 处理 Excel 2007 之后的 .xlsx（OOXML，本质是一个 zip 包加若干 XML），行上限提高到 1048576。但它是「全量用户模型」：打开文件时把整棵 DOM 树都建成 Java 对象，每一个 Row、Cell 都常驻堆内存，几十万行就足以吃掉几个 GB。SXSSFWorkbook 从 POI 3.8 起提供，它不是新格式，而是 XSSF 之上的一层「滑动窗口」封装，专治大数据量导出。

这里要纠正一个流传很广的说法：「数据量超过 65536 条后用 HSSF 或 XSSF 就会 OOM」并不准确。65536 是 .xls 的硬性行上限，超过应该直接报 IllegalArgumentException（行号越界），而不是 OOM；.xlsx 的上限是 1048576 行，与 65536 无关。真正导致 OutOfMemoryError: Java heap space 的是前面说的全量对象模型，跟行数上限是两回事——百万行导出用 XSSF 会 OOM，用 SXSSF 则不会。

版本用错还有一组典型异常：拿 HSSF 去读 .xlsx 会抛 org.apache.poi.poifs.filesystem.OfficeXmlFileException，反向操作会抛 org.apache.poi.openxml4j.exceptions.InvalidOperationException。判断版本不要自己写 if-else，交给 WorkbookFactory.create(inputStream) 自动识别；如果明确要 SXSSF，就用 new SXSSFWorkbook(xssfWorkbook, 1000) 把已有的 XSSF 包一层，这样还能复用现有代码里的样式与模板。

版本上，本章以 Apache POI 5.x（截至 5.5.x，2025 年底仍在发布）为基线，运行在 Java 17 上。POI 从 4.0 到 5.x 完成的是一次真正的模块拆分。poi 只管 BIFF（.xls）与通用用户模型，OOXML（.xlsx）的能力全部搬进 poi-ooxml。而 3.x 时代那个体积巨大的 poi-ooxml-schemas 已经消失，被拆成默认随 poi-ooxml 引入的 poi-ooxml-lite（只含常用 schema，体积小得多）和按需引入的 poi-ooxml-full。所以在 5.x 的新项目里，XSSFWorkbook 找不到类几乎总是依赖坐标写错，而不是代码写错：

<dependency>
    <groupId>org.apache.poi</groupId>
    <artifactId>poi-ooxml</artifactId>   <!-- 自动带上 poi、poi-ooxml-lite、commons-compress、xmlbeans 等 -->
    <version>5.5.1</version>              <!-- 5.x 区间内取最新，写死前先看官方发布说明 -->
</dependency>
<!-- 只有需要处理冷门 OOXML 部件（完整 chart/signature schema 等）时才换成 poi-ooxml-full -->

从 3.x 升级上来的老项目，除了改坐标还要留意两点。一是 3.x 里那些已废弃的入口在 5.x 上大多已被移除或不再维护（典型如直接拿 XMLReaderFactory 造解析器、部分 HSSFWorkbook 的老构造方式），编译期就会报错，早暴露比运行时炸好。二是 5.x 明确放弃了对 Java 8 以下和一批老旧容器的支持，poi-ooxml 会拉入较新的 commons-compress 与 xmlbeans，与 Spring Boot 的依赖管理版本冲突时要显式对齐，否则容易在运行时抛 NoSuchMethodError 而不是编译失败。

百万行导出：SXSSF 的滑动窗口怎么用

SXSSF 的原理很朴素：构造时指定一个行访问窗口 rowAccessWindowSize，默认 100。内存里最多只保留最近的这 N 行对象，一旦超窗，最早的行就被序列化成临时 XML 文件写到磁盘，对应的 Java 对象随即被回收；如此循环，直到整个表写完。所以内存占用与总行数无关，只与窗口大小和当前行宽度有关。窗口不是越大越好：调大能减少磁盘 IO，但会线性增加内存，一万行左右通常就是上限了。

用 SXSSF 必须接受三条约束。一是只能向后追加，已经刷盘的行不能再改，因此表头、列宽与样式都要在写数据之前定好。二是不支持 Sheet.clone()。三是不做公式求值，公式会作为字符串写入，等到用 Excel 打开时才计算。

SXSSFWorkbook workbook = new SXSSFWorkbook(100); // 内存中最多保留 100 行，其余刷盘
workbook.setCompressTempFiles(true);             // 临时 XML 压缩，省磁盘
try {
    Sheet sheet = workbook.createSheet("人员信息");
    String[] titles = {"编号", "姓名", "手机", "最高学历", "国家地区", "护照号",
                       "籍贯", "生日", "属相", "入职时间", "离职类型", "离职原因", "离职时间"};

    // 表头必须最先写：SXSSF 一旦刷盘就无法回头修改，样式与列宽也要在此前定好
    Row header = sheet.createRow(0);
    for (int i = 0; i < titles.length; i++) {
        header.createCell(i).setCellValue(titles[i]);
    }

    // 数据源务必是游标/分页查询，不要先 findAll() 把百万行塞进 List
    int rowIndex = 1;
    for (EmployeeReportResult r : userCompanyPersonalService.streamByReport(companyId, month)) {
        Row row = sheet.createRow(rowIndex++);
        row.createCell(0).setCellValue(r.getUserId());
        row.createCell(1).setCellValue(r.getUsername());
        row.createCell(2).setCellValue(r.getMobile());
        row.createCell(7).setCellValue(r.getBirthday()); // 需配合 yyyy-MM-dd 的 CellStyle 才显示为日期
    }

    String fileName = URLEncoder.encode("人员信息.xlsx", "UTF-8").replace("+", "%20");
    response.setContentType("application/vnd.openxmlformats-officedocument.spreadsheetml.sheet");
    response.setHeader("Content-Disposition", "attachment;filename=" + fileName);
    workbook.write(response.getOutputStream());
} finally {
    workbook.dispose(); // 关键：删除临时文件，必须放在 finally
}

这段代码里有三个容易漏掉的点：

  • 第一是 dispose()：SXSSF 会在 java.io.tmpdir（Linux 上通常是 /tmp）下生成形如 poi-sxssf-sheet4654655121378979321.xml 的临时文件，只管写不管删，几天就能把磁盘写满；dispose() 负责清理，所以它必须在 finally 里。这里还有一个运行环境的变量。CentOS 7 已于 2024 年 6 月 30 日停止维护（EOL），新部署应换到 Rocky Linux 9／AlmaLinux 9 或 Ubuntu 22.04 及之后的 LTS。这些较新发行版的 systemd 服务常默认开启 PrivateTmp=true，进程看到的 /tmp 实为 /tmp/systemd-private-* 下的独立目录。排查「临时文件到底写哪去了」要用 systemctl show -p PrivateTmp 服务名，而不是直接翻宿主机的 /tmp。反过来，PrivateTmp 也会让这些临时文件随服务重启被清掉，所以它只能兜底，不能当成可靠的落盘缓存。
  • 第二是响应头：.xlsx 建议用上面那个完整的 MIME 类型，而 URLEncoder.encode 会把空格编成 +，浏览器下载时会变成乱码文件名，所以要 replace("+", "%20")。
  • 第三是数据源。导出慢，通常是慢在把整张表查进内存；用 JDBC 游标或 MyBatis 的 ResultHandler 流式取数，再配合 SXSSF，才是完整的低内存方案。

另外，代码里若出现「外层再循环一百次」，那只是为造出大数据量做压测，并不是技巧。

大数据量导入：换用事件模式逐行解析

导出解决了，导入是同一个问题的镜像。用 WorkbookFactory.create() 读一个 50 万行的 .xlsx，POI 会先把整个文档建成 DOM 再交给你遍历，内存曲线和 XSSF 导出一样陡。这时要换成事件模式：既然 .xlsx 内部就是 XML，那就用 SAX 的机制一边扫描一边解析，每读一行处理一行，读完即丢，内存里只留当前行。POI 把这套流程封装成 XSSFReader 加一个回调接口 SheetContentsHandler，你只需要实现三个回调方法。

public void parse(String path) throws Exception {
    OPCPackage pkg = OPCPackage.open(path, PackageAccess.READ);
    try {
        XSSFReader reader = new XSSFReader(pkg);
        SharedStringsTable sst = reader.getSharedStringsTable();
        StylesTable styles = reader.getStylesTable();

        // POI 3.15 起推荐 XMLHelper.newXMLReader()，XMLReaderFactory 已废弃且依赖具体实现
        XMLReader parser = XMLHelper.newXMLReader();
        parser.setContentHandler(new XSSFSheetXMLHandler(styles, sst, new SheetHandler(), false));

        XSSFReader.SheetIterator sheets = (XSSFReader.SheetIterator) reader.getSheetsData();
        while (sheets.hasNext()) {
            try (InputStream in = sheets.next()) {
                parser.parse(new InputSource(in));
                // 每个 sheet 解析完就落库/清空，别把业务对象攒在内存里
            }
        }
    } finally {
        pkg.close(); // 必须关，否则文件句柄泄漏
    }
}

构造 XSSFSheetXMLHandler 时最后那个 boolean 是 formulasNotResults，传 false 表示取公式的计算结果而不是公式文本；这个类在演进中改过构造签名：3.x 时代是 (StylesTable, SharedStringsTable, SheetContentsHandler, boolean)；带 DataFormatter 的重载自 4.x 引入，到 5.x 已成为推荐写法，上面那种不带 DataFormatter 的老构造被标记为过时（@Deprecated）。因此新代码更宜写成 new XSSFSheetXMLHandler(styles, sst, new SheetHandler(), new DataFormatter(), false)，把数值与日期的格式化策略显式交出去，避免不同版本默认行为差异带来的字段错位。同时 SharedStringsTable 可以换成只读的 ReadOnlySharedStringsTable——它省一份内存，代价是构造时要处理 IOException，属于小改动、大收益。

真正写业务逻辑的是处理器。这里必须纠正一种常见写法：用 cellReference.substring(0, 1) 取列只能识别 A 到 Z，一遇到第 27 列（AA）就会把列号当成 A，并覆盖第一列的数据。正确做法是交给 CellReference 解析出列下标。另外 SAX 只回调存在的单元格，空单元格会被跳过，所以不能靠「第几次回调」来数第几列。

public class SheetHandler implements XSSFSheetXMLHandler.SheetContentsHandler {
    private PoiEntity entity;
    private int rowNum;

    @Override
    public void startRow(int rowNum) {           // 行号从 0 开始，0 是表头
        this.rowNum = rowNum;
        this.entity = (rowNum == 0) ? null : new PoiEntity();
    }

    @Override
    public void cell(String cellReference, String formattedValue, XSSFComment comment) {
        if (entity == null || cellReference == null) {
            return;                              // 表头行和无法定位的单元格直接跳过
        }
        int col = new CellReference(cellReference).getCol(); // 不要用 substring(0, 1)
        switch (col) {
            case 0: entity.setId(formattedValue);       break;
            case 1: entity.setBreast(formattedValue);   break;
            case 2: entity.setAdipocytes(formattedValue); break;
            default: break;
        }
    }

    @Override
    public void endRow(int rowNum) {
        if (entity != null) {
            batchSave(entity);                   // 建议攒够一批再批量入库，而不是逐行 insert
            entity = null;
        }
    }
}

模板导出、EasyExcel 与 PDF 的边界

报表往往要求固定格式，于是就有了模板导出：把做好的 .xlsx 作为输入流交给 new SXSSFWorkbook(new XSSFWorkbook(templateStream), 1000)，在既有表头下追加数据。注意模板必须先落到磁盘或内存里再包成 SXSSF，且如前所述，SXSSF 不能再改已刷盘内容、也不做公式求值，所以「动态改表头」「导出后自动算合计」这类需求用 SXSSF 会很别扭，行数不大时直接用 XSSF 更省心。

如果不想被裸 POI 的样板代码淹没，可以考虑 EasyExcel 这一系，但它的维护脉络必须先说清楚：

  • 最初是阿里的 com.alibaba.excel:EasyExcel；
  • 后来由原团队接管并更名为 FastExcel，坐标为 cn.idev.excel:fastexcel。老坐标 com.alibaba.excel 仍被大量存量项目使用，两者包结构与注解基本一致、迁移成本主要在改坐标；
  • 再往后该项目又进入 Apache 孵化器，成为 Apache Fesod (Incubating)，坐标与包名再次变化。

也就是说「EasyExcel」这个名字背后的实际维护方已经换过两轮，网上旧博客里的依赖坐标大多已过期，选型时请直接看官方仓库的当前说明，版本与坐标以官方发布为准（存疑）。功能上它用注解声明表头映射，底层仍是 POI 的 SAX 解析，写法短得多。EasyExcel.write(outputStream, EmployeeRow.class).sheet("人员信息").doWrite(list) 完成导出，EasyExcel.read(file, EmployeeRow.class, new PageReadListener<>(rows -> save(rows))).sheet().doRead() 分批读入。它的价值在于省去手写处理器，但不会替你解决「一次性把数据查进内存」的问题——读进来的批次该落库还是要落库。

最后说说标题里的 PDF。这一点必须明确：POI 只处理 OOXML 和 BIFF，不生成 PDF。生成 PDF 常用的库是 Apache PDFBox（Apache 2.0，商用友好）和 OpenPDF／iText（iText 5 为 AGPL，闭源商用需要商业授权，选型前务必确认许可证）。解析方向更麻烦：PDF 里没有「行」和「列」的概念，只有带坐标的文字块，PDFBox 的 PDFTextStripper 只能取出文本流，表格结构要靠坐标自己还原，扫描件还得先 OCR。两个原始文档都没有涉及 PDF，上面的选型建议属于通用经验，具体版本与授权条款请以官方文档为准（存疑）。

常见坑与小结

把上面几节压缩成一张检查表。第一，别混淆行数上限和 OOM：65536 是 .xls 的上限，.xlsx 是 1048576，而内存爆掉是对象模型导致的，解决办法是换成 SXSSF。第二，临时文件要清：SXSSF 用完不调 dispose()，/tmp 会被 poi-sxssf-* 塞满，磁盘告警往往比内存告警来得更晚也更致命。第三，列定位别用字符串截取，超过 26 列必错，交给 CellReference。第四，样式要复用：CellStyle 由工作簿统一管理且有数量上限（.xls 约 4000、.xlsx 约 64000），在循环里 createCellStyle() 迟早报错。第五，流和包要关：OPCPackage、InputStream、OutputStream 全部走 try-with-resources 或 finally。第六，数据源要流式：导出用游标查询，导入用批量入库，否则瓶颈根本不在 POI。

小结：Excel 导入导出的全部技术选择，都是在「内存」和「功能」之间做交换。小数据量、需要公式和动态表头，用 XSSF；几十万行以上、只关心顺序写入，用 SXSSF 的滑动窗口，并记住 dispose()；读取大文件则放弃用户模型，改用 XSSFReader 加 SheetContentsHandler 的事件模式逐行处理。PDF 不在 POI 的能力范围内，生成和解析各有专门的库。把这几条边界判断清楚，剩下的就是最朴素的工程活：流式取数、批量入库、随手关资源。
