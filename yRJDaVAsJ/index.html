nginx.conf中文详解

Posted on 2022-01-18，15 min read

nginx 的配置结构

nginx.conf 是一个「分层块结构」的配置文件：文件最外层是 main 上下文，往下依次是 events、http，http 里可以并列多个 server，每个 server 里再放多个 location。理解「哪条指令能写在哪个块里」比记住某条指令本身更重要，因为绝大多数 nginx: [emerg] "xxx" directive is not allowed here 报错都是把指令放错了层级。

main                       # 全局：user / worker_processes / pid / error_log
├── events                 # 事件模型与连接数
│   ├── use epoll
│   └── worker_connections 65535
└── http                   # HTTP 服务，可含多个 server、upstream、log_format
    ├── upstream backend   # 后端服务器组（只能在 http 里定义）
    ├── server             # 虚拟主机：listen + server_name
    │   ├── location /     # 路由规则
    │   └── location ~ \.php$
    └── server ...         # 第二个虚拟主机

指令的作用域规则

每条指令都有固定的可写范围，常见的有三类：

  • 只能写在 main：worker_processes、worker_rlimit_nofile、pid、user。
  • 只能写在 http / server / location：root、index、expires、proxy_pass、access_log。
  • 只能写在 http：upstream、log_format、server_names_hash_bucket_size。

作用域是「向下继承、就近覆盖」：写在 http 的 root 会作用于所有 server，而某个 location 里再写一次 root 就只影响它自己。同一层级里重复定义同一指令会直接启动失败，而父子层级重复定义是合法的覆盖行为。

worker 进程与并发能力

nginx 采用 master + worker 的多进程模型：master 只负责读取配置、绑定端口和管理 worker，真正处理请求的是 worker。因此 worker_processes 决定并行处理能力。

# 取值 auto 表示按 CPU 核心数自动设置（1.3.8+ 支持），
# 老版本可写死核心数，例如 8 核机器写 8。
worker_processes auto;

# 每个 worker 能打开的文件描述符上限。
# 应为 0 表示不限制（受系统上限约束），一般直接对齐 ulimit -n。
worker_rlimit_nofile 65535;

events {
    use epoll;                    # Linux 2.6+ 用 epoll，FreeBSD 用 kqueue
    worker_connections 10240;     # 单个 worker 的最大连接数
    multi_accept on;              # 一次事件循环尽量接受全部新连接
}

并发能力的关键是那条常被误传的公式。对 nginx 反向代理来说，每个客户端连接会占用「客户端 + 后端」各一个连接，所以：

\[ \text{理论最大连接数} = \text{worker\_processes} \times \text{worker\_connections} \]
\[ \text{可承载客户端并发} \approx \frac{\text{worker\_processes} \times \text{worker\_connections}}{2} \]

取 worker_connections 65535 是很多老文章的写法，但真正生效的上限由 worker_rlimit_nofile 和内核 net.core.somaxconn、fs.file-max 共同决定；只改 nginx 配置而系统 ulimit -n 仍是 1024，就会在并发达标时出现 worker_connections are not enough 或 502。建议 worker_rlimit_nofile 与 ulimit -n 保持一致，并在 /etc/security/limits.conf 里为 nginx 用户放开。

sendfile 与 TCP 优化

sendfile on 让 nginx 通过内核的零拷贝直接把文件从磁盘送进套接字，省掉「内核态 → 用户态 → 内核态」的两次拷贝和两次上下文切换，静态文件服务收益明显。

sendfile on;        # 静态文件零拷贝，普通站点保持 on
tcp_nopush on;      # 仅在使用 sendfile 时生效：攒满一个数据包再发，减少报文数
tcp_nodelay on;     # 长连接下禁用 Nagle 算法，降低小响应的延迟
aio on;             # 大文件场景可再开异步 IO；也可用 sendfile_max_chunk 限制单次大小
sendfile_max_chunk 1m;

三个指令容易互相踩：tcp_nopush 与 tcp_nodelay 并不矛盾，前者作用于完整文件的批量发送、后者作用于长连接上的小包，nginx 会按场景择一使用。反过来，如果做的是大文件下载、磁盘 IO 已经是瓶颈，可以把 sendfile 关掉以平衡磁盘与网络；aio 在 Linux 上需要配合 directio 才有明显效果。

gzip 压缩

gzip on;
gzip_min_length 1k;              # 小于 1k 的内容压缩后可能更大，不压
gzip_comp_level 5;               # 1~9，5 左右性价比最高，9 费 CPU 收益很小
gzip_types text/plain text/css application/json application/javascript
           application/xml text/xml image/svg+xml;
gzip_vary on;                    # 追加 Vary: Accept-Encoding，供 CDN/代理正确缓存
gzip_disable "msie6";            # 老 IE6 对 gzip 支持有缺陷
gzip_static on;                  # 若已预生成 .gz 文件，直接发送，省 CPU 又省时间
gzip_proxied any;                # 对代理来的请求也压缩（默认只压部分场景）

两个常见坑：一是 gzip_types 默认只包含 text/html，不写这一行会发现 CSS、JS、JSON 全都没压；二是 gzip_http_version 1.0 是十几年前为兼容 Squid 2.5 而写的，现代链路统一用 1.1 即可，写 1.0 只会在部分代理场景下让压缩失效，没必要保留。图片、视频已经是压缩格式，不要放进 gzip_types。

keepalive 长连接

长连接分两段，两段都要配，否则只优化了一半：客户端到 nginx 由 keepalive_timeout / keepalive_requests 控制；nginx 到后端则需要在 upstream 里显式声明 keepalive。

http {
    keepalive_timeout 65s;         # 空闲长连接保持时间，第二个参数可选，用于响应头 Keep-Alive: timeout=
    keepalive_requests 1000;       # 单条长连接最多处理多少个请求
    keepalive_disable msie6;
    client_header_timeout 15s;     # 读请求头的超时，防止慢速攻击占住连接
    client_body_timeout 15s;
    send_timeout 30s;              # 两次写操作之间的超时

    upstream backend {
        server 10.0.0.11:8080;
        server 10.0.0.12:8080;
        keepalive 64;              # 每个 worker 与后端保持的空闲长连接数
        keepalive_requests 1000;
        keepalive_timeout 60s;
    }

    server {
        location /api/ {
            proxy_pass http://backend;
            proxy_http_version 1.1;                 # 1.1 才支持长连接
            proxy_set_header Connection "";         # 清掉 close，交给 upstream keepalive 管理
            proxy_set_header Host $host;
        }
    }
}

只写 upstream keepalive 而漏掉 proxy_http_version 1.1 和 Connection ""，后端连接会在每个请求后被关闭，keepalive 完全不生效——这是排查「后端 TIME_WAIT 暴涨」时最常被忽略的一步。

server_name 匹配

一个请求先按 listen（IP + 端口）找到候选虚拟主机，再在候选里按 server_name 匹配。匹配优先级固定如下：

  1. 精确名字，如 www.example.com；
  2. 以通配符开头的名字，如 *.example.com；
  3. 以通配符结尾的名字，如 www.example.*；
  4. 正则表达式，如 ~^www\d+\.example\.com$；
  5. 都没命中时，使用该 listen 上第一个 server，或显式标记了 default_server 的那个。
server {
    listen 80 default_server;                # 兜底主机，接住所有未匹配域名
    server_name _;
    return 444;                              # 直接断开，避免被扫描器抓到站点信息
}

server {
    listen 80;
    server_name www.example.com example.com;  # 多个名字用空格分隔
    # 名字很多时把公共后缀提出来，减小 hash 表内存占用
    # server_name .example.com;  等价于 example.com *.example.com
}

域名（尤其是长域名或名字很多）报 could not build server_names_hash 时，先调大 server_names_hash_bucket_size（常用 64 或 128），它必须是 CPU 缓存行的倍数；再动 server_names_hash_max_size。

location 匹配优先级

location 的优先级不能只看书写顺序，规则是「先精确、再前缀、后正则」，且只有最长前缀命中 ^~ 或精确命中 = 时才会跳过正则：

  1. = /path：精确匹配，命中即结束，最快；
  2. ^~ /static/：最长前缀匹配且命中后不再尝试正则；
  3. ~ / ~*：正则匹配，按配置中出现的先后顺序取第一个命中项；
  4. 普通前缀 /path：记住最长的一个，如果正则全不命中就用它。

# 命中顺序（自上而下书写只是便于阅读，决定优先级的是前缀与修饰符）：
location = /favicon.ico { log_not_found off; access_log off; }   # 1) 精确
location ^~ /static/    { root /data/www; expires 30d; }         # 2) 前缀且阻断正则
location ~* \.(gif|jpg|jpeg|png|webp|svg)$ { expires 30d; }      # 3) 正则，不区分大小写
location ~ \.php$      { fastcgi_pass 127.0.0.1:9000; }          # 4) 正则，区分大小写
location /             { try_files $uri $uri/ /index.html; }     # 5) 兜底前缀

原文里写的 location ~ .*.(gif|jpg)$ 有两个隐患：正则中的 . 未转义会匹配任意字符；末尾的 ? 让分组变成可选，导致 /a.php.txt 这类路径也会命中 PHP 规则。正确写法是 ~* \.(gif|jpg)$，只匹配以扩展名结尾的 URI。

rewrite 与 return

能用 return 就不要用 rewrite：return 直接结束处理，开销最小；rewrite 会重新走一遍 location 匹配（last）或直接返回 30x（redirect/permanent）。

# 整站跳 HTTPS（推荐：listen 独立成 server，用 return 最简单）
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name example.com;

    # 旧域名与新路径迁移：rewrite 的替换串里不再走 location 匹配
    rewrite ^/old/(.*)$ /new/$1 permanent;

    # 条件判断要少用；if 在 location 中属于「rewrite 模块」，语义易出意外
    if ($request_method !~ ^(GET|HEAD|POST)$) { return 405; }

    location /download/ {
        rewrite ^/download/(.*)$ /files/$1 break;   # break：本 location 内改写后继续
        root /data/www;
    }

    location /search {
        # return 可以返回文本，注意 content-type 要自己写
        default_type text/plain;
        return 200 "ok\n";
    }
}

三个修饰符的区别：last 用新 URI 重新匹配 location；break 只在当前 location 内改 URI，不再匹配；permanent / redirect 直接回 301 / 302。if 处于 rewrite 阶段，对 proxy_pass 等 content 阶段指令的包裹时有已知陷阱，常见的按 UA、Referer 防盗链可以用 map 或 valid_referers 替代。

root 与 alias

两者都用来拼出磁盘路径，区别在于 root 是「拼接」，alias 是「替换」：root 后的路径 = root 值 + 完整 URI；alias 后的路径 = alias 值 + location 匹配部分之外的那段 URI。

# 请求 /img/logo.png
location /img/ {
    root /data/www;        # → /data/www/img/logo.png
}
location /img/ {
    alias /data/static/;   # → /data/static/logo.png
}

# alias 必须与结尾斜杠保持一致，且正则 location 里要用捕获组
location ~* ^/user/(.+)\.(png|jpg)$ {
    alias /data/avatars/$1.$2;
}

最常见的错误是 alias 忘了写结尾斜杠：location /img/ { alias /data/static; } 会去找 /data/staticlogo.png，表现为 404 或 403。另一条经验法则是「alias 只放在 location 里，绝不要写在 server 或 http 层」，写错层级会导致路径完全无法预期。目录索引仍由 index 决定，与 root/alias 无关。

proxy_pass 尾斜杠语义

proxy_pass 带不带斜杠、location 是前缀还是正则，决定了 URI 是否被替换，这是反代 404 的头号原因：

  • location /api/ { proxy_pass http://backend; }：不带 URI，原样透传 /api/xxx；
  • location /api/ { proxy_pass http://backend/; }：带 URI，把 location 匹配到的 /api/ 替换成 /，后端收到 /xxx；
  • location 是正则（~ / ~*）时，proxy_pass 后面不允许带 URI，只能写成 http://backend，否则启动报错。
# 后端网关前缀是 /，前端暴露 /api/ → 去掉 /api 前缀
location /api/ {
    proxy_pass http://backend/;              # 尾斜杠 → 剥掉 /api/
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_connect_timeout 5s;
    proxy_send_timeout 60s;
    proxy_read_timeout 60s;
    proxy_next_upstream error timeout http_502 http_503 http_504;
}

# 后端自带同名前缀，需要原样透传 → 不写 URI
location /service/ {
    proxy_pass http://backend;               # 无尾斜杠 → 保持 /service/
}

顺带提醒：proxy_set_header Host $host 默认并不携带端口，需要端口时用 $http_host。另外 proxy_redirect off 关掉的是重写后端返回的 Location 头，只有确认后端返回的跳转地址确实可直接访问时才关，否则浏览器会被带到内网地址。

\[ \text{最终 URI} = \begin{cases} \text{后端前缀} + \text{URI 中 location 之后的剩余部分}, & \text{proxy\_pass 带 URI} \\ \text{原 URI}, & \text{proxy\_pass 不带 URI} \end{cases} \]

upstream 负载均衡

upstream 定义一组后端服务器，默认是加权轮询；还有 ip_hash（会话保持）、least_conn（按当前连接数）、hash $key（一致性较弱但可指定键）、random。原文提到的 fair 与 url_hash 都是第三方模块，用之前要确认已编译安装。

upstream backend {
    least_conn;                        # 或默认轮询 / ip_hash / hash $request_uri consistent
    server 10.0.0.11:8080 weight=3 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:8080 weight=1;
    server 10.0.0.13:8080 backup;      # 仅当其它节点全部不可用时启用
    server 10.0.0.14:8080 down;        # 人工摘除，保留配置便于灰度
    keepalive 64;
    keepalive_requests 1000;
}

各参数含义：weight 是权重，越大分到的请求越多；max_fails 是在 fail_timeout 窗口内允许的失败次数，超过即标记为不可用；fail_timeout 同时是「统计窗口」和「摘除时长」；backup 是热备；down 是永久摘除。哪些响应算「失败」由 proxy_next_upstream 决定。

被动健康检查

开源版 nginx 只有被动健康检查：只有当请求真的打到某台后端并失败时才会累计 max_fails，没有流量就不会探测。要让检查更积极，需要把超时和判定条件写细，或者使用 nginx Plus 的 health_check 指令 / 另配 nginx_upstream_check_module。

location / {
    proxy_pass http://backend;
    proxy_connect_timeout 3s;
    proxy_read_timeout 10s;
    # 这些情况才换下一台重试；POST 等非幂等请求慎开 non_idempotent
    proxy_next_upstream error timeout http_502 http_503 http_504;
    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 10s;
}

# 需要「主动探测 + 状态面板」时，可另起一个 server 暴露 stub_status
server {
    listen 127.0.0.1:8081;
    location /nginx_status {
        stub_status;
        access_log off;
        allow 127.0.0.1;
        deny all;
    }
}

注意 auth_basic 与 auth_basic_user_file 是两条指令，单独写 auth_basic "x"; 而缺密码文件会启动失败；同时要加 allow/deny 或 listen 127.0.0.1，别把 stub_status 暴露到公网。

日志格式

log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                '$status $body_bytes_sent "$http_referer" '
                '"$http_user_agent" "$http_x_forwarded_for" '
                'rt=$request_time urt=$upstream_response_time';

access_log /var/log/nginx/access.log main buffer=64k flush=5s;
error_log  /var/log/nginx/error.log warn;

server {
    listen 80;
    server_name example.com;
    access_log /var/log/nginx/example.access.log main;
    # 被代理时记录真实客户端 IP，需要先信任代理来源
    set_real_ip_from 10.0.0.0/8;
    real_ip_header X-Forwarded-For;
    real_ip_recursive on;
}

原文里 log_format 定义在 server 内、access_log ... main 却引用了名为 main 的格式，而 log_format 只能写在 http 层，这样配置无法启动。另外 $remote_addr 在反向代理后面拿到的是代理 IP，必须靠 $http_x_forwarded_for 或 set_real_ip_from + real_ip_header 还原，前者只是记录、后者才真正改写 $remote_addr。排查性能问题时应固定带上 $request_time 与 $upstream_response_time。

一份可直接使用的配置

下面这份配置按「静态站点 + 反向代理 + HTTPS」的最小可用场景整理，改写域名、证书路径和后端地址后即可 nginx -t 校验并加载。

user  www-data;
worker_processes  auto;
worker_rlimit_nofile 65535;
error_log  /var/log/nginx/error.log warn;
pid        /var/run/nginx.pid;

events {
    use epoll;
    worker_connections 10240;
    multi_accept on;
}

http {
    include       mime.types;
    default_type  application/octet-stream;
    charset       utf-8;

    log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" "$http_x_forwarded_for" '
                    'rt=$request_time urt=$upstream_response_time';
    access_log /var/log/nginx/access.log main buffer=64k flush=5s;

    sendfile on;
    tcp_nopush on;
    tcp_nodelay on;
    keepalive_timeout 65s;
    keepalive_requests 1000;
    client_header_timeout 15s;
    client_body_timeout 15s;
    send_timeout 30s;
    client_max_body_size 16m;
    client_header_buffer_size 4k;
    large_client_header_buffers 4 16k;
    server_tokens off;                 # 隐藏版本号
    server_names_hash_bucket_size 64;

    gzip on;
    gzip_min_length 1k;
    gzip_comp_level 5;
    gzip_types text/plain text/css application/json application/javascript
               application/xml text/xml image/svg+xml;
    gzip_vary on;
    gzip_disable "msie6";
    gzip_static on;

    upstream backend {
        least_conn;
        server 10.0.0.11:8080 weight=3 max_fails=3 fail_timeout=10s;
        server 10.0.0.12:8080 weight=1 max_fails=3 fail_timeout=10s;
        keepalive 64;
    }

    server {
        listen 80 default_server;
        server_name _;
        return 444;
    }

    server {
        listen 80;
        server_name example.com www.example.com;
        return 301 https://$host$request_uri;
    }

    server {
        listen 443 ssl;
        http2 on;                       # 1.25.1+ 的写法；旧版本用 listen 443 ssl http2;
        server_name example.com www.example.com;

        ssl_certificate     /etc/nginx/ssl/example.com.pem;
        ssl_certificate_key /etc/nginx/ssl/example.com.key;
        ssl_protocols       TLSv1.2 TLSv1.3;
        ssl_session_cache   shared:SSL:10m;
        ssl_session_timeout 1h;

        root  /data/www/example;
        index index.html;

        location = /favicon.ico { access_log off; log_not_found off; }
        location ^~ /static/    { expires 30d; add_header Cache-Control "public"; }
        location ~* \.(gif|jpg|jpeg|png|webp|svg|css|js)$ { expires 7d; }

        location /api/ {
            proxy_pass http://backend/;          # 尾斜杠：剥掉 /api 前缀
            proxy_http_version 1.1;
            proxy_set_header Connection "";
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_connect_timeout 3s;
            proxy_read_timeout 30s;
            proxy_next_upstream error timeout http_502 http_503 http_504;
        }

        location / {
            try_files $uri $uri/ /index.html;
        }
    }
}

常见坑清单

  • autoindex on：会把目录内容列给所有人看，只在确实做下载站时开启，并配合 location 限制范围。
  • 指令放错层级：upstream/log_format 必须在 http 内，alias 只写在 location 内。
  • x_forwarded_for 写反：客户端伪造同名头就能污染日志，务必只信任已知代理并配合 set_real_ip_from。
  • 正则里 . 不转义：.*.(jpg)$ 会额外匹配 aXjpg，应为 \.(jpg)$。
  • limit_zone 已废弃：现代版本用 limit_conn_zone $binary_remote_addr zone=perip:10m; 配合 limit_conn perip 20;。
  • 只配 gzip 不开 gzip_types：CSS/JS/JSON 不会被压缩。
  • reload 与 restart 混用：nginx -s reload 会优雅重启，改配置后先用 nginx -t 验证；kill -HUP 等价于 reload。
