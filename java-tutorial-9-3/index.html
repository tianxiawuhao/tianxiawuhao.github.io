JVM 面试题

Posted on 2026-09-19，6 min read

JVM 面试题的特点是"看着像背书，一追问就露馅"：问完堆和栈的区别，下一句往往是"线上 OOM 你怎么定位"。本文按内存区域、垃圾回收、类加载、调优排查四个环节讲清结论背后的机制，适合会写 Java 但没系统整理过 JVM 的同学。

一、运行时数据区域：哪些线程私有，哪些会 OOM

JVM 在运行时会划分出若干数据区域，按"是否线程共享"记最省力：程序计数器、虚拟机栈、本地方法栈是线程私有的；堆和方法区是线程共享的。线程私有的三个区域随线程创建而创建、随线程结束而销毁，所以不需要垃圾回收；GC 的主要战场是堆和方法区。

  • 程序计数器：记录当前线程执行的字节码指令地址，执行本地方法时为空；唯一不会抛 OutOfMemoryError 的区域。
  • 虚拟机栈：每个方法执行时创建一个栈帧，保存局部变量表、操作数栈等。栈深超限抛 StackOverflowError，扩展失败抛 OOM，大小由 -Xss 指定。
  • 本地方法栈：与虚拟机栈类似，只是为 native 方法服务。
  • 堆：对象分配与 GC 的主要区域，不要求连续内存，扩展失败抛 OOM，由 -Xms、-Xmx 控制。
  • 方法区：存放类信息、常量、静态变量、即时编译后的代码。HotSpot 在 JDK 7 及以前用永久代实现，JDK 8 起改为使用本地内存的元空间。
  • 运行时常量池：方法区的一部分，Class 常量池的字面量与符号引用在类加载后进入这里，并允许运行期动态添加（String.intern()）。
  • 直接内存：JDK 1.4 的 NIO 可用 Native 库分配堆外内存，由堆中 DirectByteBuffer 引用，省去堆内堆外拷贝；受本机内存限制，同样会 OOM。
追问：为什么移除永久代？永久代大小受加载类与常量数量影响、每次 Full GC 后还会变化，很难调准，容易 OOM；改为本地内存中的元空间后由 -XX:MaxMetaspaceSize 限制。

二、垃圾回收：怎么判断对象已死，什么时候回收

判断对象死活有两种思路。引用计数算法给对象加计数器，引用加一、失效减一、归零即回收，简单但无法处理循环引用，因此主流 JVM 没有采用。可达性分析算法从 GC Roots 向下搜索，不可达者才可回收。GC Roots 通常包括：虚拟机栈局部变量表引用的对象、本地方法栈 JNI 引用的对象、方法区中类静态属性与常量引用的对象。

引用按强度分四类：强引用只要可达就不回收；软引用（SoftReference）内存不足时回收，适合做缓存；弱引用（WeakReference）一 GC 就回收，典型是 ThreadLocal 的 key；虚引用（PhantomReference）取不到对象，只用于回收前通知，配合 ReferenceQueue 清理堆外内存。

堆按分代收集划分：新生代（Eden + 两个 Survivor）用复制算法，老年代用标记-清除或标记-整理。对象优先在 Eden 分配，熬过一次 Minor GC 进入 Survivor 且年龄加一，达到 -XX:MaxTenuringThreshold（默认 15）后晋升老年代，大对象可直接进入老年代。Full GC 的常见诱因是：System.gc()（只是建议）、老年代空间不足、空间分配担保失败、元空间不足以及 CMS 的 Concurrent Mode Failure。所以优化只有一句：让对象尽量在新生代被回收，别活到老年代。

// 循环引用：引用计数无法回收，可达性分析可以
public class RefCountDemo {
    private RefCountDemo other;

    public static void main(String[] args) {
        RefCountDemo a = new RefCountDemo();
        RefCountDemo b = new RefCountDemo();
        a.other = b;
        b.other = a;   // 形成环
        a = null;
        b = null;
        System.gc();   // 两个对象已不可达，会被回收
    }
}

三、类加载机制：加载过程与双亲委派

类在运行期第一次使用时才动态加载，生命周期分七个阶段：加载、验证、准备、解析、初始化、使用、卸载，前五个合称类加载过程。容易答错的细节有三处：

  • 准备阶段为 static 类变量分配内存并赋零值，所以 public static int value = 123; 此时是 0，初始化阶段才变成 123；若是 static final 编译期常量，准备阶段直接赋成 123。
  • 解析阶段把常量池的符号引用替换为直接引用，可以在初始化之后开始，以支持动态绑定。
  • 初始化阶段执行类构造器 <clinit>()，由静态变量赋值语句和静态代码块按源码顺序合并而成；父类先于子类执行，虚拟机加锁保证只执行一次。

触发初始化的"主动引用"只有五种：遇到 new、getstatic、putstatic、invokestatic 四条指令；反射调用；初始化子类时先初始化父类；启动时初始化含 main() 的主类；MethodHandle 解析到上述静态字段或方法。其余都是被动引用：子类引用父类静态字段只初始化父类；new SuperClass[10] 只初始化虚拟机生成的数组类；引用编译期常量也不初始化定义常量的类。

必考的双亲委派模型分三层：启动类加载器（C++ 实现，加载 <JAVA_HOME>/lib 下被识别的类库，Java 代码里只能用 null 引用）、扩展类加载器（JDK 9 起被平台类加载器取代）、应用程序类加载器（加载 ClassPath，即 ClassLoader.getSystemClassLoader() 的返回值）。注意父子关系是组合而非继承。

工作过程一句话：先查自己加载过没有，再委派父加载器，父加载器搞不定才自己加载。好处是基础类统一——即使在 ClassPath 下写一个 java.lang.Object，最终加载的仍是启动类加载器加载的那个 Object。

public class MyClassLoader extends ClassLoader {
    private final String rootDir;

    public MyClassLoader(String rootDir) {
        super();                 // 不指定 parent，默认父加载器为系统类加载器
        this.rootDir = rootDir;
    }

    // 双亲委派的逻辑已由 ClassLoader.loadClass 实现，自定义加载器只需重写 findClass
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] data = readClassData(name);
        if (data == null) {
            throw new ClassNotFoundException(name);
        }
        return defineClass(name, data, 0, data.length);
    }

    private byte[] readClassData(String className) {
        String path = rootDir + java.io.File.separatorChar
                + className.replace('.', java.io.File.separatorChar) + ".class";
        try (java.io.InputStream in = new java.io.FileInputStream(path);
             java.io.ByteArrayOutputStream out = new java.io.ByteArrayOutputStream()) {
            byte[] buf = new byte[4096];
            int n;
            while ((n = in.read(buf)) != -1) {
                out.write(buf, 0, n);
            }
            return out.toByteArray();
        } catch (java.io.IOException e) {
            return null;   // 本加载器找不到，委派链继续向上/向下尝试
        }
    }
}

不要重写 loadClass()，它已实现"已加载则返回 → 委派 parent → findClass()"的完整流程，只有想绕过双亲委派（SPI、热部署）才覆盖它。最后记一条规则：两个类相等，要求类本身相同且由同一个类加载器加载，equals()、isAssignableFrom()、instanceof 同理；同名类被两个加载器加载后互不相认，这正是 Tomcat 中同名类不冲突、Webapp 类加载器要打破双亲委派的原因。

四、调优参数与线上排查

调优不是"把参数调好看"，而是在吞吐量与响应时间之间取舍。参数按用途记四组：

# 堆与栈
java -Xms3550m -Xmx3550m -Xmn2g -Xss128k -jar app.jar
#   -Xms/-Xmx 建议设成相同值，避免堆反复伸缩带来的额外开销
#   -Xmn 直接指定新生代大小；也可用 -XX:NewRatio=4 表示新生代:老年代 = 1:4
#   -XX:SurvivorRatio=4 表示 Eden:单个 Survivor = 4:1（Survivor 有两个）

# 收集器选择：吞吐量优先
java -Xmx3800m -Xms3800m -Xmn2g -XX:+UseParallelGC -XX:ParallelGCThreads=20 \
     -XX:+UseParallelOldGC -XX:MaxGCPauseMillis=100 -XX:+UseAdaptiveSizePolicy -jar app.jar

# 收集器选择：响应时间优先（CMS，JDK 9 起废弃，JDK 14 起移除，新项目请用 G1）
java -Xmx3550m -Xms3550m -Xmn2g -XX:+UseConcMarkSweepGC -XX:+UseCMSCompactAtFullCollection \
     -XX:CMSFullGCsBeforeCompaction=5 -jar app.jar

# 排查必备：GC 日志
java -Xms1g -Xmx1g -XX:+PrintGCDetails -XX:+PrintGCTimeStamps -Xloggc:/tmp/gc.log -jar app.jar

思路上，吞吐量优先（批处理、科学计算）适合 Parallel 系列并配较大的新生代；响应时间优先（Web 服务）适合 G1 或已被废弃的 CMS。CMS 用标记-清除、不压缩，久了产生碎片甚至退化为串行 Full GC，需用 -XX:+UseCMSCompactAtFullCollection 配合 -XX:CMSFullGCsBeforeCompaction 定期整理。

线上排查用 JDK 自带工具即可：jps -l 找进程；jstat -gcutil <pid> 1000 看各区使用率与 GC 次数，区分 Minor GC 频繁还是老年代只增不减；jmap -histo:live <pid> | head -30 看对象排名，jmap -dump:format=b,file=heap.hprof <pid> 导出快照交给 MAT，找出"谁在引用这些对象"；CPU 飙高时用 top -Hp <pid> 拿到最耗 CPU 的线程号，转十六进制后到 jstack <pid> 输出里定位栈，常见原因是死循环、锁竞争或频繁 GC。

两个坑：-Xmn 与 -XX:NewRatio 同写时后者常不生效；参数里混入全角标点（如 -Xmx2g：）会被忽略甚至启动失败。另注意版本迁移：-XX:MaxPermSize 已换成 -XX:MaxMetaspaceSize，CMS 参数在 JDK 14 后不可用。

小结

JVM 面试题只有一条主干：内存区域决定"放在哪"，垃圾回收决定"什么时候没"，类加载决定"类怎么进来"，调优排查决定"出问题看什么"。记住这条主线，再补上常被追问的细节——程序计数器不会 OOM、准备阶段只赋零值、子类引用父类静态字段不初始化子类、双亲委派是组合而非继承、CMS 不压缩会产生碎片——就足以应付大多数追问。
