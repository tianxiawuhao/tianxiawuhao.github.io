大数据集群运维

Posted on 2026-09-19，6 min read

集群装好只是起点，真正折磨人的是上线之后的日子：任务排队几小时不动、某个节点磁盘越写越慢、业务量翻倍要加机器、老服务器要退役又不能停服。本章把大数据集群的日常运维串成一条线，共四步：资源规划、调度器与队列、扩容与缩容、监控与故障定位。本章适合已经搭过 Hadoop、YARN 集群，能跑通一个 MapReduce 或 Spark 作业，但一遇到“任务卡住”就只会重启集群的读者。

先建立一个总印象：YARN 把集群抽象成“资源池 + 调度器 + 容器”。四个角色分工如下：

  • ResourceManager（RM）是整个集群资源的管理者；
  • NodeManager（NM）管单台机器的资源；
  • ApplicationMaster（AM）为每个应用向 RM 申请资源并监控任务；
  • Container 则是被封装起来的多维资源（内存、CPU、磁盘、网络）。

记住这个分工，后面所有调参和排障都能对上号。

第一步：规划资源，别让 YARN 和系统抢内存

运维的第一原则是“资源要显式声明”。NodeManager 默认认为自己有很多资源，如果不显式配置，它会按默认值分配容器，很容易把操作系统和其他进程一起挤死。两个最核心的参数是 yarn.nodemanager.resource.memory-mb，即本节点能给容器用的物理内存；以及 yarn.nodemanager.resource.cpu-vcores，即本节点能给容器用的虚拟核数。

规划时按这个顺序算：先用物理内存减去系统和 DataNode、NodeManager 等常驻进程的占用，剩下的才是容器可用内存。虚拟核数一般不超过物理核数，超过部分只是“超售”，调度器会放行，但任务之间会互相抢 CPU。另外要理解 Container 的“最小/最大内存”决定单个容器能申请的资源粒度；如果最大容器内存设得比任务实际需要还小，任务会直接抛出资源请求异常。

还有一个容易被忽略的坑：yarn.nodemanager.resource.cpu-vcores 和 yarn.nodemanager.resource.pcores-vcores-multiplier 这类“自动探测”参数，只在 yarn.nodemanager.resource.detect-hardware-capabilities 打开、且相关值为 -1 时才生效。生产环境建议关掉自动探测、手工写死数值，否则换一台机器跑出来的资源盘子都不一样，容量规划就失去意义。

第二步：选对调度器，管好队列

Hadoop 提供三种调度器：FIFO、容量调度器（Capacity Scheduler）和公平调度器（Fair Scheduler）。FIFO 的特点和现状是：

  • 它是单队列先来先服务，一个跑得久的大作业会把后面所有小作业挡死，只适合学习和单用户环境。
  • Hadoop 3.x 已将 FIFO 标记为过时（deprecated）。新集群按基线配置直接选容量调度器（3.x 的默认值），需要更细的队列内公平性时再选公平调度器。

容量调度器的思路是“按队列切蛋糕”：管理员为每个队列设置资源最低保证（capacity）和使用上限（maximum-capacity），队列内部默认按 FIFO 调度。它的关键特性是资源弹性——空闲队列的资源可以临时借给繁忙队列，一旦原队列有新应用提交，借出去的资源会归还。为了防止某个用户的作业霸占整个队列，容量调度器还支持用户级资源上限。

公平调度器的目标是“时间尺度上人人有份”：队列内部默认用 Fair 策略，两个应用同时跑就各得一半资源，三个应用各得三分之一；新提交的应用会从正在运行的应用手里“拿回”自己应得的份额。两者的区别可以这样记：容量调度器先保证队列的容量下限，公平调度器更强调运行中的公平。抢占（preemption）两者其实都支持，只是默认状态不同：容量调度器自 Hadoop 2.6 起支持抢占，Hadoop 3.x 中 yarn.scheduler.capacity.preemption.enabled 默认为 true；公平调度器需显式打开 yarn.scheduler.fair.preemption（默认 false）。抢占的语义是「先等一段时间、再把容器 kill 掉重新排队」，不是线程优先级那种即时切换，等待时长由 yarn.scheduler.capacity.preemption.max_wait_before_kill 控制。

一份可以直接抄的 Yarn 配置

下面是生产环境常用的 yarn-site.xml 片段，以 4G 内存、4 核的节点为例，把资源收紧到可控范围。真正上线时按机器实际配置改数字即可，不要照搬。

<configuration>
  <!-- 使用容量调度器 -->
  <property>
    <name>yarn.resourcemanager.scheduler.class</name>
    <value>org.apache.hadoop.yarn.server.resourcemanager.scheduler.capacity.CapacityScheduler</value>
  </property>

  <!-- 手工指定资源，关闭硬件自动探测 -->
  <property>
    <name>yarn.nodemanager.resource.detect-hardware-capabilities</name>
    <value>false</value>
  </property>
  <property>
    <name>yarn.nodemanager.resource.memory-mb</name>
    <value>4096</value>
  </property>
  <property>
    <name>yarn.nodemanager.resource.cpu-vcores</name>
    <value>4</value>
  </property>

  <!-- 容器资源粒度 -->
  <property>
    <name>yarn.scheduler.minimum-allocation-mb</name>
    <value>1024</value>
  </property>
  <property>
    <name>yarn.scheduler.maximum-allocation-mb</name>
    <value>2048</value>
  </property>
</configuration>

队列的容量配置写在 capacity-scheduler.xml 里，最小骨架是给 root.default 设定容量与上限，并用 yarn.scheduler.capacity.root.queues 声明子队列列表。改完队列配置不需要重启集群，执行下面这条命令即可让 RM 重新加载：

# 重新加载队列配置（不会中断正在运行的作业）
yarn rmadmin -refreshQueues

# 查看某个队列当前的使用情况
yarn queue -status default

需要提醒的是：yarn rmadmin -refreshQueues 只能刷新队列定义和容量参数；改了调度器实现类、NodeManager 资源总量这类参数，仍然必须重启 YARN 服务才能生效。

第三步：扩容与缩容——服役与退役

加机器（服役）不只是装好服务启动那么简单：新节点如果不在白名单里，即使 DataNode 进程正常，NameNode 也会拒绝让它存储数据。所以标准流程是：先把主机名写进白名单文件，在 hdfs-site.xml 里用 dfs.hosts 指向它，分发配置后刷新 NameNode；再启动新节点的进程，并跑一次数据均衡，把老节点的数据挪过去。

<!-- hdfs-site.xml：允许接入列表（include）与退役列表（exclude）
     属性名 dfs.hosts / dfs.hosts.exclude 自 1.x 沿用至今未变；
     新版文档已把“白名单/黑名单”的称呼改为 include/exclude 文件。
     目录名随小版本变化（3.3.x / 3.4.x），按实际安装路径填写。 -->
<property>
  <name>dfs.hosts</name>
  <value>/opt/module/hadoop-3.3.x/etc/hadoop/include</value>
</property>
<property>
  <name>dfs.hosts.exclude</name>
  <value>/opt/module/hadoop-3.3.x/etc/hadoop/exclude</value>
</property>
# 修改白名单/黑名单后刷新 NameNode，无需重启整个集群
hdfs dfsadmin -refreshNodes

# 页面查看 DataNode 状态：http://hadoop102:9870/dfshealth.html#tab-datanode

缩容（退役）走黑名单：把要下线的节点写进 blacklist 并刷新，节点状态会先变成 decommission in progress，即正在把块复制到其他节点；复制完成后变成 decommissioned，这时才可以停进程关机。这里有一个真实的坑：如果副本数是 3，而当前服役的 DataNode 数量小于等于 3，退役会一直卡在“退役中”——因为 blocks 无处可复制。必须先把副本数调小，或者先加节点，再退役。黑名单文件内容为空时也要保留文件本身，配置文件缺路径会导致集群启动异常。

第四步：监控与故障定位

运维靠三个入口：ResourceManager 的 8088 端口看应用与队列（2.x/3.x 未变）；NameNode 的 9870 端口看 HDFS 健康与 DataNode 状态；JobHistory 的 19888 端口看历史作业。注意 50070 是 Hadoop 2.x 的 NameNode UI 端口，3.x 已经换成 9870，对应属性名也从 dfs.http.address 改为 dfs.namenode.http-address；网上很多老教程混用，照抄会连不上。HA 集群还有一个细节：9870 是 Active NameNode 的页面，Standby 走 9871（dfs.namenode.https-address 与 dfs.namenode.secondary.http-address 是另外两个容易按错的入口）。

还建议开启日志聚集：把 yarn.log-aggregation-enable 置为 true，并配置 yarn.log.server.url 与保留时间，让容器日志在应用结束后自动上传到 HDFS。否则任务失败后容器一销毁，日志就跟着没了，只能靠猜。开启后必须重启 NodeManager、ResourceManager 与 HistoryServer 才生效。

两类典型故障的判断方法如下：

  • 任务一直处于 ACCEPTED 不分配容器：先看是不是队列容量被占满、容器最大内存设得比任务需求小，或 NodeManager 上报的资源总量不够；
  • 某台节点越跑越慢：先查 DataNode 与 NameNode 的心跳。完整的心跳体系是三个时间量——心跳 3 秒一次（dfs.heartbeat.interval）、全量块汇报默认 6 小时一次（dfs.blockreport.intervalMsec=21600000 毫秒，1.x 是 1 小时），而判死要等 10 分 30 秒（2 × dfs.namenode.heartbeat.recheck-interval 5 分钟 + 10 × 3 秒 = 630 秒）。所以“节点看着还在列表里但已经不干活”“退役卡住”这类现象，先对照这三个量判断是心跳停顿、块汇报积压还是单纯慢盘；再用 fio 这类工具单独测这块盘的读写带宽。

慢盘往往表现为“偶尔创建目录要一分钟以上”这类偶发现象，而不是直接报错。

常见坑与小结

把踩坑经验收成几条清单：

  • 内存单位是 MB：别把 4096 当 4G 写错位数；
  • 虚拟核数不能超过物理核数太多：超售换来的是任务互相拖慢；
  • 容器最大内存小于任务申请值时任务直接失败，而不是“降级运行”；
  • 队列参数可以热加载，但调度器实现类和 NM 资源总量改完要重启；
  • 白名单和黑名单文件缺一不可：退役前先确认副本数与节点数；
  • NameNode 与 ResourceManager 都很吃内存：不要和同类重进程挤在同一台机器上。

最后别忘了集群时间同步：内网如果没有配置 NTP 同步，时间漂移会直接搞乱调度与日志排查。

小结一下：集群运维的顺序是“先规划资源，再选调度器，然后才是扩缩容和监控”。资源规划决定了集群的上限，调度器决定了资源在多个团队之间的分配规则，扩缩容决定了集群能否随业务伸缩，而监控与日志决定了出故障时你能不能在几分钟内定位，而不是靠重启碰运气。把这四件事做成有文档、可重复的流程，集群才算真正“可运维”。
