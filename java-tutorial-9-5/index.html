数据库面试题

Posted on 2026-09-19，6 min read

数据库题是 Java 面试里最容易「背了却答不对」的一块：索引、事务、锁、优化、分库分表，几乎每个知识点都能出成场景题，而面试官真正想听的不是名词解释，而是你在具体数据量、具体 SQL 下的判断过程。本章按面试实际追问的顺序，把「索引为什么快 → 怎么判断索引有没有生效 → 隔离级别与锁 → 大表与分库分表 → 场景题怎么答」串成一条线，适合已经会写增删改查、准备面试或要给系统做数据库优化的读者。

一、索引：从 B+ 树到最左前缀

索引的本质是「用有序结构换查找次数」。InnoDB 的索引底层是 B+ 树：只有叶子节点存数据（或主键值），内部节点只存键，因此一个 16KB 的页能装下几百个键，三到四层就能覆盖千万级数据行，一次等值查询通常只需 3～4 次磁盘 I/O。B+ 树相对 B 树的优势也来自这里：内部节点不存数据，同样高度的树能索引更多行；叶子节点用链表相连，范围查询和 ORDER BY 只需定位起点再顺序扫描；且所有查询都走到叶子，耗时稳定。

InnoDB 的主键索引是聚簇索引（索引即数据，叶子节点存整行）；二级索引的叶子节点只存索引列和主键值，因此通过二级索引取非索引列时必须回表——拿主键值再回聚簇索引查一次。若查询所需列全在索引里，就称为覆盖索引，可避免回表。这也解释了面试常问的「为什么建议用自增主键」：自增主键顺序写入，页分裂少；UUID 随机插入会导致频繁页分裂与索引碎片。

联合索引遵循最左前缀匹配：MySQL 从左往右依次匹配索引列，遇到范围查询（>、<、between、like）就停止后面的列。例如有索引 (a, b, c, d)，查询 WHERE a = 1 AND b = 2 AND c > 3 AND d = 4 时只有 a、b、c 用得上索引，d 用不上；把索引建成 (a, b, d, c) 则四列都能参与。注意 a、b 之间可以任意换序，优化器会自动调整等值条件顺序，但范围列必须放在最后。

-- 建表时就规划好索引：等值列在前，范围列在后
CREATE TABLE t_order (
  id          BIGINT       NOT NULL AUTO_INCREMENT,
  user_id     BIGINT       NOT NULL,
  status      TINYINT      NOT NULL,
  amount      DECIMAL(10,2) NOT NULL,
  created_at  DATETIME     NOT NULL,
  PRIMARY KEY (id),
  KEY idx_user_status_time (user_id, status, created_at)
) ENGINE = InnoDB;

-- 走索引：user_id 等值 + status 等值 + created_at 范围，三列都用上
SELECT id, amount FROM t_order
WHERE user_id = 1001 AND status = 1 AND created_at >= '2024-01-01';

-- 用不上索引：违反最左前缀，跳过 user_id 直接查 status
SELECT * FROM t_order WHERE status = 1;

-- 也用不上索引：对索引列做函数运算，破坏了有序性
SELECT * FROM t_order WHERE DATE(created_at) = '2024-01-01';

二、让索引真正生效：EXPLAIN 与慢查询

回答「索引优化」类问题时，不要空谈原则，而要给出定位手段。第一步开慢查询日志（slow_query_log = ON、long_query_time = 1），把超过阈值的 SQL 捞出来；第二步对每条慢 SQL 执行 EXPLAIN，重点看四列：type（访问类型，从优到劣 system > const > eq_ref > ref > range > index > ALL，出现 ALL 基本就是全表扫描）、key（实际使用的索引，为 NULL 说明没走索引）、rows（预估扫描行数，越小越好）、Extra（出现 Using filesort、Using temporary 要警惕，出现 Using index 说明是覆盖索引）。

常见「索引失效」场景可以归成四类：一是违反最左前缀；二是对索引列做运算或调用函数（如上面的 DATE(created_at)，应改写成 created_at >= '2024-01-01' AND created_at < '2024-01-02'）；三是隐式类型转换，字符串列用数字查询、或字符集不一致的连表；四是以 % 开头的模糊匹配 LIKE '%jack'，只能用 LIKE 'jack%'。此外，OR 连接的条件中只要有一侧无索引，整条语句就可能退化为全表扫描。

超大分页是另一个高频场景。LIMIT 1000000, 10 会先取出并丢弃前一百万行，代价极高。可改成延迟关联，让子查询只在索引上扫描并返回主键，再用主键回表取这 10 行：

-- 慢：扫描并丢弃前 1000000 行
SELECT id, user_id, amount FROM t_order
WHERE status = 1 ORDER BY id LIMIT 1000000, 10;

-- 快：延迟关联，先在覆盖索引上翻页拿到主键，再回表取 10 行
SELECT o.id, o.user_id, o.amount
FROM t_order o
JOIN (SELECT id FROM t_order WHERE status = 1 ORDER BY id LIMIT 1000000, 10) AS t
  ON o.id = t.id;

-- 更快：能拿到上一页最大 id 时，直接用主键游标翻页
SELECT id, user_id, amount FROM t_order
WHERE status = 1 AND id > 1000000 ORDER BY id LIMIT 10;

三、事务、隔离级别与锁

事务的四个特性是原子性、一致性、隔离性、持久性（ACID）。其中「隔离性」是面试重点，因为并发事务会带来三类读异常：脏读（读到了别的事务尚未提交、随后被回滚的数据）、不可重复读（同一事务内两次读同一行结果不同，因为中间有别的事务提交了 UPDATE）、幻读（同一事务内两次范围查询行数不同，因为中间有别的事务提交了 INSERT 或 DELETE）。

SQL 标准定义四个隔离级别，逐级解决问题，注意表中「√」表示该级别仍可能发生：

隔离级别脏读不可重复读幻读
READ UNCOMMITTED可能可能可能
READ COMMITTED不可能可能可能
REPEATABLE READ不可能不可能标准允许，MySQL 基本避免
SERIALIZABLE不可能不可能不可能

MySQL InnoDB 的默认级别是 REPEATABLE READ，Oracle、SQL Server 默认是 READ COMMITTED。这里要纠正一个常见说法：很多资料照搬 SQL 标准，说「RR 无法防幻读」，但在 InnoDB 中并不准确。RR 下快照读（普通 SELECT）靠 MVCC 保证一致性，当前读（SELECT ... FOR UPDATE、UPDATE、DELETE）则靠临键锁（Next-Key Lock = 记录锁 + 间隙锁）锁住范围，从而避免幻读。所以准确答法是：SQL 标准中 RR 允许幻读，InnoDB 的 RR 在快照读与当前读下都能基本避免幻读；真正无法保证的是「同一事务内先快照读、再当前读」时可能出现的语义偏差。

锁按粒度分为表锁、行锁、页锁；按模式分为共享锁（S 锁）与排他锁（X 锁），另外还有意向锁（IS/IX，用来快速判断表中是否有行被锁）、记录锁、间隙锁、临键锁、插入意向锁。死锁的产生条件是两个事务以相反顺序持有并申请对方需要的锁，InnoDB 会自动检测并回滚其中代价较小的事务（报 Deadlock found when trying to get lock）。工程上的应对是：按固定顺序访问表和行、缩短事务长度、给更新条件加索引避免锁范围升级为全表扫描。

-- 查看与调整隔离级别（MySQL 8.0）
SELECT @@transaction_isolation;         -- 默认 REPEATABLE-READ
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 当前读：加排他锁，读到最新已提交数据，并锁住命中的索引范围
START TRANSACTION;
SELECT * FROM t_order WHERE user_id = 1001 FOR UPDATE;
UPDATE t_order SET status = 2 WHERE user_id = 1001;
COMMIT;

四、大表优化与分库分表

面对「一张表近千万数据，CRUD 变慢怎么办」这类场景题，回答要分层递进，先低成本再高成本：SQL 与索引层——先看慢日志、补/改索引、消除回表和全表扫描、避免 SELECT *；表结构层——选择合适的数据类型（定长串用 CHAR、密码散列用 CHAR(60) 存 BCrypt）、字段尽量 NOT NULL、适度反范式减少连表；架构层——加缓存（Redis）、读写分离、历史数据归档、最后才是分库分表。

分库分表分两个方向。垂直拆分是按列或按业务拆：垂直分表把不常用的大字段（text、blob）挪到扩展表，让主表更小、每页能装更多行；垂直分库按业务域拆成订单库、用户库，降低单库压力。水平拆分是按行拆：把一张大表按分片键（通常是 user_id）散到多个库或表，如 t_order_0～t_order_7。

但分片是有代价的，面试官往往就在这一步追问：跨库 JOIN 做不了、聚合与排序要改写、AUTO_INCREMENT 主键会冲突（需雪花算法或号段模式）、跨分片查询要广播到所有分片、原本单机的事务变成分布式事务。因此分片键的选择至关重要——要保证高频查询都带上分片键，否则一次查询要扫全部分片。落地时通常借助 ShardingSphere 或 MyCat 这类中间件，由它们完成 SQL 解析、路由、改写与结果归并。若只是读多写少，读写分离（基于 binlog 的主从复制，写主库、读从库）往往比分库分表更划算；但要接受主从延迟导致的「写后立刻读不到」问题，一致性要求高的读仍需走主库。

五、小结

把本章压缩成三条主线：索引看「结构 + 前缀 + 回表」——B+ 树保证层数低，最左前缀决定能否命中，覆盖索引避免回表，用 EXPLAIN 的 type/key/rows/Extra 验证而不是靠猜；事务看「隔离级别 + MVCC + 锁」——记住 InnoDB 默认 RR、Oracle 默认 RC，脏读/不可重复读/幻读的成因要能举例，并知道 InnoDB 用临键锁把 RR 的幻读基本堵住；大表与分片看「分层递进 + 分片代价」——先索引、再结构、再缓存与读写分离，最后才分库分表，并把分布式事务、跨片查询、全局唯一 ID 这些代价一并说出来。面试中遇到场景题，按「数据量 → 查询模式 → 瓶颈定位 → 方案与副作用」四步作答，比背结论更容易拿到高分。
