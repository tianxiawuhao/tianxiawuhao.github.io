elasticSearch查询语句

Posted on 2021-05-28，38 min read

原文：https://distributedbytes.timojo.com/2016/07/23-useful-elasticsearch-example-queries.html
作者：Tim Ojo

版本说明：下文示例最初基于 Elasticsearch 2.x 编写，其中带文档类型的 URL（如 /bookdb_index/book/_search）、命中结果里的 _type 字段、_all 字段、filtered 查询、Groovy 评分脚本等，在 7.x/8.x 中均已移除或废弃。为保留原文脉络，本文只把请求 URL 统一改为 7.x/8.x 可直接执行的 /{index}/_search，其余历史写法保留并逐处标注现代替代方案（注意区分 _type（文档类型，已移除）和 multi_match 的 type 参数（打分策略，仍然有效））。

为了演示不同类型的 ElasticSearch 的查询，我们将使用以下字段搜索书籍文档的集合（ title（标题）, authors（作者）, summary（摘要）, publish_date（发布日期）和 num_reviews（浏览数））。

在这之前，首先我们应该先创建一个新的索引（index），并批量导入一些文档：

创建索引：

PUT /bookdb_index
    { "settings": { "number_of_shards": 1 }}

在写入前先显式声明 mapping：字段类型与分词方式直接决定后面的范围查询、排序和聚合能否得到正确结果。publish_date 必须声明为 date，否则动态映射会把它当作文本；publisher 声明为 keyword，才能被 term / terms 精确匹配并用于聚合。

PUT /bookdb_index/_mapping
{
  "properties": {
    "title":        { "type": "text" },
    "authors":      { "type": "text" },
    "summary":      { "type": "text" },
    "publish_date": { "type": "date" },
    "num_reviews":  { "type": "integer" },
    "publisher":    { "type": "keyword" }
  }
}

批量上传文档（7.x 起一个索引只能有一种文档类型，写入路径统一为 POST /<index>/_bulk，不再带 /book）：

POST /bookdb_index/_bulk
    { "index": { "_id": 1 }}
    { "title": "Elasticsearch: The Definitive Guide", "authors": ["clinton gormley", "zachary tong"], "summary" : "A distibuted real-time search and analytics engine", "publish_date" : "2015-02-07", "num_reviews": 20, "publisher": "oreilly" }
    { "index": { "_id": 2 }}
    { "title": "Taming Text: How to Find, Organize, and Manipulate It", "authors": ["grant ingersoll", "thomas morton", "drew farris"], "summary" : "organize text using approaches such as full-text search, proper name recognition, clustering, tagging, information extraction, and summarization", "publish_date" : "2013-01-24", "num_reviews": 12, "publisher": "manning" }
    { "index": { "_id": 3 }}
    { "title": "Elasticsearch in Action", "authors": ["radu gheorge", "matthew lee hinman", "roy russo"], "summary" : "build scalable search applications using Elasticsearch without having to do complex low-level programming or understand advanced data science algorithms", "publish_date" : "2015-12-03", "num_reviews": 18, "publisher": "manning" }

    { "title": "Solr in Action", "authors": ["trey grainger", "timothy potter"], "summary" : "Comprehensive guide to implementing a scalable search engine using Apache Solr", "publish_date" : "2014-04-05", "num_reviews": 23, "publisher": "manning" }

{
    "query": {
        "multi_match" : {
            "query" : "guide",
            "fields" : ["*"]
        }
    }
}

使用multi_match关键字代替关键字match是对多个字段运行相同查询的便捷快捷方式。该fields属性指定要查询的字段，在这种情况下，我们要查询文档中的所有字段。本文已把示例中的 _all 统一替换为 "*"。
7.x/8.x 提示：_all 字段在 6.0 中废弃、7.0 中移除。要用通配符查询所有字段可写 "fields": ["*"]，也可以显式列出字段，或在 mapping 中用 copy_to 把多个字段汇聚到自定义字段再查询。
这两个API均允许您指定要搜索的字段。例如，要在标题字段中搜索带有“in action”字样的图书，请执行以下操作：

3.提高字段重要性

由于我们正在多个字段中进行搜索，因此我们可能希望提高特定字段中的得分。在以下人为设计的示例中，我们将摘要字段的得分提高了3倍，以提高摘要字段的重要性，这反过来又会增加文档_id 4的相关性。

POST /bookdb_index/_search
{
    "query": {
        "multi_match" : {
            "query" : "elasticsearch guide",
            "fields": ["title", "summary^3"]

4.布尔查询

AND / OR / NOT运算符可用于微调我们的搜索查询，以提供更相关或更具体的结果。这是在搜索API中作为bool查询实现的。该bool查询接受一个must参数（等同于AND），一个must_not参数（等同于NOT）和一个should参数（等同于OR）。例如，如果我要搜索书名中带有“ Elasticsearch”或“ Solr”字样的书，则AND由“克林顿·戈姆利”（clinton gormley）创作，而不由“ radu gheorge”（radu gheorge）创作：

POST /bookdb_index/_search
{
    "query": {
        "bool": {
            "must": [
              { "bool" : { "should": [
                    { "match": { "title": "Elasticsearch" }},
                    { "match": { "title": "Solr" }} ] }},
              { "match": { "authors": "clinton gormley" }}
            ],
            "must_not": { "match": {"authors": "radu gheorge" }}
        }
    }
}

[Results]
"hits": [
      {
        "_index": "bookdb_index",
        "_type": "book",
        "_id": "1",
        "_score": 0.3672021,
        "_source": {
          "title": "Elasticsearch: The Definitive Guide",
          "authors": [
            "clinton gormley",
            "zachary tong"
          ],
          "summary": "A distibuted real-time search and analytics engine",
          "publish_date": "2015-02-07",
          "num_reviews": 20,
          "publisher": "oreilly"
        }
      }
    ]

修正说明：原文示例里出现了两个同名的 must 键，这既不是合法 JSON（多数解析器只保留最后一个），也表达不出“标题命中 Elasticsearch 或 Solr 且作者是 clinton gormley”的意图。上面已改为用数组承载多个 must 子句，并把 clinton gormely 的拼写改成与索引数据一致的 clinton gormley。

注意：如您所见，布尔查询可以包装任何其他查询类型，包括其他布尔查询，以创建任意复杂或深度嵌套的查询。

关于 minimum_should_match：should 的默认行为取决于同级子句。当 bool 中只有 should 时，默认 minimum_should_match=1，至少要命中一个；一旦同级出现 must 或 filter，默认值就变成 0，此时 should 只参与打分、不影响文档是否被召回。本例内层 bool 只有 should，所以仍然要求标题命中 Elasticsearch 或 Solr 之一；若希望“至少命中 2 个”，需要显式写 "minimum_should_match": 2。

5.模糊查询

可以在“匹配”和“多匹配”查询中启用模糊匹配，以捕获拼写错误。模糊程度是根据距原始单词的Levenshtein距离指定的。

POST /bookdb_index/_search
{
    "query": {
        "multi_match" : {
            "query" : "comprihensiv guide",
            "fields": ["title", "summary"],
            "fuzziness": "AUTO"
        }
    },
    "_source": ["title", "summary", "publish_date"],
    "size": 1
}

[Results]
"hits": [
      {
        "_index": "bookdb_index",
        "_type": "book",
        "_id": "4",
        "_score": 0.5961596,
        "_source": {
          "summary": "Comprehensive guide to implementing a scalable search engine using Apache Solr",
          "title": "Solr in Action",
          "publish_date": "2014-04-05"
        }
      }
    ]

注意：fuzziness: "AUTO" 会按词长自动选择编辑距离：0–2 个字符为 0，3–5 个字符为 1，超过 5 个字符为 2。但约 80% 的人为拼写错误编辑距离只有 1，把模糊度固定为 1 通常能在召回率和性能之间取得更好的平衡。模糊匹配要为每个词项展开大量候选词，本身开销不低，不要在长文本字段上对大查询串滥用。更多说明参见 Elasticsearch 参考文档。

6.通配符查询

通配符查询让您可以指定要匹配的模式，而不是一个完整的词项：? 匹配任意单个字符，* 匹配零个或多个字符。注意它匹配的是分词之后的词项（authors 为 text 字段，词项已被转成小写），而不是整个字段值。例如，要查找所有作者姓名以字母 “t” 开头的记录：

POST /bookdb_index/_search
{
    "query": {
        "wildcard" : {
            "authors" : "t*"
        }
    },
    "_source": ["title", "authors"],
    "highlight": {
        "fields" : {
            "authors" : {}
        }
    }
}

性能提示：wildcard、prefix、regexp 都是 term 级查询，不分词，也无法利用倒排索引的前缀优化：以 * 或 ? 开头的模式（如 *t）需要扫描全部词项，代价极高；即使不以通配符开头，一次查询也可能展开成大量词项。生产环境应优先使用 match_phrase_prefix、completion suggester，或在索引期用 edge-ngram 过滤器预处理，并且绝不要把用户输入直接拼进模式串。

7.正则表达式查询

正则表达式查询使您可以指定比通配符查询更复杂的模式。

POST /bookdb_index/_search
{
    "query": {
        "regexp" : {
            "authors" : "t[a-z]*y"
        }
    },
    "_source": ["title", "authors"],
    "highlight": {
        "fields" : {
            "authors" : {}
        }
    }
}

[Results]
"hits": [
      {
        "_index": "bookdb_index",
        "_type": "book",
        "_id": "4",
        "_score": 1,
        "_source": {
          "title": "Solr in Action",
          "authors": [
            "trey grainger",
            "timothy potter"
          ]
        },
        "highlight": {
          "authors": [
            "<em>trey</em> grainger",
            "<em>timothy</em> potter"
          ]
        }

注意：Elasticsearch 的 regexp 查询使用受限的自动机语法，并不是完整的 PCRE，只支持一部分操作符，而且模式始终是对整个词项做匹配（相当于自动加上 ^ 和 $）。它同样属于高开销查询，只应在必要时使用。

8.匹配词组查询

匹配词组查询要求查询字符串中的所有术语都存在于文档中，并按照查询字符串中指定的顺序并且彼此接近。默认情况下，术语必须彼此完全平行，但是您可以指定一个slop值，该值指示在仍将文档视为匹配项时允许相隔多远的术语。

POST /bookdb_index/_search
{
    "query": {
        "multi_match" : {
            "query": "search engine",
            "fields": ["title", "summary"],
            "type": "phrase",
            "slop": 3
        }
    },
    "_source": [ "title", "summary", "publish_date" ]
}

[Results]
"hits": [
      {
        "_index": "bookdb_index",
        "_type": "book",
        "_id": "4",
        "_score": 0.22327082,
        "_source": {
          "summary": "Comprehensive guide to implementing a scalable search engine using Apache Solr",
          "title": "Solr in Action",
          "publish_date": "2014-04-05"
        }
      },
      {
        "_index": "bookdb_index",
        "_type": "book",
        "_id": "1",
        "_score": 0.16113183,
        "_source": {
          "summary": "A distibuted real-time search and analytics engine",
          "title": "Elasticsearch: The Definitive Guide",
          "publish_date": "2015-02-07"
        }
      }
    ]

注意：在上面的示例中，对于非短语类型查询，文档的_id 1得分通常更高，并且_id 4由于其字段长度较短而出现在文档的前面。但是，在进行短语查询时，会考虑到术语的接近度，因此文档_id 4得分会更高。

9.匹配词组前缀

匹配词组前缀查询可在查询时提供“按需输入”或“穷人”版本的自动完成功能，而无需以任何方式准备数据。像match_phrase查询一样，它接受一个slop参数以使单词顺序和相对位置的刚性降低一些。它还接受该 max_expansions 参数来限制匹配项的数量，以降低资源开销。

POST /bookdb_index/_search
{
    "query": {
        "match_phrase_prefix" : {
            "summary": {
                "query": "search en",
                "slop": 3,

10.请求参数

query_string 查询用一套简写语法同时表达多字段匹配、布尔、加权、模糊、通配符、正则和范围查询。下面的示例对 “saerch algorithm” 做模糊搜索（~1 表示允许 1 个编辑距离的拼写错误），要求作者是 “grant ingersoll” 或 “tom morton”；查询覆盖所有字段，同时把 summary 的权重提高 2 倍。

        "fields" : {
            "summary" : {}
        }
    }
}

11.简单查询字符串

simple_query_string 查询是 query_string 查询的一种版本，更适合在暴露给用户的单个搜索框中使用。它分别用+ / | /-代替了AND / OR / NOT的使用，并且丢弃了查询的无效部分，而不是在用户犯错时抛出异常。

POST /bookdb_index/_search
{
    "query": {
        "simple_query_string" : {
            "query": "(saerch~1 algorithm~1) + (grant ingersoll)  | (tom morton)",
            "fields": ["*", "summary^2"]
        }
    },
    "_source": [ "title", "summary", "authors" ],
    "highlight": {
        "fields" : {
            "summary" : {}
        }
    }
}

15.过滤查询

版本提示：filtered 查询在 Elasticsearch 5.0 中已被移除，下面的写法只能在 2.x 上执行；5.x 及以后请直接使用 bool 查询的 filter 子句，本节末尾给出了等价改写。

筛选查询允许您先筛选查询结果。在我们的示例中，我们查询标题或摘要中带有 “Elasticsearch” 一词的图书，但希望把结果过滤为仅包含 20 条或更多评论的图书。

POST /bookdb_index/_search
{
    "query": {
        "filtered": {
            "query" : {
                "multi_match": {
                    "query": "elasticsearch",
                    "fields": ["title","summary"]
                }
            },
            "filter": {
                "range" : {
                    "num_reviews": {
                        "gte": 20
                    }
                }
            }
        }
    },
    "_source" : ["title","summary","publisher", "num_reviews"]
}

[Results]
"hits": [
      {
        "_index": "bookdb_index",
        "_type": "book",
        "_id": "1",
        "_score": 0.5955761,
        "_source": {
          "summary": "A distibuted real-time search and analytics engine",
          "publisher": "oreilly",
          "num_reviews": 20,
          "title": "Elasticsearch: The Definitive Guide"
        }
      }
    ]

注意：筛选查询并不要求一定存在被筛选的查询；只写 filter 时相当于 match_all 加上过滤条件。

5.x 之后的变化：filtered 查询本身已移除，过滤条件改为写在 bool 的 filter（或 must_not）子句里。这类“过滤上下文”不参与打分，因此可以复用 Lucene 的 bitset 缓存，但不打分并不等于一定更快，最终仍取决于过滤条件本身的代价。此外，size: 0 的聚合请求还会使用节点级 request cache，这与过滤上下文是两套不同的缓存机制，早期文档中“过滤器首次使用后即被缓存”的说法已经过时。

更新：filtered 查询已在 Elasticsearch 5.0 中被删除，由 bool 查询取代。下面是上面示例的等价改写，返回结果完全相同；查询与过滤都放在 bool 里，其中 must 参与打分、filter 不参与打分，两者都可以接受数组。

POST /bookdb_index/_search
{
    "query": {
        "bool": {
            "must" : {
                "multi_match": {
                    "query": "elasticsearch",
                    "fields": ["title","summary"]
                }
            },
            "filter": {
                "range" : {
                    "num_reviews": {
                        "gte": 20
                    }
                }
            }
        }
    },
    "_source" : ["title","summary","publisher", "num_reviews"]
}

在下面的示例中，这也适用于多个过滤器。

16.多个过滤器

多个过滤条件可以组合在同一个 bool 查询里：must / filter 表示“必须满足”，must_not 表示“必须不满足”，而 should 在同时存在 must 或 filter 时默认只影响打分、不构成筛选条件。因此“必须由 oreilly 出版”应当写成 filter 里的 term 查询，而不是原文中只起加分作用的 should。下面的示例要求：至少有 20 条评论、2015 年之前未出版、且由 oreilly 出版。

19.功能评分：脚本评分

如果内置的评分功能无法满足您的需求，还可以自己写评分脚本。在我们的示例中，希望脚本先考虑 publish_date，再决定评论数量该以什么方式计入分数：较新的书不太可能积累很多评论，不应该因此被惩罚。
下面这块是 Elasticsearch 2.x 时代的 Groovy 写法——Groovy 动态脚本已在 5.0 中移除，7.x/8.x 请使用默认的 Painless 脚本：

publish_date = doc['publish_date'].value
num_reviews = doc['num_reviews'].value

if (publish_date > Date.parse('yyyy-MM-dd', threshold).getTime()) {
  my_score = Math.log(2.5 + num_reviews)
} else {
  my_score = Math.log(1 + num_reviews)
}
return my_score

下面是等价的 Painless 写法。脚本里 doc['publish_date'].value 已经是 ZonedDateTime，这里把它转成毫秒时间戳，阈值也以毫秒参数传入，从而避免在脚本中解析日期字符串：

    "function_score": {
      "query": { "multi_match": { "query": "search engine", "fields": ["title", "summary"] } },
      "functions": [
        {
          "script_score": {
            "script": {
              "lang": "painless",
              "params": { "threshold_millis": 1438214400000 },
              "source": "long pd = doc['publish_date'].value.toInstant().toEpochMilli(); double n = doc['num_reviews'].value; return pd > params.threshold_millis ? Math.log(2.5 + n) : Math.log(1.0 + n);"
            }
          }
        }
      ]
    }
  },
  "_source": ["title", "summary", "publish_date", "num_reviews"]
}

20.分页、聚合与性能实践

正文第 1 节的完整 DSL 示例中已经用到了 from / size，这是最常用的分页方式：from 是要跳过的文档数，size 是返回的文档数，两者之和不能超过 index.max_result_window（默认 10000），否则请求会被直接拒绝。深分页时，每个分片都要取出并排序 from + size 条文档，再由协调节点归并，开销随页码近似线性增长，因此它只适合浅分页、需要跳页或需要总数（hits.total）的场景。

需要向后翻页、滚动加载时应当使用 search_after：先用一次查询拿到排序值，再把最后一条的排序值作为下一次查询的 search_after。它不需要维护游标状态，每页代价恒定，但只能单向前进，并且必须有一个能唯一确定文档的排序键（常用 _id 作为最后的 tie-breaker）。

GET /bookdb_index/_search
{
  "size": 10,
  "query": { "range": { "publish_date": { "gte": "2014-01-01" } } },
  "sort": [
    { "publish_date": "desc" },
    { "_id": "asc" }
  ],
  "search_after": [1449100800000, "3"]
}

需要一次性遍历大量数据（全量导出、重建索引）时使用 scroll 或 PIT + search_after。scroll 在快照上保持上下文，首次请求返回 _scroll_id，随后用 POST /_search/scroll 分批取；快照会长时间占用分片资源，务必在结束后用 DELETE /_search/scroll 显式清理。scroll 在 7.x 中已不再推荐，官方建议改用带 keep_alive 的 PIT（point-in-time）配合 search_after。

聚合方面有几个常见坑：只做聚合时把 size 设为 0，避免把命中文档也取回来；对 text 字段做 terms 聚合会因分词把一个短语拆成多个桶，应当对 keyword 字段（或 keyword 子字段）聚合；桶数量很大时要用 composite 聚合分页，而不是不断加大 terms.size；terms 聚合的计数默认是近似的，可以用返回值里的 doc_count_error_upper_bound 判断误差上界。例如统计每个出版社的图书数量：

GET /bookdb_index/_search
{
  "size": 0,
  "aggs": {
    "by_publisher": {
      "terms": { "field": "publisher", "size": 10 }
    }
  }
}

最后是几个在 7.x/8.x 中依然常见的性能陷阱：以 * 或 ? 开头的 wildcard / regexp 查询要扫描全部词项；脚本查询与脚本字段（script_score、script_fields）对每个命中文档都要执行一次，属于高开销操作；深分页请改用 search_after；能用过滤上下文（bool.filter、constant_score）表达的条件就不要放进 must 参与打分。字段类型同样关键：把日期或数字误映射成 text（动态映射的默认行为）会让排序变成字典序、让范围查询失效，所以建议像本文开头那样显式声明 mapping。
