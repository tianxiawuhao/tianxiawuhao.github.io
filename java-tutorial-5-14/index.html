5.14 Git 版本控制与分支协作

Posted on 2024-11-07，9 min read

版本控制是团队协作的基础设施，也是面试里区分「会写代码」和「参与过真实项目」的分水岭。很多人用了几年 Git，实际只会 add / commit / push 三条命令，一遇到冲突、误提交、要回滚就手忙脚乱，甚至直接删库重来。问题出在没理解 Git 的核心模型：它管理的是提交快照与指针，而不是「文件的差异」。本章先讲清四个区域与分支的本质，再覆盖日常协作、冲突处理、撤销恢复、暂存与忽略规则，最后给出误提交密码这类真实事故的处理办法。5-3 讲的是 IDE 里的 Git 集成，本章补充命令行视角的完整用法。

从 SVN 到 Git：为什么是分布式

SVN 是集中式版本控制：只有中央仓库保存完整历史，本地工作副本不含版本信息，因此提交必须联网，断网就只能改代码不能记录。Git 是分布式版本控制：git clone 会把整个仓库历史复制到本地，git commit 只写入本地 .git 目录，git push 才同步给团队。

四个区域与文件流转

Git 里一份代码要经历四个区域，把这张图记住，绝大多数命令都能对号入座。

关键认知有两条。第一，本地就能提交：commit 与 push 是两件事，前者写本地历史，后者才共享，所以「还没推出去的提交」可以放心改写。第二，暂存区是「挑选」的地方：git add 决定这次提交包含哪些改动，与文件是否保存无关。两个不相关的修改混在一起时，正确做法是分两次 add + commit，而不是图省事一次提交——历史读得懂，回滚才救得回来。

配套的两个查看命令要分清：git diff 看的是「工作区 vs 暂存区」，git diff --cached（等价于 --staged）看的是「暂存区 vs 上次提交」。提交前先看 --cached，能避免把调试代码、密码、临时文件带进版本库。

安装与首次配置

安装完成后，第一件事就是配好身份，否则第一次提交会直接报错 Please tell me who you are；下面这几条配置也建议一次做完。

# 1. 配置身份：写进每一次提交的作者信息，团队协作必备
git config --global user.name "tianxia"
git config --global user.email "tianxia@example.com"

# 2. 换行符：Windows 与 Linux 混用时避免整文件 diff
#    Windows 上检出为 CRLF、提交时转为 LF；Linux/macOS 保持 LF
git config --global core.autocrlf true     # Windows
git config --global core.autocrlf input    # Linux / macOS

# 3. 中文文件名不转义，git status 里能正常显示中文
git config --global core.quotepath false

# 查看当前配置与来源
git config --list --show-origin

# 生成 SSH 公钥，免去每次 push 输密码（公钥加到 GitHub/GitLab 设置里）
ssh-keygen -t ed25519 -C "tianxia@example.com"
cat ~/.ssh/id_ed25519.pub
ssh -T git@github.com                      # 验证连通性

常见坑有两个：--global 是写到用户主目录的配置，如果公司项目要用企业邮箱，应在项目目录里单独执行一次不带 --global 的 git config，它会写入 .git/config，优先级高于全局配置；修改历史提交的邮箱需要重写历史，不是改配置能解决的。

日常最小工作流

把下面这几条练成肌肉记忆，就覆盖了 90% 的日常操作。

git status                     # 先看状态：哪些改了、哪些已暂存
git diff                       # 看工作区改动内容
git add src/OrderService.java  # 只暂存这个文件
git add -p                     # 交互式挑选同一文件内的部分改动（推荐）
git diff --cached              # 提交前复查暂存区内容
git commit -m "fix(order): 修复库存为 0 时仍可下单的问题"
git push origin main

# 拉取远程更新（团队协作每天第一步）
git pull --rebase origin main  # 把本地提交「垫」在远程更新之上，历史更线性

三条经验：

  • 写提交信息时讲清「为什么」而不是「做了什么」——改了什么 diff 里都能看到；
  • git add -p 比 git add . 安全得多，它能让你在同一文件里只挑相关改动提交；
  • git add . 之前务必确认 .gitignore 已生效，否则 target/、node_modules/、*.log 会被一并提交。

分支：Git 最核心的能力

Git 的分支本质上只是一个指向某个提交的引用文件（约 41 字节），不是目录副本。所以创建和切换分支几乎零成本，这也是它比 SVN 分支好用的根本原因。

git branch                      # 查看本地分支（* 标记当前分支）
git branch -a                   # 连远程分支一起看
git switch -c feature/order     # 新建并切换（等价于 git checkout -b）
git switch main                 # 切回主干（Git 2.23+ 推荐写法）
git merge feature/order         # 把功能分支合并进当前分支
git branch -d feature/order     # 合并后删除已无用的分支
git branch -D feature/order     # 强制删除（未合并时需谨慎）

# 查看提交图，理解分支关系最直观的命令
git log --oneline --graph --all --decorate

生产项目里的分支策略不需要复杂，够用即可：main 保持随时可发布，功能开发开 feature/xxx，修紧急线上问题开 hotfix/xxx，合并前先 git pull --rebase 跟上主干。要避免的是「一个人一条长期分支活三个月」——分支活得越久，合并冲突越大，正确的做法是把需求拆小、频繁合并回主干。

合并、冲突与 rebase

合并冲突的本质是：两条分支修改了同一文件的同一区域，Git 无法自动决定保留哪一份，于是停下合并，把冲突标记写进文件让你决定。

git merge feature/order
# 输出 CONFLICT (content): Merge conflict in src/OrderService.java

# 冲突文件里会出现这样的标记：三个字段分别是 当前分支 / 分界 / 待合并分支
# <<<<<<< HEAD
#         int stock = order.getStock();
# =======
#         int stock = order.getStock() - 1;
# >>>>>>> feature/order

# 手工编辑成最终想要的样子，删掉标记，然后：
git add src/OrderService.java   # 标记为已解决
git commit                      # 完成合并提交（信息已自动生成）

# 如果解决过程中发现搞乱了，随时可以放弃整个合并：
git merge --abort

三条冲突处理纪律：

  • 先看完整标记再动手，不要凭印象删；
  • 解决后必须编译并跑一次相关测试。Git 只保证文本合并成功，不保证逻辑正确，典型的「语法没错但语义错了」就出在这里；
  • 冲突要尽快解决：合并中断期间 HEAD 处于特殊状态，此时不要再开新分支或做无关提交。

再说 merge 与 rebase 的区别，这是面试常问的一对：

merge   ：保留两条分支的真实分叉，产生一个「合并提交」，历史是网状但真实
rebase  ：把你这一串提交逐个「复制」到目标分支之后，历史变成一条直线

选择原则：
- 主干合并功能分支        → 用 merge --no-ff，保留「这里合并过一个功能」的信息
- 本地分支跟随主干更新    → 用 pull --rebase，避免产生一堆无意义的合并提交
- 已经 push 的公共分支    → 绝不要 rebase，因为会重写历史、同事的本地仓库会分叉

远程协作：clone、fetch、pull、push

git clone git@github.com:tianxia/demo.git      # 克隆：拿到完整历史
git remote -v                                  # 查看远程地址（origin）
git fetch origin                               # 只下载远程更新，不改工作区（安全）
git log HEAD..origin/main --oneline            # 看看远程比我多了哪些提交
git pull origin main                           # fetch + merge（或 --rebase）
git push -u origin feature/order               # 首次推送并建立跟踪关系
git push origin --delete feature/order         # 删除远程分支

# 只想看某个文件的历史改动
git log -p -- src/OrderService.java
git blame src/OrderService.java                # 逐行看「最后是谁改的」

fetch 与 pull 的区别值得单独记：fetch 只更新本地的远程跟踪分支（origin/main），工作区一动不动；pull 等于 fetch 加一次合并。所以不确定远程改了什么时，先 fetch 再比较，比直接 pull 稳妥。

撤销与恢复：对着决策树选命令

撤销是 Git 最容易出错的地方，因为它有六七个功能相近的命令。判断顺序只有一句话：先问改动停在哪一步，再问这次提交推没推出去。

# 情形一：改错了，还没 add —— 丢弃工作区改动（不可恢复）
git restore src/OrderService.java        # Git 2.23+ 推荐
git checkout -- src/OrderService.java    # 旧写法，效果相同

# 情形二：已经 add，想撤出暂存区（改动还在工作区）
git restore --staged src/OrderService.java
git reset HEAD src/OrderService.java     # 旧写法

# 情形三：commit 了但还没 push —— 可以改写历史
git commit --amend                       # 只改最近一次：补文件或改信息
git reset --soft HEAD~1                  # 撤销提交，改动留在暂存区
git reset --mixed HEAD~1                 # 撤销提交与暂存，改动留在工作区
git reset --hard HEAD~1                  # 连改动一起丢弃（危险）

# 情形四：已经 push —— 只能追加反向提交
git revert HEAD                          # 生成一个抵消原提交的新提交
git revert <commit-id>                   # 回退指定的历史提交

三个必须记住的细节：

  • --soft / --mixed / --hard 的差别在于改动被保留到哪一层。只有 --hard 会真正丢数据，而 git reflog 是最后的后悔药，默认保留 90 天，能找到 reset --hard 之前的提交；
  • --amend 不是「修改」原提交，而是用一个新的提交替换掉它。所以它只适用于尚未推送的提交；
  • 公共分支上一律用 revert 而不是 reset。后者会重写历史、让所有同事的本地仓库分叉。

事故处理：把密码提交上去了怎么办

这是最典型的真实事故。要区分两种情况：提交还没推送时，可以本地改写历史解决；已经推送就麻烦了——即使你强推覆盖，密钥也已经出现在远程服务器的记录、别人的本地克隆、CI 日志里。

# 还没推送：从工作区删除敏感文件并把它加入忽略规则
git rm --cached config/application-prod.yml   # 从版本库移除，保留本地文件
echo "config/application-prod.yml" >> .gitignore
git commit -m "chore(config): 移除误提交的生产配置"

# 想彻底从历史中抹掉（整个仓库重写，必须通知所有同事重新克隆）
# 官方推荐用 git-filter-repo，老教程里的 filter-branch 已被官方标记为不推荐
git filter-repo --path config/application-prod.yml --invert-paths
git push --force --all
git push --force --tags

正确的事故处置顺序是：

  • 第一步永远是先去平台把密钥吊销/轮换，而不是先折腾 Git 历史——只要密钥还有效，抹历史没有任何意义；
  • 第二步再清理仓库；
  • 第三步把 .gitignore 补齐并加一道 pre-commit 检查，防止同类问题再次发生。

真实项目里更稳妥的做法是密钥根本不进仓库，用环境变量或配置中心下发。

暂存与忽略：两个日常高频工具

# 临时切分支救火：把没写完的改动先收起来
git stash push -m "订单模块做到一半"      # 保存工作区与暂存区改动
git stash list                            # 查看 stash 列表
git stash pop                             # 恢复最近一次并删除该记录
git stash apply stash@{1}                 # 恢复指定记录（保留记录）
git stash drop stash@{0}                  # 丢弃指定记录

# .gitignore 只对「尚未被跟踪」的文件生效
git check-ignore -v target/classes/App.class   # 排查某文件为何被忽略/为何没被忽略

.gitignore 最容易被误解的一点：它不会让已被跟踪的文件「取消跟踪」。如果某个文件在加入忽略规则前就已经提交过，必须先用 git rm --cached <file> 从版本库移除，忽略规则才会生效。下面是一份 Java 项目的常用规则：

# ---------- Java / Maven ----------
target/
!.mvn/wrapper/maven-wrapper.jar
*.class
*.jar
*.war

# ---------- IDE ----------
.idea/
*.iml
*.ipr
*.iws
.vscode/
.settings/
.classpath
.project

# ---------- 日志与临时文件 ----------
*.log
logs/
*.tmp
*.bak

# ---------- 敏感配置 ----------
config/application-local.yml
*.pem
*.jks
.env

# ---------- 前端 ----------
node_modules/
dist/
.npm-cache/

忽略规则的语法要点：/target/ 前导斜杠表示只忽略仓库根目录下的 target；*.log 匹配任意层级的日志文件；! 开头表示「不忽略」，用于给宽泛规则开例外（例如 target/ 之后再写 !.mvn/wrapper/maven-wrapper.jar）；目录规则末尾的斜杠表示只匹配目录。

提交规范与常用命令速查

提交信息是给人看的，团队里统一格式能省下大量沟通成本。常用的是一种带类型前缀的写法：

格式：<type>(<scope>): <subject>

fix(order): 修复库存为 0 时仍可下单的问题
feat(order): 新增订单超时自动关闭
refactor(common): 抽取 ID 生成工具类
docs(readme): 补充本地启动说明
test(order): 补充下单并发场景用例
chore(deps): 升级 Spring Boot 到 3.2.0

type 取值：feat / fix / docs / style / refactor / perf / test / build / ci / chore / revert

顺带记一条写历史的经验：一个提交只做一件事。修改格式和修改逻辑混在一个提交里，回滚时会连格式化一起回滚；功能开发和依赖升级混在一起，出问题无法单独定位。历史清晰是「能排查问题」的前提。

最后是几条最容易忘的命令：git log --oneline --graph --all 看提交图；git log -S"关键词" 按代码内容搜索提交（查「这行代码哪来的」神器）；git reflog 找回误删的分支和 reset --hard 前的提交；git diff main...feature/x 比较两条分支的差异。

小结：Git 只有一个模型——提交是不可变快照，分支是指向快照的指针。四个区域解释了 add / commit / push 的分工，暂存区让你能挑选提交内容，分支的低成本让频繁开分支、频繁合并成为可能。遇到问题时先判断「改动停在哪一步、是否已推送」：没推送就能改写历史（amend / reset / rebase），已推送就只能追加（revert）。把冲突解决流程和撤销决策树走熟，协作中的绝大多数麻烦都不会再让你手忙脚乱。
