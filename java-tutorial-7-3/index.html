进程、网络与性能排查

Posted on 2026-09-19，6 min read

Java 应用上线之后，性能问题往往不是“代码写错了”，而是“资源被谁吃掉了”说不清楚。CPU 打满、内存涨到 OOM、页面变慢，却看不出是哪一层卡住。这一章面向已经把 Spring Boot 应用跑在 Linux（裸机或容器）上的后端工程师，讲清一套可复用的排查路径。先用整体指标判断瓶颈类型，再用进程与网络工具定位到具体进程和连接，最后回到 JVM 层面确认根因。全程只用系统自带命令，不需要额外安装监控。

一、先分清四类瓶颈，再决定用哪个命令

排查最忌讳一上来就敲几十条命令。先花十秒判断瓶颈属于哪一类：CPU 不够、内存不够、磁盘 I/O 慢，还是网络有问题。对应的第一手命令是：top 看 CPU 与负载，free -h 看内存，df -h 看磁盘余量，ss / netstat 看连接状态。

# 1. 负载与 CPU：load average 的三值分别代表 1、5、15 分钟平均负载
top -bn1 | head -5

# 2. 内存：available 才是"还能用多少"，buff/cache 是可回收的
free -h

# 3. 磁盘：先看有没有分区写满
df -h

# 4. 连接：按状态统计 TCP 连接的分布（ss 输出的第一列就是状态）
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn | head

# 旧写法（netstat 属 net-tools，新系统默认不装，见下方对照表）
netstat -nat | awk '{print $6}' | sort | uniq -c | sort -rn | head

关键判断有三条。load average 要和 CPU 核数一起看，四核机器负载 6 表示有任务在排队。free 输出里不要盯 free 一列，available 小于总内存的 10% 时才需要紧张。df -h 的 Use% 到 100% 会直接导致写日志失败、应用报错，这比 CPU 高更紧急。

需要提醒的是，这四个命令只回答“是哪一类资源紧张”，不回答“为什么紧张”。请不要一看到 CPU 高就去改代码，也不要一看到内存占用大就重启应用——重启只会把现场丢掉，下一次告警时仍要从零开始判断。正确的做法是先确认问题类型，再沿着“系统整体指标→进程→进程内部资源→代码”这条链路逐层收敛。每往下走一层，可疑范围都会缩小一个数量级。

另外，排障时最好先留证据再动手：把关键输出重定向到文件（例如 top -bn1 > /tmp/top.log、ss -s > /tmp/ss.log），这样既不会因为终端滚动丢掉信息，也方便事后复盘。若机器还能登录，优先做只读的观测命令，不要急着 kill 进程。

命令换代：net-tools 已弃用，改用 iproute2 的 ip 与 ss

这套命令的基线是 Rocky 9 / Ubuntu 22.04 及更新的发行版：

  • ip 与 ss 由系统自带的 iproute2 提供。
  • ifconfig、route、netstat、arp 属于 net-tools，RHEL 8/9 与 Ubuntu 20.04 起的默认安装已不再包含它，需要 dnf install net-tools 或 apt install net-tools 才能补上。

旧命令不必背，但要看得懂——它们仍大量出现在旧文档、旧脚本和老镜像里，下表按“旧→新”对照。

旧写法（net-tools，已弃用）现代写法（iproute2 自带）用途
ifconfig / ifconfig eth0ip addr show / ip -br addr（ip a）网卡地址与状态
ifconfig eth0 up / downip link set eth0 up / down启停网卡
route -nip route show（ip r）查看路由表
route add default gw 10.0.0.1ip route add default via 10.0.0.1增删路由
arp -aip neigh show（ip n）邻居（ARP）表
netstat -tulnpss -tulnp谁在监听端口
netstat -natss -tan连接列表
netstat -rnip route路由表
netstat -iip -s link网卡收发计数与错误
netstat -sss -s；细项看 nstat -az协议栈统计（重传、丢包）

发行版基线也顺带说明：

  • CentOS 7 已于 2024-06-30 EOL、CentOS 8 于 2021-12-31 EOL，都不再有安全更新。新部署请改用 Rocky Linux 9、AlmaLinux 9 或 Ubuntu 22.04 LTS 及以上。
  • 这些系统默认既不带 net-tools，也默认启用 cgroup v2，本节的写法以它们为准。
  • 若你还在 CentOS 7 上排障，见到的会是下一节的 cgroup v1 路径——命令仍能用，但已是历史写法。

二、进程与 CPU：用 ps 和 top 找到“罪魁祸首”

ps 是 Process Status 的缩写，给出的是执行那一刻的进程快照；需要动态刷新就用 top。常用的两种写法各有侧重。ps -ef 用标准格式列出全部进程，附带 UID、PPID（父进程号）和完整命令行，适合回答“这个进程是谁拉起来的”。ps aux 用 BSD 格式，多出 %CPU、%MEM、VSZ、RSS 和 STAT 列，适合快速找耗资源大户。

注意一个常见错误：把两者混写成 ps -aux 会触发警告 Warning: bad syntax, perhaps a bogus '-'?。原因是带杠的 -a 与 BSD 的 u、x 不属于同一套语法。请统一写成 ps aux 或 ps -ef。

# 找到 Java 进程及其父进程、启动命令
ps -ef | grep '[j]ava'

# 按 CPU 占用排序，取前 10
ps aux --sort=-%cpu | head -10

# 只看指定进程号，自定义字段
ps -o pid,ppid,%cpu,%mem,rss,stat,etime,cmd -p 12345

# top 中按 P 按 CPU 排序、按 M 按内存排序；查看某进程的所有线程
top -Hp 12345

ps aux 里 STAT 列的含义必须认识。R 运行或就绪，S 可中断睡眠（绝大多数等待中的进程都是它），D 不可中断睡眠（通常在等磁盘 I/O，无法被 kill）。T 已停止，Z 僵尸（已退出但父进程未回收）。看到大量 D 状态，应该去查磁盘而不是查代码；看到 Z，要检查父进程是否忘了 wait。

top 头部几行信息量最大：us 高说明业务代码在烧 CPU，sy 高说明系统调用或上下文切换开销大，wa 高说明进程在等 I/O，si 高则可能中断频繁。定位到 Java 进程后，用 top -Hp <pid> 找出最忙的线程号，再转成十六进制去 jstack 输出里对照，才能落到具体代码。

还有一个容易忽略的细节：ps 是快照命令。想持续观察某个进程的资源曲线，可以把它放进循环：

while true; do
  ps -o pid,%cpu,%mem,rss,etime,cmd -p 12345
  sleep 5
done

这比反复手工敲命令更可靠。字段也可以按需裁剪，-o 后跟 pid,ppid,%cpu,%mem,rss,stat,etime,cmd 这类列表即可；输出列太多时反而看不清重点。

三、内存与容器：cgroup 限制和 /proc 的坑

容器场景下有一类看起来很反常的现象。明明 docker run -m 512m 限制了内存，容器里执行 free 和 top 显示的却是宿主机的内存。JVM 也按宿主机的核数与内存来计算默认堆大小和 GC 线程数，结果被 cgroup 直接 OOM Kill。

根源在于 Linux 的 /proc 文件系统并不知道 cgroup 的存在，它按宿主机的真实资源汇报。可以在 cgroup 文件系统里核对容器限额——下面是 Rocky 9 / Ubuntu 22.04+ 现行的 v2 写法，v1 的旧路径一并保留作对照：

# ——— cgroup v2（Rocky 9 / Ubuntu 22.04+ 默认）：配额在 cpu.max，格式为 "quota period"
cat /sys/fs/cgroup/cpu.max        # 如 "200000 100000"=2 核；"max 100000"=不限制
cat /sys/fs/cgroup/cpu.stat       # nr_throttled / throttled_usec 持续增长=配额不够用
cat /sys/fs/cgroup/memory.max     # 如 536870912=512MiB；"max"=不限制
cat /sys/fs/cgroup/memory.current
grep -E 'oom_kill' /sys/fs/cgroup/memory.events   # oom_kill 增长=曾被 cgroup OOM Kill

# 容器内看到的层级：v2 只有一行 "0::/..."；若出现多行 cpu:/memory:/... 则是 v1
cat /proc/self/cgroup

# ——— 旧写法（cgroup v1，CentOS 7 时代）：路径与文件名都不同，照抄只会 no such file
cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us    # -1 表示不限制
cat /sys/fs/cgroup/cpu/cpu.cfs_period_us   # 默认 100000us
grep -E 'nr_throttled|throttled_time' /sys/fs/cgroup/cpu/cpu.stat

# JVM 侧确认它"看到"了多少内存与核数
java -XX:+PrintFlagsFinal -version | grep -Ei 'maxheapsize|activeprocessorcount|maxram'

要注意 cgroup v2 的路径与文件已经改名（配额在 cpu.max，格式是 quota period），照抄 v1 的路径会找不到文件。修复思路是让 JVM 而非宿主机数据说话。升级到具备容器感知能力的 JDK 后，用 -XX:MaxRAMPercentage 按容器限额配置堆，用 -XX:ActiveProcessorCount 显式指定核数。这样线程池就不会按宿主机的 64 核去开线程。生产环境也可以在容器内挂载 lxcfs，让 /proc/meminfo、/proc/cpuinfo 返回容器视角的数据。free -h 与 top 只用于看趋势。判断内存是否泄漏，仍应回到 jstat -gcutil、jcmd <pid> GC.heap_info 和堆转储。

这里要先澄清一个常见误解：进程占用内存高，并不等于 JVM 堆大。ps aux 里的 RSS 包含了堆、元空间、线程栈、直接内存以及 mmap 映射的文件页，其中共享内存还可能被重复计算。因此它只能作为趋势参考，判断是否真的内存泄漏，要看老年代在多次 Full GC 后是否仍持续上涨。

另一条经验是：把“现象”和“容量”分开看。容器被 OOM Kill 时，先确认是达到了 cgroup 内存上限，还是宿主机整体内存不足触发了内核 OOM Killer。memory.max 与 memory.events 里的 oom_kill 计数可以看到前者的证据。两者处理方式完全不同：前者要调 JVM 堆参数，后者要查同机上其他进程。若现场还在，先用 jcmd <pid> GC.heap_info 看堆使用情况。需要留证据时用 jmap -dump:live,format=b,file=/tmp/heap.hprof <pid> 导出堆转储，再离线分析。注意 dump 会造成短暂停顿，生成的文件也可能很大。

四、网络：netstat、ss 与 lsof 的分工

接口变慢、连接超时、端口被占用，属于网络排查。老牌的 netstat 能列出 TCP/UDP 连接、监听端口、路由表和协议统计；新系统更推荐 ss，它直接读内核 netlink，连接数上万时比 netstat 快得多。常用组合是“先按状态统计，再抓具体连接”。

# 谁在监听、谁连着我：-n 不解析域名，-p 显示进程，-t/-u 限协议
ss -lntp
ss -tnp state established

# 排掉表头后按状态计数：ss 的第一列就是状态
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn
# 旧写法（netstat 的状态在第 6 列，net-tools 需自行安装）
netstat -nat | awk '{print $6}' | sort | uniq -c | sort -rn

# 找出连接某端口最多的来源 IP（ss 的对端地址在第 5 列，IPv6 会显示成 [::ffff:…]:port）
ss -tn | grep ':8080' | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn | head
# 旧写法
netstat -nat | grep ':8080' | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn | head

# 反查端口占用进程（无 ss/netstat 的精简镜像可用）
lsof -i :8080
lsof -p 12345 | wc -l

状态本身就能指出方向。CLOSE_WAIT 大量堆积，说明对端已关闭而本端代码没有关闭连接，是典型的连接泄漏，要去检查 HTTP 客户端是否漏了 close。TIME_WAIT 短时间偏高属于正常的四次挥手回收过程，不必急着改内核参数。SYN_RECV 激增则要警惕 SYN Flood。

需要抓包分析时，可以用 tcpdump -i eth0 -nn port 8080 -w /tmp/8080.pcap 落盘，再交给 Wireshark 看三次握手与重传。容器里没有这些命令时，最快的办法是用 nsenter -t <容器主进程PID> -n ss -lntp 借用宿主机的工具，进入容器网络命名空间查看。抓包命令会输出原始报文摘要，注意不要在高峰期对高流量网卡做无过滤的抓包，也不要留下包含敏感数据的 pcap 文件。

网络排查还需要区分 TCP 与 UDP、TCP 与 Unix 域套接字。ss -lntup 可以同时看 TCP 与 UDP 的监听，ss -lx 则用于查看本机进程间通信的 Unix 套接字。某些“端口没被占用却连不上”的情况，正是因为客户端连的是 Unix socket。此外，ip a 看网卡地址、ip route 看路由表，已经完全取代 net-tools 的 ifconfig、route（旧→新对照见第一节）。ping 通不代表端口可达，因为 ICMP 与 TCP 走的策略可能不同，防火墙只放行了其中一种。

如果应用是“偶发超时”，重点看重传与队列丢弃。netstat -s（新写法 ss -s，要看重传等细项用 nstat -az）里的重传段数、ss -lnt 输出中 Send-Q 长期非零（监听队列被打满，新连接会被丢弃），都是硬证据。前者通常指向网络链路或对端处理慢；后者说明应用 accept 速度跟不上，需要调大 backlog 或增加工作线程。

五、小结

性能排查的通用节奏是：用 top、free、df、ss 四板斧判断瓶颈类型，用 ps 与 top -Hp 把问题收敛到进程和线程。接着用 cgroup 文件与 JVM 参数确认容器视角的资源限额，最后用 lsof、tcpdump 处理连接与协议层的疑难。工具基线也要认准：net-tools 的 ifconfig 与 netstat 已被 ip、ss 取代（CentOS 7 已 EOL，新机器选 Rocky 9 或 Ubuntu 22.04+），cgroup 的现行路径是 v2 的 cpu.max。请记住三条最容易踩的坑。ps -aux 是错误语法；容器里的 /proc 默认汇报宿主机数据，会让 JVM 误判可用资源。CLOSE_WAIT 堆积是代码问题，TIME_WAIT 偏多通常无需干预。把这个顺序固化成清单，下次告警时就不必再从零猜测。
