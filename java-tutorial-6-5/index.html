性能诊断工具

Posted on 2026-09-19，6 min read

服务上线之后，最让人头疼的不是「报错」，而是「没报错但不对劲」：接口越来越慢、CPU 莫名其妙飙到 100%、日志停住不再输出、程序最后抛出一个 java.lang.OutOfMemoryError 就再也没起来。这些问题的共同点是——从业务日志里几乎看不出线索，必须钻到 JVM 内部去看。这一章我们就来把 JDK 自带的几件诊断工具串成一条排查链路：先用 jps 找到进程，用 jstat 看运行态势，用 jmap 把堆导出成 dump 文件交给 MAT 分析，最后用 jstack 把线程快照打出来定位死锁和热点线程。适合已经会写 Java、但对线上问题束手无策的读者。

一、先建立排查思路：先看态势，再看细节

诊断工具虽多，用法其实只有两类视角：流程视角和快照视角。流程视角是「隔一段时间看一眼」，观察指标随时间的变化趋势，回答「到底哪里在涨」；快照视角是「把某一瞬间的状态冻住」，回答「到底是什么对象、哪一行代码占着资源」。

对应的工具分工如下：

  • jps：列出当前机器上所有 Java 进程和它们的 PID，是后面所有命令的入口。
  • jstat：轻量级的实时统计，看堆各区使用量、类加载数、GC 次数和耗时，属于流程视角。
  • jmap：查看堆内存汇总、对象直方图，或者把整个堆导出成二进制 dump 文件，属于快照视角。
  • MAT（Memory Analyzer Tool）：分析 dump 文件的图形化工具，用来找内存泄漏的「支配对象」。
  • jstack：打印所有线程的调用栈，用来诊断死锁、线程阻塞和 CPU 飙高。

这些工具都随 JDK 一起安装，位于 $JAVA_HOME/bin 下，不需要额外下载。有一个前提必须记住：必须用与目标进程相同（或兼容）的 JDK 版本去执行这些命令，否则可能连不上进程。另外，jmap 导堆和 jstack 打快照都可能让目标进程短暂停顿（STW），生产环境不要在流量高峰随便执行。

二、jps 与 jstat：快速判断「是不是 GC 的锅」

第一步永远是找到进程号。很多人习惯用 ps -ef | grep java，但输出太长，容易看错。用 jps -l 可以只列出 Java 进程，并显示主类或 jar 的全名：

$ jps -l
7080 sun.tools.jps.Jps
6219 /opt/app/bootstrap.jar

# 找到 PID 之后，先看类加载情况
$ jstat -class 6219
Loaded  Bytes  Unloaded  Bytes     Time
  3273 7122.3        0     0.0     3.98

# 再看 GC 情况：每 1 秒采样一次，共采样 5 次
$ jstat -gc 6219 1000 5
 S0C    S1C    S0U    S1U      EC       EU        OC         OU       MC     MU    CCSC   CCSU   YGC     YGCT    FGC    FGCT     GCT
9216.0 8704.0  0.0   2560.0 62976.0  6127.3   33792.0    20434.9  23808.0 23196.1 2560.0 2361.6   3560   1.078     7    0.244    1.323

这里最需要注意的是 jstat 的时间单位是秒，不是毫秒；容量单位默认是 KB。-gc 输出里 S0C/S1C 是两个 Survivor 区的容量（Capacity），S0U/S1U 是对应区的已使用量（Used），EC/EU 是 Eden 区容量和使用量，OC/OU 是老年代，MC/MU 是元空间，CCSC/CCSU 是压缩类空间。YGC/YGCT 是新生代 GC 的次数与累计耗时，FGC/FGCT 是 Full GC 的次数与累计耗时，GCT 是两者之和。

如果想把每次 GC 的细节留下来做趋势分析，可以在启动参数里加上 -Xloggc:/tmp/gc.log（JDK 9 及以上推荐用统一的日志框架 -Xlog:gc*:file=/tmp/gc.log），它会把带时间戳的 GC 记录写入文件。典型的一行 GC 日志长这样：

[GC (Allocation Failure) [ParNew: 4416K->512K(4928K), 0.0032106 secs] 4416K->1988K(15872K), 0.0032697 secs] [Times: user=0.00 sys=0.00, real=0.00 secs]

解读方式是：方括号里的 ParNew 是收集器名字（这里是新生代并行收集器），4416K->512K(4928K) 是新生代回收前后的使用量和总容量，括号外的 4416K->1988K(15872K) 是整个堆回收前后的使用量和总容量，后面是本次停顿耗时。Full GC 则表示整堆回收。把这行日志和 jstat 的输出对照着看，基本就能判断到底是新生代回收太频繁，还是对象真的晋升到了老年代。

怎么读这些数字？经验判断有三条：一是 FGC 持续快速增长而 OU 每次都回不到低位，说明老年代真的被占满了，多半有内存泄漏；二是 YGCT 占 GCT 的比例很高、单次 YGC 耗时越来越长，说明对象晋升得太快或者新生代偏小；三是 GCT 占程序运行时间的比例明显偏高，吞吐量就上不去了。判断「频繁 GC」靠的是间隔采样，而不是单次输出的绝对值。

三、jmap 与 MAT：定位内存泄漏的元凶

确定是内存问题之后，用 jmap 看细节。jmap -heap 打印堆的整体配置和各代使用情况，jmap -histo 则按对象数量或占用内存给出直方图，能一眼看出是哪类对象在膨胀：

# 堆内存汇总
$ jmap -heap 6219

# 对象直方图（按占用大小排序），只看存活对象加 :live
$ jmap -histo:live 6219 | more
 num     #instances         #bytes  class name
-------------------------------------------------------
   1:       1243522      254673664  [C
   2:        883421       21202104  java.lang.String
   3:         12043        8141456  java.util.HashMap$Node

# 导出堆快照供离线分析
$ jmap -dump:format=b,file=/tmp/dump.dat 6219
Dumping heap to /tmp/dump.dat ...
Heap dump file created [254673664 bytes in 0.032 secs]

直方图中 [C 代表 char[]，[I 代表 int[]，[L+类名 代表对象数组，[B 代表 byte[]。上面这组数据里 [C 占了 2.4 亿字节，基本可以判定是大量字符串没被释放。

-histo:live 会先触发一次 Full GC 再统计，因此统计到的都是真正存活的对象；-dump 加 :live 同理。这个细节很重要：不加 :live 的 dump 会把「已经死掉但还没回收」的对象也算进来，容易误导分析。注意导堆是重量级操作，文件可能和堆一样大（几个 GB 很常见），要确认磁盘空间，并尽量先做一次 Full GC 再导。

二进制 dump 用图形化工具 MAT 打开最直观：它会直接给出 Leak Suspects 报告和支配树（Dominator Tree），把「谁持有了最多内存、谁被谁引用着不放」按占比列出来。实战中常见的结论是某个 Object[] 或某个 HashMap 占了 90% 以上内存，展开引用链就能定位到具体代码里那个只加不减的集合。

更省事的做法是让 JVM 在内存溢出时自动导堆，在启动参数里加上：

-Xms8m -Xmx8m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp

这样下次 OOM 时会自动生成 java_pid<pid>.hprof，事故现场不会丢。顺带说明一点版本差异：jhat 这个老牌的 dump 查看工具在 JDK 9 之后已被移除，JDK 8 上还能用，但官方推荐改用 MAT 或 jvisualvm；jvisualvm 也已从 JDK 9 起不再随 JDK 分发，需要单独下载。

四、jstack：死锁与 CPU 飙高的第一现场

如果日志停住、程序没反应，或者 CPU 突然跑满，问题通常在线程层面。jstack <pid> 会把 JVM 中所有线程的快照打印出来，每个线程带有 nid（操作系统线程号，十六进制）和 java.lang.Thread.State。常见的几种状态含义不同：RUNNABLE 可能真的在跑，也可能在等 IO；BLOCKED (on object monitor) 表示在等锁；WAITING / TIMED_WAITING 通常是 park 或 sleep。

先看死锁。下面这段代码里两个线程以相反顺序申请同一对锁，必然互等：

public class TestDeadLock {
    private static final Object OBJ1 = new Object();
    private static final Object OBJ2 = new Object();

    public static void main(String[] args) {
        new Thread(() -> lock(OBJ1, OBJ2), "t1").start();
        new Thread(() -> lock(OBJ2, OBJ1), "t2").start();
    }

    private static void lock(Object first, Object second) {
        synchronized (first) {
            System.out.println(Thread.currentThread().getName() + " 拿到第一把锁");
            try {
                Thread.sleep(1000); // 留出时间让另一个线程拿到第二把锁
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            synchronized (second) {
                System.out.println(Thread.currentThread().getName() + " 拿到第二把锁");
            }
        }
    }
}

运行时在另一个终端执行 jstack <pid>，输出的结尾会自动附带一段 Found one Java-level deadlock 的说明，直接点名哪两个线程、分别等在哪把锁上，以及锁的持有者。这就是排查死锁最快的方式，不需要任何额外工具。

再看 CPU 飙高。思路是「找出最耗 CPU 的线程，再回到 jstack 快照里找它」。先用 top -Hp <pid> 找到占用最高的线程号，把它转成十六进制（printf "%x\n" <tid>），然后在 jstack 输出里搜索 nid=0x 加上这个十六进制值，就能看到这个线程正在执行的代码行。连续多打几次快照，如果同一个方法反复出现在栈顶，它就是热点。对同一个进程可以重复执行 jstack，说明诊断本身对进程影响很小。

小结与常见坑

把工具用对，比记住参数更重要，几个高频坑值得单独提醒：第一，jps、jstat 看不到进程，通常是权限不一致（命令用的用户和目标进程不同）或 JDK 版本不匹配，而不是进程真的不存在；第二，jstat 的时间列是秒，别当成毫秒去算；第三，jmap -histo 与 -dump 不加 :live 会包含未回收对象，分析前最好先强制 GC 一次；第四，导堆和线程快照都可能造成短暂停顿，生产环境要挑时机，并提前确认磁盘空间；第五，Full GC 并不是「只回收老年代」，它会回收整个堆并顺带处理元空间，所以看到 Full GC 频繁，不要只盯着老年代参数调。

最后记住这条排查链路：jps 找进程 → jstat 看趋势 → jmap/MAT 抓内存 → jstack 抓线程。线上出问题时先别急着改参数，先用工具把「是 GC 太频繁、是内存泄漏、还是线程卡死」这三件事区分清楚，方向对了，改一个参数就能解决；方向错了，调再多参数也只是把问题往后推。
