Spring 全家桶面试题

Posted on 2026-09-19，6 min read

Spring 全家桶的面试题看着杂，其实只围绕一条主线：Spring 替你做了什么事，又是怎么做的。IoC 管对象怎么造，AOP 管功能怎么织，事务管多步操作怎么算一次，Boot 管配置怎么省，Cloud 管多进程之间怎么找到彼此。本文按这五层讲清常见原理题，适合会写注解、但一被追问底层就卡住的读者。

一、IoC 与 DI：反转的是什么

没有 Spring 时，依赖靠自己在代码里 new，类与类强耦合、难以替换和单测。IoC（控制反转）把“创建对象、装配依赖”的权利交给容器，业务类只声明需要什么；DI（依赖注入）是实现 IoC 的手段。记法：IoC 是思想，DI 是做法，不是并列的两个概念。容器内部是工厂 + 反射 + 配置：先读配置得到 BeanDefinition，再反射创建实例，最后按类型或名称注入。

注入方式首选构造器注入（依赖不可变、非空、好单测，Spring 4.3 起单构造器可省 @Autowired）；Setter 注入适合可选依赖；字段注入写得最短，但依赖不可见、无法在容器外构造，不推荐。作用域默认 singleton，另有 prototype 及 Web 环境的 request、session。

@Configuration
@ComponentScan("com.example.demo")
public class AppConfig {

    @Bean
    public OrderRepository orderRepository(DataSource dataSource) {
        return new JdbcOrderRepository(dataSource);   // 参数由容器注入
    }
}

@Service
public class OrderService {

    private final OrderRepository repository;         // final：依赖不可变

    public OrderService(OrderRepository repository) { // 单构造器，无需 @Autowired
        this.repository = repository;
    }
}
常被追问的循环依赖：Spring 用三级缓存解决单例的字段／setter 注入循环依赖。一级 singletonObjects 放成品，二级 earlySingletonObjects 放提前暴露的半成品。三级 singletonFactories 放能产出早期引用的工厂（若需 AOP，就在这里提前生成代理）。构造器注入的循环依赖无法解决，会抛 BeanCurrentlyInCreationException，prototype 作用域也不解决。

二、AOP：代理有两条路

AOP 的动机是 OCP 原则——对扩展开放，对修改关闭。日志、耗时监控、权限、缓存、事务这些横切逻辑若写进每个方法，代码就散了；AOP 把它们抽成切面，由代理在调用前后织入。术语要分清：连接点是所有可以被增强的方法，切入点是实际被增强的方法，通知是拦截后要做的事，切面是通知与切入点的结合。

底层只有两种动态代理。JDK 动态代理基于接口，运行时生成实现同一接口的代理类，只能代理接口中声明的方法。CGLIB 基于类，生成目标类的子类并覆写方法，因此不能代理 final 类、final 方法和 private 方法。Spring AOP 的默认规则是有接口用 JDK、无接口才用 CGLIB，可用 @EnableAspectJAutoProxy(proxyTargetClass = true) 强制 CGLIB。注意 Spring Boot 2.x 起自动配置默认走 CGLIB，与原生 Spring 的默认值不同，这是最容易答错的点。

三、事务：传播行为与失效场景

声明式事务底层就是 AOP 环绕通知：容器把 PlatformTransactionManager 交给 TransactionInterceptor，切入点匹配 @Transactional 后在方法前后完成开启、提交／回滚，不改业务代码，侵入性最小。传播行为共 7 种，记法是“三组加一个默认”：REQUIRED（默认，有就加入、没有就新建）、REQUIRES_NEW（总是新建，原事务挂起）。NESTED 是嵌套事务，靠保存点实现，内层回滚不影响外层。另外四种是 SUPPORTS／NOT_SUPPORTED／MANDATORY／NEVER，分别表示有就用、有就挂起、必须有、必须没有。

@Service
public class OrderService {

    @Transactional(rollbackFor = Exception.class)
    public void createOrder(Order order) {
        orderMapper.insert(order);
        logService.saveLog(order.getId(), "CREATE");
    }
}

@Service
public class LogService {

    // 外层事务回滚不会带走这条日志：REQUIRES_NEW 会挂起外层、单独提交
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveLog(Long orderId, String action) {
        logMapper.insert(new OperLog(orderId, action));
    }
}

接着是四种常见的事务不生效，几乎每次面试都会挑一个问：

  • 自调用：同类内 this.methodB() 不走代理，methodB 上的注解形同虚设。解法是拆到另一个 Bean、注入自身代理，或用 AopContext.currentProxy()。
  • 方法不是 public：默认 proxy 模式下非 public 方法的事务属性被忽略。
  • 异常被吞或类型不对：默认只对 RuntimeException 与 Error 回滚，受检异常不回滚，所以要写 rollbackFor = Exception.class，也别 catch 后不抛。
  • 对象不受容器管理：自己 new 出来的实例没有代理；数据库引擎不支持事务（如 MyISAM）同样失效。

四、Spring Boot：核心注解与自动配置

Boot 用 starter 提供一站式依赖、用内嵌容器做到 java -jar 即可运行、用自动配置替代大量 XML 样板。启动类的核心注解是 @SpringBootApplication，它由三个注解组合而成：@SpringBootConfiguration（内部即 @Configuration）、@EnableAutoConfiguration 与 @ComponentScan。

自动配置可概括为三步：先由 @EnableAutoConfiguration 通过 @Import(AutoConfigurationImportSelector.class) 导入候选配置清单。然后用 @ConditionalOnClass、@ConditionalOnMissingBean 等条件注解筛掉不满足的配置类。选中的配置类再结合 XxxProperties 读取配置，完成装配。

// 只需排除个别自动配置时，不必写全 @EnableAutoConfiguration
@SpringBootApplication(exclude = {DataSourceAutoConfiguration.class})
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

这里有个版本差异必须留意。Boot 2.7 之前，候选清单写在 META-INF/spring.factories。2.7 起推荐用 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports。3.0 起不再支持用 spring.factories 注册自动配置，老答案说“导入 spring.factories”在 3.x 项目上已经过时。

另外，bootstrap 与 application 的区别是前者由父 ApplicationContext 加载、优先级更高，用于远程配置的引导阶段，且属性默认不可被本地覆盖。不过从 Spring Cloud 2020.0 起，bootstrap 默认禁用，改推荐 spring.config.import。YAML 与 properties 的区别是 YAML 层级清晰、支持数组，但不支持 @PropertySource 直接导入。

五、Spring Cloud：注册发现、负载均衡与容错

单体应用膨胀后会出现代码结构混乱、多人开发频繁冲突、改一处就要整体重新编译上线等问题，微服务按业务拆成独立部署的服务，代价则是网络延迟、服务发现、冗余与部署复杂度。Spring Cloud 不是重写的框架，而是把成熟组件按 Spring Boot 风格再封装的集合。Boot 专注单个微服务，Cloud 专注全局治理，Boot 可独立使用而 Cloud 离不开 Boot。核心组件按职责记：

  • 注册与发现：服务启动时注册地址，调用方按服务名查询，无需硬编码 IP。早期主流是 Eureka，Consul、Zookeeper 也可，如今新项目更常用 Nacos。
  • 负载均衡：把请求分发到多个实例，早期用 Ribbon，现由 spring-cloud-loadbalancer 承担，配合 OpenFeign 使用。
  • 声明式调用：OpenFeign 用接口加 Spring MVC 注解描述远程调用，Spring Cloud 2.0 起已取代原 Feign 成为一等公民。
  • 容错断路器：Hystrix 用断路器模式提供熔断、降级、隔离，但已停止新特性维护，新项目多用 Resilience4j 或 Sentinel。
  • 网关：Spring Cloud Gateway 基于 WebFlux 提供路由与过滤，取代阻塞式的 Zuul 1.x。
  • 配置中心与总线：Config／Nacos 做集中配置，Bus 广播刷新事件，Sleuth + Zipkin 做链路追踪。
# 服务提供方：注册到注册中心并暴露端口
spring:
  application:
    name: order-service
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
server:
  port: 8081

与 Dubbo 的对比是经典题：Dubbo 走 RPC 加接口级治理，Spring Cloud 走 HTTP/REST 加应用级治理。Dubbo 默认注册中心是 Zookeeper（Nacos 亦可），基于 Netty 与自定义协议，调用开销更小。Spring Cloud 以 HTTP 通信，跨语言更友好、组件更全。选型看团队与生态，不必只比快慢。

小结

压成一条链：IoC 用工厂加反射把对象交给容器，三级缓存解决字段注入的循环依赖；AOP 用 JDK 或 CGLIB 代理织入横切逻辑，Boot 2.x 起默认 CGLIB。声明式事务就是 AOP 环绕通知，答传播行为先记 REQUIRED 是默认、NESTED 靠保存点，答失效先想自调用与方法非 public。Boot 的核心是 @SpringBootApplication 三合一，自动配置靠条件注解筛选，还要注意 2.7／3.0 的清单文件变更。Cloud 是组件集合：注册发现解决“找得到”，负载均衡解决“分得匀”，断路器解决“坏得住”，网关解决“进得来”。先讲清机制，再补一句版本差异，比背结论更有说服力。
