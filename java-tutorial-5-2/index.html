5.2 常用工具类

Posted on 2024-10-08，6 min read

写业务代码时，占篇幅的往往不是业务逻辑，而是判空、拼接、类型转换、属性拷贝这些重复劳动。一个 Service 里塞进十几个 if (str != null && !"".equals(str.trim()))，代码就变得又长又难读。工具类解决的正是这个问题：把高频、易错的通用操作收敛成一行调用。

本章梳理 Java 项目里最常用的几类工具：

  • 第三方库里有 Apache Commons Lang、Commons Collections、Commons BeanUtils；
  • Spring 提供了 BeanUtils 与 DigestUtils；
  • JDK 自带了 Objects。

本章适合已能写基本分支循环、但还在手写判空和 get/set 拷贝的读者。

一、StringUtils：判断空字符串的正确姿势

Commons Lang3 的 StringUtils 提供了比手写更符合业务语义的方法。isEmpty 在长度为 0 或为 null 时返回 true，不做 trim；isBlank 在 null、空串、只含空白字符时都返回 true，等价于先 trim 再判空。业务里更常用 defaultIfBlank(str, "默认值")，为空时给默认值，比三目运算清晰。此外还有 capitalize、join(数组, 分隔符)、split、trimToNull 等。

注意 Spring 也有一份 org.springframework.util.StringUtils，它没有 isBlank，判断依据是 hasText（非空白）与 hasLength（长度大于 0）。两个同名类常被同时引入，务必看清 import 来源，否则会遇到「方法存在却编译不通过」的困惑。

import org.apache.commons.lang3.StringUtils;

public class StringDemo {
    public static void main(String[] args) {
        System.out.println(StringUtils.isEmpty("  "));   // false，空格不算空
        System.out.println(StringUtils.isBlank("  "));   // true，trim 后为空
        System.out.println(StringUtils.isBlank(null));   // true，null 安全

        String name = StringUtils.defaultIfBlank("  ", "匿名用户");
        System.out.println(name);                        // 匿名用户
    }
}

org.apache.commons.lang3.StringEscapeUtils 已废弃，官方建议迁移到 commons-text 包的 StringEscapeUtils。escapeHtml4 把 <div> 这类内容转成 HTML 实体，方向别记反：escape* 是「原文 → 实体」，unescape* 才是「实体 → 原文」。它只做转义，不能替代参数化查询等安全手段。

二、集合、数组与日期

集合工具最常用 org.apache.commons.collections4.CollectionUtils（Commons Collections 3 的包名是 org.apache.commons.collections，包路径不同，别混用）。它解决了 JDK 集合 API 的两处不顺手：isEmpty 一次处理 null 与空集合；select 按条件筛选并返回新集合，原集合不受影响；transform 对每个元素做转换，类似 Stream 的 map。emptyIfNull(list) 则把 null 换成空集合，避免调用方到处判空。

数组用 ArrayUtils 的 contains、add、subarray；文件与流用 FileUtils.deleteQuietly、forceMkdir、readFileToString 与 IOUtils.copy。不过 Java 7 之后有 try-with-resources，新代码优先用它管理流。

import org.apache.commons.collections4.CollectionUtils;
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

public class CollectionDemo {
    public static void main(String[] args) {
        List<Integer> nums = Arrays.asList(1, 2, 3, 4, 5, 6);
        List<Integer> evens = new ArrayList<>(
                CollectionUtils.select(nums, n -> n % 2 == 0));
        System.out.println(evens);                          // [2, 4, 6]

        List<String> tags = null;
        for (String tag : CollectionUtils.emptyIfNull(tags)) {
            System.out.println(tag);                        // 不抛 NPE，直接不循环
        }
        System.out.println(CollectionUtils.isEmpty(tags));   // true
    }
}

日期时间直接用 java.time（Java 8 起）：LocalDateTime.now()、DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss")。旧的 Date 与 SimpleDateFormat 有两个硬伤：Date 的月份从 0 开始、年份需减 1900，极易算错；SimpleDateFormat 不是线程安全的，作为静态字段共享会在并发下错乱。摘要计算推荐 DigestUtils.md5Hex 与 sha256Hex。注意 DigestUtils.md5(String) 返回的是 16 字节数组 byte[]，不是「16 位字符串」。

三、BeanUtils：属性拷贝与它的两个坑

实体类（Entity/PO）与展示对象（VO/DTO）字段高度重合，逐个 get/set 既啰嗦又容易漏字段。BeanUtils.copyProperties 利用反射与自省按属性名自动拷贝。但有两个同名方法的参数顺序完全相反：Commons 的 copyProperties(目标对象, 源对象) 目标在前，Spring 的 copyProperties(源对象, 目标对象) 源在前。写反了不报错，只会静默地把字段拷成 null，排查非常费时。

另外两个坑：它只拷贝同名同类型的属性，字段名不一致时不会自动映射，需要手动赋值或改用 MapStruct；反射拷贝在批量循环中性能不如直接赋值。若两个类结构差距很大，也可用 JSON 中转（JSON.parseObject(json, UserVO.class)），只要求属性名一致、不要求类型继承关系，代价是多一次序列化开销。

import org.springframework.beans.BeanUtils;

public class CopyDemo {
    public static void main(String[] args) {
        User user = new User();          // 有 name、age 属性及 getter/setter
        user.setName("张三");
        user.setAge(20);

        UserVO vo = new UserVO();        // 字段与 User 同名
        // Spring：源在前、目标在后
        BeanUtils.copyProperties(user, vo);
        System.out.println(vo.getName());   // 张三

        // Commons BeanUtils 顺序恰好相反，切勿照搬：
        // org.apache.commons.beanutils.BeanUtils.copyProperties(vo, user);
    }
}

四、Objects 与密码工具

引入第三方库前，先看看 JDK 已提供了什么。java.util.Objects 从 Java 7 起覆盖了大部分判空与比较场景：Objects.equals(a, b) 在内存地址相同或 a.equals(b) 为 true 时返回 true；Objects.hashCode(o) 在 o 为 null 时返回 0。Objects.toString(o, nullDefault) 在 null 时给默认值；Objects.requireNonNull(obj, "message") 抛出带信息的 NullPointerException，适合做方法入口的参数校验。

密码存储必须用成熟工具类。MD5、SHA 系列都是快速摘要算法，加不加盐都扛不住暴力破解与彩虹表；Spring Security 的 BCryptPasswordEncoder 内置随机盐与可调计算强度，是更合适的选择：

import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import java.util.Objects;

public class PasswordDemo {
    public static void main(String[] args) {
        PasswordEncoder encoder = new BCryptPasswordEncoder();
        String raw = "111111";

        String hash1 = encoder.encode(raw);
        String hash2 = encoder.encode(raw);
        // 每次 encode 都含随机盐，两次结果不同
        System.out.println(Objects.equals(hash1, hash2)); // false
        System.out.println(encoder.matches(raw, hash1));  // true，校验用 matches
    }
}

校验密码只能调用 matches(原文, 密文)，绝不能用「把用户输入重新加密后与数据库字符串做 equals」的方式比对——随机盐会让这种比较永远失败。BCrypt 密文本身含盐与强度信息，长度约 60 字符，建库时字段宽度要给足。

五、ID 生成与集合处理：两个最常被手写的工具

业务代码里有两类逻辑几乎每个项目都会手写一遍：生成唯一 ID、按批切分集合。前者写错会在分布式环境下产生重复主键，后者写错会出现边界越界或漏数据。

分布式 ID：四种方案怎么选

单机项目用数据库自增主键就够了，但一旦分库分表或需要提前生成 ID，就必须换方案。四种常见方案的能力边界如下：

  • UUID：本地生成、无依赖、性能好，但它是 36 字符的随机字符串，无序会导致 B+ 树索引频繁页分裂，且占用空间是 long 的四倍多，只适合做日志追踪号、临时文件名这类不需要当主键的场景。
  • 数据库自增：严格有序、实现简单，但并发写入会成为瓶颈，分库分表后需要额外设置步长，而且 ID 连续可被遍历（竞对可以通过下单号推算业务量）。
  • 号段模式：一次从数据库取一批 ID（如 1000 个）缓存在内存里慢慢发，把数据库写入频率降低千倍；代价是 ID 不连续，服务重启会浪费一段。
  • 雪花算法（Snowflake）：纯内存生成、趋势递增、每秒可产出数百万个，是业务主键最常用的方案，唯一要处理的是时钟回拨。

雪花算法的结构并不复杂：一个 long 的 64 位被切成四段。1 位符号位固定为 0，41 位时间戳（相对自定义起始时间，够用约 69 年），10 位机器标识（5 位数据中心 + 5 位机器，最多 1024 个节点），12 位序列号（同一毫秒内自增，每毫秒最多 4096 个）。这样切是为了让 ID 整体趋势递增——同一毫秒内的 ID 连续，跨毫秒按时间递增。而 MySQL 的 B+ 树索引正好喜欢这种「始终在右侧追加」的写入模式。

public class SnowflakeIdWorker {

    /** 起始时间戳（2024-01-01），一旦上线就不能再改，否则可能生成重复 ID */
    private static final long START_TIMESTAMP = 1704038400000L;

    private static final long WORKER_ID_BITS = 5L;
    private static final long DATACENTER_ID_BITS = 5L;
    private static final long SEQUENCE_BITS = 12L;

    private static final long MAX_WORKER_ID = ~(-1L << WORKER_ID_BITS);              // 31
    private static final long MAX_DATACENTER_ID = ~(-1L << DATACENTER_ID_BITS);      // 31
    private static final long SEQUENCE_MASK = ~(-1L << SEQUENCE_BITS);              // 4095

    private static final long WORKER_ID_SHIFT = SEQUENCE_BITS;                       // 12
    private static final long DATACENTER_ID_SHIFT = SEQUENCE_BITS + WORKER_ID_BITS;  // 17
    private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + WORKER_ID_BITS + DATACENTER_ID_BITS; // 22

    private final long workerId;
    private final long datacenterId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public SnowflakeIdWorker(long workerId, long datacenterId) {
        if (workerId < 0 || workerId > MAX_WORKER_ID) {
            throw new IllegalArgumentException("workerId 必须在 0~" + MAX_WORKER_ID + " 之间");
        }
        if (datacenterId < 0 || datacenterId > MAX_DATACENTER_ID) {
            throw new IllegalArgumentException("datacenterId 必须在 0~" + MAX_DATACENTER_ID + " 之间");
        }
        this.workerId = workerId;
        this.datacenterId = datacenterId;
    }

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();
        // 时钟回拨：NTP 校时、虚拟机迁移都会导致时间倒退
        if (timestamp < lastTimestamp) {
            long offset = lastTimestamp - timestamp;
            if (offset <= 5) {
                // 回拨很小（5ms 内）：自旋等待，追上上次的时间戳即可
                while (timestamp < lastTimestamp) {
                    timestamp = System.currentTimeMillis();
                }
            } else {
                // 回拨较大：宁可抛异常让上层重试，也不能生成重复 ID
                throw new IllegalStateException("检测到时钟回拨 " + offset + "ms，拒绝生成 ID");
            }
        }
        if (timestamp == lastTimestamp) {
            // 同一毫秒：序列号自增；用位与保证溢出后回到 0（同一毫秒最多 4096 个）
            sequence = (sequence + 1) & SEQUENCE_MASK;
            if (sequence == 0) {
                // 本毫秒的 4096 个已用完，等到下一毫秒
                while (timestamp <= lastTimestamp) {
                    timestamp = System.currentTimeMillis();
                }
            }
        } else {
            sequence = 0L;   // 新的毫秒，序列号归零
        }
        lastTimestamp = timestamp;
        return ((timestamp - START_TIMESTAMP) << TIMESTAMP_SHIFT)
                | (datacenterId << DATACENTER_ID_SHIFT)
                | (workerId << WORKER_ID_SHIFT)
                | sequence;
    }
}

使用上有三个必须注意的点。第一，方法必须加锁（上面的 synchronized），因为 lastTimestamp 与 sequence 的组合更新不是原子的。第二，时钟回拨一定要处理：小回拨自旋等待，大回拨直接抛异常并告警——绝不能「容忍」它，否则会生成重复 ID，而重复主键的排查成本极高。第三，机器标识的分配要唯一：可以用 IP 末段、K8s 的 StatefulSet 序号，或启动时向 Redis/Zookeeper 注册领号；同一集群里两台机器用同一个 workerId 是雪花算法最常见的事故原因。如果不想自己实现，可以直接用 MyBatis-Plus 的 IdWorker 或美团的 Leaf、百度的 UidGenerator。

集合处理：切批、判空与树形组装

批量入库、批量调用接口时都需要把大集合切成固定大小的批次。这段代码看着简单，但边界条件容易写错（最后一批不足 batchSize、空集合、batchSize 为 0 导致死循环）。

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class BatchUtils {

    /** 把列表按 batchSize 切分成多批，保证：空集合返回空列表、最后一批可取到剩余元素 */
    public static <T> List<List<T>> partition(List<T> source, int batchSize) {
        if (source == null || source.isEmpty()) {
            return Collections.emptyList();
        }
        if (batchSize <= 0) {
            throw new IllegalArgumentException("batchSize 必须大于 0");
        }
        List<List<T>> result = new ArrayList<>();
        for (int start = 0; start < source.size(); start += batchSize) {
            // 关键：用 min 兜住最后一批，否则 subList 会抛 IndexOutOfBoundsException
            int end = Math.min(start + batchSize, source.size());
            result.add(new ArrayList<>(source.subList(start, end)));
        }
        return result;
    }
}

几个细节值得留意：subList 返回的是原列表的视图而不是副本，所以这里套了一层 new ArrayList<>()——否则对原列表的结构性修改会让子列表失效，抛 ConcurrentModificationException；Guava 有现成的 Lists.partition()，Apache Commons 有 ListUtils.partition()，能用库就不要手写。判空则统一用 CollectionUtils.isEmpty()（Spring）或 list == null || list.isEmpty()，不要用 list.size() == 0。

另一个高频场景是把扁平列表组装成树（菜单、部门、商品分类）。推荐的写法是「一次分组 + 一次递归」：先把所有节点按 parentId 分组成 Map<Long, List<Node>>，再从根节点出发递归挂载子节点。

import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

public class TreeUtils {

    public static class Node {
        private final Long id;
        private final Long parentId;
        private final String name;
        private final List<Node> children = new ArrayList<>();

        public Node(Long id, Long parentId, String name) {
            this.id = id;
            this.parentId = parentId;
            this.name = name;
        }

        public Long getId() {
            return id;
        }

        public Long getParentId() {
            return parentId;
        }

        public List<Node> getChildren() {
            return children;
        }

        @Override
        public String toString() {
            return name + children;
        }
    }

    /** 一次分组 + 一次递归，避免每个节点都去遍历全表（那会退化成 O(n²)） */
    public static List<Node> buildTree(List<Node> all, Long rootParentId) {
        Map<Long, List<Node>> byParent = all.stream()
                .collect(Collectors.groupingBy(Node::getParentId));
        List<Node> roots = byParent.getOrDefault(rootParentId, new ArrayList<>());
        roots.forEach(node -> attach(node, byParent));
        return roots;
    }

    private static void attach(Node parent, Map<Long, List<Node>> byParent) {
        List<Node> children = byParent.getOrDefault(parent.getId(), new ArrayList<>());
        parent.getChildren().addAll(children);
        children.forEach(child -> attach(child, byParent));
    }
}

这段实现把复杂度从「每个节点都扫一遍全表」的 O(n²) 降到 O(n)。生产上还要补两件事。

  • 防环：如果数据里出现 A 的父节点是 B、B 的父节点又是 A 的脏数据，递归会栈溢出；稳妥做法是用 Set 记录访问路径，发现重复就跳过并告警。
  • 限制层级：菜单类数据通常不超过 5 层，超过就说明数据有问题；直接截断比无限递归安全。

六、小结

工具类的价值在于把容易写错的细节封装起来：StringUtils.isBlank 区分了「空串」与「空白串」，CollectionUtils 省掉判空与手写循环，BeanUtils.copyProperties 消灭成片的 get/set，Objects 与 java.time 让你不必依赖第三方库就能写好判空和日期。优先用 JDK 自带 API，其次用社区活跃、维护正常的库，已废弃的类按官方指引迁移；工具类放在 util 包下并命名为 XxxUtils。此外，分布式 ID 与集合切批/建树这两类「人人都会写、人人容易写错」的逻辑也应当收敛到工具类里，把时钟回拨处理、边界条件与防环判断一次写对、处处复用。

最后两点：工具类都是静态方法，天然无状态，不要在其中保存可变成员，否则会引入并发问题；使用第三方库时务必声明依赖并统一版本（commons-lang3、commons-collections4、commons-beanutils），避免同一库多版本导致 NoSuchMethodError。
