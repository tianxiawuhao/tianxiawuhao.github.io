8.7 RabbitMQ 与 RocketMQ

Posted on 2025-01-04，6 min read

上一章的 Kafka 擅长吞吐，但它并不是所有场景的最优解：业务系统里大量消息只有几 KB、要求毫秒级投递、还要能按业务字段灵活路由，这时候 RabbitMQ 和 RocketMQ 往往更顺手。本章解决两个问题：一是把 RabbitMQ 的交换机路由模型和端到端可靠投递讲清楚。二是讲清 RocketMQ 的存储与消费模型，最后给出选型判断。适合已经会写 Java、正在为项目挑一款 MQ 或准备面试的读者。

一、MQ 到底解决什么问题

先用一句话定位：消息队列是介于生产者和消费者之间的异步通信中间件，核心价值是三件事——异步、解耦、削峰。典型例子是下单：写库只用 3 ms，但发短信、加积分、更新搜索索引各要几百毫秒，串行执行用户就要等近 1 秒；改成写库后发一条消息，接口总耗时降到十几毫秒，下游各自慢慢消费。

代价也必须清楚：引入 MQ 后系统可用性下降（MQ 挂了整条链路就断），一致性变复杂（消息可能重复或丢失），运维成本也会上升。因此下面讨论的所有机制，本质上都是在为这三个代价买单。

二、RabbitMQ：以 Broker 为中心的路由模型

2.1 Exchange 才是路由的核心

RabbitMQ 用 Erlang 编写，实现 AMQP 0-9-1 协议。它和 Kafka 最大的架构差异是：生产者不直接把消息写进队列，而是发给 Exchange（交换机）。Exchange 按 Binding（绑定）和 Routing Key 决定投递到哪些 Queue。生产者对队列是无感知的，这正是它能做灵活路由的原因。

  • direct：Routing Key 完全匹配，用于点对点精确投递。
  • fanout：忽略 Routing Key，广播到所有绑定队列。
  • topic：通配符匹配，* 匹配一个单词，# 匹配零个或多个单词。例如绑定 order.*.pay 能收到 order.cn.pay，绑定 order.# 能收到 order.cn.pay.success。
  • headers：按消息头键值匹配，性能不如前三种，实际项目用得很少。

上面四种是协议内置的类型。工程里还会遇到两种“看起来像交换机类型”的扩展：一是延迟交换机 x-delayed-message（由 rabbitmq-delayed-message-exchange 插件提供，声明时再用 x-delayed-type 指定底层类型），它比“DLX + TTL + 死信”那套组合更直观，也不必为每个延迟档位单独建队列；二是 x-consistent-hash 这类社区插件。插件是可选的，需要先在集群安装启用，并确认与 broker 大版本（3.13 / 4.x）兼容。

另外要区分两套“模型”的说法：AMQP 协议层面是 Exchange/Queue/Binding 这套模型。教学资料里常说的“5 种消息模型”（简单、work、订阅、路由、主题）其实是同一套组件的不同用法组合，第 6 种 RPC 已经不属于消息队列范畴。

2.2 写一个最小可运行的生产者与消费者

以官方 amqp-client 5.x 为例，声明一个 direct 交换机并发送持久化消息：

ConnectionFactory factory = new ConnectionFactory();
factory.setHost("192.168.1.10");
factory.setPort(5672);
factory.setUsername("guest");
factory.setPassword("guest");

try (Connection conn = factory.newConnection();
     Channel channel = conn.createChannel()) {

    // 声明交换机与队列，并绑定路由键；服务端已存在时不会重复创建
    channel.exchangeDeclare("order.exchange", BuiltinExchangeType.DIRECT, true);
    channel.queueDeclare("order.pay.queue", true, false, false, null);
    channel.queueBind("order.pay.queue", "order.exchange", "order.pay");

    // MessageProperties.PERSISTENT_TEXT_PLAIN 让消息落盘
    channel.basicPublish("order.exchange", "order.pay",
            MessageProperties.PERSISTENT_TEXT_PLAIN, "order-1001-paid".getBytes(StandardCharsets.UTF_8));
}

消费端的关键是手动确认，而不是自动 ack：

channel.basicQos(1); // 每次只预取 1 条，避免快慢消费者把内存撑爆
channel.basicConsume("order.pay.queue", false, (tag, delivery) -> {
    try {
        handle(new String(delivery.getBody(), StandardCharsets.UTF_8));
        channel.basicAck(delivery.getEnvelope().getDeliveryTag(), false);
    } catch (Exception e) {
        // requeue=false 表示不重回队列，交给死信交换机处理，避免死循环重投
        channel.basicNack(delivery.getEnvelope().getDeliveryTag(), false, false);
    }
}, tag -> { });

这段代码能跑通，但直接搬到生产会踩两个坑。第一，Channel 不是线程安全的：官方明确要求不要在多个线程间共享同一个 Channel，而是“每个线程一个 Channel”（channel-per-thread）。把 Channel 塞进线程池共享，轻则响应错配，重则触发帧交错（frame interleaving）导致的 UNEXPECTED_FRAME 或连接被 broker 直接关闭。第二，预取必须显式设置：basicQos(1) 表示该消费者最多同时持有 1 条未确认消息，配合手动 ack 才能既限流又不丢消息。另外这里的 basicQos(prefetchCount) 已是现行写法——三参数的 basicQos(prefetchSize, prefetchCount, global) 属于旧形式，RabbitMQ 4.x 起不再支持 global=true 的语义（以 4.x release notes 为准），按消费者预取时用单参重载即可。

// 线程池场景：每个工作线程持有自己的 Channel，用完归还、绝不跨线程复用
private static final ThreadLocal<Channel> CHANNEL = ThreadLocal.withInitial(() -> {
    try {
        return conn.createChannel();          // 每线程一个 Channel，天然隔离
    } catch (IOException e) {
        throw new UncheckedIOException(e);
    }
});

// Channel 数量上千时不要无节制地建：需要池化时用连接池/信道池管理，
// 原生 amqp-client 只给 ConnectionFactory，池化通常交给框架（如 Spring AMQP 的
// CachingConnectionFactory 可复用 Channel），或客户端生态里的 ChannelPool 封装；
// 具体 API 以所用客户端版本的官方文档为准。

2.3 可靠投递：三个环节都不能漏

消息丢失可能发生在三处，必须分别设防：

  • 生产者到 Broker：开事务（txSelect/txCommit/txRollback）或更常用的 confirm 模式。信道进入 confirm 模式后每条消息获得唯一递增 ID，Broker 确认后才回调 ack；未确认的消息可重发。
  • Broker 内部：队列声明为 durable、消息标记为持久化，并且刷盘成功后才算落盘；节点故障要靠复制兜底。这里有一条重要的版本演进：早期的镜像队列（classic mirror queue）自 3.9 起弃用，4.0 起已被彻底移除。新部署应改用 Quorum Queue（声明时 x-queue-type: quorum，可用 x-delivery-limit 限制重投次数）或 Streams。非复制的 classic queue 仍受支持，以官方 4.x 文档为准。
  • Broker 到消费者：关闭 autoAck，业务处理成功后再 basicAck；失败走 basicNack 或直接送死信交换机（DLX）配 TTL 实现延迟队列。
// 生产者：confirm 模式 + 异步回调（相比 txSelect 事务，吞吐更好，是现在的推荐做法）
channel.confirmSelect();
channel.addConfirmListener(
        (seq, multiple) -> metrics.markAck(seq),   // broker 已确认
        (seq, multiple) -> retryLater(seq));       // nack，需要重发
channel.basicPublish("order.exchange", "order.pay",
        MessageProperties.PERSISTENT_TEXT_PLAIN, body);

// 队列：带上死信参数，消费失败又不重回队列的消息才会进 DLX，而不是被丢弃
Map<String, Object> args = new HashMap<>();
args.put("x-dead-letter-exchange", "order.dlx");
args.put("x-dead-letter-routing-key", "order.pay.dead");
channel.queueDeclare("order.pay.queue", true, false, false, args);
channel.exchangeDeclare("order.dlx", BuiltinExchangeType.DIRECT, true);

因此“消息不丢”不是某个开关，而是一组配置叠加，代价是吞吐下降。不要给所有消息都开全套持久化与 confirm：日志、埋点这类可容忍丢失的消息用瞬时投递即可。

2.4 顺序性：RabbitMQ 的软肋

RabbitMQ 只保证单队列 + 单消费者范围内有序。一个队列挂多个消费者、或消费者内部用线程池并发处理，顺序立刻被打破。要严格顺序只有两条路：拆多个队列、每队列一个消费者；或者单队列单消费者、内部用内存队列排队再按 key 哈希分发。这也是 RocketMQ、Kafka 在顺序场景更受欢迎的原因。

三、RocketMQ：CommitLog 与 ConsumeQueue 的分层存储

3.1 存储结构决定了它的读写特性

RocketMQ 由阿里巴巴开源，用 Java 编写，最初服务于双十一的交易链路。它把消息存储拆成三层：

  • CommitLog：所有消息按到达顺序追加写在一个文件组里，单文件默认 1 GB。写入完全顺序，是它高吞吐的根基。
  • ConsumeQueue：每个 Topic 的每个队列一个轻量索引，只记录消息在 CommitLog 中的物理偏移、消息大小和 Tag 的哈希值。条目定长 20 字节（8 字节物理偏移 + 4 字节消息长度 + 8 字节 Tag 哈希），5.x 仍是这一结构，以官方文档或实测为准。所以队列本身几乎不占空间。
  • IndexFile：按 Message Key 建立的哈希索引，供控制台按业务键查询，结构类似 HashMap。

这个设计的取舍很鲜明：写是纯顺序写，读却变成随机读。RocketMQ 依赖 page cache 预读、把 IO 调度算法调成 deadline 或 NOOP，来把随机读尽量变成“顺序跳跃”，官方称这类读性能可提升 5 倍以上。同时因为 CommitLog 里保存了全部元信息，ConsumeQueue 即使损坏也能重建。5.x 之后还引入了可选的分层存储（Tiered Storage，把较旧的数据下沉到对象存储），不过 CommitLog + ConsumeQueue 的索引模型没有变，具体能力以所用版本的官方文档为准。

3.2 刷盘、主从与消息重试

刷盘分异步与同步：异步刷盘写进 page cache 就返回，靠后台线程刷盘，性能高但机器掉电可能丢少量消息；同步刷盘要等落盘才返回，可靠性高、RT 变长。主从复制同理，异步复制在 Master 磁盘损坏时可能丢极少量消息，同步双写才能完全避免单点，但明显影响性能，适合资金类业务。

消费失败时，RocketMQ 会把消息投递到 %RETRY%消费组名 这个重试 Topic，按延迟级别逐次退避，默认重试 16 次后进入死信队列。这里要分清两种失败：反序列化失败、数据本身无法处理（如号码已注销）这类“永远失败”的消息应立即人工介入，不要傻等重试；下游数据库或外部服务不可用这类“暂时失败”，则适合延迟重试。

发送消息时用 MessageQueueSelector 把同一业务键的消息固定发到同一队列，就能获得分区有序：

DefaultMQProducer producer = new DefaultMQProducer("order_producer_group");
producer.setNamesrvAddr("192.168.1.10:9876");
producer.start();

Message msg = new Message("OrderTopic", "PAY", ("order-1001-paid").getBytes(StandardCharsets.UTF_8));
// 按订单号哈希选队列：同一订单的消息必定落在同一队列，从而保证分区有序
SendResult result = producer.send(msg, (queues, m, arg) -> {
    int index = Math.abs(arg.hashCode()) % queues.size();
    return queues.get(index);
}, "order-1001");
System.out.println(result.getSendStatus() + " " + result.getMsgId());

顺带说明版本边界：这段用的是 DefaultMQProducer 这套 remoting 客户端，4.x 时代就是经典写法，5.x 依然提供并兼容。RocketMQ 5.x 另外提供了基于 gRPC 与 Proxy 的新一代 Java 客户端（rocketmq-client-java），API 是 builder 风格，消费模型也略有差别。新项目选哪一套建议以官方 5.x 客户端文档为准，不要混用两套客户端。

3.3 事务消息与定时消息

RocketMQ 的事务消息采用两阶段思路：先发送半消息（对消费者不可见），执行本地事务，再根据结果提交或回滚；若 Broker 长时间未收到二次确认，会回查生产者的本地事务状态。它的实现绕开了按 Key 查消息，而是复用第一条消息的 Offset 定位状态，因此半消息数量大时会产生较多脏页，需要关注。

定时消息这块的写法随版本变化最大，值得单独记。4.x 只支持固定延迟级别，不能指定任意时刻。档位表由 broker 的 messageDelayLevel 决定，常见默认是 1s 5s 10s 30s 1m … 1h 2h 共 18 级。所以“能延迟多久”是配置出来的，级别个数也随版本和部署而变——有资料把 5.x 的默认级别数写作 24 级，这里以官方文档与实际 broker 配置为准，不要照抄常量。5.x 新增了真正的定时消息（timer message）：直接给出绝对投递时间即可，秒级精度，官方 Delay Message 文档说明默认可设的最大时间范围为 24 小时（不可调）。固定级别写法仍然保留，两者按场景选。

// 5.x 定时消息：给出绝对投递时间（秒级精度，默认最长 24 小时，以官方为准）
Message timer = new Message("OrderTopic", "PAY", body);
timer.setDeliverTimeMs(System.currentTimeMillis() + 30 * 60 * 1000L);
producer.send(timer);

// 4.x/5.x 通用的固定延迟级别写法：级别个数与档位由 messageDelayLevel 决定
Message delayed = new Message("OrderTopic", "PAY", body);
delayed.setDelayTimeLevel(3);   // 第 3 档，实际延迟多久取决于 broker 配置

至于投递语义，RocketMQ 与 RabbitMQ 一样默认只保证 At Least Once（至少一次）。Exactly Once 在分布式环境下开销极大，工程上的做法是业务侧做幂等去重，例如把消息 ID 或业务唯一键写入数据库唯一索引。

四、怎么选：一张对照表

  • RabbitMQ：单机吞吐约万级，延迟低至微秒—毫秒级，路由最灵活，管理界面完善，社区成熟；Erlang 生态导致二次开发门槛高，堆积大量消息时性能明显下滑。
  • RocketMQ：单机吞吐十万级，支持事务消息、定时消息、按时间回溯消费和亿级堆积，Java 技术栈易改造，有活跃中文社区；生态与多语言客户端不如 Kafka 广泛。
  • Kafka：吞吐最高，适合日志、埋点、流式计算，但队列数过多时性能下降，早期版本不具备事务消息与完善的重试机制。

落地建议是：业务解耦、需要复杂路由或低延迟的场景选 RabbitMQ；交易、订单等需要事务消息、顺序消息和海量堆积的场景选 RocketMQ；日志管道和大数据链路选 Kafka。如果团队同时维护多套成本高，也要接受“用一套 MQ 覆盖所有场景”必然在某些场景上做妥协。

五、小结

本章要点有四个。

  • 路由模型是核心：RabbitMQ 的核心是 Exchange/Binding/Routing Key 的路由模型，direct、fanout、topic 三种类型覆盖了绝大多数业务。
  • 可靠投递要三端设防：必须在生产者、Broker、消费者三端同时设防，confirm 加手动 ack 加持久化是标配，且要按消息重要性分级。
  • 高吞吐源于分层存储：RocketMQ 的高吞吐来自 CommitLog 顺序写加 ConsumeQueue 轻量索引的分层存储，代价是随机读，顺序消息要靠队列选择器加单队列单线程消费。
  • 选型没有银弹：按业务对吞吐、延迟、可靠性和堆积能力的要求取舍。

最后提醒一句：本章不少数字与语义都是版本敏感的。RabbitMQ 4.x 移除了 classic mirror queue 与 global QoS 语义，RocketMQ 的延迟级别数量、定时消息能力在 4.x 与 5.x 之间也有差别。上线前请以所用版本的官方文档和实际 broker 配置为准，不要照搬博客里的常量。
