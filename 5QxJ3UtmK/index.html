手写一个生产者消费者模式

Posted on 2021-09-08，2 min read

一、基于阻塞队列的实现

生产者消费者模式要解决的核心问题是：生产者和消费者通过一个共享缓冲区解耦，生产者不关心谁消费、消费者不关心谁生产，双方只与缓冲区打交道。缓冲区满时生产者等一等，缓冲区空时消费者等一等。JDK 的 java.util.concurrent.BlockingQueue 已经把“线程安全 + 阻塞等待”这两件事封装好了，所以最省事的写法就是直接用它。

先看一个可以直接运行的完整例子：

import lombok.SneakyThrows;

import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

class MyResource {
    // 结束标志：用基本类型 boolean + volatile，避免包装类型带来的空指针与可见性问题
    private volatile boolean FLAG = true;
    private final AtomicInteger atomicInteger = new AtomicInteger();
    private final BlockingQueue<String> blockingQueue;

    public MyResource(BlockingQueue<String> blockingQueue) {
        this.blockingQueue = blockingQueue;
        System.out.println(blockingQueue.getClass().getName());
    }

    @SneakyThrows
    public void myProd() {
        String data;
        while (FLAG) {
            data = String.valueOf(atomicInteger.incrementAndGet());
            // offer 带超时：队列满时最多等 2 秒，仍放不进去就返回 false，不会永久阻塞
            if (blockingQueue.offer(data, 2L, TimeUnit.SECONDS)) {
                System.out.println(Thread.currentThread().getName() + "插入数据" + data + "成功");
            } else {
                System.out.println(Thread.currentThread().getName() + "插入数据" + data + "失败");
            }
            TimeUnit.SECONDS.sleep(1L);
        }
        System.out.println(Thread.currentThread().getName() + "生产停止");
    }

    @SneakyThrows
    public void myConsumer() {
        String result;
        while (FLAG) {
            // poll 带超时：队列空时最多等 2 秒，返回 null 表示“暂时没数据”
            result = blockingQueue.poll(2L, TimeUnit.SECONDS);
            if (null == result) {
                // 连续 2 秒取不到数据，认为生产端已停止，主动收尾而不是空转
                System.out.println(Thread.currentThread().getName() + "超过2秒没有取到值，消费退出");
                return;
            }
            System.out.println(Thread.currentThread().getName() + "消费数据" + result + "成功");
        }
        System.out.println(Thread.currentThread().getName() + "消费停止");
    }

    public void stop() {
        FLAG = false;
    }
}

public class ProdConsumer_BlockQueue {

    @SneakyThrows
    public static void main(String[] args) {
        MyResource myResource = new MyResource(new ArrayBlockingQueue<>(10));

        new Thread(() -> {
            System.out.println(Thread.currentThread().getName() + "生产线程启动");
            myResource.myProd();
        }, "Prod").start();

        new Thread(() -> {
            System.out.println(Thread.currentThread().getName() + "消费线程启动");
            myResource.myConsumer();
        }, "Consumer").start();

        TimeUnit.SECONDS.sleep(5L);
        System.out.println("5秒时间到，通知结束");
        myResource.stop();
    }
}

这段代码里容易踩的坑

  • 结束标志用 Boolean 包装类型：private volatile Boolean FLAG = true; 能跑，但一旦被赋值为 null，while (FLAG) 拆箱就会抛 NullPointerException。结束标志没有“未知”状态，用基本类型 boolean 更合适。

  • 在消费线程里修改结束标志：如果消费者把 FLAG 置为 false，生产者虽然会退出循环，但此时队列里可能还堆着数据，双方对“谁负责收尾”理解不一致。更清晰的做法是：由主线程统一调用 stop()，或者用毒丸对象（见第五节）。

  • 用 StringUtils.isEmpty(result) 判断取值结果：队列里完全可能存入空字符串 ""，这时会被误判成“没取到数据”。BlockingQueue 不允许存入 null，所以判断 null == result 就足够了。

  • 不加超时的阻塞调用：put() 和 take() 会一直等下去。一旦对端线程异常退出，当前线程就永久挂起。带超时的 offer() / poll() 配合 while 循环，能在对端消失后自行退出。

  • 随手吞掉中断：@SneakyThrows 把 InterruptedException 直接抛出去，等于放弃了优雅停机的能力。生产环境里应显式捕获，并遵循“恢复中断状态或退出循环”的约定。

二、wait/notify 的经典写法

如果不用 BlockingQueue，就要自己用 synchronized + wait() / notifyAll() 实现同样的语义。这是最经典、也最容易写错的版本，关键点只有一个：条件判断必须放在 while 循环里，而不是 if。

import java.util.LinkedList;
import java.util.Queue;
import java.util.concurrent.TimeUnit;

public class WaitNotifyDemo {
    private static final int CAPACITY = 10;
    private final Queue<Integer> queue = new LinkedList<>();
    private final Object lock = new Object();
    private int count = 0;
    private volatile boolean running = true;

    /** 生产者 */
    public void produce(int value) throws InterruptedException {
        synchronized (lock) {
            // 必须用 while：被唤醒后条件可能又被别的线程抢占，也可能发生虚假唤醒
            while (queue.size() == CAPACITY) {
                if (!running) {
                    return;
                }
                System.out.println("队列满，" + Thread.currentThread().getName() + " 等待");
                lock.wait();
            }
            queue.offer(value);
            System.out.println(Thread.currentThread().getName() + " 生产 " + value + "，当前 " + queue.size());
            // 唤醒了所有等待者：等待“非空”的消费者需要被叫醒，等待“未满”的其他生产者也会重新判断条件
            lock.notifyAll();
        }
    }

    /** 消费者 */
    public int consume() throws InterruptedException {
        synchronized (lock) {
            while (queue.isEmpty()) {
                if (!running) {
                    return -1; // 结束标志，调用方据此退出
                }
                System.out.println("队列空，" + Thread.currentThread().getName() + " 等待");
                lock.wait();
            }
            int value = queue.poll();
            count++;
            System.out.println(Thread.currentThread().getName() + " 消费 " + value + "，当前 " + queue.size());
            lock.notifyAll();
            return value;
        }
    }

    public void shutdown() {
        synchronized (lock) {
            running = false;
            // 只置标志不唤醒，等待中的线程会一直睡下去
            lock.notifyAll();
        }
    }

    public int getCount() {
        synchronized (lock) {
            return count;
        }
    }

    public static void main(String[] args) throws InterruptedException {
        WaitNotifyDemo demo = new WaitNotifyDemo();
        Thread p = new Thread(() -> {
            for (int i = 1; i <= 100; i++) {
                try {
                    demo.produce(i);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt(); // 恢复中断状态后退出
                    return;
                }
            }
        }, "Producer");

        Thread c = new Thread(() -> {
            try {
                while (demo.consume() != -1) {
                    TimeUnit.MILLISECONDS.sleep(10);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "Consumer");

        p.start();
        c.start();
        p.join();
        TimeUnit.SECONDS.sleep(1);
        demo.shutdown();
        System.out.println("共消费 " + demo.getCount() + " 个元素");
    }
}

为什么必须是 while 而不是 if

  1. 虚假唤醒（spurious wakeup）：JVM 规范允许 wait() 在没有收到任何 notify 的情况下返回。用法只保证“醒来了”，不保证“条件成立了”。

  2. 唤醒后条件可能已被抢占：notifyAll() 唤醒 3 个生产者，第一个抢到锁并把队列塞满了，后两个拿到锁时条件已经不成立，必须重新回到 wait() 等待。

把上面两点合起来就是一句口诀：“等待要在循环里等，唤醒后要重新检查条件”。写成 if 的版本在低并发下往往也能跑通，但属于典型的“看起来能用的 bug”。

另外两点同样重要：

  • wait() / notify() 必须在持有锁的前提下调用，否则抛 IllegalMonitorStateException；
  • shutdown() 里必须 notifyAll()，否则等待中的线程永远醒不过来——这是“程序跑完但不退出”的最常见原因。

三、ReentrantLock + Condition 版本

java.util.concurrent.locks.Condition 把 Object 上唯一的等待队列拆成了多个，可以做到“只唤醒对端”，避免 notifyAll() 把同类线程也一起唤醒后又要重新等待。ArrayBlockingQueue 内部用的正是这个结构。

import java.util.ArrayDeque;
import java.util.Deque;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class LockConditionQueue<T> {
    private final Deque<T> items = new ArrayDeque<>();
    private final int capacity;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();   // 生产者在这里等
    private final Condition notEmpty = lock.newCondition();  // 消费者在这里等

    public LockConditionQueue(int capacity) {
        this.capacity = capacity;
    }

    public void put(T item) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (items.size() == capacity) {
                notFull.await();          // 只挂起生产者
            }
            items.addLast(item);
            notEmpty.signal();            // 只唤醒一个消费者
        } finally {
            lock.unlock();                // 必须在 finally 中释放
        }
    }

    public T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (items.isEmpty()) {
                notEmpty.await();         // 只挂起消费者
            }
            T item = items.pollFirst();
            notFull.signal();
            return item;
        } finally {
            lock.unlock();
        }
    }

    public int size() {
        lock.lock();
        try {
            return items.size();
        } finally {
            lock.unlock();
        }
    }
}

几个要点：

  • await() 必须在 while 循环里，原因和 wait() 完全一样；
  • lock() 之后的代码要用 try/finally 包住并在 finally 中 unlock()，否则异常路径上锁不会释放；
  • 需要响应中断时用 lockInterruptibly() / await()；不关心中断、只希望拿到锁的场合才用 lock()；
  • signal() 只唤醒一个等待者，如果存在多种等待原因（比如带超时的等待和普通等待混用），用 signalAll() 更稳妥。

四、线程池版本

把线程交给线程池管理，配合阻塞队列，就是生产环境里最常见的形态：生产者提交任务，消费者线程池负责执行。

import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

public class PoolDemo {
    public static void main(String[] args) throws InterruptedException {
        BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(20);
        CountDownLatch done = new CountDownLatch(5);

        // 消费者池：2 个线程持续从队列取任务
        ExecutorService consumers = Executors.newFixedThreadPool(2);
        for (int i = 0; i < 2; i++) {
            consumers.submit(() -> {
                try {
                    while (!Thread.currentThread().isInterrupted()) {
                        Integer task = queue.poll(1, TimeUnit.SECONDS);
                        if (task == null) {
                            continue;      // 暂时没任务，继续等；退出由中断控制
                        }
                        try {
                            System.out.println("处理任务 " + task);
                            done.countDown();
                        } catch (RuntimeException e) {
                            System.err.println("任务 " + task + " 失败: " + e.getMessage());
                        }
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt(); // 恢复中断状态，让线程正常退出
                }
            });
        }

        // 生产者
        for (int i = 1; i <= 5; i++) {
            queue.put(i);
        }

        done.await(10, TimeUnit.SECONDS);
        consumers.shutdownNow();          // 先中断，让 poll/put 抛出中断退出
        if (!consumers.awaitTermination(5, TimeUnit.SECONDS)) {
            System.err.println("线程池未在超时时间内结束");
        }
        System.out.println("全部任务处理完毕");
    }
}

线程池版本要注意的边界条件：

  • 消费循环的退出条件：poll 返回 null 只代表“这一秒没数据”，不能据此退出；退出应由中断或毒丸驱动；
  • 关停顺序：先 shutdownNow() 中断消费者，再 awaitTermination 确认结束，最后才认为流程收尾完成；
  • 任务异常不能吃掉线程：消费者线程里必须 catch 住任务抛出的异常，否则一个坏任务就可能让消费线程静默消失；
  • 拒绝策略：ThreadPoolExecutor 默认在队列满且线程数达到上限时抛 RejectedExecutionException，需要根据业务选择 CallerRunsPolicy 等策略或直接反压到生产者。

五、边界条件与终止方式

生产者消费者模式的正确性，八成取决于对下面这些边界情况的处理。

满与空

  • 队列满：put() 阻塞、offer(e, timeout) 超时返回 false、add() 直接抛 IllegalStateException；
  • 队列空：take() 阻塞、poll(timeout) 超时返回 null、remove() 抛 NoSuchElementException；
  • 容量为 0 的 SynchronousQueue 相当于“一手交钱一手交货”，生产者必须等到消费者接手才能返回；
  • 条件判断永远基于“当前状态”而不是“变化次数”，所以用 while 而不是记录第几次唤醒。

中断处理

BlockingQueue、Condition.await()、Thread.sleep() 在收到中断时都会抛 InterruptedException，并清空中断标志。正确的处理套路是：

  1. 能向上抛就向上抛，让调用方决定；
  2. 不能向上抛时，捕获后调用 Thread.currentThread().interrupt() 恢复中断状态，然后退出循环；
  3. 不要在 catch 块里什么都不做——中断是线程间协作停机的唯一手段，吞掉它等于让线程池的 shutdownNow() 失效。

毒丸终止

毒丸（poison pill）适合“任务数量已知、希望消费者把剩余任务做完再退出”的场景：

BlockingQueue<String> queue = new ArrayBlockingQueue<>(10);
final String POISON = "__POISON__";

// 生产者：放完数据后放入毒丸
queue.put("data-1");
queue.put("data-2");
queue.put(POISON);

// 消费者：遇到毒丸就退出，队列里剩余数据已在此之前被处理
String item;
while (!POISON.equals(item = queue.take())) {
    System.out.println("处理 " + item);
}
System.out.println("见到毒丸，退出");

毒丸的注意事项：

  • 毒丸只有一个，多消费者场景要为每个消费者各放一个，否则收不到毒丸的线程会一直等待；
  • 毒丸必须放在所有正常数据之后，否则会提前终止、丢掉后面的数据；
  • 如果队列是有界的且可能已满，放毒丸这一步本身也要考虑阻塞或超时。

六、三种实现怎么选

实现方式优点代价适用场景
BlockingQueue线程安全与阻塞语义开箱即用，代码最短，几乎不会写错无法定制调度策略绝大多数生产 / 消费场景
wait/notify不依赖 JUC，能看清底层同步原语条件判断易写成 if；notifyAll 有惊群；必须自己处理满空与唤醒学习原理、极简共享缓冲
ReentrantLock + Condition可分离等待队列，只唤醒对端；支持公平锁、超时与可中断等待必须 try/finally 释放锁，代码量更大需要精细控制唤醒与公平性的场景

一句话总结：能上 BlockingQueue 就不要手写 wait/notify；只有在需要自定义唤醒策略或想真正理解同步原语时，才自己实现。ArrayBlockingQueue 的源码本身就是“ReentrantLock + 两个 Condition + while 循环防虚假唤醒”的最佳范例。
