安全与加密

Posted on 2026-09-19，6 min read

只要系统走出局域网、连上公网，"安全"就不再是可选项：登录密码明文提交会被抓包看到，接口不签名可以被人随意伪造，令牌里的用户身份可以随手改成管理员。本章要解决的就是这些问题：Java 里怎么做对称与非对称加密、怎么做摘要与数字签名、JWT 令牌为什么能既不查库又防篡改、以及日常开发最常踩的几个安全坑。适合已经会写 Spring Boot 接口、准备上线的读者。

为什么需要加密：先把三件事分清

很多初学者把"安全"等同于"调一个加密 API"，结果做出"用 AES 加密密码后存数据库"这类看似安全、实则错误的设计。先分清三类需求，选型才不会错。

保密性：数据不能被无关的人看懂。这靠加密，分对称与非对称两种。完整性：数据不能被人偷偷改动。这靠摘要（哈希）与数字签名。身份认证：证明"你是谁"。这靠签名、证书、令牌（如 JWT）组合实现。三者互不替代：加密后的报文仍可能被整段替换，摘要也无法隐藏原文。

另一个前置原则是不要把密钥写进代码。硬编码在 .java 或 application.yml 里的密钥，会随 Git 历史、反编译的 jar 一起泄露。生产环境应放在环境变量、配置中心或 KMS 中，并做到可轮换。

对称加密：AES 与它必须写对的参数

对称加密只用一个密钥，加解密双方持有同一个它。优点是快，适合加密大块数据（文件、报文、数据库字段）。Java 标准库自带 AES 实现，不需要额外依赖。

public static byte[] aesEncrypt(byte[] plain, byte[] key) throws Exception {
    // GCM 是带认证的加密模式，能同时保证保密性与完整性
    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    byte[] iv = new byte[12];                      // GCM 推荐 12 字节 IV
    new SecureRandom().nextBytes(iv);              // 必须每次随机，绝不可复用
    cipher.init(Cipher.ENCRYPT_MODE, new SecretKeySpec(key, "AES"),
                new GCMParameterSpec(128, iv));
    byte[] cipherText = cipher.doFinal(plain);
    // 实际传输时要把 IV 和密文一起发给对方，IV 不是秘密
    ByteBuffer buffer = ByteBuffer.allocate(iv.length + cipherText.length);
    return buffer.put(iv).put(cipherText).array();
}

这段代码里有三个"写错就等于没加密"的点。第一，模式不要选 ECB：ECB 对相同明文块产生相同密文块，会泄露数据规律（经典的"ECB 企鹅图"），现在应优先用 GCM，退而求其次用 CBC 并配合 HMAC。第二，IV 必须随机且不可复用：GCM 下重复使用同一密钥 + 同一 IV 会直接导致密钥流复用、可被恢复明文，这是严重漏洞。第三，密钥长度要够：AES-128 是底线，AES-256 更常见；从口令派生密钥请用 PBKDF2、bcrypt 或 scrypt，不要直接 password.getBytes() 当密钥。

非对称加密：RSA 加密与数字签名

非对称加密有一对密钥：公钥可以公开，私钥必须自己保管。它解决的是对称加密"密钥怎么安全地给对方"这个死结，代价是慢——RSA 大约比 AES 慢几个数量级，所以工程上常见的组合是"RSA 传密钥、AES 传数据"（即数字信封）。

只用 JDK 就能完成 RSA 的密钥生成、公钥加密、私钥解密：

// 1. 生成密钥对，2048 位是当前最低推荐值（源笔记中的 1024 位已不安全）
KeyPairGenerator generator = KeyPairGenerator.getInstance("RSA");
generator.initialize(2048);
KeyPair keyPair = generator.generateKeyPair();

// 2. 公钥加密：任何拿到公钥的人都能加密，但只有私钥持有者能解开
Cipher cipher = Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding");
cipher.init(Cipher.ENCRYPT_MODE, keyPair.getPublic());
byte[] cipherText = cipher.doFinal("hello rsa".getBytes(StandardCharsets.UTF_8));

// 3. 私钥解密
cipher.init(Cipher.DECRYPT_MODE, keyPair.getPrivate());
byte[] plain = cipher.doFinal(cipherText);

// 4. 数字签名：发方用私钥签，收方用公钥验（算法必须写全，别用 MD5withRSA）
Signature signer = Signature.getInstance("SHA256withRSA");
signer.initSign(keyPair.getPrivate());
signer.update(plain);
String sign = Base64.getEncoder().encodeToString(signer.sign());

Signature verifier = Signature.getInstance("SHA256withRSA");
verifier.initVerify(keyPair.getPublic());
verifier.update(plain);
boolean ok = verifier.verify(Base64.getDecoder().decode(sign));

数字签名是反向使用密钥：发送方用自己的私钥签名，接收方用发送方的公钥验证（见上面示例的第 4 步）。它不为了保密（签名的原文通常是公开的），而是证明"内容确实来自私钥持有者，且没被改过"。JDK 的 Signature 类已经把"先对内容做摘要、再对摘要做非对称运算"封装好了，你只需要选对算法名。

实际业务里有一类高频场景：前端登录时不想把密码明文发给后端。做法是公钥由后端接口下发，前端用 jsencrypt 库（new JSEncrypt() 后 setPublicKey()、再 encrypt()）加密密码，后端用私钥解密。

但要注意：RSA 加密密码并不能替代 HTTPS。JSEncrypt 默认使用 PKCS#1 v1.5 填充，且 RSA 单块能加密的明文长度有限（2048 位密钥约 245 字节），密文本身也可能被攻击者原样重放。正确组合是 HTTPS 保证链路安全，RSA 只作为密码不明文落地日志的补充手段。

摘要、签名与 JWT：一次登录怎么被记住

前两节解决"数据怎么不被看懂"，本节解决"请求怎么被信任"。传统做法是：客户端带上令牌，资源服务每次都去认证服务校验令牌、换取用户信息，认证服务成为性能瓶颈和单点。

JWT（JSON Web Token，RFC 7519）换了个思路：把用户信息直接放进令牌里，再由资源服务用事先约定的密钥或公钥自行校验，不必每次回源认证服务。JWT 是一个自包含的字符串，由 . 分隔成三部分：

// Header：声明类型与签名算法，Base64Url 编码后是第一部分
{ "alg": "HS256", "typ": "JWT" }

// Payload：标准声明（iss 签发者、exp 过期时间、sub 面向用户、iat 签发时间）加自定义字段
{ "sub": "1234567890", "name": "mrt", "roles": "r01,r02" }

// Signature：对"前两部分的 Base64Url 串"用密钥签名，防止内容被篡改
// HS256 用同一个密钥，RS256 用私钥签名、公钥验签

必须强调：Header 与 Payload 只是 Base64Url 编码，不是加密，任何人都能还原出里面的内容。因此 JWT 里绝不能放密码、手机号、身份证号等敏感信息。

用 jjwt 生成与解析令牌的最小示例如下（注意 jjwt 0.10 起 signWith 要求密钥长度满足算法要求，HS256 至少 256 位即 32 字节）：

// 生成
String secret = "a-32-bytes-long-secret-key-for-hs256";
String token = Jwts.builder()
        .setId("888")
        .setSubject("mrt")
        .setIssuedAt(new Date())
        .setExpiration(new Date(System.currentTimeMillis() + 30 * 60 * 1000L)) // 30 分钟
        .claim("roles", "admin")
        .signWith(SignatureAlgorithm.HS256, secret.getBytes(StandardCharsets.UTF_8))
        .compact();

// 校验并解析：签名不对或已过期都会抛 JwtException
Claims claims = Jwts.parserBuilder()
        .setSigningKey(secret.getBytes(StandardCharsets.UTF_8))
        .build()
        .parseClaimsJws(token)
        .getBody();
System.out.println(claims.getSubject() + " / " + claims.get("roles"));

如果认证服务与资源服务是不同团队、不同部署，建议用 RS256：认证服务持有私钥签发，资源服务只保存公钥验签，这样公钥泄露也不会导致令牌被伪造。JDK 自带的 keytool 可以生成密钥库并导出公钥，交给资源服务配置即可。

常见坑与上线前检查清单

1）算法混淆攻击。最著名的 JWT 漏洞是：攻击者把 Header 里的 alg 改成 none 或把 RS256 改成 HS256，诱使服务端用公钥当 HMAC 密钥验签。防御方式是服务端固定期望的算法，绝不信任 Header 里的 alg。

2）JWT 无法主动失效。令牌一旦签发，在 exp 之前一直有效，服务端删不掉它。所以过期时间要短（分钟级），并配合 Redis 维护黑名单或改用可撤销的 refresh token 机制。

3）哈希算法选错。MD5、SHA-1 已被证明可构造碰撞，签名请用 SHA256withRSA / SHA384withECDSA；口令存储请用 bcrypt、scrypt 或 Argon2（自带盐值与计算代价），而不是"MD5 加盐"。

4）随机数用错。密钥、IV、盐值都必须来自 SecureRandom；用 new Random() 或 Math.random() 生成安全参数是可以被预测的。

5）自造加密算法与自造协议。"把字符串按位异或再倒序"不是加密。用标准算法、标准模式、成熟库，是自己写安全代码最划算的一条原则。

6）把令牌或密钥写进日志与前端存储。JWT 放 localStorage 容易受 XSS 窃取，放 Cookie 则要设置 HttpOnly 与 Secure，并按需选择是否加 SameSite。日志脱敏同样重要。

上线前不妨过一遍这个清单：传输是否强制 HTTPS 且禁用弱协议；密钥是否外置且可轮换；签名算法是否固定、是否用 SHA-256 及以上；令牌有效期是否够短、是否有吊销手段；密码是否用 bcrypt 存储；错误信息是否泄露堆栈与内部路径。

小结

安全与加密的核心是"对症下药"：保密性用对称加密（AES-GCM，注意随机 IV）加密数据、用非对称加密（RSA-2048，注意 OAEP 填充）交换密钥；完整性用 SHA-256 摘要与数字签名，签名用私钥、验签用公钥；身份认证用 JWT 这样的自包含令牌，让资源服务不必每次回源认证服务。三条落地纪律贯穿全篇——密钥不进代码库、算法与参数用标准且现代的配置、永远不信任客户端传来的任何字段。把这几条守住，前面绝大多数"经典漏洞"自然与你无关。
