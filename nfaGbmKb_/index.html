存储系统搭建—Ceph集群

Posted on 2022-12-13，19 min read

一、Ceph基础简介

NFS 简单够用，但缺少多副本与故障域概念，规模一大就容易成为单点，所以生产环境更适合 Ceph 这类分布式存储。本文先在已有的 Kubernetes 集群上用 Rook 部署 Ceph，再补充 cephadm（裸机）方式，以及存储池、PG、CRUSH 的调优要点与常见告警处理。

1、Ceph简介

Ceph 是一个为优秀性能、可靠性与可扩展性而设计的统一分布式文件系统。它在一套 RADOS 集群之上同时提供三种接口：对象存储（RGW，兼容 S3/Swift）、块存储（RBD）和文件系统（CephFS），没有单点，可横向扩展到数千个 OSD。

本文涉及的版本：Rook v1.11.2，对应 Ceph Quincy 17.2.x（默认守护进程镜像 quay.io/ceph/ceph:v17.2.5）。Rook 的每个大版本会绑定一个 Ceph 版本——v1.6/v1.7 对应 Pacific 16.2.x，v1.11 对应 Quincy 17.2.x，v1.13 及以后对应 Reef 18.2.x，升级 Rook 前务必确认目标 Ceph 版本。

2、Ceph集群的安装方式选择

官方安装文档：https://docs.ceph.com/en/quincy/install/（原文链接指向 Pacific，本文按 Quincy 17.2.x 编写；换版本时把 URL 里的代号改成 reef、squid 即可）。

  • Cephadm 安装（官方推荐）：Ceph Octopus（15.2.1）起内置的部署工具，通过 SSH 与容器管理 mon/mgr/osd/mds 等守护进程，适合裸机或虚机环境，命令形如 cephadm bootstrap --mon-ip <ip>、ceph orch apply osd --all-available-devices。
  • Rook 安装（Kubernetes 环境推荐）：把 Ceph 变成 Kubernetes 的原生扩展（CRD + Operator），一步到位。Rook 官网（该链接指向 v1.7 文档，请按所用版本切换，例如 https://rook.io/docs/rook/v1.11/）。
  • 其他方式（手动部署，以及已停止维护的 ceph-deploy）：不推荐。

选型建议：在 Kubernetes 集群内提供存储用 Rook；独立存储集群或已有物理机用 cephadm。两者底层是同一套 Ceph 守护进程与 CRUSH 算法，运维命令（ceph -s、ceph osd tree 等）完全通用。

4、Ceph 集群的角色（mon / mgr / mds / osd / rgw）

Ceph 集群没有中心节点，各守护进程（daemon）地位平等。先把角色分清楚，后面看 ceph -s、排障才不会晕：

角色作用数量与高可用
MON（Monitor）用 Paxos 维护 cluster map（mon map、osd map、pg map、crush map），是集群的共识中心必须 3 或 5 个（奇数）组成 quorum，存活数少于半数时集群不可用
MGR（Manager）采集指标，提供 Dashboard（8443）与 Prometheus exporter（9283），并承载 balancer、pg_autoscaler 等模块至少 1 个 active，建议再配 1 个 standby 实现自动接管
OSD（Object Storage Daemon）真正存放数据：一块磁盘对应一个 OSD，负责读写、复制、恢复与心跳每块盘 1 个，通常至少 3 个，单盘故障靠副本或纠删码恢复
MDS（Metadata Server）只有 CephFS 需要，负责目录树、文件元数据与分布式锁active + standby；块存储与对象存储不需要 MDS
RGW（RADOS Gateway）提供 S3/Swift 兼容的对象存储网关无状态，可多实例加负载均衡

5、数据分布：Pool、PG 与 CRUSH

Ceph 的寻址过程是「对象 → 归置组（PG）→ OSD 集合」，全程由 CRUSH 算法计算，不需要中心元数据服务器：

  • Pool（存储池）：逻辑隔离单元，决定副本数（size）或纠删码参数、故障域（failureDomain）与 PG 数量；RBD、CephFS、RGW 的数据最终都写在自己的池里。
  • PG（Placement Group，归置组）：对象的聚合单位，用 hash(对象名) % pg_num 决定对象属于哪个 PG。PG 是数据分布与恢复的最小粒度，它的多个副本必须落在不同故障域。
  • CRUSH：以 cluster map 为输入，把 PG 映射到一组 OSD，并保证同一 PG 的副本或分片分散在不同 host（或 rack）；扩容时只迁移必要的数据。故障域层级越粗（rack > host > osd）容错能力越强，但对节点数量要求也越高。

下图对比副本池（replicated，size=3）与纠删码池（erasure coded，k=4 m=2）的数据摆放与容量开销：

经验值：故障域选 host 时，3 副本至少需要 3 台主机；PG 总数按「(OSD 总数 × 100) ÷ 副本数」估算并向上取到 2 的幂，让每个 OSD 承载 100 个左右的 PG。Quincy 起可以交给 PG 自动扩缩器（pg_autoscale_mode）管理。

6、cephadm 安装（裸机 / 虚拟机场景）

没有 Kubernetes，或者希望存储与业务集群解耦时，用官方 cephadm 部署。下面以 Quincy 17.2.x、三台节点 node1/node2/node3 为例：

# 1. 在 node1 安装 cephadm 与 ceph 客户端
curl --silent --remote-name --location https://github.com/ceph/ceph/raw/quincy/src/cephadm/cephadm
chmod +x cephadm
./cephadm add-repo --release quincy
./cephadm install

# 2. 引导首个 MON（自动在本机部署 mon + mgr，并生成 /etc/ceph/ceph.conf）
cephadm bootstrap --mon-ip 192.168.40.11 \
  --initial-dashboard-user admin --initial-dashboard-password 'ChangeMe_123'
ceph -s

# 3. 把 node2/node3 纳入集群（需要 root 免密或已分发公钥）
ssh-copy-id -f -i /etc/ceph/ceph.pub root@192.168.40.12
ssh-copy-id -f -i /etc/ceph/ceph.pub root@192.168.40.13
ceph orch host add node2 192.168.40.12
ceph orch host add node3 192.168.40.13
ceph orch host label add node2 osd && ceph orch host label add node3 osd

# 4. 把 MON 补到 3 个、MGR 补到 2 个，避免单点
ceph orch apply mon --placement="3 node1 node2 node3"
ceph orch apply mgr --placement="2 node1 node2"

# 5. 用裸盘创建 OSD（BlueStore；设备必须未分区、未格式化）
ceph orch device ls --wide
ceph orch apply osd --all-available-devices
# 也可以精确指定：ceph orch daemon add osd node2:/dev/vdb

需要 CephFS 时直接创建文件系统，cephadm 会自动建好元数据池、数据池并部署 MDS：

ceph fs volume create myfs
ceph orch apply mds myfs --placement="2 node1 node2"
ceph fs status

查看服务与设备状态：

ceph orch ls        # 各服务的期望数量与实际数量
ceph orch ps        # 各守护进程状态
ceph orch device ls # 可用设备（Available 才算可用）

cephadm 与 Rook 的对应关系：MON/MGR/OSD/MDS 完全相同，区别只在编排层——cephadm 用 ceph orch 命令，Rook 用 CRD 与 Operator。

二、Rook+Ceph的安装

1、查看前提条件——硬件要求

  • Raw devices (no partitions or formatted filesystems)； 原始磁盘，无分区或者格式化
  • Raw partitions (no formatted filesystem)；原始分区，无格式化文件系统

意思是不要用系统盘或已有数据的盘：现代 Ceph 默认的存储后端是 BlueStore，它直接接管整块裸设备（raw device），数据不再经过本地文件系统；只有已被淘汰的 FileStore 才依赖 XFS/ext4 + LVM。Rook/Ceph 会拒绝使用带分区表或文件系统签名的设备，所以要准备未分区、未格式化的干净磁盘（可用 wipefs -a 清除残留签名）。

fdisk -l

如： Disk /dev/vdc: 107.4 GB, 107374182400 bytes, 209715200 sectors

2、升级内核（可选）

升级内核（可选） 如果你将使用 Ceph 共享文件系统（CephFS）来创建卷（Volumes），则 rook 官方建议使用至少 4.17 版本的 Linux 内核。如果你使用的内核版本低于 4.17，则请求的 Persistent Volume Claim（PVC）大小将不会被强制执行。存储配额（Storage quotas）只能在较新的内核上得到强制执行。

版本提示：本节的操作系统是 CentOS 7（内核 3.10），而 CentOS 7 已于 2024-06-30 停止维护，当时 elrepo 的 kernel-ml 是 6.2.9。新环境建议直接用 Rocky/AlmaLinux 9（内核 5.14）或 Ubuntu 22.04（内核 5.15），可以省掉这一步。

在 Kubernetes 中，PVC 用于向存储系统请求指定大小的存储空间。如果请求的 PVC 大小无法得到强制执行，则无法保证所请求的存储空间大小。由于存储配额在较旧的内核上无法得到强制执行，因此在使用 CephFS 创建卷时，如果使用较旧的内核版本，则可能无法正确地管理和分配存储空间。因此，rook 官方建议使用至少 4.17 版本的内核。

在所有k8s节点升级内核，之前忘记考虑这个事情，以后得提前升级好内核再搭建k8s集群，这种情况下升级内核，很难保证不会对k8s集群带来直接影响。注意了，生产环境可不能这么玩，得提前做好规划和准备。

4、修改安装operator.yaml：

把文件中的默认镜像修改为自己的：

## operator 自身镜像（v1.11.2 分支中为 quay.io/rook/ceph:v1.11.2），换成自己的私有仓库
#    image: quay.io/rook/ceph:v1.11.2  ->  image: registry.example.com/rook/ceph:v1.11.2

## Ceph 守护进程镜像（Rook v1.11.2 默认 Quincy；也可在 cluster.yaml 的 spec.cephVersion 指定）
ROOK_CEPH_IMAGE: "registry.example.com/ceph/ceph:v17.2.5"

## CSI 组件镜像：以下为 v1.11.2 的 operator.yaml 默认值，务必以仓库该分支实际值为准
ROOK_CSI_CEPH_IMAGE: "registry.example.com/cephcsi/cephcsi:v3.8.0"
ROOK_CSI_REGISTRAR_IMAGE: "registry.example.com/sig-storage/csi-node-driver-registrar:v2.7.0"
ROOK_CSI_RESIZER_IMAGE: "registry.example.com/sig-storage/csi-resizer:v1.7.0"
ROOK_CSI_PROVISIONER_IMAGE: "registry.example.com/sig-storage/csi-provisioner:v3.4.0"
ROOK_CSI_SNAPSHOTTER_IMAGE: "registry.example.com/sig-storage/csi-snapshotter:v6.2.1"
ROOK_CSI_ATTACHER_IMAGE: "registry.example.com/sig-storage/csi-attacher:v4.2.0"

特别注意：原文这里的 rook/ceph:v1.6.3、cephcsi:v3.3.1、csi-*:v2.x 是 Rook v1.6 时代的标签，与上面 clone 的 v1.11.2 分支并不匹配，混用会出现 CSI 版本不符、csi-provisioner 启动失败等问题。正确做法是：打开所用分支里的 operator.yaml，把镜像仓库前缀替换成自己的私有仓库，标签保持原值不动。

安装operator：

5、修改 cluster.yaml中的集群信息：

因为默认会使用所有节点；如果不想使用所有节点，则需要做以下修改：

  storage: # cluster level storage configuration and selection
  # resources: 生产环境尽量配大一点，测试环境用默认值即可
    useAllNodes: false       # 不使用所有节点
    useAllDevices: false     # 不使用所有设备
    config:
      osdsPerDevice: "1"    # 每块设备创建的 OSD 数量：机械盘/SATA SSD 建议 1，NVMe 可用 2
      # metadataDevice: "nvme0n1"   # 可选：把 BlueStore 的 RocksDB/WAL 单独放到 NVMe
    nodes:
    - name: "k8s-a-node01"   # 必须是 kubectl get nodes 里的节点名，不能写 IP
      devices:
      - name: "vdc"
    - name: "k8s-a-node02"
      devices:
      - name: "vdc"
    - name: "k8s-a-node03"
      devices:
      - name: "vdc"
    # 设备较多时更推荐用过滤器：
    # deviceFilter: "^vd[b-z]$"

要点：nodes[].name 必须与 kubectl get nodes 的节点名完全一致——原文这里写的是 k8s-node1，而验证输出里是 k8s-a-node01，不一致会导致 OSD 准备作业找不到节点；devices[].name 用短名 vdc 或 /dev/vdc 都可以；osdsPerDevice 大于 1 会在同一块盘上创建多个 OSD，只有高性能 NVMe 才建议这么做。Rook 会先在每个节点跑一次 rook-ceph-osd-prepare-<node> Job，成功（Completed）后才创建对应的 OSD Pod。

6、正式安装集群：

kubectl apply -f cluster.yaml

如果 OSD 迟迟不出来，先看准备作业的日志：kubectl -n rook-ceph logs job/rook-ceph-osd-prepare-<node>。常见原因是设备名写错、磁盘上仍有残留文件系统签名（wipefs -a 后重试），或者 cluster.yaml 里的节点名与集群实际节点名不一致。

ceph osd status 里的状态要分三个维度理解，它们经常被混淆：

  • up / down：守护进程维度。up 表示 OSD 进程正常、能与 MON 保持心跳；down 表示进程不可用（宕机、磁盘故障或网络不通）。
  • in / out：CRUSH 维度。in 表示该 OSD 参与数据分布；out 表示已被移出 CRUSH，数据会向其他 OSD 回填，常用于下线维护。
  • exists：该 OSD 已在 osd map 中注册（配置存在），与是否正在运行无关，正常输出常见 exists,up。

组合起来看：down,in 说明进程挂了但 CRUSH 仍认为它该存数据，PG 会降级（degraded）；up,out 通常是维护中的正常状态；exists,down,out 一般是被手动剔除的盘。

8、健康检查与常见告警处理

日常巡检最少看三条命令：ceph -s 看总体健康，ceph health detail 看告警明细，ceph osd df tree 看容量水位。

ceph -s
ceph health detail
ceph osd df tree
ceph osd pool autoscale-status
ceph pg dump_stuck inactive    # 检查卡住的 PG
ceph time-sync-status          # MON 之间的时间偏差

ceph -s 的 health 一行有三种结果：HEALTH_OK、HEALTH_WARN（带告警但可继续服务，需要处理）和 HEALTH_ERR（存在数据丢失风险，必须优先处理）。常见告警与处理办法：

告警含义处理办法
clock skew detectedMON 节点之间时间偏差过大（默认超过 0.05 s 告警），会导致 MON 选举异常甚至失去 quorum所有节点启用时间同步：yum install -y chrony，systemctl enable --now chronyd，再用 chronyc sources -v 与 ceph time-sync-status 复核
osd.X is down / N osds downOSD 进程停止，对应 PG 降级；若同一 PG 的其他副本也异常，PG 会进入 inactive物理机看 systemctl status ceph-osd@X 与 journalctl -u ceph-osd@X；Rook 环境看 kubectl -n rook-ceph get pod -l app=rook-ceph-osd 与 describe pod。确认盘或节点无法恢复后，依次执行 ceph osd out X、ceph osd crush remove osd.X、ceph auth del osd.X、ceph osd rm X
PGs are degraded / inactive / undersized副本数不足或 PG 选不出主，常见于 OSD down、故障域配置不当先 ceph pg dump_stuck inactive 定位，再恢复 OSD 或补节点；用 ceph osd pool get <pool> size 与 min_size 校验池参数
pool(s) have no replicas configured池副本数为 1，没有任何冗余ceph osd pool set <pool> size 3（min_size 保持 2）
OSD(s) near full / full容量超过 nearfull（默认 85%）或 full（默认 95%），full 之后集群会拒绝写入扩容 OSD 或清理数据；紧急时可 ceph osd set-nearfull-ratio 0.9 临时缓解，但不建议长期使用
mons are allowing insecure global_id reclaimMON 仍接受旧客户端的不安全重连，属于兼容性告警确认客户端版本较新后执行 ceph config set mon auth_allow_insecure_global_id_reclaim false
application not enabled on pool池没有声明用途，新版本 Ceph 会告警ceph osd pool application enable <pool> rbd（CephFS 用 cephfs，对象存储用 rgw）

维护窗口内的常见做法：先 ceph osd set noout 再重启 OSD，避免大规模回填；维护结束后 ceph osd unset noout。排查 OSD 是否可安全销毁，用 ceph osd safe-to-destroy <id>。

2、存储池、PG 数与 CRUSH 故障域

Rook 用 CRD 声明存储池，池的 pg_num/pgp_num 由 Operator 按规模自动设置；如果直接用 ceph 命令建池，就要自己算 PG 数量。

# 手工建一个副本池（在 toolbox 里执行）
ceph osd pool create mypool 128 128          # pg_num / pgp_num，先建同值避免二次迁移
ceph osd pool application enable mypool rbd  # 声明用途：rbd / cephfs / rgw
ceph osd pool set mypool size 3              # 副本数
ceph osd pool set mypool min_size 2          # 最小可写副本数，低于它池会停止写入
ceph osd pool set mypool pg_autoscale_mode on

# 调整 PG 数量：先扩 pg_num，确认回填完成后再同步 pgp_num
ceph osd pool set mypool pg_num 256
ceph osd pool set mypool pgp_num 256
ceph osd pool get mypool all
ceph osd pool autoscale-status

PG 总数按「(OSD 总数 × 100) ÷ 副本数」估算，再向上取到 2 的幂：例如 6 个 OSD、3 副本约需 200 个 PG，取 256。PG 太少会导致单个 OSD 压力不均、恢复慢；PG 太多会加重 MON 与内存负担。

CRUSH 故障域决定副本落在哪一层级。默认故障域是 host，即同一个 PG 的副本分散到不同主机；如果机架之间独立供电和联网，建议把故障域提升到 rack，先给主机打上机架标签：

ceph osd crush add-bucket rack1 rack        # 建机架
ceph osd crush add-bucket rack2 rack
ceph osd crush move node1 rack=rack1        # 主机移入机架
ceph osd crush move node2 rack=rack1
ceph osd crush move node3 rack=rack2
ceph osd crush move rack1 root=default
ceph osd crush move rack2 root=default

# 按设备类型或故障域建规则，再让池使用它
ceph osd crush rule create-replicated hdd-rule default host hdd
ceph osd pool set mypool crush_rule hdd-rule
ceph osd crush rule dump                    # 查看规则细节
ceph osd tree                               # 查看当前层级与权重

注意：故障域越粗容错越强，但门槛越高——3 副本加 rack 故障域至少需要 3 个机架，否则 PG 会长期处于 undersized。

3、副本池与纠删码池（replicated vs erasure coded）

副本池实现简单、恢复快，缺点是容量开销大（3 副本只有 1/3 可用率）。纠删码池用 k 个数据块加 m 个校验块，容量开销为 (k+m)/k，适合对象存储、大文件等顺序读写场景。

对比项副本池 replicated纠删码池 erasure coded
容量开销size=3 时为 3×（可用率约 33%）k=4、m=2 时为 1.5×（可用率约 67%）
容错能力可容忍 size-1 个故障域失效可容忍 m 个分片或故障域失效
适用场景RBD 块存储、CephFS 元数据池、小 IO对象存储、大文件、冷数据、顺序读写
恢复代价整副本复制，恢复快需要读 k 块解码，CPU 与网络开销更高

用 Rook CRD 声明纠删码池：

apiVersion: ceph.rook.io/v1
kind: CephBlockPool
metadata:
  name: ec-pool
  namespace: rook-ceph
spec:
  failureDomain: host      # 分片分布在不同主机
  erasureCoded:
    dataChunks: 4          # k
    codingChunks: 2        # m

等价的命令行方式：

ceph osd erasure-code-profile set myprofile k=4 m=2 crush-failure-domain=host
ceph osd erasure-code-profile get myprofile
ceph osd pool create ecpool 64 64 erasure myprofile
ceph osd pool application enable ecpool rgw

# 若要在纠删码池上跑 RBD，需要 BlueStore 并开启覆盖写
ceph osd pool set ecpool allow_ec_overwrites true

注意两点：纠删码池不能存放 RBD 的元数据，RBD 场景通常是「副本池存元数据 + 纠删码池存数据」，生产上更常见的做法是 RBD 直接用副本池；CephFS 的数据池可以用纠删码，但元数据池必须是副本池（Rook 的 CephFilesystem 中 metadataPool 只能使用 replication）。
