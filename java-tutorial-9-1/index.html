9.1 Java 基础面试题精讲

Posted on 2026-09-19，7 min read

Java 基础面试题的特点是题目看着简单，追问之下却层层见底。像“== 和 equals 有什么区别”这种问题，答完区别只是及格；面试官接着会问为什么重写 equals 必须重写 hashCode、Integer 的缓存区间是多少、HashMap 为什么容量取 2 的幂。本章不堆题海，而是把对象契约、集合、异常、泛型与反射这几条主线上的高频考点串成一条逻辑链：先讲清“为什么这么设计”，再给出可以直接讲出来的准确说法，最后点出那些一答错就暴露功底的常见陷阱。适合已经学完 Java 语法、准备面试或做技术复盘的读者。

一、equals 与 hashCode：一条必须同时遵守的契约

equals 默认比较引用地址，hashCode 默认返回由对象地址派生的整数，两者都来自 Object。一旦按“业务值相等”重写 equals，就必须同时重写 hashCode，否则以哈希为基础的集合会立刻出错。《Effective Java》把这条契约写得很明确：如果两个对象 equals 返回 true，它们的 hashCode 必须相等；反过来，hashCode 相等并不要求 equals 为 true，这就是哈希冲突。

违反契约的后果很具体。假设只重写了 equals，两个“相等”的对象会落入哈希表的不同桶，于是 HashSet 里出现两个看起来重复的元素；HashMap 的 get 找不到刚刚 put 进去的键。数据没丢，只是找不到了，这类 bug 排查起来非常耗时。

import java.util.Objects;

public final class User {
    private final String name;
    private final int age;

    public User(String name, int age) {
        this.name = name;
        this.age = age;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) {          // 1. 同一引用，直接返回 true
            return true;
        }
        if (o == null || getClass() != o.getClass()) {  // 2. 类型不同，直接 false
            return false;
        }
        User other = (User) o;
        return age == other.age && Objects.equals(name, other.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(name, age);   // 3. 参与 equals 的字段必须参与 hashCode
    }
}

写这段代码时有四个必须遵守的细节：

  • equals 的参数类型是 Object，写成 User 就变成了重载而不是覆盖，所以必须加 @Override，让编译器帮你发现这类错误；
  • 比较引用类型字段时用 Objects.equals 而不是直接 a.equals(b)，避免空指针；
  • 判断类型优先用 getClass() 而不是 instanceof，否则子类实例可能和父类实例“相等”，破坏对称性；
  • 比较 float、double 要用 Float.compare、Double.compare，不能直接写 ==。

二、重载与覆盖：编译期和运行期的分岔口

追问最多的一句话是“重载和覆盖有什么区别”。准确的回答要落到两个不同的决策时机上。重载（overload）指同一个类中方法名相同、参数列表不同的多个方法。编译器在编译期就根据参数的静态类型选定调用哪一个。覆盖（override）指子类重新实现父类的方法，方法签名相同，JVM 在运行期根据对象的实际类型动态绑定，这就是多态的实现基础。

由此可以解释两个经典现象。其一，私有方法、静态方法、构造方法都不能被覆盖：私有方法对子类不可见，静态方法属于类而不属于对象（只能被隐藏），构造方法根本不参与继承。其二，父类构造方法中调用一个被子类覆盖的方法时，会执行子类的版本，而此时子类字段尚未初始化，读到的是默认值 0 或 null——这正是"构造方法里不要调用可被覆盖的方法"这条规范的原因。

顺便区分三组容易混的词：

  • final 是修饰符，类不可继承、方法不可覆盖、变量不可重新赋值；
  • finally 是异常处理的收尾代码块；
  • finalize 是 Object 上一个已被废弃的回收前回调，Java 9 起标记 @Deprecated、JDK 18 起进一步标记为 forRemoval（Java 21 中仍在，但只剩告警；资源清理应改用 try-with-resources 或 Cleaner）。

三者毫无关系。同理，String 是不可变类且被 final 修饰，StringBuilder 可变但线程不安全，StringBuffer 可变且方法加了同步。顺带纠正一个常被说错的细节：StringBuilder.capacity() 的计量单位是 char 数而不是字节数（一个 ASCII 字符和一个中文都算 1 个 char），它返回的是内部数组容量而非字符个数，字符个数要用 length()。

三、集合：数据结构决定你怎么选

集合类的问题几乎都能回到数据结构上。ArrayList 底层是动态数组，按下标随机访问是 O(1)，中间插入删除要搬移元素，是 O(n)；LinkedList 底层是双向链表，头尾增删是 O(1)，但按下标访问需要遍历，是 O(n)。所以“ArrayList 查询快、LinkedList 增删快”这句话只在增删发生在两端、或已经持有节点位置时才成立。在中间频繁增删时，LinkedList 还要付出遍历定位的代价，因此实际项目中绝大多数场景直接用 ArrayList 就好。

HashMap 底层是数组 + 链表 + 红黑树：先用键的 hashCode 经过扰动函数算出桶下标，冲突的键以链表串在同一个桶里。当单个桶的链表长度达到 8 且数组长度达到 64 时，链表转为红黑树，把最坏查找从 O(n) 降到 O(log n)。扩容阈值是“容量 × 负载因子”，默认负载因子 0.75，每次扩容容量翻倍。容量之所以总是 2 的幂，是因为取模被优化成了位运算 (n - 1) & hash——只有 n 是 2 的幂时，结果才等价于 hash % n。另外要记住：HashMap 允许一个 null 键和多个 null 值，线程不安全；需要并发时用 ConcurrentHashMap，而不是早已被淘汰的 Hashtable。需要保持迭代顺序时用 LinkedHashMap，它维护的是插入顺序，构造时传入 true 才变成访问顺序，而不是“按哈希值排序”；要按键排序则用 TreeMap。

import java.util.HashMap;
import java.util.Map;

Map<String, Integer> count = new HashMap<>();
String[] words = {"java", "map", "java"};

for (String w : words) {
    // getOrDefault 避免手写 null 判断
    count.put(w, count.getOrDefault(w, 0) + 1);
}
System.out.println(count);   // {java=2, map=1}

// 遍历时用 entrySet，避免“先取 key 再 get”的二次查找
for (Map.Entry<String, Integer> e : count.entrySet()) {
    System.out.println(e.getKey() + " -> " + e.getValue());
}

这里还连着一个经典陷阱：== 比较基本类型比的是值，比较引用类型比的是地址，而包装类型之间的 == 是否相等取决于缓存。Integer 会把 -128 到 127 之间的值缓存复用，所以 Integer a = 127; Integer b = 127; 时 a == b 为 true；写成 new Integer(127)，或者值超过 127，结果则为 false。这里补一条版本现状：包装类的构造方法自 JDK 9 起标记 @Deprecated、JDK 16 起标记为 forRemoval，在 Java 17/21 上仍可编译、只发告警（尚未真正移除），新代码应改用 valueOf 或自动装箱。结论很干脆：所有包装类型的值比较一律用 equals。

四、异常：什么时候该抛，什么时候该接

异常体系的根是 Throwable，下面分两支。Error 表示 JVM 层面的严重问题，如 OutOfMemoryError、StackOverflowError，程序不该也无法处理。Exception 才是业务代码关心的部分，又分两类：受检异常（继承 Exception 但不继承 RuntimeException）必须显式 try-catch 或用 throws 声明；非受检异常是 RuntimeException 及其子类，如 NullPointerException、ClassCastException、ArithmeticException，编译器不强制处理。

try-catch-finally 有三个高频追问。catch 和 finally 都可以省略，但两者不能同时省略；catch 中 return 时 finally 依然会执行。如果 finally 里也写了 return，它会覆盖前面的返回值，还会吞掉尚未处理的异常，所以规范里明确禁止在 finally 中写 return。资源释放不要再手写 finally，用 try-with-resources 更短也更安全：它按声明的逆序自动调用 close()，并且把 close() 抛出的异常记为“被抑制的异常”，可用 getSuppressed() 取到，因此，不会覆盖主异常。

import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;

// 资源必须实现 AutoCloseable，退出 try 块时自动关闭
public static String firstLine(String path) throws IOException {
    try (BufferedReader reader = new BufferedReader(new FileReader(path))) {
        return reader.readLine();
    }
}

// 业务异常：继承 RuntimeException，把“哪一步失败”写进消息与 cause
public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(Long orderId, Throwable cause) {
        super("订单不存在：" + orderId, cause);
    }
}

使用异常还有两条经验：不要用异常做流程控制（能判空就不要靠捕获 NullPointerException），捕获后也不要只写一句 e.printStackTrace() 或干脆吞掉异常，至少记录日志并保留原始 cause，否则线上问题会彻底失去线索。自定义异常继承 RuntimeException 可以避免污染每一层的方法签名，让调用方只在真正能处理的地方处理。

五、泛型与反射：类型擦除带来的陷阱

泛型最大的考点是类型擦除：泛型信息只存在于编译期：编译后 List<String> 和 List<Integer> 在字节码里都是 List，类型参数被替换为上界（无界时是 Object），并在必要处插入强制类型转换。由此推出四个结论：不能写 new T[10] 或 new ArrayList<T>()；不能用 instanceof List<String>；静态成员不能使用类的类型参数；重载不能只靠泛型参数区分。同时，List<String> 不是 List<Object> 的子类型，想让方法接收任意类型的列表要用通配符 List<?>，需要写入时用 List<? super T>，只读取时用 List<? extends T>，即 PECS 原则：生产者用 extends，消费者用 super。

反射则是运行期获取类信息的入口，Class.forName、getDeclaredFields、setAccessible(true) 这些 API 让框架得以在不知道具体类的情况下创建对象、注入依赖、解析注解。代价是绕过了编译期检查、性能低于直接调用、对模块化与安全性不友好，所以业务代码里应避免滥用，只在框架、序列化、通用工具等确有必要的地方使用。模块化之后还有一条硬约束：JDK 9 引入 JPMS、JDK 17 起对 JDK 内部 API 的强封装默认开启，此时对 JDK 内部类反射调用 setAccessible(true) 会抛 InaccessibleObjectException，必须显式加 --add-opens（老框架迁到 Java 17 时的常见报错来源）。与之配套，sun.misc.Unsafe 的内存访问方法也在被逐步废弃，新代码应改用 VarHandle 或 MethodHandles。

最后把这一章的高频陷阱收拢成一张“止损清单”：

  • 重写 equals 忘了 hashCode；
  • 用 == 比较包装类型；
  • String.split 丢弃末尾空串导致下标越界（"a,b,,".split(",") 长度为 2，需要保留时应写 split(",", -1)）；
  • Arrays.asList 返回的是固定长度视图，调用 add 会抛 UnsupportedOperationException；
  • 遍历集合时用集合自身的方法删除元素会抛 ConcurrentModificationException，应改用 Iterator.remove() 或 removeIf；
  • long 字面量用小写 l 与数字 1 难分，要用大写 L。

小结：Java 基础面试题考的不是记忆量，而是你是否理解语言设计背后的取舍。对象契约部分抓住“契约”二字——equals 与 hashCode 是一份契约，覆盖与重载的时机划分也是一份契约。集合部分抓住"数据结构决定复杂度"，能顺手讲出哈希、扩容与 2 的幂之间的关系，就比背结论高一个层次。异常部分抓住"该谁处理就谁处理"，受检与非受检的划分、try-with-resources 的自动关闭都是这一原则的体现。泛型与反射部分抓住"编译期与运行期的分工"，类型擦除的每一条限制都能由此推出。把这几条线索讲顺，基础题就不会再是随机抽卡。
