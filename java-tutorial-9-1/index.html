Java 基础面试题精讲

Posted on 2026-09-19，6 min read

面试里问「Java 基础」，考的从来不是背诵能力，而是你有没有被线上问题教育过。本章挑四个最高频、也最容易答错的考点——数据类型与自动装箱、equals 与 hashCode、异常体系、集合与语言细节陷阱——按「为什么错 → 正确的规则 → 可运行示例 → 怎么答」的顺序讲一遍。适合已经会写 Java、准备面试或带新人的开发者；读完后你应该能说出每一条结论背后的原因，而不是只记得结论。

一、基本类型与自动装箱：== 什么时候骗你

Java 有 8 种基本类型：byte(8 位)、short(16)、int(32)、long(64)、float(32)、double(64)、char(16)、boolean。它们都有对应的包装类型，两者之间的赋值由编译器自动装箱、拆箱完成。

坑出在「引用比较」上。== 比较基本类型时比的是值，比较引用类型时比的是是不是同一个对象。而装箱并不是每次都创建新对象：包装类型有缓存池，byte 的全部取值、short 与 int 的 -128~127、char 的 \u0000~\u007F 都会复用缓存对象。所以下面这段代码打印出两个不一样的结果：

Integer a = 127, b = 127;
Integer c = 128, d = 128;
System.out.println(a == b);              // true：都在缓存池内，是同一个对象
System.out.println(c == d);              // false：超出缓存范围，各自 new 出来的
System.out.println(c.equals(d));         // true：equals 比的是值

Long e = 128L, f = 128L;
System.out.println(e.equals(f));         // true
// System.out.println(e == 128);         // 编译错误：Long 与 int 比较会拆箱

注意反过来的坑：Long 与 int 字面量做 == 时，包装类型会拆箱成基本类型再比较，结果是 true；但直接用 == 比较两个包装对象，比的却是地址。结论很简单：只要类型是包装类型，比较值一律用 equals，或者干脆先拆箱成基本类型。更稳妥的写法是让工具类兜住空值，例如 Objects.equals(a, b) 能正确处理 null；Objects 是 JDK 7 引入的。

顺带纠正两个常见说法：其一，「基本类型都存栈上」不准确——局部变量确实在栈上，但对象的字段是跟着对象存在堆里的。其二，new Integer(123) 从 Java 9 起已被标记为废弃，构造器明确不推荐使用，写示例时直接写 Integer.valueOf(123) 或字面量赋值即可。

二、equals 与 hashCode：集合里最贵的一条契约

先记住契约：equals 必须满足自反、对称、传递、一致性，且 x.equals(null) 恒为 false；而 hashCode 的规则是——两个对象 equals 相等，hashCode 就必须相等（反过来不要求）。所以「重写 equals 就必须重写 hashCode」不是风格建议，而是硬性约束：只重写 equals，两个「相等」的对象会算出不同的哈希值，落进哈希表的不同桶里，HashSet 会出现重复元素，HashMap 会 get 不到刚放进去的键。

import java.util.*;

final class Student {
    private final String no;
    private final String name;

    Student(String no, String name) { this.no = no; this.name = name; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                        // 同一引用直接返回，顺便挡住 null
        if (!(o instanceof Student)) return false;         // 类型不对
        Student other = (Student) o;
        return Objects.equals(no, other.no)
            && Objects.equals(name, other.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(no, name);                     // 与 equals 用同一组字段
    }
}

public class EqualsDemo {
    public static void main(String[] args) {
        Set<Student> set = new HashSet<>();
        set.add(new Student("1001", "张三"));
        set.add(new Student("1001", "张三"));
        System.out.println(set.size());                    // 1

        Map<Student, String> map = new HashMap<>();
        map.put(new Student("1001", "张三"), "优秀");
        System.out.println(map.get(new Student("1001", "张三"))); // 优秀
    }
}

两个补充要点。第一，参与 equals 比较的字段和参与 hashCode 计算的字段必须保持一致，不能一个多一个少。第二，别用可变对象当 HashMap 的键：对象放进桶里之后又改了参与哈希计算的字段，它的哈希值变了，再 get 就再也找不回来——上面的 Student 把字段声明为 final，正是为了从源头避免这类问题。

三、异常体系：受检与非受检的分界线

所有能被 throw 的东西都继承自 Throwable，它下面只有两个分支：

  • Error：JVM 层面的严重故障，如 OutOfMemoryError、StackOverflowError，程序无力恢复，不应该捕获；
  • Exception：程序可以处理的问题，又分成受检异常与非受检异常。

分界线是 RuntimeException：NullPointerException、ArrayIndexOutOfBoundsException、ClassCastException、ArithmeticException、IllegalArgumentException 都属于这一类，编译器不强制处理；其余继承 Exception 的（如 IOException、SQLException、InterruptedException）是受检异常，编译器强制你 try-catch 或 throws 声明。这不是折腾人：受检异常在提醒调用方「这里可能失败，你必须给出策略」。

再区分三组容易混的关键字。throw 是抛出一个异常实例，throws 是写在方法签名上声明可能抛出哪些异常；final 修饰不可继承/不可重写的成员，finally 是必然执行的收尾代码块，finalize 是 Object 上的老方法，早已废弃、不要依赖。关于执行顺序有一条固定结论：无论是否发生异常、甚至 catch 里 return 了，finally 都会执行；而如果 finally 里也写了 return，它会覆盖 catch 的返回值——所以别把业务返回值写进 finally。

释放资源推荐用 try-with-resources，而不是手写 finally：只要资源实现了 AutoCloseable，无论正常结束还是抛异常都会自动关闭，而且 close() 自身抛出的异常不会把原始异常吞掉（它被挂到 getSuppressed() 上）。

import java.io.*;

public class TryWithResourcesDemo {
    public static String firstLine(String path) throws IOException {
        try (BufferedReader reader = new BufferedReader(new FileReader(path))) {
            return reader.readLine();
        }                       // 退出代码块时自动 reader.close()
    }

    public static void main(String[] args) {
        try {
            System.out.println(firstLine("no-such-file.txt"));
        } catch (FileNotFoundException e) {        // 先捕具体异常
            System.out.println("文件不存在：" + e.getMessage());
        } catch (IOException e) {
            throw new RuntimeException("读取失败", e); // 包装时带上原始异常
        }
    }
}

四、集合与语言细节里的常见陷阱

集合部分面试常问两件事：选型和返回值语义。ArrayList 底层是数组，随机访问快、中间插入删除要搬元素；LinkedList 底层是双向链表，头尾增删快、随机访问慢；HashMap 用数组加链表（桶内过长时转红黑树）实现，靠 hashCode 定位、靠 equals 判等。集合接口里几个返回值也经常被记反：Collection.remove(Object)、removeAll、containsAll、retainAll 返回的都是 boolean。其中 retainAll 的返回值表示「当前集合是否因此被修改」，不是「是否有交集」，两个集合元素完全相同时也可能返回 false；而 List.remove(int index) 返回的是被删掉的元素，remove(Object o) 返回的是是否删成功，重载时极易选错。

语言细节上，这几条几乎每年都会被问到：

  • 调用 equals 时把常量写在前面，用 "test".equals(object) 而不是 object.equals("test")，可以避免 object 为 null 时的空指针；项目规约通常要求直接使用 Objects.equals。
  • String 被声明为 final 且内部不可变，所以字符串常量可以安全共享；但在循环里用 + 拼接会在每轮产生新对象，应改用 StringBuilder。
  • switch 的 case 忘了写 break 会「贯穿」执行下一个分支；String 可以用来做 switch 的判断值。
  • 重载（overload）在编译期按静态类型决定调用哪个方法，重写（override）在运行期按实际类型动态分派——父类引用指向子类对象时，重载结果可能出乎意料。
  • 用一个很大的包装类型和一个小类型做运算，结果会被提升为更大的类型；byte b = 1; b = b + 1; 编译失败，因为 b + 1 已经是 int，必须强转或写成 b += 1。

五、小结

把这章的四条主线压缩成一张答题卡：包装类型比较值用 equals，== 只在基本类型上表示值相等；重写 equals 必须同时重写 hashCode，且两者使用同一组字段，别用可变对象当 Map 的键；Throwable 分 Error 与 Exception，RuntimeException 是受检与非受检的分界线，资源释放优先用 try-with-resources 并且不要在 finally 里写 return；集合的返回值语义要记准，retainAll 返回的是「是否被修改」。面试时可以按「规则 → 原因 → 反例 → 我会怎么写」四步展开，比只给结论更有说服力。
