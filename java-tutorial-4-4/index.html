Spring IoC 与依赖注入

Posted on 2026-09-19，6 min read

上一章用 Hibernate 打通了持久层，但你可能还没弄清：那些 Service、DAO 对象究竟是谁 new 出来的？为什么在 Controller 里只写一个字段就能直接调用？答案就是本章的主角——IoC 容器与依赖注入（DI）。这一章面向已经会写 Java、准备上手 Spring 或正在被面试追问的读者。把「容器怎么建对象、怎么塞依赖、Bean 从生到死经历什么、有哪几种作用域、循环依赖为什么能解又为什么解不了」这条主线讲透。读完你应当能看懂任意一份 Spring 配置，并说出每一步背后的取舍。

一、容器与 IoC：把 new 的权力交出去

传统写法里，对象自己负责寻找和创建协作者：NoticeService 要发通知，就自己 new 一个 SmsSender。后果是编译期就绑死了实现，想换成邮件通知必须改源码，单元测试也没法替换成假实现。IoC（Inversion of Control，控制反转）把这件事倒过来：对象只声明它需要什么，由容器在运行期把实现塞给它。这个「塞」的动作就是依赖注入。所以 IoC 是思想，DI 是它的实现手段。

Spring 侧的容器有两代接口。BeanFactory 是最底层的 IoC 容器，默认懒加载，只有调用 getBean() 时才创建对象，功能少、启动快。ApplicationContext 是它的超集，启动时就预实例化所有单例 Bean，并额外提供国际化消息、事件发布、资源加载等能力，日常开发基本都用它。两者最常见的实现分别是 DefaultListableBeanFactory，以及 ClassPathXmlApplicationContext、AnnotationConfigApplicationContext。

至于配置元数据，Spring 支持 XML、注解、Java 配置类三种来源。现代项目以 Java 配置（@Configuration + @Bean）和组件扫描（@ComponentScan）为主，XML 在维护老项目时仍会遇到。

二、三种注入方式：构造器、Setter、字段

按注入入口区分，共有三种写法。构造器注入通过构造参数传入依赖，能保证对象一创建就处于可用状态，也便于把依赖声明为 final。Setter 注入在无参构造或静态工厂实例化之后调用 setter，适合可选依赖；字段注入直接标注在成员变量上，代码最短，但绕过了构造器，对象脱离容器就无法工作，测试时只能靠反射赋值。

@Configuration
@ComponentScan("com.example.notice")
public class AppConfig {
}

@Component
public class SmsSender {

    public void send(String to, String text) {
        System.out.println("sms -> " + to + ": " + text);
    }
}

@Component
public class NoticeService {

    private final SmsSender smsSender;   // 强制依赖：不给就创建不了

    public NoticeService(SmsSender smsSender) {   // Spring 4.3 起单构造器可省略 @Autowired
        this.smsSender = smsSender;
    }

    public void notice(String user) {
        smsSender.send(user, "your order has been shipped");
    }
}

当容器里存在多个同类型候选时，构造器参数上的 @Autowired 就会抛 NoUniqueBeanDefinitionException。此时用 @Qualifier("smsSender") 指明 Bean 名，或在候选 Bean 上加 @Primary 指定首选。@Resource 是 JSR-250 的注解，默认按名称装配，名字找不到时才退回按类型，这是它与 @Autowired（默认按类型）最本质的区别。

该怎么选？Spring 官方现在的建议是：强制依赖用构造器，可选依赖用 Setter。构造器注入的额外好处是依赖不可变、字段能加 final、对象不可能处于「半装配」状态；写单元测试时直接 new 出来传入假的 SmsSender 就能跑，完全不需要容器。代价是多参数构造器会让类显得臃肿，而且它参与不了后面要讲的循环依赖三级缓存（见第五节）。字段注入写起来最省事，但只适合临时脚本或不关心可测性的场景。

XML 时代对应的是 <constructor-arg> 与 <property>。看一段老项目里很典型的 Setter 注入：

<bean id="noticeService" class="com.example.notice.NoticeService">
    <property name="sender" ref="smsSender"/>
    <property name="retryTimes" value="3"/>
</bean>

<bean id="smsSender" class="com.example.notice.SmsSender"/>

值得注意的是，属性上的 @Autowired 与 @Resource 由 AutowiredAnnotationBeanPostProcessor 和 CommonAnnotationBeanPostProcessor 处理，二者随 AnnotationConfigApplicationContext 自动注册。如果用的是纯 XML 容器，则必须加 <context:annotation-config/> 或 <context:component-scan/>，否则注解形同注释。

三、Bean 的生命周期：从实例化到销毁

把容器启动一个单例 Bean 的过程拆开，顺序大致如下。容器先读取 Bean 定义，再调用 BeanFactoryPostProcessor（Bean 定义的后处理器，可在此修改元数据），其中 ConfigurationClassPostProcessor 负责解析配置类、完成组件扫描与条件判断。随后是实例化 Bean、属性注入，以及各类 Aware 回调（BeanNameAware.setBeanName、BeanFactoryAware.setBeanFactory、ApplicationContextAware.setApplicationContext）。接着依次执行 BeanPostProcessor.postProcessBeforeInitialization、@PostConstruct、InitializingBean.afterPropertiesSet()、init-method，再执行 postProcessAfterInitialization（AOP 代理通常在这一步生成），Bean 至此就绪。容器关闭时，@PreDestroy、DisposableBean.destroy()、destroy-method 依次执行。

@Component
public class CacheWarmer implements InitializingBean, DisposableBean {

    private final Map<String, String> cache = new HashMap<>();

    @PostConstruct
    public void loadHotData() {
        cache.put("hot", "ready");            // 依赖注入已完成，可以安全使用字段
    }

    @Override
    public void afterPropertiesSet() {
        System.out.println("@PostConstruct 先执行，本方法后执行");
    }

    @Override
    public void destroy() {
        cache.clear();
    }
}

这里有三个容易记错的点。第一，@PostConstruct 属于 JSR-250，在 Spring 6 / Spring Boot 3 中随 jakarta.annotation-api 迁移到 jakarta.annotation 包，不再是 javax.annotation，升级时导入错包是真实存在的坑。第二，同一个 Bean 上三种初始化方式同时存在时，执行顺序固定为注解 → InitializingBean → 配置里的 init-method，销毁顺序同理。第三，BeanPostProcessor 会作用于容器内几乎所有 Bean，是「容器级」扩展点；而 Aware、InitializingBean 只作用于实现了它们的那个 Bean，是「Bean 级」扩展点。把这两类混为一谈是常见的表述错误。另外要注意，prototype 作用域的 Bean，容器只负责创建和装配，销毁阶段不再回调。

四、作用域：单例之外的选择

Spring 提供六种作用域：singleton（默认，每个容器一个实例）、prototype（每次获取都新建）、request、session、application，以及用于 WebSocket 会话的 websocket。后四种依赖 Web 环境，在普通容器里注册会直接抛异常。历史上还有一个 global-session，用于 Portlet 应用的全局会话，Spring 5 已经移除，现在再提它属于过时知识。

第二个高频误区是：单例 Bean 不等于线程安全。容器只保证「每个容器一个实例」，并不给这个实例加锁。只要 Bean 里存在可变的成员状态，多线程并发写就会出现数据错乱。正确做法是让单例 Bean 无状态——依赖字段全部 final 且不可变，需要变化的数据放进方法局部变量、ThreadLocal 或交给数据库；确实有状态时再评估是否改成 prototype，并同步评估频繁创建对象的开销。

还有一种真实场景：单例 Bean 里注入 prototype Bean，结果拿到的永远是同一个实例，原因是一次性注入只发生一次。此时可以让单例实现 ApplicationContextAware，每次调用时 getBean()；更优雅的做法是用 @Lookup 标注一个抽象方法，由 CGLIB 在运行期覆盖它，每次调用都向容器要一个新实例。

五、常见坑：循环依赖以及容器误用

循环依赖指 A 依赖 B、B 又依赖 A。Spring 用三级缓存解决其中的 Setter / 字段注入场景：一级缓存 singletonObjects 存成品 Bean；二级缓存 earlySingletonObjects 存属性尚未填充完的早期引用；三级缓存 singletonFactories 存返回早期引用的 ObjectFactory。A 实例化后先把工厂放进三级缓存，再填充属性时发现需要 B；B 创建时从三级缓存拿到 A 的早期引用完成注入。B 顺利走完流程后，A 再补全属性。需要强调的是，三级缓存的价值不只是「提前暴露引用」，更在于通过工厂让循环依赖处能拿到 AOP 代理对象，避免注入到半成品。

但构造器注入的循环依赖无解：B 的构造需要 A，而 A 的构造也需要 B，两者都卡在实例化之前，容器只能抛 BeanCurrentlyInCreationException。Spring Boot 2.6 起默认禁止循环引用（spring.main.allow-circular-references=false），把它从「能跑但危险」变成「启动即失败」。正确姿势是重构：抽出第三个 Bean 承接共同职责，或对其中一处依赖加 @Lazy，让注入的是一个延迟解析的代理，从而打断构造期的死锁。

最后是两个工程习惯。其一，不要让业务代码直接 new ClassPathXmlApplicationContext() 或到处 getBean()：前者会创建出容器之外的野容器，后者把依赖关系藏进字符串，等于退回手动查找。在 Web 项目里，应让 ContextLoaderListener 或 Spring Boot 的引导类统一启动容器。其二，@Component 家族只负责把类注册为 Bean，@Bean 方法则用于装配第三方类，两者不要为了「看起来更 Spring」而滥用。

小结

本章的主线其实是一条链：容器负责创建与装配（IoC），装配的方式是注入（构造器 / Setter / 字段）。装配完成后 Bean 走过生命周期回调，期间受作用域约束，而循环依赖是在这条链上被三级缓存兜住的特殊情形。记住三句话：构造器注入强制依赖、Setter 注入可选依赖；单例不等于线程安全；循环依赖是设计信号而非配置问题。下一章进入 AOP，看 Spring 怎样用动态代理把日志、事务这些横切逻辑从业务代码里剥离出去。
