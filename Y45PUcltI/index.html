openfeign-ribbon核心源码剖析

Posted on 2022-07-05，20 min read

一、总结前置：

1 ribbon,feign,openfeign三者的对比

我们现在工作中几乎都是直接使用 OpenFeign，而我们很有必要了解一下，ribbon、feign、openfeign三者之间的关系！

  • ribbon：ribbon是netflix开源的客户端负载均衡组件，可以调用注册中心获取服务列表，并通过负载均衡算法挑选一台Server；
  • feign：feign也是netflix开源的，是对ribbon的一层封装，通过接口的方式使用，更加优雅，不需要每次都去写restTemplate，只需要定义一个接口来使用；但是Feign不支持springmvc的注解；
  • openfeign：是对feign的进一步封装，使其能够支持springmvc注解，如@GetMapping等，使用起来更加方便和优雅！

2 工作中都是如何使用openfeign

// 想要使用 OpenFeign，必须在启动类上增加 @EnableFeignClients 注解，否则 @FeignClient 接口不会被扫描、启动时注入失败
@FeignClient("feign-provider")
public interface OrderService {
 
    @GetMapping("/order/get/{id}")
    public String getById(@PathVariable("id") String id);
}

3 openfeign与ribbon如何分工

  • openfeign通过动态代理的方式，对feignclient注解修饰的类进行动态代理，拼接成临时URL：http://feign-provider/order/get/100，交给ribbon
  • ribbon通过自己的拦截器，截取出serviceName在服务注册表中找到对应的serverList，并通过负载均衡策略挑选一台Server，拼接成最终的URL：http://10.206.73.156:1111/order/get/100，交还给feign；
  • 最后，feign通过自己封装的Client对目标地址发起调用，并获得返回结果；（Client是对原生 java.net 中的URL类的封装，实现远程调用）

4 版本演进：Ribbon 进入维护模式，Spring Cloud LoadBalancer 接棒

本文分析的源码来自 Spring Cloud Hoxton / 2020.0 之前的版本，也就是 OpenFeign 仍然集成 Netflix Ribbon 的时期。这套代码在今天的项目里已经不再生效，原因如下：

  • Netflix 早在 2018 年就宣布 Ribbon 进入维护模式（maintenance mode），只做必要的 bug 修复，不再新增功能。
  • Spring Cloud 2020.0.0（Ilford，对应 Spring Boot 2.4）正式把 Ribbon 标记为废弃，改用 spring-cloud-starter-loadbalancer 提供的 Spring Cloud LoadBalancer；该版本中 Ribbon 需要显式打开才能使用。
  • Spring Cloud 2022.0.0（Kilburn，对应 Spring Boot 3.0）移除了 Netflix Ribbon 相关模块以及 OpenFeign 中针对 Ribbon 的适配（LoadBalancerFeignClient、SpringClientFactory 等），只保留 Spring Cloud LoadBalancer 的实现。

对应的替换关系如下表所示。需要注意的是，这并不影响本文的价值：Ribbon 的 ILoadBalancer → IRule → ServerList 三段式设计，正是 Spring Cloud LoadBalancer 中 LoadBalancerClient → ReactorServiceInstanceLoadBalancer → ServiceInstanceListSupplier 的设计蓝本，看懂一套就很容易迁移到另一套。

能力Ribbon（Hoxton 及以前）Spring Cloud LoadBalancer（2020.0+）
入口注解@EnableFeignClients / @RibbonClients@EnableFeignClients / @LoadBalancerClients
负载均衡器ILoadBalancer（ZoneAwareLoadBalancer）ReactorLoadBalancer / ReactorServiceInstanceLoadBalancer（RoundRobinLoadBalancer）
负载均衡策略IRule（默认 ZoneAvoidanceRule）ReactorServiceInstanceLoadBalancer 实现类
服务实例列表ServerList（NacosServerList）+ ServerListUpdaterServiceInstanceListSupplier（DiscoveryClientServiceInstanceListSupplier）
Feign 侧 ClientLoadBalancerFeignClientFeignBlockingLoadBalancerClient
配置前缀ribbon.* / feign.client.config.*spring.cloud.loadbalancer.* / spring.cloud.openfeign.client.config.*

因此在 Spring Boot 3.x + Spring Cloud 2022.0+ 的项目中读本文时，请把文中的 Ribbon 组件按上表“翻译”一遍；本文后半部分关于重试与超时的结论，也同步标注了新旧两套配置项。

protected <T> T loadBalance(Feign.Builder builder, FeignContext context,
      HardCodedTarget<T> target) {
   // 从容器中获取一个类型为Client的bean，那么IOC容器中肯定有一个这样的Bean
   Client client = getOptional(context, Client.class);
   if (client != null) {
      builder.client(client);
      Targeter targeter = get(context, Targeter.class);
      return targeter.target(this, builder, context, target);
   }
 
   // 如果找不到类型为Client的Bean就是有问题的啦！
   throw new IllegalStateException(
         "No Feign Client for loadBalancing defined. Did you forget to include spring-cloud-starter-netflix-ribbon?");
}

到这里就非常清晰了。这两个自动配置类“谁能生效”，由三处条件共同决定，值得单独说明：

  • @ConditionalOnClass：类路径上有没有 Ribbon 的 ILoadBalancer、有没有 Spring Cloud LoadBalancer 的 BlockingLoadBalancerClient。
  • @ConditionalOnProperty(value = "spring.cloud.loadbalancer.ribbon.enabled", matchIfMissing = true)：这是 Ribbon 版本的“总开关”，matchIfMissing = true 表示不配置时也按开启处理；把它显式设为 false，FeignRibbonClientAutoConfiguration 就整体失效，容器中只剩下 FeignBlockingLoadBalancerClient。
  • @ConditionalOnMissingBean：谁先注册谁生效，后注册的因为容器中已经有 Client 类型的 Bean 而跳过，这就是“只会有一个成功”的原因。
  • @AutoConfigureBefore / @AutoConfigureAfter：强制装载顺序（FeignRibbonClientAutoConfiguration 先于 FeignAutoConfiguration，FeignLoadBalancerAutoConfiguration 又在它之后），而顺序决定了哪个 @ConditionalOnMissingBean 先拿到注册权。

两个配置类都被约束在 FeignAutoConfiguration 之前装配，说明“负载均衡用的 Client”必须比 Feign 自身的默认装配更早确定；而 @ConditionalOnMissingBean 又允许我们通过自定义 Client Bean 直接接管，这正是后来接入 OkHttp、Apache HttpClient 或自定义拦截逻辑的通用做法。

  • 通过spring.factories注入了两个配置类，并通过 @AutoConfigureBefore 和 @AutoConfigureAfter强制了两个配置类的装载顺序！
  • 这两个配置类各import 了 另一个配置类：DefaultFeignLoadBalancedConfiguration（注入：LoadBalancerFeignClient） 和 DefaultFeignLoadBalancerConfiguration（注入：FeignBlockingLoadBalancerClient），但是由于@ConditionalOnMissingBean注解，只有一个前面那个会注入成功！
  • 所以，结论就是：IOC容器中的“Client”类型的 Bean 为 “LoadBalancerFeignClient”

所以，最终的结论就是：Openfeign通过的动态代理，为每个“@FeignClient”注解修饰的接口生成一个类型为 “LoadBalancerFeignClient”的代理类。

3 RibbonClientConfiguration又是如何注入我们需要的ZoneAwareLoadBalancer的

@Configuration(proxyBeanMethods = false)
@EnableConfigurationProperties
// Order is important here, last should be the default, first should be optional
// see
// https://github.com/spring-cloud/spring-cloud-netflix/issues/2086#issuecomment-316281653
@Import({ HttpClientConfiguration.class, OkHttpRibbonConfiguration.class,
      RestClientRibbonConfiguration.class, HttpClientRibbonConfiguration.class })
public class RibbonClientConfiguration {
 
    @Bean
    @ConditionalOnMissingBean
    public ILoadBalancer ribbonLoadBalancer(IClientConfig config,
          ServerList<Server> serverList, ServerListFilter<Server> serverListFilter,
          IRule rule, IPing ping, ServerListUpdater serverListUpdater) {
       if (this.propertiesFactory.isSet(ILoadBalancer.class, name)) {
          return this.propertiesFactory.get(ILoadBalancer.class, config, name);
       }
        
       // 默认注入的类正是ZoneAwareLoadBalancer
       return new ZoneAwareLoadBalancer<>(config, rule, ping, serverList,
             serverListFilter, serverListUpdater);
    }
 
}

补充一点：ribbonLoadBalancer() 上标注了 @ConditionalOnMissingBean，而类上 @Import 的四个配置类按“最后一个优先级最低、第一个优先级最高”排列，因此默认实现的优先级是：@LoadBalancerClients 的 defaultConfiguration > @LoadBalancerClient 的 configuration > RibbonClientConfiguration（即 ZoneAwareLoadBalancer）。只有前面几处都没有定义 ILoadBalancer 时，才会落到本文默认的 ZoneAwareLoadBalancer。

所以，这就解释了，为什么在后面的 ILoadBalancer lb = getLoadBalancer(); 获得到的就是ZoneAwareLoadBalancer！

同时，这个类是在动态代理被执行execute()的时候被调起的，所以Ribbon也是在被使用时才从Nacos获取注册表的，并不是在容器启动时！

// com.netflix.loadbalancer.DynamicServerListLoadBalancer#updateAllServerList
protected void updateAllServerList(List<T> ls) {
    // other threads might be doing this - in which case, we pass
    if (serverListUpdateInProgress.compareAndSet(false, true)) {
        try {
            for (T s : ls) {
                s.setAlive(true); // set so that clients can start using these
                                  // servers right away instead
                                  // of having to wait out the ping cycle.
            }
            setServersList(ls);
            super.forceQuickPing();
        } finally {
            serverListUpdateInProgress.set(false);
        }
    }
}

public void setServersList(List lsrv) {
    super.setServersList(lsrv);  // 核心
    List<T> serverList = (List<T>) lsrv;
    Map<String, List<Server>> serversInZones = new HashMap<String, List<Server>>();
    for (Server server : serverList) {
        // make sure ServerStats is created to avoid creating them on hot
        // path
        getLoadBalancerStats().getSingleServerStat(server);
        String zone = server.getZone();
        if (zone != null) {
            zone = zone.toLowerCase();
            List<Server> servers = serversInZones.get(zone);
            if (servers == null) {
                servers = new ArrayList<Server>();
                serversInZones.put(zone, servers);
            }
            servers.add(server);
        }
    }
    setServerListForZones(serversInZones);
}

4 Feign的默认重试器的核心代码（默认是不开启的）

public static class Default implements Retryer {
    private final int maxAttempts;
    private final long period;
    private final long maxPeriod;
    int attempt;
    long sleptForMillis;
 
    public Default() {
        // 默认的重试间隔时间100ms，最大间隔时间为1s，最大重试次数为5次
        this(100L, TimeUnit.SECONDS.toMillis(1L), 5);
    }
     
    // 默认下次重试间隔时间 100 * 1.5^(尝试轮次-1) 次方
    // 第一次尝试：100 * 1.5(2 -1) = 150ms; 以此类推
    long nextMaxInterval() {
        long interval = (long)((double)this.period * Math.pow(1.5D, (double)(this.attempt - 1)));
        return interval > this.maxPeriod ? this.maxPeriod : interval;
    }
}

5 Ribbon和Feign的重试器的源码就不过度追溯了，直接上结论

  • Ribbon 的重试机制默认是开启的：ribbon.MaxAutoRetries 默认 0（同一实例不重试），ribbon.MaxAutoRetriesNextServer 默认 1（换一个实例再试一次），因此在只有一个服务实例时表现为“调用两次”。
  • Feign 的 Retryer 默认是关闭的，即 Retryer.NEVER_RETRY；而且它只对 IO 异常与 RetryableException 生效，业务异常不会触发重试。
  • Feign 如果想开启默认重试器，直接在 Spring 容器中注入 Retryer.Default 即可（new Retryer.Default() 的 maxAttempts 默认为 5）。
  • 两套重试会叠加：Ribbon 的重试发生在“换实例再调”这一层，Feign 的重试发生在“整个方法调用”这一层；两者同时开启时请求次数是相乘的，排查重复调用时要先分清是哪一层在重发。

8 超时配置与重试次数的关系

做重试实验时有一个很容易踩的坑：Feign 的默认读超时是 60 秒，而上面服务提供者 sleep 100 秒，如果读超时小于服务端处理时间，就不会看到“重试 10 次”的结果，而是直接抛 SocketTimeoutException，或者被 Ribbon 的 ribbon.ReadTimeout（默认 5 秒）、ribbon.ConnectTimeout（默认 2 秒）提前截断。所以调大超时是复现重试现象的前提。

# 旧版本（Spring Cloud Hoxton 及以前，由 Ribbon 承载负载均衡）
feign:
  client:
    config:
      default:
        connectTimeout: 10000
        readTimeout: 120000     # 必须大于服务端的处理时间
ribbon:
  ConnectTimeout: 10000
  ReadTimeout: 120000

# 新版本（Spring Cloud 2020.0+，由 Spring Cloud LoadBalancer 承载负载均衡）
spring:
  cloud:
    openfeign:
      client:
        config:
          default:
            connectTimeout: 10000
            readTimeout: 120000
    loadbalancer:
      retry:
        enabled: true           # 需要额外引入 spring-retry 依赖

所以，项目里排查“一次请求被调用多次”，要同时看 Feign 的 Retryer、Ribbon/Spring Cloud LoadBalancer 的重试以及服务端幂等性三方；这也是 Ribbon 时代 ribbon.OkToRetryOnAllOperations=false（默认只对 GET 重试）被反复强调的原因。

6 修改Ribbon的默认重试机制

# Ribbon 配置
ribbon:
  # 单节点最大重试次数(不包含默认调用的1次)，达到最大值时，切换到下一个实例
  MaxAutoRetries: 0  # 0 相当于关闭ribbon重试
   
  # 更换下一个重试节点的最大次数，可以设置为服务提供者副本数（副本数 = 总机器数 - 1），也是就每个副本都查询一次
  MaxAutoRetriesNextServer: 0
   
  # 是否对所有请求进行重试，默认 false，则只会对GET请求进行重试，建议配置为false，不然添加数据接口，会造成多条重复，也就是幂等性问题。
  OkToRetryOnAllOperations: false

7 自定义Feign重试机制（直接给 Retryer.Default 构造方法传参即可）
