设计模式：行为型

Posted on 2026-09-19，7 min read

前面几章讨论的多半是“怎么把代码组织成类”：继承、接口、抽象类。可当业务开始变复杂，真正难的不是写出一个类，而是让一组会变的行为在运行期自由替换、互相通知、按顺序传递。这正是行为型设计模式要解决的问题。本章挑出最常用的几个——策略、观察者、模板方法，并串讲同样属于行为型的责任链、状态、命令、迭代器，说明它们各自解决什么、结构长什么样、什么时候不该用。适合已经能熟练写接口与多态、但在真实项目里被成堆的 if-else 和散落的通知代码折磨过的读者。

行为型模式解决什么问题

创建型模式关心“对象怎么来”，结构型模式关心“对象怎么拼”，而行为型模式关心的是对象之间如何分配职责与通信。它的核心矛盾往往只有一句话：变化的部分被硬编码在了稳定的部分里。最典型的症状就是 if-else 链——用户等级决定折扣、订单类型决定流程、消息种类决定处理方式，每加一种情况就要回头改老代码，违反开闭原则。

行为型模式的共同手法是把会变的那一小块抽成对象，让稳定的一端持有它的引用，从而用组合代替条件判断。本章涉及的七个模式，可以先按“变化维度”记一张地图。把一整个算法抽出来自由切换，是策略模式；把算法的骨架固定、只放开其中几步，是模板方法；把“谁需要知道”抽出来动态注册，是观察者模式。让多个处理者依次尝试、直到有人接手，是责任链模式；把“当前处于哪个阶段”变成对象，是状态模式；把“一次请求”连同参数封装成对象，是命令模式；把“怎么遍历一个聚合”从聚合本身剥离，是迭代器模式。下面逐个展开，重点放在前三个。

策略模式：把算法变成可替换的对象

策略模式（Strategy）的意图是：定义一系列算法，把它们分别封装起来，并使它们可以相互替换。它有三个角色——抽象策略（接口或抽象类）、具体策略（实现类）、环境类（持有策略引用并对外提供统一入口）。关键点是“运行时唯一性”：任一时刻环境类只使用一个具体策略，但可以在运行期切换。

策略模式的重心不在“怎么实现算法”，而在“怎么组织与调用算法”。以会员折扣为例，初级会员无折扣、中级 10%、高级 20%，写成 if-else 时，判断逻辑与计算逻辑混在一处；抽成策略后，判断逻辑退化为选择策略的一行代码，新增等级只需加一个新类。这也解释了策略与工厂容易混淆的原因：两者结构相似，但关注点不同。工厂是创建型、关注“造出对象”，对调用方是黑盒；策略是行为型、关注“封装行为”，对调用方是白盒——调用方必须知道有哪些策略可选。

public interface DiscountStrategy {
    /** 返回折后价格 */
    double apply(double originalPrice);
}

public class NoDiscount implements DiscountStrategy {
    @Override
    public double apply(double originalPrice) {
        return originalPrice;
    }
}

public class VipDiscount implements DiscountStrategy {
    private final double rate; // 例如 0.9 表示九折

    public VipDiscount(double rate) {
        this.rate = rate;
    }

    @Override
    public double apply(double originalPrice) {
        return originalPrice * rate;
    }
}

public class PricingContext {
    private DiscountStrategy strategy;

    public PricingContext(DiscountStrategy strategy) {
        this.strategy = strategy;
    }

    /** 运行期可随时切换策略 */
    public void setStrategy(DiscountStrategy strategy) {
        this.strategy = strategy;
    }

    public double quote(double originalPrice) {
        if (strategy == null) {
            throw new IllegalStateException("未设置折扣策略");
        }
        return strategy.apply(originalPrice);
    }
}

调用方按需注入：new PricingContext(new VipDiscount(0.9)).quote(100) 得到 90.0。

策略模式的收益是算法可自由切换、消除多重条件判断、扩展性良好；代价是策略类数量会增长，而且所有策略都要对调用方暴露。实践中有两条经验。第一，如果策略超过四五个，不要急着继续堆类，可以考虑用枚举承载简单策略，或者引入工厂或映射表（如 Map<String, DiscountStrategy>）把“选策略”这一步也封装起来。第二，如果策略类之间有明显的重复公共行为，应把它上移到抽象策略类中，此时抽象策略必须用抽象类而不是接口。策略与模板方法在结构上都用于封装变化，选择的标准是：要封装的是“一整个算法”，用策略；要封装的是“一个算法中的某几步”，用模板方法。

观察者模式：一对多的通知机制

观察者模式（Observer）定义对象间一对多的依赖关系：当一个对象（目标，也称主题）的状态改变时，所有依赖它的对象（观察者）都得到通知并被自动更新。它包含目标（维护观察者集合并提供注册、注销、通知能力）、抽象观察者（通常是接口）与具体观察者。

import java.util.ArrayList;
import java.util.List;

public interface PriceListener {
    void onPriceChanged(String symbol, double newPrice);
}

public class Stock {
    private final String symbol;
    private final List<PriceListener> listeners = new ArrayList<>();
    private double price;

    public Stock(String symbol) {
        this.symbol = symbol;
    }

    public void addListener(PriceListener listener) {
        listeners.add(listener);
    }

    public void removeListener(PriceListener listener) {
        listeners.remove(listener);
    }

    public void setPrice(double price) {
        this.price = price;
        notifyListeners();
    }

    private void notifyListeners() {
        for (PriceListener listener : listeners) {
            listener.onPriceChanged(symbol, price);
        }
    }
}

public class StockDemo {
    public static void main(String[] args) {
        Stock stock = new Stock("600519");
        stock.addListener((symbol, newPrice) ->
                System.out.println("[日志] " + symbol + " 现价 " + newPrice));
        stock.addListener((symbol, newPrice) -> {
            if (newPrice > 1800) {
                System.out.println("[预警] " + symbol + " 超过阈值");
            }
        });
        stock.setPrice(1850);
    }
}

运行结果会先打印日志行，再打印预警行。这个例子体现了观察者模式的两个优点：观察者与目标之间是抽象耦合，新增一种通知方式不用改 Stock；并且建立了一套触发机制，通知自动发生。

但要留意三个坑。第一，通知放在 setter 里会“每次都广播”：上面的写法在价格未变化时也会通知，工程上通常先判等再决定是否通知。第二，观察者若在回调中反向修改目标，容易形成循环调用，必须避免循环引用。第三，遍历通知是同步顺序执行的，某个观察者抛异常或阻塞会拖垮整条链路，因此常改为异步投递，或对每个观察者单独 try-catch 隔离故障。此外，JDK 早期提供的 java.util.Observable 与 java.util.Observer 已在 Java 9 标记为废弃，不要在新代码中使用，自己定义接口（如上例）或使用 Spring 的 ApplicationEventPublisher 更合适。

模板方法与责任链：骨架固定、步骤可变

模板方法模式（Template Method）在一个抽象类中定义算法的骨架（模板方法），把其中若干步骤留给子类实现。它区分三类基本方法：抽象方法必须由子类实现；具体方法由父类实现、子类可选择覆盖；钩子方法（hook）由父类给出空实现或默认实现，子类按需扩展。因为模板方法本身是具体方法，要求抽象层能持有具体实现，所以模板方法的抽象层只能是抽象类，不能是接口。

public abstract class DataImporter {

    /** 模板方法：骨架固定，子类不要覆盖 */
    public final void importData(String source) {
        open();
        String raw = read(source);
        if (needValidate()) {           // 钩子：默认返回 true
            validate(raw);
        }
        save(raw);
        close();
    }

    protected abstract void open();
    protected abstract String read(String source);
    protected abstract void save(String raw);

    /** 钩子方法：默认给出非空实现 */
    protected boolean needValidate() {
        return true;
    }

    protected void validate(String raw) {
        if (raw == null || raw.isEmpty()) {
            throw new IllegalArgumentException("数据为空");
        }
    }

    protected void close() {
        System.out.println("释放资源");
    }
}

public class CsvImporter extends DataImporter {
    @Override
    protected void open() {
        System.out.println("打开 CSV 文件");
    }

    @Override
    protected String read(String source) {
        return "id,name";
    }

    @Override
    protected void save(String raw) {
        System.out.println("写入 CSV: " + raw);
    }
}

把骨架声明为 final 是模板方法的关键细节：它防止子类改写流程，只允许填充步骤，这就是“好莱坞原则”的含义——由框架决定何时调用你的代码，而不是由你的代码去调用框架。

责任链模式（Chain of Responsibility）同样把处理逻辑拆开，但方向不同：它让多个处理者串成一条链，请求沿链传递，直到某个处理者接手或链结束。典型场景是审批流（组长 → 经理 → 总监）、过滤器、参数校验链。链式结构要注意三点：必须保证所有分支最终都能终止，否则请求会“掉在地上”；链的顺序即业务优先级，需要显式配置而非写死在代码里。处理者之间应通过统一的抽象处理者接口持有后继引用，而不是彼此直接依赖。若把责任链的每个节点改成“由当前状态决定下一个节点”，就得到了状态模式（State）。状态与策略结构相似，区别在目的：策略由外部选择算法，状态由对象内部的状态迁移驱动行为变化。

另外两个行为型模式适合在需要时再深入。命令模式（Command）把一次请求封装成对象，因而支持参数化、排队、记录日志与撤销重做，GUI 的按钮回调与事务型操作日志都是它的应用。实现撤销时，通常为命令接口追加 undo()，由具体命令自己保存执行前的状态。迭代器模式（Iterator）把遍历逻辑从聚合中剥离，让聚合只负责存储、迭代器负责访问顺序；Java 集合已经内置了这一模式，Iterator 的 hasNext()/next() 就是它的标准形态，自定义容器只要实现 Iterable 即可获得增强 for 循环支持。需要提醒的是：在使用迭代器遍历时直接调用集合的 add/remove 会抛出 ConcurrentModificationException，删除元素应使用迭代器自身的 remove()。

访问者、备忘录与中介者：三个「非典型」行为型模式

前面七个模式处理的是「怎么替换、怎么通知、怎么传递」。还有一批行为型模式解决的是另外三类问题：给稳定的数据结构不断加新操作（访问者）、让对象能回滚到历史状态（备忘录）、把网状依赖收敛成星型（中介者）。它们用得比策略、观察者少，但在面试与框架源码里出现频率很高，值得单独认识。

访问者模式：把「操作」从「数据结构」里搬出来

访问者模式（Visitor）的意图是：将数据结构与作用于其上的操作分离，使新增操作不必修改元素类。它有两个角色——元素提供 accept(visitor) 方法并把自身交给访问者，访问者为每种元素提供一个 visit 重载。新增一种导出格式时，只需加一个访问者类，元素类一行不动。

import java.util.ArrayList;
import java.util.List;

/** 元素接口：所有节点都能接受访问者 */
public interface DocNode {
    void accept(DocVisitor visitor);
}

public class Paragraph implements DocNode {
    private final String text;

    public Paragraph(String text) {
        this.text = text;
    }

    public String getText() {
        return text;
    }

    @Override
    public void accept(DocVisitor visitor) {
        visitor.visit(this);          // 把自身交给访问者，由访问者决定怎么处理
    }
}

public class Image implements DocNode {
    private final String url;

    public Image(String url) {
        this.url = url;
    }

    public String getUrl() {
        return url;
    }

    @Override
    public void accept(DocVisitor visitor) {
        visitor.visit(this);
    }
}

/** 访问者接口：为每种元素声明一个 visit 重载 */
public interface DocVisitor {
    void visit(Paragraph paragraph);

    void visit(Image image);
}

/** 具体访问者一：导出 Markdown */
public class MarkdownExportVisitor implements DocVisitor {
    @Override
    public void visit(Paragraph paragraph) {
        System.out.println(paragraph.getText());
    }

    @Override
    public void visit(Image image) {
        System.out.println("![](" + image.getUrl() + ")");
    }
}

/** 具体访问者二：统计字数，新增操作无需改动任何元素类 */
public class WordCountVisitor implements DocVisitor {
    private int total;

    @Override
    public void visit(Paragraph paragraph) {
        total += paragraph.getText().length();
    }

    @Override
    public void visit(Image image) {
        // 图片不计入字数，这里实现为空即可
    }

    public int getTotal() {
        return total;
    }
}

public class Document {
    private final List<DocNode> nodes = new ArrayList<>();

    public void add(DocNode node) {
        nodes.add(node);
    }

    public void accept(DocVisitor visitor) {
        for (DocNode node : nodes) {
            node.accept(visitor);     // 由元素反向调用访问者，即「双重分派」
        }
    }
}

这里有一个面试高频点：为什么不能只在访问者里用 instanceof 判断类型，而要写 accept？因为 node.accept(visitor) 这一调用同时决定了「哪种元素」和「哪个访问者」两个维度的具体类型，Java 靠这一次虚方法调用完成了所谓的双重分派。若改成 instanceof 链，同一种操作的类型判断就会散落在各处：每加一种元素，所有操作类里的判断链都得改一遍——这正是访问者要用 accept 把选择权交回元素的原因。

访问者的收益与代价是同一件事的两面：新增操作容易，新增元素困难。往 DocNode 家族里加一个 Table，就必须给 DocVisitor 及全部实现补上 visit(Table)，接口一变全线报错。此外，访问者为了处理元素，通常需要元素暴露内部细节（如上面的 getText()），这在某种程度上违反了迪米特法则，也让它依赖具体元素类而非抽象——所以它适用且仅适用于「元素种类稳定、操作频繁增加」的场景，编译器语法树、代码检查工具、报表导出是最典型的落点。

备忘录模式：不破坏封装地保存与恢复状态

备忘录模式（Memento）在不暴露对象内部细节的前提下，捕获并保存对象的某个状态，以便之后恢复。它有三个角色：发起人（Originator，拥有状态并负责创建/恢复备忘录）、备忘录（Memento，只保存状态快照）、管理者（Caretaker，负责保管备忘录，但不关心里面是什么）。

import java.util.ArrayDeque;
import java.util.Deque;

/** 备忘录：对外只暴露不透明的状态，字段用 final 保证快照不可变 */
public final class EditorMemento {
    private final String content;
    private final int cursor;

    EditorMemento(String content, int cursor) {
        this.content = content;
        this.cursor = cursor;
    }

    String getContent() {
        return content;
    }

    int getCursor() {
        return cursor;
    }
}

/** 发起人：负责创建快照与从快照恢复 */
public class Editor {
    private String content = "";
    private int cursor = 0;

    public void type(String text) {
        content += text;
        cursor = content.length();
    }

    public EditorMemento save() {
        return new EditorMemento(content, cursor);
    }

    public void restore(EditorMemento memento) {
        this.content = memento.getContent();
        this.cursor = memento.getCursor();
    }

    @Override
    public String toString() {
        return content;
    }
}

/** 管理者：只负责存取快照，不解读内容；用栈实现多级撤销 */
public class History {
    private final Deque<EditorMemento> stack = new ArrayDeque<>();

    public void push(EditorMemento memento) {
        stack.push(memento);
    }

    public EditorMemento pop() {
        return stack.isEmpty() ? null : stack.pop();
    }
}

使用方式就是「改之前存一份、撤销时弹一份」：history.push(editor.save()) 与 editor.restore(history.pop())。设计上的关键点有两个：一是备忘录必须不可变，否则外部一改，历史状态就被污染；二是管理者不应提供读取状态的接口，它只管保管，这就是「不破坏封装」的含义——状态没有被暴露给第三方，却依然能恢复。

它要解决的痛点是真实的：文本编辑器的 Ctrl + Z、游戏存档、数据库事务回滚、表单草稿，都是状态的保存与恢复。代价是内存——每次快照都会复制一份状态，字段多、保存频繁时内存会迅速膨胀。常见优化有三条：只保存增量（diff）而不是全量；对快照对象使用原型模式做浅拷贝并共享不可变部分；限制历史栈深度（例如只保留最近 20 步）。与原型模式的区别也要分清：原型是为了少创建对象而拷贝，备忘录是为了能回到过去而快照，前者的产物是同类对象，后者的产物是历史数据。

中介者模式：把网状依赖收敛成星型

中介者模式（Mediator）用一个中介对象封装一系列对象之间的交互，让对象之间不再显式互相引用。判断是否该用它，只要看类图上有没有出现「网状依赖」——五个同事类两两通信会连出十条线，改一个类的接口可能波及另外四个。

import java.util.ArrayList;
import java.util.List;

/** 中介者接口 */
public interface ChatMediator {
    void register(User user);

    void send(String message, User from);   // 由中介者决定转发给谁
}

/** 同事类：只认识中介者，不认识其他同事 */
public abstract class User {
    protected final ChatMediator mediator;   // 抽象依赖，不依赖具体中介者
    protected final String name;

    protected User(ChatMediator mediator, String name) {
        this.mediator = mediator;
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public abstract void receive(String message, String from);

    public void send(String message) {
        mediator.send(message, this);
    }
}

public class ChatUser extends User {
    public ChatUser(ChatMediator mediator, String name) {
        super(mediator, name);
    }

    @Override
    public void receive(String message, String from) {
        System.out.println(name + " 收到 " + from + " 的消息: " + message);
    }
}

/** 具体中介者：掌握全部同事，负责路由与广播 */
public class ChatRoom implements ChatMediator {
    private final List<User> users = new ArrayList<>();

    @Override
    public void register(User user) {
        users.add(user);
    }

    @Override
    public void send(String message, User from) {
        for (User user : users) {
            if (user != from) {              // 广播给除发送者外的所有人
                user.receive(message, from.getName());
            }
        }
    }
}

同事类只持有 ChatMediator 接口，通信规则全部集中在中介者里：把广播改成「只发给管理员」或「按房间隔离」，只改 ChatRoom 一处。代价同样明确——中介者会随着交互规则变多而膨胀成上帝类。因此实践中有两条纪律：中介者只负责「转发与路由」，不要塞业务计算；交互规则复杂到一定程度时，把中介者本身再拆分（例如按房间拆成多个中介者）。

它与外观模式、观察者模式的区别经常被问到：外观是单向的——客户端调门面，子系统之间不通过门面互相通信；中介者是双向的——同事之间通过中介者互相通信；观察者是一对多的通知，目标与观察者之间仍是直接引用，而中介者把引用也一并收走了。MVC 里的控制器其实就是模型与视图之间的中介者。

解释器模式与空对象模式：两个「窄场景」工具

解释器模式（Interpreter）为一种简单语言定义文法表示，并给出解释器来求值。它的结构是构建一棵抽象语法树：终结符表达式对应叶子，非终结符表达式（与、或、非）对应内部节点，interpret 递归求值。

/** 抽象表达式 */
public interface Expression {
    boolean interpret(String context);
}

/** 终结符：判断上下文是否包含某个关键词 */
public class KeywordExpression implements Expression {
    private final String keyword;

    public KeywordExpression(String keyword) {
        this.keyword = keyword;
    }

    @Override
    public boolean interpret(String context) {
        return context != null && context.contains(keyword);
    }
}

/** 非终结符：或 */
public class OrExpression implements Expression {
    private final Expression left;
    private final Expression right;

    public OrExpression(Expression left, Expression right) {
        this.left = left;
        this.right = right;
    }

    @Override
    public boolean interpret(String context) {
        return left.interpret(context) || right.interpret(context);
    }
}

/** 非终结符：与 */
public class AndExpression implements Expression {
    private final Expression left;
    private final Expression right;

    public AndExpression(Expression left, Expression right) {
        this.left = left;
        this.right = right;
    }

    @Override
    public boolean interpret(String context) {
        return left.interpret(context) && right.interpret(context);
    }
}

// 用法：组合出「包含 Java 且包含 教程」的规则
Expression rule = new AndExpression(
        new KeywordExpression("Java"),
        new KeywordExpression("教程"));
System.out.println(rule.interpret("Java 设计模式教程"));   // true

它的优点是文法易扩展、实现简单；缺点是复杂文法会导致类的数量爆炸，且递归调用带来性能开销。真实项目中很少手写完整解释器，通常只在「规则表达式」这一层使用，其余场景直接换用成熟方案：定时任务的 cron 表达式交给 Quartz，权限与规则表达式交给 SpEL 或 Aviator，SQL 交给数据库。一句话总结：解释器适合「文法简单且需要频繁组合」的规则判断，不适合当通用语言解析器。

空对象模式（Null Object）用一个「什么都不做」的对象代替 null，让调用方不必到处判空：

public interface Logger {
    void log(String message);
}

public class ConsoleLogger implements Logger {
    @Override
    public void log(String message) {
        System.out.println(message);
    }
}

/** 空对象：实现同一接口，但所有方法都是安全的空实现 */
public class NullLogger implements Logger {
    @Override
    public void log(String message) {
        // 有意为空：关闭日志时不产生任何输出
    }
}

public class Service {
    private final Logger logger;

    public Service(Logger logger) {
        this.logger = logger == null ? new NullLogger() : logger;   // 一次兜底，处处省心
    }

    public void doWork() {
        logger.log("开始处理");     // 不需要再判空
    }
}

空对象模式消除了大量 if (x != null)，但它只适合「什么都不做」是合理默认行为的场景。如果空值意味着调用出错，用空对象把错误吞掉，只会让问题推迟到更难排查的地方——这时抛出异常或返回 Optional 更合适。JDK 里也有同样的取舍：Collections.emptyList() 返回的空集合可安全遍历，而 Optional 明确要求调用方处理「值不存在」，两者面向的是不同语义。

这五个模式可以串成一句话记忆：访问者把操作搬出数据结构，备忘录把历史存进快照，中介者把网状收成星型，解释器把文法搭成语法树，空对象把判空换成空实现。它们的共同点依然是那个核心手法——找出会变的部分并抽成对象，只是变化点的形态不同。

小结

行为型模式的核心动作只有两步：找出代码里会变化的那一部分，把它抽成对象，再让稳定的一端持有它。策略模式抽走整个算法，模板方法只放开算法中的几步，观察者抽走“谁要知道”，责任链抽走“谁来处理”。状态抽走“当前在哪个阶段”，命令抽走“一次请求”，迭代器抽走“遍历顺序”。选用时先问三句话：变化的是一个完整算法还是其中几步？是运行期切换还是编译期继承？调用方需要知道细节吗？想清楚这三点，多数“该用哪个模式”的纠结都会迎刃而解。最后提醒一句：设计模式是重构的结果而非设计的起点，代码还没到需要抽象的时候，用 if-else 反而更清楚。
