微信生态开发

Posted on 2026-09-19，10 min read

只要产品要在微信里落地——扫码登录、小程序下单、公众号发通知——Java 后端就绕不开四件事：身份识别（openid / unionid）、会话保持（session_key）、服务端调用凭证（access_token）、资金与通知（支付、消息推送）。这四件事各自有独立的接口、独立的有效期、独立的失败码，混在一起写就会变成“登录偶尔失败、token 互相踢掉、支付回调重复发货”。本章把这条链路按调用顺序串起来讲，适合已经会写 Spring MVC / Spring Boot、但第一次对接微信的读者。示例基于微信官方接口的通用形态，字段细节请以你所用的公众号或小程序后台文档为准。

一、先分清应用、用户、凭证与消息的边界

新手最容易犯的错，是把公众号和小程序当成一个东西。它们共用同一个开放平台账号体系，但能力并不等价：

  • 公众号（订阅号 / 服务号）：服务号才有网页授权（OAuth2.0 拉取用户信息）、模板消息，以及绑定商户号后开通支付；订阅号的消息与支付能力受限。
  • 小程序：通过 wx.login() 拿临时 code，后端换 openid；支付走小程序支付，退款、对账走商户平台。
  • 用户标识：openid 只在单个应用内唯一，换个小程序就不一样；把多个应用绑到同一个开放平台账号后，才会返回 unionid，用它做跨应用的用户主键。
  • 凭证：access_token 是应用级凭证，不是用户级，全局只能有一份有效值——这一条决定了它必须集中缓存，而不是每个请求各取一次。

把这张“谁是谁”的地图记住，后面所有接口的职责就清楚了：code / jscode2session 负责认人，session_key 负责保护用户数据，access_token 负责让服务端有资格调接口，消息推送负责把结果告诉用户。

二、登录授权：用 code 换 openid 与 session_key

小程序登录链路只有三步：前端调用 wx.login() 拿到临时 code；把 code 通过 HTTPS 发给自己的后端；后端调用 sns/jscode2session 换取 openid、session_key（若绑定开放平台还会有 unionid）。核心实现如下：

@Component
public class WxaUserApi {

    private static final String JSCODE2SESSION_URL =
            "https://api.weixin.qq.com/sns/jscode2session";

    private final RestTemplate restTemplate;
    private final String appId;      // 从配置/环境变量注入
    private final String appSecret;  // 绝不写进代码仓库

    public WxaUserApi(RestTemplate restTemplate,
                      @Value("${wx.app-id}") String appId,
                      @Value("${wx.app-secret}") String appSecret) {
        this.restTemplate = restTemplate;
        this.appId = appId;
        this.appSecret = appSecret;
    }

    public Jscode2SessionResult code2Session(String jsCode) {
        if (!StringUtils.hasText(jsCode)) {
            throw new IllegalArgumentException("jsCode 不能为空");
        }
        // 关键：交给构建器做 URL 编码，不要手工拼 query，更不要用支付签名工具拼参数
        URI uri = UriComponentsBuilder.fromHttpUrl(JSCODE2SESSION_URL)
                .queryParam("appid", appId)
                .queryParam("secret", appSecret)
                .queryParam("js_code", jsCode)
                .queryParam("grant_type", "authorization_code")
                .build().encode().toUri();

        Jscode2SessionResult body =
                restTemplate.getForObject(uri, Jscode2SessionResult.class);
        if (body == null) {
            throw new IllegalStateException("jscode2session 返回空响应");
        }
        // 成功时 errcode 为 0 或字段缺省；非 0 一律视为失败
        if (body.getErrcode() != null && body.getErrcode() != 0) {
            // 常见错误：40029 code 无效或已被使用；45011 频率限制
            throw new WxApiException(body.getErrcode(), body.getErrmsg());
        }
        return body;
    }
}

拿到 session_key 后有两个用途：解密前端提交的 encryptedData（AES-128-CBC），以及校验数据完整性。官方校验规则是 signature = sha1(rawData + sessionKey)，注意 rawData 在前、session_key 在后，且结果是小写十六进制：

/** 校验微信用户信息的完整性：signature = sha1(rawData + session_key) */
public static boolean checkSignature(String rawData, String sessionKey, String signature) {
    if (!StringUtils.hasText(rawData) || !StringUtils.hasText(sessionKey)
            || !StringUtils.hasText(signature)) {
        return false;
    }
    String expect = DigestUtils.sha1Hex(rawData + sessionKey);
    // 用定长比较，避免逐字符比较带来的时序差异
    return MessageDigest.isEqual(
            expect.getBytes(StandardCharsets.UTF_8),
            signature.getBytes(StandardCharsets.UTF_8));
}

/** 登录成功后：session_key 只留在服务端，前端只拿一个不透明 token */
public String saveSession(String openid, String sessionKey) {
    String token = UUID.randomUUID().toString().replace("-", "");
    redis.opsForValue().set("wx:session:" + token, sessionKey, Duration.ofMinutes(30));
    redis.opsForValue().set("wx:openid:" + token, openid, Duration.ofMinutes(30));
    return token;
}

这里的几个坑值得单独强调：

  • code 是一次性的，5 分钟内有效，用过即废。所以“刷新页面重新登录”必须重新走 wx.login()，不能复用旧 code，否则稳定复现 40029。
  • session_key 不能下发到前端。它是能解密的密钥，一旦泄露，用户手机号等敏感数据就等于公开。前端只应拿到你自己签发的、可撤销的业务 token。
  • 不要用固定字符串代替 rawData 参与校验。有些实现把 rawData 为空时替换成应用名再算签名，这样算出来的值只用于生成缓存键，不能当作“用户信息未被篡改”的证据；如果确实只需要一个缓存键，用随机 token 更直接。
  • 存疑项：微信并未公开 session_key 的固定有效期，它随登录刷新而更换。上例按业务会话给了 30 分钟，实际时长请按自己的登录态策略调整。

三、服务端凭证 access_token 与两种“消息推送”

调用模板消息、客服消息、订阅消息、二维码等接口，都要带上 access_token。它通过 cgi-bin/token 获取，expires_in 通常为 7200 秒，而且全局唯一：新取一次，旧的就可能失效。因此正确做法是“集中缓存 + 提前刷新 + 分布式锁”，绝不能在每个业务请求里现取：

@Component
public class WxAccessTokenService {

    private static final String TOKEN_URL = "https://api.weixin.qq.com/cgi-bin/token";
    private static final String CACHE_KEY = "wx:access_token";

    private final StringRedisTemplate redis;
    private final RestTemplate restTemplate;
    private final String appId;
    private final String appSecret;

    public String getAccessToken() {
        String cached = redis.opsForValue().get(CACHE_KEY);
        if (cached != null) {
            return cached;
        }
        // 多实例同时刷新会互相踢掉对方的 token，先抢锁
        Boolean locked = redis.opsForValue()
                .setIfAbsent(CACHE_KEY + ":lock", "1", Duration.ofSeconds(10));
        if (Boolean.FALSE.equals(locked)) {
            throw new IllegalStateException("access_token 正在刷新，请稍后重试");
        }
        try {
            String url = TOKEN_URL + "?grant_type=client_credential"
                    + "&appid=" + appId + "&secret=" + appSecret;
            TokenResponse resp = restTemplate.getForObject(url, TokenResponse.class);
            if (resp == null || resp.getAccess_token() == null) {
                throw new WxApiException(resp == null ? -1 : resp.getErrcode(),
                                         resp == null ? "空响应" : resp.getErrmsg());
            }
            // 提前 300 秒过期，避免边界时刻拿到一个刚失效的 token
            long ttl = Math.max(60, resp.getExpires_in() - 300);
            redis.opsForValue().set(CACHE_KEY, resp.getAccess_token(), Duration.ofSeconds(ttl));
            return resp.getAccess_token();
        } finally {
            redis.delete(CACHE_KEY + ":lock");
        }
    }
}

注意 40001（凭证失效）和 42001（凭证过期）都说明缓存脏了：正确的处理不是立刻重取后盲目重试，而是先删缓存、再取一次、失败即向上抛，避免把刷新风暴放大。

“消息推送”在微信生态里有两个完全不同的方向，别混为一谈。第一层是微信推给你：公众号后台配置服务器地址与 Token 后，用户消息会以 XML 形式回调到你的接口，你要用 sha1(sort(token, timestamp, nonce)) 验签，并在 5 秒内回复，否则微信会重试三次——所以必须用 MsgId 做幂等。小程序侧则多用订阅消息，用户授权一次只能推一条。第二层是你推给自己的前端：站内实时提醒通常用 Spring WebSocket，实现上有几个源文档里没处理好的细节：

@Configuration
@EnableWebSocket
public class WxPushWebSocketConfig implements WebMvcConfigurer, WebSocketConfigurer {

    @Override
    public void registerWebSocketHandlers(WebSocketHandlerRegistry registry) {
        registry.addHandler(pushHandler(), "/ws/push")
                .addInterceptors(new AuthHandshakeInterceptor())
                .setAllowedOriginPatterns("https://your-domain.com"); // 别用 "*" 搭配凭证
    }

    @Bean
    public PushHandler pushHandler() {
        return new PushHandler();
    }
}

public class PushHandler extends TextWebSocketHandler {

    // 静态 ArrayList 既不是线程安全的，定向发送也只能全表遍历；换成按用户索引的并发 Map
    private final Map<String, WebSocketSession> sessions = new ConcurrentHashMap<>();

    @Override
    public void afterConnectionEstablished(WebSocketSession session) throws Exception {
        String userId = userIdOf(session);
        WebSocketSession old = sessions.put(userId, session);
        if (old != null && old.isOpen()) {
            old.close(CloseStatus.NORMAL);   // 同一用户重复登录，踢掉旧连接
        }
    }

    @Override
    public void afterConnectionClosed(WebSocketSession session, CloseStatus status) {
        sessions.remove(userIdOf(session), session);
    }

    @Override
    public void handleTransportError(WebSocketSession session, Throwable ex) throws Exception {
        sessions.remove(userIdOf(session), session);
        if (session.isOpen()) {
            session.close(CloseStatus.SERVER_ERROR);
        }
    }

    public void sendToUser(String userId, String text) throws IOException {
        WebSocketSession session = sessions.get(userId);
        if (session != null && session.isOpen()) {
            session.sendMessage(new TextMessage(text));
        }
    }

    private String userIdOf(WebSocketSession session) {
        Object userId = session.getAttributes().get("WEBSOCKET_USERNAME");
        return userId == null ? "anonymous" : userId.toString(); // 直接 .equals() 会 NPE
    }
}

补充两点工程习惯：握手拦截器里要用 HttpSessionHandshakeInterceptor 把登录用户写进 attributes，否则无法定向推送；集群部署时 WebSocket 连接分散在多个实例上，需要引入 Redis 发布订阅或消息队列做跨节点广播。

四、微信支付：V2 与 V3 的差别只有两点

支付部分的接口形式取决于你接的是哪一代：V2 用 XML 报文，签名靠商户 API 密钥做 MD5 或 HMAC-SHA256；V3 用 JSON 报文，签名靠商户私钥做 RSA-SHA256，回调数据则用 APIv3 密钥做 AES-256-GCM 解密。无论哪一代，业务链路是一致的：服务端下单（小程序支付 / JSAPI）拿到 prepay_id，再用它做一次签名返回给前端唤起支付面板；支付结果由微信异步回调通知。

回调处理必须按固定顺序做四件事：验签（否则任何人都能伪造到账通知）、解密（V3 的 resource 是密文，不能直接读明文金额）、幂等（以 out_trade_no 为唯一键，重复通知只处理一次）、校验金额（回调金额必须与本地订单金额相等，单位是分）。最后按平台要求应答成功标识，V2 回 SUCCESS 的 XML，V3 回 {"code":"SUCCESS"}，否则微信会持续重推。签名时最容易翻车的是签名串的拼接顺序、结尾换行、时间戳单位与证书序列号，建议直接使用官方 SDK 的签名工具类，而不是手写字符串拼接。存疑：各接口的必填字段随版本迭代较快，请以商户平台 APIv3 文档为准。

五、小结

微信生态的 Java 对接并不复杂，难在把四类凭证的边界守住：code 一次性、五分钟内换 openid + session_key；session_key 只留服务端，只给前端一个可撤销的业务 token；access_token 全局一份、集中缓存、提前刷新；支付回调先验签再幂等，金额必须比对。消息推送则要分清“微信推给你”和“你推给前端”两个方向，前者靠验签加幂等，后者靠并发安全的会话表与跨节点广播。把这四条守住，剩下的就是按官方文档填字段了。
