Table API & SQL 介绍

1.1 Flink Table模块

参考：https://ci.apache.org/projects/flink/flink-docs-release-1.12/dev/table/

Flink的Table模块包括 Table API和 SQL：

  • Table API： 是一种类SQL的API，通过Table API，用户可以像操作表一样操作数据，非常直观和方便；

  • SQL：作为一种声明式语言，有着标准的语法和规范，用户可以不用关心底层实现即可进行数据的处理，非常易于上手。
    Flink Table API 和 SQL 的实现上有80%左右的代码是公用的。作为一个流批统一的计算引擎，Flink 的 Runtime 层是统一的。

1.2 Table API & SQL特点

Flink之所以选择将 Table API & SQL作为未来的核心 API，是因为其具有一些非常重要的特点：

  • 声明式：用户只关心做什么，不用关心怎么做

  • 高性能：支持查询优化，可以获取更好的执行性能

  • 批流统一：相同的统计逻辑，既可以流模式运行，也可以批模式运行

  • 标准稳定：语义遵循SQL标准，不易变动

  • 易理解：语义明确，所见即所得

使用举例：

Table API SQL
tab.groupBy("word").select("word, count(1) as cnt") SELECT word,COUNT(*) AS cnt FROM MyTable GROUP BY word

1.3 Table API& SQL发展历程

自 2015 年开始，阿里巴巴开始调研开源流计算引擎，最终决定基于 Flink 打造新一代计算引擎，针对 Flink存在的不足进行优化和改进，并且在 2019 年初将最终代码开源，也就是Blink。

Blink 在原来的 Flink 基础上最显著的一个贡献就是 Flink SQL的实现！

查询处理器的选择 ： Flink1.11之后Blink Query Processor查询处理器已经是默认的了。

解析：

  • flink-table-common：这个包中主要是包含 Flink Planner和 Blink Planner一些共用的代码。

  • flink-table-api-java：这部分是用户编程使用的 API，包含了大部分的API。

  • flink-table-api-scala：这里只是非常薄的一层，仅和 Table API的 Expression 和 DSL 相关。

  • 两个 Planner：flink-table-planner和 flink-table-planner-blink。

  • 两个 Bridge：flink-table-api-scala-bridge 和 flink-table-api-java-bridge

Flink Planner 和 Blink Planner 都会依赖于具体的 JavaAPI，也会依赖于具体的 Bridge，通过Bridge可以将 API 操作相应的转化为Scala的 DataStream，或者转化为JAVA的 DataStream

版本差异提示：上面的两个 Planner 不要同时引入（类名相同会冲突），flink-table-planner 一般也只在写单元测试时才需要，生产代码用 provided 即可；另外 Java 业务代码只需要 flink-table-api-java-bridge，Scala 的 Bridge 可以不加。各版本的坐标对应关系如下：

  • 1.9 – 1.10：默认是旧 Planner flink-table-planner_2.12，要用 Blink 需显式引入 flink-table-planner-blink_2.12；

  • 1.11 – 1.13：Blink Planner 成为默认（useBlinkPlanner()），旧 Planner 被标记为废弃，并计划在 1.14 移除；

  • 1.14 起：旧 Planner 已被移除（同时 BatchTableEnvironment 与 DataSet 的互操作也不再支持），flink-table-planner-blink 改回原名 flink-table-planner，flink-table-runtime-blink 改名为 flink-table-runtime；

  • 1.15 起：推荐引入 flink-table-planner-loader（把 Planner 放在独立 ClassLoader 中加载，避免与用户依赖的 Scala 版本冲突），flink-table-planner 只在需要直接使用 Planner 内部类（例如自定义优化规则）时才引入；

  • 1.18：Java 侧可以完全不依赖 Scala，只引 flink-table-api-java-bridge + flink-table-planner-loader；EnvironmentSettings.Builder#useOldPlanner()、useBlinkPlanner() 这些方法已不再需要，直接创建环境即可。

2.3.2 环境与 Planner 的版本差异

1.14 之前，创建执行环境必须显式选择 Planner，而且流、批两套环境用的是不同的类；1.14 之后旧 Planner 被移除，useOldPlanner()、useBlinkPlanner() 也随之失去意义，流批两种模式可以统一成同一种写法：

// 1.14+ 推荐写法：不再指定 Planner，靠 inStreamingMode / inBatchMode 区分流批
EnvironmentSettings settings = EnvironmentSettings.newInstance()
        .inStreamingMode()      // 批处理改为 inBatchMode()
        .build();
TableEnvironment tableEnv = TableEnvironment.create(settings);

// 需要与 DataStream API 混用时，用 StreamTableEnvironment
StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
StreamTableEnvironment streamTableEnv = StreamTableEnvironment.create(env);

注意：TableEnvironment 与 StreamTableEnvironment 的建表、查询方法基本通用，但 fromDataStream()、toChangelogStream() 这类与 DataStream 互转的方法只存在于 StreamTableEnvironment 上，混编程序里请直接使用后者。

2.3.6.3 转换表到DataStream

Convert a Table into a DataStream：

  • 追加模式（Append Mode）：只有当动态表仅通过插入更改进行修改时，才能使用此模式，即，它是仅追加模式，并且以前发出的结果从不更新；

  • 撤回模式（Retract Mode）：此模式始终可用。它使用布尔标志对插入和删除更改进行编码。

// get StreamTableEnvironment.
StreamTableEnvironment tableEnv = ...; // see "Create a TableEnvironment" section

// Table with two fields (String name, Integer age)
Table table = ...

// convert the Table into an append DataStream of Row by specifying the class
DataStream<Row> dsRow = tableEnv.toAppendStream(table, Row.class);

// convert the Table into an append DataStream of Tuple2<String, Integer>
 //   via a TypeInformation
TupleTypeInfo<Tuple2<String, Integer>> tupleType = new TupleTypeInfo<>(
  Types.STRING(),
  Types.INT());
DataStream<Tuple2<String, Integer>> dsTuple =
  tableEnv.toAppendStream(table, tupleType);
// convert the Table into a retract DataStream of Row.
//   A retract stream of type X is a DataStream<Tuple2<Boolean, X>>.
//   The boolean field indicates the type of the change.
//   True is INSERT, false is DELETE.
DataStream<Tuple2<Boolean, Row>> retractStream =
  tableEnv.toRetractStream(table, Row.class);

版本差异：toAppendStream() / toRetractStream() 自 1.13 起被标记为废弃，新代码应统一使用 toChangelogStream()。changelog 流里的每条 Row 都带一个 RowKind（+I 插入、-U 更新前、+U 更新后、-D 删除），它和动态表的四种变更一一对应，是 Table 与 DataStream 之间唯一能无损表达回撤的桥梁。

StreamTableEnvironment tableEnv = ...; // see "Create a TableEnvironment" section

// 交互式查询得到的结果表，按用户分组累计金额
Table result = tableEnv.sqlQuery(
    "SELECT user_id, SUM(money) AS total_money FROM order_source GROUP BY user_id");

// Table -> DataStream：changelog 流
DataStream<Row> changelogStream = tableEnv.toChangelogStream(result);

// 若结果只会追加，可以显式声明期望的 ChangelogMode，
// 这样一旦 SQL 产生 -U/+U，规划阶段就会报错而不是运行期才失败
// tableEnv.toChangelogStream(result, Schema.newBuilder().build(), ChangelogMode.insertOnly());

// DataStream（Row 带 RowKind） -> Table
Table table = tableEnv.fromChangelogStream(changelogStream);

03 相关概念

参考：https://ci.apache.org/projects/flink/flink-docs-release-1.12/dev/table/streaming/dynamic_tables.html

3.1 动态表和连续查询

在Flink中，它把针对无界流的表称之为Dynamic Table（动态表）。它是Flink Table API和SQL的核心概念，顾名思义，它表示了Table是不断变化的。

我们可以这样来理解，当我们用Flink的API，建立一个表，其实把它理解为建立一个逻辑结构，这个逻辑结构需要映射到数据上去。

Flink source源源不断的流入数据，就好比每次都往表上新增一条数据。表中有了数据，我们就可以使用SQL去查询了。要注意一下，流处理中的数据是只有新增的，所以看起来数据会源源不断地添加到表中。

动态表也是一种表，既然是表，就应该能够被查询。我们来回想一下原先我们查询表的场景。

打开编译工具，编写一条SQL语句

  • 将SQL语句放入到mysql的终端执行

  • 查看结果

  • 再编写一条SQL语句

  • 再放入到终端执行

  • 再查看结果

……如此反复

而针对动态表，Flink的source端肯定是源源不断地会有数据流入，然后我们基于这个数据流建立了一张表，再编写SQL语句查询数据，进行处理。这个SQL语句一定是不断地执行的，而不是只执行一次。

注意：针对流处理的SQL绝对不会像批式处理一样，执行一次拿到结果就完了。而是会不停地执行，不断地查询获取结果处理。所以，官方给这种查询方式取了一个名字，叫Continuous Query，中文翻译过来叫连续查询。而且每一次查询出来的数据也是不断变化的。

该示意图描述了：我们通过建立动态表和连续查询来实现在无界流中的SQL操作。

大家也可以看到，在Continuous上面有一个State，表示查询出来的结果会存储在State中，再下来Flink最终还是使用流来进行处理。

所以，我们可以理解为Flink的Table API和SQL，是一个逻辑模型，通过该逻辑模型可以让我们的数据处理变得更加简单。

3.2 表与Stream的转换

3.2.1 表中的Update和Delete

我们前面提到的表示不断地 Append，表的数据是一直累加的，因为表示对接Source的，Source是不会有update的，但如果我们编写了一个SQL。这个SQL看起来是这样的：

SELECT `user`, SUM(money) AS total_money
FROM t_order
GROUP BY `user`;
-- user、order 都是 SQL 保留字，作为表名/列名时必须用反引号包起来

当执行一条SQL语句之后，这条语句的结果还是一个表，因为在Flink中执行的SQL是Continuous Query，这个表的数据是不断变化的。新创建的表存在Update的情况。仔细看下下面的示例，例如：

  • 第一条数据，张三,2000，执行这条SQL语句的结果是，张三,2000

  • 第二条数据，李四,1500，继续执行这条SQL语句，结果是，张三,2000 | 李四,1500

  • 第三条数据，张三,300，继续执行这条SQL语句，结果是，张三,2300 | 李四,1500

  • ….

大家发现了吗，现在数据结果是有Update的，张三一开始是2000，但后面变成了2300。

那还有删除的情况吗？有的，看下面这条SQL语句：

SELECT t1.`user`, SUM(t1.money) AS total_money
FROM t_order t1
WHERE NOT EXISTS (
    SELECT 1
    FROM t_order t2
    WHERE t2.`user` = t1.`user`
    GROUP BY t2.`user`
    HAVING SUM(t2.money) > 3000
)
GROUP BY t1.`user`;

  • 第一条数据，张三,2000，执行这条SQL语句的结果是，张三,2000

  • 第二条数据，李四,1500，继续执行这条SQL语句，结果是，张三,2000 | 李四,1500

  • 第三条数据，张三,300，继续执行这条SQL语句，结果是，张三,2300 | 李四,1500

  • 第四条数据，张三,800，继续执行这条SQL语句，结果是，李四,1500

因为张三的消费的金额已经超过了3000，所以SQL执行完后，张三是被处理掉了。从数据的角度来看，它不就是被删除了吗？

通过上面的两个示例，可以知道在Flink SQL中，对接Source的表都是Append-only的，不断地增加，执行一些SQL生成的表，这个表可能是要UPDATE的、也可能是要INSERT的。

3.2.2 对表的编码操作

我们前面说到过，表是一种逻辑结构，而Flink中的核心还是Stream，所以，Table最终还是会以Stream方式来继续处理，如果是以Stream方式处理，最终Stream中的数据有可能会写入到其他的外部系统中，例如：将Stream中的数据写入到MySQL中。

我们前面也看到了，表是有可能会UPDATE和DELETE的，那么如果是输出到MySQL中，就要执行UPDATE和DELETE语句了，而DataStream我们在学习Flink的时候就学习过了，DataStream是不能更新、删除事件的。

如果对表的操作是INSERT，这很好办，直接转换输出就好，因为DataStream数据也是不断递增的。但如果一个TABLE中的数据被UPDATE了、或者被DELETE了，如果用流来表达呢？ 因为流不可变的特征，我们肯定要对这种能够进行UPDATE/DELETE的TABLE做特殊操作。

解决方案：我们可以针对每一种操作，INSERT/UPDATE/DELETE都用一个或多个经过编码的事件来表示。例如：

  • 针对UPDATE，我们用两个操作来表达，[DELETE]数据+ [INSERT]数据。也就是先把之前的数据删除，然后再插入一条新的数据。

  • 针对DELETE，我们也可以对流中的数据进行编码，[DELETE]数据。

总体来说，我们通过对流数据进行编码，也可以告诉DataStream的下游，[DELETE]表示发出MySQL的DELETE操作，将数据删除。用[INSERT]表示插入新的数据。

3.2.3 将表转换为三种不同编码方式的流

Flink中的Table API或者SQL支持三种不同的编码方式，分别是：

  • Append-only流

  • Retract流

  • Upsert流

3.2.3.1 Append-only流

跟INSERT操作对应。这种编码类型的流针对的是只会不断新增的Dynamic Table，这种方式好处理，不需要进行特殊处理，源源不断地往流中发送事件即可。

3.2.3.2 Retract流

这种流就和Append-only不太一样，上面的只能处理INSERT，如果表会发生DELETE或者UPDATE，Append-only编码方式的流就不合适了。

Retract流有几种类型的事件类型：

  • ADD MESSAGE：这种消息对应的就是INSERT操作。

  • RETRACT MESSAGE：直译过来叫撤回消息，这种消息对应的就是DELETE操作。

我们可以看到通过ADD MESSAGE和RETRACT MESSAGE可以很好的向外部系统表达删除和插入操作，那如何进行UPDATE呢？其实RETRACT MESSAGE + ADD MESSAGE即可（先把之前的数据进行删除，然后插入一条新的）。

3.2.3.3 Upsert流

前面我们看到的RETRACT编码方式的流，实现UPDATE是使用DELETE + INSERT模式的。

大家想一下：在MySQL中我们更新数据的时候，肯定不会先DELETE掉一条数据，然后再插入一条数据，肯定是直接发出UPDATE语句执行更新。

而Upsert编码方式的流，是能够支持Update的，这种效率更高。它同样有两种类型的消息：

  • UPSERT MESSAGE：这种消息可以表示要对外部系统进行Update或者INSERT操作

  • DELETE MESSAGE：这种消息表示DELETE操作。

Upsert流是要求必须指定Primary Key的，因为Upsert操作是要有Key的，Upsert流针对UPDATE操作用一个UPSERT MESSAGE就可以描述，所以效率会更高。

3.3 时间属性与 WATERMARK

窗口、interval join、按时间去重这些能力都建立在「时间属性」之上。Flink SQL 里只有两种时间属性：事件时间（event time）和处理时间（processing time），它们都必须写在建表 DDL 中声明，声明之后才能像普通字段一样在 SQL 里使用。

3.3.1 事件时间与 WATERMARK

事件时间来自数据本身携带的时间戳，必须通过 WATERMARK 告诉 Flink「时间已经推进到哪里」，否则事件时间窗口永远不会触发：

CREATE TABLE click_source (
    user_id  BIGINT,
    url      STRING,
    ts       TIMESTAMP(3),                          -- 事件时间字段，毫秒精度
    -- 允许 5 秒乱序：水位线 = 观察到的最大事件时间 - 5 秒
    WATERMARK FOR ts AS ts - INTERVAL '5' SECOND
) WITH (
    'connector'                    = 'kafka',
    'topic'                        = 'clicks',
    'properties.bootstrap.servers' = 'hadoop102:9092',
    'properties.group.id'          = 'click-group',
    'scan.startup.mode'            = 'latest-offset',
    'format'                       = 'json'
);

三个要点：

  • WATERMARK FOR ts AS ... 中的字段必须是 TIMESTAMP(3) 或 TIMESTAMP_LTZ(3) 类型，早期版本只支持 TIMESTAMP(3)；

  • 水位线相当于一个「事件时间时钟」，只有它越过窗口的结束时间，窗口才会触发计算，所以水位线的延迟公式直接决定了结果的延迟；

  • 水位线单调递增，比当前水位线更早到达的数据属于迟到数据，窗口聚合默认会丢弃它。

3.3.2 处理时间

处理时间由计算节点在运行时生成，不需要数据自带时间戳，在 DDL 中声明成一个计算列即可：

CREATE TABLE order_source (
    user_id   BIGINT,
    money     DECIMAL(10, 2),
    proc_time AS PROCTIME()      -- 处理时间属性，原始数据中不存在这个字段
) WITH (
    'connector'                    = 'kafka',
    'topic'                        = 'orders',
    'properties.bootstrap.servers' = 'hadoop102:9092',
    'format'                       = 'json'
);

两种时间属性怎么选：处理时间实现简单、不需要等待乱序数据，但结果不可重放（同一份数据重跑结果可能不同）；事件时间结果确定、可重放，代价是要维护水位线并容忍一定乱序。生产上的统计类需求优先选事件时间。

时间戳也可以来自 DataStream：注册表时用 fromDataStream(stream, $("ts").rowtime()) 声明行时间，用 $("pt").proctime() 声明处理时间，就不必再写 DDL。

3.4 窗口 TVF（TUMBLE / HOP / CUMULATE）

Flink 1.13 起，窗口统一用「窗口表值函数」（Windowing TVF）来表达：窗口函数先把流按时间切成带 window_start、window_end 两列的关系，再与主表连接，最后按窗口聚合。相比更早的 GROUP BY TUMBLE(ts, INTERVAL '10' SECOND) 写法（自 1.13 起被标记为废弃），TVF 的语义更清晰，也支持窗口 TopN、窗口 join 等扩展用法。

三种窗口的语义差别：

  • TUMBLE（滚动窗口）：窗口等长且互不重叠，只有一个 size 参数，每条数据只属于一个窗口；

  • HOP（滑动窗口）：窗口等长但可以重叠，参数是 slide 和 size，slide < size 时一条数据会属于多个窗口，常用于「每 5 秒看一眼最近 10 秒」；

  • CUMULATE（累积窗口）：窗口从起点按 step 逐步扩大，最大到 size，适合「每小时要一个统计值，但结果每分钟都在更新」的场景。

以 3.3.1 节的 click_source 为例：

-- 事件时间滚动窗口：每 10 秒统计一次每个用户的点击量
SELECT
    user_id,
    window_start,
    window_end,
    COUNT(*) AS click_cnt
FROM TABLE(
    TUMBLE(TABLE click_source, DESCRIPTOR(ts), INTERVAL '10' SECOND)
)
GROUP BY user_id, window_start, window_end;

-- 滑动窗口：每 5 秒输出一次最近 10 秒的统计结果
SELECT user_id, window_start, window_end, COUNT(*) AS click_cnt
FROM TABLE(
    HOP(TABLE click_source, DESCRIPTOR(ts), INTERVAL '5' SECOND, INTERVAL '10' SECOND)
)
GROUP BY user_id, window_start, window_end;

-- 累积窗口：每 5 秒输出一次，窗口从 5 秒逐步累积到 15 秒
SELECT user_id, window_start, window_end, COUNT(*) AS click_cnt
FROM TABLE(
    CUMULATE(TABLE click_source, DESCRIPTOR(ts), INTERVAL '5' SECOND, INTERVAL '15' SECOND)
)
GROUP BY user_id, window_start, window_end;

使用窗口 TVF 时有几个容易踩坑的地方：

  • window_start、window_end 必须同时出现在 SELECT 和 GROUP BY 中，否则 SQL 校验不通过；

  • 事件时间窗口用事件时间字段（DESCRIPTOR(ts)），处理时间窗口用 DESCRIPTOR(proc_time)，两者不能混用；

  • 窗口默认只在触发时输出一次，需要提前看到中间结果可以打开提前触发（table.exec.emit.early-fire.enabled）；

  • 除 TUMBLE / HOP / CUMULATE 外，Flink 还提供会话窗口 TVF SESSION：按活跃间隔切分，窗口大小不固定。

3.5 连接（Join）

流上的 join 比批复杂：数据永远不会「到齐」，Flink 只能把暂时匹配不上的数据放进状态里等对方到来。所以选择哪种 join，本质上是在回答两个问题——状态能留多久、要不要查外部系统。

3.5.1 Regular Join（常规连接）

就是普通的 JOIN，两侧都可以是流，语义与批一致，但结果是回撤流：

SELECT o.order_id, o.user_id, u.user_name, o.money
FROM order_stream AS o
JOIN user_stream  AS u
  ON o.user_id = u.user_id;

两侧的输入数据都要长期保存在状态里（默认永不过期），状态会随运行时间不断增长，因此线上必须配置状态 TTL，例如 table.exec.state.ttl = 1 h；TTL 太小又会丢掉本来可以匹配上的数据。另外 regular join 只支持等值连接条件，非等值连接只能写成 CROSS JOIN + WHERE，代价更高。

3.5.2 Interval Join（区间连接）

给 join 加上时间区间约束，只保留区间内的数据，从而把「无限状态」压成「有限状态」：

SELECT o.order_id, o.user_id, o.money, p.pay_id
FROM order_stream AS o,
     pay_stream   AS p
WHERE o.user_id = p.user_id
  AND p.pay_time BETWEEN o.order_time - INTERVAL '5' MINUTE
                     AND o.order_time + INTERVAL '5' MINUTE;

使用限制：两侧都必须有事件时间属性，并且至少有一个等值连接条件，处理时间表不支持 interval join。区间越窄状态越小，但超出区间的数据无法匹配，需要按业务能接受的延迟来确定区间大小。

3.5.3 Lookup Join（维表连接）

事实流 join 外部维表（MySQL、HBase、Redis 等）时，用 FOR SYSTEM_TIME AS OF 声明「按处理时间去查维表当前的数据」，维表不需要全量进入状态：

-- 维表：JDBC connector
CREATE TABLE user_dim (
    user_id   BIGINT,
    user_name STRING,
    PRIMARY KEY (user_id) NOT ENFORCED
) WITH (
    'connector'             = 'jdbc',
    'url'                   = 'jdbc:mysql://hadoop102:3306/gmall',
    'table-name'            = 'user_info',
    'username'              = 'root',
    'password'              = '123456',
    'lookup.cache.max-rows' = '1000',
    'lookup.cache.ttl'      = '1 min'
);

-- 事实表要带处理时间属性（见 3.3.2）
SELECT o.order_id, o.user_id, d.user_name, o.money
FROM order_source AS o
JOIN user_dim FOR SYSTEM_TIME AS OF o.proc_time AS d
  ON o.user_id = d.user_id;

要点：事实表必须有处理时间属性，连接条件必须是等值条件，维表 connector 必须实现 LookupTableSource；每条事实数据到来都会查一次维表，建议开启 lookup.cache 降低外部系统压力。lookup join 的输出是追加流——维表后来发生变化，已经输出的历史结果不会被回撤重算；如果维表本身是带版本的变化流、并且希望按事件时间取当时的历史版本，则要改用 temporal join（版本表 + FOR SYSTEM_TIME AS OF 事件时间字段）。

3.6 SQL 与 DataStream 互转

SQL 擅长表达统计逻辑，而 Source / Sink 和自定义算子仍然要用 DataStream API 写，两者的边界就是 fromChangelogStream() 与 toChangelogStream()。1.13 起这两个方法是 Table 与 DataStream 之间唯一推荐的桥梁，旧的 toAppendStream() / toRetractStream() 已经废弃。

StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
StreamTableEnvironment tableEnv = StreamTableEnvironment.create(env);

// DataStream -> Table：注册成临时视图后即可用 SQL 查询
DataStream<Order> orderStream = env.addSource(new OrderSource());
tableEnv.createTemporaryView("order_source", orderStream);

// SQL -> Table
Table result = tableEnv.sqlQuery(
        "SELECT user_id, SUM(money) AS total_money FROM order_source GROUP BY user_id");

// Table -> DataStream：changelog 流，每条 Row 带 RowKind
DataStream<Row> changelogStream = tableEnv.toChangelogStream(result);
changelogStream.print("changelog");

// DataStream（Row 带 RowKind） -> Table，继续用 SQL 处理
Table table = tableEnv.fromChangelogStream(changelogStream);

两个常见问题：

  • 下游只接受追加流时，可以给 toChangelogStream() 显式传入期望的 ChangelogMode（org.apache.flink.table.connector.ChangelogMode），这样结果表一旦产生 -U/+U，规划阶段就会报错，而不是运行期才失败；

  • fromChangelogStream() 要求输入是带 RowKind 的 changelog 流（一般来自 toChangelogStream()，或实现了 changelog 语义的 connector），普通 POJO 流应先用 fromDataStream() 注册成表。
