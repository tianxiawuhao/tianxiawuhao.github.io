设计原则与 UML

Posted on 2026-09-19，9 min read

前面三章把 23 种经典模式按创建型、结构型、行为型过了一遍。但如果你只记住模式的名字，遇到新需求时依然不知道该怎么选——因为模式只是结论，原则才是推导过程。为什么工厂方法要引入工厂类层次，为什么装饰器能而代理不能在运行期层层嵌套，判断依据都藏在几条设计原则里。本章先讲三条最基本的面向对象原则，再拆开最常被面试问到的单一职责、开闭、里氏代换、依赖倒转、接口隔离、迪米特法则，最后补齐读源码必备的 UML 类图：类怎么画、六种关系分别对应哪行 Java 代码。读完再回头看 5-4 到 5-6，你会发现它们都是这些原则在不同场景下的落地。

三条基本面向对象原则

在六条具体原则之前，有三条更底层的指导思想，几乎所有模式都在反复使用它们。

第一，针对接口编程，而不是针对实现编程。变量的声明类型应该是接口或抽象类，而不是具体实现。这样换实现时调用方一行都不用改，也方便在测试里替换成桩对象。集合框架就是最好的例子：List<String> list = new ArrayList<>()，左边是抽象、右边是具体，日后换成 LinkedList 只需改一处。

第二，优先使用对象组合，而不是类继承。继承是编译期就固定下来的白盒复用，父类的内部实现对子类完全暴露；组合是运行期可替换的黑盒复用，只需知道对方暴露的接口。继承层次一旦超过两三层，父类任何改动都会波及所有子类，这就是所谓的「继承脆弱性」。策略模式、装饰器模式、桥接模式本质上都是用组合替换继承的产物。

第三，封装变化点。找出程序中会变化的部分，把它抽出来独立封装，不要让它会污染稳定的部分。如果一段逻辑永远不会变，为它引入抽象就是纯粹的负担——拒绝不成熟的抽象，和抽象本身一样重要。

六大设计原则：每条都配一个反例

六条原则里前五条通常缩写为 SOLID，最后一条是迪米特法则。下面每条都从一个真实代码坏味道出发，而不是从定义出发。

单一职责原则（SRP）：一个类只有一个变化原因

反例很常见：一个 ReportService 既负责拼装报表数据，又负责导出 PDF，还负责发邮件。看起来「功能集中、方便调用」，实际上它有三个变化原因——业务字段变了要改它，PDF 模板换了要改它，邮件网关换了还要改它。三个不相关的需求挤在一个类里，改动时的回归测试成本成倍上升。

判断标准不是「这个类有多少行代码」，而是「这个类会因为几个不同的原因被修改」。拆分的收益是每个类的测试范围变小、复用变容易；代价是类数量增加，所以也不要把每个方法都拆成一个类。实践中一条经验：如果描述这个类的职责时用到了「并且」「同时」，基本就该拆了。

开闭原则（OCP）：对扩展开放，对修改关闭

开闭原则说的是软件实体应该可以扩展，但不必修改原有代码。它的落地手段只有一个：把变化点抽象出来，新增行为时是加类，而不是改 if-else。

// 违反开闭：每加一种支付方式都要改这个方法，还要重新测试所有分支
public class PaymentService {
    public void pay(String type, BigDecimal amount) {
        if ("alipay".equals(type)) {
            // 支付宝逻辑
        } else if ("wechat".equals(type)) {
            // 微信逻辑
        } else if ("unionpay".equals(type)) {
            // 银联逻辑（新增，老方法被动变长）
        } else {
            throw new IllegalArgumentException("不支持的支付方式: " + type);
        }
    }
}

// 遵守开闭：把「怎么支付」抽成接口，新增渠道只需新增一个类
public interface PaymentChannel {
    String name();                       // 渠道标识，供工厂或注册表使用
    void pay(BigDecimal amount);         // 各渠道各自的实现
}

public class AlipayChannel implements PaymentChannel {
    @Override
    public String name() {
        return "alipay";
    }

    @Override
    public void pay(BigDecimal amount) {
        System.out.println("支付宝支付 " + amount);
    }
}

public class PaymentService {
    private final Map<String, PaymentChannel> channels = new HashMap<>();

    /** 注册渠道：新增渠道时业务类一行不改 */
    public void register(PaymentChannel channel) {
        channels.put(channel.name(), channel);
    }

    public void pay(String type, BigDecimal amount) {
        PaymentChannel channel = channels.get(type);
        if (channel == null) {
            throw new IllegalArgumentException("不支持的支付方式: " + type);
        }
        channel.pay(amount);
    }
}

需要强调：完全对修改关闭是不可能的。任何设计都必须对某类变化封闭，设计者的工作就是预判最可能变化的那类需求，只对它建立抽象。上面的改造并非消灭了 if，而是把「判断哪个渠道」和「渠道怎么支付」解耦：判断退化成一次查表，新增渠道只影响新类。

里氏代换原则（LSP）：子类型必须能替换父类型

里氏代换原则要求：凡是使用父类的地方，换成子类后程序行为不能出问题。它是继承复用的基石——只有子类能无缝替换父类，父类的代码才真正被复用了。

public class Rectangle {
    protected int width;
    protected int height;

    public void setWidth(int width) {
        this.width = width;
    }

    public void setHeight(int height) {
        this.height = height;
    }

    public int area() {
        return width * height;
    }
}

// 经典反例：正方形「是」矩形在数学上成立，在行为约定上不成立
public class Square extends Rectangle {
    @Override
    public void setWidth(int width) {
        this.width = width;
        this.height = width;   // 强行保持正方形，破坏了父类「宽高独立」的约定
    }

    @Override
    public void setHeight(int height) {
        this.height = height;
        this.width = height;
    }
}

// 调用方按父类约定写代码：设置宽高各一次，期望面积 = 4 * 5
public class AreaCalculator {
    public static int calculate(Rectangle rectangle) {
        rectangle.setWidth(4);
        rectangle.setHeight(5);
        return rectangle.area();   // 传入 Square 时返回 25，而不是 20
    }
}

常见违反信号有三个：子类重写方法后抛出父类没有声明的异常、子类把父类方法改成空实现、子类收紧了参数或放宽了返回值语义。判断方法是「基类契约」，不是「现实世界的 is-a」。正方形与矩形、鸵鸟与鸟都是教科书级别的不适用继承的例子，正确处理是让两者实现同一个接口，而不是互相继承。

依赖倒转原则（DIP）：依赖抽象，不依赖具体

依赖倒转包含两层意思：高层模块不应该依赖低层模块，两者都应该依赖抽象；抽象不应该依赖细节，细节应该依赖抽象。通俗说就是「针对接口编程」，它也是开闭原则得以实现的基础。

// 违反依赖倒转：高层业务直接依赖具体的低层实现，换数据库要改业务代码
public class OrderService {
    private final MysqlOrderRepository repository = new MysqlOrderRepository();
}

// 遵守依赖倒转：业务依赖接口，具体实现由外部注入
public interface OrderRepository {
    void save(Order order);

    Optional<Order> findById(Long id);
}

public class OrderService {
    private final OrderRepository repository;

    /** 构造器注入：依赖从外部传入，实现可替换、可 mock */
    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    public void create(Order order) {
        repository.save(order);
    }
}

Spring 的整个 IoC 容器就是依赖倒转的工程化实现：类里只声明接口，具体实现由容器在启动时注入。不要把依赖倒转等同于「依赖注入」——注入只是手段，倒转的是依赖的方向，让高层模块不再被低层实现绑死。

接口隔离原则（ISP）：别强迫客户依赖不用的方法

接口隔离原则主张用多个专门的接口，而不是一个包罗万象的胖接口。接口属于它的客户，不属于实现它的类层次。

// 胖接口：把打印、扫描、传真塞在一个接口里
public interface MultiFunctionDevice {
    void print(String content);

    void scan();

    void fax(String number);
}

// 只有打印功能的设备被迫实现用不到的方法，只能抛异常或空实现
public class SimplePrinter implements MultiFunctionDevice {
    @Override
    public void print(String content) {
        System.out.println("打印: " + content);
    }

    @Override
    public void scan() {
        throw new UnsupportedOperationException("本机不支持扫描");
    }

    @Override
    public void fax(String number) {
        throw new UnsupportedOperationException("本机不支持传真");
    }
}

// 按能力拆成小接口，谁需要谁实现
public interface Printer {
    void print(String content);
}

public interface Scanner {
    void scan();
}

胖接口最典型的危害是：连只用到 print() 的客户，也不得不随接口里其他方法的签名变化而重新编译。实践中的信号是「实现类里出现大量抛 UnsupportedOperationException 的方法」或者「测试里要为无关方法写空桩」。

迪米特法则（LoD）：只和直接朋友通信

迪米特法则又叫最少知识原则：一个对象应该对其它对象知道得尽可能少，只与直接朋友（字段、方法参数、自己创建的对象）通信，不要跟「陌生人的朋友」打交道。

// 违反迪米特：调用方穿透三层对象，任何中间类的结构变动都会破坏这行代码
String cityCode = order.getCustomer().getAddress().getCity().getCode();

// 遵守迪米特：由直接朋友提供一次到位的服务
String cityCode = order.getCustomerCityCode();

// Customer 内部再去委托 Address，链式调用被收敛在各自的边界内
public class Customer {
    private Address address;

    public String getCityCode() {
        return address == null ? null : address.getCityCode();
    }
}

迪米特法则的两个常见误区：第一，它并非禁止链式调用，StringBuilder 那种「每次返回自身」的流式 API 完全不违反它，因为链上始终是同一个对象；第二，它强调的是降低耦合，不是把所有方法都做成转发，过度使用会制造一堆毫无含义的包装方法。

UML 类图：把设计画成大家都能读懂的图

设计模式是团队沟通的词汇，而 UML 类图是描述这些词汇的语法。读源码、看框架文档、面试白板题都离不开它，所以它比记住任何一个具体模式都更基础。

类与接口的画法

类用一个矩形表示，分三层：第一层是类名，第二层是属性（字段），第三层是方法。类名用斜体表示抽象类；成员前面的符号 + 表示 public、- 表示 private、# 表示 protected。下面这个抽象类和它的实现类，画成 UML 就是两个矩形加一条空心三角箭头：

public abstract class Animal {
    protected String name;                 // # name : String

    public abstract void move();           // + move() : void
}

public class Duck extends Animal {
    private double wingspan;               // - wingspan : double

    @Override
    public void move() {
        System.out.println("游泳");
    }
}

接口有两种画法：矩形表示法在顶层写 <<interface>>，第一行是接口名，第二行是方法；棒棒糖表示法画一个小圆圈连一条实线，圆圈旁写接口名，接口方法写在实现类里。实际交流中，接口少时用棒棒糖更清爽，接口方法多时用矩形更完整。

六种关系：符号与 Java 代码的对应

类图里真正有信息量的是类与类之间的连线。六种关系按耦合从强到弱排下来，正好覆盖了 Java 里所有「两个类发生联系」的方式。

// 1. 继承（泛化）：实线 + 空心三角，箭头指向父类 → extends
public class Duck extends Animal { }

// 2. 实现：虚线 + 空心三角，箭头指向接口 → implements
public class Duck implements Flyable { }

// 3. 关联：实线（可带箭头与多重度），通常是成员变量 → 字段持有引用
public class Order {
    private Customer customer;            // 1 个订单关联 1 个客户
    private List<OrderItem> items;        // 1 个订单关联 0..* 个明细
}

// 4. 聚合：空心菱形 + 实线，整体与部分可分离 → 部分由外部传入
public class ParkingLot {
    private List<Car> cars = new ArrayList<>();

    public void park(Car car) {           // Car 在停车场之外也能独立存在
        cars.add(car);
    }
}

// 5. 组合：实心菱形 + 实线，生命周期同步 → 整体自己创建部分
public class Bird {
    private final List<Wing> wings = new ArrayList<>();

    public Bird() {
        wings.add(new Wing());
        wings.add(new Wing());            // 鸟不存在了，翅膀也没有意义
    }
}

// 6. 依赖：虚线 + 箭头，方法级临时使用 → 参数、局部变量、静态调用
public class ReportGenerator {
    public String generate(ReportTemplate template) {   // 只在这里用到
        return template.render();
    }
}

多重度、读图顺序与常见误画

关联线的两端可以标注多重度，用来表达数量约束：1 表示恰好一个，0..1 表示零或一个，* 或 0..* 表示零到多个，1..* 表示至少一个。多重度不是装饰，它直接决定代码里该用单个引用还是集合。

读一张类图，建议按固定顺序：先找抽象层（斜体类名、<<interface>>），再顺着空心三角看继承链，然后看实心菱形找到强组合关系，最后看虚线箭头找出方法级的临时依赖。三个最常见的画错是：把「聚合」画成「组合」（差别在于部分对象能否脱离整体独立存在）、把「依赖」画成「关联」（只在方法参数里出现过就不该画成字段）、把多重度写成实现类数量（多重度说的是某一时刻的实例数量关系，不是有多少个子类）。

回到模式：先守原则，再挑模式

原则与模式的关系可以用一句话概括：原则是判断标准，模式是被反复验证过的答案。桥接与适配器的选择、代理与装饰器的区别、策略与模板方法的取舍，本质上都在回答同一个问题——变化点在哪里，我该把哪一部分抽象出来。

把本章的原则代入前面三章的结论，很多「记不住、容易混」的地方会有统一解释：

  • 单例常被滥用，是因为它把「实例数量」这个变化点固定死了，同时引入全局可变状态，违反了「只和直接朋友通信」——所以无状态工具类应优先用静态方法。
  • 策略、观察者、责任链都是「封装变化点」的具体形态，分别封装了算法、通知对象和处理者链；它们能成立，靠的是依赖倒转——环境类依赖接口而不是具体实现。
  • 装饰器能层层嵌套、代理不能，是因为装饰器由客户端把原对象传进构造器（典型组合复用），而代理的内部实现在编译期就固定了。
  • 桥接与抽象工厂常一起出现，因为两者都在处理「两个或多个变化维度」，一个拆结构、一个拆产品族，都是为了避免继承层次呈乘积式膨胀。

实践建议只有三条：先写出能跑的简单版本，识别出真正会变化的那一处，再用最小代价抽象它。任何为了「将来可能扩展」而提前引入的模式，大概率都会变成维护负担——这也是开闭原则的另一面：拒绝不成熟的抽象，和不做抽象一样重要。

小结：三条基本面向对象原则给出了方向（针对接口编程、优先组合、封装变化点），六条具体原则给出了判断标准（单一职责看变化原因、开闭看能否只加类、里氏看能否替换父类、依赖倒转看依赖的方向、接口隔离看是否强迫客户、迪米特看是否只跟直接朋友通信），UML 类图给出了沟通语法。掌握这三层，再回头读 23 种模式，就不再是背名字，而是看它们在守哪条原则。
