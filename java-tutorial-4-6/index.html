Spring MVC

Posted on 2026-09-19，9 min read

上一章我们把 Spring 的 IoC 与 AOP 讲清楚了，这一章开始进入 Web 层。很多人用 Spring MVC 很久，却只记得「写个 @RequestMapping 就能跑」，一旦遇到参数收不到、拦截器不生效、异常直接变成 500 页面，就无从下手。本章要解决的问题就是：把一个 HTTP 请求从进入容器到返回响应这条链路讲透，并且说清楚参数绑定、拦截器、异常处理这三件最常用的扩展点各自插在链路的哪一环。适合已经会写 Spring 配置、准备做真实 Web 项目的读者。

一、一个请求的完整旅程：DispatcherServlet 到底做了什么

Spring MVC 也是 Servlet 技术栈上的一层封装，它只注册了一个 Servlet，也就是前端控制器 DispatcherServlet。所有请求先到它手里，再由它去「找方法、调方法、渲染视图」。注册方式很简单：在 web.xml 里声明它并配上 url-pattern，load-on-startup 设为 1 可以让它在容器启动时就初始化，而不是等第一个请求来了才初始化。

它默认读取的配置文件是 /WEB-INF/{servlet-name}-servlet.xml，所以当 servlet-name 取 springmvc 时，配置文件就必须叫 springmvc-servlet.xml；当然也可以用 contextConfigLocation 这个初始化参数显式指定别的路径。

请求进来之后的流程，可以拆成六步：

  1. DispatcherServlet 收到请求，交给 HandlerMapping（处理器映射器）按 URL 查找能处理它的 Handler。
  2. HandlerMapping 返回的不是光秃秃的 Handler，而是 HandlerExecutionChain——里面装着 Handler 对象，以及匹配到的一组拦截器。这就是理解拦截器的前提：拦截器是跟着 Handler 一起返回的。
  3. DispatcherServlet 拿着 Chain 依次调用拦截器的 preHandle，任何一次返回 false，流程立刻终止。
  4. 放行后由 HandlerAdapter（处理器适配器）去真正调用 Handler 方法。为什么要适配器？因为 Handler 的写法不止一种（实现 Controller 接口、注解方法等），适配器负责让统一的调用接口适配不同写法。
  5. 方法返回 ModelAndView（或方法名对应的逻辑视图名），再由 ViewResolver（视图解析器）把逻辑视图名解析成真实视图，例如 prefix + viewName + suffix 拼出 /WEB-INF/views/hello.jsp。
  6. 渲染视图写回响应，最后逆序执行拦截器的 postHandle 与 afterCompletion。

一句话总结：DispatcherServlet 是调度者，HandlerMapping 负责「找」，HandlerAdapter 负责「调」，ViewResolver 负责「渲染」，拦截器负责在「调」的前后插逻辑。理解了这五个角色的分工，后面所有配置项都能对上号。

二、参数绑定：请求数据怎么落到方法形参上

Spring MVC 最省心的地方是参数绑定：方法形参的顺序无所谓，只要名字和类型对得上，前端传来的数据就会被自动填进去。常见有五种场景。

普通参数用 @RequestParam 显式声明：required 默认为 true，请求里缺这个参数会直接抛异常（表现为 400）；一旦设置了 defaultValue，required 就自动失效变成 false，缺参数时用默认值兜底。路径占位符用 @PathVariable，@RequestMapping("/user/{id}") 里的名字必须和注解中的名字一致，而方法形参名可以随便取。POJO 不需要任何注解，Spring MVC 会把参数名和实体属性的 setter 自动匹配，还支持 user.dept.id 这种级联写法。Servlet 内置对象（HttpServletRequest、HttpServletResponse、HttpSession）只要出现在形参列表里就能拿到。最后是 JSON：@RequestBody 负责把请求体里的 JSON 反序列化成对象，@ResponseBody 负责把返回值写回响应体。

@Controller
@RequestMapping("/user")
public class UserController {

    // 1. 普通参数：page 缺省时用 1，keyword 必填
    @RequestMapping("/list")
    @ResponseBody
    public List<String> list(@RequestParam("keyword") String keyword,
                             @RequestParam(value = "page", defaultValue = "1") int page) {
        return userService.search(keyword, page);
    }

    // 2. 路径占位符：/user/42/detail
    @RequestMapping("/{id}/detail")
    @ResponseBody
    public User detail(@PathVariable("id") Long id) {
        return userService.findById(id);
    }

    // 3. POJO 自动绑定 + 级联：name=Tom&dept.id=3
    @RequestMapping("/save")
    @ResponseBody
    public User save(User user) {
        return userService.save(user);
    }

    // 4. JSON 请求体：Content-Type 必须是 application/json
    @RequestMapping(value = "/update", method = RequestMethod.POST)
    @ResponseBody
    public User update(@RequestBody User user) {
        return userService.update(user);
    }
}

这里有个容易被笔记带偏的点：@ResponseBody 并不等于「转成 JSON」。它真正的含义是「返回值不走视图解析，而是交给 HttpMessageConverter 写进响应体」，写出来是 JSON 还是 XML，取决于请求的 Accept 和项目里注册了哪个消息转换器。如果只写了注解却没引入 Jackson 依赖，运行时会因找不到可用的转换器而报错（典型是 406 或 HttpMediaTypeNotAcceptableException），这也是「本地跑得好、换环境就挂」的常见原因。

三、拦截器：在 Handler 前后插入横切逻辑

拦截器实现 HandlerInterceptor 接口，三个方法对应三个时机：preHandle 在 Handler 执行前调用，返回值决定是否放行；postHandle 在 Handler 执行后、视图渲染前调用；afterCompletion 在视图渲染完成后调用，相当于清理现场，而且它的形参里有 Exception ex，非常合适合计耗时、记日志。

执行顺序必须记牢：多个拦截器的 preHandle 按配置顺序依次执行，而 postHandle 与 afterCompletion 按相反顺序执行——像一层层进出门，先进后出。另外要区分两种情况：某个 preHandle 返回 false 时，它自己以及排在它后面的拦截器和 Handler 都不会执行，但之前已经放行（返回过 true）的拦截器，其 afterCompletion 仍会逆序执行，而 postHandle 不会执行。

public class LoginInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) throws Exception {
        HttpSession session = request.getSession(false);
        if (session == null || session.getAttribute("username") == null) {
            // 未登录：拦截并跳转，返回 false 终止后续流程
            response.sendRedirect(request.getContextPath() + "/login.html");
            return false;
        }
        return true;
    }

    @Override
    public void postHandle(HttpServletRequest request, HttpServletResponse response,
                           Object handler, ModelAndView modelAndView) throws Exception {
        // Handler 执行完、视图渲染前，可往 model 里补公共数据
        if (modelAndView != null) {
            modelAndView.addObject("appName", "TianXiaWuHao");
        }
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) throws Exception {
        // 视图渲染完成（或流程异常结束）后执行，适合释放资源、记录耗时
        if (ex != null) {
            System.out.println("request finished with exception: " + ex.getMessage());
        }
    }
}

写完类还要注册才会生效，XML 与 Java 配置二选一。注意路径写 /**（匹配所有层级）而不是 /*（只匹配一层），这是新手最常踩的坑。

<!-- springmvc-servlet.xml：注册拦截器 -->
<mvc:interceptors>
    <mvc:interceptor>
        <!-- 拦截所有请求；只想拦截部分路径时可写 /admin/** -->
        <mvc:mapping path="/**"/>
        <!-- 放行登录页与登录接口 -->
        <mvc:exclude-mapping path="/login.html"/>
        <mvc:exclude-mapping path="/user/login"/>
        <bean class="cn.itcast.springmvc.interceptor.LoginInterceptor"/>
    </mvc:interceptor>
</mvc:interceptors>

顺便纠正一个常见的以讹传讹：不少 Struts2 笔记里写「拦截器不依赖 Servlet 容器，过滤器才依赖」。那是 Struts2 拦截器的情况；在 Spring MVC 里，HandlerInterceptor 的方法签名直接要求 HttpServletRequest/HttpServletResponse，它本身就是 Servlet 体系的一部分。真正稳妥的区分是：Filter 由 Servlet 容器管理，作用于 URL 而不认识你写的方法；Interceptor 由 Spring 容器管理，作用在 Handler 上，因此能拿到 Handler 方法信息、能读写 Spring 的 model。需要改请求体、改编码、做全局跨域时用 Filter；需要登录校验、权限、按方法埋点时用 Interceptor。

四、异常处理：让所有错误有统一的出口

Handler 里抛出的异常如果没人管，会一路抛回 Servlet 容器，用户看到的是容器默认的 500 错误页。工程化的做法是用 Spring MVC 提供的异常解析机制接管它。默认情况下，DispatcherServlet 会依次尝试三个解析器：ExceptionHandlerExceptionResolver（处理 @ExceptionHandler）、ResponseStatusExceptionResolver（处理 @ResponseStatus）、DefaultHandlerExceptionResolver（兜住框架自身的标准异常），所以自定义的 @ExceptionHandler 通常最先命中。

@ExceptionHandler 写在某个 Controller 里只对该 Controller 生效，写在 @ControllerAdvice 标注的类里就变成全局处理。匹配时遵循「更具体的异常类型优先」的原则，所以同一个类里可以同时写 BusinessException 和 Exception 两个方法做兜底分层。

@ControllerAdvice
public class GlobalExceptionHandler {

    // 业务异常：返回统一 JSON 错误体，HTTP 状态仍是 200
    @ExceptionHandler(BusinessException.class)
    @ResponseBody
    public Map<String, Object> handleBusiness(BusinessException e) {
        Map<String, Object> body = new HashMap<>();
        body.put("code", e.getCode());
        body.put("msg", e.getMessage());
        return body;
    }

    // 兜底：非预期异常记日志，并给出友好的错误页
    @ExceptionHandler(Exception.class)
    public ModelAndView handleOthers(Exception e) {
        log.error("unexpected error", e);
        ModelAndView mv = new ModelAndView("error/500");
        mv.addObject("message", "服务暂时不可用，请稍后再试");
        return mv;
    }
}

注意两个细节：一是 @ResponseBody 与返回 ModelAndView 是两条路，全局处理器里通常混用，别在同一个方法上同时用；二是异常被拦截器或 Controller 里的 try/catch 吞掉之后，异常处理器就再也看不到它了——要么别吞，要么在 catch 里重新抛出，否则日志里一片安静，线上排查会极其痛苦。在纯 XML 项目中，还可以用 SimpleMappingExceptionResolver 把异常类型映射到错误页面，效果类似，适合老项目改造。

五、常见坑与小结

最后集中列几个高频问题。静态资源 404：DispatcherServlet 的 url-pattern 写成 / 时会接管所有请求（不含 JSP），图片、CSS 也会被当成 Handler 去找，此时需要加 <mvc:default-servlet-handler/> 或 <mvc:resources/> 把它们交还给默认 Servlet；写成 *.do 则不会有这个问题，但 URL 会带后缀。拦截器不生效：先确认路径是 /**、确认拦截器类被 Spring 扫描到，再确认请求确实匹配了 @RequestMapping。参数收不到：@RequestParam 名称写错会直接 400，@RequestBody 忘记设置 Content-Type: application/json 会 415，两条报错含义完全不同，按状态码定位很快。响应已提交：在 postHandle 里再往响应写数据已经晚了，因为视图即将渲染，这类逻辑应放到 preHandle。

小结一下：Spring MVC 的请求链路是「DispatcherServlet → HandlerMapping（返回 Handler + 拦截器链）→ 拦截器 preHandle → HandlerAdapter 调用 Handler（参数绑定在此发生）→ ViewResolver 渲染 → 拦截器逆序收尾」；异常则在链路任何一环抛出后，统一由 @ExceptionHandler / @ControllerAdvice 接住。抓住这条主线，注解、配置、拦截器、异常处理器各自的位置就都清楚了，下一章我们在此基础上讲 RESTful 接口设计与数据校验。
