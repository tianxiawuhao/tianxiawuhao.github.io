定时任务与实时推送

Posted on 2026-09-19，10 min read

有两类需求几乎每个业务系统都会遇到：一是「到点自动做一件事」，比如活动到期自动下架、订单超时自动关闭、每天凌晨跑对账；二是「服务端主动把消息告诉浏览器」，比如站内通知、客服消息、实时进度。前者靠定时任务，后者靠服务端推送。本章把这两块放在一起讲：定时任务从 JDK 自带的调度器讲到 Quartz 与集群防重，推送从轮询讲到 WebSocket 与集群广播。5-13 讲的 Git 属于交付链路，本章则是运行期的定时与实时能力。

定时任务：从 JDK 自带调度器开始

很多人第一反应是 java.util.Timer，但它在生产代码里几乎不该出现，原因有四条：它是单线程执行，一个任务卡住会拖住其它任务；任务抛出未捕获异常会直接终止整个 Timer，后续调度全部失效；它按绝对时间计算，系统时间被改动会影响调度；任务列表只在内存里，重启即丢。

import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.TimeUnit;

/** 单机小任务的推荐写法：线程池版调度器，一个任务异常不影响其它任务 */
public class SchedulerDemo {

    public static void main(String[] args) {
        ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2);

        // 固定频率：以上一次「开始执行」的时刻为基准计算下一次（任务耗时超过周期会顺延）
        scheduler.scheduleAtFixedRate(() -> {
            try {
                System.out.println("每 5 秒执行一次: " + System.currentTimeMillis());
            } catch (Exception e) {
                // 必须自己兜住异常，否则线程池会吞掉后续调度
                System.out.println("任务异常: " + e.getMessage());
            }
        }, 0, 5, TimeUnit.SECONDS);

        // 固定延迟：以上一次「执行结束」的时刻为基准，适合不允许并发执行的任务
        scheduler.scheduleWithFixedDelay(() -> System.out.println("上次结束后再等 3 秒"), 0, 3, TimeUnit.SECONDS);
    }
}

注意 scheduleAtFixedRate 与 scheduleWithFixedDelay 的区别：前者按固定节奏，任务执行时间超过周期时下一次会立刻开始；后者总是等上一次执行完再计时，不容易造成任务堆积。另外这个调度器不支持 cron 表达式，也不会持久化任务，而且多节点部署时会每个节点各跑一遍，这正是需要 Quartz 一类框架的原因。

Quartz：Job、Trigger、Scheduler 三件套

Quartz 把「做什么」和「什么时候做」彻底拆开：Job 只写业务逻辑，Trigger 描述触发时间表，Scheduler 负责把两者绑定并驱动执行。

import org.quartz.CronScheduleBuilder;
import org.quartz.Job;
import org.quartz.JobBuilder;
import org.quartz.JobDetail;
import org.quartz.JobExecutionContext;
import org.quartz.Scheduler;
import org.quartz.Trigger;
import org.quartz.TriggerBuilder;
import org.quartz.impl.StdSchedulerFactory;

/** 1. 工作任务：只关心「做什么」，不关心「什么时候做」 */
public class PromotionExpireJob implements Job {

    @Override
    public void execute(JobExecutionContext context) {
        // 通过 JobDataMap 接收外部传入的参数
        String promotionId = context.getJobDetail().getJobDataMap().getString("promotionId");
        System.out.println("检查活动是否到期并下架: " + promotionId);
    }
}

public class QuartzDemo {

    public static void main(String[] args) throws Exception {
        // 2. 创建 JobDetail：任务的「实例定义」，可以携带参数
        JobDetail jobDetail = JobBuilder.newJob(PromotionExpireJob.class)
                .withIdentity("promotionExpireJob", "marketing")   // name + group
                .usingJobData("promotionId", "P20260919")
                .build();

        // 3. 创建 Trigger：这里用 cron，每天凌晨 2 点执行
        Trigger trigger = TriggerBuilder.newTrigger()
                .withIdentity("promotionExpireTrigger", "marketing")
                .withSchedule(CronScheduleBuilder.cronSchedule("0 0 2 * * ?"))
                .build();

        // 4. 交给 Scheduler 调度
        Scheduler scheduler = StdSchedulerFactory.getDefaultScheduler();
        scheduler.scheduleJob(jobDetail, trigger);
        scheduler.start();   // 启动后调度线程开始工作；standby() 暂停，shutdown() 关闭
    }
}

几个容易踩的点。第一，Job 实例会被复用：Quartz 默认每次执行都新建实例，但如果 Job 类上标了 @DisallowConcurrentExecution，同一 JobDetail 的多次触发会串行执行，避免并发重入；如果 Job 类里有可变成员变量，务必加 @PersistJobDataAfterExecution 或干脆写成无状态类。第二，Job 里不要抛未捕获异常，否则该次执行失败并可能影响后续触发，正确做法是内部 try-catch 并记录日志。第三，cron 表达式以「秒」开头，共 6 或 7 位，与 Linux crontab 的 5 位不同。

Quartz cron 格式：秒 分 时 日 月 周 [年]

0 0 2 * * ?          每天 02:00:00 执行
0 */5 * * * ?        每 5 分钟执行一次
0 0 9 ? * MON-FRI    周一到周五 09:00 执行
0 30 8 1 * ?         每月 1 日 08:30 执行
0 0 0 L * ?          每月最后一天 00:00 执行（L 表示 Last）

注意：日和周不能同时指定，其中一个必须写 ?（Quartz 的强制约定）
     与 Linux crontab 的区别：crontab 是「分 时 日 月 周」五位，没有秒

还要理解 Misfire（错失触发）：任务该执行时线程池被占满、应用正在重启或宕机，Quartz 会记录一次「错失」。不同 Trigger 有不同的补偿策略，例如 withMisfireHandlingInstructionFireNow() 表示错过后立即补执行一次，...DoNothing() 表示直接跳过。对账、扣款这类任务应选择补执行，而「每天 8 点推送早报」这类任务跳过更合理。

Spring 的 @Scheduled：单体项目最省事

Spring Boot 项目里如果只是单体应用，用 @Scheduled 就够了，不必引入 Quartz。

import org.springframework.scheduling.annotation.EnableScheduling;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

@EnableScheduling              // 启动类或配置类上加一次即可
@Component
public class OrderTimeoutTask {

    /** fixedDelay 以「上次执行结束」为基准，比 fixedRate 更安全 */
    @Scheduled(fixedDelay = 60_000, initialDelay = 10_000)
    public void closeTimeoutOrders() {
        System.out.println("关闭超时未支付订单");
    }

    /** 也可以用 cron，Spring 的 cron 是 6 位（秒 分 时 日 月 周） */
    @Scheduled(cron = "0 0 3 * * ?")
    public void dailyReconcile() {
        System.out.println("每日对账");
    }
}

三个必须知道的坑：@Scheduled 默认只有一个调度线程，多个任务会互相等待，任务多时要配置 spring.task.scheduling.pool.size；同一个任务在多实例部署时会重复执行，这是集群环境最典型的事故；任务方法不能有参数、不能是 private，否则不生效。此外它没有重试、没有执行历史、没有可视化界面，任务一多就该考虑专业调度平台。

集群下如何保证任务只执行一次

多节点部署时，每个节点的调度器都会触发同一个任务，活动会被下架多次、消息会重复发送。解决思路有三种，复杂度递增。

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Component;

/** 思路一：数据库「抢锁」——用 UPDATE 的影响行数判断谁抢到了这次执行权 */
@Component
public class DbLockScheduler {

    private final JdbcTemplate jdbcTemplate;

    public DbLockScheduler(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    /** 每分钟尝试抢占「今天的对账任务」 */
    public void tryRun(String taskName, String runDate) {
        // 先确保记录存在（唯一索引：task_name + run_date）
        jdbcTemplate.update(
                "INSERT IGNORE INTO sys_task_lock(task_name, run_date, status) VALUES (?, ?, 0)",
                taskName, runDate);
        // 只有把 status 从 0 成功改为 1 的那个节点，影响行数为 1
        int updated = jdbcTemplate.update(
                "UPDATE sys_task_lock SET status = 1, owner = ? WHERE task_name = ? AND run_date = ? AND status = 0",
                currentNodeId(), taskName, runDate);
        if (updated == 1) {
            doBusiness();      // 抢到了才执行
        }
    }

    private String currentNodeId() {
        return "node-" + System.currentTimeMillis();
    }

    private void doBusiness() {
        System.out.println("执行对账任务");
    }
}

这条路线的要点是用数据库的原子性做互斥，靠唯一索引 + 条件更新保证只有一个节点改成功，不依赖任何中间件。第二种是 Redis 分布式锁：SET key value NX PX 30000 抢锁，执行期间要续期，释放时要用 Lua 脚本校验持有者，避免误删他人的锁。第三种是直接用专业调度平台：XXL-JOB、ElasticJob 自带调度中心、失败重试、分片执行（把一个大任务拆到多台机器并行）、执行日志与可视化界面，是中大型项目的常规选择。技术选型的经验是：只有几个简单定时任务就用 @Scheduled + 数据库锁；任务数量上规模、需要运维可视化与分片，就直接上 XXL-JOB，不要自己造轮子。

服务端推送：四种方案怎么选

「服务端主动通知浏览器」并不只有 WebSocket 一条路，四种方案各有适用区间。

选型判断可以按三句话走：只推不收（进度条、日志流、AI 逐字输出）用 SSE，它基于普通 HTTP、自带断线重连、服务端实现最简单；要双向交互（IM、协同编辑、行情下单）用 WebSocket；兼容性优先或消息稀疏（扫码登录结果通知）用长轮询；消息极少变化且能容忍分钟级延迟（未读红点）用短轮询最省事。

WebSocket 省在哪里？一次 HTTP 请求要带上几百字节到几 KB 的请求头与 Cookie，若每秒轮询一次、在线一万用户，就是每秒一万次请求和相应带宽；而 WebSocket 只在握手时用一次 HTTP，之后走极简的帧协议，头部开销只有 2～14 字节。握手的本质是一次「协议升级」：客户端发 GET 请求带 Upgrade: websocket 与 Sec-WebSocket-Key，服务端返回 101 Switching Protocols 与按固定算法算出的 Sec-WebSocket-Accept，连接从此升级为 TCP 长连接。

Spring Boot 实现 WebSocket 推送

Spring 提供了两种写法：偏底层的 WebSocketHandler（完全控制消息格式）和基于 STOMP 的消息代理（自带订阅、广播语义）。做站内通知、简单 IM 时，前者已经足够。

import java.io.IOException;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import org.springframework.stereotype.Component;
import org.springframework.web.socket.CloseStatus;
import org.springframework.web.socket.TextMessage;
import org.springframework.web.socket.WebSocketSession;
import org.springframework.web.socket.handler.TextWebSocketHandler;

/** 用 Map 保存「用户 → 会话」，参考笔记里用 ArrayList 存会话会导致只能广播、无法定向推送 */
@Component
public class NoticeWebSocketHandler extends TextWebSocketHandler {

    private final Map<String, WebSocketSession> sessions = new ConcurrentHashMap<>();

    /** 连接建立：把会话与当前登录用户绑定 */
    @Override
    public void afterConnectionEstablished(WebSocketSession session) {
        String userId = currentUserId(session);       // 握手拦截器里放进 attributes
        sessions.put(userId, session);
        send(session, "连接成功，当前在线: " + sessions.size());
    }

    /** 收到客户端消息：处理业务，例如心跳或拉取离线消息 */
    @Override
    protected void handleTextMessage(WebSocketSession session, TextMessage message) throws IOException {
        if ("ping".equals(message.getPayload())) {    // 心跳，直接回 pong
            session.sendMessage(new TextMessage("pong"));
            return;
        }
        System.out.println("收到 " + currentUserId(session) + " 的消息: " + message.getPayload());
    }

    /** 连接关闭：必须清理，否则会内存泄漏并导致推送失败 */
    @Override
    public void afterConnectionClosed(WebSocketSession session, CloseStatus status) {
        sessions.remove(currentUserId(session));
    }

    /** 定向推送：找出目标用户的会话并发送 */
    public boolean sendToUser(String userId, String payload) throws IOException {
        WebSocketSession session = sessions.get(userId);
        if (session == null || !session.isOpen()) {
            return false;      // 用户不在线，应落到离线消息表，等下次连接后补推
        }
        synchronized (session) {     // 同一会话并发 sendMessage 会抛 IllegalStateException
            session.sendMessage(new TextMessage(payload));
        }
        return true;
    }

    private String currentUserId(WebSocketSession session) {
        return String.valueOf(session.getAttributes().get("userId"));
    }

    private void send(WebSocketSession session, String text) {
        try {
            synchronized (session) {
                session.sendMessage(new TextMessage(text));
            }
        } catch (IOException e) {
            System.out.println("发送失败: " + e.getMessage());
        }
    }
}

注册处理器时，除了原生 WebSocket 地址，通常还会注册一个带 withSockJS() 的地址，作为不支持 WebSocket 的浏览器或中间设备的降级方案。更关键的是认证要在握手阶段完成：浏览器发起 WebSocket 时不会自动带上自定义请求头，所以要么把 token 放在 URL 参数里，要么依赖 Cookie/Session，由 HandshakeInterceptor 校验后写入 attributes。若校验失败就拒绝握手，避免未登录连接白白占用资源。

集群推送与可靠性

WebSocket 在生产环境最容易翻车的地方是集群：连接是有状态的，会话对象无法跨 JVM 共享，也不能序列化到 Redis。用户 A 连在节点 1、用户 B 连在节点 2，业务代码在节点 2 上想给 A 发消息就找不到了。

标准解法是「业务服务只负责发消息，广播交给中间件」：业务代码把消息 publish 到 Redis 频道（或 MQ 广播主题），每个应用节点都订阅该频道，收到后查本地会话表，推给自己机器上的在线用户。这样既保证了跨节点可达，又避免了节点间互相调用。

import org.springframework.data.redis.connection.Message;
import org.springframework.data.redis.connection.MessageListener;
import org.springframework.stereotype.Component;

/** 每个应用节点都订阅同一个频道；本机推送给本机在线用户 */
@Component
public class PushMessageListener implements MessageListener {

    private final NoticeWebSocketHandler handler;

    public PushMessageListener(NoticeWebSocketHandler handler) {
        this.handler = handler;
    }

    @Override
    public void onMessage(Message message, byte[] pattern) {
        String body = new String(message.getBody());
        // 约定消息格式：userId|payload
        String[] parts = body.split("\\|", 2);
        try {
            boolean online = handler.sendToUser(parts[0], parts[1]);
            if (!online) {
                System.out.println(parts[0] + " 不在线，写入离线消息表");
            }
        } catch (Exception e) {
            System.out.println("推送失败: " + e.getMessage());
        }
    }
}

除此之外还有四件必须做的事。心跳与超时：Nginx 默认 60 秒断开空闲连接，客户端要每 30 秒发一次 ping、服务端回 pong，同时清理掉没有回应的僵尸会话。断线重连：前端用指数退避重连（1s、2s、4s……），重连成功后带上「最后收到的消息 ID」向服务端补拉，避免漏消息。消息可靠性：重要消息要在服务端落库，客户端收到后回 ACK，超时未 ACK 就重发，用消息 ID 做幂等避免重复处理。安全：生产必须用 wss://，并在握手时校验 Origin 头——WebSocket 不受同源策略保护，不校验 Origin 会存在跨站 WebSocket 劫持（CSWSH）风险。

小结：定时任务优先用 @Scheduled 起步，需要 cron、持久化、集群防重时再上 Quartz 或调度平台；集群下无论用哪种，都必须解决「多节点重复执行」，数据库抢锁是成本最低的方案。服务端推送先按「单向还是双向」选 SSE 或 WebSocket，再用中间件解决集群广播，最后补上心跳、重连、ACK 与 Origin 校验这四道保险。这两块能力的共同经验是：单机demo都很简单，真正的工作量在集群与异常路径上。
