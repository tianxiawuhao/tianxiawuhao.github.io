异常处理与调试

Posted on 2026-09-19，6 min read

程序出错并不可怕，可怕的是出错之后不知道发生了什么。本章讲 Java 的异常机制与调试手段。前半部分解决“怎么处理错误”：用 try-catch-finally 捕获并处理，用 throw / throws 把问题交给上层，用自定义异常表达业务规则。后半部分解决“怎么定位错误”：用断点调试找到异常的真正源头。

本章适合已经会写基本 Java 类和方法、但一看到红色堆栈就发懵的读者。

假设要写一个“计算两个整数相除”的方法。如果不用异常，就得让方法返回一个特殊值表示失败，比如返回 -1；可调用方怎么区分“结果是 -1”和“出错了”？再比如数组越界，返回什么值都无法表达“下标超出范围”这件事。靠返回值传递错误，会让每个调用点都塞满 if 判断，正常逻辑反而被淹没。

异常机制解决的正是这个分离问题：把“错误”也描述成一个对象，里面装着错误类型、发生位置、调用链和补充信息，然后沿着调用栈一路向上抛，直到有人愿意处理它。它带来三个好处：正常流程与错误处理彻底分开；错误信息自带上下文；编译器还能对某些异常做强制检查，提醒别忘了处理。

需要先明确一点：如果没有任何代码处理异常，JVM 的默认做法是把异常对象的堆栈轨迹（stack trace）打印到标准错误流，然后终止当前线程。控制台上那一长串 at com.xxx.Main.main(Main.java:8)，就是这条规则的结果。所以“程序突然挂了并打印一堆英文”，本质上不是 JVM 在报错，而是没人接住这个异常。

异常体系与两类异常

Java 中所有能被抛出、捕获、声明的异常类都继承自 java.lang.Throwable。它下面有两个直接子类：

Error：表示 JVM 层面的严重问题，例如 OutOfMemoryError、StackOverflowError。这类问题通常超出了应用代码的处理能力，程序不应该去捕获它，捕获了也做不了什么。

Exception：表示程序运行中可以处理的问题，日常打交道的基本都在这一支。它的子类 RuntimeException 及其派生类被称为非受检异常（unchecked，也叫运行时异常），其余 Exception 子类被称为受检异常（checked，旧笔记常称作“编译期异常”）。

这里有两个常见说法需要纠正。第一，“编译期异常”这个叫法容易让人误解为“异常发生在编译期”。事实上所有异常都发生在运行时。受检异常之所以和“编译期”挂上关系，只是因为编译器会检查有没有写处理代码：要么用 try-catch 捕获，要么在方法签名上用 throws 声明出去，否则编译直接失败。第二，非受检的并不只有 RuntimeException 一族。Error 及其子类同样不受编译检查。按 Java 语言规范，受检异常指的是 Throwable 的子类中，除 RuntimeException 和 Error 及其子类之外的部分。不少入门材料只写 Exception 分支，漏掉了 Error 这一支。

常见受检异常：IOException、SQLException、ClassNotFoundException、InterruptedException。常见非受检异常：NullPointerException、ArrayIndexOutOfBoundsException、ClassCastException、IllegalArgumentException，以及它的子类 NumberFormatException。

选择继承哪一支，决定了错误的“强制程度”。如果某种问题调用方必须处理，就继承 Exception，交给编译器把关。如果是调用方的代码写错了（比如传了非法参数），就继承 RuntimeException，不要用受检异常去污染整条调用链的签名。

捕获异常：try-catch-finally

能自己解决的问题就自己解决，这对应异常的捕获。基本形式是 try { 可能出错的代码 } catch (异常类型 变量) { 处理代码 }。catch 块从上到下依次匹配，一旦匹配成功，后面的 catch 不再执行。

public static int divide(String a, String b) {
    try {
        int x = Integer.parseInt(a);      // 可能抛 NumberFormatException
        return x / Integer.parseInt(b);   // 可能抛 ArithmeticException
    } catch (NumberFormatException e) {
        // 子类异常写在前面，父类异常写在后面
        System.out.println("参数不是合法整数: " + e.getMessage());
        return 0;
    } catch (ArithmeticException | NullPointerException e) {
        // Java 7+ 的多重捕获：多个类型共用一个处理块
        System.out.println("计算失败: " + e);
        return 0;
    } finally {
        System.out.println("本次计算结束");   // 无论成功失败都会执行
    }
}

关于捕获，有几条规则必须记牢。catch 的顺序不能颠倒：如果把 catch (Exception e) 写在 catch (NumberFormatException e) 前面，编译器会报错，因为后面的分支永远不可能被执行（unreachable）。多重捕获有前提：catch (A | B e) 中的多个类型之间不能存在继承关系。原因就是重复捕获：子类与父类能捕获同一批异常，编译器同样判定为错误。旧笔记只含糊地说“只能使用没有继承关系的异常类”，没有点明这层原因。

处理资源时，Java 7 之前必须把 close() 写在 finally 里，还得再套一层 try，非常啰嗦。现在应优先使用 try-with-resources。只要资源实现了 AutoCloseable，就会在语句结束时自动关闭，关闭顺序与打开顺序相反。关闭时抛出的异常会作为 suppressed 异常附加到主异常上，不会丢失。

public static String readFirstLine(String path) throws IOException {
    try (BufferedReader reader = new BufferedReader(new FileReader(path))) {
        return reader.readLine();
    }   // 无论正常返回还是抛异常，reader 都会在这里自动 close()
}

最后是 finally 的两个要点。它的语义是“离开 try 语句时必然执行”，但并非绝对：System.exit()、JVM 崩溃、线程被强制终止时不会执行。更要命的是陷阱——千万不要在 finally 里写 return 或 throw。它会覆盖 try 或 catch 中正在返回的值，甚至吞掉正在抛出的异常，让问题凭空消失。

抛出、声明与自定义异常

自己解决不了的问题，就交给调用者，这对应异常的声明。throw 用在方法体内，抛出一个异常对象；throws 写在方法参数列表之后、方法体大括号之前，声明本方法可能抛出的受检异常，多个用逗号分隔。注意二者分工：throw 是动作，throws 是承诺。

自定义异常是表达业务规则的推荐方式，步骤只有三步：类名以 Exception 结尾；继承 Exception（受检）或 RuntimeException（非受检）；提供接收消息字符串的构造方法，并用 super(message) 把信息交给父类。建议再补一个 (String message, Throwable cause) 构造，用于保留原始异常形成异常链；也可以补一个无参构造，供框架反射和序列化使用。

/** 年龄超出自定义范围时抛出；属于非受检异常，不强制调用方捕获 */
public class WrongAgeException extends RuntimeException {
    public WrongAgeException() { }

    public WrongAgeException(String message) {
        super(message);
    }

    public WrongAgeException(String message, Throwable cause) {
        super(message, cause);
    }
}

public class Person {
    private String name;
    private int age;

    public Person(String name, int age) {
        this.name = name;
        setAge(age);   // 校验失败会抛出 WrongAgeException
    }

    public void setAge(int age) {
        if (age < 0 || age > 150) {
            throw new WrongAgeException("年龄 " + age + " 不合法，合法范围是 0~150");
        }
        this.age = age;
    }

    // getter / setter / toString 省略
}

在继承场景下，重写方法还有一个容易忽略的限制：子类重写方法不能声明比父类更多的受检异常。具体来说，父类方法没声明受检异常，子类就不能新增；父类声明了一个受检异常，子类只能声明这个异常本身或它的子类；父类声明了多个，子类只能取其中的子集。原因是多态：调用方按父类签名来调用方法，如果子类突然抛出父类没承诺的受检异常，调用方的既有代码就会被破坏。非受检异常不受这条限制。

断点调试：找到异常的源头

堆栈轨迹只告诉你“异常在哪里抛出”，却常常回答不了“这个 null 是谁放进来的”。断点调试就是补上后半句的工具。以 IntelliJ IDEA 为例，常用的断点调试操作如下：

  • 打断点：在行号左侧单击打上断点（Ctrl+F8）。
  • 启动调试：以 Debug 方式启动（Shift+F9）。
  • 观察现场：程序停在断点后，通过 Debug 窗口查看调用栈（Frames）、当前变量（Variables）和自定义表达式（Watches，或按 Alt+F8 打开 Evaluate Expression 临时求值）。

单步操作记住四个就够：Step Over（F8，不进入方法）、Step Into（F7，进入方法）、Step Out（Shift+F8，跳出当前方法）、Resume（F9，继续运行到下一个断点）。

四类断点在排查异常时特别有用。行断点最常用，用于观察某个时刻的变量状态。条件断点可以右键断点填写 Condition，例如 i == 500 或 name == null，避免在循环里连续暂停几百次。异常断点在 Run → View Breakpoints（Ctrl+Shift+F8）中添加 Java Exception Breakpoint 并填入异常类名。程序会在异常被抛出的第一现场停下，这是定位空指针最有效的手段。字段断点（Watchpoint）则用于监视某个字段被谁修改。

最后是几个实战中反复出现的坑。不要写空的 catch 块，catch (Exception e) {} 是最典型的排查灾难：异常被静默吞掉后，只能看到错误的结果却看不到原因，至少要用日志记录下来。不要用异常控制正常流程，创建异常对象时要填充栈轨迹，开销远高于一次普通判断。捕获后重新抛出要保留原因，写成 throw new OrderException("下单失败", e) 而不是丢掉 e，否则异常链断裂，排查又从零开始。区分环境使用手段：e.printStackTrace() 只适合本地调试，生产环境应当接入 SLF4J + Logback 之类的日志框架，输出上下文并做告警。

小结

异常机制的核心是把错误从正常流程中分离出来。Throwable 是体系根，Error 与 RuntimeException 一族是非受检异常，其余 Exception 子类是受检异常，编译器只强制处理后者。处理异常时把握好四条原则：

  • 能自己解决就用 try-catch-finally 或 try-with-resources 捕获。
  • 自己解决不了就用 throws 交给上层。
  • 业务规则用自定义异常表达得更清楚。
  • 重写方法只能“收窄”不能“扩大”受检异常的声明范围。

遇到难以定位的问题时，异常断点往往比读堆栈更快找到第一现场；写代码时则要守住底线——不吞异常、不丢原因、不在 finally 里 return。掌握这些，程序就能从“出错就崩”进化为“出错可控、出错可查”。
