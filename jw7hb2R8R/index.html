Dockerfile详解

本文按「一条指令一节」的方式梳理 Dockerfile 的常用指令：先讲编写时容易踩坑的几条约定，再逐条说明语法、参数与典型用法，重点区分最容易混淆的 ADD/COPY 与 RUN/CMD/ENTRYPOINT 两组指令。

环境介绍

  1. Dockerfile中所用的所有文件一定要和Dockerfile文件在同一级父目录下，可以为Dockerfile父目录的子目录

  2. Dockerfile中相对路径默认都是Dockerfile所在的目录

  3. Dockerfile中一定要惜字如金，能写到一行的指令，一定要写到一行，原因是分层构建，联合挂载这个特性。

    Dockerfile中每一条指令被视为一层

  4. Dockerfile中指明大写（约定俗成）

指令介绍

FROM

功能为指定基础镜像，并且必须是第一条指令。

如果不以任何镜像为基础，那么写法为：FROM scratch。

同时意味着接下来所写的指令将作为镜像的第一层开始

语法：

FROM <image>
FROM <image>:<tag>
FROM <image>@<digest>

三种写法，其中 <tag> 和 <digest> 是可选项，不写时默认为 latest。注意摘要必须用 @ 连接，例如 FROM ubuntu@sha256:...，写成冒号是无效的。

MAINTAINER

指定作者

语法：

MAINTAINER <name>
  • 该指令已废弃，新版 Docker（1.13 起）建议改用 LABEL maintainer="name <mail@example.com>"，一个 LABEL 还能同时声明多个键值。

LABEL

功能是为镜像指定标签

语法：

LABEL <key>=<value> <key>=<value> <key>=<value> ...
 一个Dockerfile 中可以有多个LABEL，如下：

LABEL "com.example.vendor"="ACME Incorporated"
LABEL com.example.label-with-value="foo"
LABEL version="1.0"
LABEL description="This text illustrates \
that label-values can span multiple lines."
 但是并不建议这样写，最好就写成一行，如太长需要换行的话则使用\符号

如下：

LABEL multi.label1="value1" \
      multi.label2="value2" \
      other="value3"

说明：LABEL 会继承基础镜像中的 LABEL，如遇到 key 相同，则值覆盖

ADD

一个复制命令，把文件复制到镜像中。

如果把虚拟机与容器想象成两台linux服务器的话，那么这个命令就类似于scp，只是scp需要加用户名和密码的权限验证，而ADD不用。

语法如下：

ADD <src>... <dest>
ADD ["<src>",... "<dest>"]
  • 路径的填写可以是容器内的绝对路径，也可以是相对于工作目录的相对路径，推荐写成绝对路径
  • 可以是一个本地文件或者是一个本地压缩文件，还可以是一个url
  • 如果 src 写成一个 url，那么 ADD 就类似于 wget 命令

示例

ADD test relativeDir/ 
ADD test /relativeDir
ADD http://example.com/foobar/

注意事项

  • src 为一个目录的时候，会自动把目录下的文件复制过去，目录本身不会复制
  • 如果 src 是多个文件或使用了通配符，dest 必须以 / 结尾，否则会被当成一个普通文件名
  • src 是本地可识别的压缩包（tar、gzip、bzip2、xz）时，ADD 会自动解压到 dest；从 URL 下载的压缩包不会解压
  • 因此只在需要「自动解压」时才用 ADD，其余场景优先用 COPY，语义更清晰

COPY

看这个名字就知道，又是一个复制命令

语法如下：

COPY <src>... <dest>
COPY ["<src>",... "<dest>"]

与ADD的区别

  • COPY 只能复制本地文件，不支持 URL，也不会自动解压压缩包；其余用法与 ADD 一致
  • 两者都支持 --chown=<user>:<group>，可在复制时直接改属主，省掉额外一层 RUN chown

EXPOSE

功能为暴露容器运行时的监听端口给外部

但是EXPOSE并不会使容器访问主机的端口

要真正建立映射，需在 docker run 时用 -p 8080:80（宿主机端口:容器端口）指定，或用 -P 把所有已声明的端口随机映射到宿主机高位端口

语法：

EXPOSE <port>[/<protocol>]

ENV

功能为设置环境变量

语法有两种

 ENV <key> <value>
 ENV <key>=<value> ...

两者的区别就是第一种是一次设置一个，第二种是一次设置多个

在Dockerfile中使用变量的方式

  • $varname
  • ${varname}
  • ${varname:-default value}
  • ${varname:+default value}

第一种和第二种相同

第三种表示当变量不存在使用-号后面的值

第四种表示当变量已存在时使用 + 号后面的值，变量不存在时替换为空字符串——+ 后面写的是「替代值」而不是默认值，这是最容易记反的一处

RUN

功能为运行指定的命令

RUN命令有两种格式

RUN <command>
RUN ["executable", "param1", "param2"]

第一种后边直接跟shell命令

  • 在linux操作系统上默认 /bin/sh -c
  • 在windows操作系统上默认 cmd /S /C

第二种是 exec 形式，把可执行文件和各参数写成 JSON 数组，运行时不再经过 shell。

  • 可将 executable 理解成为可执行文件，后面就是依次传入的参数。
  • 因为不经过 shell，exec 形式不支持变量替换、通配符展开、管道和重定向，需要这些能力时请用第一种写法。
  • 每条 RUN 都会生成一层镜像，所以常见做法是用 && 把安装、清理串进同一条 RUN，避免层数与体积膨胀。

SHELL

覆盖后续 RUN、CMD、ENTRYPOINT 在使用 shell 形式时默认调用的 shell 程序

语法：

SHELL ["executable", "parameters"]

Linux 上默认是 ["/bin/sh", "-c"]，Windows 上默认是 ["cmd", "/S", "/C"]。最常见的用法是换成 bash，以便在 RUN 里使用 pipefail 或 source：

SHELL ["/bin/bash", "-o", "pipefail", "-c"]
RUN apt-get update && apt-get install -y nginx

注意 SHELL 只影响 shell 形式的指令；exec 形式的 RUN/CMD/ENTRYPOINT 不经过 shell，因此不受影响。

CMD

功能为容器启动时默认命令或参数

语法有三种写法

CMD ["executable","param1","param2"]
CMD ["param1","param2"]
CMD command param1 param2

第三种是 shell 形式，写起来最直观，docker 会用 /bin/sh -c "command param1 param2" 去执行它

第一种和第二种其实都是可执行文件加上参数的形式

举例说明两种写法：

CMD [ "sh", "-c", "echo $HOME" ]
CMD [ "echo", "$HOME" ]

补充细节：exec 形式里每个元素都必须用双引号，不能写成单引号。原因是 docker 会把这段内容当作 JSON 数组解析，单引号不是合法的 JSON 字符串定界符。

原因是参数传递后，docker解析的是一个JSON array

RUN&&CMD

不要把 RUN 和 CMD 搞混了。RUN 是构建镜像时运行的命令，运行结果会被提交进镜像；CMD 是容器启动时才执行的命令，构建时并不运行，只是把「容器默认怎么启动」记录下来。

ENTRYPOINT

功能是：容器启动时运行的启动命令

语法如下：

ENTRYPOINT ["executable", "param1", "param2"]  
ENTRYPOINT command param1 param2

如果从上到下看到这里的话，那么你应该对这两种语法很熟悉啦。

  • 第二种就是写shell
  • 第一种就是可执行文件加参数

与CMD比较说明（这俩命令太像了，而且还可以配合使用）：

相同点

  • 通常只写一条，写了多条时只有最后一条生效
  • 都是容器启动时才运行，运行时机相同

不同点

  • ENTRYPOINT不会被运行的command覆盖，而CMD则会被覆盖
  • 如果我们在Dockerfile 中同时写了ENTRYPOINT和CMD，并且CMD指令不是一个完整的可执行命令，那么CMD指定的内容将会作为ENTRYPOINT的参数

如下：

FROM ubuntu
ENTRYPOINT ["top", "-b"]
CMD ["-c"]

第二个例子更容易误解：即使 CMD 写成完整的 shell 指令，ENTRYPOINT 也不会被它覆盖，CMD 的内容只是被包装后追加到 ENTRYPOINT 后面当作参数。

如下：

FROM ubuntu
ENTRYPOINT ["top", "-b"]
CMD ls -al

这里实际执行的命令是 top -b /bin/sh -c "ls -al"：top -b 仍然会启动，只是额外接收了 /bin/sh -c "ls -al" 这一串参数，而不是只执行 ls -al。这也说明「CMD 是完整指令就会与 ENTRYPOINT 互相覆盖」的说法是不准确的。

VOLUME

可实现挂载功能，可以将宿主机目录挂载到容器中

也就是说，可以把专用块存储、NFS 或宿主机目录挂进容器，作为容器的数据存储部分。

语法如下：

VOLUME ["/data"]

说明：

["/data"]可以是一个JsonArray ，也可以是多个值。所以如下几种写法都是正确的

VOLUME ["/var/log/"]
VOLUME /var/log
VOLUME /var/log /var/db

一般的使用场景为需要持久化存储数据时

容器的可写层依附于容器本身：删除容器时，写层里的改动会一并丢失（现代 Docker 默认使用 overlay2 存储驱动，AUFS 已是历史选项）。需要跨容器、跨重建保留的数据，就应该通过 VOLUME 或 docker run -v 挂载出来。

USER

设置启动容器的用户，可以是用户名或UID，所以，只有下面的两种写法是正确的

USER daemon
USER 1000

注意：设置之后，RUN、CMD、ENTRYPOINT 以及容器内后续启动的进程都会以这个用户身份运行。

使用这个命令一定要确认容器中拥有这个用户，并且拥有足够权限

WORKDIR

设置工作目录

语法：

WORKDIR /path/to/workdir

设置工作目录，对RUN,CMD,ENTRYPOINT,COPY,ADD生效。如果不存在则会创建，也可以设置多次。

如：

WORKDIR /a
WORKDIR b
WORKDIR c
RUN pwd

pwd执行的结果是/a/b/c

WORKDIR也可以解析环境变量

如：

ENV DIRPATH /path
WORKDIR $DIRPATH/$DIRNAME
RUN pwd

pwd的执行结果是/path/$DIRNAME

ARG

设置变量命令

语法：

ARG <name>[=<default value>]

ARG 定义的变量只在构建期可见，容器运行时并不存在（这一点与 ENV 不同）。构建时用 docker build --build-arg <name>=<value> 传值。

注意：写在第一个 FROM 之前的 ARG 属于「全局 ARG」，在 FROM 之后要继续引用，必须在对应构建阶段里再声明一次。

如果用户在 build 镜像时指定了一个没有在 Dockerfile 中定义的参数，那么会出现一条 Warning：

[Warning] One or more build-args [foo] were not consumed.

我们可以定义一个或多个参数，如下：

FROM busybox
ARG user1
ARG buildno

也可以给参数一个默认值：

FROM busybox
ARG user1=someuser
ARG buildno=1

如果我们给了ARG定义的参数默认值，那么当build镜像时没有指定参数值，将会使用这个默认值

ONBUILD

语法：

ONBUILD [INSTRUCTION]

这个命令只对当前镜像的子镜像生效。

比如当前镜像为A，在Dockerfile 中添加：

ONBUILD RUN ls -al
  • 这个 ls -al 命令不会在 A 镜像构建或启动的时候执行，也不会在基于 A 运行的容器里执行
  • 子镜像构建完成后这些触发器会被清除，因此不会再传递给「孙子」镜像

此时有一个镜像B是基于A镜像构建的，那么这个ls -al 命令会在B镜像构建的时候被执行。

STOPSIGNAL

语法：

STOPSIGNAL signal

STOPSIGNAL 用于指定 docker stop 停止容器时向容器内 1 号进程发送什么信号，默认是 SIGTERM（信号值 15）。如果程序只有收到 SIGINT 才会优雅退出，就应显式写成 STOPSIGNAL SIGINT。

HEALTHCHECK

容器健康状况检查命令

语法有两种：

 HEALTHCHECK [OPTIONS] CMD command
 HEALTHCHECK NONE

第一个的功能是在容器内部运行一个命令来检查容器的健康状况

第二个的功能是在基础镜像中取消健康检查命令

[OPTIONS]的选项支持以下三中选项：

  • --interval=DURATION：两次检查的时间间隔，默认 30s
  • --timeout=DURATION：单次健康检查命令的超时时长，默认 30s
  • --retries=N：连续失败指定次数后容器被标记为 unhealthy，默认 3 次
  • --start-period=DURATION：容器启动后的宽限期，这段时间内的失败不计入 retries，适合启动较慢的服务

注意：

HEALTHCHECK命令只能出现一次，如果出现了多次，只有最后一个生效。

CMD后边的命令的返回值决定了本次健康检查是否成功，具体的返回值如下：

  • 0: success - 表示容器是健康的
  • 1: unhealthy - 表示容器已经不能工作了
  • 2: reserved - 保留值

例子：

HEALTHCHECK --interval=5m --timeout=3s \
  CMD curl -f http://localhost/ || exit 1

健康检查命令是：curl -f http://localhost/ || exit 1

两次检查的间隔时间是 5 分钟（5m 表示 5 minutes，不是 5 秒）

命令超时时间为 3 秒

等价的 exec 写法是 HEALTHCHECK CMD ["curl", "-f", "http://localhost/"]；这种写法不经过 shell，所以 || exit 1 这类语法不能再用。
