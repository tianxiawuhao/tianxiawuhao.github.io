Hadoop 生态与 HDFS

Posted on 2026-09-19，6 min read

单机时代，一个操作系统的磁盘容量和数据吞吐能力就是天花板。当数据量涨到几十 TB 甚至 PB 级别，唯一的出路是把数据分散到多台机器上——可一旦分散，问题立刻从「怎么存」变成「怎么管」：文件放在哪台机器？某台机器坏了数据怎么办？一百台机器怎么拼成一块磁盘？HDFS（Hadoop Distributed File System）就是为回答这些问题而生的分布式文件系统。本节从 HDFS 的定位讲起，说清 NameNode/DataNode 的分工、块的切分与副本放置、读写数据流程，再补充 YARN 与 MapReduce 在生态中的位置，最后给出可复制的 Shell 与 Java API 示例。适合有 Java 基础、准备第一次接触大数据存储与计算的读者。

一、为什么需要分布式文件系统

把文件切碎散落到多台机器上，看似解决了容量问题，但随之而来三个硬需求：

  • 统一命名空间：用户看到的是/user/atguigu/ss.avi这样一棵目录树，而不是「第 37 台机器上的某个文件」。定位文件靠目录树，而不是靠记住机器编号。
  • 容错：机器故障在大规模集群里是常态而不是意外。数据必须自动保存多个副本，某个副本丢失后能自动恢复，且恢复过程不需要人工介入。
  • 可扩展：扩容时只需加机器，而不是重新设计存储结构；同时要能跑在廉价商用机器上，靠软件层面的多副本机制保证可靠性。

HDFS 的取舍非常鲜明：它适合一次写入、多次读出的场景，一个文件创建、写入、关闭之后基本不再改动。反过来，它不适合毫秒级低延迟访问，也不擅长存海量小文件——每个文件、每个块的元数据都要占用 NameNode 的内存，而 NameNode 内存是有限的；小文件的寻址时间甚至会超过真正的读取时间，违背设计目标。此外 HDFS 不支持并发写入，一个文件同一时刻只能有一个写者，修改方式仅限追加（append），不支持任意位置随机修改。

二、HDFS 组成架构与文件块

HDFS 集群是一套主从（Master/Slave）结构，四个角色各司其职：

  • NameNode（nn，主）：管理文件系统的名称空间（文件名、目录结构、属性如创建时间/副本数/权限），管理数据块到 DataNode 的映射信息，配置副本策略，并处理客户端的读写请求。
  • DataNode（dn，从）：存储实际的数据块，执行数据块的读/写操作，并向 NameNode 汇报自身持有的块信息。
  • Client（客户端）：上传前把文件切分成一个个 Block；与 NameNode 交互获取文件位置信息；再与 DataNode 交互读写真实数据；同时提供管理 HDFS 的命令（如格式化 NameNode）。
  • Secondary NameNode（2nn）：注意它不是 NameNode 的热备——NameNode 挂掉时它并不能立刻顶替对外提供服务。它的职责是辅助 NameNode，定期合并 Fsimage 与 Edits 并推送给 NameNode，在紧急情况下可辅助恢复 NameNode。

从 Hadoop 2.x 开始，Hadoop 的组成拆分为四层：HDFS 负责数据存储，YARN 负责资源调度，MapReduce 负责业务运算，Common 是公共辅助工具。而在 Hadoop 1.x 时代，MapReduce 把运算和资源调度耦合在一起，这也是 2.x 引入 YARN 的直接原因；Hadoop 3.x 在组成上没有变化。

文件在物理上是分块存储的，块大小由 dfs.blocksize 规定：Hadoop 2.x/3.x 默认 128MB，1.x 默认 64MB。块不能设得太小，否则程序会把大量时间花在反复寻找每个块的起始位置；也不能设得太大，否则单个块从磁盘传输的时间会远大于定位该块的时间，而一个块的处理只能等它传完。经验结论是：块大小主要取决于磁盘传输速率。

三、写数据、读数据与副本放置

写数据流程：客户端向 NameNode 请求上传文件 → NameNode 校验权限与目录，响应「可以上传」→ 客户端请求上传第一个 Block（例如 0–128M），请 NameNode 返回可用的 DataNode → NameNode 返回一组 DataNode，客户端与它们建立 Pipeline 流水线，把 Block 以 packet 为单位传输 → 全部 Block 传完后通知 NameNode 关闭文件。过程中副本沿流水线逐级复制，因此写一份数据实际上在网络中会被放大数倍，这也是副本策略要尽量减少跨机架写入的原因。

读数据流程：客户端请求下载文件 → NameNode 返回目标文件的元数据（各 Block 所在的 DataNode 列表）→ 客户端就近选择 DataNode 建立连接并读取 Block → 读完后关闭连接。由于同一块可能有多个副本，读取时拥有最大的选择空间。

「就近」不是凭感觉，而是按网络拓扑算出来的节点距离：两个节点到最近的共同祖先的距离之和。Distance(/d1/r1/n0, /d1/r1/n0)=0（同一节点）、Distance(/d1/r1/n1, /d1/r1/n2)=2（同机架不同节点）、Distance(/d1/r2/n0, /d1/r3/n2)=4（同数据中心不同机架）、Distance(/d1/r2/n1, /d2/r4/n1)=6（不同数据中心）。

副本数默认为 3，其放置遵循机架感知策略：第一个副本放在客户端所在的节点上（若客户端在集群外则随机选一个节点），第二个副本放在另一个机架上的随机节点，第三个副本放在第二个副本所在机架的另一个随机节点。这样跨机架的写入流量被压到最小，而机架级故障的概率远低于节点级故障，可靠性并未下降。

四、YARN 与 MapReduce：生态中的另外两块拼图

HDFS 只解决「存」，计算交给 MapReduce，而「哪台机器有多少资源、任务分给谁」交给 YARN（Yet Another Resource Negotiator）。YARN 的四个概念要记住：ResourceManager（RM）是整个集群资源（内存、CPU）的总管；NodeManager（NM）是单台节点服务器上的资源管理者；ApplicationMaster（AM）是单个任务运行的管理者，负责为作业申请资源、协调进度；Container是容器，相当于一台被分配出来的独立服务器，任务真正跑在里面。

MapReduce 把计算过程分为两个阶段：Map 阶段并行处理输入数据，Reduce 阶段对 Map 的结果进行汇总。一个完整的 MapReduce 程序在分布式运行时有三类实例进程：MrAppMaster（负责整个程序的过程调度与状态协调）、MapTask（负责 Map 阶段的整个数据处理流程）、ReduceTask（负责 Reduce 阶段的整个数据处理流程）。编程时用户只需写三个部分：Mapper、Reducer 和 Driver。

五、动手示例与常见坑

HDFS 提供两套等价的操作入口：命令行和 Java API。命令行里 hadoop fs 与 hdfs dfs 完全等价，前者更通用。

# 上传：-put 等同于 -copyFromLocal，生产环境更习惯用 -put
hadoop fs -mkdir /sanguo
hadoop fs -put ./wuguo.txt /sanguo
hadoop fs -appendToFile liubei.txt /sanguo/wuguo.txt

# 查看与下载：-get 等同于 -copyToLocal
hadoop fs -ls /sanguo
hadoop fs -cat /sanguo/wuguo.txt
hadoop fs -get /sanguo/wuguo.txt ./wuguo2.txt

# -du 输出两列：第一列是文件大小，第二列是「大小 × 副本数」
hadoop fs -du -s -h /sanguo
# 27  81  /sanguo

# 设置副本数：只是记录在 NameNode 元数据中，实际副本数受 DataNode 数量限制
hadoop fs -setrep 10 /sanguo/wuguo.txt

Java 侧使用 FileSystem 这一抽象类，靠 URI 的 scheme 决定底层是 HDFS 还是本地文件系统。hadoop-client 依赖是必需项，另外一定要显式传入操作 HDFS 的用户名。

<dependency>
  <groupId>org.apache.hadoop</groupId>
  <artifactId>hadoop-client</artifactId>
  <version>3.1.3</version>
</dependency>

public class HdfsClient {

    @Test
    public void testMkdirs() throws IOException, URISyntaxException, InterruptedException {
        Configuration conf = new Configuration();
        // 第三个参数是操作 HDFS 的用户名，传 null 时会退化为操作系统默认用户
        FileSystem fs = FileSystem.get(new URI("hdfs://hadoop102:8020"), conf, "atguigu");
        try {
            fs.mkdirs(new Path("/xiyou/huaguoshan"));
        } finally {
            fs.close();
        }
    }
}

如果省略用户名参数，客户端会采用操作系统默认用户去访问 HDFS，容易报出 org.apache.hadoop.security.AccessControlException: Permission denied。注意这类异常是权限问题而非网络问题：日志里已经能看到 inode="/xiyou/huaguoshan":atguigu:supergroup:drwxr-xr-x，说明 NameNode 已经正常响应，只是当前用户没有写权限。

常见坑速查

把上面几节压缩成几条实战经验：

  • 别把小文件当普通文件存。海量小文件会吃掉 NameNode 内存，并让寻址时间超过读取时间。
  • 别指望并发写和随机改。HDFS 一个文件只能有一个写者，且只支持追加。
  • -setrep 不等于立刻有那么多副本。它只改元数据，实际副本数受 DataNode 数量上限约束：3 台机器最多 3 个副本。
  • API 访问务必带上用户名，否则很容易掉进权限异常。
  • 端口默认值随版本变化。本文示例使用 hdfs://hadoop102:8020，这是 Hadoop 3.x 的 NameNode RPC 默认端口；老资料里常见的 9000 是 2.x 的历史配置，请以自己集群 core-site.xml 中 fs.defaultFS 的实际值为准。
  • Secondary NameNode 不是备份。它可以辅助合并元数据、辅助恢复集群，但不能在 NameNode 故障时立即接管服务；生产环境的真正高可用方案是 NameNode HA。

小结：HDFS 用「NameNode 管元数据 + DataNode 存块 + 多副本 + 机架感知」这套组合，把多台廉价机器拼成了一块容量近乎无限、能容忍机器故障的大磁盘；它的能力边界同样清晰——一次写入多次读取、大文件、高吞吐、可以接受较高延迟。在此之上，YARN 负责把集群的内存与 CPU 切分给各个作业，MapReduce 负责把计算拆成并行的 Map 与汇总的 Reduce，三者与 Common 共同构成 Hadoop 生态的地基。下一节我们继续沿着这条线，看更上层的计算与查询框架如何复用这套存储。
