git-worktree

Posted on 2024-02-22，7 min read

名称

git-worktree - 管理附加到同一存储库的多个工作树。git worktree 自 Git 2.5.0 引入（当时属于实验特性），Git 2.17 起 remove、move 齐备，已可用于日常工作流；各子命令的版本要求见文末「版本要求」一节。

语法

git worktree add [-f] [--detach] [--checkout] [--lock [--reason <string>]]
                 [--orphan] [-b <new-branch> | -B <new-branch>] <path> [<commit-ish>]
git worktree list [-v | --porcelain [-z]]
git worktree lock [--reason <string>] <worktree>
git worktree move <worktree> <new-path>
git worktree prune [-n] [-v] [--expire <expire>]
git worktree remove [-f] <worktree>
git worktree repair [<path>…]
git worktree unlock <worktree>

与旧版手册相比，list 增加了 -v/--porcelain，add 增加了 --orphan 与 -B（重置同名分支）。用 git worktree -h 可以直接确认本机 Git 支持的子命令与选项。

描述

一个 Git 仓库可以同时挂载多棵工作树，从而一次检出多个分支。用 git worktree add 新建的目录称为「链接工作树」（linked worktree），而 git init、git clone 建立的那个称为「主工作树」（main worktree）。非裸仓库有且只有一个主工作树，外加零个或多个链接工作树；裸仓库没有主工作树，所有工作树都是链接工作树。链接工作树用完后应当用 git worktree remove 删除，而不是直接删目录。

与「把仓库 clone 成多份」相比，工作树共享同一个对象库、分支与标签等引用，只占一份仓库历史与对象存储；每棵工作树又各自拥有独立的工作区、索引（index）与 HEAD。因此可以一边在主工作树跑构建，一边在链接工作树里改 hotfix，切换成本为零，也不会出现多份 clone「各 fetch 各推」的分支漂移。

最简单的用法是 git worktree add <path>：它会自动创建一个新分支，分支名取 <path> 的最后一段（basename），适合开启一个新主题。例如 git worktree add ../hotfix 会创建分支 hotfix 并检出到 ../hotfix。若要在新工作树里检出已存在的分支，用 git worktree add <path> <branch>。如果只想做实验或测试、又不干扰现有开发，可以创建不与任何分支关联的一次性工作树：git worktree add --detach <path> 会在当前分支所在的提交处创建一棵游离 HEAD 的工作树。

如果绕开 git worktree remove 直接删除了工作树目录，其管理文件（见下文「共享与独占的元数据」）会残留下来；它们最终会被自动清理（由 git-config(1) 的 gc.worktreePruneExpire 控制），也可以在任一工作树中运行 git worktree prune 立即清理。

如果链接工作树存放在不常挂载的移动设备或网络共享上，可以用 git worktree lock 阻止其管理文件被修剪，并可用 --reason 说明锁定原因。

初始化一个仓库

$ git init
Initialized empty Git repository in D:/VSCode/testGit/.git/

$ git status
$ git add .
$ git commit -m 'f commit'
[master (root-commit) f7f05d0] f commit
 3 files changed, 18 insertions(+)
 create mode 100644 blob.config
 create mode 100644 copy.sh
 create mode 100644 fff.txt

## 再新建两个分支
$ git branch dev
$ git branch release
$ git branch -a
  dev
* master
  release

新建工作树 add

git worktree add [-f] [--detach] [--checkout] [--lock [--reason <string>]] <path> [<commit-ish>]

## 1) 新建分支：分支名默认取 path 的最后一段
$ git worktree add ./wtree1
Preparing worktree (new branch 'wtree1')
HEAD is now at f7f05d0 f commit

$ git worktree list
D:/VSCode/testGit         f7f05d0 [master]
D:/VSCode/testGit/wtree1  f7f05d0 [wtree1]

## 2) 检出已存在的分支
$ git worktree add ../wt-dev dev
Preparing worktree (checking out 'dev')
HEAD is now at 2c05e7a ...

## 3) 一次性实验：游离 HEAD，不占用分支名
$ git worktree add --detach ../try-idea
Preparing worktree (detached HEAD f7f05d0)
HEAD is now at f7f05d0 f commit

## 4) 指定新分支名与起点（-B 会重置同名分支）
$ git worktree add -b nb-wtree4 ../wt/wtree4 master
Preparing worktree (new branch 'nb-wtree4')

除上面四种用法外，还有几个常用选项：--no-checkout（Git 2.9+）只建立管理目录、不检出文件，适合配合 sparse-checkout 按需拉取；--lock（Git 2.13+，--reason 需 2.33+）在创建时就锁定；--orphan（Git 2.42+）基于一个尚无提交的分支创建工作树，例如为 gh-pages 之类的全新历史做准备。不带 <commit-ish> 时，默认以当前 HEAD 为起点。

上面把工作树建在仓库内部（./wtree1）只是为了演示；实际使用建议放到仓库外的兄弟目录（如 ../wt-dev）。仓库内部的工作树会被主工作树的 git status 视为一大堆未跟踪文件，git add . 有可能误提交其中的内容。

工作树与分支的关系：同一分支只能检出一处

分支引用（refs/heads/*）是所有工作树共享的，而每棵工作树都有自己的 HEAD 与索引。Git 因此规定：同一个分支最多只能被一棵工作树检出，否则两棵工作树会同时移动同一个分支引用，提交历史会变得难以理解。

$ git worktree add ../wt-dev2 dev
fatal: 'dev' is already checked out at 'D:/VSCode/wt/wtdev'

## 在另一棵工作树里切到已被检出的分支，同样会被拒绝
$ git checkout dev
fatal: 'dev' is already checked out at 'D:/VSCode/wt/wtdev'

确实需要同时查看/修改同一个分支时，可以：用 git worktree add --detach <path> <branch> 让游离 HEAD 指向该分支的提交（不占用分支名）、用 -b 另建一个新分支，或者先 git worktree remove 掉原来的工作树。git worktree add -f 可以强制绕过这项检查，但两棵工作树会各自推进同一个分支，除非明确知道后果，否则不要这么做。

「分支已被检出」的依据是 $GIT_DIR/worktrees/<name>/HEAD：只要管理目录还在，即使工作树目录已被删除，Git 仍会认为该分支被占用，需要用 git worktree prune 清理记录（见下文）。

共享与独占的元数据

所有工作树共享主仓库 .git 下的对象库与公共引用；每棵链接工作树的私有状态则放在 .git/worktrees/<name>/ 下。链接工作树里的 .git 不是目录，而是一个普通文本文件，内容指向管理目录：

## 在链接工作树里
$ cat .git
gitdir: D:/VSCode/testGit/.git/worktrees/wtree1

## 管理目录中的内容
$ ls $(git rev-parse --git-dir)
HEAD  ORIG_HEAD  commondir  gitdir  index  logs

其中 gitdir 反过来记录该工作树 .git 文件的路径，commondir 的内容是 ../..，指向公共的 $GIT_DIR。下图给出两棵链接工作树与主仓库之间的目录关系。

由此可以推出几条实用结论：git log、git branch、git fetch 得到的对象与引用立刻对所有工作树可见，无需重复 fetch；而工作区文件、索引、HEAD、stash 与 bisect 状态都是每棵工作树各自一份，互不影响，所以可以放心地在不同工作树里并行 rebase、bisect 或 stash。

锁定（解锁）工作树 lock/unlock

锁定的工作树可以防止被修剪（prune），也不能被删除或移动，直到执行 git worktree unlock。

user@NAME MINGW64 /d/VSCode/testGit (master)
$ git worktree lock --reason='lock reason' wtdev

user@NAME MINGW64 /d/VSCode/testGit (master)
$ git worktree list
D:/VSCode/testGit    f4c1226 [master]
D:/VSCode/wt/wtdev   8ec2b56 [dev] locked
D:/VSCode/wt/wtree1  e14fd71 [wtree1]
D:/VSCode/wt/wtree2  2c05e7a [wtree2]
D:/VSCode/wt/wtree3  e3a3c4c (detached HEAD)
D:/VSCode/wt/wtree4  e4b08e3 [nb-wtree4]

## 解锁：允许它被 prune / move / remove
user@NAME MINGW64 /d/VSCode/wt/wtree5 (wtree5)
$ git worktree unlock wtdev

展示工作树列表 list

## git worktree list [-v | --porcelain [-z]]
user@NAME MINGW64 /d/VSCode/testGit (master)
$ git worktree list
D:/VSCode/testGit    f4c1226 [master]
D:/VSCode/wt/wtdev   2c05e7a [dev]
D:/VSCode/wt/wtree1  e14fd71 [wtree1]
D:/VSCode/wt/wtree2  2c05e7a [wtree2]
D:/VSCode/wt/wtree3  e3a3c4c (detached HEAD)
D:/VSCode/wt/wtree4  e4b08e3 [nb-wtree4]
D:/VSCode/wt/wtree5  f4c1226 [wtree5] locked
D:/VSCode/wt/wtrele  7f91b4d [release]

每行依次是：工作树路径、HEAD 提交、分支名（游离时显示 (detached HEAD)），以及 locked、prunable 等状态标注。主工作树固定排在第一行，其余按路径排序。--porcelain 输出稳定、便于脚本解析（-z 以 NUL 分隔记录）；-v 会额外打印锁定或可修剪的原因。注意 locked 状态自 Git 2.30 起才直接在默认输出中显示。

删除工作树 remove

remove 只删除干净的工作树（没有未跟踪文件、没有已跟踪文件的修改），否则需要 --force；要删除被锁定的工作树需要重复两次 --force。它只删除工作区目录并清理管理文件，分支本身以及已提交的历史都不会丢失。

$ git worktree remove wtree2
fatal: 'wtree2' contains modified or untracked files, use --force to delete it

## 确认改动无用之后再强制删除
user@NAME MINGW64 /d/VSCode/testGit (master)
$ git worktree remove -f wtree2

如果工作树目录已经被手工删除，remove 无法再进行校验，此时应当用 git worktree prune 清理记录。

修剪工作树 prune

prune 清理 $GIT_DIR/worktrees 中指向已不存在目录的管理文件；被 lock 的工作树永远不会被修剪。-n 只预览不删除，-v 打印细节，--expire <time> 指定「目录消失多久之后才算陈旧」（默认由 gc.worktreePruneExpire 控制，未设置时相当于 3.months.ago，因此自动 gc 只会顺带清理很久以前就消失的工作树）。

## 修剪前：wtree5 被锁定
$ git worktree list
D:/VSCode/testGit    f4c1226 [master]
D:/VSCode/wt/wtdev   2c05e7a [dev]
D:/VSCode/wt/wtree1  e14fd71 [wtree1]
D:/VSCode/wt/wtree3  e3a3c4c (detached HEAD)
D:/VSCode/wt/wtree4  e4b08e3 [nb-wtree4]
D:/VSCode/wt/wtree5  f4c1226 [wtree5] locked
D:/VSCode/wt/wtrele  7f91b4d [release]

## 手工删除了 wtrele 目录，并把 wtree4、wtree5 移到其他目录之后
$ git worktree list
D:/VSCode/testGit    f4c1226 [master]
D:/VSCode/wt/wtdev   2c05e7a [dev]
D:/VSCode/wt/wtree1  e14fd71 [wtree1]
D:/VSCode/wt/wtree3  e3a3c4c (detached HEAD)
D:/VSCode/wt/wtree4  e4b08e3 [nb-wtree4] prunable
D:/VSCode/wt/wtree5  f4c1226 [wtree5] locked
D:/VSCode/wt/wtrele  7f91b4d [release] prunable

## 先预览再修剪：prunable 的记录被清掉，锁定的工作树不受影响
$ git worktree prune -n -v
$ git worktree prune
$ git worktree list
D:/VSCode/testGit    f4c1226 [master]
D:/VSCode/wt/wtdev   2c05e7a [dev]
D:/VSCode/wt/wtree1  e14fd71 [wtree1]
D:/VSCode/wt/wtree3  e3a3c4c (detached HEAD)
D:/VSCode/wt/wtree5  f4c1226 [wtree5] locked

重新关联工作树 repair

repair（Git 2.29+）用于修复被外部因素破坏或过期的关联信息：整个仓库被移动后，在主工作树里执行 git worktree repair 可以重建「链接工作树 → 主仓库」的指向；某棵链接工作树被手工移动后，在该工作树里执行 git worktree repair，或在任一工作树中执行 git worktree repair <新路径>…，可以重建反向的指向。repair 的参数是被移动的链接工作树路径；不带参数时修复当前工作树与主仓库的连接。需要注意的是：已经被 prune 掉的管理目录无法恢复，只能重新 add。

## 被修剪掉的工作树无法重新关联
user@NAME MINGW64 /d/VSCode/wt/wtinner/wtree4
$ git worktree repair ../../../testGit/
fatal: not a git repository: D:/VSCode/testGit/.git/worktrees/wtree4

## 被锁定的工作树没有被 prune 掉，所以重新关联上了
user@NAME MINGW64 /d/VSCode/wt/wtinner/wtree5 (wtree5)
$ git worktree repair ../../../testGit/

## 被移动到别处、但还没被 prune 的工作树同样可以修复
$ cd /d/VSCode/wt/wtinner/wtree3
user@NAME MINGW64 /d/VSCode/wt/wtinner/wtree3 ((e3a3c4c...))
$ git worktree repair ../../../testGit/

与 clone 和子模块的取舍

  • 用 worktree：需要同一仓库的多个分支并行工作（一边开发、一边 review 或构建或 hotfix），希望共用对象库、节省磁盘与网络。代价是分支不能重复检出，且共享的 .git 一旦损坏会影响全部工作树。
  • 用 clone：需要真正独立的副本——不同的 remote、不同的凭据、交给其他用户或 CI 使用、要做破坏性实验（改写历史、彻底清理）。代价是每个副本都要 fetch，磁盘占用成倍，分支还容易漂移。
  • 含子模块的超级项目：官方手册仍把多重检出列为实验特性，并明确「子模块支持并不完整，不建议对超级项目做多重检出」。每棵工作树下的子模块目录互相独立，需要各自执行 git submodule update --init；含子模块的工作树 remove 时需要 --force，move 则直接不支持。

另外要记住：删除工作树只删除工作区中未提交的改动与未跟踪文件，不会删除任何分支或已提交的历史。

常见错误与排查

  • fatal: '<branch>' is already checked out at '<path>'：该分支已被别的工作树检出；改用 --detach、另建分支，或先移除那棵工作树。
  • fatal: '<path>' contains modified or untracked files, use --force to delete it：工作树不干净；先提交或备份，确实不要了再加 -f。
  • fatal: '<path>' is a main working tree：主工作树既不能用 remove 删除，也不能用 move 移动。
  • fatal: '<path>' is locked：先用 git worktree unlock <worktree>，或重复两次 --force。
  • fatal: not a git repository: .../.git/worktrees/<name>：管理目录已被 prune，repair 无法恢复；把工作区里的改动备份出来后重新 add。
  • 提示 git: 'worktree' is not a git command：Git 版本低于 2.5，需要升级。
  • 目录已被手工删除、git worktree list 里残留 prunable 记录：执行 git worktree prune（锁定的需先 unlock）。
  • 整个仓库或某棵工作树被移动后路径失效：用 git worktree repair，不要手工去改 .git 文件。
  • 把工作树建在仓库内部：父工作树的 git status 会把它当成大量未跟踪文件，git add . 可能误提交；建议放在仓库外的兄弟目录。

版本要求

  • Git 2.5.0+：引入 git worktree（实验特性，子命令很少）。
  • Git 2.7.0+：git worktree list。
  • Git 2.9.0+：add --no-checkout。
  • Git 2.11.0+：lock / unlock。
  • Git 2.13.0+：add --lock。
  • Git 2.17.0+：remove / move，此后可放心用于日常工作流。
  • Git 2.29.0+：repair。
  • Git 2.30.0+：git worktree list 默认输出中直接显示 locked 状态。
  • Git 2.33.0+：lock --reason 记录锁定原因。
  • Git 2.42.0+：add --orphan。

用 git --version 确认本机版本；日常使用建议 2.17 以上，需要在移动仓库后修复关联则建议 2.29 以上。
